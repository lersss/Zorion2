# Правила написания кода для агента

> Подгружается автоматически через `opencode.json` → `instructions`. Открывать вручную не нужно — файл уже в контексте.
> Организационные правила проекта (приоритеты, коммиты, несколько агентов) — `AGENTS.md` §4. Здесь только поведение при написании кода.
> Источник: `github.com/multica-ai/andrej-karpathy-skills`, `CLAUDE.md`.

**Обновлено:** 2026-09-11

**Компромисс:** эти правила смещают баланс в сторону осторожности, а не скорости. На тривиальных задачах — по ситуации.

---

## 1. Думать до кода

**Не домысливать. Не прятать непонимание. Проговаривать компромиссы.**

До реализации:

- Излагать предположения явно. Сомневаешься — спроси.
- Есть несколько трактовок — показать все, а не выбрать молча.
- Есть решение проще — сказать об этом. Возражать, когда есть основания. Это действует на **любую** задачу, а не только на текущую: возражение или сомнение к любому запросу озвучивается до исполнения, а не «принимается тихо».
- Что-то неясно — остановиться. Назвать, что именно неясно. Спросить.

## 2. Сначала простота

**Минимум кода, решающий задачу. Ничего спекулятивного.**

- Никаких функций сверх запрошенного.
- Никаких абстракций ради одного места использования.
- Никакой «гибкости» и «настраиваемости», которых не просили.
- Никакой обработки невозможных ситуаций.
- Написал 200 строк там, где хватило бы 50, — переписать.

Вопрос себе: «Сеньор сказал бы, что это переусложнено?» Если да — упростить.

## 3. Хирургические изменения

**Трогать только необходимое. Убирать только за собой.**

При правке существующего кода:

- Не «улучшать» соседний код, комментарии, форматирование.
- Не рефакторить то, что не сломано.
- Следовать существующему стилю, даже если сам сделал бы иначе.
- Заметил посторонний мёртвый код — сказать о нём, а не удалять.

Когда правка порождает висяки:

- Удалять импорты, переменные и функции, которые осиротели именно из-за твоей правки.
- Не удалять ранее существовавший мёртвый код без запроса.

Проверка: каждая изменённая строка должна прямо выводиться из запроса пользователя.

## 4. Работа от цели

**Определить критерий успеха. Итерировать до подтверждения.**

Превращать задачи в проверяемые цели:

- «Добавить валидацию» → «написать тесты на невалидный вход, затем сделать их зелёными»
- «Починить баг» → «написать тест, воспроизводящий баг, затем сделать его зелёным»
- «Отрефакторить X» → «убедиться, что тесты проходят до и после»

Для многошаговых задач — короткий план:

```
1. [Шаг] → проверка: [чем]
2. [Шаг] → проверка: [чем]
3. [Шаг] → проверка: [чем]
```

Сильный критерий успеха позволяет итерировать самостоятельно. Слабый («чтобы работало») заставляет постоянно переспрашивать.

В этом проекте критерий по умолчанию для правок Go — definition of done из `AGENTS.md` §2.

---

**Правила работают, если:** в дифах меньше лишних изменений, меньше переделок из-за переусложнения, а уточняющие вопросы появляются до реализации, а не после ошибок.
