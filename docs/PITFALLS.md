## БД и шелл

- **`TRUNCATE ... CASCADE` запрещён.** Работает на уровне таблиц, а не строк,
  и игнорирует `ON DELETE SET NULL`. Однажды снёс таблицу `users` с паролями
  целиком. Только `TRUNCATE` без CASCADE + явный список + временное снятие FK.
  Разбор: `internal/handlers/admin_universe.go`, `clearUniverseTx`, `ARCHITECTURE.md` §4.1.

- **NULL-спектр экзотики роняет `Scan` в любой выборке `worlds.spectral_class`.**
  Экзотика (ЧД/НЗ/WD/протозвезда) пишет NULL в `spectral_class` (спека `99.2.4` §3),
  и `rows.Scan(&w.SpectralClass)` на NULL падает — строка молча выпадает из
  результата. Любой новый SQL по `worlds` обязан читать
  `COALESCE(spectral_class,'')` (образцы: `repository/world_repository.go`
  `worldColumns`, `handlers/admin_stats_load.go`, `mapcache/snapshot.go`,
  `handlers/planet_handler.go`).

- **`/admin/stats` кэшируется.** Отдал 318 257 планет при 319 573 в БД.
  Для точных цифр — SQL, не эндпоинт.

- **После массовой генерации вселенной нужен `VACUUM (ANALYZE) planets`.**
  Без него карта видимости холодная, `Index Only Scan` фильтров карты даёт
  тысячи heap fetches: `has_life` 306 мс вместо 63. В миграцию не положить —
  `VACUUM` не работает внутри транзакции.

- **`GeneratePlanets` сам очищает старые планеты** (`DELETE FROM planets` в
  начале генерации, каскад безопасен). Баг B11 закрыт 2026-09-12; ручная чистка
  перед перегенерацией больше не нужна.

- **Кэш статистики после перегенерации.** `GenerateUniverse` кэширует «0 планет»
  (планет на тот момент нет — корректно), `GeneratePlanets` сбрасывает кэш
  в начале генерации и пересчитывает в конце (~20 сек на 318k планет) — в окне
  пересчёта вкладка статистики считает заново при каждом запросе. Кнопка
  «Обновить» (`?refresh=1`) сбрасывает кэш принудительно.

- ~~**Две таблицы ресурсов**~~ — снято 2026-09-12. Legacy-таблица `resources`
  удалена (коммит `f69d991`), вселенная очищена. `substances`/`deposits`
  (миграция `000017`) созданы и пусты; решено убить и пересоздать по итогам
  перевывода номенклатуры (`docs/gamedesign/99_roadmap.md` §99.2.5).

- **Windows-шелл: кодировка cp866/cp1251 ломает вывод psql и curl.** В
  PowerShell 5.1 на русской Windows вывод `psql.exe` / `curl.exe` кодируется
  в cp866/cp1251 — при выводе в stdout ломаются русские буквы, а при передаче
  аргументов через `cmd /c` PowerShell экранирует кавычки и `*` не как bash,
  а как glob-шаблон Windows. Неисправимо на уровне оформления — это среда.
  **Как работать:**
  - **psql:** писать SQL-запросы во временный `.sql`-файл (`Set-Content -Encoding
    UTF8`) и вызывать `cmd /c "C:\pgsql\pgsql\bin\psql.exe -h 127.0.0.1 -U
    zorion -d zorion -f C:\path\q.sql"` — НЕ передавать `-c` с unicode-текстом
    в PowerShell (psql получает разбитые аргументы). Пароль — через
    `$env:PGPASSWORD="zorion123"` перед вызовом.
  - **HTTP-запросы к dev-серверу:** использовать `Invoke-RestMethod` (не
    `Invoke-WebRequest` в PSReadLine, он может падать). Для авторизации:
    `POST /login` → токен → заголовок `Authorization: Bearer $token`.
  - **curl:** в PowerShell алиас `curl` — это `Invoke-WebRequest`, НЕ реальный
    `curl.exe`. Для нативного curl: `cmd /c "curl.exe http://..."` или
    `& "C:\Windows\System32\curl.exe" ...`.

- **`schema_migrations.version` — TEXT, сортировка лексикографическая.**
  `ORDER BY version DESC` ставит `007` выше `000035` (строка «007» > «000035»).
  Для проверки актуальной миграции — `ORDER BY version::int DESC` либо
  `COUNT(*)` (проверено 2026-09-16 при сверке перед миграцией `000036`).

- **Порядок генерации поселений: человеческий проход стирает поселения рас.**
  `GenerateSettlements` (люди) в начале удаляет ВСЕ поселения
  (`clearSettlementsLayer`, `DELETE FROM settlements`), включая расовые
  (`race_id IS NOT NULL`). Обратный порядок безопасен: проход рас
  (`GenerateRaceSettlements`) удаляет только свой слой (`WHERE race_id IS
  NOT NULL`). Оператору: сначала «Сгенерировать поселения» (люди), потом
  «Сгенерировать поселения рас» — иначе расовые поселения пропадут.
  **Снято 2026-09-17 (65a):** человеческий генератор скрыт (роут
  `/admin/generate-settlements` не регистрируется, кнопка убрана) — расовый
  проход остался единственным путём расселения.

- **PowerShell `Set-Content -Encoding UTF8` портит кириллицу в Go-файлах.**
  PowerShell 5.1 читает файл в системной кодировке (cp1251) и пишет UTF-8 —
  русские комментарии/строки превращаются в «РЅРµРІРѕР·РјРѕР¶РЅС‹С…»
  (двойное кодирование). Проверено 2026-09-17 дважды (race_balancer.go,
  admin_hypothesis_test.go — оба переписаны заново). Правило: правка Go/JS
  файлов с кириллицей — только через редактор (Edit/Write), НЕ через
  PowerShell-команды чтения-записи файлов.

## Go и конкурентность

- **Персистентность полёта игрока (97a): БД-строку `player_flights` удаляет
  ТОЛЬКО актуальный полёт и ПОСЛЕ onArrival.** Три правила
  (`internal/travel/manager.go`): (1) удаление до onArrival = краш между
  DELETE и апдейтом `users.current_world_id` теряет полёт — ровно баг 97a;
  (2) старая горутина редиректа (отменена через CancelChan) БД не трогает —
  строку уже заменил новый StartFlight (Upsert); (3) гвард после onArrival:
  если для пользователя уже зарегистрирован новый полёт — строку НЕ удалять
  (иначе удалишь строку нового сегмента), причём проверка актуальности и
  Delete — под ОДНИМ локом (TOCTOU-фикс ревью 97a: между проверкой и
  удалением новый StartFlight успел бы вставить полёт в map и сделать
  Upsert). `CancelFlight` чистит БД под локом — иначе DELETE мог бы снести
  строку нового полёта, стартовавшего между разблокировкой и удалением.

- **gorilla/websocket: чтение с истёкшим дедлайном необратимо ломает
  соединение.** `Conn.ReadMessage` при ошибке (в т.ч. i/o timeout по
  `SetReadDeadline`) фиксирует `readErr` — все последующие `ReadMessage` на
  этом соединении сразу возвращают ту же ошибку, продление дедлайна не
  помогает. В тестах «сообщение не приходит в интервале» нельзя читать с
  коротким таймаутом, а потом продолжать читать то же соединение — для
  негативной проверки использовать отдельное соединение/тест, либо проверять
  дроссель на уровне логики (в Zorion — юнит-тесты `NotificationBatch`,
  `internal/npc/notification_batch_test.go`).

- **Кэш агентов для позиций (идея 26c A2): любая внешняя мутация `npc_agents`
  без `MarkDirty()` → позиции на карте устаревают НАВСЕГДА.** Позиции карты
  интерполируются из in-memory кэша менеджера (`internal/npc/agent_cache.go`),
  который перезагружается из БД только при dirty-флаге (или старте). Пока
  тик не трогает агента (нет стартов/прибытий), кэш не обновится — если
  хендлер изменил агента мимо тика и не поставил dirty, карта будет показывать
  старое состояние бесконечно (а не до следующего тика, как было при
  `ListAll` на каждый тик). Правило: **каждая точка записи в `npc_agents`
  вне тика обязана вызвать `manager.MarkDirty()`** (или `OnAgentsDeleted()`
  при массовом удалении). Текущие точки: `CreateAgent`/`PatchAgent`/
  `DeleteAgent`/`GenerateNPC` (`internal/handlers/admin_npc.go`),
  `ClearUniverse`/`GenerateUniverse` — TRUNCATE `npc_agents`
  (`internal/handlers/admin_universe.go`, через `SetNPCManager`). Кэш мутирует
  ТОЛЬКО тик (И1): хендлеры — только atomic-флаг, иначе data race (§0).

- **Балансировщик кривых (99.2.17): мини-R читают store на КАЖДОМ вызове,
  GetCurve обязан возвращать копию слайсов.** `HeatTemperatureChangeRate`/
  `ColdChangeRate`/`GravityChangeRate`/`RadiationChangeRate` зовут
  `GetCurve("heat"...)` из `ChangeComponents`, который выполняется во многих
  горутинах (пересчёт населения, смерть, проеция). Store — глобальный
  `RWMutex` (`internal/economy/settlement/balancer_store.go`); `GetCurve`
  возвращает **копии** `nodes`/`bends`, а не внутренние слайсы — иначе
  вызывающий код (напр. `evaluateCurve`) или мутация извне испортил бы store
  без блокировки. `SetCurve`/`ResetCurve` — `Lock` + атомарная замена всей
  кривой (клон). Экстраполяция кривых горизонтальная (константа крайнего
  узла): экстремальные входы (гравитация 1000 g) больше НЕ дают r ≥ 1 — гвард
  Population остаётся страховкой, но не срабатывает от перегрузки (см.
  `TestRGuardCap` в `mortality_test.go`).

- **Тип и переменная пакета не могут называться одинаково.** Спека `99.2.17`
  §5 показывает `type balancerStore struct {...}` + `var balancerStore = &balancerStore{...}`
  — это не компилируется. В коде переменная названа `balancerCurveStore`
  (конвенция как `settings.go`: тип `populationSettings` → var `popSettings`).

- **Пресеты балансировщика (99.2.17 итерация 7): не вызывать `SetCurve`/
  `ResetCurve` из пресет-операций — вложенный `Lock` = deadlock.**
  `SetCurve`/`ResetCurve` сами берут `balancerCurveStore.mu.Lock()`, а пресет-
  операции (`SavePreset`/`ApplyPreset`/`ResetDefaultPreset`) обязаны держать
  ту же блокировку, чтобы store и файл менялись согласованно (§5). Поэтому
  внутри пресет-операций кривая мутируется напрямую
  (`balancerCurveStore.curves[comp] = cloneCurve(...)`), а не через сеттеры.
  `sync.Mutex` не реентрабельный — вложенный Lock убьёт сервер. Файл
  пресетов пишется атомарно (tmp + `os.Rename`) под той же блокировкой;
  ошибка записи — лог, пресеты сессионные (сервер не падает).

- **`galaxy` не может импортировать `planet` (цикл через `planet/twin.go`).**
  Для сортировки пары «главная = самая массивная» (35c) galaxy нужно
  сравнивать массы, а при равенстве/отсутствии массы — светимости (tiebreak,
  `compMassiveThan` — единый источник правила) — но `luminosityBySpectral`
  живёт в `planet/physics.go`, а `planet` импортирует `galaxy` (`twin.go`,
  «Проверка гипотез»). Решение: таблица вынесена в `internal/astro` (единый
  источник), `planet/physics.go` использует её через обёртку
  `luminosityBySpectral` (fallback 1.0 закреплён тестами). Новый общий код
  звёздной физики — только в `internal/astro`.

- **`settlement.Suitable` вызывается в двух разных порядках аргументов.**
  Сигнатура — `Suitable(water, temp, ...)`, так вызывают `descriptions_tags.go`
  (inhabited) и `circumbinary.go` (35b §4.1); но `properties.go` и
  `generateOceanicPlanet` передают `(temp, waterPercent)` — при этом
  `suitable()` проверяет `water-slot < MinWater(10)` и `temp-slot ∈ [200,350]`,
  т.е. у стандартного пути «settleable» фактически всегда false (вода должна
  была бы быть 200–350%). Не-регрессия: менять существующие вызовы — вне
  скоупа; новый код (P-ветка) использует сигнатурный порядок, чтобы
  пригодные P-планеты (спека 35b §4.1) действительно могли быть пригодными.

- **Windows: `time.Now()` имеет гранулярность ~0.5 мс.** Два вызова подряд
  (в пределах одного тика системного таймера) возвращают **одинаковое**
  значение — в тестах сравнение `StartTime` двух последовательных запусков
  через `NotEqual` флейкает. Проверено 2026-09-16 (61a): шаг значений между
  итерациями ~512 мкс, иногда 0. Если тест обязан доказать, что время
  «продвинулось» (напр. полёт перезапущен с новым `start_time`), вставить
  `time.Sleep(5 * time.Millisecond)` между вызовами (см.
  `internal/handlers/travel_handlers_test.go`, `TestStartTravelRedirectInFlight`).

- **Каталог оборудования (спека 77a) — глобальное in-memory состояние
  `internal/ship`.** `RadarRadius`/`HasScanner` читают map, загружаемую
  `ship.LoadCatalog(db)` при старте (или `LoadDefaults()` при пустой БД).
  В юнит-тестах каталог пуст → `RadarRadius` молча возвращает минимум 200 px
  (не 800), тест «стартовый радар → 800» падает. Правило: тест, проверяющий
  радиус/сканер, обязан сначала вызвать `ship.LoadDefaults()` (или
  `LoadCatalog` с sqlmock) — как `newVisibilityHarness` в
  `internal/handlers/visibility_test.go`.

- **Комбинаторный словарь форм арт-студии: полное произведение ~69M строк
  (F2) — юнит-тесту материализовать нельзя.** Спека 67a.1 §11.6 закладывала
  28×25×20×25 = 350k компонентов, но оси `forms.json` выросли (78a/88a/76a)
  до 130 shapes × 107 struct × 89 character × 105 parts — для F2 это
  ~69M комбинаций: `TestFormsFor` шёл 98 с и ел ~4 ГБ (под `-race` — таймаут).
  Вторая половина причины — `strings.NewReplacer` на КАЖДУЮ комбинацию
  (884 ns/ит, ~60% стоимости; разбор шаблона один раз + конкатенация —
  50 ns/ит, 17.7x, `parsePhraseTemplate` в `cmd/art-studio/generator/prompt.go`).
  Урок: юнит-тест проверяет ЛОГИКУ (шаблон + фильтр категорий), а не объём
  данных — ортогональные оси (struct/character/parts) в тесте урезаются до
  3 элементов, реальные shapes/template остаются (`prompt_test.go`,
  `TestFormsFor`).

- **`filterPool` арт-студии (98a) — чистый фильтр БЕЗ фолбека; фолбек — на
  вызывающей стороне.** Если «упростить» и вернуть исходный пул при пустом
  результате внутри `filterPool` (`cmd/art-studio/generator/prompt.go`), тихо
  сломаются две вещи: (1) структурное правило «раса-не-существо» (§5.3) —
  проверка `len(filterPool(anthro/beast, blocked)) == 0` перестанет срабатывать
  (пул «не пуст» из-за фолбека) и планктону/роям вернётся морф-ветка с лицом;
  (2) акценты палитры (§5.2 п.5) — «все отфильтрованы → акцент не добавляется»
  превратится в «вернулись тёплые акценты холодной расе». Фолбек применяется
точечно: character/parts → исходный пул, морф-пулы → глобальные формы морфа,
   акценты → НЕ фолбечат.

- **Windows: `os.Rename` поверх открытого файла падает «Access is denied» —
  атомарная запись `status.json` арт-студии застревает.** `WriteStatus`
  (`cmd/art-studio/generator/worker.go`) пишет tmp + rename; читатель
  (UI-поллинг `/status` каждые 3 с, тесты) держит `status.json` открытым
  микросекунды — rename в это окно падает, файл остаётся на старом значении:
  UI видит «running» вечно (финальная запись Running=false потеряна). Проверено
  2026-09-18 (98b-дополнение 2): воспроизводилось на `-race`-тестах джобов
  (n=3, 5 записей статуса за ~40 мс). Фикс: rename ретраится 5×5 мс (окно
  читателя короткое). Тест-хелпер `waitJobDone` дополнительно требует
  существования `status.json` — иначе при упавшей стартовой записи тест
  вернулся бы раньше, чем джоб дописал файлы пула (гонка с `t.TempDir()`
  cleanup).

## Дизайн и числа

- **Каталог реальных веществ (`internal/resource/real.go`, идея 2026-09-18 §4б):
  сублимация — механическое правило `TBoil <= TMelt`, и оно НЕ совпадает
  с «*» в таблице оценки.** У графита/алмаза из таблицы §4б T_boil > T_melt
  (3800/3900, 4000/4500) — механически НЕ сублимирующие, хотя помечены «*»
  (реальные графит/алмаз сублимируют при нормальном давлении, но оцифровка
  даёт T_melt < T_boil). He/He-3 (кламп 10/10 K) механически «сублимирующие» —
  артефакт клампа, не физика. Числа различимости: оценка §4а 92/110/40,
  фактические на каталоге §4б — **86/107/43** (кросс-семейные коллизии
  N₂↔благородные газы, природный газ↔метан, T₂↔алканы, SO₂/NO₂/NO; T-порог
  ≥ 10 K не разрешает природный газ↔метан (разница 1–2 K) и H₂↔D₂↔T₂ (2–7 K);
  оценка 110 предполагала «любое различие T»). Тест `distance_test.go`
  закрепляет фактические числа — не «чинить» его под оценку.

- **Окна потребления (94a) — включительные: границы входят в интервал.**
  Иначе генератор полноты «все накормлены» (§8.1) даёт ложные дыры на
  граничных значениях каталога: №16/18/19/20 хим 60 = нижняя граница ГРД
  [60,100]; №17 T_melt 350 = верхняя граница ОРГ [250,350]; №14 T_boil 400 =
  граница ВОД [350,400] и ОРГ [400,600]. Проверка попадания профиля в окно —
  `>= Lo && <= Hi`, не строгие неравенства (`internal/resource/checks.go`,
  `Interval.Contains`).

- **Температура: в данных — Кельвины, в UI — везде °C.** `planet.data.temperature`
  и Go-модели хранят K. В UI температура отображается только в °C
  (хелпер `kelvinToCelsius` в `web/static/js/modal/tabs.js`; в форме поселений
  конверсия `K = °C + 273` в `web/static/js/admin/generation.js`,
  `buildSettlementModel`). Значение в K — максимум как уточнение в скобках,
  но не в приоритете. Реестр полей близнецов (`settlement/fields.go`) хранит
  рамку температуры тоже в °C — серверная валидация `TwinSpec.Validate`
  сверяет оверрайд как `(K − 273)`, иначе 2500 K < 2227 °C прошло бы молча
  (99.2.15).

- ~~**Жёсткий ноль смертности → λ = +Inf**~~ — **снято 2026-09-14 (99.2.13)**.
  Холод/гравитация/радиация переведены на рекурсивные R-компоненты, полюса-
  обнуления и severity-механизм убраны: никакая температура/гравитация не даёт
  λ = +Inf. `MaxSerializedLambda`/`ClampLambda` остаются на будущее (страховка
  от переполнения), но +Inf в расчёте больше не возникает.

- **R-модель изменения населения: Δt строго в СЕКУНДАХ.** `Population(p0, r,
  Δt_сек)` = `p0·(1−r)^Δt_сек` (99.2.12 + 99.2.13 + 99.2.16,
  `change_components.go`):
  r — сумма всех рекурсивных компонент за 1 секунду (R_ест + R_рожд + R_жара +
  R_холод + R_гравитация + R_радиация; R_ест = 1/СПЖ, дефолт 50 лет ≈
  6.34·10⁻¹⁰/сек; R_рожд = −k·R_ест, k — коэффициент рождаемости, дефолт 2,
  нетто (1−k)/СПЖ; обе ручки — из админки, `internal/economy/settlement/
  settings.go`);
  R_total ∈ [0, 1) для убыли, < 0 — рост), на JSON —
  `r_per_sec`; `lambda_per_hour` всегда 0 (`omitempty`, ранее `decay_lambda`,
  переименовано 2026-09-14; λ-механизм убран с 99.2.13).
  Порог «p < 1 → 0» (поселение мёртвое);
  возрастной потолок 120 лет **удалён** (99.2.16, решение создателя
  2026-09-15: возраст поселения ни на что не влияет, `MaxLifespanSeconds` из
  кода убран, при росте/равновесии r ≤ 0 поселение живёт бесконечно);
  `NDead` остаётся механизмом 18_needs (не температурным). Клиент
  (`extrapolate.js`) считает `pow(1−r, Δt_сек)` — не перепутать с `exp(−λ·Δt)`.
  **Гвард `r < 1`** (99.2.13, замечание баланс-тестера): гравитационная
  степенная неограничена сверху (при g ≳ 550 R_в > 1) → при суммарном r ≥ 1
  `pow(1−r, Δt)` дал бы отрицательное основание = NaN; гвард: r ≥ 1 →
  мгновенная гибель (p = 0 при Δt > 0) либо кламп r = min(r, 1−ε). Рост r < 0
  разрешён (обрезка только сверху).

- **Жёсткий ноль как порог-переключатель → разрыв непрерывности** (пример
  Quinvarom 101/100 K: 1 K разницы — «3.6 сут» → «0»). Эталон создателя
  2026-09-14 (`18a_population_death.md`, §Эталоны (FAQ)): порог-переключатель
  запрещён — скорость изменения населения должна сходиться к нулю плавно
  (асимптота,
  «ноль = насыщение»), либо разрыв явно обосновать. Кандидаты формул и числа —
  `docs/specs/99.2.12-temperature-mortality-calibration.md`, §Плавная
  сходимость у жёсткого нуля.

- ~~**Полюсная форма B: guard `dev ≥ HardZero → +Inf` обязателен ДО вычисления
  severity**~~ — **снято 2026-09-14 (99.2.13)**. Полюсная форма B
  (`TwoSidedSeverity`/`OneSidedSeverity`, `mortality.go`) была действующей для
  холода; холод переведён на рекурсивную R_холод (гладкая двухрежимная
  сшивка) — severity-механизм и полюса из расчёта населения **удалены**.
  Функции могут остаться в коде только как история/тесты; в расчёте
  `ChangeComponents` не участвуют.

- **«Событие» против «лог» — разбирай природу сущности до ТЗ, а не после
  дизайна.** В фиче «события в карточке поселения» (2026-09-14) «вымерло»
  спроектировали как два поля у поселения (`died_at`/`death_cause`) — «сущность
  ради одного факта». Создатель заметил, что это не событие (происшествие), а
  **лог** (результат, в который перешло состояние), и что записей/типов будет
  много, возможно у разных объектов (звёзды, игроки, рынки) — нужна таблица
  записей, не поля. Урок: при добавлении сущности/хранилища сначала разбирать
  природу (событие/лог/атрибут), владельца (один/многие объекты) и
  расширяемость (один/много типов); менеджер **предлагает модель создателю, а
  не ждёт подсказки**. Механизм — «Архитектурный фильтр приёмки» в
  `.opencode/agents/manager.md`; сверка с архитектурой при проектировании
  сущностей — в `.opencode/agents/designer.md`. Разбор:
  `docs/gamedesign/ideas/16a...md`, `18b_settlement_log.md` §«Лог поселения».

- **`planets.data` НЕ едет в API сам: `populatePlanetFromJSON` — whitelist.**
  Спека 35b §2.3 предполагала «JSONB приезжает автоматически» — но API
  флаттенит `planets.data` через `models.Planet` + `populatePlanetFromJSON`
  (`internal/repository/planet_repo.go`), и любой новый ключ data без правки
  модели и маппера молча пропадает из `/api/worlds/{id}/planets` (блокер
  тестера, 2026-09-15: `orbit_center`/`orbit_radius_au`/`circumbinary` были
  null). Правило: новый ключ в `planets.data` → поле в `models.Planet` +
  строка в `populatePlanetFromJSON` (фолбэки — там же, по 35b §2.4).

- **Пригодность для людей (Settleable, тег inhabited) зависит от каталога рас.**
  С 65a `res.Settleable` и `inhabited` считаются через `races.HumansSuitable`
  (`internal/generator/planet/cascade.go`, `descriptions_tags.go`) — карточка
  `humans` из `config/races.json`. Если каталог не загружен (`ByID("humans")`
  → nil), `HumansSuitable` возвращает **false** — все планеты становятся
  непригодными, поселения не генерируются. В проде каталог грузится в
  `main.go` до генерации; в юнит-тестах пакета planet — `TestMain`
  (`testmain_test.go`). Новый код, читающий пригодность людей, обязан
  учитывать эту зависимость (не «улучшать» `HumansSuitable` до встроенной
  карточки — единый источник — каталог).

- **Раздача рас потребляет `g.rng` в `generateWorldsPoisson`** (shuffle 50 био-рас; роботы 51–60 раздаются жадным рассеиванием без rng, 99.2.24 §5). Один и тот же seed даёт разные миры при загруженном
  каталоге рас (`config/races.json`) и без него (в юнит-тестах каталог не
  загружен — no-op, rng не тратится). Детерминизм сохраняется внутри одного
  состояния каталога; «золотых» значений миров по seed нет — в проде seed
  случайный (`time.Now().UnixNano()`).

- **Точные значения планет НЕ детерминированы между прогонами одного seed**
  (99.2.20, проверено при тестах подкрутки рас 99.2.22): генерация композиции
  (`applyRandomJitter`, `resolveConflicts` в `composition_modifiers.go`/
  `composition_conflicts.go`) потребляет `rng` в порядке итерации map, а Go
  рандомизирует порядок итерации — роллы достаются разным формам, число
  роллов в `resolveConflicts` тоже плавает. Детерминизм по seed держится
  только на уровне «тот же seed → то же распределение/те же ручки подкрутки»,
  НЕ на уровне точных значений планеты. Тесты детерминизма сравнивают вывод
  подкрутки (`raceTunePlanet`) или RNG-поток, а не `planet.data` целиком
  (UUID планет/спутников тоже случайны — не часть seed).

- **Расовые R-кривые (99.2.23): кламп Y «≤ 0.999» из спеки невалиден —
  валидация требует y < 0.999.** Спека §3.3 пишет «кламп Y ≤ 0.999 — гвард,
  как в validateCurve», но `validateCurve`/`validateRaceCurve` отклоняют
  y = 0.999 (y ∈ [0, 0.999)). При `applyResilienceScale` (масштаб 50/resilience,
  максимум человеческой кривой 0.98 × 1.43 = 1.40) кламп на ровно 0.999 даёт
  невалидную запись — запись расы пропускается при загрузке (лог), раса
  инициализируется заново из карточки. Кламп — строго ниже: `0.999 − 1e-9`
  (проверено на saltfolk: resilience 40 → 0.9799 × 1.25 = 1.22).

- **Расовые R-кривые (99.2.23): «нулевой узел» гравитации — по порогу
  |Y| < 1e-9, не по точному == 0.** `raceGravityBranch` (`death.go`) ищет
  комфорт-интервал кривой гравитации по нулевым Y узлам; ручная правка
  комфорта в балансер-UI пишет не ровный 0, а ~1e-14 (лог-шкала canvas,
  `Y_MIN = 1e-12` в %), и точное `Y == 0` уводило в fallback на человеческие
  границы 0.8/1.2 — причина гибели классифицировалась неверно (gravity_high
  вместо gravity_low и наоборот). Порог 1e-9 отделяет «почти ноль» комфорта
  от веток (минимум низкой ветки ≈ 1.4e-8 после ResilienceScale).

- **У роботов (99.2.24, 51–60) `consumption` пуст — инвариант «сумма = 100»
  к ним не применяется.** Слой роботов — блок `robotic` (энергия + сырьё:
  power_source/materials/heat), 13 биоосей не заполняются. Любой код, который
  итерирует `races.Catalog()` и предполагает consumption у каждой расы
  (сумма 100, непустые ключи), молча сломается на роботах. Отличить робота:
  `race.Robotic != nil`. Валидация (`Race.Validate`) пропускает сумму-100 для
  роботов, но проверяет robotic-блок (enum power_source/heat, 6 категорий,
  10 осей) и `territory == "conditions"`. Тесты с жёстким «50 рас» в каталоге
  (например, `require.Len(t, races.Catalog(), 50)`) при добавлении рас
  обновлять на актуальное число (60).

## Фронт и UI

- **Браузерный WebSocket API не умеет кастомные заголовки.** WS-ручки,
  закрытые `AuthMiddleware` (только заголовок `Authorization`), в браузере
  недостижимы — `new WebSocket(url)` всегда получит 401 и уйдёт в реконнект.
  Решение в Zorion: для пути `/ws` middleware принимает токен в query
  (`?token=JWT`) — ограничено ТОЛЬКО этим путём (остальные ручки не
  расширены), см. `internal/auth/middleware.go`. При добавлении новых
  WS-ручек учитывать: либо query-токен, либо subprotocol (Bearer с пробелом
  в subprotocol невалиден — токен передавать без префикса).

- **Перекраска спрайта через `globalCompositeOperation='hue'` НЕ сохраняет
  альфу: фон красится в цвет заливки.** Blend-режим 'hue' для прозрачных
  пикселей берёт цвет заливки — без восстановления альфы получаются цветные
  квадраты вместо кораблей (найдено на живом демо 2026-09-16, спека 61b §5.3).
  Обязательная последовательность в `recolorShipSprite`
  (`web/static/js/map/ship_sprites.js`): `drawImage(спрайт)` →
  `gCO='hue'` → `fillRect(цвет)` → `gCO='destination-in'` →
  `drawImage(оригинал)` (вернуть альфу) → `gCO='source-over'`. Кэш по ключу
  «спрайт|цвет», лениво; `color = null` — исходный Image без перекраски.

- **Hit-область объекта на канвасе обязана совпадать с отрисовкой (экранный
  минимум радиуса).** В модалке системы (70a, найдено тестером 2026-09-17)
  звезда на низком зуме рисуется с экранным минимумом `MIN_STAR_PX`
  (`Math.max(s.radius, MIN_STAR_PX / zoom)` в `modal_render.js`), а hit-тест
  в `events.js` сравнивал с голым `s.radius + 8` в мировых координатах — на
  wide-зуме (~0.0007) hit-область была ≈0.04 px при нарисованных 4 px, тултип
  и клик по компаньону не срабатывали (83% бинарных систем — wide). Правило:
  hit-тест использует тот же радиус, что рендер
  (`Math.max(s.radius, MIN_STAR_PX / modalState.zoom) + 8`); константа
  экспортируется из `modal_render.js` — не дублировать.

## Прочее

- **opencode serve: контракт HTTP-API (студия товаров 99a.1 §7.5, белое пятно
  спеки — решено на разработке).** Локальный opencode (`opencode serve`, порт
  по умолчанию 4096; в `config/goods/studio.json` — `opencode_url`) отдаёт
  OpenAPI-спеку на `/doc`. Рабочий путь «заполнить комплектующие»:
  `POST {url}/session` → `{id}`; `POST {url}/session/{id}/message` с телом
  `{model, parts:[{type:"text", text: prompt}]}` → `{info, parts[]}` — текст
  ответа собирается из `parts` с `type=="text"`. Модель передаётся явно в теле
  (решение создателя: «модель должна быть явно указана»). 5xx/сетевые ошибки —
  retryable (`max_retries`), 4xx/парсинг — нет. Реализация:
  `cmd/goods-studio/ai/client.go`.
  **`default_agent` из `opencode.json` ломает fill:** проект задаёт
  `"default_agent": "manager"` — сессия без явного агента отвечает приветствием
  менеджера (7 векторов), а не JSON-составом: fill падает «invalid character
  looking for beginning of value». Фикс: в теле message передавать
  `"agent": ""` (пустая строка = сырая модель, проверено живым прогоном
  2026-09-19). Модель (deepseek-v4-flash) при этом иногда возвращает не-JSON —
  ретрай fill лечит (транзиентно).

- **Go не читал `.env` автоматически → `JWT_SECRET` «плавал» между рестартами**

  рабочего каталога), либо задать `JWT_SECRET` в env явно.
