# docs/PITFALLS.md — ловушки проекта, проверенные на практике

> Сюда добавляют после того, как упёрлись в проблему и разобрались.
> Дублировать в `AGENTS.md` или `STATUS.md` не нужно (один факт — одно место).

- **`TRUNCATE ... CASCADE` запрещён.** Работает на уровне таблиц, а не строк,
  и игнорирует `ON DELETE SET NULL`. Однажды снёс таблицу `users` с паролями
  целиком. Только `TRUNCATE` без CASCADE + явный список + временное снятие FK.
  Разбор: `internal/handlers/admin_universe.go`, `clearUniverseTx`, `ARCHITECTURE.md` §4.1.

- **NULL-спектр экзотики роняет `Scan` в любой выборке `worlds.spectral_class`.**
  Экзотика (ЧД/НЗ/WD/протозвезда) пишет NULL в `spectral_class` (спека `99.2.4` §3),
  и `rows.Scan(&w.SpectralClass)` на NULL падает — строка молча выпадает из
  результата. Любой новый SQL по `worlds` обязан читать
  `COALESCE(spectral_class,'')` (образцы: `repository/world_repository.go`
  `worldColumns`, `handlers/admin_stats_load.go`, `mapcache/snapshot.go`,
  `handlers/planet_handler.go`).

- **`/admin/stats` кэшируется.** Отдал 318 257 планет при 319 573 в БД.
  Для точных цифр — SQL, не эндпоинт.

- **После массовой генерации вселенной нужен `VACUUM (ANALYZE) planets`.**
  Без него карта видимости холодная, `Index Only Scan` фильтров карты даёт
  тысячи heap fetches: `has_life` 306 мс вместо 63. В миграцию не положить —
  `VACUUM` не работает внутри транзакции.

  `config/anomalies/`. Не ориентируйся на него.

- **Go не читал `.env` автоматически → `JWT_SECRET` «плавал» между рестартами**
  (баг 21a). До фикса сервер читал `JWT_SECRET` только из `os.Getenv`
  (`internal/config/config.go:48`); при ручном запуске бинаря `zorion-server.exe`
  секрет задавался «на глаз» — при каждом рестарте он мог отличаться, все
  выданные ранее токены умирали (401), фронт чистил localStorage и разлогинивал.
  Исправлено: в начале `main()` (`cmd/server/main.go`) вызывается
  `godotenv.Load()` ДО `config.Load()` — `JWT_SECRET`/`DATABASE_URL`/`REDIS_URL`
  берутся из `.env` единообразно. Поведение: уже заданные переменные окружения
  имеют приоритет (godotenv их не перетирает); отсутствие `.env` — только
  лог-предупреждение, не fatal (прод задаёт env иначе: Docker/Amvera).
  Соглашение: запускать сервер **из корня репо** (godotenv читает `.env` из
  рабочего каталога), либо задать `JWT_SECRET` в env явно.

- ~~**Жёсткий ноль смертности → λ = +Inf**~~ — **снято 2026-09-14 (99.2.13)**.
  Холод/гравитация/радиация переведены на рекурсивные R-компоненты, полюса-
  обнуления и severity-механизм убраны: никакая температура/гравитация не даёт

- **R-модель изменения населения: Δt строго в СЕКУНДАХ.** `Population(p0, r,
  Δt_сек)` = `p0·(1−r)^Δt_сек` (99.2.12 + 99.2.13 + 99.2.16,
  `change_components.go`):
  r — сумма всех рекурсивных компонент за 1 секунду (R_ест + R_рожд + R_жара +
  R_холод + R_гравитация + R_радиация; R_ест = 1/СПЖ, дефолт 50 лет ≈
  6.34·10⁻¹⁰/сек; R_рожд = −k·R_ест, k — коэффициент рождаемости, дефолт 2,
  нетто (1−k)/СПЖ; обе ручки — из админки, `internal/economy/settlement/
  settings.go`);
  R_total ∈ [0, 1) для убыли, < 0 — рост), на JSON —
  `r_per_sec`; `lambda_per_hour` всегда 0 (`omitempty`, ранее `decay_lambda`,
  переименовано 2026-09-14; λ-механизм убран с 99.2.13).
  Порог «p < 1 → 0» (поселение мёртвое);
  возрастной потолок 120 лет **удалён** (99.2.16, решение создателя
  2026-09-15: возраст поселения ни на что не влияет, `MaxLifespanSeconds` из
  кода убран, при росте/равновесии r ≤ 0 поселение живёт бесконечно);
  `NDead` остаётся механизмом 18_needs (не температурным). Клиент
  (`extrapolate.js`) считает `pow(1−r, Δt_сек)` — не перепутать с `exp(−λ·Δt)`.
  **Гвард `r < 1`** (99.2.13, замечание баланс-тестера): гравитационная
  степенная неограничена сверху (при g ≳ 550 R_в > 1) → при суммарном r ≥ 1
  `pow(1−r, Δt)` дал бы отрицательное основание = NaN; гвард: r ≥ 1 →
  мгновенная гибель (p = 0 при Δt > 0) либо кламп r = min(r, 1−ε). Рост r < 0
  разрешён (обрезка только сверху).

- **Жёсткий ноль как порог-переключатель → разрыв непрерывности** (пример
  Quinvarom 101/100 K: 1 K разницы — «3.6 сут» → «0»). Эталон создателя

  запрещён — скорость изменения населения должна сходиться к нулю плавно
  (асимптота,
  «ноль = насыщение»), либо разрыв явно обосновать. Кандидаты формул и числа —
  `docs/specs/99.2.12-temperature-mortality-calibration.md`, §Плавная
  сходимость у жёсткого нуля.

- **«Событие» против «лог» — разбирай природу сущности до ТЗ, а не после
  дизайна.** В фиче «события в карточке поселения» (2026-09-14) «вымерло»
  спроектировали как два поля у поселения (`died_at`/`death_cause`) — «сущность
  ради одного факта». Создатель заметил, что это не событие (происшествие), а
  **лог** (результат, в который перешло состояние), и что записей/типов будет
  много, возможно у разных объектов (звёзды, игроки, рынки) — нужна таблица
  записей, не поля. Урок: при добавлении сущности/хранилища сначала разбирать
  природу (событие/лог/атрибут), владельца (один/многие объекты) и
  расширяемость (один/много типов); менеджер **предлагает модель создателю, а
  не ждёт подсказки**. Механизм — «Архитектурный фильтр приёмки» в
  `.opencode/agents/manager.md`; сверка с архитектурой при проектировании
  сущностей — в `.opencode/agents/designer.md`. Разбор:
  `docs/gamedesign/ideas/16a...md`, `18a_population_death.md` §«Лог поселения».

- **Bootstrap skycomposer не меняет пароль существующей учётки.** Если
  `SKYCOMPOSER_BOOTSTRAP_USERNAME` совпадает с уже существующим пользователем,
  бутстрап только повышает роль — `SKYCOMPOSER_BOOTSTRAP_PASSWORD` игнорируется
  (спека 99.2.14 §5, п. 2). При проверке на dev-БД это выглядит как «логин

  отдельной учётки через раздел «Пользователи» (или SQL на dev).

- **Windows-шелл: кодировка cp866/cp1251 ломает вывод psql и curl.** В
  PowerShell 5.1 на русской Windows вывод `psql.exe` / `curl.exe` кодируется
  в cp866/cp1251 — при выводе в stdout ломаются русские буквы, а при передаче
  аргументов через `cmd /c` PowerShell экранирует кавычки и `*` не как bash,
  а как glob-шаблон Windows. Неисправимо на уровне оформления — это среда.
  **Как работать:**
  - **psql:** писать SQL-запросы во временный `.sql`-файл (`Set-Content -Encoding
    UTF8`) и вызывать `cmd /c "C:\pgsql\pgsql\bin\psql.exe -h 127.0.0.1 -U
    zorion -d zorion -f C:\path\q.sql"` — НЕ передавать `-c` с unicode-текстом
    в PowerShell (psql получает разбитые аргументы). Пароль — через
    `$env:PGPASSWORD="zorion123"` перед вызовом.
  - **HTTP-запросы к dev-серверу:** использовать `Invoke-RestMethod` (не
    `Invoke-WebRequest` в PSReadLine, он может падать). Для авторизации:
    `POST /login` → токен → заголовок `Authorization: Bearer $token`.
  - **curl:** в PowerShell алиас `curl` — это `Invoke-WebRequest`, НЕ реальный
    `curl.exe`. Для нативного curl: `cmd /c "curl.exe http://..."` или
    `& "C:\Windows\System32\curl.exe" ...`.

- **gorilla/websocket: чтение с истёкшим дедлайном необратимо ломает
  соединение.** `Conn.ReadMessage` при ошибке (в т.ч. i/o timeout по
  `SetReadDeadline`) фиксирует `readErr` — все последующие `ReadMessage` на
  этом соединении сразу возвращают ту же ошибку, продление дедлайна не
  помогает. В тестах «сообщение не приходит в интервале» нельзя читать с
  коротким таймаутом, а потом продолжать читать то же соединение — для
  негативной проверки использовать отдельное соединение/тест, либо проверять
  дроссель на уровне логики (в Zorion — юнит-тесты `NotificationBatch`,
  `internal/npc/notification_batch_test.go`).

- **Браузерный WebSocket API не умеет кастомные заголовки.** WS-ручки,
  закрытые `AuthMiddleware` (только заголовок `Authorization`), в браузере
  недостижимы — `new WebSocket(url)` всегда получит 401 и уйдёт в реконнект.
  Решение в Zorion: для пути `/ws` middleware принимает токен в query
  (`?token=JWT`) — ограничено ТОЛЬКО этим путём (остальные ручки не
  расширены), см. `internal/auth/middleware.go`. При добавлении новых
  WS-ручек учитывать: либо query-токен, либо subprotocol (Bearer с пробелом
  в subprotocol невалиден — токен передавать без префикса).

- **Кэш агентов для позиций (идея 26c A2): любая внешняя мутация `npc_agents`
  без `MarkDirty()` → позиции на карте устаревают НАВСЕГДА.** Позиции карты
  интерполируются из in-memory кэша менеджера (`internal/npc/agent_cache.go`),
  который перезагружается из БД только при dirty-флаге (или старте). Пока
  тик не трогает агента (нет стартов/прибытий), кэш не обновится — если
  хендлер изменил агента мимо тика и не поставил dirty, карта будет показывать
  старое состояние бесконечно (а не до следующего тика, как было при
  `ListAll` на каждый тик). Правило: **каждая точка записи в `npc_agents`
  вне тика обязана вызвать `manager.MarkDirty()`** (или `OnAgentsDeleted()`
  при массовом удалении). Текущие точки: `CreateAgent`/`PatchAgent`/
  `DeleteAgent`/`GenerateNPC` (`internal/handlers/admin_npc.go`),
  `ClearUniverse`/`GenerateUniverse` — TRUNCATE `npc_agents`
  (`internal/handlers/admin_universe.go`, через `SetNPCManager`). Кэш мутирует
  ТОЛЬКО тик (И1): хендлеры — только atomic-флаг, иначе data race (§0).

- **Балансировщик кривых (99.2.17): мини-R читают store на КАЖДОМ вызове,
  GetCurve обязан возвращать копию слайсов.** `HeatTemperatureChangeRate`/
  `ColdChangeRate`/`GravityChangeRate`/`RadiationChangeRate` зовут
  `GetCurve("heat"...)` из `ChangeComponents`, который выполняется во многих
  горутинах (пересчёт населения, смерть, проеция). Store — глобальный
  `RWMutex` (`internal/economy/settlement/balancer_store.go`); `GetCurve`
  возвращает **копии** `nodes`/`bends`, а не внутренние слайсы — иначе
  вызывающий код (напр. `evaluateCurve`) или мутация извне испортил бы store
  без блокировки. `SetCurve`/`ResetCurve` — `Lock` + атомарная замена всей
  кривой (клон). Экстраполяция кривых горизонтальная (константа крайнего
  узла): экстремальные входы (гравитация 1000 g) больше НЕ дают r ≥ 1 — гвард
  Population остаётся страховкой, но не срабатывает от перегрузки (см.
  `TestRGuardCap` в `mortality_test.go`).
- **Тип и переменная пакета не могут называться одинаково.** Спека `99.2.17`
  §5 показывает `type balancerStore struct {...}` + `var balancerStore = &balancerStore{...}`
  — это не компилируется. В коде переменная названа `balancerCurveStore`
  (конвенция как `settings.go`: тип `populationSettings` → var `popSettings`).

- **Пресеты балансировщика (99.2.17 итерация 7): не вызывать `SetCurve`/
  `ResetCurve` из пресет-операций — вложенный `Lock` = deadlock.**
  `SetCurve`/`ResetCurve` сами берут `balancerCurveStore.mu.Lock()`, а пресет-
  операции (`SavePreset`/`ApplyPreset`/`ResetDefaultPreset`) обязаны держать
  ту же блокировку, чтобы store и файл менялись согласованно (§5). Поэтому
  внутри пресет-операций кривая мутируется напрямую
  (`balancerCurveStore.curves[comp] = cloneCurve(...)`), а не через сеттеры.
  `sync.Mutex` не реентрабельный — вложенный Lock убьёт сервер. Файл
  пресетов пишется атомарно (tmp + `os.Rename`) под той же блокировкой;
  ошибка записи — лог, пресеты сессионные (сервер не падает).

- **SVG-спрайт схемы корабля: `currentColor` без `style="color:"` на корневом
  `<svg>` рисуется чёрным.** Детали кораблей (спека 99.2.15) — `fill="currentColor"`;
  при композиции цвет кладётся ТОЛЬКО в `style="color:{color}"` корневого
  `<svg>` (`web/static/js/map/ship_render.js`, `composeShipSVG`) — иначе
  в data-URL-картинке спрайт полностью чёрный (нет «одного цвета корабля»,
  И1). Акценты с явным `fill` (кабина/сопло/огни) от этого не зависят.
  Тот же приём на клиенте админки (`web/static/js/admin/ships.js`).

- **`schema_migrations.version` — TEXT, сортировка лексикографическая.**
  `ORDER BY version DESC` ставит `007` выше `000035` (строка «007» > «000035»).

- **`galaxy` не может импортировать `planet` (цикл через `planet/twin.go`).**
  Для сортировки пары «главная = самая массивная» (35c) galaxy нужно
  сравнивать массы, а при равенстве/отсутствии массы — светимости (tiebreak,
  `compMassiveThan` — единый источник правила) — но `luminosityBySpectral`
  живёт в `planet/physics.go`, а `planet` импортирует `galaxy` (`twin.go`,
  «Проверка гипотез»). Решение: таблица вынесена в `internal/astro` (единый
  источник), `planet/physics.go` использует её через обёртку
  `luminosityBySpectral` (fallback 1.0 закреплён тестами). Новый общий код
  звёздной физики — только в `internal/astro`.

- **`settlement.Suitable` вызывается в двух разных порядках аргументов.**
  Сигнатура — `Suitable(water, temp, ...)`, так вызывают `descriptions_tags.go`
  (inhabited) и `circumbinary.go` (35b §4.1); но `properties.go` и
  `generateOceanicPlanet` передают `(temp, waterPercent)` — при этом
  `suitable()` проверяет `water-slot < MinWater(10)` и `temp-slot ∈ [200,350]`,
  т.е. у стандартного пути «settleable» фактически всегда false (вода должна
  была бы быть 200–350%). Не-регрессия: менять существующие вызовы — вне
  скоупа; новый код (P-ветка) использует сигнатурный порядок, чтобы
  пригодные P-планеты (спека 35b §4.1) действительно могли быть пригодными.

- **`planets.data` НЕ едет в API сам: `populatePlanetFromJSON` — whitelist.**
  Спека 35b §2.3 предполагала «JSONB приезжает автоматически» — но API
  флаттенит `planets.data` через `models.Planet` + `populatePlanetFromJSON`
  (`internal/repository/planet_repo.go`), и любой новый ключ data без правки
  модели и маппера молча пропадает из `/api/worlds/{id}/planets` (блокер
  тестера, 2026-09-15: `orbit_center`/`orbit_radius_au`/`circumbinary` были
  null). Правило: новый ключ в `planets.data` → поле в `models.Planet` +
  строка в `populatePlanetFromJSON` (фолбэки — там же, по 35b §2.4).
