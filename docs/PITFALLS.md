## БД и шелл

- **`TRUNCATE ... CASCADE` запрещён.** Работает на уровне таблиц, а не строк,
  и игнорирует `ON DELETE SET NULL`. Однажды снёс таблицу `users` с паролями
  целиком. Только `TRUNCATE` без CASCADE + явный список + временное снятие FK.
  Разбор: `internal/handlers/admin_universe.go`, `clearUniverseTx`, `ARCHITECTURE.md` §4.1.

- **NULL-спектр экзотики роняет `Scan` в любой выборке `worlds.spectral_class`.**
  Экзотика (ЧД/НЗ/WD/протозвезда) пишет NULL в `spectral_class` (спека `99.2.4` §3),
  и `rows.Scan(&w.SpectralClass)` на NULL падает — строка молча выпадает из
  результата. Любой новый SQL по `worlds` обязан читать
  `COALESCE(spectral_class,'')` (образцы: `repository/world_repository.go`
  `worldColumns`, `handlers/admin_stats_load.go`, `mapcache/snapshot.go`,
  `handlers/planet_handler.go`).

- **`/admin/stats` кэшируется.** Отдал 318 257 планет при 319 573 в БД.
  Для точных цифр — SQL, не эндпоинт.

- **После массовой генерации вселенной нужен `VACUUM (ANALYZE) planets`.**
  Без него карта видимости холодная, `Index Only Scan` фильтров карты даёт
  тысячи heap fetches: `has_life` 306 мс вместо 63. В миграцию не положить —
  `VACUUM` не работает внутри транзакции.

- **`GeneratePlanets` сам очищает старые планеты** (`DELETE FROM planets` в
  начале генерации, каскад безопасен). Баг B11 закрыт 2026-09-12; ручная чистка
  перед перегенерацией больше не нужна.

- **Кэш статистики после перегенерации.** `GenerateUniverse` кэширует «0 планет»
  (планет на тот момент нет — корректно), `GeneratePlanets` сбрасывает кэш
  в начале генерации и пересчитывает в конце (~20 сек на 318k планет) — в окне
  пересчёта вкладка статистики считает заново при каждом запросе. Кнопка
  «Обновить» (`?refresh=1`) сбрасывает кэш принудительно.

- ~~**Две таблицы ресурсов**~~ — снято 2026-09-12. Legacy-таблица `resources`
  удалена (коммит `f69d991`), вселенная очищена. `substances`/`deposits`
  (миграция `000017`) созданы и пусты; решено убить и пересоздать по итогам
  перевывода номенклатуры (`docs/gamedesign/99_roadmap.md` §99.2.5).

- **Windows-шелл: кодировка cp866/cp1251 ломает вывод psql и curl.** В
  PowerShell 5.1 на русской Windows вывод `psql.exe` / `curl.exe` кодируется
  в cp866/cp1251 — при выводе в stdout ломаются русские буквы, а при передаче
  аргументов через `cmd /c` PowerShell экранирует кавычки и `*` не как bash,
  а как glob-шаблон Windows. Неисправимо на уровне оформления — это среда.
  **Как работать:**
  - **psql:** писать SQL-запросы во временный `.sql`-файл (`Set-Content -Encoding
    UTF8`) и вызывать `cmd /c "C:\pgsql\pgsql\bin\psql.exe -h 127.0.0.1 -U
    zorion -d zorion -f C:\path\q.sql"` — НЕ передавать `-c` с unicode-текстом
    в PowerShell (psql получает разбитые аргументы). Пароль — через
    `$env:PGPASSWORD="zorion123"` перед вызовом.
  - **HTTP-запросы к dev-серверу:** использовать `Invoke-RestMethod` (не
    `Invoke-WebRequest` в PSReadLine, он может падать). Для авторизации:
    `POST /login` → токен → заголовок `Authorization: Bearer $token`.
  - **curl:** в PowerShell алиас `curl` — это `Invoke-WebRequest`, НЕ реальный
    `curl.exe`. Для нативного curl: `cmd /c "curl.exe http://..."` или
    `& "C:\Windows\System32\curl.exe" ...`.

- **`schema_migrations.version` — TEXT, сортировка лексикографическая.**
  `ORDER BY version DESC` ставит `007` выше `000035` (строка «007» > «000035»).
  Для проверки актуальной миграции — `ORDER BY version::int DESC` либо
  `COUNT(*)` (проверено 2026-09-16 при сверке перед миграцией `000036`).

- **PostgreSQL `lower()` НЕ конвертирует кириллицу при collation `C`.** БД
  `zorion` создана с `datcollate = C` — `lower('Лаборатория')` возвращает
  `'Лаборатория'` без изменений (работает только ASCII). Проверено 2026-09-21
  (миграция `000051`): data-миграция по `name_norm` молча не сработала —
  `WHERE name_norm = lower('Лаборатория корабельных модулей')` не нашёл строку
  (в БД `'лаборатория корабельных модулей'`), а INSERT создал «Лабораторию» с
  заглавной буквой в `name_norm`. Правило: в SQL-миграциях сравнивать
  `name_norm` **литералами нижнего регистра** (их пишет Go
  `graph.NormalizeName` = `strings.ToLower`, Unicode-корректный), НЕ через
  `lower()`. Проверка: `SELECT lower('Лаборатория')` на целевой БД.

- **Номер миграции может быть занят параллельной работой между проверкой
  `docs/DB.md` и созданием файла.** Проверено 2026-09-20 (фабрики релиз 1):
  задача давала дроп `production_units` как 000049 (последний в DB.md —
  000047), но параллельная спека 99.2.30 (composite-route) уже создала
  `000049_add_users_pending_destination.sql` — сервер упал на старте
  «duplicate key value violates unique constraint schema_migrations_pkey»
  (две миграции с версией 000049, вторая не записалась). Правило: перед
  созданием миграции проверять **рабочее дерево** (`Get-ChildItem migrations/`),
  а не только `docs/DB.md`; при конфликте — брать следующий свободный номер
  (дроп ушёл в 000050, как в спеке §11.6).

- **Порядок генерации поселений: человеческий проход стирает поселения рас.**
  `GenerateSettlements` (люди) в начале удаляет ВСЕ поселения
  (`clearSettlementsLayer`, `DELETE FROM settlements`), включая расовые
  (`race_id IS NOT NULL`). Обратный порядок безопасен: проход рас
  (`GenerateRaceSettlements`) удаляет только свой слой (`WHERE race_id IS
  NOT NULL`). Оператору: сначала «Сгенерировать поселения» (люди), потом
  «Сгенерировать поселения рас» — иначе расовые поселения пропадут.
  **Снято 2026-09-17 (65a):** человеческий генератор скрыт (роут
  `/admin/generate-settlements` не регистрируется, кнопка убрана) — расовый
  проход остался единственным путём расселения.

- **PowerShell `Set-Content -Encoding UTF8` портит кириллицу в Go-файлах.**
  PowerShell 5.1 читает файл в системной кодировке (cp1251) и пишет UTF-8 —
  русские комментарии/строки превращаются в «РЅРµРІРѕР·РјРѕР¶РЅС‹С…»
  (двойное кодирование). Проверено 2026-09-17 дважды (race_balancer.go,
  admin_hypothesis_test.go — оба переписаны заново), 2026-09-21 — на
  Python-скрипте (`tools/spike_ship_sprite_flight.py`: `Get-Content -Raw` +
  `-replace` + `Set-Content -Encoding UTF8` превратил кириллицу в мусор и
  добавил BOM). Правило: правка Go/JS/**Python** файлов с кириллицей — только
  через редактор (Edit/Write), НЕ через PowerShell-команды чтения-записи
  файлов (даже для «одной строки» — `-replace`).

- **cmd.exe режет аргументы по `=` — фейковый python/.cmd в тестах получает
  разбитые аргументы.** `cmd /c "script.cmd --spec=C:\x\in.json"` даёт
  `%1=--spec`, `%2=C:\x\in.json` (не `%1=--spec=C:\x\in.json`). Проверено
  2026-09-20 (ships-races-generator): фейковый python для джоба кораблей
  (`--spec=<json> --out=<png>`) не находил файл `--spec` — аргумент был
  разрезан. Реальный python.exe (Go `exec.Command` без cmd) получает
  `--spec=...` целиком — ловушка только для `.cmd`-фейков и ручных вызовов
  через `cmd /c`. Правило: `.cmd`-фейк в тестах обрабатывает split-форму
  (`if "%2"=="--spec"` → `copy %3 %5`), а не `--spec=` целиком
  (`cmd/art-studio/generator/ships_job_test.go`, `writeFakeShipPython`).

- **Windows: `exec.CommandContext` + таймаут не спасает, если внук держит
  пайп вывода.** `cmd.Wait()`/`CombinedOutput` ждут EOF пайпа, а `Kill()` по
  таймауту убивает только прямой процесс (`cmd.exe`), не внука (`ping`/python)
  — ответ «по таймауту» задерживается на всё время жизни внука. Проверено
  2026-09-21 (подсказка носа кораблей `/ships/auto`): тест с 300 мс таймаутом
  возвращался ~3 с. Фикс: `cmd.WaitDelay = 2 * time.Second` (Go 1.20+) —
  после отмены контекста Wait закрывает пайпы через WaitDelay и возвращает
  `ErrWaitDelay`; в фейке внук не должен наследовать пайп (`>nul 2>&1`).
  Действует для любого `exec.CommandContext` с таймаутом на Windows.

- **Сторож `TestTruncateTablesCoverMigrationFK` приписывает `REFERENCES` после
  последнего `CREATE TABLE` этой таблице.** Проверено 2026-09-22 (миграция
  `000061_money.sql`): `ALTER TABLE npc_agents ... REFERENCES factions(id)` стоял
  ПОСЛЕ `CREATE TABLE money_operations` — парсер теста (`reCreate` ищет
  `CREATE TABLE`, блок тянется до следующего `CREATE` или EOF) отнёс FK к
  `money_operations` и потребовал её в `truncateTables`. Реальная FK — от
  `npc_agents` (обе таблицы уже в списке). Правило: `ALTER ... REFERENCES`
  в миграции ставить **до** первого `CREATE TABLE` (или добавлять таблицу в
  `truncateTables` осознанно) — иначе сторож падает на ложном срабатывании.

## Go и конкурентность

- **Go: тег JSON на строке с несколькими полями применяется ко ВСЕМ полям
  строки.** `TMin, TMax float64 json:"t_min,omitempty"` — оба поля получают
  тег `t_min`: `TMax` молча не читает `"t_max"` из JSON (остаётся 0), а
  `TMin` конкурирует с `TMax` за ключ `t_min`. Проверено 2026-09-20
  (99.2.28, biome_catalog.go): T-диапазоны биомов читались как 0, крио-биомы
  не рождались. Правило: каждое поле — на своей строке со своим тегом
  (`TMin float64 json:"t_min,omitempty"` / `TMax float64 json:"t_max,omitempty"`).

- **Персистентность полёта игрока (97a): БД-строку `player_flights` удаляет
  ТОЛЬКО актуальный полёт и ПОСЛЕ onArrival.** Три правила
  (`internal/travel/manager.go`): (1) удаление до onArrival = краш между
  DELETE и апдейтом `users.current_world_id` теряет полёт — ровно баг 97a;
  (2) старая горутина редиректа (отменена через CancelChan) БД не трогает —
  строку уже заменил новый StartFlight (Upsert); (3) гвард после onArrival:
  если для пользователя уже зарегистрирован новый полёт — строку НЕ удалять
  (иначе удалишь строку нового сегмента), причём проверка актуальности и
  Delete — под ОДНИМ локом (TOCTOU-фикс ревью 97a: между проверкой и
  удалением новый StartFlight успел бы вставить полёт в map и сделать
  Upsert). `CancelFlight` чистит БД под локом — иначе DELETE мог бы снести
  строку нового полёта, стартовавшего между разблокировкой и удалением.

- **Композитный маршрут (99.2.30): Restore-колбэк межзвёздного полёта обязан
  идти через общий `TravelHandlers.ArrivalHandler`, а не через простой
  UPDATE.** Фаза 1 Restore (`travelManager.Restore` в main.go) передаёт
  onArrival-колбэк; если он делает только `UpdateCurrentWorldAndPosition`
  (как было до фикса ревью 2026-09-21), автостарт внутрисистемного сегмента
  по намерению (`users.pending_destination`) не сработает для восстановленного
  полёта: игрок прилетит к звезде, намерение останется в БД и «выстрелит»
  неожиданным intra-стартом при следующем рестарте (намерение-призрак, И6).
  Правило: live-onArrival и Restore-колбэк — один общий `ArrivalHandler`
  (ИП-2 + чтение намерения + автостарт). Вторая ловушка той же зоны:
  автостарт корректен только при `current_world_id == dest.WorldID` (прибытие
  засчитано onArrival до краша); краш между `CancelAtomicWithDestination` и
  `StartFlight` оставляет намерение при current_world_id мира отправления —
  фаза 3а Restore обязана очистить намерение, а не стартовать intra (иначе
  рассинхрон current_world_id/current_position, ИП-1 99.2.27).

- **gorilla/websocket: чтение с истёкшим дедлайном необратимо ломает
  соединение.** `Conn.ReadMessage` при ошибке (в т.ч. i/o timeout по
  `SetReadDeadline`) фиксирует `readErr` — все последующие `ReadMessage` на
  этом соединении сразу возвращают ту же ошибку, продление дедлайна не
  помогает. В тестах «сообщение не приходит в интервале» нельзя читать с
  коротким таймаутом, а потом продолжать читать то же соединение — для
  негативной проверки использовать отдельное соединение/тест, либо проверять
  дроссель на уровне логики (в Zorion — юнит-тесты `NotificationBatch`,
  `internal/npc/notification_batch_test.go`).

- **Кэш агентов для позиций (идея 26c A2): любая внешняя мутация `npc_agents`
  без `MarkDirty()` → позиции на карте устаревают НАВСЕГДА.** Позиции карты
  интерполируются из in-memory кэша менеджера (`internal/npc/agent_cache.go`),
  который перезагружается из БД только при dirty-флаге (или старте). Пока
  тик не трогает агента (нет стартов/прибытий), кэш не обновится — если
  хендлер изменил агента мимо тика и не поставил dirty, карта будет показывать
  старое состояние бесконечно (а не до следующего тика, как было при
  `ListAll` на каждый тик). Правило: **каждая точка записи в `npc_agents`
  вне тика обязана вызвать `manager.MarkDirty()`** (или `OnAgentsDeleted()`
  при массовом удалении). Текущие точки: `CreateAgent`/`PatchAgent`/
  `DeleteAgent`/`GenerateNPC` (`internal/handlers/admin_npc.go`),
  `ClearUniverse`/`GenerateUniverse` — TRUNCATE `npc_agents`
  (`internal/handlers/admin_universe.go`, через `SetNPCManager`). Кэш мутирует
  ТОЛЬКО тик (И1): хендлеры — только atomic-флаг, иначе data race (§0).

- **Балансировщик кривых (99.2.17): мини-R читают store на КАЖДОМ вызове,
  GetCurve обязан возвращать копию слайсов.** `HeatTemperatureChangeRate`/
  `ColdChangeRate`/`GravityChangeRate`/`RadiationChangeRate` зовут
  `GetCurve("heat"...)` из `ChangeComponents`, который выполняется во многих
  горутинах (пересчёт населения, смерть, проеция). Store — глобальный
  `RWMutex` (`internal/economy/settlement/balancer_store.go`); `GetCurve`
  возвращает **копии** `nodes`/`bends`, а не внутренние слайсы — иначе
  вызывающий код (напр. `evaluateCurve`) или мутация извне испортил бы store
  без блокировки. `SetCurve`/`ResetCurve` — `Lock` + атомарная замена всей
  кривой (клон). Экстраполяция кривых горизонтальная (константа крайнего
  узла): экстремальные входы (гравитация 1000 g) больше НЕ дают r ≥ 1 — гвард
  Population остаётся страховкой, но не срабатывает от перегрузки (см.
  `TestRGuardCap` в `mortality_test.go`).

- **Тип и переменная пакета не могут называться одинаково.** Спека `99.2.17`
  §5 показывает `type balancerStore struct {...}` + `var balancerStore = &balancerStore{...}`
  — это не компилируется. В коде переменная названа `balancerCurveStore`
  (конвенция как `settings.go`: тип `populationSettings` → var `popSettings`).

- **Пресеты балансировщика (99.2.17 итерация 7): не вызывать `SetCurve`/
  `ResetCurve` из пресет-операций — вложенный `Lock` = deadlock.**
  `SetCurve`/`ResetCurve` сами берут `balancerCurveStore.mu.Lock()`, а пресет-
  операции (`SavePreset`/`ApplyPreset`/`ResetDefaultPreset`) обязаны держать
  ту же блокировку, чтобы store и файл менялись согласованно (§5). Поэтому
  внутри пресет-операций кривая мутируется напрямую
  (`balancerCurveStore.curves[comp] = cloneCurve(...)`), а не через сеттеры.
  `sync.Mutex` не реентрабельный — вложенный Lock убьёт сервер. Файл
  пресетов пишется атомарно (tmp + `os.Rename`) под той же блокировкой;
  ошибка записи — лог, пресеты сессионные (сервер не падает).

- **`galaxy` не может импортировать `planet` (цикл через `planet/twin.go`).**
  Для сортировки пары «главная = самая массивная» (35c) galaxy нужно
  сравнивать массы, а при равенстве/отсутствии массы — светимости (tiebreak,
  `compMassiveThan` — единый источник правила) — но `luminosityBySpectral`
  живёт в `planet/physics.go`, а `planet` импортирует `galaxy` (`twin.go`,
  «Проверка гипотез»). Решение: таблица вынесена в `internal/astro` (единый
  источник), `planet/physics.go` использует её через обёртку
  `luminosityBySpectral` (fallback 1.0 закреплён тестами). Новый общий код
  звёздной физики — только в `internal/astro`.

- **`settlement.Suitable` вызывается в двух разных порядках аргументов.**
  Сигнатура — `Suitable(water, temp, ...)`, так вызывают `descriptions_tags.go`
  (inhabited) и `circumbinary.go` (35b §4.1); но `properties.go` и
  `generateOceanicPlanet` передают `(temp, waterPercent)` — при этом
  `suitable()` проверяет `water-slot < MinWater(10)` и `temp-slot ∈ [200,350]`,
  т.е. у стандартного пути «settleable» фактически всегда false (вода должна
  была бы быть 200–350%). Не-регрессия: менять существующие вызовы — вне
  скоупа; новый код (P-ветка) использует сигнатурный порядок, чтобы
  пригодные P-планеты (спека 35b §4.1) действительно могли быть пригодными.

- **Windows: `time.Now()` имеет гранулярность ~0.5 мс.** Два вызова подряд
  (в пределах одного тика системного таймера) возвращают **одинаковое**
  значение — в тестах сравнение `StartTime` двух последовательных запусков
  через `NotEqual` флейкает. Проверено 2026-09-16 (61a): шаг значений между
  итерациями ~512 мкс, иногда 0. Если тест обязан доказать, что время
  «продвинулось» (напр. полёт перезапущен с новым `start_time`), вставить
  `time.Sleep(5 * time.Millisecond)` между вызовами (см.

## Дизайн и числа

- **Пятна биомов на картинке планеты (2026-09-20): формула радиуса из спеки
  даёт ~3× перекрытие — крупнейший биом покрывает весь диск.** `blobs()`
  (`internal/generator/planet/planet_image_v2.go`): радиус пятна
  `R_base·sqrt(share/100)·(0.5+rng·0.5)` при `R_base` = радиус диска даёт
  суммарную площадь пятен ~3× площади диска (k_i ∝ share, r_i² ∝ share →
  площадь ∝ share²) — биом с share ≥ 35% покрывает диск целиком, мелкие
  биомы не видны (тест «каждый биом ≥ 1% присутствует» красный). Калибровка:
  `R_base = 0.5·радиус диска` (суммарная площадь ≈ площади диска). Вторая
  ловушка той же функции: растеризация обязана сравнивать расстояние до
  **центра пятна** (`sqrt((x−cx)²+(y−cy)²)`), не до центра диска — иначе
  крупный биом «съедает» всё (проверено на `TestBlobAllocation`).

- **Бюджет долей поверхности планеты (2026-09-21): «остаток → доминирующий
  биом» из спеки ломает бюджет ±30% — доминант получает share + остаток
  (~20–40% диска), бюджет не выполняется ни на одном seed.** «Поле высот +
  регионы» (`surfaceRegions`/`generateBiomeSurface`, `planet_image_v2.go`):
  регионы перекрываются при случайном размещении, остаток (зазоры) по спеке
  уходит доминанту — для состава 40/35/22/3 горы получали 57–85% вместо
  ≤ 52%. Решение: остаток заполняется **ближайшим регионом** (распределяется
  пропорционально долям), а зоны высот — **мягкий байас** (точка вне зоны
  принимается с вероятностью 0.35): жёсткий фильтр зон кластеризует регионы
  в узких зонах (вода в низ-зоне, крио у полюсов) и ломает бюджет. Тест
  `TestSurfaceRegionAllocation` закрепляет бюджет.

- **R-модель изменения населения: Δt строго в СЕКУНДАХ.** `Population(p0, r,
  Δt_сек)` = `p0·(1−r)^Δt_сек` (99.2.12 + 99.2.13 + 99.2.16,
  `change_components.go`):
  r — сумма всех рекурсивных компонент за 1 секунду (R_ест + R_рожд + R_жара +
  R_холод + R_гравитация + R_радиация; R_ест = 1/СПЖ, дефолт 50 лет ≈
  6.34·10⁻¹⁰/сек; R_рожд = −k·R_ест, k — коэффициент рождаемости, дефолт 2,
  нетто (1−k)/СПЖ; обе ручки — из админки, `internal/economy/settlement/
  settings.go`);
  R_total ∈ [0, 1) для убыли, < 0 — рост), на JSON —
  `r_per_sec`; `lambda_per_hour` всегда 0 (`omitempty`, ранее `decay_lambda`,
  переименовано 2026-09-14; λ-механизм убран с 99.2.13).
  Порог «p < 1 → 0» (поселение мёртвое);
  возрастной потолок 120 лет **удалён** (99.2.16, решение создателя
  2026-09-15: возраст поселения ни на что не влияет, `MaxLifespanSeconds` из
  кода убран, при росте/равновесии r ≤ 0 поселение живёт бесконечно);
  `NDead` остаётся механизмом 18_needs (не температурным). Клиент
  (`extrapolate.js`) считает `pow(1−r, Δt_сек)` — не перепутать с `exp(−λ·Δt)`.
  **Гвард `r < 1`** (99.2.13, замечание баланс-тестера): гравитационная
  степенная неограничена сверху (при g ≳ 550 R_в > 1) → при суммарном r ≥ 1
  `pow(1−r, Δt)` дал бы отрицательное основание = NaN; гвард: r ≥ 1 →
  мгновенная гибель (p = 0 при Δt > 0) либо кламп r = min(r, 1−ε). Рост r < 0
  разрешён (обрезка только сверху).

- **Тест ленивого пересчёта населения не должен зависеть от реального Δt**
  (2026-09-21, флак `TestGetPlanetByID`): `RecomputeSettlementPopulation` берёт

  миллион населения убывает 1–2 (`p0·(1−r)^Δt`; при жаре 400 K
  `r ≈ 2.7·10⁻⁴/сек` — ≈0.27 за мс). Лечится сдвигом чек-поинта вперёд

  остаётся точной), либо инъекцией `now` (образец —

  (образец — `planet_repo_settlements_test.go`).

  дизайна.** В фиче «события в карточке поселения» (2026-09-14) «вымерло»
  спроектировали как два поля у поселения (`died_at`/`death_cause`) — «сущность
  ради одного факта». Создатель заметил, что это не событие (происшествие), а
  **лог** (результат, в который перешло состояние), и что записей/типов будет
  много, возможно у разных объектов (звёзды, игроки, рынки) — нужна таблица
  записей, не поля. Урок: при добавлении сущности/хранилища сначала разбирать
  природу (событие/лог/атрибут), владельца (один/многие объекты) и
  расширяемость (один/много типов); менеджер **предлагает модель создателю, а
  не ждёт подсказки**. Механизм — «Архитектурный фильтр приёмки» в
  `.opencode/agents/manager.md`; сверка с архитектурой при проектировании
  сущностей — в `.opencode/agents/designer.md`. Разбор:
  `docs/gamedesign/ideas/16a...md`, `18b_settlement_log.md` §«Лог поселения».

- **`planets.data` НЕ едет в API сам: `populatePlanetFromJSON` — whitelist.**
  Спека 35b §2.3 предполагала «JSONB приезжает автоматически» — но API
  флаттенит `planets.data` через `models.Planet` + `populatePlanetFromJSON`
  (`internal/repository/planet_repo.go`), и любой новый ключ data без правки
  модели и маппера молча пропадает из `/api/worlds/{id}/planets` (блокер
  тестера, 2026-09-15: `orbit_center`/`orbit_radius_au`/`circumbinary` были
  null). Правило: новый ключ в `planets.data` → поле в `models.Planet` +
  строка в `populatePlanetFromJSON` (фолбэки — там же, по 35b §2.4).

- **Пригодность для людей (Settleable, тег inhabited) зависит от каталога рас.**
  С 65a `res.Settleable` и `inhabited` считаются через `races.HumansSuitable`
  (`internal/generator/planet/cascade.go`, `descriptions_tags.go`) — карточка
  `humans` из `config/races.json`. Если каталог не загружен (`ByID("humans")`
  → nil), `HumansSuitable` возвращает **false** — все планеты становятся
  непригодными, поселения не генерируются. В проде каталог грузится в
  `main.go` до генерации; в юнит-тестах пакета planet — `TestMain`
  (`testmain_test.go`). Новый код, читающий пригодность людей, обязан
  учитывать эту зависимость (не «улучшать» `HumansSuitable` до встроенной
  карточки — единый источник — каталог).

- **Раздача рас потребляет `g.rng` в `generateWorldsPoisson`** (shuffle 50 био-рас; роботы 51–60 раздаются жадным рассеиванием без rng, 99.2.24 §5). Один и тот же seed даёт разные миры при загруженном
  каталоге рас (`config/races.json`) и без него (в юнит-тестах каталог не
  загружен — no-op, rng не тратится). Детерминизм сохраняется внутри одного
  состояния каталога; «золотых» значений миров по seed нет — в проде seed
  случайный (`time.Now().UnixNano()`).

- **Точные значения планет НЕ детерминированы между прогонами одного seed**
  (99.2.20, проверено при тестах подкрутки рас 99.2.22): генерация композиции
  (`applyRandomJitter`, `resolveConflicts` в `composition_modifiers.go`/
  `composition_conflicts.go`) потребляет `rng` в порядке итерации map, а Go
  рандомизирует порядок итерации — роллы достаются разным формам, число
  роллов в `resolveConflicts` тоже плавает. Детерминизм по seed держится
  только на уровне «тот же seed → то же распределение/те же ручки подкрутки»,
  НЕ на уровне точных значений планеты. Тесты детерминизма сравнивают вывод
  подкрутки (`raceTunePlanet`) или RNG-поток, а не `planet.data` целиком
  (UUID планет/спутников тоже случайны — не часть seed).

- **Расовые R-кривые (99.2.23): кламп Y «≤ 0.999» из спеки невалиден —
  валидация требует y < 0.999.** Спека §3.3 пишет «кламп Y ≤ 0.999 — гвард,
  как в validateCurve», но `validateCurve`/`validateRaceCurve` отклоняют
  y = 0.999 (y ∈ [0, 0.999)). При `applyResilienceScale` (масштаб 50/resilience,
  максимум человеческой кривой 0.98 × 1.43 = 1.40) кламп на ровно 0.999 даёт
  невалидную запись — запись расы пропускается при загрузке (лог), раса
  инициализируется заново из карточки. Кламп — строго ниже: `0.999 − 1e-9`
  (проверено на saltfolk: resilience 40 → 0.9799 × 1.25 = 1.22).

- **Расовые R-кривые (99.2.23): «нулевой узел» гравитации — по порогу
  |Y| < 1e-9, не по точному == 0.** `raceGravityBranch` (`death.go`) ищет
  комфорт-интервал кривой гравитации по нулевым Y узлам; ручная правка
  комфорта в балансер-UI пишет не ровный 0, а ~1e-14 (лог-шкала canvas,
  `Y_MIN = 1e-12` в %), и точное `Y == 0` уводило в fallback на человеческие
  границы 0.8/1.2 — причина гибели классифицировалась неверно (gravity_high
  вместо gravity_low и наоборот). Порог 1e-9 отделяет «почти ноль» комфорта
  от веток (минимум низкой ветки ≈ 1.4e-8 после ResilienceScale).

- **У роботов (99.2.24, 51–60) `consumption` пуст — инвариант «сумма = 100»
  к ним не применяется.** Слой роботов — блок `robotic` (энергия + сырьё:
  power_source/materials/heat), 13 биоосей не заполняются. Любой код, который
  итерирует `races.Catalog()` и предполагает consumption у каждой расы
  (сумма 100, непустые ключи), молча сломается на роботах. Отличить робота:
  `race.Robotic != nil`. Валидация (`Race.Validate`) пропускает сумму-100 для
  роботов, но проверяет robotic-блок (enum power_source/heat, 6 категорий,
  10 осей) и `territory == "conditions"`. Тесты с жёстким «50 рас» в каталоге
  (например, `require.Len(t, races.Catalog(), 50)`) при добавлении рас
  обновлять на актуальное число (60).

- **Каскад 99.2.20 самоподобен по √L** — орбиты нормированы так, что «номер
  орбиты» = одни условия у любой звезды. Любая новая величина, зависящая от `r`,
  не должна ещё раз зависеть от светимости: скрытый множитель `L^0.75` (масса
  брала `r^1.5` при `r ∝ √L`) дал плоские полки «ровно 0.10» и «ровно 8.00».

- **Списание `accounts.balance` без урезания `withdrawable` отвергается CHECK
  (деньги, 2026-09-22).** Инвариант `CHECK (withdrawable <= balance)` (спека
  `2026-09-22-деньги-и-эскроу` §3.3): `withdrawable` — подмножество `balance`.
  При **трате/прочей трате** (покупка, обычный расход) `withdrawable` урезается
  до нового баланса в том же операторе: `withdrawable = LEAST(withdrawable,
  balance - amount)` — иначе строка с `withdrawable > нового balance` даст ошибку
  CHECK. В `SET` используются значения строки ДО `UPDATE`
  (`LEAST(withdrawable, balance - $3)`) — это и нужно. Образец —
  `internal/repository/account_repository.go`, `debitAccountSQL`.
  **Запирание залога — ДРУГАЯ формула (метка не сгорает, а переносится на
  контракт, §3.3):** `e = LEAST(withdrawable, amount)`,
  `withdrawable = withdrawable - e`, `balance = balance - amount`, а `e` пишется
  в `contracts.escrow_withdrawable`; возврат — `+amount` к `balance` и
  `+escrow_withdrawable` к `withdrawable` (метка восстанавливается). Выпуск
  (`escrow_release`, оплата труда) — метка сгорает: автору в `withdrawable` не
  возвращается, исполнителю подряда — `+withdrawable` (обычному — только
  `balance`). Не применять формулу траты к запиранию.

## Фронт и UI

- **Браузерный WebSocket API не умеет кастомные заголовки.** WS-ручки,
  закрытые `AuthMiddleware` (только заголовок `Authorization`), в браузере
  недостижимы — `new WebSocket(url)` всегда получит 401 и уйдёт в реконнект.
  Решение в Zorion: для пути `/ws` middleware принимает токен в query
  (`?token=JWT`) — ограничено ТОЛЬКО этим путём (остальные ручки не
  расширены), см. `internal/auth/middleware.go`. При добавлении новых
  WS-ручек учитывать: либо query-токен, либо subprotocol (Bearer с пробелом
  в subprotocol невалиден — токен передавать без префикса).

- **Перекраска спрайта через `globalCompositeOperation='hue'` НЕ сохраняет
  альфу: фон красится в цвет заливки.** Blend-режим 'hue' для прозрачных
  пикселей берёт цвет заливки — без восстановления альфы получаются цветные
  квадраты вместо кораблей (найдено на живом демо 2026-09-16, спека 61b §5.3).
  Обязательная последовательность в `recolorShipSprite`
  (`web/static/js/map/ship_sprites.js`): `drawImage(спрайт)` →
  `gCO='hue'` → `fillRect(цвет)` → `gCO='destination-in'` →
  `drawImage(оригинал)` (вернуть альфу) → `gCO='source-over'`. Кэш по ключу
  «спрайт|цвет», лениво; `color = null` — исходный Image без перекраски.

- **Hit-область объекта на канвасе обязана совпадать с отрисовкой (экранный
  минимум радиуса).** В модалке системы (70a, найдено тестером 2026-09-17)
  звезда на низком зуме рисуется с экранным минимумом `MIN_STAR_PX`
  (`Math.max(s.radius, MIN_STAR_PX / zoom)` в `modal_render.js`), а hit-тест
  в `events.js` сравнивал с голым `s.radius + 8` в мировых координатах — на
  wide-зуме (~0.0007) hit-область была ≈0.04 px при нарисованных 4 px, тултип
  и клик по компаньону не срабатывали (83% бинарных систем — wide). Правило:
  hit-тест использует тот же радиус, что рендер
  (`Math.max(s.radius, MIN_STAR_PX / modalState.zoom) + 8`); константа
  экспортируется из `modal_render.js` — не дублировать.

- **Браузер кэширует картинки пула арт-студии по URL — после перегенерации
  с теми же именами (s01..sNN) превью показывает старые.** `loadShipsList`
  (`cmd/art-studio/web/index.html`) дифф-рендерит карточки по `data-file`:
  существующая карточка не пересоздаётся, а `img.src` без параметра остаётся
  тем же URL — браузер отдаёт закэшированную старую картинку. Фикс (2026-09-20):
  cache-busting `?t=<счётчик>` — `shipBust` растёт на каждый «Сгенерировать»
  (не `Date.now()` на каждый 3-сек поллинг — перекачивал бы все картинки вечно);
  src обновляется и у существующих карточек (карточка не пересоздаётся —
  сохраняются кнопки/вердикт). Тот же паттерн в `loadHumans` (`/humans/img/`) —
  при перегенерации пула людей с теми же именами баг воспроизведётся.

- **Аудио-модуль, попадающий в import-граф админки, обязан быть
  Node-безопасным, а звук — активируемым по странице.** `web/static/js/ui/sound.js`
  тянется в админку через `ui/toast.js`, а `web/frontend_test.go`
  (`TestAdminFrontendLoadsInNode`) исполняет граф `admin/main.js` в Node под
  DOM-стабом **без** `AudioContext`. Правило: ни одного обращения к
  `document`/`AudioContext`/`fetch` на верхнем уровне модуля — `AudioContext`
  создаётся лениво, буферы грузятся по роли внутри функций. Guard — именно
  `typeof AudioContext` (в стабе `window === globalThis`, проверка `window` не
  спасает). Промисы `resume()`/`decodeAudioData`/`fetch` глушить
  (`p.catch(()=>{})`), иначе
  unhandled rejection роняет e2e-смоук `tools/e2e/map-check.js` на любом
  `pageerror`. Админка молчит через **флаг активации**: страница карты зовёт
  `activateSound()`, до этого все play-функции — no-op (общий `ui/toast.js` сам
  по себе звук не включает). Звуки — файлы Kenney CC0 (`web/static/audio/`,
  OGG Vorbis).
  **Гул — только Web Audio, НЕ `<audio loop>` (ловушка 8, баг 2026-09-21):**
  `<audio loop>` вставляет разрыв ~0.3 с на стыке повтора (слышно «рвётся»),
  даже если файл склеен в бесшовный луп. Лечение: `AudioBufferSourceNode` с
  `loop = true`; остановка — ramp `GainNode` в 0 (без щелчка).
  **F5/автоплей (ловушка 7):** `AudioContext` стартует `suspended`; гул, стартовавший
  при инициализации, звучит только после `resume()` на первом жесте. При
  `activateSound()` вешается **одноразовый** слушатель первого жеста
  (`pointerdown`/`keydown`/`touchstart`): делает `resume()` и, если гул был
  запрошен (`humRequested`), поднимает его; после жеста снимает себя.
  Проверено 2026-09-21 (звук отклика и полёта).

- **`formationBlend` (прогулка по поверхности) со смесью `prev+cur+next` рвал
  рельеф на границах регионов.** `web/static/js/surface/surface_world.js`:
  на `local=1` региона `i` вес `wNext=1` давал формацию региона `i+1`, а на
  `local=0` региона `i+1` вес `wPrev=1` давал формацию региона `i` — скачок
  высоты до **~128 px** на 32 из 41 границы (комментарий обещал непрерывность).
  Последствие: парящий камень (`float`) привязан к `terrainHeight`, и на обрыве
  повисал ниже игрока — упор в видимую стену, а сам рельеф читался «обрывом
  мира» каждые 1400 px. Фикс (идея 2026-09-21 §4, 2026-09-21): смесь только
  `prev→cur` на входе региона (`wCur = 1 - wPrev`) — обе стороны границы дают
  одну высоту; смесь на входе (а не на выходе) выбрана, чтобы не менять высоту
  в точке спавна `x=0` (`local=0`). Проверено живым прогоном
  `tools/e2e/surface-walk-check.js` и покадровой симуляцией `Player`.

- **Спавн прогулки ниже корки поверхности = провал в пещеру.** `surface_player.js`
  ставил центр на `terrainHeight(0) − 4`, ноги — на `th+10`, ниже 8-px корки
  `isCave` (`d < 8`). Если под спавном пещера, игрок падал в неё и застревал в
  породе (10f «персонаж идёт» в e2e падал на биомах вроде «Планктонные моря» —
  старая и новая версия одинаково, баг не от правки стен). Фикс: центр на
  `th − h/2 − 2` (ноги у поверхности, корка держит). Проверено симуляцией
  `Player` (планктонные_моря: 28 px → 480 px пути).

- **Мировые сущности перебирать по экранной сетке = дёргание слоёв (прогулка по
  поверхности).** `drawDecor` (`web/static/js/surface/surface_render.js`) шёл по
  экранной сетке `sx += 4`, для точки брал мировую колонку `Math.floor(left + sx)`,
  а рисовал по экранной `sx`: при дробном сдвиге камеры набор опрошенных колонок
  менялся — дерево выпадало из выборки или попадало в соседнюю клетку (за 4 px
  хода ~527 «мерцаний», позиция «дрожала» до 0.9 px). `drawFarRelief` брал ту же
  мелкодетальную `terrainHeight(wx*1.4)` шагом 12 px по экрану — силуэт менял
  форму каждый кадр (до 4 px при 10 px хода). Правило: выборку/перебор мировых
  сущностей вести по **мировой** решётке (шаг в мире), экранную координату брать
  непрерывной `wx − camera.x + vw/2`; дальний план — своя низкочастотная функция
  высоты (`SurfaceWorld.farHeight`, только крупные октавы) на фиксированной
  мировой решётке, тогда при сдвиге камеры на Δ силуэт уезжает цельно на 0.35Δ.
  Проверено чистой геометрией (смещение и форма — бит-в-бит) и e2e
  `tools/e2e/surface-walk-check.js` (14/14) + `surface-admin-biome-check.js` (13/13).

- **Зум прогулки по поверхности: число рисуемых чанков — от ширины вьюпорта и
  зума, не константа.** `drawTerrain`/`drawCreatures`
  (`web/static/js/surface/surface_render.js`) рисовали ±`CHUNK_RADIUS`=3 чанка
  (~1792 px) вокруг камеры, а декор (`visibleDecor`) перебирался по всей ширине
  экрана. На экране шире ~1792 px за краями чанков земли не было, а деревья были —
  висели в пустоте (идея 2026-09-22 §8.3). Плюс общий визуальный масштаб `ZOOM`
  (1.8×, только отрисовка — трансформ камеры в `surface_main.js`; физика
  `PPM`/скорости/гравитация не меняются) сужает видимую ширину мира до `vw/ZOOM`.
  Правило: радиус считать `max(CHUNK_RADIUS, ceil(vw/(2·ZOOM)/CHUNK)+1)`. Канвас —
  в device-пикселях (`devicePixelRatio`), логика — в CSS-пикселях (базовый
  `ctx.setTransform(dpr,…)`, размеры `window.innerWidth/innerHeight`).

- **Апскейл 1:1 кэшированных чанков зумом даёт 1-px шов на стыках.** Билинейная
  выборка края канваса чанка (`drawImage` под `scale(ZOOM)`) на границе сэмплит
  «за» битмапом → полупрозрачная вертикальная полоса каждые `CHUNK·ZOOM` px
  (в скриншоте — тёмный столбец). Фикс: `getChunkCanvas` рендерит канвас на 1
  колонку шире (`CHUNK+1`) с реальными данными следующей мировой колонки —
  перекрытие без искажения. Растянуть `drawImage` (destination `CHUNK+1`) нельзя:
  сдвинет рельеф относительно декора на краю чанка. Проверено замером столбцов
  скриншота (было 2 столбца с перепадом ≥5 на ~460 px шага — стало 0).

- **Отрисовка твёрдого объёма грубым шагом = невидимые стены (парящая порода,
  прогулка по поверхности).** Растр парящей породы в `getChunkCanvas`
  (`web/static/js/surface/surface_render.js`) шёл по x шагом 3 px и рисовал блоки
  3×3 по сэмплу: у твёрдой области оставалась непокрашенной **левая кромка до
  3 px** (первый сэмпл внутри области рисует блок ВПРАВО от себя), плюс сетка
  сэмплов смещалась на `baseX % 3` в каждом чанке. Игрок, идя влево→вправо,
  упирался ровно в непокрашенную кромку — невидимая стена. Правка: растр —
  **надмножество** твёрдой области (`isSolid`). Шаг по x — 1 px, блок 3×3 со
  сдвигом −1 (запас ±1 px по x), по y — полоса сканируется шагом 1 px с запасом
  `FLOAT_BLEED`; у самых границ полосы (`y < th−FLOAT_GAP` / `y > th−FLOAT_SPAN`)
  обязательны **пробы, смещённые внутрь на ε** — граница обрезает блоб, оставляя
  субпиксельные твёрдые полоски, где ни один сэмпл сетки не твёрд. Замер (все 6
  категорий × все формации, все точки коллизий игрока: центр, `x±w/2`, `y±h/2`,
  ground truth — реальный `getChunkCanvas` + `isSolid`): было **5709**
  непокрашенных твёрдых точек (0.609 %, все 9 float-формаций 1.1–1.5 %), стало
  **0**. Цена: генерация чанка ~11.7 → ~20.0 мс (шаг по x 3→1 и по y 3→1);
  кэшируется, на спринте — единичный кадр ~33 мс на генерации нового чанка.

- **Настройки графики карты — в localStorage дашборда, и тумблер мерцания
  обязан гасить непрерывный кадр, а не только эффект.** Вкладка дашборда
  «⚙️ Графика» (`web/static/js/dashboard/graphics.js`, идея 2026-09-22) пишет
  ключи `starVisualPreset`, `starVisualTwinkle`, `starVisualIgnite`,
  `starVisualAdditive`, `starVisualExotic`, `starVisualPetals`,
  `radarBoundaryVariant`, `starVisualLite`; карта (`map/star_render.js`) их
  только читает — общий origin, сервер не участвует. Ловушка: `starVisualOptions()`
  управляет и видом, и эффектами, но непрерывный rAF-кадр поднимают
  `starNeedsAnim()`/`ensureStarAnimLoop()`. Если гасить мерцание только в
  `twinkleFactor()`, `starNeedsAnim()` продолжит поднимать кадр, пока
  `singles ≤ 400`, и слабый ПК будет крутить перерисовку на статичной картинке —
  экономия пропадёт. Режим «Для слабых ПК» (`starVisualLite='1'`) возвращает из
  `starVisualOptions()` `{mode:'sprite', все эффекты false}`, **не трогая**
  сохранённые ключи игрока (выключил режим — вернулись прежние значения). Смена
  вида звёзд в дашборде сама перезаписывает ключи эффектов набором вида
  (`PRESET_EFFECTS`), дальше ручные правки чекбоксов сохраняются. Наборы вида
  (`PRESETS`) и эффектов (`PRESET_EFFECTS`) — в одном чистом модуле данных
  `web/static/js/map/star_presets.js` (без DOM/localStorage на верхнем уровне):
  его импортируют и карта (`map/star_render.js`), и дашборд
  (`dashboard/graphics.js`), иначе дефолты расходятся. Проверено
  `web/frontend_graphics_test.go` (Node) и `tools/e2e/dashboard-graphics-check.js`.

## Прочее

- **blocked_by текстурных тегов кораблей (ship_dict.json) — substring-матчинг
  коллизит с чужими токенами: «ice» в «pumice».** `blockedByMatch`
  (`cmd/art-studio/generator/ship_prompt.go`) исключает тег, если любой токен
  его `blocked_by` — подстрока любого токена `blocked` расы. Токен «ice» у
  холодных тегов («dense frost texture» и др.) ловил «pumice» (пемза) в blocked
  аммиачников — теги ошибочно исключались у расы, которая их НЕ блокирует
  (проверено 2026-09-20, диагноз визуального аудита ammonia). Правило: токен
  `blocked_by` проверять на коллизии со ВСЕМИ blocked-токенами рас, которые
  тег должен получать; при коллизии — брать токен без коллизии (у ледяных
  тегов — `["frost", "snow"]` вместо «ice»: все 26 рас, блокирующих «ice»,
  блокируют и «frost»). Аналогичная коллизия в парсере модулей: «бледный»
  содержит «лед» (б-л-е-д) — холодный стем корпуса «лед» давал ложный
  cold_hull; стемы «лёд»/«ледян» покрывают реальные слова без коллизии.

- **Go-структура с nil-слайсом сериализуется в JSON как `null`, а Python-скрипт
  силуэтов падает на `spec.get('modules', [])`.** `SilhouetteSpecJSON`
  (`cmd/art-studio/generator/ship_prompt.go`) маршалит `SilhouetteSpec.Modules`
  (nil, если в ТЗ нет секции «модули:») в `"modules": null` — скрипт
  `tools/make_ship_silhouettes.py` получал `None` из `.get('modules', [])`
  (ключ есть, значение null) и падал `TypeError: 'NoneType' object is not
  iterable` (проверено 2026-09-20 на пиксельных тестах форм без модулей).
  Правило: Python-чтение опциональных полей spec — `spec.get('modules') or []`
  (и `has_cockpit` — тот же паттерн), не `.get(key, [])`.

- **opencode serve: контракт HTTP-API (студия товаров 99a.1 §7.5, белое пятно
  спеки — решено на разработке).** Локальный opencode (`opencode serve`, порт
  по умолчанию 4096; конфиг — env `OPENCODE_URL/MODEL/TIMEOUT_S/MAX_RETRIES`
  (файл `config/goods/studio.json` удалён, iterC 2026-09-20)) отдаёт
  OpenAPI-спеку на `/doc`. Рабочий путь «заполнить комплектующие»:
  `POST {url}/session` → `{id}`; `POST {url}/session/{id}/message` с телом
  `{model, parts:[{type:"text", text: prompt}]}` → `{info, parts[]}` — текст
  ответа собирается из `parts` с `type=="text"`. Модель передаётся явно в теле
  (решение создателя: «модель должна быть явно указана»). 5xx/сетевые ошибки —
  retryable (`max_retries`), 4xx/парсинг — нет. Реализация:
  `internal/goodsstudio/ai/client.go` (перенос iterC 2026-09-20).
  **`default_agent` из `opencode.json` ломает fill:** проект задаёт
  `"default_agent": "manager"` — сессия без явного агента отвечает приветствием
  менеджера (7 векторов), а не JSON-составом: fill падает «invalid character
  looking for beginning of value». Фикс: в теле message передавать
  `"agent": ""` (пустая строка = сырая модель, проверено живым прогоном
  2026-09-19). Модель (deepseek-v4-flash) при этом иногда возвращает не-JSON —
  ретрай fill лечит (транзиентно).
