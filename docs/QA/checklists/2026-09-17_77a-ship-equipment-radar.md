## Вердикт

**С ОГОВОРКАМИ** — фича работает, инварианты И1/И7/И11 держатся на всех проверенных точках,
но найдено одно отклонение от спеки (сканер за пределами радиуса) и два минорных замечания.

## Найденное (по приоритету)

1. **🟡 Сканер срабатывает на системах ВНЕ радиуса радара** — `internal/handlers/planet_handler.go:91-95`.
   Спека §6.1: «при открытии модалки системы, **находящейся в радиусе радара**, сервер обновляет
   знание»; §1.7: «сканирует планеты **в радиусе действия радара**». Код запускает `ScanSystem`
   для любой доступной системы (в радиусе ИЛИ «зажжённой» знанием) — проверка радиуса для скана
   отсутствует. Проверено живьём: открытие модалки зажжённой Yelal (dist 2005, вне радиуса 400)
   записало свежее знание (scanned_at=now) для всех её планет. Следствие: знание известных
   систем никогда не стареет (игрок обновляет его из любой точки), подрывает И8 (возраст данных)
   и зазор рынка отчётов (И9). Фикс: сканировать только при `IsVisible(...)` (в радиусе), а не
   при `known[worldID]`.

2. **🟢 skycomposer/admin видны в `/api/players/positions` как «игроки»** —
   `internal/handlers/players_positions.go:28` (`PlayerPositions()` выбирает всех пользователей,
   включая role=skycomposer/admin). Спека §5.3 говорит о «чужих игроках»; служебные аккаунты на
   карте игрока — вопрос дизайна (в dev-БД их много, в проде — единицы). Решение за создателем:
   фильтровать по `role='player'` или оставить.

3. **🟢 «Зажигание» не работает для звёзд внутри мульти-кластеров (cnt>1)** —
   `internal/handlers/filter_worlds_handler.go:241`: `known[c.SampleID]` — SampleID заполнен
   только при cnt==1; для cnt>1 SampleID пуст → `known[""]`=false → кластер с известной звездой
   урезается до точки-огонька. Не утечка (безопасное направление), но известная звезда в
   мульти-кластере не «зажигается» до зума, когда кластер распадётся на cnt==1. Минор.

4. **🟢 `IsFresh` без юнит-теста** — `internal/models/knowledge.go:21-23` (протухание 7 дней)
   не покрыто тестом; `PlanetKnowledgeView.SettlementsCount` с `omitempty` — 0 поселений не
   отличить от отсутствия поля (клиент полагается на наличие самого `knowledge`).

## Предложения в чек-лист (для @manager)

- Новая зона «видимость/радар (77a)»: гибрид «звёздное поле» в `/api/worlds/filter` (в радиусе
  полные, за радаром точки-огоньки, знание «зажигает»); 403 `/worlds/{id}`/`/planets`/`/travel`
  вне радиуса; сканер пишет знание при взгляде в радиусе (поверхность + поселения, дата);
  протухание 7 дней (fresh:false при старом scanned_at); `/api/players/positions` — только в
  радиусе; NPC-фильтр по радиусу; админ видит всё.
- Регрессионный кейс на найденный баг №1: открытие модалки зажжённой системы вне радиуса НЕ
  должно обновлять знание (scanned_at не меняется).

## Не проверено (граница покрытия)

- **Живой браузер/UX:** фактический вид границы радара (4 варианта), точек-огоньков, тултипа
  «вне зоны детальной видимости», клика по точке-огоньку, рендера чужих игроков (спрайт+имя).
  Проверено статически (код) и по API; визуальная приёмка — за создателем (гейт §16.6).
- **Протухание в UI:** показ «устарело (дата)» в модалке при fresh:false — путь кода есть
  (`Fresh` в `PlanetKnowledgeView`), но живьём не воспроизведён (ленивый скан обновляет знание
  при взгляде; fresh:false достижим только без сканера или для систем вне радиуса без знания).
- **Экстремальные планеты/спектр NULL:** экзотика (spectral_class NULL) в модалке зажжённой
  звезды — COALESCE в SQL есть (planet_handler.go:44), но живьём не проверял.
- **Два игрока вблизи вживую:** позиции чужих игроков проверены на скоплении тестовых аккаунтов
  в Jinversim; сценарий «два реальных игрока летят навстречу» (интерполяция позиции в полёте)
  покрыт юнит-тестом `TestPlayerPositionInFlight`, живьём не гонял.
