# QA-прогон: студия «Производство» — расовость из фильтра шапки в кнопке «+ тип»

**Дата:** 2026-09-21
**Что проверялось:** правка в `web/studio.html`: функция `prodAdd()` (кнопка
«+ тип» ветки «Производители») теперь подставляет расовость из фильтра шапки —
паритет с уже работающим созданием из пустого слота категории (`doProdCreate`).
Идея `docs/gamedesign/ideas/2026-09-21_студия-расовость-фильтра-при-создании.md`
(§0/§2, решение создателя 2026-09-21 «подставляй»). Дифф (автор — @manager):
после `const body = {name, kind};` добавлено
`if (prodRaceLevel === "family") body.race_family = prodRaceFamily;` и
`if (prodRaceLevel === "race") { body.race_family = raceFamilyOf(prodRace); body.race = prodRace; }`
(`web/studio.html:2394-2397`; зеркало `doProdCreate` — строки 2825-2827).
**Окружение:** сервер `cmd/server` на 127.0.0.1:8080 (`/health`=OK, статика
noCache — рестарт не нужен), БД с каталогом студии, учётка skycomposer
(`skycomposer`/`qa77a_admin_pass`), Chrome headless (playwright-core).
**Обстоятельство окружения:** в студии фоном шёл чужой ИИ-джоб описаний
каталога — он держит **общий флаг И6** с fill (`tryStartDesc`/`tryStartFill`,
`internal/handlers/studio_handlers.go:1583-1589` и `1292-1298`, один
`h.fillMu`/`h.fillGenerating`). Джоб не отменялся и не применялся.
**Независимость:** свой скрипт `tools/e2e/qa-prodadd-race-independent.js` —
водит **реальные** селекты шапки (`#prodRaceLevelSel`/`#prodRaceFamilySel`/
`#prodRaceSel`) и **реальную** кнопку `#btnProdAdd`, а записанное подтверждает
через сервер (`/studio/api/state`, Node fetch вне страницы); видимость читает из
`buildProdTree()` (настоящий построитель дерева), а не из `prodVisible()`.
Скрипт менеджера не перезапускался.
**Проверял:** @tester (deepseek-v4-flash)

## Найденные баги

**Функциональных багов в правке не найдено.** Дифф (`web/studio.html:2394-2397`)
точно повторяет паттерн `doProdCreate` (2825-2827), оба пути создания дают
одинаковый результат на всех трёх уровнях расовости.

Наблюдение (не баг, не регрессия): если выбрать уровень «Семейство»/«Раса», но
не выбрать конкретное значение (селект остаётся на «—», `prodRaceFamily`/
`prodRace` = ""), клиент отправляет `race_family:""`/`race:""`. Сервер принимает
201 и нормализует пустые строки в NULL — запись получается универсальной
(`race_family`/`race` = null). Поведение идентично существующему `doProdCreate`,
деградация безопасная (без 500/400, без ложной расовости). Отдельной задачи не
требует.

## Вердикт: **ПРОЙДЕНО**

Кнопка «+ тип» ветки «Производители» подставляет расовость из фильтра шапки
ровно как создание из пустого слота: «Семейство» → `race_family`=выбранное
семейство, `race`=NULL (п.2); «Раса» → `race`=раса, `race_family`=её семейство
(п.3); «Универсальный» → без расовости (п.4). Созданный на уровне «Семейство»
тип виден в дереве на своём уровне и не виден на «Универсальном» (п.5,
`buildProdTree`), JS-ошибок нет, тестовые записи удалены. Независимый прогон —
**9/9 PASS**. Штатный смоук — 18/20, оба FAIL на fill-шаге 8 из-за чужого
ИИ-джоба (общий флаг И6), к правке отношения не имеют.

**Предложения в чек-лист (для @manager):**
- Кейс (зона «Студия товаров»): «кнопка “+ тип” ветки Производители подставляет
  расовость из фильтра шапки: Семейство → `race_family` без `race`; Раса →
  `race` + её семейство; Универсальный → пусто; созданный на семействе тип виден
  в дереве на этом уровне и не виден на универсальном» (паритет с
  `doProdCreate`).
- Уточнение к существующему fill-кейсу: «fill → 409, пока идёт любой ИИ-джоб
  (общий флаг И6, `tryStartDesc`/`tryStartFill`)» — среда, не баг; прогон fill
  требует свободной студии.
