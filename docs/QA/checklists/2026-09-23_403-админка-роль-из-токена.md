Серверная сверка (curl, роли из БД: `adm1`=admin, `stale`=admin после апгрейда, `sky`=skycomposer):

```
GET /me               (stale_token, role в БД = admin) -> role = "player"   <-- ключ фикса
GET /me               (t1, свежий admin)               -> role = "admin"
GET /me               (t4, свежий skycomposer)         -> role = "skycomposer"
GET /admin/stats      (stale_token)                    -> 403
```

## Чек-лист (жёсткий, каждый пункт ровно один раз)

1. **PASS** — свежий админ (регресс). Учётка через `/register`, роль `admin` в БД, вход `/login` (токен с ролью admin), `/admin` с `localStorage.adminToken`. Оверлей логина скрыт, пройдены все 10 видимых вкладок: `bad4xx=[]`, `toastErrors=[]`, вкладка «Пользователи» скрыта (`display:none`), `pageErrors=[]` (37 запросов `/admin/*`, все < 400).
2. **PASS** — устаревший токен. Токен выдан при роли player, затем роль поднята до admin в БД. `/admin` с этим токеном: `overlayDisplay=flex` (окно входа показано), запросов к `/admin/*` = **0**, 4xx = **0**, тостов = **0**, JS-ошибок = **0**.
3. **PASS** — пере-вход. На той же странице (оверлей логина) введён логин/пароль через UI → свежий токен, оверлей скрыт, все 10 вкладок: `bad4xx=[]`, `toastErrors=[]`, `pageErrors=[]` (22 запроса `/admin/*`).
4. **PASS** — skycomposer (регресс). Вкладка «Пользователи» видна, её открытие → `200 /admin/users?query=&role=&page=1&limit=20` (UI-запрос; отдельно `?page=1&limit=1` = 200 curl'ом), остальные 10 вкладок: `bad4xx=[]`, `toastErrors=[]`, `pageErrors=[]`.

**ИТОГО: 4/4 PASS.** Поведение совпадает с ожиданием: устаревший токен не пускает в админку (сразу окно входа), 403-спама нет.

## Что НЕ проверено (границы покрытия)

- **Обратный сценарий** «токен admin, в БД понижен до player»: спекулятивно не входил в чек-лист. По дизайну фикса токен — источник истины, поэтому UI и ручки согласованы (оба видят admin) — рассинхрона быть не должно, но живой прогон не делал. Закрыть: поднять токен admin, понизить роль в БД, открыть `/admin` — ожидается вход и работа вкладок.
- **Полный обход ручек `/admin/users*`** (создание/смена роли/сброс пароля/удаление) — чек-лист требовал только `GET /admin/users`. Мутирующие операции не гонял (не требовалось; правило 16 — не писать в БД поверх чужих джобов).
- **Экстремальные/долгие состояния** (протухший по TTL токен, роль `player` при живом admin-токене) — только статически по коду; TTL-протухание = известный UX-оверлей, отдельно не воспроизводил.
- **Визуал/UX глазами игрока** — только скриншоты (`tools/e2e/artifacts/qa-admin-role-{1..4}-*.png`); читаемость окна входа не оценивалась.
