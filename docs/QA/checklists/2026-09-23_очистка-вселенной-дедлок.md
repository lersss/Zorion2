## Пункт 3 — ревью логики ретрая (по коду)

- **а) Повтор только `40P01` через `errors.As` на `*pq.Error`** — PASS.
  `isDeadlockErr` (`:117`): `errors.As(err, &pqErr) && pqErr.Code == "40P01"`.
  Ошибки из `clearUniverseTx` обёрнуты `fmt.Errorf(... %w)`, `errors.As` их
  разворачивает. `40001` (serialization) намеренно не ретраится — по ТЗ идеи
  «при необходимости»; на практике TRUNCATE-дедлок даёт `40P01`.
- **б) Свежий `BeginTx` на попытку, откат при неуспехе, эффекты в одной tx** — PASS.
  `clearUniverseOnce` (`:145`): `BeginTx` → `defer tx.Rollback()` → `clearUniverseTx`
  → `Commit`. Все шаги очистки (escrow/`UPDATE users`/DROP FK/TRUNCATE/DELETE
  accounts/ADD FK) идут внутри одной транзакции; после дедлока Postgres откатывает
  её целиком, поэтому двойного применения (повторный возврат залога и т.п.) нет.
- **в) Не-дедлок отдаётся наружу без повторов** — PASS. `:136`:
  `if err == nil || !isDeadlockErr(err) { return err }`. Подтверждено тестом
  `TestClearUniverseNoRetryOnOtherError` (одна транзакция, ошибка `23503`).
- **г) Исчерпание попыток — ошибка наружу, без паники** — PASS. Цикл `:127–141`
  возвращает последний `err` (дедлок). Подтверждено `TestClearUniverseRetryExhausted`
  (`require.True(isDeadlockErr(err))`, паники нет).
- **д) Инварианты целы** — PASS. `universeMutationMu.TryLock()`→409 (`:886`) и
  `defer Unlock()` (`:890`) на месте, ретрай идёт под тем же локом; порядок шагов
  `clearUniverseTx` не менялся (escrow → users → DROP FK → TRUNCATE → счета → ADD FK);
  `truncateTables` (`:62`) не тронут.

Наблюдение (не баг): backoff `time.Duration(attempt) * retryWait` даёт 150 мс
(попытка 2), 300 мс (попытка 3) — соответствует комментарию «150, 300 мс».
При `attempts=1` ретраев нет вовсе (одна попытка) — поведение корректное.

## Что не проверено и почему

- **Живой гейт 409 на `/admin/clear`** (п.4б) — не гонялся: (1) для ответа 409 нужен
  **активный** джоб генерации/пакмана, а его создавать ради проверки запрещено
  (`AGENTS.md` §16); (2) без активного джоба POST прошёл бы гейт и **реально снёс
  ~10 000 миров** общей dev-БД. В логе сервера активного джоба нет. Гейт покрыт
  юнит-тестами (`BlockedByPacman`, `MutexHeldByPacman`, `BlockedByRegenerate` — PASS
  в п.2). Чтобы закрыть живьём: создателю/менеджеру запустить (или дождаться) джоб
  генерации/пакмана на отдельной БД и вызвать POST `/admin/clear` под админ-JWT —
  ожидается 409.
- **Живой end-to-end прогон самой очистки под нагрузкой NPC-тика** (реальный дедлок
  `40P01` → успешный ретрай на живом сервере) — не гонялся: это полная очистка
  dev-БД, запрещена (риск чужих данных). Проверено sqlmock-тестами (п.2) + ревью (п.3).
  Чтобы закрыть: поднять временную БД, наполнить агентами/мирами, запустить очистку
  при активном тике, убедиться, что `pg_stat_database.deadlocks` растёт, но операция
  доходит до `{"status":"cleared"}`.
- **Ретрай на родственных TRUNCATE-путях** (`GenerateUniverse`, гипотезы) — не
  реализован и не проверялся (п.5): вне объёма этой задачи, решение о расширении — за
  менеджером/создателем (в идее §2/§3 п.2 помечено «на усмотрение разработчика»).
- **Приоритет/поведение `40001`** (serialization failure) — не ретраится намеренно;
  является ли это достаточным для прода — вопрос создателя, не проверяется тестером.
