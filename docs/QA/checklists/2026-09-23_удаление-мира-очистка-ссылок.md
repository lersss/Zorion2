## Наблюдения (не FAIL, вне объёма правки)

- **Порядок шага escrow различается у двух путей.** `DeleteWorld`: `ReturnEscrow` → очистка → `DELETE worlds`. Пакман: очистка (вкл. `DELETE npc_agents`) → `ReturnEscrow` → `DELETE worlds`. Комментарий в хелпере (admin_pacman.go:430-434) прямо оговаривает, что удаление агента до возврата залога безопасно лишь пока агент — исполнитель, а не автор (B2). Для `DeleteWorld` порядок безопаснее; для пакмана — известное ограничение итерации 1, регрессии нет.
- **Артефакт харнесса (не баг продукта):** первый запуск контрольной транзакции был отправлен параллельно с очищающей — Postgres отдал `deadlock detected` на `npc_agents` (две транзакции ждали `KEY SHARE` друг друга). Контроль перезапущен **последовательно** — дал ожидаемую FK-ошибку. Параллельный запуск транзакций в psql — нештатный сценарий проверки.

## Не проверено вживую

- **Полный HTTP-флоу `POST /admin/worlds/delete` на реальном сервере** (200 + `{"status":"deleted"}`): не гонялся, чтобы не менять dev-БД без rollback-контроля; поведение покрыто кодом (admin_worlds.go:157–168) и sqlmock-тестом.
- **Мир с игроком в `current_world_id`** (>0 users): выбранный мир Rotenin имел 0 игроков, `UPDATE users` вернул `UPDATE 0`. Ветка `users_current_world_id_fkey` подтверждена только по схеме; в живой транзакции сработала ветка шага 2 (npc_agents).
- **Мир с `pending_destination`/`player_intrasystem_flights`**: в dev-БД таких строк 0 (`pending_to_world=0`, `iflights=0`), шаги 4/4.5 выполнились как `DELETE 0`/`UPDATE 0`.
- **Реальная гонка пакмана с читателями** (одновременный запрос карты/подтверждение контракта) — только `-race` в юнит-тестах, не живой многопользовательский прогон.
