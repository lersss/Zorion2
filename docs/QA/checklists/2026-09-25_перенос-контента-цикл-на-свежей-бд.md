## Главные находки

- **H1 (наблюдение, не дефект).** На двух **свежих** базах метки `code` **совпадают** (обе
  засеяны детерминированно в одном порядке; сверено: `g_0001=вода-ресурс`, `p_0003=Форпост`),
  поэтому импорт идёт в режиме **`managed`**, `remap=0`, а не `bootstrap`. Premise задачи
  «метки разойдутся, т.к. выдавались по локальным номерам» верен только для **dev→свежая**
  (расхождение F2 из прошлого прогона), но не для «свежая→свежая». Для проверки `bootstrap`
  в этом цикле нужна цель со снятыми метками или источник-клон dev.
- **H2 (операционное, требует решения).** Дамп S6 **не самодостаточен**: `pg_dump -t <10 таблиц>`
  включает DEFAULT `code public.catalog_next_code(...)`, но **не** включает саму функцию
  `catalog_next_code` и последовательности `*_code_seq` (они не `OWNED BY` колонки и не попали
  в фильтр `-t`). `psql -f` в чистую БД падает на `CREATE TABLE effect_types`. Восстановление
  возможно либо на БД с уже накатанными миграциями (тогда мешают `CREATE TABLE` → нужен
  `--data-only`/`--clean`), либо после ручного создания помощников. Для боевого бэкапа это
  значит: репетиция восстановления «в чистую» **не проходит без оговорок** — стоит зафиксировать
  рабочий рецепт (напр. `pg_dump --data-only` + схема из миграций, или `pg_dump -Fc` всей БД).
- **H3 (позитив).** `blocked=0`, `unmatched=0`, `delete=0` — полная замена на свежей цели
  ничего не снесла; локальные `id` сохранены; `section` (в т.ч. изменённый `p_0012 mining→colony`)
  доехал; `default_settlement_type_id` резолвится по метке в «Форпост».

## Что не удалось проверить (граница покрытия)

1. **`mode=bootstrap` живьём в этом цикле.** Две свежие БД дали `managed` (H1). Чтобы получить
   `bootstrap`, нужна цель с записями без меток (или dev-клон) — тогда сухой прогон покажет
   `remap`, и надо отдельно проверить, что локальные `id` сохраняются при впечатывании меток.
   В прошлом прогоне это покрыто интеграционным `TestContentImportBootstrap`.
2. **Путь «deletion» на свежей цели** не проверялся: `delete=0` (свежая цель — надмножество
   seed-контента; чтобы проверить удаление, нужно убрать запись из файла). Тест `delete`/`blocked`
   закрыт прошлым прогоном И3 (`TestContentImportFullReplacementDelete`, `...BlockedByWorldRef`).
3. **`remap` > 0** — не наблюдался (следствие H1).
4. **Боевой рецепт восстановления бэкапа** (H2): выбрал вариант «предсоздать помощников»; какой
   именно рецепт канонизировать (data-only / full dump / `--clean`) — решение создателя/операционки.
5. **Контентные таблицы `recipes`/`recipe_components`/`producer_recipes` на свежей БД пусты (0)** —
   перенос по ним не на чем было проверить (на dev они, вероятно, заполнены). Это ограничение
   свежего сида, не дефект импорта.
