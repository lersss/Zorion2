## Найденное

**Дефектов нет.** Наблюдения (не баги фичи):

1. **Живой `/api/npc/positions` в момент прогона пуст** — все 60 расовых агентов в БД (`npc_agents`)
   в статусе не-`flying` (6124 idle / 60 рас), эндпоинт отдаёт только летящих (90a) → `[]`. Живого
   значения `race_name` не увидел, но все 60 `race_id` в БД совпадают с id каталога (`config/races.json`),
   т.е. в бою `race_name` разрешится у 100% агентов.
2. **Косметика комментария (не баг).** `npc_positions.go:38-40` говорит «поверх снимка менеджера
   (idle/flying…)», тогда как выше уже отсёк только `flying`. На результат не влияет.
3. `gofmt -l` перечисляет изменённые Go-файлы, но так же перечисляет и нетронутые
   (`manager.go`, `catalog.go`) — это CRLF рабочего дерева на Windows, а не форматирование правки.
   В DoD gofmt не входит.

## Не проверено (границы покрытия)

- **Живой тултип агента в браузере (п. 4-5 «глазами»).** В `map-check.js` нет наведения на
  агента; в момент прогона летящих агентов нет → на канвасе агентов не показать. Проверено чтением
  кода + синтаксисом. Закрыть: приёмка создателем (в момент, когда есть летящий агент во вьюпорте,
  навести: строка «Фракция» видна игроку, «Корабль» — только админу) либо отдельный e2e-шаг ховера.
- **Живое `race_name` в ответе сервера (п. 1-3).** Dev-сервер отдаёт `[]` (нет летящих агентов);
  проверено уровнем хендлера с реальным каталогом. Закрыть: повторить `GET /api/npc/positions`
  при наличии летящих агентов (игрок — отфильтрованно, админ — полный список).
- **Роль игрока vs admin на живом ответе (п. 4).** Учётку admin/skycomposer не запрашивал (bootstrap
  из `.env`); вывод по коду: `userRole` из `/me.role`.
- **Вкусовая формулировка/порядок строк тултипа** — зона создателя.
