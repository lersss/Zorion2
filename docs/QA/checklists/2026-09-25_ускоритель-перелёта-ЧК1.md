## Итог: 14/14 PASS

**Найденных дефектов нет.** Инвариант «одно активное ускорение на сегмент» (И-9)
держится на трёх уровнях: пред-гейт менеджера под `m.mu`, `already_active` под
row-lock в `ApplyBoost`, `SELECT … FOR UPDATE`; подтверждён тестом
`TestBoostFlightConcurrentOneWins` (8 параллельных submit → одно применение) и
`-race` без гонок.

**Наблюдение (не дефект, не воспроизводится).** `StartFlight` пишет
`StartTime = time.Now()` без усечения (`internal/travel/manager.go:98`), а буст
усекает момент до мс. Если разворот 61a случится в ту же миллисекунду, что и буст,
`UnixMilli` нового сегмента может совпасть с `last_boost_at` и `active` ложно
станет true. Через HTTP (два отдельных запроса) недостижимо; спека сама выбрала
точность мс (§3.3).

## Не проверено (границы покрытия)

- **Живой end-to-end через dev-сервер.** На dev-БД `000089` ещё не накатана
  (сервер стартовал раньше появления файла), каталог без `accel_1` → `/travel`-блок
  отдал бы `no_module`, а не `unknown_game`. Проверка check 3 — уровень юнита
  (`LoadDefaults`) + чтения кода. **Чтобы закрыть:** перезапустить dev-сервер —
  миграции применяются при старте (`cmd/server/main.go:102`, `migrations.Apply`).
- **`newRem = remaining/(1+bonus)` и гейт `min_remaining_boost_s`** — по спеке §4.1
  (шаги 6–7) и §3.4 отнесены к ЧК3; в ЧК1 отсутствуют легитимно. «Остаток только
  уменьшается»: `BoostFlight` принимает `newRem` как есть, без валидации; гарантия
  И-6 опирается на handler ЧК3. Проверена только `AcceleratorBonus`.
- **Ручки offer/boost, мини-игра `route`, поле/`q`, UI** — ЧК3 (не мой чекпоинт).
- **Числа баланса** (`bonus_max 0.50`, `cooldown 25 мин`, пороги 180/90) — зона
  `@balancetester`, не проверял.
