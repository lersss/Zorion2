## Лог поселения (запись «Вымерло»)

**Статус:** дизайн — одобрен создателем (2026-09-14) · код — реализован
(2026-09-14, сдача; R-модель `99.2.13`: `death.go`, `change_components.go`,
транзакция синка в `economy_repository.go`)

Требования создателя (2026-09-14, `ideas/16a`): в карточке поселения — лог
записей (одно поселение — много записей, **не поля** у поселения); первая запись
«Вымерло» появляется автоматически при обвале населения через порог `NDead`;
показ «дата + причина»; последние 3 записи; записей/типов будет много и
разнообразных; общую систему «событий вселенной» не строим (журналы других
объектов — звёзды, игроки, рынки — отдельная задача). **Бэкфилл отменён
(2026-09-14): «Если не было события, то и записи о нем никакой нет. Вообще не

не получают вовсе (ни «дата неизвестна», ни причина «по текущим условиям»).
Дата и причина — **чистый вывод из уже принятой модели**, новых констант
баланса не вводится.

> Владелец: **один объект** — поселение; журналы других объектов отложены, но

### Дата смерти

Запись «Вымерло» фиксируется в момент, когда пересчёт **впервые** видит обвал
(`Recompute`: `next < NDead` → население обнуляется целиком, стыковка с
разовым обвалом `18_needs.md` §18.3.1). Дата — момент пересечения порога по
R-модели (`99.2.13`, `internal/economy/settlement/death.go` `DeathTime`):
население убывает как `p(t) = pop·(1−r)^t` (сек), пересечение
`p(t) = NDead` → `t = ln(pop/NDead)/|ln(1−r)|`:

```
t_death = computed_at + ln(population_exact / NDead) / |ln(1 − r)|   (секунды)
```

где `r = ChangeComponents(input)` — полная рекурсивная компонента изменения
населения за 1 секунду (сумма: естественная + рождаемость + жара + холод +
гравитация + радиация, `change_components.go`); `computed_at`/`population_exact` — чек-точка
пересчёта. Время в реальных секундах (игровое = реальному, 1:1, `18a` §«Время»).
Дата «Вымерло» — **Unix-секунды от `computed_at`**, без возрастного потолка
(99.2.16: `MaxLifespanSeconds` удалён; равновесие и рост живут вечно, запись
есть у всех вымерших). Все величины уже в модели: `NDead`, `r`
(ChangeComponents), чек-точка — новых констант нет. λ-механизм
(`exp(−λ·Δt)`, `TotalLambda`) удалён в R-модели (99.2.13) и в формуле не
участвует.

Краевые случаи:

- **`r ≥ 1`** (мгновенная гибель, гвард робастности — экстремальные входы,
  степенная неограничена): `t = 0` → `t_death = computed_at`. Жёстких
  нулей-обнулений и λ = +Inf в R-модели **больше нет** (99.2.13: все компоненты
  рекурсивные, `Uninhabitable` — витринный порог «смерть < 1 ч», не механика).
- **`r ≤ 0`** (изменения нет или рост): запись не
  создаётся (не вымирают).
- **`population_exact ≤ NDead` на чек-точке** (поселение пришло уже мёртвым,
  в т.ч. умершее до введения фичи): дата невычислима из чек-точки — **запись не
  создаётся вовсе** (решение создателя 2026-09-14: бэкфилл отменён; «если не
  было события, то и записи о нём никакой нет»). Это штатное поведение, не
  особый случай.
- **Δt ≤ 0**: обвала нет, запись не возникает.

**Ключевое следствие — запись обязана создаваться в момент первого обвала.**
Дата вычислима только пока чек-точка живая (`population_exact ≥ NDead`): после
продвижения чек-точки (запись `population_exact = 0`) дата теряется навсегда.
Поэтому создание записи идёт **той же транзакцией синка** (`SELECT ... FOR
UPDATE`, Δt ≥ `MinPersistInterval`), что и продвижение чек-точки — отдельного
тика нет (инвариант ленивой архитектуры, `18a` §«Точность и округление»).

### Причина

Доминирующий фактор по вкладу в изменение населения (`DeathCause`,
`internal/economy/settlement/death.go`): сравниваются рекурсивные компоненты
среды за секунду —

```
вклад_фактора = R_фактор (жара HeatTemperatureChangeRate / холод ColdChangeRate /
                 гравитация GravityChangeRate, ветки high/low / радиация RadiationChangeRate)
причина = argmax(вклад_жары, вклад_холода, вклад_гравитации, вклад_радиации)
```

Естественная компонента (`NaturalComponent`) в сравнение **не входит** — она
есть всегда (убыль от возраста), но не является «причиной» по смыслу кода.
Порог не нужен — сравниваются фактические значения, новых констант нет;
жёстких нулей и +Inf нет ни у одного фактора (99.2.13).

При равенстве вкладов — **температура → гравитация → радиация** (решение
создателя 2026-09-14). В коде это реализовано так: база `best = cold`,
сравнение строгим `>` в порядке heat, gravity_high, gravity_low, radiation —
при равенстве побеждает первый в переборе. Порядок **внутри** температуры
(жара/холод) несущественен: оба не могут быть > 0 одновременно (heat = 0 при
T ≤ 30 °C, cold = 0 при T ≥ 288 K; зона 288–303 K — комфорт, оба нулевые, там
решает другой фактор).

Если **все вклады среды = 0** (поселение в полном комфорте: T 288–303 K,
g 0.8–1.2, радиация ≤ 20), причина — `natural` (естественная убыль,
`NaturalComponent`); иначе «Вымерло» при идеальном климате получило бы
«Сильный холод» — ложь (решение менеджера 2026-09-14 по замечанию дизайнера).

Строка для игрока — «Вымерло · <дата> · <причина>», дата — реальная дата и
время (игровое время равно реальному). Коды и тексты причины:

| Код | Текст | Условие |
|---|---|---|
| `heat` | Экстремальная жара | R_жара > прочих (T > 30 °C) |
| `cold` | Сильный холод | R_холод ≥ прочих (T < 288 K) |
| `gravity_high` | Высокая гравитация | g > 1.2, R_верх > прочих |
| `gravity_low` | Низкая гравитация | g < 0.8, R_низ > прочих |
| `radiation` | Радиоактивный фон | радиация ядра > 20, R_рад > прочих |
| `natural` | Естественная убыль | все вклады среды = 0 (полный комфорт) |

### Схема данных

**Отдельная таблица записей лога** (решение создателя 2026-09-14: не поля у
поселения). Имя — `settlement_log` (прецедент единственного числа —
`compatibility_matrix`; «log» — журнал как единый объект на поселение, записей
в нём много). Миграция `000024_create_settlement_log.sql` (стиль — как
`000021`/`000018`):

```sql
CREATE TABLE IF NOT EXISTS settlement_log (
    id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    settlement_id uuid NOT NULL REFERENCES settlements(id) ON DELETE CASCADE,
    type          text NOT NULL,          -- 'extinct' — первый тип; список открыт
    occurred_at   timestamptz NOT NULL,   -- когда произошло; запись без даты не существует (бэкфилл отменён)
    cause         text,                   -- причина записи; NULL = неприменимо (будущие типы)
    created_at    timestamptz DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_settlement_log_settlement_id ON settlement_log (settlement_id);
-- Анти-дубль: одна запись «Вымерло» на поселение (инвариант, см. ниже).
CREATE UNIQUE INDEX IF NOT EXISTS uq_settlement_log_extinct ON settlement_log (settlement_id) WHERE type = 'extinct';
```

Поля: `id` (uuid, как у всех таблиц), `settlement_id` (FK, `ON DELETE CASCADE` —
конвенция `settlements.planet_id`), `type` — тип записи (открытый список, первый
`extinct`), `occurred_at` — когда произошло (для «Вымерло» — дата смерти;
**NOT NULL** — записи без даты не существует, решение создателя 2026-09-14
«бэкфилл отменён»; будущие типы тоже происходят в момент времени),
`cause` — причина (для `extinct` — код причины из таблицы выше; NULL —
неприменимо для будущих типов), `created_at` — когда система зафиксировала
запись (отличается от `occurred_at` при отложенном синке; лог неизменяем,
`updated_at` не нужен — как у таблицы `events`).

**Отдельный столбец под произвольные детали (`data JSONB`) — не добавляем
(решение дизайна).** Первый тип записи требует ровно одно поле деталей —
`cause`. JSONB — спекулятивная гибкость «на будущее» (GD_PROMPT: никакой
гибкости, которой не просили). Когда появится второй тип с другими деталями —
`data JSONB` добавится одной миграцией, таблица поселений не изменится; схема
это позволяет, комментарий выше. Готовая таблица `events` (001_init,
«неизменяемый лог» агрегатов) **не используется**: она спроектирована как общая
система событий разных объектов (`aggregate_type`), а её построение отложено
создателем («общую систему не строим»).

### Анти-дубль и синк

Одна запись «Вымерло» на поселение — гарантия на двух уровнях:

1. **Частичный уникальный индекс** `uq_settlement_log_extinct` — на уровне БД
   физически невозможно две записи `type='extinct'` у одного поселения
   (инвариант «не спамить при каждом просмотре»). Индекс не мешает будущим
   типам: ограничение только на `extinct`.
2. **Транзакция синка** — запись создаётся в той же транзакции, что продвигает
   чек-точку (`SELECT ... FOR UPDATE` строки поселения, Δt ≥
   `MinPersistInterval`), и **только когда дата вычислима**: чек-точка живая
   (`population_exact > NDead`) и `next < NDead` → `INSERT INTO settlement_log
   ... ON CONFLICT DO NOTHING` (конфликт по уникальному индексу). Если чек-точка
   уже мёртвая (`population_exact ≤ NDead`) — запись не создаётся, транзакция
   только продвигает чек-точку (штатное поведение, бэкфилла нет). Два
   одновременных синка сериализуются блокировкой строки поселения; второй
   `INSERT` упирается в индекс и ничего не пишет.

Пересчёт в памяти (Δt < 30 мин) БД не трогает и запись не создаёт — она
появится при первом же синке после смерти, с точной датой по формуле (чек-точка
в БД ещё живая, раз её не продвигали). Клиентская экстраполяция запись не
рисует (см. «UI»).

### Бэкфилл — отменён (решение создателя 2026-09-14)

> «Если не было события, то и записи о нем никакой нет. Вообще не надо старых
> обслуживать».

Поселения, умершие **до** введения фичи (`population_exact ≤ NDead` уже на
чек-точке, дата невычислима), записей лога **не получают вовсе**: ни «дата
неизвестна», ни причина «по текущим условиям», ни `occurred_at = NULL` (в схеме
`occurred_at NOT NULL` — записи без даты не существует). Для них блок «Лог»
просто скрыт. Эталон зафиксирован в `18a` §«Эталоны (FAQ)». Следствие для кода:
ветвления «дата известна/неизвестна» нет — запись пишется ровно тогда, когда
пересчёт впервые видит обвал с вычислимой датой.

### UI

Блок «Лог» — внутри карточки поселения на вкладке «Поселения»
(`web/static/js/modal/tabs.js`, `renderSettlements`): строка
«💀 Вымерло · <дата> · <причина>» — всегда с датой (записи без даты не
существует). При 0 записей блок скрыт (не рисовать). Сортировка по дате
убывающая, максимум 3 записи (сейчас запись одна). Данные: сервер прикрепляет
последние 3 записи лога к поселению в ответе
(`settlements[].log = [{type, occurred_at, cause}]`, чтение — один запрос
`WHERE settlement_id = ANY(...)` в `attachSettlements`, `docs/ARCHITECTURE.md`
§2; в `internal/models/economy.go` — поле `Log`). Косметическая экстраполяция
(`extrapolate.js`) запись **не рисует**: строка появляется только после
серверного синка, отдавшего `log` (модель «правда на сервере»).
