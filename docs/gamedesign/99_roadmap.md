## 99.2. Крупные блоки в разработке

### 99.2.1. Аномалии как контент

**Статус:** 🔄 следующий блок

Редкие «нарушения» физики — не баги, а фичи мира. Библиотека **готова** (22 JSON-файла
в `config/anomalies/`). Осталось превратить её в рабочий контент:

1. **Go-код:** чтение `config/anomalies/` при старте, кеш в памяти под `RWMutex`.
   Ошибка чтения JSON — `log.Fatal`, а не старт с полупустым кешем.
2. **API:** эндпоинт, отдающий тексты фронту.
3. **Детекция на фронте:** по кодам из аудита (см. `internal/audit/planet/`).
4. **Показ:** отдельный блок в карточке планеты, под описанием.
   Может быть несколько аномалий на одной планете.

Формат и список — в `config/anomalies/README.md`.

### 99.2.2. LLM-генерация описаний

**Идея:** при создании планеты (в `GeneratePlanets`) генерировать уникальные описания
через LLM и сохранять в БД. Детерминизм обеспечен — читается из БД, а не генерится
на каждый запрос.

**API на выбор:**
- **Groq** — быстрый, 1000 запросов/день бесплатно.
- **YandexGPT 5 Lite** — 10 млн токенов/месяц, работает из РФ.
- **Google Gemini** — 30 запросов/день.
- **OpenRouter** — 26+ бесплатных моделей.

**Что генерировать:**
- Обычные описания планет (вместо библиотеки `config/descriptions/`).
- Описания аномалий.

**Fallback:** если API недоступен — библиотека `config/descriptions/` + библиотека аномалий.

**Архитектура:**
- Пакет `internal/llm/` — обёртка над API.
- Вызов из `GeneratePlanetsForWorld` после генерации планеты.
- Батчи по 100 планет с параллельным запросом.
- Поле `description` уже есть в JSON планеты — не надо миграций.

### 99.2.3. Тонкая настройка генерации

Все хардкод-константы вынести в конфиг, редактируемый через админку:
- Спектральные классы (веса, диапазоны T).
- Планеты (количество, возраст, шансы газовых гигантов).
- Классификатор (пороги).
- Физика (альбедо, парниковые факторы).
- Ядро (пороги массы, диапазоны).
- Композиция (множители по T и воде).

**Хранение:** JSON-дефолты + override в БД (как у матрицы совместимости).

### 99.2.4. Экзотические типы звёзд

**Идея:** добавить в генерацию редкие «экзотические» звёзды и системы вокруг них.
Список типов систем с распределением уже заявлен в `02_worlds.md` §2.1
(нейтронная звезда 1%, чёрная дыра 1%, протозвезда 1%, экзотическая ~5%),
но **в коде не реализован** — `internal/generator/galaxy/galaxy.go` генерирует
только обычные спектральные классы O–Y.

**Продумать (главный открытый вопрос):**
1. **Список типов** — нейтронные звёзды, пульсары, магнетары, чёрные дыры,
   белые карлики, квазары, красные гиганты, протозвёзды. Что входит, что нет.
2. **Генерация объектов в таких системах** — как это отличается от обычной
   звезды: аккреционные диски, приливное разрушение, пульсарные ветра,
   отсутствие планет у чёрных дыр, «выжженные» внутренние орбиты,
   спутники вокруг экзотических тел.
3. **Влияние на физику** — `luminosityBySpectral` (светимость для формулы
   температуры), `determineSystemAge`, `determinePlanetCount`, шансы
   газовых гигантов, архетипы планет.
4. **Влияние на спектральные классы** — хранить тип звезды отдельным полем
   или расширять `spectral_class` (нужна миграция `worlds`).
5. **UI и карта** — как рисовать и отличать такие системы на карте.

**Связь с профилями регионов** (§99.2.10). Экзотический тип звезды —
физическая причина профиля региона. Реализовывать их стоит вместе.

**Ограничения:** не в MVP. Каждый тип — редкий (≤1%), не должен ломать
баланс аудита и статистики (см. `internal/audit/`, `admin_stats_anomalies.go`).

> **РАЗБЛОКИРОВАНО 2026-09-12.** Перевывод выполнен: номенклатура выведена

**Порядок работ:**

1. **Разделить «вещество» и «месторождение».** Сейчас одна строка = ресурс на
   конкретной планете, то есть сущности слиты, и универсальному веществу негде

   Побочная выгода: свойства перестают дублироваться в каждой строке ресурса

2. **Универсальный слой** — 20–30 веществ **вне генератора полей**

3. **Генератор полей** — «дом + радиус», степенное распределение радиусов

4. **Месторождения и истощение** (`10_exploration.md` §10.1): запас зависит от
   типа и доли источника, а не случайное число в фиксированном диапазоне.

5. **Сводка богатства** — только вещества полей, не универсальные
   (`05_economy.md` §5.4).

**Предпосылки — сделать до первой перегенерации вселенной:**

- **B11** (`STATUS.md` §2) — `GeneratePlanets` не очищает старые планеты.
- **Две таблицы ресурсов** в живой БД (`AGENTS.md` §8) — разрулить одной миграцией.
- **B9** (`STATUS.md` §2) — фильтр карты по ресурсам. Кормится сводкой
  `data["resources"]`, которую переписывать всё равно придётся.

**Чем проверять.** Гарантии генератора из `05_economy.md` §5.3 — готовый список
красных тестов: количество универсальных и отсутствие у них дома и радиуса;
фильтр категорий; число веществ в произвольной системе в коридоре; доля систем с
веществом редчайшего тира; минимальное расстояние между областями двух редчайших;
доля профилей товаров, не закрываемых локально, — больше нуля везде.

**Чего не делать:**

- **Не начинать тик симуляции.** Истощение и рынок энергии спроектированы под
  ленивый пересчёт (`11_production.md` §11.1.2) и работают без глобального тика.
- **Не строить лаборатории и сертификаты анализа** (`10_exploration.md` §10.3.5).
  Генератор должен лишь записать точные значения в `substances`.

### 99.2.9. Сеть ретрансляторов

**Статус:** 📅 планируется · новый блок 2026-09-12 · **обязательна до 1.0**

Опирается на `10_exploration.md` §10.3.2 и `14_money.md` §14.5.4. Сеть — не
определение сада, а **дорогой инструмент**, который сад может себе позволить, а
фронтир — нет. Где появилась сеть, там больше не фронтир.

**Пять подсистем:**

1. **Ретранслятор как постройка.** Производится из существующих категорий
   (электроника, комплектующие). Отдельной ветки «деталей для связи» нет.

2. **Покрытие.** Радиус зависит от качества материалов: хороший проводник, но
   хрупкий и легкоплавкий → большой радиус, гибнет от первого удара.
   Плотное и тугоплавкое → малый радиус, но переживает войну.

3. **Возраст данных.** `10_exploration.md` §10.3.1: возраст данных зависит от
   расстояния и покрытия. Сеть не делает данные свежее присутствия (§10.3.3).

4. **Уязвимость.** Перерезать связь — законный удар. Ослепший магнат владеет
   всем, но перестаёт управлять. Сеть становится платёжным рельсом
   (`14_money.md` §14.5.4): отрезать от расчётов болезненнее, чем ослепить.

5. **Содержание.** Энергия и комплектующие постоянно
   (`11_production.md` §11.1.3). Обеднел — покрытие сжимается, видишь меньше,
   зарабатываешь меньше.

**Параллельный поток.** Не блокирует поселения. Можно начинать одновременно
с блоком 11.

**Чего не делать:**

- **Не делать сеть определением сада.** Граница сада — изолиния по цене еды
  (`17_decay.md` §17.2.2). Сеть идёт следом, но не задаёт её.
- **Не доходить сетью до фронтира.** Присутствие обязано быть свежее
  инфраструктуры (`10_exploration.md` §10.3.3). Где сеть, там не фронтир.

2. **Генерация профиля при создании региона.** Физическая причина (квазар,
   токсичная звезда) выводится из генерации. Контентная (пиратская база,
   древняя катастрофа) назначается вручную или по правилу.

3. **Интенсивность** — слабая / средняя / сильная. Даёт градиент без второй
   сущности.

4. **Связь с кризисами** (`17_decay.md` §17.5.2) — профиль как дополнительное
   предусловие. Кризис, типичный для региона, возникает чаще.

5. **Связь с границей сада** (`17_decay.md` §17.2.2) — профиль как второй
   носитель изолинии рядом с ценой еды.

6. **Связь с войной.** Пиратский профиль — источник угроз для охраны
   (`11_contracts.md` §11.3.2).

**Связь с экзотическими типами звёзд** (§99.2.4). Физическая причина профиля —
это и есть экзотический тип. Реализовывать вместе.

**Чего не делать:**

- **Не публиковать профиль как ярлык.** Последствия скрыты, открываются
  наблюдением (`02_worlds.md` §2.6.1).
- **Не делать набор профилей нормой.** 1–2 на регион, чаще один. Комбинации —
  только как отдельные комбинированные классы, написанные руками.
