# 100b. Сторож зацикливания агентов — повторный вызов режется, сессия гасится

**Создано:** 2026-09-21
**Статус:** ✅ реализовано 2026-09-21 (этим коммитом) — сторож принят создателем;
потолки шагов отклонены на приёмке («сторожа пока что. Посмотрим, как будет
работать»), в промтах ролей их нет
**Приоритет:** операционная задача (экономия бюджета команды агентов)
**Вектор:** не игровой — обвязка команды (как 62a, 63a, 93a)

---

## Пожелание (слова создателя, 2026-09-21)

> «я не могу всех контролировать. Надо что-то делать, очень много бюджета
> отжирают зацикленные дев и тестер»

Началось с вопроса «может ли opencode отслеживать зацикленных агентов и вырубать
их» → после диагностики создатель дал «ок» на сторожа (плагин + потолок шагов
для разработчика и тестера).

## Диагностика (что найдено в хранилище сессий, 2026-09-21)

Источник — `~/.local/share/opencode/opencode.db` (1034 сессии по проекту).

- Замер по 223 сессиям дороже $0.2 ($375 суммарно): **точные повторные вызовы**
  (тот же инструмент + те же параметры, сверх 3 раз) — 3694 вызова, оценка
  **$34 (9% затрат)**.
- Доля по ролям: разработчик $21 из $106 (20%), дизайнер $7 из $31 (23%),
  тестер $4.6 из $18 (26%). У менеджера/билда/артиста — около нуля.
- Чемпион: сессия разработчика «Реализация композитного маршрута» — 888 действий,
  из них **774 — одна и та же команда** (`git log` по одному файлу), стоимость
  $9.36, из них ~$8.1 на повторы. Далее: 347× grep, 311× read, 159×, 128×, 117×.
- **Встроенный предохранитель opencode (`doom_loop`) не сработал ни разу за 12
  дней** (проверено по журналу: 477k строк, с 2026-09-09). Причина найдена в коде
  приложения: он требует, чтобы **три последних действия подряд** были одним и
  тем же вызовом с тем же входом; перемежающиеся повторы (bash → read → bash) под
  условие не попадают. Полагаться на него нельзя.
- Отдельно: журнал штрафов не выявлено у «медленных, но разных» сессий — это не
  зацикливание, а долгая работа.

## Решение

1. **Сторож `.opencode/plugins/loop-guard.js`** (автоподхват opencode, работает
   для всех агентов и подсессий, без обращений к модели):
   - один и тот же вызов (инструмент + параметры) **с неизменным выводом** 4 раза
     подряд → 5-й **блокируется** с текстом «не повторяй, меняй подход или пиши
     отчёт»;
   - тот же вызов **с любым выводом** больше 40 раз → блокируется;
   - серия блокировок в сессии (6) → **сессия гасится** (обрыв через API);
   - состояние сессии чистится по её удалению.
   Ключ повтора — нормализованные параметры (порядок ключей не важен).
2. **Потолок шагов** в промтах ролей — **отклонён создателем на приёмке**
   («сторожа пока что»). Предлагались `developer` 600 / `tester` 400; в промтах
   ролей потолков нет.

## Честные границы (что сторож НЕ ловит)

- Цикл «слегка разными» командами, где вывод каждый раз отличается (например,
  команда печатает время) — до 40 повторов.
- Потолок шагов (в итоге не поставлен) — слабый инструмент: по факту медиана сессии
  разработчика 133 шага, p90 — 343, максимум 863. Набросок 60/40 из первого гейта
  данные опровергли — он бы калечил нормальную работу; 600 рубил бы ровно одну
  сессию за всю историю.
- Прошлый расход не возвращается: сторож работает только вперёд.
- Сторож включится только после перезапуска opencode: конфиг и плагины читаются
  один раз при старте. В сессии, где он был написан, он ещё спал.

## Артефакты

- `.opencode/plugins/loop-guard.js` (создан 2026-09-21).
- Потолки шагов в `.opencode/agents/developer.md` / `tester.md` — не поставлены
  (отклонены на приёмке).
- Требуется **перезапуск opencode**: конфиг и плагины читаются один раз при старте.
- Аварийный выключатель: `OPENCODE_PURE=1` в окружении отключает внешние плагины
  целиком; пороги — в первых строках файла сторожа.

## Проверка

Прогон на локальном стенде (копия плагина + поддельный клиент, 11 проверок, все
зелёные): 4 одинаковых вызова проходят, 5-й блокируется; 60 разных вызовов
проходят; 40 идентичных команд с разным выводом проходят, 41-я блокируется;
порядок ключей параметров не влияет; после 6 блокировок сессия гасится и привязка
идёт к верной сессии; удаление сессии сбрасывает счётчики.
