## Повод (факт 2026-09-21)

Сторож запер `@developer` на критерии «файл переписан 25 раз» (в журнале — 37
правок `web/studio.html`), хотя шла легитимная правка одной большой страницы: к
моменту отказа Go-часть была готова, DoD зелёный, не доделана только страница; в
отчёте разработчик так и написал. По тому же критерию утром спотыкались три
сессии `@designer` (спеки: 25 → 33/37/41 правок), причём отказ прилетал уже на
чтение и поиск — они даже не правили.

Корень: критерий считал **объём** действий по одному файлу, а не **результат**.
Вторая половина сигнала — память — вообще не работала: во всех 14 срабатываниях
за утро `mem: 0`.

## Что сделано

### 1. Критерий по результату (часть 1, коммит `b10efd9`)

- Файл оценивается по содержимому: пока оно меняется — идёт работа, сторож молчит;
  спираль — **возврат к уже виденному состоянию** (`SAME_FILE_REPEATS = 5`).
- Грубая страховка по объёму поднята 25 → **60 правок** одного файла
  (`SAME_FILE_EDITS`), срабатывает, даже если содержимое меняется.
- Содержимое берётся дёшево: `write`/`apply_patch` — из аргументов вызова; `edit` —
  чтением файла после вызова, только для «горячих» файлов (≥ 8 правок,
  `FILE_HASH_MIN_EDITS`) и не больше 1 МБ (`FILE_HASH_MAX_BYTES`).

### 2. Починка памяти (коммит `f8ec128`, живая проверка — пробником)

Диагноз подтверждён живым потоком событий: событие `message.updated` доходит,
форма сообщения — старая (`role` + `tokens`), но у нового сообщения токены
приходят **нулями**, и старая формула затирала память в 0 на каждом таком
событии — отсюда `mem: 0` во всех срабатываниях. Теперь: форма роли читается как
`info.role ?? info.type`, токены — `tokens.input + (tokens.cache?.read ??
tokens.cacheRead)`, а **нулевые значения память не стирают** (проверено живьём:
`session.updated` несёт накопленную память сессии — 2 млн; брать её вместо
последнего сообщения было бы ошибкой).

### 3. Продление лимитов на лету (часть 2, коммит `bf02f41`)

- Сторож читает заявку `.opencode/loop-guard.override.json` (кэш по времени
  изменения файла): `{ "<sessionID>": { until, extra, by } }`. Активная заявка:
  строка `action="extend"` в журнале, сброс счётчика «после напоминания»
  (`afterReminder`), разрешение нового напоминания, объёмный предел файла
  `60 + extra`.
- Продление **только на срок**; истёкшая заявка, заявка без срока и битый файл —
  игнорируются, сторожа не роняют.
- Продление **не отменяет**: возврат файла к виденному состоянию и порог памяти
  900k — это и есть признаки «агент встал».
- Сервис учёта (`tools/agent-dash`, порт 8790): `POST /api/extend`
  (`{session, minutes, actions, reason}`) — атомарная запись (`.tmp` + rename),
  ответ `{ok, session, until, extra, minutes}`; пустая сессия и не-JSON → 400,
  тело > 4 КБ → 413; активные заявки отдаются в `/api/stats` полем `extensions`.
- Страница учёта: в карточке активной сессии — кнопка «продлить +15 / 30 мин»,
  плашка «продлено ещё N мин». Пределы сервиса: ≤ 240 минут, ≤ 200 действий.
