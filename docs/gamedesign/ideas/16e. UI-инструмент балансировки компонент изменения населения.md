## Решения создателя (гейт дизайна, 2026-09-15)

1. **Жара не держит дефолтные эталоны (+200/+500/+1000)** — менять калибровку
   99.2.12 НЕ надо: «для калибровки и нужен инструмент, ничего сейчас менять
   не надо». Инструмент с первого дня показывает отклонение — это честная
   диагностика, балансировка будет делаться через него.
2. **Эталоны +1000/+4000 сливаются в один маркер** (оба R=0.6019) — «пока как
   есть оставляем, и посмотрим». Единый маркер фиксируем в спеке.
3. **«Двигать мышкой, сохраняя гладкость» — это и есть смысл инструмента**
   (уточнение создателя 2026-09-15, отменяет более ранние трактовки): прямое
   перетаскивание точек кривой мышкой — основной способ балансировки; кривая
   при этом ОСТАЁТСЯ гладкой (не превращается в ломаную изломов). Механизм:
   drag точки → пересчёт параметров аналитической формулы (фиттинг под новую
   точку/точки) → кривая перерисовывается, гладкость сохраняется (эталон
   «порог-переключатель запрещён»).
4. **Диапазоны параметров §3 — ок** (эмпирические).
5. **Natural/Birth — УБРАТЬ из балансировщика полностью** (создатель: «вообще
   можно убрать»): в списке остаются только 4 редактируемые компоненты
   (жара/холод/гравитация/радиация); СПЖ/k — только в «Основном».
6. **Горизонтальный drag тоже нужен** (создатель 2026-09-15): точка двигается
   и по X, и по Y; при горизонтальном движении синхронно меняется параметр,
   привязанный к X (порог/сигмоида). Кривая остаётся гладкой.
7. **Стартовые drag-точки = текущие сконфигурированные значения** (создатель:
   «в этом и смысл — корректировать, перезаписывать, балансировать»), а НЕ
   эталонные X. Эталоны остаются на графике как фиксированные крестики.
8. **Числовые пороги фита** — «делайте как считаете нужным, потом поправим».
   Решение за дизайнером.
9. **X-параметр жары** — дизайнер предложил `rSigmaT` (центр сшивки, деф.
   90 °C), а не `heatTempC` (множитель наклона, не двигает кривую по X).
   Создатель: «можно попробовать, не понимаю пока о чём речь. Интуитивно
   надо двигать T. Гляну после реализации, но интуитивно надо двигать T».
   → Принимаем rSigmaT; создатель проверит после реализации.
10. **Гравитация: нет X-параметра как такового** (пороги 0.8/1.2 вшиты).
    X-drag = пересчёт `gravityLowC`/`gravityHighC` (сдвиг ветки). Создатель:
    «любой X-параметр — это фактическое значение переменной из R-спектра» —
    подтверждает подход. → Принимаем.
11. **Стартовые точки = текущие сконфигурированные значения** (жара 3: 90 °C /
    66.85 / 500; холод 3: 150 K / 223 / 73; гравитация 2: 0.5 / 2;
    радиация 2: 20 / 60; лимит 2..8). Создатель: «стартовые точки определяют
    ровно то, как сейчас функция себя ведёт, где у неё ключевые изгибы.
    Инструмент должен уметь изменять их». → Подтверждено.
12. **МОДЕЛЬ КРИВЫХ = СЕГМЕНТЫ С ИЗГИБОМ (архитектурное решение создателя
    2026-09-15, переопределяет вариант C фита параметров):**
    - Каждый сегмент (между парой точек) имеет свой параметр **«изгиб»**:
      0 = прямая, <0 = вогнутая (логарифм), >0 = выпуклая (экспонента).
    - Архитектура мини-R **сохраняется как в коде** (`ChangeComponents`
      вызывает по очереди `HeatTemperatureChangeRate`, `ColdChangeRate`,
      `GravityChangeRate`, `RadiationChangeRate` и т.д., каждая получает ОДИН
      параметр — значение компоненты, возвращает R). Меняются ВНУТРЕННОСТИ
      каждой мини-R: вместо аналитической формулы — сегментная кривая
      (точки X/Y + изгибы). Ядро сборки большого R не трогаем. Будущие
      компоненты (кислотная атмосфера и т.п.) — той же схемой.
    - **Изгиб 0 = прямая разрешён** (линейная зависимость «где она нужна»;
      сознательное дополнение эталона «порог-переключатель запрещён»).
    - **Старт = совпадение с текущими формулами в контрольных точках**
      (баланс смертности не должен молча поменяться при установке
      инструмента). Точки-узлы на старте — в характерных местах.
    - Хранение: конфигурация кривой компоненты, in-memory (как текущие
      настройки СПЖ/k), не таблица БД.

## Факты из кода (менеджер, проверено)

- Компоненты изменения населения и их константы зашиты в код
  (`internal/economy/settlement/mortality.go`):
  - жара — R(T) сшивка (Rnatur K1, тепловая a/n, сигмоида kσ/T_сш, рампа 15–30,
    `NaturalChangeRate` 6.6e-10/сек);
  - холод — полюс B (SaturateCold 350, HardZeroCold 100 K) через
    `HumanTemperatureProfile`;
  - гравитация — `HumanGravityProfile` (комфорт [0.8,1.2], Sat 4, линейная);
  - радиоактивность — `HumanRadioactivityProfile` (порог 20, Sat 60, линейная);
  - общий масштаб `MaxRatePerHour = 0.1` (`DefaultScale`).
- Уже есть только-чтение предпросмотр `GET /admin/mortality-preview`
  (`internal/handlers/admin_mortality.go`): по конкретной планете severity,
  r_per_sec, lambda_per_hour, t_death, projection (население на
  1ч/сут/нед/мес/год). Кнопка «Обновить» — в карточке планеты. Отдельной
  вкладки балансировки в админке нет (`web/static/js/admin/`).
- Контрольные точки-эталоны создателя («+200 °C → 20% за минуты, последний
  3–5 дней»; «+500 °C → 95% за секунды…»; «+30 °C → вымирание ~1000 лет» и
  др.) — только в `docs/gamedesign/18a_population_death.md`, в коде их нет.

## ТЗ (готово по ответам создателя 2026-09-14; финальный вопрос: эталоны)

Инструмент в админке (графический), для каждой компоненты изменения населения
**отдельно**:

1. **Выбор и загрузка значений компоненты** — температура (жара),
   гравитация, радиоактивность, естественная смертность, рождаемость и т.д.
   Список компонент открытый (рождаемость/рост — будущие компоненты со
   знаком минус R < 0? уточняется; сейчас в модели жары R — сшивка,
   λ-факторы — холод/гравитация/радио, `NaturalChangeRate` — естественная).
2. **График одной компоненты:** ось X — значение компоненты, ось Y — R
   (скорость изменения населения). Каждую компоненту балансируем отдельно.
3. **Точки излома:** можно добавить точку излома и задать её значения вручную,
   либо двигать точки мышкой прямо на графике.
4. **Масштаб:** инструмент сам подбирает подходящий масштаб — без
   «пиксельхантинга», кривая не теряется в углу графика.
5. **Сохранять значения.** Ответ создателя: **«да, должен менять баланс»** —
   сохранённые значения применяются к игре (влияют на рантайм), а не только
   показываются.
6. **Эталоны на графике (ответ создателя: «да, нужно»):** на графике рисуются
   контрольные точки-эталоны создателя («+30 °C → вымирание ~1000 лет»,
   «+200 °C → 20% за минуты, последний 3–5 дней», «+300 °C → мгновенная гибель,
   минуты», «+500 °C → 95% за секунды», «+1000 °C → 99% за секунды, остаток
   через час», «+4000 °C → смерть за 5 секунд»; холод: «−200 °C → минуты») —
   видно, держит ли кривая эталоны. Как транслировать эталон («поведение
   населения») в точку на графике (X = значение компоненты, Y = R) — перевод
   через R: по моменту исчезновения всего населения при заданном p0 или по
   долям — решает @designer (эталоны дословно — `docs/gamedesign/
   18a_population_death.md`, §«Эталоны (FAQ)»).

**Дизайн-развилки (решает @designer при запуске, согласует с создателем):**

- **Репрезентация кривой:** существующие компоненты заданы аналитическими
  формулами (сшивка R(T): зоны+сигмоида, полюс B холода, линейные
  гравитация/радио). Инструмент оперирует точками излома. Как вводятся точки
  излома в рантайм-модель: замена формулы кусочно-линейной функцией, или
  точки излома — узлы интерполяции поверх формулы? (Это меняет или не меняет
  математику модели; 99.2.12 контрольные точки — «критерий тестера, не узлы» —
  см. правило 14c.)
- **Персистентность и применение:** где хранить значения (конфиг-файл, БД,
  генерация параметров в код) и как применять к рантайму (перезапуск?
  горячая подмена?).
- **Список компонент:** какие реально балансируются сейчас (жара-сшивка,
  холод-полюс B, гравитация, радиоактивность, естественная смертность),
  рождаемость — будущая (не реализована, рост = отрицательная компонента).
