## Сырое пожелание (создатель, 2026-09-14)

Нужно сделать ролевую модель. Роли на данный момент — игрок, админ. Уровни доступа
предложи. А ещё CREATOR — главный админ. В этом спринте нужно сделать раздел админки
«Пользователи» (удобный для поиска-редактирования прав пользователей и просмотра их
профилей).

## Уточнения (вопросы → ответы создателя, 2026-09-14)

1. **Как открывается админка?** → «Всё верно, обычная форма логина». Переводим вход в
   админку на обычную учётку (логин/пароль как у игрока, роль в JWT).
2. **Схема уровней доступа:** PLAYER (только игровой клиент) / ADMIN (вся админка, но
   без управления правами и системных настроек) / CREATOR (всё, что ADMIN + управление
   ролями, сброс паролей, бан/удаление, создание пользователей) → «давай сделаем, если
   что поправим и добавим, чего не хватит».
3. **Раздел «Пользователи»:** поиск (логин/email) + пагинация + просмотр профиля +
   редактирование прав + создание пользователя → подтверждено, плюс **«Ещё — создать
   пользователя»**.
4. **Кто распоряжается правами:** → «Админов назначает/убирает только creator».
5. **Переименование роли** (2026-09-14): вместо «creator» — **«skycomposer»** (значение роли в БД, JWT, middleware, env-переменные, интерфейс).
6. **Открытые вопросы дизайна — решения создателя (2026-09-14):**
   - **Бан** → в долгий ящик бэклога (отдельная идея, см. ниже). В спринте — только удаление учётки.
   - **Bootstrap первого skycomposer** → через секретную переменную сервера: env
     `SKYCOMPOSER_BOOTSTRAP_USERNAME`/`SKYCOMPOSER_BOOTSTRAP_PASSWORD` на старте
     (создание или повышение учётки, пока skycomposer'ов 0) — подтверждено.
   - **Смена пароля самому себе** → вне раздела «Пользователи»; оставить так.
   - **Подтверждение (2026-09-14, сессия FAQ):** создатель повторно подтвердил: бан — «будет позже»
     (в спринте только удаление), bootstrap через env — «ок».

## Текущее состояние кода (проверено менеджером, 2026-09-14)

- `internal/models/user.go` — `User` без поля роли.
- `internal/auth/jwt.go` — `Claims{UserID}` без роли.
- `internal/auth/middleware.go` — `AuthMiddleware` кладёт в контекст только userID.
- `internal/auth/admin_auth.go` — `AdminAuth` проверяет общий `X-Admin-Password`
  (env `ADMIN_PASSWORD`), ролей/учёток нет.
- `web/admin.html` — админка без раздела «Пользователи» (вкладки: Основное,
  Генерация, Статистика, Аудит, Тесты, Поселения, Гипотезы, Миры).
- `internal/repository/user_repository.go` — CRUD базовый: Create / GetByUsername /
  GetByID / UpdateCurrentWorld / UpdateShipIcon. Листинга пользователей нет.
- Таблица `users` (миграция `002_users.sql`): id, username, password_hash, email,
  agent_id, current_world_id, ship_icon, created_at, updated_at. Роли нет.

## ТЗ (для дизайна)

1. Поле роли у пользователя (миграция), роли: `player`, `admin`, `creator`.
2. JWT несёт роль пользователя; ручки авторизации обновляются.
3. Админка открывается обычным логином; старый глобальный `X-Admin-Password`
   снимается/заменяется (решить вопрос начального CREATOR — как создать первую учётку
   с ролью creator).
4. Раздел «Пользователи» в админке: поиск по username/email, пагинация, просмотр
   профиля, редактирование прав, создание пользователя.
5. Ограничения доступа: игровые маршруты — любому залогиненному (роль не ограничивает
   игру); админка (ADMIN, CREATOR) — по роли JWT; управление ролями и создание
   пользователей — только CREATOR.
6. Защита от потери контроля: нельзя снять/понизить последнего CREATOR (и/или себя?) —
   продумать в дизайне.

## Открытые вопросы для дизайна

- Bootstrap первого CREATOR (env-флаг / первая регистрация / служебная команда).
- Вход в админку: отдельная страница логина или общая `/login-page` с проверкой роли?
- Что видно в «профиле пользователя» (текущий мир, иконка корабля, даты и т.п.).
- Запреты: само-понижение, удаление себя, понижение последнего CREATOR.
- Влияние на существующий `/admin/*`-хендлеры (весь пул админки переводится с
  `X-Admin-Password` на роль).
