## 1. Пожелание (дословно)

«Нужна возможность долететь до выбранной планеты из открытой модалки этой планеты,
даже если пользователь в другой системе. "композитный маршрут". Слежение при этом
определяет, где пользователь, и следит за ним там (внутри системы или на основной
карте)».

## 2. Решения создателя (2026-09-20, приёмная)

1. **Поток (A): где игрок, там и камера.** Клик «Лететь» к планете чужой системы →
   модалка закрывается, игрок на основной карте (полоса перелёта к системе, камера
   следит за кораблём); по прибытии в систему модалка системы открывается сама и
   показывает второй сегмент — внутрисистемный полёт к планете (камера следит там).
2. **Механика маршрута — СЕРВЕР.** Сервер хранит намерение «после прибытия в систему
   X — лететь к планете P»; по прибытии межзвёздного сегмента сервер сам запускает
   внутрисистемный сегмент. Переживает обновление страницы (клиентский вариант
   отклонён).
3. **Разворот маршрута:** игрок уже в межзвёздном полёте + клик «Лететь» к планете
   другой системы → маршрут разворачивается (полёт к новой системе), намерение
   планеты новой системы сохраняется (паттерн 61a + намерение).
4. **Слежение переключается само** (карта ↔ модалка). В скоуп фичи входит починка
   бага «Найти меня» при межзвёздном полёте (99.2.27 §8.10): кнопка 🎯 в модалке при
   межзвёздном полёте должна закрывать модалку и вести камеру карты за кораблём со
   слежением (реализовано частично, нужна диагностика).
5. **Границы:** кнопка «Лететь» на планете чужой системы активна, пока модалка
   открыта (данные планеты есть: знание/радиус, 77a). Если игрок уже в этой системе —
   остаётся обычный внутрисистемный полёт, без изменений. Создатель: «скорее всего
   так, если что поправим».
6. **Приоритет — высокий**, стартовать сейчас.

## 3. Архитектурный фильтр (менеджер, предлагает модель)

Новая сущность — серверное **намерение** «долететь до объекта системы после
прибытия».

1. **Природа** — результат-состояние игрока («куда я направляюсь дальше»), не
   событие/история: одна запись на игрока, убирается по выполнению/замене. → атрибут
   игрока.
2. **Владелец** — один объект (игрок): одна запись на игрока → атрибут `users`, не
   таблица (аналог `users.current_position` 99.2.27 — та же природа).
3. **Расширяемость** — тип один (цель = объект системы: мир + объект); второй тип
   (например, «вернуться к месту после добычи») ложится в ту же JSONB-схему полем
   `kind`.

**Модель (гипотеза менеджера, на подтверждение на гейте дизайна):**
`users.pending_destination JSONB NULL` — `{ world_id, object_type, object_id }`.
NULL = намерения нет. Пишется при старте композитного маршрута (вместе со стартом
межзвёздного /travel, атомарно), читается по onArrival межзвёздного полёта
(намерение актуально → автостарт внутрисистемного полёта + очистка), очищается при
развороте/отмене/неактуальности (мир не совпал; любой /travel-старт без объекта
цели — по M1; пакман при съедении мира-цели — по M3). Битая цель (перегенерация) →
**намерение отбрасывается**; позиция игрока при автостарте уходит в фолбэк «орбита
звезды» (по образцу ИП-4 99.2.27; критик, мелкое 1 — формулировка уточнена).

Миграция: бронь номера — @manager при старте разработки. Факты (проверено 2026-09-20):
`000045` (студия), `000046` (внутрисистемный полёт), `000047` (индексы npc_agents,
пакман) заняты; `000048` и `000049+` **планирует** дизайн-спека фабрик (этап 2 —
buildings). Предложение дизайнера в спеке 99.2.30 — `000049`: свободна физически, не
конфликтует с фабриками (берём 000050, если фабрики выйдут в один релиз с нами).

## 4. ТЗ-свёртка (начальная, уточнит @designer в спеке)

1. **Серверное намерение** (`users.pending_destination`, §3): пишется атомарно со
   стартом межзвёздного, когда старт инициирован «к планете»; onArrival валидирует
   (мир == намерение, объект жив) → старт внутрисистемного полёта + очистка
   намерения. **Автостарт — серверный, НЕ «как POST /api/intrasystem-flight»**
   (критик, мелкое 2: общий код с POST перенёс бы известный баг §8.9 — битая цель →
   400 «Объект не найден»): onArrival делает валидацию «объект жив» ДО старта и при
   битой цели уходит в фолбэк «орбита звезды» БЕЗ 400. **Намерение очищается и при
   ПРОВАЛЕ автостарта** (двигатель снят за время межзвёздной фазы — 91a; иначе
   намерение-призрак висит до следующего /travel; критик, мелкое 3).
2. **Правило согласования:** композитное намерение существует только во время
   межзвёздного сегмента (по M2 — и при идемпотентном 202-пути, см. ниже); активный
   внутрисистемный полёт намерения не требует (полёт уже идёт, виден в модалке).
   Намерение не сосуществует с позицией в чужой системе (позиция NULL при
   межзвёздном — С1 99.2.27 — сохраняется).
3. **Разворот (решение 3):** старт /travel при активном межзвёздном полёте (61a) с
   объектом цели → новое намерение перезаписывает старое атомарно со стартом.
   **Очистка (критик, среднее M1):** любой /travel-старт на целевую звезду БЕЗ
   объекта (обычный «Перелететь») очищает намерение — иначе намерение {X,P} висит
   весь полёт к Z (нарушение «намерение только в сегменте») и переживает редирект к
   той же системе X (игрок явно «перелетел» к звезде, а сервер потащит к P).
   **Запись на 202-пути (критик, среднее M2):** POST /travel с объектом цели, когда
   полёт к той же системе УЖЕ идёт (202-идемпотентность, путь не пишет намерение) —
   намерение записывается и на 202-пути (иначе игрок прилетит к звезде, а не к
   планете, хотя кликнул «Лететь»).
4. **UI модалки:** на планетах/спутниках чужой системы — кнопка «🚀 Лететь»
   (композитный маршрут); в своей системе — существующая внутрисистемная кнопка без
   изменений; у звезды чужой системы — существующий «Перелететь» (простой
   межзвёздный, без намерения). Пометка на кнопке: полёт «через систему» (2 сегмента).
   **Блокировка (критик, мелкое 4):** кнопка «Лететь» в модалке бывшей «своей»
   системы при активном межзвёздном полёте (current_world_id — система отправления
   до прибытия, my_position есть, но старт даст 400 «Вы в межзвёздном полёте») —
   клиентски блокируется при активном межзвёздном.
5. **Слежение (решение 1/4):** старт композитного → модалка закрывается, камера
   карты + слежение (существующий followShip); прибытие в систему → модалка системы
   автоматически открывается → внутрисистемный сегмент виден (полоса полёта
   99.2.27, камера модалки со слежением). Детали стыка (когда клиент узнаёт о
   прибытии, автооткрытие при неактивной вкладке) — @uidesigner. **Распознавание
   автостарта (критик, среднее M5):** к моменту клиентского рефреша me.flight уже
   null (межзвёздный завершён и удалён сервером), current_position уже in_flight —
   клиент не должен решать «полёт просто закончился»; механизм распознавания
   автостартовавшего сегмента (например, перезапрос /me: current_position с
   status=in_flight + модалка своей системы) зафиксировать в спеке до UX-прохода.
6. **Починка «Найти меня» при межзвёздном (баг 99.2.27 §8.10, решение 4):** 🎯 в
   модалке при активном межзвёздном полёте → закрыть модалку + клик кнопки «Найти
   меня» карты (слежение за кораблём). Диагностика: заполняется ли
   `modalState.interstellarFlight` из /me (`me.flight`), находится ли centerBtn.
7. **Авто-знание планеты** после композитного — уже есть (прибытие на орбиту =
   presence, 99.2.27 §3.6) — повторно не реализуется.
8. **Пакман (критик, среднее M3):** джоб «Пакман» при съедении мира-цели чистит
   намерение (как уже чистит current_world_id/current_position и
   player_intrasystem_flights) — иначе намерение висит на удалённом мире.
9. **Дельта сданной спеки 99.2.27 (критик, среднее M4):** §5.1/§5.5 («для чужих
   систем — только „Перелететь"») изменяется этой фичей — при сдаче обязателен
   явный дельта-абзац в спеках 99.2.27 и новой.

3. **Формулировки — везде «Лететь»** (создатель: «где-то лететь, где-то перелететь…

4. **Компаньоны чужой системы — в скоупе** (создатель: «добавляем»): ПКМ по компаньону
