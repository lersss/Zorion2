## 0. Пожелание создателя (2026-09-21)

> «На странице "Товары" я выбираю конкретную фабрику-дочку (универсальную,
> семейства или расы) и рисую ей рецепты, какие бывают (завожу товары,
> заполняю, из чего они производятся). Причём это не обязательно связанный
> граф будет. То есть любой граф существует только в разрезе какой-то
> конкретной фабрики.»
>
> «Может, стоит рецепты сущность завести сразу? В фабрику просто кидать, какие
> рецепты ей доступны.»

**Уточнения создателя (2026-09-21):**

- Список товаров в справочнике — **общий**; нужен **фильтр по семейству**
  (сократить список; «зачем роевым расам хлеб?»).
- Ресурсы и товары из **других категорий** могут быть компонентами рецепта;
  **выходной продукт — всегда категории фабрики**.
- Ресурсы — **общий пул**.
- **Рецепт — один на товар**; дубли имён запрещены (сравнение в нижнем регистре —
  уже enforced через `name_norm`).
- Товар **не «принадлежит»** фабрике: одна «пища» с одним рецептом может
  производиться и человеческой, и водной фабрикой (разные фабрики — один товар).
- Категория остаётся — это просто справочник-классификация.
- Существующие товары — **мигрировать** (по категории), с возможностью менять
  через справочник.

## 1. Решения создателя (2026-09-21) — модель подтверждена

### 1.1. Модель (подтверждена «да, красиво»)

- **Рецепт — отдельная сущность** (справочник правил «что из чего»), со своими
  свойствами (задел: сложность; в GDD «сложность — поле рецепта»).
- **Состав рецепта** — компоненты: товар/ресурс + количество + галка «ресурс».
- **Связь «фабрика ↔ рецепты»** — какие рецепты фабрике доступны (её граф).
- **Товар — общий словарь** (материал); рецепт ссылается на товары. Товар НЕ
  принадлежит фабрике; одна «пища» (один рецепт) — у нескольких фабрик.
- Рецепт **один на товар** сейчас; схема готова к вариантам (альтернативные
  рецепты) на будущее.
- **Выход рецепта — всегда категории фабрики**; компоненты — любые товары
  (в т.ч. других категорий) + ресурсы (общий пул).
- Категория остаётся — классификация товаров.
- Ветка «Товары» получает **селектор фабрики**: выбранная фабрика → её граф
  (её рецепты, вниз к компонентам/ресурсам; граф может быть **несвязным**).
- **Фильтр справочника по семейству** (предложение): у товара нет своего поля
  «семейство»; семейство товара определяется фабриками-производителями. Фильтр
  по F — товары, которые производит хотя бы одна фабрика, доступная F (своя
  фабрика F + универсальная — та же лестница, что правило «самая конкретная
  фабрика»). Универсальные товары видны всем.
- **Миграция:** существующие товары → фабрике по категории; привязка меняется
  через справочник.
- Дубли имён товаров запрещены (lowercase) — уже enforced.

### 1.2. Архитектурный фильтр (рецепт) — почему сущность

1. **Природа:** рецепт — не событие, а правило/запись; и у него есть **свои
   свойства** (сложность — «поле рецепта» по GDD; оси качества). Значит —
   самостоятельная сущность, а не атрибут товара.
2. **Владелец:** один рецепт нужен **многим фабрикам** (человеческой и водной —
   одна «пища») → связь «фабрика ↔ рецепты» M:N, расширяемая сразу.
3. **Расширяемость:** альтернативные рецепты на один товар лягут в ту же
   таблицу; рецепты **предметов** (лаборатории) — другая механика (другой
   выход), в одну таблицу с товарными НЕ смешивать.

## 2. Нынешнее состояние (факты, 2026-09-21)

- Рецепт сейчас = **состав товара** (`goods_slots`: good_id, pos, component,
  quantity, allow_resource); отдельной сущности нет; рецепт 1:1 с товаром.
- Фабрика-дочка привязана к **категории** (`producer_types.category_id`);
  «цепочка» фабрики = товары её категории (общие для всех фабрик категории).
- Ветка «Товары» — глобальный граф рецептов по категориям; **селектора
  фабрики нет**.
- Имена нормализуются (lowercase/trim/схлопывание пробелов) и дубли запрещены
  (goods/categories/producer_types/items) — `graph.NormalizeName`.

**Корень зависания:** задача «сделать весь UI по ТЗ» выдана одним куском, а
основная правка — **один файл на ~2900 строк**; каждая точечная правка = новая
запись файла, счётчик сторожа набрался до порога, сессия погибла на середине
(проверка и e2e остались за бортом). Ни менеджер, ни разработчик не оценили
объём одной сессии заранее.

**Предлагаемая дельта в `.opencode/agents/manager.md` (шаг 6 «Разработка»):**
«Перед постановкой задачи разработчику оцени объём по файлам: если основная
правка — один файл больше ~1000 строк (напр. `web/studio.html`), разбей задачу на
подэтапы (структура → поведение → проверка/e2e), каждый со своим гейтом, и укажи
дробление в ТЗ; иначе сторож зацикливания режет сессию по счётчику перезаписей
файла и итерация теряется.»

**Область:** коммуникация/постановка задачи (дробление объёма), не процессные
критерии гейтов и не DoD.
