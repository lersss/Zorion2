# Анти-бот проверка добычи: запись вводов и серверный реплей

**Дата:** 2026-09-22
**Вектор:** Новые механики · Игрок
**Статус:** 🟡 **сырая идея — НЕ реализуем сейчас** (решение создателя 2026-09-22: «заводи
отдельной незакрытой идеей, но пока не надо реализовывать»)

## Замысел (алгоритм создателя, 2026-09-22)

Добычу в поясе (и вообще клиентские мини-игры) можно автоматизировать: клиент шлёт события,
не играя. Создатель предложил проверять клиента **пост-фактум реплеем**:

1. **Триггер.** Проверку запускаем, только если заявленная скорость добычи **превышает
   расчётную «живую»** скорость игрока (сервер видит сырой `amount` до клампа). Плюс — редкие
   случайные проверки (умный бот заявляет ровно потолок и под триггер не попадёт).
2. **Меченый астероид.** В момент проверки выпускаем «меченый» астероид (обычные астероиды
   могут летать на клиенте — проверяем только меченый). Сохраняем состояние сцены на этот момент.
3. **Запись.** Клиент записывает вводы игрока за время полёта астероида и отправляет запись
   **одним пакетом** по истечении окна.
4. **Реплей.** Сервер моделирует сцену по записи вводов и сверяет с расчётными данными:
   столкнулся/не столкнулся, угол поворота астероида в момент столкновения и т.п.
5. **Наказание.** Провал проверки → добыча за это окно **не засчитывается** (без урона —
   урон отложен до снаряжения, §10.2).

## Текущее состояние (факт, проверено 2026-09-22)

Сервер уже анти-абьюзит по скорости, но **не проверяет, что игрок играет**:
`internal/handlers/belt_mining_handlers.go` — клампы `beltGranted` (скорость `R_cap·Δ`, запас
пояса, свободный трюм), `beltDeltaSeconds` (`Δt_max = 2 c`), `MiningPosition` ставит
`last_collect_at = now` (первый collect ≈ 0). Потолок `R_cap = 2·R_base·k_iron` (§8.2 спеки этапа 3):
«читер ≤ 2× идеального игрока». **Итог:** мгновенный полный трюм отправить нельзя, но
**автоматизировать сбор можно** — не быстрее ~2× честного игрока. Мини-игру сервер не видит
(вся «игра» — на клиенте).

## Анализ приёмной (2026-09-22)

**Что верно.** Проверка **пост-фактум реплеем** (не в реальном времени) снимает главный риск —
сетевую задержку: сверка идёт офлайн, а игрок уклоняется в реальном времени. Подход масштабируется
на **поверхность** (`web/static/js/surface/*`) — там та же дыра.

**Что нужно, чтобы заработало:**
1. Физика корабля и меченого астероида — **в Go**, идентичная клиентской.
2. Меченый астероид — **серверный секрет** (не выводится из seed пояса, иначе клиент, зная seed,
   предпосчитает всё заранее).
3. Проверять **команды** (реплей), а не «ответ» клиента: клиент шлёт только ввод.
4. Триггер — по сырому `amount` выше «живой» скорости + редкие случайные проверки.
5. Наказание — не засчитывать добычу за окно (v1, без урона).

**Риски:**
- **Детерминизм клиент↔сервер (главный).** Go и JS считают `sin/cos`/float по-разному, а `dt` у
  клиента плавает от кадров. Лечится: клиент пишет в пакет **свой таймлайн** (последовательность
  `dt`), а не только кнопки; сверка — **с допуском**; либо фиксированная/целочисленная арифметика.
  Иначе — ложные срабатывания на честных игроках.
- **Угол поворота** как «отпечаток» — самый чувствительный к детерминизму; брать как
  **дополнительную** проверку с допуском, не единственную.
- **Обрывы связи/реконнект** во время окна проверки — что считать (провал/нейтрально).
- **Сложность:** WS/протокол + физика в Go + жизненный цикл вызова + баланс частоты проверок.

## Открытые вопросы (для дизайна, когда возьмёмся)

- Канал: отдельный WebSocket или HTTP-пакет с записью вводов.
- Точная формула триггера и порог «живой» скорости.
- Допуск сверки (позиция / время / угол).
- Наказание: только текущее окно или буфер всего захода.
- Роль урона (отложено до снаряжения).
