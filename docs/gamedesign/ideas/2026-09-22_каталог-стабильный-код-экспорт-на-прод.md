## 1. Суть

1. **Рабочий процесс — «в базе».** Создатель правит каталог через студию, студия
   пишет прямо в БД; код-сид остаётся только стартовым наполнением пустой базы.
2. **Нужен экспорт/перенос** контента из рабочей базы на прод (и вообще между
   средами).
3. **Нужна стабильная идентичность записи каталога** — короткий `code`, не зависящий
   ни от `id` (автоинкремент, в каждой базе свой), ни от `name_norm` (меняется при
   переименовании). Без неё экспорт/перенос и ссылки из кода/генератора не
   переносимы.

## 6. Сидер — что это и как связан с идеей

**Сидер** — программное стартовое наполнение пустой базы: Go-код, который при **первом**
старте сервера заливает в БД базовый контент. Работает **один раз** — защищён маркером
в `generation_config`:

- `goods_catalog_seed` (`internal/goodsstudio/seed.go`) — базовый каталог (131 ресурс +
  категории);
- `producer_catalog_seed` (`internal/goodsstudio/seed_producers.go`) — типы построек
  (класс «Поселение» + 7 ступеней, фабрика, автофабрика, добывающая платформа,
  энергостанция, 3 лаборатории) + предметы + связи.

Есть маркер → повторные старты сид **пропускают**. На **существующей** (dev) базе маркер
уже стоит, поэтому сидер молчит, а всё, что создатель правит в студии, живёт только в
этой БД. На **свежей** (прод-подобной) базе маркера нет → сидер заливает базовый контент.

**Почему всплыло:** создатель переименовал в студии класс и ступени, а сидер и доки знают
**старые** имена:

| | в dev-БД (студия) | в сидере (свежая база/прод) |
|---|---|---|
| класс (тип-родитель) | **Колония** | `Поселение` |
| ступень-пол | **Форпост** | `Аутпост` |
| следующая ступень | **Поселение** | `Посёлок` |

Причём локальный ключ ступени в студии — тоже `поселение` (id 155), то есть имя класса в
сидере и имя ступени в dev-БД **совпадают**. Отсюда два риска на свежей базе/проде:

1. Прогон сидера вставил бы класс `Поселение` и ступень `Посёлок` (`ON CONFLICT
   (name_norm) DO NOTHING`) — то есть **старые имена**, и вернулась бы путаница
   «класс = ступень»;
2. `default_settlement_type_id` в сидере цепляется к `Аутпост` **по имени** → на
   переименованной базе ключ уедет не на «Форпост».

**Вывод:** сидер и переименование должны быть согласованы. Два пути (решение — создатель):

- **(1) Переименование — часть канона.** Сидер (и доки, и тесты-фикстуры) приводим к
  именам класса «Колония», ступеней «Форпост»/«Поселение»/… ; `default_settlement_type_id`
  цепляем к коду ступени-пола (`code`, не имя) — тогда это и есть «конфиг вгрузить» для
  свежей базы.
- **(2) Оставить канон-имена.** Тогда переименование в студии — локальная косметика dev-БД;
  для свежей базы она не даёт эффекта.

Это часть той же задачи «синхронизация dev → прод»: экспорт контента + загрузка конфига,
и обе опираются на **стабильный `code` записи** (п.1.3 этой идеи). Адрес: сидер/тесты —
`@developer`, доки — `@dispatcher`, дизайн — `@designer`.

### Решения создателя по спеке (2026-09-24, гейт дизайна)

1. **Настройки генерации не переносим** — только контент (+ ссылка-якорь
   `default_settlement_type_id`). *«1. нет»*.
2. **Импорт — полная замена:** контент, которого нет в файле, **удаляется**
   (прод = точная копия dev). *«2. да»*. Осознанно опаснее дефолта: потерянная при
   выгрузке запись пропадёт и на проде — риск зафиксировать в спеке.
3. **Правки прода импорт перезаписывает** (dev — источник истины, last-write-wins).
   *«3. да»*.
4. **Проверка целостности — дефолт:** минимальные проверки + атомарность, полную
   валидацию студии не дублируем. *«4. дефолт»*.
5. **Метка записи — цифровая/номерная** (`p_0001`, `g_0142`, бессмысленная, не из
   имени): не «врёт» при переименованиях, в отличие от описательной. Решение создателя
   *«дак пусть метка будет цифровой»* после обсуждения, что `id` для переноса **не
   годится** (номера не совпадают между базами; по `id` ссылаются объекты мира).
   Тайминг (сразу/итерацией) — **уточняется**.

**Замечание по п.2 (полная замена) и п.5 (метка):** «удалять то, чего нет в файле»
безопасно только при надёжном сопоставлении записей — то есть по метке, а не по имени
(при переименовании запись «исчезла бы» из файла и была бы удалена на проде вместе со
связями). Связка «полная замена ↔ метка» — довод в пользу того, чтобы метка была
**сразу**, а не третьей итерацией; вынесено создателю.

**Где стоим.** И1 (метки `code` + канон-имена) и И2 (экспорт-снимок) сданы и в origin
(`09e9f41`, `7e32fa3`, `eb8f801`). Спека готова: `docs/specs/2026-09-24-каталог-экспорт-импорт-контента-на-прод.md`
(§5 алгоритм, §7 UI, §9 тесты T3–T15). Решения создателя закрыты (§12). Открыт хвост 39
(реестр — узел заведён, досверить автосверку) и И3 (в `EPICS.md`).

**Спека и ориентир.** Импорт `POST /studio/api/content/import` (тело `{}` — файл с диска,
или `{"snapshot":{...}}`; параметр `dry_run=true`), одна транзакция + `pg_advisory_xact_lock`
(паттерн `beginMutation`), атомарный отказ при любой ошибке.

**Задача следующего чекпоинта (сжато):**
1. Режим сопоставления (§3.5): все без метки → первичная накатка по `(kind,name_norm)`;
   все с меткой → штатный по метке; **смесь → отказ**.
2. Порядок секций топологически: `categories → goods → recipes/recipe_components →
   producer_types` (родители раньше детей) `→ items → producer_slots/producer_recipes/
   producer_items → effect_types`.
3. Upsert по метке; **`id` не меняются** (мировые FK целы); дочерние наборы — `DELETE`+`INSERT`
   целиком (листья).
4. Ссылки — по картам (метка→id); `items.unlocks` → в БД id-форма.
5. **Полная замена:** удаление «чего нет в файле» — по метке; **предсчёт мировых ссылок**
   (независимо от `ON DELETE`; каскад — ловушка) → любая ссылка = `blocked` + отказ 409.
6. `default_settlement_type_id` — резолв по метке якоря; не найдено → отказ.
7. `dry_run` — тот же алгоритм с `ROLLBACK`, возвращает дифф (`create/update/delete/blocked/unmatched`).
8. UI: кнопка «Импорт» двумя шагами — «Проверить» (дифф) → «Применить» (2-е подтверждение);
   `blocked/unmatched` непусты → «Применить» неактивна.

**Рамки/безопасность:** бэкап перед первым применением (В4); dev — источник истины (перезапись
правок прода); настройки генерации не переносим; валидация — минимальная (дефолт O5). Импорт —
самая «трогающая много файлов» часть: запускать на **чистом дереве** (без чужих незакоммиченных
линий), коммит — с разделением хунков при переплетении.

**Тесты:** T3–T13 + T15 (полный список — спека §9). Обязательно живой PG (`internal/integration/`)
на: экспорт→импорт в пустую БД; идемпотентность 0/0/0; блок удаления живой записи; `dry_run` без
записи; bootstrap на цели без меток. Плюс контракт студии на две кнопки.
