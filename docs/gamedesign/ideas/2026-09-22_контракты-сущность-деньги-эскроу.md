## 1. Решения создателя (свод)

1. **Оборот высокий** — контракты массово открываются/закрываются/выполняются/отменяются; модель хранения обязана это держать.
2. **Деньги — делаем** (новая сущность; база под эскроу).
3. **Авторы — все сразу:** постройки, игроки, фракции, отдельные агенты.
4. **Место — планета.** Витрина — карточка планеты (вкладка «Задания/Контракты»), агрегирует **все** источники. Привязка «к миру» — неправильно, убирается.
5. **Первый тип — перелёт.**
6. **Исполнитель — один** (мульти-участник/операция — позже).
7. **Деньги:** полноценный счёт — у игрока; казна/бюджет — у фракций, поселений, построек (принято).
8. **Исполняют и игроки, и NPC-агенты.**
9. **Язык требований (окно свойств)** — дизайнер предлагает модель, создатель решает по реализации.

### Решения после критика (2026-09-22)

10. **История контракта — свой отдельный лог** (как у поселения); общую систему событий не строим и мёртвый общий журнал не оживляем. Создатель делегировал («не моя экспертная область») — решение менеджера, взято простое и совпадающее с каноном. **Снимает K1.**
11. **Залог — со счёта владельца.** Поселение/постройка кому-то принадлежат → залог платит **общий счёт владельца**. **Снимает K2.**
12. **Деньги фракций — практически бесконечные** (очень большое число) на этот релиз; экономика фракций — позже. **Снимает C1.**
13. **Валюта единая** — поле «валюта» у контракта не вводим (канон: мультивалютности нет). **Снимает C3.**
14. **Валюта/имущество:** остальные средние — по предложению менеджера (§5.1): NPC-агент получает бюджет от владельца-фракции; постройки-заказчики — после появления у построек производства/казны; «место-планета» — доска на планете, перелёт задаётся системой→системой, задержку доставки в первой итерации не вводим; язык свойств — проектируем заново (окон как структуры в коде нет). **Статус средних — «принято по умолчанию», уточняются на гейте дизайна.**

## 2. Архитектурный фильтр (приёмка)

1. **Природа — состояние + свой лог.** Контракт живёт и меняет статус (состояние). Его жизнь (взял → поставил → провалил → отменён) — отдельная таблица-лог `contract_log` (как `settlement_log`), а **не** общий `events` (решение 10: общую систему событий не строим, мёртвый общий журнал не оживляем).
2. **Владелец — многие.** Автор полиморфный: тип + id (игрок/фракция/постройка/агент). Уже так устроен муляж — сохраняем.
3. **Расширяемость — открытый список типов.** Не колонка-на-тип, а `type` + «нагрузка типа» (payload JSONB под специфику: A→B для перелёта, доля для охраны, окно сбора для операции).

**Оборот (решение 1) — следствия для хранения:** доска читает только живые контракты (индекс «планета + статус»); закрытые уходят из горячего запроса и живут историей в **своём `contract_log`** (не в общем `events`); никаких полносканов; срок истекает ленивым свипом (как население/полёты — без тика).

## 3. Факты (сверка с кодом, 2026-09-22)

- **Муляж уже есть:** `assignments(world_id, author_type, author_id, title, description, type, reward, expires_at, status, effects, created_at, updated_at)`. Статусы `open → taken → completed` (`expired` объявлен, но не реализован). Типы-заглушки: `tech/agri/military/trade/mixed/test`. Хендлеры: `GET /api/contracts`, `POST /api/contracts/take`, `POST /api/contracts/complete-test`. Фронт — `web/contracts.html` (список + фильтры).
- **Мёртвый дубль:** `internal/models/contracts.go` (`Contract` с `SystemID` и `Effects`, без типа/награды) — нигде не подключён.
- **Денег нет вообще:** ни счёта игрока, ни казны, ни эскроу. `models/economy.go` — это поселения (население/стабильность), не деньги. GDD: «кошелёк поселения — лимит, а не счёт» (`GLOSSARY.md` §Кошелёк поселения), «балансы приватны, платёжеспособность доказывается эскроу».
- **Язык свойств частично есть:** ресурсы хранят свойства в `goods.props` JSONB; рецепты — `recipes`/`recipe_components` (компонент + количество). Готового «окна свойств» (свойство ≥ порога) как структуры пока нет — его надо спроектировать.
- **Авторы существуют как сущности:** `buildings` (000056), `factions`, `npc_agents` (000026), `users`. Привязки контракта к ним нет.
- **Общий журнал:** таблица `events(aggregate_id, aggregate_type, event_type, data, created_at)` — **мёртвая, не используем** (решение 10); историю контракта несёт свой `contract_log`.

## 4. Модель (предложение; финализирует @designer)

- **Деньги/эскроу:** счёт игрока (реальные кредиты, можно обнулить) + казна/бюджет фракций, поселений, построек, агентов + **залог** (эскроу): средства запираются при публикации, освобождаются при выполнении или возвращаются заказчику при провале/истечении.
- **Контракт (состояние):** `id`, автор (тип+id), тип, заголовок/описание, **планета публикации** + цель (для перелёта), цена, признак «подряд» (реальные деньги) и валюта, залог (сумма+состояние), срок, статус (черновик → на доске → взят → частично → выполнен / отменён / истёк), видимость (публичная доска / прямой), `payload` типа (JSONB).
- **Требования (окно свойств):** дочерние строки — свойство/категория + сравнение + порог + количество (единый язык с рецептами и ресурсами).
- **Поставки (частичное исполнение):** контракт + исполнитель + что и сколько сдано + когда.
- **Участники** (мульти-исполнитель, операция) — **позже** (решение 6: сейчас один).
- **История:** свой лог `contract_log` (взял/поставил/провалил/отменён) — как у поселения, не через мёртвый общий `events` (решение 10).
- **Легаси под нож:** `assignments` развиваем в `contracts`; `models/contracts.go` (мёртвый дубль) сносим.

## 5. Что предстоит решить дизайнеру (к гейту)

1. Расхождения муляжа с дизайном (место: мир → планета; статусы; залог; требования).
2. Форма «окна свойств» и его состыковка с `recipes`/`goods.props`.
3. Цена и срок перелёта (GDD: цена = топливо A→B + малая надбавка; срок выводится из времени полёта + запас) — числа для @balancetester.
4. Эскроу: одинаково ли у всех авторов; как «казна/бюджет» фракции соотносится с залогом (реальные накопления vs неограниченный источник).
5. Как считаем «доску» на карточке планеты (агрегация источников, пометка автора, видимость).
6. Порядок итераций (см. §6) — в частности, что именно из «всех авторов сразу» попадает в первую итерацию автоматической генерации, а что — ручным инструментом.

## 5.1. Находки @critic (2026-09-22, до спеки) — статус «ждёт решения создателя»

**Крупные (жёсткий стоп):**
- **K1. Журнал контракта в общий `events`** противоречит решению «общую систему событий не строим» (`18b_settlement_log.md` §«лог поселения»; `PITFALLS.md` «Событие против лог»); `events` сейчас мёртвая таблица. Либо у контракта свой отдельный лог (как у поселения), либо передумываем про общую систему.
- **K2. «Казна/бюджет у поселений»** противоречит канону «кошелёк поселения — лимит, а не счёт, баланса нет» (`14_money.md` §14.3.0, `GLOSSARY`). Эскроу требует блокировки баланса, которого у поселения по канону нет.

**Средние (звоночек создателю):**
- **С1.** Казна фракций как источник награды — канон `14_money.md` §14.2 отклонял «внешнего покупателя» (фракция не привилегированный эмитент); источник наполнения казны не назван.
- **С2.** NPC-агенты: текущая модель (`npc_agents`, 000026) — мирокоординатная, без бюджета; планетарный перелёт + оплата требуют бюджета и торговли, которых у агента нет.
- **С3.** Поле «валюта» в контракте — канон: валюта единая, мультивалютность не вводится (`14_money.md` §14.5.1).
- **С4.** «Окно свойств»: в коде окна как структуры нет, `recipe_components` — конкретные компоненты, не окна; риск второго языка свойств.
- **С5.** Постройки как авторы преждевременны: `buildings` (000056) — только столица, без производства и денег.
- **С6.** «Место — планета»: перелёт по канону привязан к системе (`11_contracts.md` §11.3.4), а деньги описывают контракт как «пакет» с задержкой появления на доске назначения (`14_money.md` §14.5.2/§14.6.1).
- **С7.** Легаси-потребители `assignments` перечислены неполно (ответ мира, страница заданий `/assignments`, тесты, очистка вселенной, пакман, `impact_map`).

**Мелкие (правим сами):** внутреннее противоречие про частичную поставку (§4 vs §6); термин «бюджет» — в каноне это форма эскроу, а не касса; расхождение списка владельцев казны (§1 vs §4); неполный фронт (не упомянут существующий `assignments.html`); эскроу сведён к одной форме из трёх.

## 5.2. Находки @critic и @balancetester по спекам (2026-09-22, после дизайна)

Спеки: `docs/specs/2026-09-22-контракт-модель-сущности.md`, `2026-09-22-деньги-и-эскроу.md`, `2026-09-22-контракт-перелёт-и-доска.md`.

**Крупное (жёсткий стоп):**
- **K1.** Залог теряется при очистке вселенной / генерации / перегенерации планет: контракты удаляются (TRUNCATE/каскад FK), а кошельки игроков сохраняются — деньги пропадают. Противоречит канону замкнутой массы и собственному правилу спеки (для пакмана возврат залога прописан, для остальных путей — нет). Пути: `clearUniverseTx`, `GeneratePlanets`, `RegeneratePlanets`.

**Средние:**

- **С2.** Правило закрытия перелёта не различает цель-систему и цель-планету — закроет контракт при прибытии к звезде, даже если цель — планета.
- **С3.** Новый игрок (после миграции) не получает счёт — основная петля «новичок берёт перелёт и получает оплату» ломается.
- **С4.** «Подряд» (деньги за реальную оплату, две корзины) не учтён ни в контракте, ни в счёте — при вводе подряда потребуется переделка схемы.
- **С5.** Пакман не чистит контракты с мёртвой целью (`payload.dest_world_id` съеденного мира), если планета публикации жива.

**Балансировщик — В1** (противоречие + эталон чисел не задан): вариант «цена = k·дистанция» без топлива превращает **всю** награду в чистый доход исполнителя (≈36.7 кр/с ≈ 2 200 кр/мин; удвоение стартового капитала за ~4.5 мин) — нарушает инвариант «перелёт не заработок». Плюс: обоснование радиуса карты неверно (2500 — радиус кластера, карта — до 45 000), `min_reward` мёртв, срок считается от публикации (капкан «взял перед истечением»), `PlayerBalanceSeed` разошёлся с ценой. Маршрут матрицы: **вернуть @designer на анализ противоречия**.

**Мелкие:** неполный список потребителей `assignments` (доки/QA/ARCHITECTURE); формулировка «по образцу `settlement_log`» при отсутствии FK; `subject='engine'` вместо параметра `speed_factor`; внутренние расхождения денежной спеки (строка `settlement` в резолве); `CHECK escrow_amount` vs обнуление при release/return; в идее остались упоминания `events` (исправлено).

## 6. Итерации (трекер, предложение менеджера — подтверждается на гейте дизайна)

### Спека 1 — Деньги и эскроу (фундамент)
- Счёт игрока (кредиты), операции начисления/списания.
- Казна/бюджет авторов-не-игроков.
- Залог (эскроу): запирание при публикации, выплата при выполнении, возврат при провале/истечении.

### Спека 2 — Контракты: сущность + доска + перелёт
- Сущность контракта (состояние + требования + поставки + журнал).
- Доска на карточке планеты, агрегирует все источники, вкладка «Задания/Контракты».
- Тип «перелёт»: публикация A→B, цена = топливо + надбавка, закрытие по прибытии; берут **игрок и NPC-агент**.
- Публикация контракта всеми типами авторов (игрок/фракция/постройка/агент) — начиная с ручного инструмента.

### Этап B1 — ядро контрактов + эскроу + снос легаси ✅ реализован 2026-09-22 (ждёт коммита)

- Миграция `000062`: `contracts` (+CHECK-и, частичные индексы), `contract_requirements`, `contract_log` (FK нет — лог переживает удаление), `DROP TABLE assignments`.
- Модель `models/contract.go`; снесены `models/assignment.go`, мёртвый дубль `models/contracts.go`.
- Репозиторий: публикация (одна tx: залог-lock + `escrow_withdrawable` + журнал), атомарные `take`/`cancel`/`complete`, `ExpireDue` (ленивое истечение), `ReturnEscrowForContracts` (атомарный статусный flip §6.5), резолв плательщика.
- Возврат залога во всех путях удаления: очистка/генерация вселенной, гипотезы, генерация/перегенерация планет, удаление мира, пакман (+ контракты с мёртвой целью). Везде — одна tx.
- API: доска планеты (гейт знанием), «мои контракты», взять, отменить, публикация игроком, админ-публикация; снесены страницы `/assignments` и `/contracts`, ключ `assignments` из ответа мира, тестовый путь Assignment.
- Тесты: репозиторий (переходы/гонки/эскроу/истечение/возврат) + хендлеры (8). Ревью: «ок с замечаниями», блокирующих нет; оба ключевых инварианта (залог не теряется; `withdrawable ⊆ balance`) подтверждены; дофорс — `gofmt`.
- **Бэклог B1 — ✅ закрыт 2026-09-22** (хвосты, без окна коммита не оставляем; тестер 7/7 PASS):
  - мёртвый экспорт `ReturnEscrowForContracts` — удалён (вызовов не было);
  - `ContractScope.All` (футеган) — убран; пустая область `ContractScope{}` = вся таблица;
  - `Complete` не завершает просроченный `taken` (`AND expires_at > NOW()`, тест); при проводке прибытия (B2) — сперва `ExpireDue`;
  - `AdminCreateContract` берёт планету **из автора** (`ResolvePublicationPlanet`: faction→`homeworld_id`, building→`planet_id`, player→позиция игрока, agent→400 в итерации 1), тело игнорируется; 5 тестов + живая проверка;

### Этап B2a — тип «перелёт» (флоу игрока) ✅ реализован 2026-09-22 (ждёт коммита)

- Публикация перелёта: payload `from_world_id`/`dest_world_id`/`dest_planet_id` (nullable) валидируется; сервер сам добавляет требование `gear/speed_factor le 0.3` (если не задано — «двигатель не хуже референсного») и форсит `funding='regular'` (подряд у перелёта невозможен, Р8).
- Взятие: проверка двигателя при взятии (нет двигателя → отказ; формула переиспользует `ship.HasEngine`/`EngineSpeed`, как `/travel`); срок **перебазируется от взятия** `max(dist·0.3,3с)·1.5` (капкан «взял перед истечением» закрыт, §4.3).
- `offer_window` на доске для перелёта выводится (`flight_time_ref·10`), клиентский `expires_at` для travel игнорируется.
- Закрытие по прибытии в **двух точках** (§1.1): цель-система — межзвёздная (`ArrivalHandler`, `dest_planet_id IS NULL`); цель-планета — внутрисистемная (`NewIntraArrivalHandler`). Порядок «истечение → завершение», весь проход `CloseTravelArrivals` — **одной транзакцией** (награда не теряется при сбое). Работает и в Restore.
- Модель `ContractTypeTravel`; `Take` принимает перебазированный срок; `takeContractSQL` — `COALESCE($5::timestamptz, expires_at)` (типизированный каст против ловушки lib/pq untyped NULL). Миграция не нужна (payload/requirements из 000062).
- Ревью: «ок с замечаниями», крупных нет; все три закрыты в доработке (двигатель обязателен, срок не перекрывается телом, одна tx). Тестер: 9/9 PASS + живой довесок (перезапуск сервера во время полёта — контракт закрылся на новом инстансе, +500 `escrow_release`).
- **Осознанное упрощение (комментарий в коде):** `from_world_id` не сверяется с позицией берущего — перелёт = «проездной билет» A→B; ограничения места во взятии нет ни в каноне, ни в спеке (не «додумывать» проверку).
- **Не входит (следующие подэтапы):** B2b — агент-исполнитель (`NPCManager.processArrivals`, взятие при совпадении маршрута); B3 — доска во фронте.

### Этап B2b — агент-исполнитель перелёта ✅ реализован 2026-09-22 (ждёт коммита)

- **Взятие агентом — только при совпадении маршрута** (О-п8): отдельного поиска контрактов у агента нет; планировщик `NPCManager` выбирает цель сам, и если из текущей системы есть открытый перелёт с этим `dest_world_id` и без планеты-цели — берёт его. Требование к двигателю к агенту не применяется (своя `npcSpeedFactor`).
- **Только цель-система:** агент физически не видит контракты с `dest_planet_id` (у него нет внутрисистемного движения) — не может закрыть на звезде преждевременно.
- **Закрытие по прибытии** — шаг в `NPCManager.processArrivals` (свой путь прибытия агента, не `ArrivalHandler`): батч `CloseArrivedTravels` (одна tx на тик, порядок истечение→завершение), залог уходит счёту `agent`.
- **Перебазирование срока при взятии агентом** — как у игрока (правило типа travel §4.3, не флоу игрока): иначе агент, берущий контракт в конце окна, истекал в полёте и терял награду.
- **Одна точка формулы:** срок/длительность вынесены в `models` (`TravelDuration`/`TravelDeadline`/`TravelOfferWindow`) — зовут и игрок, и агент; дубликат `npc.FlightDuration` сведён к обёртке. Найдено расхождение формул (игрок округляет до целых секунд, NPC хранил доли) — принята формула игрока (поведение игрока не меняем; разница <1с на тике).
- **Убран висяк:** агент берёт контракт после успешной записи статуса — при сбое контракт не остаётся `taken` за нелетящим агентом.
- Новые файлы: `internal/repository/travel_contract_repository.go` (методы контрактов NPC-перелётов на общем `*ContractRepository` — файловое разделение, SQL переходов общий `expireDueTx`/`completeTx`), `internal/npc/contracts.go` (интерфейс `ContractStore`), `internal/models/contract_travel.go` (формулы). Миграция не нужна (`npc_agents.owner_faction_id` есть с `000061`).
- Ревью: «ок с замечаниями», блокирующих нет; три замечания закрыты (одна точка формулы, висяк, комментарий). Тестер: 11/11 (живой прогон агентом — SKIP: нужен сгенерированный мир с агентами; цель планировщика случайна; юнит-интеграция на реальном SQL покрывает пути).
- **Известные ограничения итерации 1** (не чиним): `visibility='public'` при взятии не фильтруется (у игрока так же — консистентно); `CloseArrivedTravels` читает всех taken-агентских перелётов на тик (при росте — сужение по `executor_id = ANY(...)`); не-атомарность «контракт ↔ статус агента» закрыта порядком записи.
- **Не входит:** агент-автор и агентда-автогенерация контрактов; B3 — доска во фронте.

### Этап B3 — доска контрактов во фронте ✅ реализован 2026-09-22 (ждёт коммита)

- Вкладка «Задания/Контракты» карточки планеты (`web/static/js/modal/contracts.js` + `tabs.js` + кнопка в `panel.js`): тип, заголовок, цена, «осталось N», требования читаемо («двигатель не хуже 0.3»), пометка автора (иконка+тип). Взятые/закрытые/прямые на доске не показываются (сервер).

После правок — «ок с замечаниями». Тестер: 9/9 PASS, e2e 7/7 (реальный клик «Взять → 200»), живой цикл публикация→доска→взятие→«мои».
- **Осознанные усечения итерации 1 (серверные, в другой релиз — решение создателя 2026-09-22):**
