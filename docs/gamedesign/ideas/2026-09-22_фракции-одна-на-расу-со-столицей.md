## 1. Почему это задача (факты разведки 2026-09-22)

- Фракции создаются **только кнопкой** `POST /admin/generate-factions`; в БД их 0 — кнопку не нажимали.
- Текущая логика: 1–3 фракции **на каждую обитаемую планету**. Обитаемых планет **32 001** → одно нажатие дало бы **32–96 тыс. фракций и столиц**. Это и был риск.
- Канон `06_factions.md` §6.1: «1–3 фракции на планету. Это присутствие, а не количество: **одна фракция присутствует на многих планетах**». То есть текущая реализация — отступление от канона.
- Рас в каталоге `config/races.json` — **60**. Заселено — **29** рас (по одному поселению на планету, `settlements.race_id` заполнен у всех заселённых).
- Новая логика даёт **~29–30 фракций** — разумный масштаб.
- `factions` **не знает расы** (колонки `race_id` нет) → нужна миграция.

## 2. ТЗ в разработку

**Цель:** одна фракция на расу, у каждой — своя столица на родной планете расы. Идемпотентно.

1. **Миграция** `migrations/000066_factions_race.sql` (номер свободен; проверить glob перед созданием):
   - `ALTER TABLE factions ADD COLUMN IF NOT EXISTS race_id TEXT;`
   - `CREATE UNIQUE INDEX IF NOT EXISTS uq_factions_race ON factions(race_id) WHERE race_id IS NOT NULL;`
2. **`internal/generator/faction/faction.go` — `GenerateFactions()`:** вместо «планет с поселениями» — **расы с поселениями**:
   - кандидаты: `settlements` с `race_id IS NOT NULL AND race_id <> '' AND population > 0`, сгруппированные по расе;
   - родная планета расы = планета с **наибольшим** населением среди её поселений (при равенстве — меньший `planet_id`, детерминированно);
   - фракция уже с таким `race_id` — пропускается (идемпотентность; повторный прогон только добивает недостающие);
   - поля: `race_id`, `homeworld_id` = родная планета, `name` = **название расы** (из каталога `internal/races`, fallback — `race_id`), `type` = как раньше (`randomFactionType`), ресурсы/цвет/описание — как раньше (в описании — название расы и планеты);
   - в конце — `EnsureCapitals()` (столица на `homeworld_id`, как сейчас, идемпотентно);
   - возврат: (число **созданных** фракций, число созданных столиц).
3. **`internal/handlers/admin_universe.go` — `GenerateFactions`:** `total` (для статуса джоба) = число рас-кандидатов вместо числа планет; гейты (`JobPacman`, `universeMutationMu`) и ветка `total == 0` — без изменений.
4. **Тесты:** существующие мокают старые запросы — обновить; добавить: «одна фракция на расу», «идемпотентность повторного прогона», «столица на планете крупнейшего поселения расы», «раса без поселений пропускается».
5. **DoD** (`AGENTS.md` §2): `go build`, `go vet`, `go test -race -short` (генераторные пакеты исключены).
6. **Живую генерацию на dev-БД не запускать** — отдельное решение (данные 32k планет / 29 рас).
7. Локейт в `docs/COORDINATION.md`: `migrations/000066*`, `internal/generator/faction/*`, `internal/handlers/admin_universe.go`.

### Принятые допущения (мои решения, «пока так»)

- Расы **без поселений** (31 из 60) — фракция не создаётся (столицы негде поставить).
- Одна фракция = одна раса; `race_id` уникален.
- Имя фракции — название расы; тип остаётся случайным.
- Присутствие фракции на других планетах (канон §6.1) — **не в этой задаче**.

## 3. Решения создателя (2026-09-22, по звоночкам @critic)

1. **Действует то, что сказано последним** — новое решение (одна фракция на расу) отменяет прежнее «1–3 фракции на планету, генератор не менять»: старые записи доков правим под новую модель.
2. **Две столицы на одной планете — допускаем.** Если родные планеты двух рас совпали, на планете стоят две столицы; ограничение «одна столица на планету» не вводим.
3. **Число фракций связано с числом заселённых рас** — «пока да».
4. **Сейчас делаем только фракции рас** — владение поселениями расы (фракция → её поселения) и присутствие на многих планетах — **не в этой задаче**.
5. Имя фракции = название расы — остаётся (отдельный генератор имён «раса + тип» не вводим).

Крупных противоречий критик не нашёл; средние сняты решениями выше.
