> «некоторые поля в админке, похоже, недоступны админам, только роли skycomposer. При этом админам сыплются уведомления 403 при заходе в админку. Они не нужны»

Уточнения:

> «сразу после входа, на любой вкладке почти»
> «похоже просто те разделы, которые мы скрыли для роли admin и оставили только skycomposer, выдают ошибку 403 явно, а их просто не надо показывать и все»

Решение создателя по фиксу: «ок» (2026-09-23) — гейт UI брать по той же роли, что проверяют ручки (роль из токена).

## 1. Диагноз (менеджер, воспроизведено вживую 2026-09-23)

Гипотеза создателя (скрытые разделы) **не подтвердилась**: у свежего админа
(вошедшего заново) 403 нет ни на одной вкладке — все `/admin/*` ручки, кроме
`/admin/users` (только skycomposer, вкладка у админа скрыта), отвечают 200.

**Настоящая причина — рассинхрон роли.** Панель пускает внутрь по роли **из
базы** (её отдаёт `/me`), а админские ручки проверяют роль **в токене**, выданном
при входе. Если роль поменяли **после** выдачи токена (например, игрока повысили
до админа, а он остался в старой сессии), панель его впускает, но каждый
админский запрос отвечает 403.

Воспроизведение: завёл обычного игрока → повысил до `admin` прямо в БД →
**не перелогиниваясь** открыл `/admin`. Результат: вход прошёл, и сразу тост
«Не удалось загрузить поля: HTTP 403», плюс 403 почти на каждой вкладке
(`/admin/settlement-settings`, `/admin/biome-catalog`, `/admin/stats`,
`/admin/worlds`, `/admin/generate-status`, `/admin/npc/*`, `/admin/balancer/*`,
`/admin/resources`, …). У свежего админа — чисто.

Тот же класс — дословно как «разделы, оставленные skycomposer»: если админа
повысили до skycomposer без пере-входа, `/me` отдаёт `skycomposer`, вкладка
«Пользователи» показывается, а `/admin/users` проверяет роль в токене (`admin`)
→ 403.

## 2. Решение

Роль для UI-гейта должна совпадать с ролью, по которой авторизуют ручки, —
то есть с ролью **из токена**. Меняем отдачу роли текущего пользователя:
- `internal/handlers/auth_handlers.go` (`GetMe`) — поле `role` брать из контекста
  запроса (`auth.RoleKey`, её кладёт `AuthMiddleware`), а не из БД. Пусто в
  контексте — фолбэк на роль из БД (юнит-тесты `/me` без контекста роли).
- `internal/handlers/surface_handlers.go` — то же для поля `role` ответа
  поверхности (тот же класс: роль самого игрока для UI-гейта).

Роль **других** пользователей (`/admin/users*`) остаётся из БД — это правильно.

**Зачем:** устаревший токен не пустит в панель вовсе (сразу окно входа) — нет
403-спама; а разделы, недоступные текущей роли, не показываются сами. Правка
чинит это разом для админки, карты, студии и поверхности (все гейтят по `/me`).

## 3. ТЗ (быстрый путь, сервер)

1. `GetMe`: `role` в ответе — из `r.Context().Value(auth.RoleKey)`; пусто —
   фолбэк на `user.Role` (БД). Значение по умолчанию для токена без роли уже
   `player` (`VerifyToken`).
2. `surface_handlers.go`: поле `role` ответа — так же из контекста (фолбэк — БД).
3. Тест (TDD): `GetMe` отдаёт роль из контекста, а не из БД (например, БД =
   `admin`, контекст = `player` → `role == "player"`; и наоборот). Аналогично для
   поля роли поверхности, если правим.
4. Ничего в клиентах не трогаем — они уже читают `role` из `/me`.

**Не трогаем:** логин/регистрацию (там токен свежий, роль совпадает), ручки
`/admin/users*` (роль других — из БД).
