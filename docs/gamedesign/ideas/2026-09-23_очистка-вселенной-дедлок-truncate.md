# 2026-09-23. «Очистить вселенную» падает с дедлоком (TRUNCATE × фоновый NPC-тик)

**Вектор:** Баги (админка → Очистка)
**Приоритет:** средний (баг некритичный: операция откатывалась целиком, данные целы, повтор обычно проходил)

## 0. Пожелание создателя (дословно)

> «❌ Ошибка: Failed to clear universe: truncate: pq: deadlock detected»

> «При удалении вселенной»

## 1. Диагноз (менеджер, по коду и логам)

Ошибка приходит из шага TRUNCATE внутри транзакции очистки
(`clearUniverseTx`, `internal/handlers/admin_universe.go:84`). Это **дедлок
двух транзакций**, а не ошибка схемы (та была раньше и уже починена — в логе
`server_stderr.log` видна старая `cannot truncate a table referenced in a
foreign key constraint` и успешная очистка за 353 мс).

**Механика цикла.** TRUNCATE берёт `ACCESS EXCLUSIVE` на таблицы из списка
по порядку: `worlds` (1-я) … `contracts` (4-я) … `npc_agents` (15-я). Фоновый
**NPC-тик** (одна горутина, каждые 5 с, `internal/npc/manager.go:329`) делает
`UPDATE npc_agents SET current_world_id = …` (`statusBatchArrivalQuery`,
`npc_repository.go:258`). Столбец — внешний ключ на `worlds`, поэтому UPDATE
берёт `KEY SHARE` на нужную строку `worlds`. Получается цикл:

- TRUNCATE уже держит `worlds` и ждёт `npc_agents`;
- NPC-тик держит `npc_agents` и ждёт `worlds` (KEY SHARE под FK).

Postgres убивает одну из транзакций — очистку, целиком (данные не портятся,
откат). Тот же класс подтверждён наблюдением в QA-прогоне 2026-09-23:
«Postgres отдал `deadlock detected` на `npc_agents` (две транзакции ждали
`KEY SHARE` друг друга)».

**Почему гейт не спасает.** `universeMutationMu` (`admin_universe.go:30`)
сериализует только админские операции между собой (Clear / пакман / фракции /
залежи). Фоновый NPC-тик под него **не** заходит и продолжает писать во время
очистки. Авто-повтора на дедлоке в коде нет (проверено `rg` по `40P01`/`retry`).

**Кого ещё может задеть:** любой конкурентный писатель, обновляющий строку со
ссылкой на `worlds` (тик — всегда включён; плюс игроки: `users.current_world_id`,
планы полётов, знание). Значит, дедлок принципиально возможен, а не разовый.

## 2. Направление фикса (принято)

Наиболее устойчивый и точечный — **авто-повтор транзакции очистки на дедлоке**
(SQLSTATE `40P01`; при необходимости и `40001`): обернуть весь
Begin→clearUniverseTx→Commit в цикл с 2–3 попытками и короткой паузой. Это
чинит и остальные пути TRUNCATE (генерация/перегенерация/пакман), если вынести
в общий хелпер. Альтернатива — сериализовать тик с очисткой (тик заходит под
общий мьютекс) — тяжелее и не покрывает писателей-игроков. **Принято:** авто-повтор
ровно по первому направлению (см. «Сдача»).

## 3. ТЗ (быстрый путь, сервер)

1. Дедлок при очистке вселенной → транзакция повторяется автоматически и
   очистка доходит до конца (пользователь не видит ошибку), либо, если
   исчерпаны попытки, отдаётся понятный ответ. **Зачем:** админ-кнопка должна
   работать стабильно, а не «через раз».
2. То же поведение для родственных TRUNCATE-путей (генерация вселенной,
   перегенерация планет, пакман) — если выносится общий хелпер (на усмотрение
   разработчика, с сохранением текущих гейтов).
3. Тест (TDD): воспроизвести цикл (транзакция, держащая ссылку на `worlds`
   параллельно TRUNCATE) → очистка завершается успехом. Точный способ
   воспроизведения — за разработчиком.
4. Инварианты не меняем: `universeMutationMu`, порядок шагов очистки
   (escrow → users → снять FK → TRUNCATE → счета → вернуть FK) — как есть.

**Не трогаем:** список `truncateTables`, шаги `clearUniverseTx` по существу.
