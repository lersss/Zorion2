## 0. Пожелание создателя (дословно)

> «скажи, а мы можем интегрировать игру с vk mini apps?»
> «площадку»

Уточнения создателя (2026-09-24, по нумерованным вопросам менеджера):

1. **Вход:** оставить обычный логин/пароль, но **не для пользователей ВК** — две
   двери, каждая для своей аудитории: зашёл из ВК → только вход через ВК; зашёл на
   сайт напрямую → только логин/пароль. Привязка старых аккаунтов не нужна
   (аудитории не смешиваются).
2. **Мостик между дверями не нужен** (создатель: «да, согласен»): ВК-игрок не играет
   на сайте, сайтовый — не в ВК.
3. **Площадка — «с запасом»:** заложить слой под другие площадки (например,
   Одноклассники), не только ВК.
4. **Телефон:** «да, нужно будет сделать под мобилки» — полноценный мобильный вид
   (не MVP «тесно, но играется»).
5. **Деньги:** монетизация через ВК — **обязательна**.
6. **Приоритет:** «когда сделаем MVP с game loop» — браться после MVP с игровым циклом.

## 1. Замысел

Игра Zorion живёт **внутри ВК** как Mini App: открывается в окне ВК (телефон/веб),
входим по ВК-личности, играем с телефона, покупаем за голоса ВК. Основной сайт с
обычным логином/паролем продолжает жить отдельно — **две двери, одна игра, одна
база игроков**.

Площадка не одна: закладываем слой «внешняя площадка», чтобы позже добавить другую
без переделки ядра.

Связь с идеей «один мир — много клиентов»: площадка ВК — один из входов в общий мир
(наряду с мини-играми); требует того же стержня — логика мира на сервере, клиент
тонкий.

## 2. Факты разведки (проверено менеджером 2026-09-24)

- **Внешнего входа нет:** только свой логин/пароль (`internal/handlers/auth_handlers.go`),
  JWT HS256 TTL 24 ч (`internal/auth/jwt.go`), роли player/admin/skycomposer.
  Ни ВК, ни OAuth-провайдеров.
- **Публичный HTTPS есть** (Amvera, `docs/DEPLOY.md` §3) — базовое требование ВК
  «приложение живёт на своём защищённом адресе» закрыто.
- **Мобильного интерфейса фактически нет:** карта/модалки заточены под широкий экран
  (Canvas 2D); тач-поддержка — буквально в одном месте (`web/static/js/ui/sound.js`,
  `touchstart`). `<meta viewport>` есть во всех HTML, но это не адаптив. В QA отмечено:
  «Тач/мобильная вёрстка меню и погодных чипов не проверялась».
- **Смежная идея про «толстый клиент»** (`60a`, Tauri/Electron под Windows/Steam Deck) —
  другой сюжет, но при дизайне сверить, чтобы не дублировать.

## 3. Архитектурный фильтр (новая сущность — модель-гипотеза)

Пожелание вводит **внешнюю личность игрока** (кто пришёл с площадки). Модель-гипотеза
менеджера (на подтверждение создателю — §6):

1. **Природа** — состояние/запись («кто есть кто»), не событие; таймеров нет.
2. **Владелец** — у игрока.
3. **Расширяемость** — площадок будет много («с запасом») → **отдельная таблица
   привязок** `external_accounts` (игрок, площадка, внешний id), а не колонка в `users`.
   Второй тип площадки влезает в ту же схему.
4. **Эксплуатация** — это вход, а не механика: обойти нечего.

**Следствия для дизайна (не решаем здесь):** у ВК-игрока нет пароля → путь «вход без
пароля»; проверка подписи данных запуска от площадки — на сервере (секрет приложения),
клиент лишь получает их; платформенный слой (мост/SDK, платежи) — абстрагировать под
несколько площадок.

---

## 4. Что понадобится (объём, черновой)

1. **Платформенный слой входа:** проверка подписи запуска на сервере → выдача нашего
   JWT; создание/поиск игрока по внешнему id. Две двери раздельно.
2. **Клиент площадки:** подключение официального SDK ВК (данные игрока, тема,
   нативные элементы).
3. **Мобильный вид игрока:** отдельная раскладка карты/модалок под узкий экран и
   управление пальцем (большая работа, не пара правок).
4. **Монетизация:** покупка за голоса ВК, обработка платежей площадки, начисление
   игроку.
5. **Запас под площадки:** абстракция так, чтобы вторая площадка не требовала
   переделки ядра.

---

## 5. Риски (честно)

1. **Мобильный UI — главный объём.** Canvas-карта и модалки проектировались под
   монитор; «играть с телефона» может потребовать перекомпоновки ключевых экранов.
2. **Монетизация — отдельный пласт** (платежи площадки, вебхуки, начисление),
   не «галочка».
3. **Зависимость от правил площадки** (модерация, требования к данным и платежам) —
   меняются, держать в узде.
4. **Раздвоение клиентов** — перекликается с рисками идеи «один мир — много клиентов»:
   чем больше логики на клиенте, тем дороже каждый вход.
5. **Внешний вход — зона безопасности:** проверка подписи площадки обязательна,
   иначе подделка личности.
