## 0. Пожелание (слова создателя)

- В дашборде игрока нужна **отдельная вкладка «Собственность»**.
- В ней перечислить **собственность игрока** — пока это **поселения и строения, где владелец — игрок**.
- По каждой единице собственности нужны два действия:
  - **«Посмотреть»** — открывает попап планеты; показывается **только то, что игрок знает**;
  - **«Перелететь»** — перелёт **к нужной планете из любой точки**, одним действием до планеты.

## 1. Уточнения создателя

1. Тип собственности на сейчас: поселения и строения с владельцем-игроком. «Пока да» — состав
   списка может расшириться позже.
2. «Посмотреть» — попап планеты, но без раскрытия неизвестной информации; игрок видит своё
   имущество в рамках уже известного ему знания о планете.
3. «Перелететь» — одним действием доводит до планеты, откуда бы игрок ни находился.
4. Отдельная вкладка в дашборде, а не блок внутри другой вкладки.
5. **Видеть, что происходит на планете, можно только при личном присутствии или через
   ретранслятор.** Собственность не даёт бесплатного обзора планеты. Сеть ретрансляторов
   — запланированная механика (`99.2.9`), пока не реализована; до неё наблюдение — только
   личным присутствием.
6. **Строку собственности показываем всегда** — игрок знает, чем владеет. Состояние
   планеты внутри строки — только по знанию: присутствие, ретранслятор или уже
   сохранённый снимок; неизвестное не раскрывается.

## 2. Что уже есть (факты для дизайна)

- Дашборд игрока — `web/index.html`, вкладки по паттерну админки (`.tab-btn`/`.tab-pane`).
- Владение: `settlements.owner_type='player'` + `owner_id`, `buildings.owner_type='player'` +
  `owner_id` (миграции `000082`; у поселений — владелец только у новых, легаси без владельца).
- Знание о планете — отдельный слой (`player_planet_knowledge`, присутствие/снимок); попап
  планеты уже умеет показывать урезанную картину по знанию.
- Полёты: межзвёздный перелёт к звезде и внутрисистемный перелёт к планете — существующие
  механики; у игрока один активный полёт. Автоматическая цепочка «межзвёздный → к планете»
  уже реализована (спека `99.2.30`, `users.pending_destination`) — новую не изобретать.
- Ретранслятор как тип строения в дереве есть, но сети покрытия и наблюдения нет: механика
  `99.2.9` запланирована, не реализована. До неё «что происходит на планете» — только
  личным присутствием.
- API собственности игрока отдельным списком пока нет.

## 3. Открытые вопросы для дизайна

1. **Два плеча перелёта.** Если игрок в другой системе, «Перелететь» должен сам выполнить
   межзвёздный перелёт до звезды, а по прибытии — внутрисистемный до планеты. Как это
   оформляется: цепочка полётов, фоновое продолжение после прибытия, статус в списке?
2. **Ограничения.** Что делать, если уже есть активный полёт, нет двигателя, игрок на
   поверхности или уже на месте? Кто и когда отменяет цепочку?
3. **Знание и собственность.** ✅ **Решение создателя:** сведения о состоянии планеты
   доступны только при личном присутствии или через ретранслятор; собственность не
   раскрывает планету. Открытый остаток: показывать ли **саму строку владения** на
   непосещённой планете (игрок знает, что владеет объектом) или скрывать и её до
   присутствия/ретранслятора; что именно доступно в «Посмотреть» без наблюдения.
4. **Живость списка.** Что происходит со строкой, если владелец сменился, поселение вымерло
   или мир очищен, пока игрок смотрит вкладку/летит.
5. **Границы.** Новых сущностей/таблиц не требуется (владение уже есть); нужен только
   список и действия. Подтвердить API-форму: отдельный список собственности игрока.
6. **Нарезка.** Список и «Посмотреть» — одно; «Перелететь» с двумя плечами — отдельный
   чекпоинт из-за сложности маршрута. Подтвердить у создателя.

## 4. Границы

- Не переписывать существующие механизмы полёта и знания — только использовать их.
- Не добавлять новые сущности владения: владелец-игрок уже есть.
- Не раскрывать игроку неизвестную планету через вкладку собственности.
- Вне скоупа: продажа/дарение собственности, управление имуществом из вкладки, рейтинги,
  доходность, уведомления о нападении.

## 5. Маршрут (предложение)

1. Дизайн-спека: данные и API списка, вкладка и действия, поведение «Посмотреть» по знанию.
2. Отдельно — дизайн «Перелететь» с двумя плечами и краевыми случаями.
3. `@critic` после спеки — связь с полётами, знанием, владением.
4. Гейт создателя → разработка → тестер.

## 5а. Критика идеи (2026-09-25)

**Вердикт:** 1 крупное, 4 средних, 3 мелких.

- **Крупное** (раскрытие неизвестной планеты через вкладку) закрыто решением создателя:
  собственность не даёт обзора, сведения — только присутствие или ретранслятор.
- **Средние к учёту в дизайне:** автоматическая цепочка двух плеч уже есть — переиспользовать;
  ветвление «своя/чужая система, орбита, поверхность, уже на месте, активный полёт»; стык
  «дашборд ↔ карта» для открытия модалки и полёта; живость списка при вымирании поселения,
  смене владельца и очистке мира.
- **Мелкие:** терминология (в проекте — модалка системы, термин «собственность» не заведён);
  пока нет игрового пути приобретения собственности (владелец-игрок ставится админом);
  полиморфный владелец без FK — возможны строки-сироты.

## 5б. Критика спеки (2026-09-26)

Прогон `@critic` по спеке `docs/specs/2026-09-26-собственность-игрока-в-дашборде.md`:
**крупных 0, средних 6, мелких 4.** Фундамент не сломан. Создатель: «чини» (делегировал решения).

Закрыто в спеке (2 пакета правок дизайнера):
- **С1** пакетное чтение знания в новом файле репозитория (per-planet резолв не переиспользуется);
- **С2** честное поведение для системы вне знания (карточка звезды — только при наличии кэша карты,
  иначе тост «система вне зоны видимости — данных нет», попап не открываем);
- **С3** детерминированный приоритет deeplink над отложенными авто-открывателями (прибытие/пояс);
- **С4** ветвление «своя/чужая система» — серверным флагом модалки, не косвенным признаком;
- **С5** запуск маршрута — существующей обёрткой (маркер/закрытие модалки/слежение), не низкоуровневым стартом;
- **С6** (координация) — менеджер: спека **не трогает** занятые файлы (`planet_visibility.go`,
  `knowledge_repository.go`) — доступ к знанию живёт в новом `property_repository.go`; номер миграции
  `000090` забронирован в `docs/COORDINATION.md`;
- мелкие М1–М4 (ссылки словаря, fallback имени строения, формулировка индекса, ложный вывод «ничего не добавляет») — исправлены.

Решения-развилки (закрыты менеджером, гейт создателя 2026-09-26): **В1** «Посмотреть» = переход
на карту; **В2** числа в списке не показываем; **В3** система вне знания — честное «данных нет»;
**В4** вымершее поселение остаётся в списке.
