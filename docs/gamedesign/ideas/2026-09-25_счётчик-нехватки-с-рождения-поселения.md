# Счётчик нехватки (голод/жажда) должен идти с момента появления поселения

**Создано:** 2026-09-25
**Статус:** ✅ исправлено 2026-09-25 (коммит `d77f688`): счётчик нехватки идёт с рождения поселения (если эффект есть с появления), первая запись сохраняет накопленную нагрузку; повторный прогон тестера — ПРОЙДЕНО
**Приоритет:** баг/поведение (🟡 — механику не ломает, но искажает сроки вымирания)
**Вектор:** **Поселения** (экономика поселения, `internal/economy/settlement`, owner-проход)

---

## Пожелание (создатель, 2026-09-25)

Обсуждение форпоста на планете Meredsha (форпост игрока, 500 чел., без веток и
снабжения; типы «Форпост» объявляет потребности «пища» → голод, «очищенная
вода» → жажда). Карточка эффектов показывала: `нагрузка: 0 · порог: 24 ·
состояние: снят` у обоих эффектов.

Решение создателя:
1. **Счётчик нехватки должен идти с момента появления поселения** (а не с первой
   контрольной точки owner-прохода ~через 30 минут).
2. Жажда, использующая ту же кривую `hunger`, что и голод, — **«пока так»**
   (отдельную кривую жажды не заводим).

---

## Диагноз (проверено по коду и БД)

- У нового поселения нет сохранённого базиса нагрузки (`active_effects` пусто).
  В `runOwnerPass` (`internal/repository/settlement_owner_pass.go`) для привязки
  без базиса задаётся `load = 0`, `load_at = now` — первый интервал считается с
  `now`, поэтому **накопления нет** (`Δt = 0`), пока не пройдёт первая
  персистентная запись (порог `MinPersistInterval` = 30 минут).
- Между чтениями до этой точки каждый раз базис «создаётся заново» с
  `load_at = now` → нагрузка и `w` стоят в нуле. Потому и карточка показывала
  `нагрузка: 0`, `w: —`, `состояние: снят`.
- Фактически: форпост, рождённый без снабжения, получает ~30 минут «форы» —
  счётчик нехватки стартует не с рождения, а с первой контрольной точки.
  По замыслу создателя этого быть не должно.

---

## Требование к фиксу

Для привязки без сохранённого базиса у **новорождённого** поселения (ещё ни разу
не пересчитывалось — контрольная точка совпадает с моментом рождения) интервал
накопления считать **с момента появления поселения** (`created_at`), а не с
`now`.

Уточнение создателя (2026-09-25): **счёт с рождения — только если эффект
(привязка) есть у поселения с самого появления.** Эффект, появившийся позже,
считает с момента своего появления (назад не отматывается).

Ограничения (не сломать существующее):
1. **Смена стадии** намеренно сбрасывает базис нагрузки и ведёт счёт заново **с
   текущего момента** — это поведение сохранить (там `load_at = now`).
2. **Новая привязка у старого поселения** (эффект добавлен позже) не должна
   «бэкдейтиться» к рождению — счёт с текущего момента.
3. Значения `w`/`load`/`состояние` в карточке после фикса должны оживать сразу:
   у форпоста без источников `w = 1`, нагрузка растёт со временем, состояние
   переключается на «включён» при `load ≥ 24`.

Механизм — на усмотрение `@developer` (например, явный признак «базис от
рождения» из `syncOwner`, либо различение «контрольная точка == рождение»).
Важно: отличие от сброса-по-стадии должно быть явным, а не выведенным из
совпадения времён.

## Найдено тестером (итерация 2, 2026-09-25): первая запись обнуляет нагрузку

Прогон показал: «счёт с рождения» работает только на пути «в памяти». Первая
персистентная запись (~30 мин) **обнуляет** накопленную нагрузку:
`activeEffectUpsertSQL` (`internal/repository/settlement_owner_pass.go`) в ветке
`INSERT` жёстко пишет `load = 0`, а вычисленная нагрузка передаётся в `$5`,
который `INSERT` игнорирует (используется только в `DO UPDATE`). Факт живьём:
чтение отдало `load = 0.5121`, в БД записалось `load = 0`; следующее чтение —
`load = 0.0116` ч (счёт начался заново с чек-поинта).

Фикс: ветка `INSERT` должна писать вычисленную нагрузку (`$5`), а не 0. Нормально
и для новорождённого (нагрузка сохраняется), и для поздней привязки (там
вычисленная нагрузка и так 0).
