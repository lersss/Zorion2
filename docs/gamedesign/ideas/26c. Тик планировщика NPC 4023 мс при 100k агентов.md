## Сырое пожелание (создатель, 2026-09-15)

> «Мне нужно максимально оптимизировать решения. Сейчас конкретно надо решить
> задачу Агентов: 100000 · В полёте: 30596 · idle: 69404 · Очередь на тик: 384 ·
> Тик: 4023 мс · Полных батчей: 13 · Последняя пачка: —. Сервер перегружен (3 ядра)»

Уточнение создателя: «по ядру 0,44, ОЗУ 3 из 6, троттлинг 0%» — **сервер НЕ
голодает по ресурсам** (CPU ~15% общего, ОЗУ в норме, троттлинга нет). Значит
4023 мс тика — не вычисления, а **ожидание**: БД-запросы, round-trip'ы, аллокации/GC.

Второе уточнение создателя (Postgres): «ОЗУ 46,84, CPU 9,5, **троттлинг 18%»** —
**БД троттлится хостингом**: Postgres упирается в лимиты CPU ровно на нашей
нагрузке (4000 одиночных UPDATE + ListAll 100k каждые 5 с — парсинг, планирование,
WAL на каждый запрос). **БД — подтверждённое узкое место.** Снижение числа запросов
к БД (multi-row UPDATE, убрать ListAll из тика) напрямую снимет троттлинг.

## Контекст (факты из кода/спек)

- Планировщик `internal/npc/manager.go` (спека `20a.1` §3.1): одна горутина,
  тик каждые `npcTickInterval` (5 с), batch 2000. На тик 3 шага (см. диагноз).
- Метрики пришли с прода (Amvera, 3 ядра / 6 ГБ): агентов 100к, очередь 384 —
  система на грани бюджета тика (4.0 из 5.0 с); 13 полных батчей — перегрузки уже были.
- Поток прибытий при 100k ≈ 500/сек (спека §2.1); равновесный бюджет — 400/сек
  (batch 2000/тик). Любое увеличение числа агентов или скорости полёта — коллапс очереди.

## Диагноз (по коду, требует замера)

Горячий путь тика (всё последовательно в одной горутине):

| # | Фаза тика | Что делает | Подозрение |
|---|-----------|-----------|------------|
| 1 | `ListDueArrivals` | SQL: `WHERE status='flying' AND arrive_at <= now AND id > cursor ORDER BY id LIMIT 2000`. Фильтр по `arrive_at` **НЕ покрыт индексом** (есть только `(status,id)` из 000026) | при 30k flying — bitmap/seq scan + фильтр, ~100–500 мс |
| 2 | `UpdateStatusBatch` (прибытия) | транзакция + **до 2000 одиночных UPDATE-Exec в цикле** (`applyAgentUpdate` по PK) | **до 2000 round-trip'ов к БД за тик** |
| 3 | `ListBatch(idle)` | по индексу `(status,id)`, курсор — быстро | ок |
| 4 | `UpdateStatusBatch` (старты) | ещё **до 2000 одиночных UPDATE-Exec** | **ещё до 2000 round-trip'ов** |
| 5 | `refreshPositions` → `ListAll()` | **SELECT всех 100k агентов** (12 колонок, ~20–30 МБ) каждые 5 с + аллокации 100k моделей + 100k интерполяций | **главный кандидат на секунды** |
| 6 | `refreshGrid` | `mapcache.Snapshot()` — `atomic.Pointer.Load()`, копий нет | дёшево, не виноват |

**Сумма:** до **4000 round-trip'ов UPDATE** + **ListAll 100k** каждые 5 с. При
свободном CPU (0.44 ядра) — это и есть 4023 мс: ожидания БД + передача данных + GC.

**Отклонение от замысла спеки:** `20a.1` §2.2.B обещала «позиции in-memory,
пересчёт интерполяций тривиален» — но источник данных реализован как `ListAll()`
из БД на КАЖДЫЙ тик, а не как кэш в памяти. Это и есть главное расхождение.

### Фикс блокера (ревью, 2026-09-15) ✅
