## Сырое пожелание (создатель, 2026-09-15)

> «Надо дальше копать, в будущих сессиях, как улучшить логику и архитектуру,

Контекст: после 26c (тик 691→160 мс при 100k) — как масштабироваться за 100k
(500k? 1M?), не ломая инварианты 20a и не уткнувшись в новые стены.

## Контекст (факты из кода/замеров 26c)

- Планировщик — ОДНА горутина, тик 5 с, batch 2000 прибытий + 2000 стартов,
  кэш агентов в памяти (agentCache, ~20–25 МБ на 100k), `ListAll` только при
  старте/инвалидации. `UpdateStatusBatch` — 2 multi-row UPDATE (лимит параметров
  65535 ≈ до 13000 строк на запрос).
- Поток прибытий ∝ числу агентов: при 100k ≈ 500/сек (полёт ~200 с); бюджет тика
  400/сек — сходится в равновесие (28–30k в полёте). **При 500k поток ≈ 2500/сек,
  бюджет 400/сек — очередь растёт навсегда** (данные не теряются, но лаги
  наблюдения/уведомлений неограниченно растут). Это главная стена.
- `ListDueArrivals` — фильтр `arrive_at <= now` не покрыт индексом (14–17 мс при
  30k flying; при 500k flying — заметнее).
- `/api/npc/positions` отдаёт ВСЕ позиции: 20.7 МБ при 100k (~2.2 с на трансфер) —
  при 500k это ~100 МБ: узкое место и для сервера, и для фронта (26e).
- Интерполяции O(N) на тик: при 100k ~47 мс, при 500k ~240 мс — уже значимо в тике.

## Направления (сыро, для будущего дизайна)

1. **Покрыть поток прибытий при большем N:**
   - размер батча/тик конфигурируемо и автоматически под поток (сейчас фикс. 2000);
   - параллельная обработка батчей в рамках тика (воркеры читают, пишет один —
     И1 «единственный писатель» сохраняется);
   - снижение потока длительностью полёта — НО это геймдизайн (эталон §3.3 20a.1,
     открытый вопрос создателя — формула A/B/C), без решения создателя не трогать.
2. **Сегментация/шардинг:** агенты по регионам/мирам — независимые под-планировщики
   (сложно: глобальные курсоры, пересечения полётов между регионами).
3. **Событийная/поточная модель:** in-memory симуляция полётов с периодическим
   снапшотом в БД вместо «тик = порция БД» (рестарт-устойчивость — снапшот;
   репликация позиций — дельты).
4. **Выдача позиций:** серверный cull по вьюпорту/зуму клиента, кластеризация
   агентов как звёзды (mapcache.Query паттерн), дельты через WS вместо полного
   снапшота каждые 5 с — общее с 26e (фронт).
5. **Память кэша:** компактная структура вместо полной модели (25 МБ на 100k →
   ~10 МБ), если пойдём за 500k.
