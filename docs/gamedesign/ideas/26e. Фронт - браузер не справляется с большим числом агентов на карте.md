# 26e. Фронт: браузер не справляется с большим числом агентов на карте

**Создано:** 2026-09-15
**Статус:** Отклонена создателем (2026-09-17)
**Приоритет:** 🟡 производительность фронта (заметно при 100k)

---

## Сырое пожелание (создатель, 2026-09-15)

> «Есть еще проблема на фронте — при большом количестве агентов браузер не
> справляется. Всё надо оформить в виде пользовательских реквестов как-то,
> и разбирать.»

## Контекст (факты из кода/замеров 26c)

- Карта рисует агентов иконками-ромбами (`web/static/js/map/npc_agents.js`),
  видимы при зуме, где видны имена звёзд (порог `nameDisplayThreshold`).
- **`GET /api/npc/positions` отдаёт ВСЕ позиции одним ответом: 100 000 записей,
  ~20.7 МБ, ~2.2 с трансфер** (замер 26c). Клиент опрашивает раз в ~5 с.
  При 100k: парсинг 20 МБ JSON каждые 5 с + отрисовка — браузер не справляется
  (лаги, заморозки). Это подтверждённая стена (замер тестера: «UX карты глазами
  игрока не смотрел — нужен прогон игроком»).
- Экранный cull уже есть у звёзд (`map_render.js`), у агентов — частично; но
  данные всё равно грузятся ВСЕ, независимо от вьюпорта/зума.

## Направления (сыро, для будущего дизайна)

1. **Серверный cull по вьюпорту:** клиент передаёт bounds/зум → сервер отдаёт
   только агентов в окне (паттерн mapcache.Query по кластерам). При обзоре
   галактики агентов мало/нет — экономия трансфера ×100.
2. **Кластеризация агентов** как звёзд: на мелком зуме — кластеры, на крупном —
   отдельные иконки.
3. **Дельты через WS** вместо полного снапшота каждые 5 с: пришёл/вылетел/позиции
   изменившихся; полный снапшот — при заходе на карту.
4. **Рендер:** лимит FPS, слой агентов отдельно от звёзд, отрисовка только
   движущихся/в окне, `requestAnimationFrame`-батчинг.
5. **Дроссель опроса** (раз в 10–15 с вместо 5) на мелком зуме, где агенты скрыты.

Общее с 26d (выдача позиций — серверная сторона): решать вместе или согласованно.

## Что это примерно будет (сыро)

Дизайн: какой объём данных реально нужен клиенту на каждом зуме → контракт
`/api/npc/positions` расширяется параметрами вьюпорта (или отдельная ручка) →
кластеризация на сервере/клиенте → рендер-оптимизации. Проверка — ручной прогон
игроком с 100k (что тестер не покрыл) + FPS-замер.
