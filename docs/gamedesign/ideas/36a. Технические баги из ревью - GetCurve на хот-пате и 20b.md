## Пункт 1 — GetCurve на хот-пате (риск производительности)

**Где:** `internal/economy/settlement/change_components.go:57-88` +
`internal/economy/settlement/balancer_store.go:65` (`GetCurve`).

**Суть:** каждая из 4 компонент (Heat/Cold/Gravity/Radiation) на КАЖДЫЙ вызов
делает `GetCurve(component)` → `RLock` + копия двух слайсов (2 аллокации).
`ChangeComponents` вызывается из `Recompute` на каждый просмотр поселения
(ленивый пересчёт, хот-пат). При 100k поселений/тик это 400k аллокаций/проход.
Корректно, но дорого.

**Ожидаемое решение (ревьюер):** кэширование кривых в мини-R / store-версии:
кривые меняются редко (только из админки), читаются постоянно. Не менять
публичную семантику: `SetCurve` из админки применяется к следующему расчёту без
рестарта (TestHotSwap в `balancer_store_test.go` остаётся зелёным).

**Критерий готовности:**
- `go build`/`go vet`/`go test ./...` зелёные
- `TestHotSwap` (SetCurve ⇒ следующий evaluateCurve считает по новой) зелёный
- хот-пат не аллоцирует копии кривых на каждый вызов (бенчмарк или код-чтение)

## Пункт 2 — 20b паника генератора при малом world_count

**Где:** `internal/generator/galaxy/poisson.go:129`.

**Суть:** `g.rng.Intn(perCluster/2)` при `perCluster=1` → `Intn(0)` → panic.
Воспроизводится стабильно: `POST /admin/generate {"world_count":3}` (дефолт
`cluster_count=20`) → `clusterPoints=2`, `perCluster=1` → panic. С `world_count=1000`
или `cluster_count=1` — работает.

**Ожидаемое решение:** защита от `Intn(0)` (например, `perCluster/2` минимум 1 —
или пересчёт разброса при малых perCluster) + регрессионный тест на малые
`perCluster` (см. `20b. Баг - паника генератора при малом world_count.md`).

**Критерий готовности:**
- `POST /admin/generate` с `world_count` 2–5 и дефолтным `cluster_count` не падает
- регрессионный тест: `Intn` не вызывается с нулевым/отрицательным аргументом
