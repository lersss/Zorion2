# 60a. Steam-интеграция — обёртка клиента, Steamworks, офлайн-мини-игры

**Дата:** 2026-09-16
**Статус:** сырая идея, бэклог — НЕ запускать
**Приоритет:** горизонт (после 1.0, крупный)
**Вектор:** Игрок / Новые механики

## Пожелание (сырое, словами создателя)

«Можем ли сделать "толстый клиент" под эту игру?» — изначально уточнено: **общий мир**
(онлайн не ломается), **визуал и отрисовка на клиентах**, аппаратное ускорение.
Создатель: «Запускать ничего не надо, я просто смотрю вперёд».

## Боль (2026-09-16, второе уточнение — ключевое)

«Вообще я думал в сторону возможности интеграции в **Steam**, такая вот боль».

То есть замысел — **выложить игру в Steam**, а «толстый клиент» был средством.
Это меняет вывод (см. «Пересмотр развилки» ниже).

## Развилка, зафиксированная при уточнении (2026-09-16)

Два пути:
- Путь 1: десктоп-обёртка (Electron/Tauri) вокруг веб-клиента — архитектура не
  меняется, сервер остаётся авторитарным, мир общий.
- Путь 2: перенос логики/отрисовки на клиент при общем мире.

**Пересмотр после уточнения боли:** для Steam перенос логики на клиент НЕ нужен.
Steam требует исполняемое приложение (не браузерный URL), а не клиентскую логику.
Сервер-авторитарная архитектура — норма для онлайновых игр в Steam. Первоначальный
выбор пути 2 был сделан без учёта реальной боли; менеджер возразил (2026-09-16),
ждём решения создателя: обёртка (путь 1) + Steamworks против переноса логики (путь 2).

Ключевые параметры замысла (если путь 1):
1. Общий мир: многопользовательность и сервер-источник-правды сохраняются
   (авторитарная модель, AGENTS.md §0 — не отменяется).
2. Вся существующая игра (Canvas 2D, модалки, анимации) работает в обёртке как есть.
3. Steamworks SDK: достижения, облачные сохранения, оверлей, вход через Steam ID
   (greenworks для Electron / плагины Tauri). Состав — на уточнение.
4. «Аппаратное ускорение/визуал на клиенте» — не требование Steam; если захочется
   красивее — отдельная задача (WebGL/WebGPU), не связанная с интеграцией.

## Решения создателя (2026-09-16, третье уточнение)

1. **Путь 1 подтверждён:** обёртка (Electron/Tauri) + Steamworks.
2. **Steamworks — всё:** достижения, облачные сохранения, оверлей, вход через Steam ID.
3. **Платформы:** Windows + Steam Deck (Linux) → кроссплатформенная обёртка (Tauri
   легче в этом, чем Electron; окончательный выбор — на этапе дизайна).
4. **Офлайн — развилка из двух вариантов** (создатель сам отметил уязвимости первого):
   - (а) мини-игры добычи/исследований (из роадмапа) встроить в клиент: играть
     офлайн, потом отдать данные в онлайн. **Есть уязвимости** (подделка клиента).
   - (б) отдельные мини-приложения/мини-игры для Steam: игроки не знают, что они
     часть «роя» (несколько разных отдельных игр в Steam, связанных скрыто).
5. **Визуал/аппаратное ускорение на клиенте — отложено**, не смотреть (не связано
   с Steam-замыслом, это было приложением).

## Оценка менеджера по офлайн-вариантам (2026-09-16)

- **Вариант (а)** — дыра для читеров: клиент сам отдаёт данные в онлайн, значит
  его можно подделать. Смягчение: серверная приёмка по верхним границам
  (валидация лимитов), аудит (движок Run[T] + 43 правила), но не панацея.
  Это тот же класс проблем, что у клиентской правды (путь 2) — только в малом объёме.
- **Вариант (б)** — уязвимость уходит (мини-игры самодостаточны, рой не зависит от
  их честности), но это отдельный продукт: свои страницы Steam, онбординг,
  скрытая связь с основной игрой. Красиво, но больше работы и отдельный маркетинг.
- Обе опции — горизонт; при старте развилку решать заново, с учётом состояния
  роадмапа и мини-игр.

## Честная оценка масштаба (менеджер, 2026-09-16)

- **Для Steam: путь 1 (обёртка) — реалистичен и мал по сравнению с путём 2.**
  Electron/Tauri оборачивает текущий веб-клиент (Canvas 2D работает как есть),
  Steamworks добавляет достижения/облака/оверлей/вход. Объём: обёртка + SDK +
  билд/пайплайн + страница Steam. Ноль переписывания игры.
- **Путь 2 (общий мир + логика на клиентах)** — смена парадигмы: авторитарный сервер
  (43 правила аудита, верификация) несовместим с клиентской правдой без огромного
  слоя верификации/синхронизации. Это отдельный проект поверх текущего и для Steam
  НЕ требуется.
- Офлайн-режим: игра онлайн-зависимая; чисто онлайн-игры в Steam допустимы, но если
  офлайн ожидается (вариант а) — это отдельные изменения с уязвимостями.

## Что нужно решить до запуска (задел для будущего дизайна)

- Выбор обёртки: Tauri vs Electron (кроссплатформенность Windows+Linux).
- Вход: Steam ID как основной или в паре с JWT-аккаунтами (миграция аккаунтов).
- Офлайн-развилка (а) vs (б) — решать заново при старте.
- Судьба текущего браузерного клиента: остаётся как бесплатная веб-версия
  или поглощается десктопным? (не решено, влияет на страницу Steam и аудиторию).

## Связанное
