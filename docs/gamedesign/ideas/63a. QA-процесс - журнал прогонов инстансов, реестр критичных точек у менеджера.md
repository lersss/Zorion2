# 63a. QA-процесс — журнал прогонов инстансов, реестр критичных точек у менеджера

**Создано:** 2026-09-16
**Статус:** процесс (ждёт внесения через @dispatcher по «го»)
**Приоритет:** процессный
**Ведёт:** @manager

---

## Суть

`docs/QA_CHECKLIST.md` — единый файл-реестр «кейс → последняя проверка» с одним
правилом записи («@tester перезаписывает только дату»). При параллельной работе
команд (несколько инстансов `@tester` одновременно) это даёт:

- **гонку на запись** общего файла (last-writer-wins, затирание чужих дат);
- **«чужое/своё» без границы** — инстанс тестирует зоны, которые не относятся
  к его задаче, и переписывает чужие даты;
- **смешение инструкций разных команд** в одном файле без атрибуции.

Разделяем две разные вещи, которые сейчас слиты: **журнал прогонов** (растёт,
файл на инстанс) и **реестр критичных точек** (один, ведёт @manager).

## Решения создателя (2026-09-16)

1. **Журнал прогонов** — каждый инстанс `@tester` при прогоне пишет **свой
   файл** в `docs/QA/checklists/`: `<дата>_<задача>.md` (например
   `2026-09-16_63a-log-settlement.md`). Журнал растёт — это норма.
   **Владелец файла — инстанс, который его создал**; чужие файлы не трогает.
2. **Единый реестр критичных точек** — `docs/QA_CHECKLIST.md` остаётся
   (компактный, «кейс → последняя проверка»). **Менеджер решает, что критично
   тестировать, чтобы не падало, и отвечает за этот файл** (единственный
   писатель — @manager; @tester туда не пишет).
3. **Расписание полных прогонов** — по реестру гоняем **не каждый раз**:
   только **после больших релизов** или **раз в 3–4 мелких релиза**.
   При обычной задаче — только затронутые диффом кейсы (в отчёт инстанса).

## Схема

| Файл | Кто пишет | Когда |
|---|---|---|
| `docs/QA/checklists/<дата>_<задача>.md` | инстанс `@tester` (свой файл, чужие не трогает) | при каждом прогоне |
| `docs/QA_CHECKLIST.md` | **только @manager** (состав критичных точек, даты из отчётов инстансов, инициация полных прогонов) | по отчётам / по расписанию |

- Инстанс в отчёте: что прогнал (A#/B-ЗОНА-#), вердикт, найденное
  (file:line), «предложения в чек-лист». Отчёт = артефакт команды —
  коммитит @manager после «го» (инстанс не коммитит, `git` у него deny).
- Полный прогон реестра инициирует @manager (после большого релиза /
  раз в 3–4 мелких) — сам решает состав «критичного» и передаёт инстансу
  готовый список кейсов (без права инстанса интерпретировать дифф).
- Ядро (A1–A7) — критичные точки по умолчанию; состав Ядра меняет
  @manager по решению создателя (критерий сохранён: «поломка = нельзя
  играть / краш / потеря прогресса»).
- Регрессионные кейсы по-прежнему общие (в реестре) — баг команды А
  виден команде Б, «замыкания внутри команды» нет.

## Кто что коммитит

| Артефакт | Кто коммитит | Когда |
|---|---|---|
| Отчёт инстанса `docs/QA/checklists/*.md` | @manager (артефакт команды) | после «го» |
| `docs/QA_CHECKLIST.md` (даты/состав) | @manager | после «го» / по расписанию |
| Горячие доки (дельты) | только @dispatcher | в паузу |

## Что НЕ меняется

- Полный прогон реестра — не шлюз, вердикт инстанса можно не ждать
  (AGENTS.md §14: «это не шлюз»); реестр — быстрый взгляд на покрытие,
  а не блокер релиза.
- Go-автотесты в чек-лист не дублируем (правило «Актуализация»).
- «Предложения в чек-лист» — по-прежнему применит @manager (теперь он же
  владелец реестра — становится проще: применяет сразу).
