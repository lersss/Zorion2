## Зачем

Каждая фича сегодня вручную собирает список «что зацепит правка» (в 80a
дизайнер собрал §9 спеки: R-кривые, race_balancer.json, тест, миграция, 5 доков,
арт-конфиги — и всё равно допустил ошибку в числах кластеризации). Цель — один
постоянный реестр: «меняем X → смотрим на Y, Z». Не анализировать проект каждый
раз заново.

## Решения создателя (2026-09-17)

1. **Формат — машиночитаемый, JSON** (вести будут ИИ). Создатель: «Json, или
   предложишь что-то получше?» — решение: JSON + лёгкая схема (поля ниже),
   при желании позже — валидация скриптом/тестом.
2. **Уровень — «горячие точки»**: сущности с 2+ потребителями (конфиги рас,
   таблицы БД, числа баланса, спеки↔код↔доки). Полный граф не строим —
   конкретные файлы всё равно лучше анализировать точечно.
3. **Владелец — @manager** (по аналогии с `docs/QA_CHECKLIST.md`).
4. **Место — новый файл** `docs/impact_map.json` (не горячий док; ведёт менеджер,
   дельты на @dispatcher не нужны).
5. **Автосверка после каждого коммита** (2026-09-17, «Можно чтобы я не говорил?
   после каждого комита надо сверяться автоматически»): валидатор
   `scripts/check_impact_map.ps1` + git hook `post-commit` (через
   `core.hooksPath` → `.githooks/`), поведение — только предупреждение в
   консоль, коммит НЕ блокирует. Настройка `core.hooksPath` — явное согласие
   создателя получено.
6. **Семантика остаётся на @manager** (автоматика ловит механику: файл пропал,
   новый файл появился, JSON сломан; что именно зацепит правка — вычислить
   скриптом нельзя). При сдаче каждой фичи менеджер прогоняет валидатор и
   дополняет реестр влияниями из спеки.

## ТЗ (дизайн схемы — выполнен @designer 2026-09-17)

### 1. Уточнённая схема JSON

```json
{
  "schema_version": 1,
  "updated_at": "2026-09-17",
  "entities": [
    {
      "id": "races.json",
      "type": "config",
      "path": "config/races.json",
      "note": "каталог 60 рас: карточки (окна, атрибуты, потребление, forage, home)",
      "impacts": [
        {
          "on": "race_balancer.json",
          "kind": "balance",
          "reason": "R-кривые генерируются из карточки (99.2.23 §3.3); card_hash устаревает → пометка «заводские настройки устарели» + перегенерация factory"
        },
        {
          "on": "settlements.race_id",
          "kind": "table",
          "reason": "строковый ключ ссылается на id расы; смена id = миграция данных (000039/000038)"
        }
      ]
    }
  ]
}
```

**Поля `entity`:**

| Поле | Тип | Обязательно | Смысл |
|---|---|---|---|
| `id` | string | да | Уникальный ключ сущности. Формат: имя файла (`races.json`), `таблица.колонка` (`settlements.race_id`), номер спеки (`99.2.21`), имя дока (`22_races.md`) |
| `type` | string (список) | да | Класс сущности (см. ниже) |
| `path` | string | да | Относительный путь от корня репо; для таблиц — `db:таблица` (виртуальный, файла нет) |
| `note` | string | нет | Зачем сущность, что в ней (1–2 строки) |
| `impacts[]` | array | да (может быть пустым) | На что смотреть при правке этой сущности |

**Поля `impact`:**

| Поле | Тип | Обязательно | Смысл |
|---|---|---|---|
| `on` | string | да | Куда смотреть: `id` другой сущности из реестра ИЛИ путь файла, если цели в реестре нет |
| `kind` | string (список) | да | Класс влияния (см. ниже) |
| `reason` | string | да | Почему влияет: что читает/пишет/дублирует/устаревает |

**Контролируемые списки:**

- `type` (класс сущности): `config` (JSON-конфиг), `table` (таблица/колонка БД), `balance` (числа баланса/R-кривые), `spec` (спека/строка роадмапа), `doc` (GDD-док), `test` (тест), `art` (арт-конфиг/спрайт), `api` (HTTP-хендлер/API-контракт), `code` (Go-код), `migration` (миграция SQL).
- `kind` (класс влияния): `reads` (потребитель читает сущность — правка формата ломает чтение), `writes` (пишет в сущность), `duplicates` (дублирует данные — док/спека повторяет факты), `derives` (производное: R-кривые из карточки, card_hash), `schema` (схема/структура: миграция, колонки), `test` (тест зависит), `api` (API-контракт), `docs` (документация устаревает).

**Правила:**

1. **Дедупликация по `entity.id`** — id уникален во всём файле. При переносе влияний из спеки: сущность уже есть → дополнить `impacts` (новые `on`+`kind` не дублируются); нет → создать.
2. **`schema_version`** — целое; растёт ТОЛЬКО при изменении структуры файла (поля, списки type/kind). Добавление сущностей/влияний версию НЕ меняет.
3. **`updated_at`** — дата последней правки файла (YYYY-MM-DD), обновляется при каждом изменении.
4. **`on` ссылается на `id`**, если цель уже есть в реестре; если цели в реестре нет (не горячая точка, 1 потребитель) — `on` = относительный путь файла. Это позволяет указывать цели без обязательного заведения сущности.
5. **Порог заведения сущности** (решение создателя): ≥ 2 потребителей (на неё ссылаются ≥ 2 раза из разных мест) ИЛИ она сама источник ≥ 2 влияний. Один потребитель — не горячая точка, в реестр не вносим (упоминаем только в `on` других).

### 3. Критерий валидности файла

Файл корректен, если (проверка скриптом/вручную):

1. JSON парсится (PowerShell: `Get-Content docs/impact_map.json -Raw | ConvertFrom-Json` не бросает ошибку).
2. `schema_version` — целое ≥ 1; `updated_at` — дата `YYYY-MM-DD`.
3. `entity.id` уникальны (нет дублей).
4. `type` и `impact.kind` — из контролируемых списков (см. §1).
5. `path` — существующий файл от корня репо (кроме `db:`-префикса таблиц). Допускается glob-маска (`docs/gamedesign/races/*.md`, `config/art/*.json`) — тогда по маске существует ≥ 1 файл.
6. `on` — либо существующий `entity.id`, либо существующий путь файла (для `db:` — имя таблицы из миграций); путь может быть glob-маской — по ней существует ≥ 1 файл.
7. Внутри одной сущности нет дублей пар `on`+`kind`.

### 4. Правило ведения (дословно для manager.md — дельта)

В `manager.md` в раздел «ПРАВИЛА» добавить:

> **Impact map (`docs/impact_map.json`)** — твой реестр каскадных влияний («меняем X → смотрим на Y»). При сдаче каждой фичи (шаг 8) переноси влияния из раздела «Пометки на смежное» спеки в реестр: сущность заводится/дополняется (дедупликация по `entity.id`, новые пары `on`+`kind` не дублируются), `updated_at` = дата сдачи, `schema_version` не трогается (растёт только при изменении структуры файла). Сущность заводится при ≥ 2 потребителях или ≥ 2 собственных влияниях; цель с 1 потребителем указывается в `on` путём, без сущности. Схема и наполнение — идея 83a §1–§2.

**Преамбула файла** (комментарий в начале `docs/impact_map.json`):

```json
{
  "_comment": "Реестр каскадных влияний Zorion. Вопрос: «меняем X → смотрим на Y». Ведёт @manager при сдаче фич (идея 83a): дедупликация по entity.id, schema_version растёт только при изменении структуры, updated_at — дата правки. Сущность заводится при ≥2 потребителях или ≥2 влияниях.",
  "schema_version": 1,
  ...
}
```

### 5. Открытые вопросы — решения создателя (2026-09-17, «ок»)

1. **`_comment`-преамбула в JSON** — принято: оставить (валидный JSON, парсеры
   игнорируют лишние поля; файл самодокументирован).
2. **Порог «≥ 2 потребителей»** — принято: код-потребитель считается
   (catalog.go читает races.json — это потребитель).
3. **`on` с путём вместо id** — принято: допустимо для целей вне реестра
   (не заводим сущность ради одного упоминания).

### 6. Автосверка после каждого коммита (ТЗ, решение создателя 2026-09-17)

Цель: создатель не говорит «сверь» — реестр проверяется сам после каждого
коммита. Автоматика ловит МЕХАНИКУ (файл пропал, новый файл появился, JSON
сломан, пути не существуют); СЕМАНТИКУ (что зацепит правка) скрипт не
вычисляет — это @manager при сдаче фичи (шаг 8, правило §4).

**6.1. Валидатор `scripts/check_impact_map.ps1`** (PowerShell, ~100 строк):

- Читает `docs/impact_map.json`; проверяет критерии валидности §3 (JSON
  парсится, id уникальны, type/kind из списков, пути существуют, glob ≥ 1
  файла, `on` = id или путь, нет дублей `on`+`kind`).
- Сверка с git (механика):
  - файлы, упомянутые в реестре (`path` сущностей и `on`-пути), но
    отсутствующие в рабочем дереве → **ERROR** «реестр протух»;
  - файлы, менявшиеся в последних коммитах (`git log --name-only -n 20`) и НЕ
    упомянутые в реестре ни как `path`, ни как `on` → **WARNING** «возможно,
    новая горячая точка» (пропускает служебные пути: `.opencode/`, `docs/gamedesign/ideas/`, `scripts/`);
  - итог: вывод счётчика ERROR/WARNING; exit code 0 при отсутствии ERROR.
- Код пишет @developer, коммитит developer (зона scripts/ — его, правка в
  `AGENTS.md` §3 не нужна, добавляем в структуру в `docs/INDEX.md` дельтой).

**6.2. Git hook `post-commit`** (`.githooks/post-commit`):

- Запускает `scripts/check_impact_map.ps1` после каждого коммита;
- вывод — предупреждение в консоль, коммит НЕ блокируется;
- настройка: `git config core.hooksPath .githooks` (один раз, согласие
  создателя получено; выполняет @developer при реализации).

**6.3. Правило для @manager** (дополнение к §4):

- при сдаче каждой фичи (шаг 8) — прогнать валидатор + перенести влияния из
  спеки в реестр (дедупликация, `updated_at`);
- при прогоне hook'а ERROR — менеджер чинит реестр (актуализирует пути/
  сущности), WARNING — решает, новая ли это горячая точка, по порогу §1.5.

**Критерий успеха автосверки:** после коммита правки расы hook выводит
предупреждение без участия создателя; удаление файла из реестра → ERROR;
реестр остаётся валидным по §3.
