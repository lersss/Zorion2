## Факты (сверка с проектом, собрал @manager перед интервью)

- **Арт-студия — образец продукта:** отдельный локальный инструмент
  `cmd/art-studio` (бинарь `zorion-art-studio.exe`, порт 8798, веб-UI embed),
  конфиги `config/art/*.json`, генерация пачек + отбор (эталоны), «порт занят» —
  мягкий выход. Спека продукта `docs/specs/67a.1-art-studio-go.md`.
- **Экономика — каркас есть, код — нет:**
  - Категории товаров: метод «товар существует, если есть потребитель»,
    13 стартовых позиций (§5.2.1 `05_economy.md`); «постройка — не товар» (§5.2.1).
  - Профиль категории = требования (жёсткие интервалы 1–3 оси) + предпочтения
    (цель+вес 2–4 оси) (§5.2.2); качество 0–100 с нормировкой (§5.2.3).
  - Рецепт = какие вещества по окнам свойств и в каком количестве (§5.2.4);
    фиксируются в коде, структура расширяемая.
  - Сложность рецепта — поле: завод производит, если тир поселения ≥ сложности
    (`13_tiers.md` §13.9.1; `docs/GLOSSARY.md` §5).
- **Ресурсы:** 6 категорий (минералы, органика, редкие, топливо, вода, газы) —
  `09_resources.md` §9.1.3, `internal/resource/categories.go`; универсальный слой
  94a — каталог 20 ресурсов (`internal/resource/layer.go`); витрина 111 реальных
  веществ (`real.go`, 10 осей + T_melt/T_boil; НЕ контент, граница в 99.2.5);
  вкладка «Ресурсы» в админке.
- **Схема БД substances/resources — следующий релиз** (не реализована).

## Конспект интервью (@interviewer, 2026-09-18)

### Ядро механики (словами создателя)

> «Студия товаров — генератор производственных цепочек сверху вниз: топ-тир
> товары → составляющие (товары меньших тиров или новые) → ... → ресурсы.
> Любой товар может стать составляющим любого товара выше тира. Задача студии —
> сгенерировать все производственные цепочки в удобном UI. Результаты
> сохраняются в JSON, который игра потом может прочитать и загрузить себе в
> базу. Заодно поймём, каких ресурсов у нас сейчас нет.»

Отдельный локальный бинарь (как арт-студия), генерация контента — нейросеть
через opencode API создателя (на проде не будет).

### Аспекты (решения создателя)

1. **Форма продукта:** отдельный бинарь (не вкладка админки), работает локально
   с opencode API создателя; игровой сервер не трогает. «Результаты переезжают
   в игру».
2. **Три способа добавить товар в граф:** (а) выбрать из сгенерированных
   нейросетью кандидатов-составляющих; (б) написать и добавить самому;
   (в) выбрать из уже имеющихся товаров тиром ниже (включая ресурсы).
3. **Удаление:** удалить совсем или исключить из рецепта (не удаляя из базы
   сервиса — чтобы сохранить возможность включить в другие рецепты).
4. **Статусы «согласовано / исключено»:** подтверждено, память статусов
   переживает перезапуск студии; исключённое генерация больше не предлагает.
   **«Бан» — отдельный статус** (не путать с «переносом в неиспользуемые»):
   забаненный исключается из предложений нейросети, но возвращаем в один клик
   (см. UI, п.7).
5. **Генерация пачки:** студия генерирует до 10 кандидатов-составляющих на
   товар («нейросеть через API скажет, какие логически подходят»), создатель
   решает, сколько оставить; нужна кнопка «удалить». Плюс ручное добавление
   своего товара.
6. **Тир — уровень в графе:** не назначается и не высчитывается специально —
   «мы сами увидим». Рёбра только вверх: товар может быть составляющим только
   товара выше тира (циклы исключены по построению).
7. **UI (видение создателя):** «приятный современный интерфейс со слотами, куда
   кладутся карточки ресурсов, от топ вниз; каждый листик связан с другими».
   Карточка товара; отдельный просмотр «что делается ИЗ этого товара»;
   добавление/удаление слотов составляющих; заполнение слотов сгенерированными
   товарами; новые товары становятся листиками графа. Zoom и drag («на экран
   всё не влезет»). **Правая колонка — «неиспользуемые» компоненты (НЕ
   забаненные)**, карточками, перетаскиваются на слоты; **отдельный
   переключатель на «забаненные»**, отсортированные по времени бана — чтобы
   вернуть случайно забаненное. Валидность и перекосы — валидаторами (позже).
8. **Рецепт = слоты под компоненты** (товары; ресурс — частный вид товара,
   отдельного «ресурсного» слота нет): по умолчанию слот один, пустые
   добавляются кнопкой, заполняются одной кнопкой (нейросеть) или вручную
   (три способа, п.2). Ссылка на ресурсы окном характеристик (твёрдость ≥ X,
   радиоактивность ≤ Y) — остаётся в отложенной корзине качества, в первой
   итерации не решена (см. белые пятна).
9. **Товар-верхушка графа:** возможность добавить товар хай-тира из
   определённой категории («какую-то базу категорий мы накидывали уже») — какой
   именно «базы категорий» (13 позиций §5.2.1 / 6 категорий ресурсов /
   свободное множество) — вопрос задан создателю, ответ не получен — развилка
   для @designer.
10. **Витрина 111 веществ — база листьев графа:** «не контент» означает, что
    названия можно менять либо перестроить состав, чтобы производственная
    цепочка была валидной; число может стать больше.
11. **Результат:** студия сохраняет JSON, «который игра может потом прочитать
    и загрузить себе в базу». Загрузка в БД — будущий мост.
12. **Качество:** «давай пока сделаем то, что выше, потом придумаем, куда
    качество запихнуть» — отложено (см. белые пятна).
13. **Валидаторы графа** (в т.ч. «поймём, каких ресурсов нет») — следующая
    итерация: «пока не знаю, какие нужны».

### Поправки (режим 2 — сверка утверждений)

- **«До 5 составляющих» (пожелание) → фактически генерируется до 10
  кандидатов, создатель отбирает.** Уточнение создателя 2026-09-18: «генерирует
  10, а я решаю, сколько оставить; и надо дать возможность добавить свой».
- **«Сейчас ресурсов у нас 111» → в `real.go` витрина 111 реальных веществ
  помечена «НЕ контент»** (граница спеки 99.2.5; справочные данные по физике);
  игровой контент сейчас — универсальный слой 20 ресурсов (94a,
  `internal/resource/layer.go`). Создатель подтвердил: витрина становится базой
  листьев графа (имена/состав можно перестроить) — это разворачивает границу
  99.2.5.
- **«Допустимое окно качества сужается с тиром» → в доках такой связи нет.**
  §5.2.4: рецепт = ресурсы по окнам свойств и в количестве, без связи с тиром;
  сложность рецепта — отдельное целое число (`11_production.md` §11.1.1),
  запирает тир поселения (`13_tiers.md` §13.9.1). Фраза создателя — новое
  правило (см. развилки).
- **«Тир — уровень в графе» → в `11_production.md` §11.1.1 сложность рецепта —
  целое число.** Связь «уровень в графе ↔ число сложности» не решена.
- **«Рецепты фиксируются в коде» (§5.2.4) → студия производит рецепты как
  данные (JSON).** Где истина — развилка для @designer.
- **«Переезд в игру» → JSON, который игра потом загрузит в базу.** Схема БД
  substances/resources не реализована (следующий релиз), так что загрузка —
  будущий мост.
- **«Перенос в правую колонку = исключение из рецепта» → неверно: колонка
  «неиспользуемые» — это НЕ забаненные.** Уточнение создателя 2026-09-18:
  справа лежат неиспользуемые (не забаненные) компоненты, а забаненные — на
  отдельном переключателе, отсортированы по времени бана (разбан случайно
  забаненного). Бан — отдельный статус: исключает компонент из предложений
  нейросети.
- **«Рецепт ссылается на ресурсы окном характеристик» → формулировка
  уточнена: рецепт = слоты под компоненты** (товары; ресурс — частный вид
  товара, отдельного «ресурсного» слота нет); по умолчанию слот один, пустые
  добавляются кнопкой, заполнение одной кнопкой (нейросеть). Окна
  характеристик остаются в отложенной корзине качества. Также исправление
  создателя: «товар хай-тира, не ресурс. Ошибся. Верхушка графа» — возможность
  добавить товар-верхушку из категории.

## Критика концепта (@critic, 2026-09-18, прогон до дизайна)

Вердикт: **ЕСТЬ 8 (мелких 1, средних 6, крупных 1)**. Полный отчёт — в сессии
критика; здесь — сводка для дизайна и гейта.

**Крупное (1):** студийный рецепт-список (слоты-товары, «до 5 составляющих»)
≠ формальный рецепт §5.2.4 (вещества по окнам свойств и в количестве; «язык
профилей и контрактов — один», §5.2.2). Выход студии без окон не потребляется
игровой моделью рецептов — обещанный «переезд в игру» из посылок первой
итерации не выводится. Решение создателя обязательно (см. гейт).

**Средние (6):**
- №2 «Каких ресурсов нет»: листья графа = витрина 111 (НЕ контент, граница
  99.2.5); валидатор по 111+20 не видит будущие тысячи полевых ресурсов.
- №3 Направление «сверху вниз» vs метод «товар существует, если есть
  потребитель» (§5.2.1) — сверка с потребителями не проговорена.
- №4 Авт. сложность vs «сложность — целое число, тир ≥ сложности» (§11.1.1,
  §13.9.1); связь «уровень в графе ↔ число» не решена (уже в развилках).
- №5 Категории студии = третий реестр поверх категорий ресурсов (6, §9.1.3) и
  товаров (§5.2.1) — терминологическая коллизия + правила §5.2.1.
- №6 Без валидаторов студия может генерировать «постройки»/«энергию» как
  товары (третье правило §5.2.1, §11.1.2).
- №7 «Аналог арт-студии»: у арт-студии нет механизма «переезда в игру»
  (интеграция аватаров — сама кандидат, 67a.1 §13); входные каталоги ресурсов
  живут в коде сервера (layer.go/real.go — Go-литералы), не в конфигах.

**Мелкое (1):** №8 количество — §5.2.4 требует «в каком количестве», слот без
количества не покрывает (если «1 слот = 1 единица» не проговорить явно).

**Дополнения реестра (impact map):** экономический док-блок отсутствует
целиком (05_economy, 09_resources, 11_production, 13_tiers, 11_contracts,
99.2.5); после сдачи 99a добавить связи: 99a → 05_economy §5.2 / 94a / real.go /
99.2.5 / 11_production §11.1.1 / 13_tiers §13.9.1 / cmd/art-studio / GLOSSARY.
