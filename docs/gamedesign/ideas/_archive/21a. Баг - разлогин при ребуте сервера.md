# 21a. Баг — разлогин (при ребуте сервера?)

**Дата:** 2026-09-14
**Приоритет:** 🔴 баг
**Статус:** ✅ Готово (2026-09-14), создатель принял фикс

## Сырое пожелание (создатель, дословно)

> Постоянно сталкиваюсь с разлогином (возможно после ребута сервера, может нет. Нужно исследование)

Уточнения:
- браузер: Chrome;
- после не обязательно долгого простоя; про ребут сервера точно не сказал, но параллельно идёт разработка — вероятно;
- симптом: выкидывает на страницу логина.

## Результат исследования (менеджер, 2026-09-14)

### Как устроена авторизация (факты из кода)

1. JWT stateless, HS256, TTL **24 часа** (`internal/auth/jwt.go:89`). Redis к сессиям отношения не имеет — только ping в `/health` и `/status` (`cmd/server/main.go:298`). Значит **ребут Redis не причина**.
2. Секрет читается из окружения при старте (`JWT_SECRET`), в БД/файлах не хранится (`internal/config/config.go:48`).
3. Фронт хранит токен в `localStorage` (`'token'`), на 401/403 чистит его и редиректит на `/login-page` (`web/static/js/map/data.js:37-42`). Выкидывание на страницу логина = ответ 401 от любого API-запроса (или отсутствие токена в localStorage).

### Тест-гипотеза: «секрет на живом сервере не тот, что зафиксирован»

Эмпирическая проверка 2026-09-14 (сервер запущен как бинарь `C:\Zorion2\zorion-server.exe`, PID 54528):

| Откуда секрет | Длина | Статус запроса `/me` |
|---|---|---|
| `.env` | 53 | **401 Invalid token** |
| `run.ps1` | 53 (hash совпадает с .env) | **401 Invalid token** |
| `AGENTS.md` («минимум-32-символа») | — | **401 Invalid token** |

Все три известных секрета отклонены живым сервером. Значит бинарь запущен **с четвёртым секретом, нигде не зафиксированным**.

## Вывод (гипотезы, по убыванию вероятности)

1. **Секрет JWT плавает между перезапусками.** Кто-то (разработчик/агент/создатель) запускает `zorion-server.exe` вручную с env-переменной, заданной «на глаз» — при каждом рестарте секрет может отличаться → **все выданные ранее токены мгновенно умирают** → любой запрос даёт 401 → фронт выкидывает на логин. Идеально совпадает с симптомом «после ребута сервера».
2. **TTL 24 часа.** Если создатель залогинен дольше суток и не перезаходит — токен протухает; фронт честно разлогинивает. «Не долгий простой» этому противоречит (если только токен не жил сутки в фоне).

## Варианты решения (для выбора создателем)

- **A. Зафиксировать секрет и читать его единообразно** (самый простой, лечит причину №1): читать `JWT_SECRET` из `.env` файла при старте (сейчас Go `.env` не читает), либо договориться: запуск ТОЛЬКО через `run.ps1`. Тогда рестарты не ломают токены.
- **B. Хранить секрет в одном месте вне репо** (например, в БД или в переменной окружения системы) — более надёжно, чуть больше работы.
- **C. Ничего не менять в авторизации**, а рассматривать разлогин как норму после рестарта — если секрет задуман «одноразовым» (маловероятно, неудобно).

## Критерий готовности

После фикса: токен, выданный до рестарта сервера, продолжает работать после рестарта (тест: логин → перезапуск server → `/me` отвечает 200 без перелогина).

## Что НЕ зафиксировано/открытый вопрос

- Откуда берётся секрет при текущем ручном запуске бинаря — вне кода; требует ответа создателя или договорённости.
- Разлогин чаще чем раз в сутки? (для оценки роли TTL)
