# 28a. FPS-счётчик на карте для admin и skycomposer

**Создано:** 2026-09-15
**Статус:** ✅ Готово (2026-09-17, подтверждено создателем)
**Приоритет:** мелкая фича (инструмент создателя, не для игроков)

---

## Сырое пожелание (создатель, 2026-09-15)

> «Интересно, можно ли встроить счётчик FPS на карту, чтоб он дополнительно
> не сильно нагружал проц?»

## Уточнения (создатель, 2026-09-15)

1. **Где:** нижний левый угол карты (канвас).
2. **Кому:** только роли `admin` и `skycomposer`. Для игроков не показывать.
3. **Тесты:** без тестов — создатель проверит сам (явный отказ от @tester,
   решение создателя 2026-09-15).

## Факты из кода (менеджер)

- Цикл кадров карты уже работает постоянно: `animationLoop()`
  (`web/static/js/map/animation.js`) вызывает `requestAnimationFrame(animationLoop)`
  на каждом кадре; `draw()` зовётся из него (ветка полёта). Счётчик FPS
  измеряет кадры, которые и так идут — сам по себе почти бесплатен.
- Роль уже доступна на клиенте: `/me` возвращает `role`
  (`internal/handlers/auth_handlers.go:193`), а `loadUserData()`
  (`web/static/js/map/data.js:210`) его уже вызывает — сейчас сохраняет
  `user.id`, `user.ship_icon`, `user.current_world_id`; `role` не сохраняется
  (нужно добавить).
- Роли: `player` / `admin` / `skycomposer` (`internal/models/user.go`).
- Бэк-энд и миграции НЕ затрагиваются — фича чисто фронтовая.

## ТЗ

1. **Роль (фронт).** В `loadUserData()` (`web/static/js/map/data.js`) сохранять
   `state.userRole = user.role`. В `state` (`web/static/js/map/config.js`) — поле
   `userRole: ''`.
2. **Счётчик (фронт).** В `animationLoop()` (`web/static/js/map/animation.js`):
   - замерять `delta` между кадрами (по `Date.now()` или `performance.now()`);
   - сглаживание: скользящее среднее (EMA) или среднее за ~1 сек, чтобы цифра
     не дёргалась;
   - рисовать надпись **не каждый кадр**, а ~2 раза в секунду (редкое
     `fillText` — самая дорогая часть, поэтому редко = дёшево);
   - позиция — нижний левый угол канваса (с небольшим отступом);
   - рендерить только если `state.userRole` ∈ {`admin`, `skycomposer`}; иначе
     вообще не трогать (ни вычислений, ни рисования).
3. **Нагрузка.** Счётчик не должен добавлять заметной нагрузки: только
   вычитание/деление на кадр + редкое рисование текста.
4. **Внешний вид** — на усмотрение @developer, но просто: число FPS в
   маленьком полупрозрачном тексте/прямоугольнике.

## Критерии готовности

- `state.userRole` заполняется из `/me`.
- На карте у `admin`/`skycomposer` в нижнем левом углу виден FPS
  (сглаженный, обновляется ~2 раза в секунду); у `player` — ничего.
- Нагрузка на процесор от счётчика пренебрежима (редкое рисование).
- Фронт: `node --check` на изменённых файлах (или проверка создателем — по
  его решению тесты/проверку делает сам).

## Реализация (2026-09-15)

**@developer** — 3 файла, ~37 строк. Хирургически, без Go и миграций:

- `web/static/js/map/config.js:34` — `state.userRole: ''`.
- `web/static/js/map/data.js:224` — `if (user.role) state.userRole = user.role;`
  (роль приходит из `/me`, который `loadUserData()` уже вызывает).
- `web/static/js/map/animation.js` — `updateFpsCounter()` + `drawFpsOverlay()`:
  мгновенный return для не-привилегированных ролей (ноль нагрузки); EMA-сглаживание
  по `performance.now()` между кадрами; `fillText` раз в 500 мс (~2 раза/сек);
  полупрозрачная плашка «N FPS» в левом нижнем углу (отступ 8 px, палитра как у
  `drawHoveredStarName`).

**Менеджер (2026-09-15):** перенёс вызов `updateFpsCounter()` из начала кадра в
конец `animationLoop()` — при полёте `draw()` чистит канвас каждый кадр, иначе
плашка мигала бы. `node --check` — ок (все 3 файла).

## Вердикт @tester (2026-09-15): ПРОЙДЕНО после правки (первичный — НЕ ПРОЙДЕНО)

- Первичный прогон: **НЕ ПРОЙДЕНО** — при полёте `draw()` (`clearRect` всей
  канвы, `map_render.js:97`) стирает плашку, нарисованную раз в 500 мс →
  строб ~2 Гц, число нечитаемо. В покое плашка стабильна. Всё остальное по ТЗ
  ок: role-гвард (мгновенный return до `performance.now()`), EMA 0.1, позиция
  левый низ, `elements.ctx`/`state.canvasHeight` существуют, роли совпадают с
  бэком (`models/user.go:10-11`), полётная логика не задета, `node --check` 0.
- **Правка менеджера (2026-09-15):** троттлинг отрисовки (500 мс) убран —
  плашка рисуется каждый кадр после `draw()`. Нагрузка от одной короткой
  строки `fillText` на кадр пренебрежима (при полёте карта и так перерисовывается
  целиком каждый кадр; в покое — один текст без `clearRect`). EMA оставлена для
  плавности цифры. `node --check` — ок.
- **Правка менеджера №2 (2026-09-15, по живому прогону создателя).** Создатель:
  «мигает. не работает на близком зуме» (первое — уже было устранено, второе —
  реальный баг). Причина: **отдельный rAF-цикл `npcAnimTick`**
  (`npc_agents.js:199-206`) — на близком зуме (`scale > nameDisplayThreshold`)
  при летящем NPC-агенте сам вызывает `draw()` после `animationLoop`, и
  `clearRect` стирает плашку (плюс разовые `scheduleRedraw` из ship_render.js).
  Решение: рисование плашки перенесено в **конец `draw()`** (`map_render.js`),
  в `animationLoop` осталось только EMA-обновление (`updateFpsCounter` без
  отрисовки). Теперь любой источник перерисовки (полёт, мышь/панорамирование,
  NPC-цикл, спрайты) заканчивается плашкой — затереть её некому.
  `node --check` — ок (animation.js, map_render.js).
- Проверка тестером была статической (браузера/сервера в окружении нет);
  живой прогон — за создателем (он и планировал проверить сам).
- **Повторный живой прогон создателя (2026-09-15):** «стоп, не мигает. только
  близкий зум проверьте» → после правки №2 (плашка в конце `draw()`) баг
  «не работает на близком зуме» закрыт; ожидается финальное подтверждение.
- Предложенный регрессионный кейс для `docs/QA_CHECKLIST.md`: «FPS-плашка у
  admin/skycomposer в левом нижнем углу: видна в покое, обновляется, стабильна
  при полёте; у player ничего не рисуется» (передано дельтой в «Разнос по докам»).
