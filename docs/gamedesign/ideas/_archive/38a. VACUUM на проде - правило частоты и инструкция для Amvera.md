## Что выяснили (менеджер, 2026-09-15)

### Это событийная частота, а не календарная

VACUUM (ANALYZE) `planets` нужен **после каждой массовой операции, которая
переписывает `planets`**, а не «раз в неделю». Триггеры в админке (из кода):

| Операция | Что происходит | Что чинит VACUUM |
|---|---|---|
| **Генерация вселенной** (`GenerateUniverse`) | TRUNCATE всех таблиц + массовый `INSERT INTO planets` | ANALYZE (статистика планировщика устарела после массовой вставки) |
| **Очистка вселенной** (`ClearUniverse`) | TRUNCATE всех таблиц | после TRUNCATE мёртвых строк нет; ANALYZE нужен при последующей генерации |
| **Регенерация планет** (по мирам) | `DELETE FROM planets WHERE world_id=ANY($1)` + новые INSERT | и VACUUM (мёртвые строки от DELETE), и ANALYZE |

Плюс **массовые прогоны «близнецов»** в «Проверке гипотез» — при больших
сериях накапливают мёртвые строки в `planets`.

**Правило:** сделал массовое (генерация, очистка, регенерация, большой прогон
гипотез) → сразу `VACUUM (ANALYZE) planets;` руками. Не уверен → замерь фильтр
карты: деградировал с ~63 до ~300 мс — пора; вернулся к ~63 мс — хватило.
Единичные операции (одно поселение, одна планета, NPC-агенты — у тех отдельные
таблицы) — не требуют.

**Нюанс:** TRUNCATE не оставляет мёртвых строк (таблица пустая) — после него
VACUUM бессмыслен, но ANALYZE нужен, если следом была большая генерация.
Реальную нагрузку VACUUM несёт после DELETE/UPDATE (регенерация планет, гипотезы).

### Как сделать VACUUM на Amvera (по офиц. документации docs.amvera.ru/databases/postgreSQL.html)

**Ключевой факт:** встроенной SQL-консоли для PostgreSQL в панели Amvera **нет**.
Внутренние имена (`amvera-<user>-cnpg-<project>-rw`) резолвятся только внутри
кластера Amvera — снаружи (с локальной машины) `psql` по ним не подключится
(проверено менеджером: DNS-резолв падает). Два документированных пути:

**Путь A — публичный домен типа POSTGRES + локальный клиент:**
1. В панели Amvera у проекта БД: «Сетевое взаимодействие» → создать **доменное
   имя с типом POSTGRES** (бесплатное, вида `<project>-<user>.db-msk0.amvera.tech`).
2. С локальной машины подключиться по этому домену (клиент **обязан
   поддерживать SSL**): `psql "postgres://<user>:<pass>@<project>-<user>.db-msk0.amvera.tech:5432/zoriondb?sslmode=require"`.
   (pgAdmin: Host `<project>-<user>.db-msk0.amvera.tech`, SSL mode prefer,
   версия pgAdmin ≤ 8.12 — выше v17 libpq даёт SSL-ошибку; альтернатива DBeaver.)
3. Выполнить: `VACUUM (ANALYZE) planets;` (вне транзакции).

**Путь B — pgAdmin как преднастроенный сервис (внутри Amvera):**
1. «Преднастроенные сервисы» → «Утилиты для баз данных» → pgAdmin
   (тариф не ниже «Начальный»).
2. Переменные: `PGADMIN_DEFAULT_EMAIL`, секрет `PGADMIN_DEFAULT_PASSWORD`.
3. В «Настройки» активировать бесплатное доменное имя → зайти в pgAdmin по нему.
4. Register Server: Host = внутреннее имя СУБД (`amvera-<user>-cnpg-<project>-rw`,
   видно на странице «Инфо» СУБД), Maintenance db = `zoriondb`, User/Pass — как
   при создании БД. → Query Tool → `VACUUM (ANALYZE) planets;`.

Проверка после любого пути: фильтр карты по `planets.data` снова ~63 мс (было ~306 мс).

> Доступ к проду из панели — только у создателя; менеджер и субагенты прод-БД
> не трогают (внешних «дверей» в прод нет, что и правильно).
