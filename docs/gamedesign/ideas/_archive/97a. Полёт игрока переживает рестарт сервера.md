# 97a. Полёт игрока переживает рестарт сервера — персистентность активного полёта

**Создано:** 2026-09-18
**Статус:** ✅ Готово (2026-09-18; принято создателем «ок, в тест, и если все хорошо — комить», тест ПРОЙДЕНО)
**Приоритет:** 🔴 баг (потеря прогресса полёта при рестарте сервера; реальный игрок потерял часы пути)

---

## Сырое пожелание (создатель, 2026-09-18)

> «Пользователь летел в далекий мир, полет должен был длиться еще несколько часов. Но после
> перезагрузки сервера пользователь остался в своем мире, хотя проделал уже большой путь.
> Почему так могло случиться, и как это поправить?»

## Диагностика (менеджер, факты из кода)

- **Полёты игроков живут только в памяти:** `internal/travel/manager.go` — in-memory
  `flights map[string]*TravelInfo` + горутина `runFlight` на полёт (`time.After(duration)` →
  `onArrival` → `userRepo.UpdateCurrentWorld`).
- **Никакого хранения в БД нет.** Рестарт = карта пуста + горутины мертвы.
- `users.current_world_id` меняется **только по прибытии** (`travel_handlers.go:214-218`) →
  после рестарта в БД остаётся мир отправления.
- Фронт восстанавливает полёт из `/me` (идея 42a), но после рестарта `/me` отдаёт
  `flight: null` — восстанавливать нечего. Пользователь «откатывается» в свой мир,
  полёт и пройденный путь потеряны.
- **NPC-полёты рестарт переживают** (спека `20a.1` §3.1 «Отказной режим»): в `npc_agents`
  хранится абсолютный `arrive_at`, тик засчитывает прибытие по `arrive_at <= now`.
  Игрок — единственный, кто откатывается. Потолок полёта 20 с убран (2026-09-16) —
  полёты на часы, окно потерь реальное.

## Решения создателя (2026-09-18, дословно)

1. Неоконченный полёт после рестарта — **A: продолжить с оставшегося времени**.
2. `arrive_at` уже прошёл к моменту старта — **да: сразу засчитать прибытие** (как у NPC).
3. Приоритет — **🔴 сейчас**.

## ТЗ

**1. БД — миграция `000044_create_player_flights.sql`.** Таблица активных полётов
(состояние, одна запись на игрока, PK `user_id`):

```sql
CREATE TABLE IF NOT EXISTS player_flights (
    user_id       UUID PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    from_world_id UUID NOT NULL,
    to_world_id   UUID NOT NULL,
    start_x       DOUBLE PRECISION NOT NULL,  -- стартовая точка сегмента (61a, точка P)
    start_y       DOUBLE PRECISION NOT NULL,
    start_time    TIMESTAMPTZ NOT NULL,
    arrive_at     TIMESTAMPTZ NOT NULL        -- абсолютное время прибытия
);
```

**2. travel.Manager — персистентность.**

- `StartFlight`: запись в БД (INSERT, ON CONFLICT (user_id) DO UPDATE — редирект 61a
  заменяет сегмент: новое `start_x/y` = точка P, новый `start_time`, новый `arrive_at`).
- **БД-строку удаляет ТОЛЬКО актуальный полёт** (критик 97a, среднее 1 — гонка
  «старая горутина редиректа ↔ новая строка»):
  - прибытие (`runFlight`, ветка `arrived`): под проверкой актуальности
    (`current == flight`, как в `manager.go:95`) удалить строку **ПОСЛЕ успешного
    `onArrival`** (или одной транзакцией с ним). НЕ удалять до `onArrival`: краш между
    удалением и апдейтом мира = строка потеряна, полёт не восстановится — ровно тот
    баг, который фича чинит (критик, мелкое 3).
  - ветка `cancelled` (старая горутина после редиректа/отмены) — **БД не трогает**
    (строку уже обновил новый `StartFlight` / удалил `CancelFlight`).
  - `CancelFlight` (handler): удаляет строку.
  - `Restore`: удаляет строки обработанных полётов.
- `CancelFlight`: удалить строку из БД (в проде сейчас не вызывается — факт для
  разработчика, ветка мёртвая до появления отмены; критик, мелкое 5).
- **`Restore(now, onArrival)`** — восстановление при старте сервера:
  - строки с `arrive_at <= now` → сразу вызвать `onArrival(userID, toWorldID)`, удалить строку;
  - строки с `arrive_at > now` → перерегистрировать полёт в памяти:
    `StartTime`/`Duration`/`StartX/Y`/`FromWorld`/`ToWorld` — **оригинальные из БД**
    (прогресс и редиректы 61a считаются от них), но горутина ждёт
    `remaining = arrive_at - now`, а не полный `Duration`.
    **Ожидание — отдельное поле `TravelInfo` (напр. `waitFor`), `Duration` НЕ
    уменьшать** (критик, мелкое 4): иначе интерполяция `visibility.go`
    (`timeSince(StartTime)/Duration`) и точка P редиректа разъедутся; фронт сам
    досчитает остаток от оригинального `start_time` (42a, `data.js`).
  - **Фолбэк (единый, критик 97a, среднее 2):** если **любой** из `from_world_id` /
    `to_world_id` не существует (мир удалён перегенерацией) — полёт НЕ восстанавливать,
    строку удалить (молча, как фолбэки 42a/61a). Фронт 42a требует оба мира —
    иначе серверный полёт и клиент разойдутся.
  - Вызывается ДО старта HTTP-сервера (гонок нет).

**3. Обвязка в `cmd/server/main.go`:** после `travel.NewManager()` — `Restore` с
`onArrival = UpdateCurrentWorld` (тот же колбэк, что в `StartTravel`). Порядок: репозитории
готовы → restore → дальше по коду.

**4. Тесты (TDD):**

- travel.Manager: StartFlight пишет в БД; прибытие удаляет; cancel удаляет; редирект
  (повторный StartFlight) обновляет строку (новый сегмент P);
- Restore: будущий `arrive_at` → полёт в памяти с оставшимся временем, оригинальные
  start_time/duration сохранены; прошлый `arrive_at` → `onArrival` вызван + строка удалена;
  битый `to_world_id` → не восстановлен + строка удалена;
- DoD по `AGENTS.md` §2 (`go build` / `go vet` / `go test -race ./...`, `-race` локально
  доступен — PITFALLS «БД и шелл»).

## Критерии готовности

- Полёт, активный на момент рестарта сервера, переживает рестарт: `/me` отдаёт `flight`
  с оригинальными `start_time`/`duration`, остаток пути корректен, прибытие засчитывается
  вовремя (в целевой мир).
- Если рестарт был дольше полёта — пользователь сразу оказывается в целевом мире.
- Редирект в полёте (61a) не ломается: сегмент обновляется в БД.
- `CancelFlight` чистит БД.
- Фронт не меняется (42a восстанавливает из `/me` — уже работает).
- DoD `go build` / `go vet` / `go test -race ./...` зелёные.
