# Ловушки: БД и шелл

- **`TRUNCATE ... CASCADE` запрещён.** Работает на уровне таблиц, а не строк,
  и игнорирует `ON DELETE SET NULL`. Однажды снёс таблицу `users` с паролями
  целиком. Только `TRUNCATE` без CASCADE + явный список + временное снятие FK.
  Разбор: `internal/handlers/admin_universe.go`, `clearUniverseTx`, `ARCHITECTURE.md` §4.1.

- **NULL-спектр экзотики роняет `Scan` в любой выборке `worlds.spectral_class`.**
  Экзотика (ЧД/НЗ/WD/протозвезда) пишет NULL в `spectral_class` (спека `99.2.4` §3),
  и `rows.Scan(&w.SpectralClass)` на NULL падает — строка молча выпадает из
  результата. Любой новый SQL по `worlds` обязан читать
  `COALESCE(spectral_class,'')` (образцы: `repository/world_repository.go`
  `worldColumns`, `handlers/admin_stats_load.go`, `mapcache/snapshot.go`,
  `handlers/planet_handler.go`).

- **`/admin/stats` кэшируется.** Отдал 318 257 планет при 319 573 в БД.
  Для точных цифр — SQL, не эндпоинт.

- **После массовой генерации вселенной нужен `VACUUM (ANALYZE) planets`.**
  Без него карта видимости холодная, `Index Only Scan` фильтров карты даёт
  тысячи heap fetches: `has_life` 306 мс вместо 63. В миграцию не положить —
  `VACUUM` не работает внутри транзакции.

- **`GeneratePlanets` сам очищает старые планеты** (`DELETE FROM planets` в
  начале генерации, каскад безопасен). Баг B11 закрыт 2026-09-12; ручная чистка
  перед перегенерацией больше не нужна.

- **Кэш статистики после перегенерации.** `GenerateUniverse` кэширует «0 планет»
  (планет на тот момент нет — корректно), `GeneratePlanets` сбрасывает кэш
  в начале генерации и пересчитывает в конце (~20 сек на 318k планет) — в окне
  пересчёта вкладка статистики считает заново при каждом запросе. Кнопка
  «Обновить» (`?refresh=1`) сбрасывает кэш принудительно.

- **Windows-шелл: кодировка cp866/cp1251 ломает вывод psql и curl.** В
  PowerShell 5.1 на русской Windows вывод `psql.exe` / `curl.exe` кодируется
  в cp866/cp1251 — при выводе в stdout ломаются русские буквы, а при передаче
  аргументов через `cmd /c` PowerShell экранирует кавычки и `*` не как bash,
  а как glob-шаблон Windows. Неисправимо на уровне оформления — это среда.
  **Как работать:**
  - **psql:** писать SQL-запросы во временный `.sql`-файл (`Set-Content -Encoding
    UTF8`) и вызывать `cmd /c "C:\pgsql\pgsql\bin\psql.exe -h 127.0.0.1 -U
    zorion -d zorion -f C:\path\q.sql"` — НЕ передавать `-c` с unicode-текстом
    в PowerShell (psql получает разбитые аргументы). Пароль — через
    `$env:PGPASSWORD="zorion123"` перед вызовом.
  - **HTTP-запросы к dev-серверу:** использовать `Invoke-RestMethod` (не
    `Invoke-WebRequest` в PSReadLine, он может падать). Для авторизации:
    `POST /login` → токен → заголовок `Authorization: Bearer $token`.
  - **curl:** в PowerShell алиас `curl` — это `Invoke-WebRequest`, НЕ реальный
    `curl.exe`. Для нативного curl: `cmd /c "curl.exe http://..."` или
    `& "C:\Windows\System32\curl.exe" ...`.

- **Готовый вызов (не сочинять заново): `tools/db.ps1` (2026-09-22).**
  `powershell -File tools/db.ps1 -Sql "..."` / `-File q.sql` / stdin — учёт
  кодировки, многострочного SQL, `PGPASSWORD` и `ON_ERROR_STOP` уже внутри.
  Создан 2026-09-22 (идея «устойчивость агентов»).

- **`tools/db.ps1 -Sql` теряет двойные кавычки в JSON-литералах (фича
  «магазин модулей», коммит `a333827`, 2026-09-24).** При вызове из командной
  строки PowerShell (`powershell -File tools/db.ps1 -Sql "…"`) внешняя
  PowerShell пересобирает native-аргумент для дочернего `powershell.exe` и
  вырезает `"`: запрос `SELECT '{"a":1}'::jsonb` доходит до psql как
  `SELECT '{a:1}'::jsonb` и падает `invalid input syntax for type json`
  (проверено живым прогоном). Правило: не встраивать JSON строковым литералом
  в `-Sql` — собирать его функциями `jsonb_build_object(...)`/
  `jsonb_build_array(...)` (образец — `tools/e2e/market-check.js`: знание и
  позиция игрока пишутся через `jsonb_build_object`; при прямом `execFileSync`
  кавычки доживают, но полагаться на это не стоит).

- **`schema_migrations.version` — TEXT, сортировка лексикографическая.**
  `ORDER BY version DESC` ставит `007` выше `000035` (строка «007» > «000035»).
  Для проверки актуальной миграции — `ORDER BY version::int DESC` либо
  `COUNT(*)` (проверено 2026-09-16 при сверке перед миграцией `000036`).

- **PostgreSQL `lower()` НЕ конвертирует кириллицу при collation `C`.** БД
  `zorion` создана с `datcollate = C` — `lower('Лаборатория')` возвращает
  `'Лаборатория'` без изменений (работает только ASCII). Проверено 2026-09-21
  (миграция `000051`): data-миграция по `name_norm` молча не сработала —
  `WHERE name_norm = lower('Лаборатория корабельных модулей')` не нашёл строку
  (в БД `'лаборатория корабельных модулей'`), а INSERT создал «Лабораторию» с
  заглавной буквой в `name_norm`. Правило: в SQL-миграциях сравнивать
  `name_norm` **литералами нижнего регистра** (их пишет Go
  `graph.NormalizeName` = `strings.ToLower`, Unicode-корректный), НЕ через
  `lower()`. Проверка: `SELECT lower('Лаборатория')` на целевой БД.

- **Номер миграции может быть занят параллельной работой между проверкой
  `docs/DB.md` и созданием файла.** Проверено 2026-09-20 (фабрики релиз 1):
  задача давала дроп `production_units` как 000049 (последний в DB.md —
  000047), но параллельная спека 99.2.30 (composite-route) уже создала
  `000049_add_users_pending_destination.sql` — сервер упал на старте
  «duplicate key value violates unique constraint schema_migrations_pkey»
  (две миграции с версией 000049, вторая не записалась). Правило: перед
  созданием миграции проверять **рабочее дерево** (`Get-ChildItem migrations/`),
  а не только `docs/DB.md`; при конфликте — брать следующий свободный номер
  (дроп ушёл в 000050, как в спеке §11.6).

- **PowerShell `Set-Content -Encoding UTF8` портит кириллицу в Go-файлах.**
  PowerShell 5.1 читает файл в системной кодировке (cp1251) и пишет UTF-8 —
  русские комментарии/строки превращаются в «РЅРµРІРѕР·РјРѕР¶РЅС‹С…»
  (двойное кодирование). Проверено 2026-09-17 дважды (race_balancer.go,
  admin_hypothesis_test.go — оба переписаны заново), 2026-09-21 — на
  Python-скрипте (`tools/spike_ship_sprite_flight.py`: `Get-Content -Raw` +
  `-replace` + `Set-Content -Encoding UTF8` превратил кириллицу в мусор и
  добавил BOM). Правило: правка Go/JS/**Python** файлов с кириллицей — только
  через редактор (Edit/Write), НЕ через PowerShell-команды чтения-записи
  файлов (даже для «одной строки» — `-replace`).

- **cmd.exe режет аргументы по `=` — ручные `cmd /c` и `.cmd`/`.bat` получают
  разбитые аргументы.** `cmd /c "script.cmd --spec=C:\x\in.json"` даёт
  `%1=--spec`, `%2=C:\x\in.json` (не `%1=--spec=C:\x\in.json`). Проверено
  2026-09-20 (ships-races-generator): фейковый python для джоба кораблей
  (`--spec=<json> --out=<png>`) не находил файл `--spec` — аргумент был
  разрезан. Реальный python.exe (Go `exec.Command` без cmd) получает
  `--spec=...` целиком — ловушка только у ручных вызовов через `cmd /c` и в
  батниках (`start-all.cmd`). Раньше от неё страдали и `.cmd`-фейки тестов:
  такой фейк обязан был обрабатывать split-форму (`if "%2"=="--spec"` →
  `copy %3 %5`), а не `--spec=` целиком. С 2026-09-24 `.cmd`-фейков в репо нет
  (арт-студия перешла на helper-процесс, см. ниже) — запись остаётся для
  ручных `cmd /c`-вызовов и `start-all.cmd`.

- **Windows-only фейковый python (`.cmd`) делает тесты красными на Linux-CI.**
  `cmd.exe` запускает `.cmd`/`.bat`, а Linux — нет (не программа и не скрипт с
  shebang): `exec.Command(pythonCmd, ...)` падает, пакет красный (арт-студия,
  CI 2026-09-24). Решение — **helper-процесс**: путь к самому тест-бинарнику
  берётся через `os.Executable()` (fallback `filepath.Abs(os.Args[0])`), режим
  эмуляции — через env, `TestMain` перехватывает повторный запуск, выполняет
  эмуляцию и завершает процесс кодом эмуляции до `m.Run` (обычно `0`; режим
  `copy` при исчерпании ретраев возвращает `1`); один код эмуляции на
  обеих ОС, без шелла и `.cmd`
  (`cmd/art-studio/{postproc,generator,handlers}`). Прод-код (`exec.Command`
  без `cmd.Env`) наследует env, поэтому `t.Setenv` доходит до дочернего
  процесса. `t.Skip` на Linux — не решение: фейк должен реально исполняться.

- **Windows: `exec.CommandContext` + таймаут не спасает, если внук держит
  пайп вывода.** `cmd.Wait()`/`CombinedOutput` ждут EOF пайпа, а `Kill()` по
  таймауту убивает только прямой процесс (`cmd.exe`), не внука (`ping`/python)
  — ответ «по таймауту» задерживается на всё время жизни внука. Проверено
  2026-09-21 (подсказка носа кораблей `/ships/auto`): тест с 300 мс таймаутом
  возвращался ~3 с. Фикс: `cmd.WaitDelay = 2 * time.Second` (Go 1.20+) —
  после отмены контекста Wait закрывает пайпы через WaitDelay и возвращает
  `ErrWaitDelay`; в фейке внук не должен наследовать пайп (`>nul 2>&1`).
  Действует для любого `exec.CommandContext` с таймаутом на Windows.

- **Сторож `TestTruncateTablesCoverMigrationFK` приписывает `REFERENCES` после
  последнего `CREATE TABLE` этой таблице.** Проверено 2026-09-22 (миграция
  `000061_money.sql`): `ALTER TABLE npc_agents ... REFERENCES factions(id)` стоял
  ПОСЛЕ `CREATE TABLE money_operations` — парсер теста (`reCreate` ищет
  `CREATE TABLE`, блок тянется до следующего `CREATE` или EOF) отнёс FK к
  `money_operations` и потребовал её в `truncateTables`. Реальная FK — от
  `npc_agents` (обе таблицы уже в списке). Правило: `ALTER ... REFERENCES`
  в миграции ставить **до** первого `CREATE TABLE` (или добавлять таблицу в
  `truncateTables` осознанно) — иначе сторож падает на ложном срабатывании.

- **Ребёнок `planets` без `ON DELETE CASCADE` рушит пути удаления планет (B25,
  2026-09-23).** `player_planet_knowledge.planet_id` создан в `000040` без каскада
  (в отличие от `settlements`/`buildings`/`deposits`/`contracts`/`contract_board_state`/
  `factions`/`planet_resources`) — `DELETE FROM planets` (`clearPlanets` в
  `admin_universe.go`, `clearPlanetsOf` в `admin_regenerate_planets.go`) и
  `DELETE FROM worlds` (каскад `worlds → planets`, `admin_worlds.go`) падали с ошибкой FK.
  Исправлено `000073_planet_knowledge_cascade.sql`. Правило: новая таблица-ребёнок
  планеты/мира — сразу `ON DELETE CASCADE`, иначе админские пути удаления ломаются;
  отказ от каскада — осознанное решение (`TRUNCATE`-путь `clearUniverseTx` использует
  временное снятие FK + явный список `truncateTables`, а не `ON DELETE`).

- **Батник в репозитории: файл только CRLF + cp866 (OEM) (2026-09-22).** `cmd.exe` читает
  `.cmd`/`.bat` побайтово в текущей кодовой странице консоли: UTF-8 или LF-переводы строк
  ломают парсинг неочевидно — исполняются обрывки строк (симптом: `'порт' is not recognized
  as an internal or external command`, вывод обрезан, часть шагов молча пропускается).
  Кодировка консоли машины — 866, в начале батника стоит `chcp 866`. Инструменты
  редактирования сохраняют UTF-8/LF — после каждой правки батника (`start-all.cmd`)
  кодировку и переводы строк проверять заново.
  Второе: при запуске батника с редиректом вывода в файл (`start-all.cmd --no-pause > файл`)
  файл-приёмник остаётся заблокирован после завершения — дескриптор наследуют отвязанные
  дочерние сервисы; в автоматических прогонах писать вывод в отдельный файл на прогон.

- **JSONB-параметры: `jsonb_set` НЕ создаёт отсутствующий промежуточный объект.**
  `jsonb_set(p, '{a,b}', v, true)` при отсутствии `a` — **молчаливый no-op**
  (проверено на PG 16.9: `jsonb_set('{"eat":{"x":1}}', '{effects,продовольствие}', '"голод"', true)`
  → `{"eat":{"x":1}}`). Пилотная привязка эффектов
  (`migrations/000070_supply_effects.sql`, спека
  `2026-09-22-эффекты-снабжения-задержка-голод` finding 1) из-за этого не
  активировала голод на существующих БД. Правило: вложенные привязки в `params`
  собирать слиянием `||` с объектом-обёрткой
  `jsonb_build_object('effects', COALESCE(params->'effects','{}'::jsonb) || '{"продовольствие":"голод"}')`
  — отсутствующий промежуточный объект создаётся, чужие ключи внутри
  сохраняются. Слияние `params || '{"eat": {…}}'` по-прежнему запрещено
  (затирает **весь** объект `eat` — нормы «вода»/«пища» пропадают). **Строка в
  миграции — не доказательство: проверять на живой БД.**

- **JSONB-слияние `||` сливает только ВЕРХНИЙ уровень: вложенный объект
  заменяется целиком (фича снимка, коммит `7de1ca0`, 2026-09-23).** Upsert
  знания (`knowledge_repository.go`:
  `data = player_planet_knowledge.data || EXCLUDED.data`) сохраняет ключи,
  которых нет во входящем payload, но если payload несёт
  `surface_composition`/`snapshot`, старое значение этого ключа исчезает
  **целиком** — вместе со всеми под-ключами. Правило: нужен «частичный»
  апдейт внутри вложенного объекта — сначала прочитай запись
  (`GetKnowledge`), собери значение в Go и отправь целиком; частичных
  обновлений внутри JSONB здесь нет.

- **Data-миграция каталога идёт ДО Go-сида — вставка ребёнка по подзапросу
  родителя на свежей БД даёт `parent_id = NULL`.** Проверено 2026-09-24 (миграция
  `000077`, ступени поселения): `migrations.Apply` вызывается раньше
  `goodsstudio.SeedProducers` (`cmd/server/main.go`), поэтому на свежей БД
  типа-родителя («Поселение») ещё нет. Прямой `INSERT ... parent_id = (SELECT id
  FROM producer_types WHERE name_norm = 'поселение')` вставил бы детей с
  `parent_id = NULL`, и сид (`ON CONFLICT (name_norm) DO NOTHING`) их уже не
  починил бы: запись есть, но в дерево/ладдеру не входит. Правило: data-миграция,
  вставляющая детей каталога, защищается от отсутствия родителя — `INSERT ...
  SELECT ... CROSS JOIN (SELECT id FROM producer_types WHERE name_norm = 'родитель')
  AS root` (пусто → ноль строк, записи создаст сид) либо `WHERE EXISTS (...)`.

- **Локальный ИИ-помощник студии: спавн и гашение отдельного процесса
  (спека `2026-09-24-студия-управление-локальным-ии`, пакет
  `internal/goodsstudio/aiserve`).** Запуск — `cmd.exe /c npx -y opencode-ai
  serve --port <порт>` с `DETACHED_PROCESS` + `CREATE_NEW_PROCESS_GROUP`, лог —
  `logs/opencode_serve.log` (append, общий с `start-all.cmd`). Гашение —
  `taskkill /PID <pid> /T /F`: `/T` убивает сам процесс **и его потомков** —
  слушающий порт `node` и всё, что он породил; обёртки `cmd`/`npx` — **предки**
  и в дерево не входят (завершаются сами, порт не держат). Поэтому критерий
  успеха гашения — **освобождение порта** (поллинг до 10 с), а не смерть
  каждой обёртки: метод Б (скан процессов) даёт несколько кандидатов одного
  дерева, первый `taskkill /T` убивает дерево, а последующие вызовы по мёртвым
  PID дают «process not found» — это **успех**, а не 500. Опознание кандидата —
  по командной строке (`opencode` + `serve` + порт отдельным токеном), чужое
  не гасим. Второе: если в окружении сервера задан `OPENCODE_SERVER_PASSWORD`,
  помощник, поднятый вручную (`start-all.cmd`/из окна opencode), наследует его и
  требует basic-auth — клиент студии (`internal/goodsstudio/ai`) его не умеет и
  получает 401. Поэтому спавн помощника **из студии** вырезает
  `OPENCODE_SERVER_PASSWORD`/`OPENCODE_SERVER_USERNAME` из окружения ребёнка
  (`helperEnv`, `proc_windows.go`) — помощник, поднятый кнопкой, пароля не
  требует (проверено 2026-09-24: без заголовка авторизации
  `GET /global/health` → 200, `version` в статусе непуст).

- **Колонка `system_belts` — «тройная правка» в тестах (лёд в поясе, 2026-09-24,
  миграция `000078`).** Добавление колонки к `system_belts` (`ice_remaining`, как
  раньше `iron_remaining`) требует синхронной правки в **трёх** точках одного
  INSERT/SELECT-контракта: (а) регекс/текст запроса, (б) список колонок, (в) число
  значений-плейсхолдеров. Плюс в дереве есть **отдельная хардкод-копия** SELECT-запроса
  поясов — её тоже надо обновить. Пропуск любой из точек даёт
  `expected N arguments`/`column does not exist` или молча зелёный тест, разошедшийся с
  репозиторием.

- **Форматирование номерной метки: `lpad` обрезает, `to_char` переполняется
  (метка `code`, 2026-09-24, миграция `*_catalog_code.sql`).** `lpad(n::text, 4, '0')`
  при `n ≥ 10000` **обрезает** до 4 цифр (`lpad('10001',4,'0')` → `'1000'`), а
  `to_char(n, 'FM0000')` при `n ≥ 10000` даёт `'####'` (проверено на PG). Метка
  обязана расти без обрезки (`g_0001` … `g_10001`), поэтому номер собирается
  `CASE WHEN n < 10000 THEN lpad(n::text, 4, '0') ELSE n::text END` — в функции
  `catalog_format_code(prefix, n)`; DEFAULT колонки вызывает
  `catalog_next_code(prefix, seq)` (`nextval` **один** раз на вызов: два `nextval`
  в одном выражении сожгли бы два номера).
