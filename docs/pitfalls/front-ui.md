# Ловушки: Фронт и UI

- **Браузерный WebSocket API не умеет кастомные заголовки.** WS-ручки,
  закрытые `AuthMiddleware` (только заголовок `Authorization`), в браузере
  недостижимы — `new WebSocket(url)` всегда получит 401 и уйдёт в реконнект.
  Решение в Zorion: для пути `/ws` middleware принимает токен в query
  (`?token=JWT`) — ограничено ТОЛЬКО этим путём (остальные ручки не
  расширены), см. `internal/auth/middleware.go`. При добавлении новых
  WS-ручек учитывать: либо query-токен, либо subprotocol (Bearer с пробелом
  в subprotocol невалиден — токен передавать без префикса).

- **Перекраска спрайта через `globalCompositeOperation='hue'` НЕ сохраняет
  альфу: фон красится в цвет заливки.** Blend-режим 'hue' для прозрачных
  пикселей берёт цвет заливки — без восстановления альфы получаются цветные
  квадраты вместо кораблей (найдено на живом демо 2026-09-16, спека 61b §5.3).
  Обязательная последовательность в `recolorShipSprite`
  (`web/static/js/map/ship_sprites.js`): `drawImage(спрайт)` →
  `gCO='hue'` → `fillRect(цвет)` → `gCO='destination-in'` →
  `drawImage(оригинал)` (вернуть альфу) → `gCO='source-over'`. Кэш по ключу
  «спрайт|цвет», лениво; `color = null` — исходный Image без перекраски.

- **Выбор корабля агента на клиенте: людской пул содержит 4 типа, и «вариант
  по суффиксу» без типа сваливает всех людей в один корабль.** В расовом
  реестре `shipFilesByRace["humans"]` — 12 файлов (4 типа × 3 варианта), у
  остальных рас — один тип. Наивный выбор по суффиксу `_0<v>` находит
  совпадение сразу в четырёх типах (выигрывает последний) → все люди с одним
  слотом получают один корабль. Правило (`spriteForAgent`,
  `web/static/js/map/ship_sprites.js`, спека 2026-09-23 §6.3): у людей сначала
  тип вторым хешем по фиксированному списку (`starship/cruiser/carrier/fighter`),
  затем вариант слотом внутри типа. Второе: `pool[v % len(pool)]` ломает
  стабильность при росте реестра — выбор только по суффиксу; нет `_0<v>` →
  НАИМЕНЬШИЙ суффикс расы (не нейтральный; нейтральный — только пустой
  расы/пул). Проверка — `tools/e2e/race-ships-variant-check.js`.

- **Выпил легаси-набора кораблей (П4): `neutral.png` — байтовая копия
  удалённого `crescent.png`, чистка каталога по имени/хешу снесёт нейтральный
  корабль.** Из `web/static/sprites/` удалены 21 легаси-PNG (`anchor.png` …
  `volcano.png`, включая `crescent.png`), но `neutral.png` (`NeutralShip`,
  фолбэк рас без корабля) намеренно оставлен и **побайтово равен**
  `crescent.png` (спека `2026-09-23-корабли-рас…` §6.4). Массовая чистка «все
  файлы без префикса `race_`» или дедупликация по хешу уберут и его — раса без
  пула получит 404 и ромб вместо нейтрального. Правило: в этой папке живут
  `race_*.png` + `neutral.png` (и подкаталоги `biomes/`, `belt/`); легаси-
  идентификаторы (`ShipSprites`, `LegacyShipIconMap`, `DefaultShipIcon`, дефолт
  `crescent.png`) из `internal/models/` удалены — не возвращать; дефолт
  `users.ship_icon` — `DefaultHumanShip` (`race_humans_starship.png`),
  неизвестное имя → он же (`ResolveShipIcon`).

- **Hit-область объекта на канвасе обязана совпадать с отрисовкой (экранный
  минимум радиуса).** В модалке системы (70a, найдено тестером 2026-09-17)
  звезда на низком зуме рисуется с экранным минимумом `MIN_STAR_PX`
  (`Math.max(s.radius, MIN_STAR_PX / zoom)` в `modal_render.js`), а hit-тест
  в `events.js` сравнивал с голым `s.radius + 8` в мировых координатах — на
  wide-зуме (~0.0007) hit-область была ≈0.04 px при нарисованных 4 px, тултип
  и клик по компаньону не срабатывали (83% бинарных систем — wide). Правило:
  hit-тест использует тот же радиус, что рендер
  (`Math.max(s.radius, MIN_STAR_PX / modalState.zoom) + 8`); константа
  экспортируется из `modal_render.js` — не дублировать.

- **Браузер кэширует картинки пула арт-студии по URL — после перегенерации
  с теми же именами (s01..sNN) превью показывает старые.** `loadShipsList`
  (`cmd/art-studio/web/index.html`) дифф-рендерит карточки по `data-file`:
  существующая карточка не пересоздаётся, а `img.src` без параметра остаётся
  тем же URL — браузер отдаёт закэшированную старую картинку. Фикс (2026-09-20):
  cache-busting `?t=<счётчик>` — `shipBust` растёт на каждый «Сгенерировать»
  (не `Date.now()` на каждый 3-сек поллинг — перекачивал бы все картинки вечно);
  src обновляется и у существующих карточек (карточка не пересоздаётся —
  сохраняются кнопки/вердикт). Тот же паттерн в `loadHumans` (`/humans/img/`) —
  при перегенерации пула людей с теми же именами баг воспроизведётся.

- **Аудио-модуль, попадающий в import-граф админки, обязан быть
  Node-безопасным, а звук — активируемым по странице.** `web/static/js/ui/sound.js`
  тянется в админку через `ui/toast.js`, а `web/frontend_test.go`
  (`TestAdminFrontendLoadsInNode`) исполняет граф `admin/main.js` в Node под
  DOM-стабом **без** `AudioContext`. Правило: ни одного обращения к
  `document`/`AudioContext`/`fetch` на верхнем уровне модуля — `AudioContext`
  создаётся лениво, буферы грузятся по роли внутри функций. Guard — именно
  `typeof AudioContext` (в стабе `window === globalThis`, проверка `window` не
  спасает). Промисы `resume()`/`decodeAudioData`/`fetch` глушить
  (`p.catch(()=>{})`), иначе
  unhandled rejection роняет e2e-смоук `tools/e2e/map-check.js` на любом
  `pageerror`. Админка молчит через **флаг активации**: страница карты зовёт
  `activateSound()`, до этого все play-функции — no-op (общий `ui/toast.js` сам
  по себе звук не включает). Звуки — файлы Kenney CC0 (`web/static/audio/`,
  OGG Vorbis).
  **Гул — только Web Audio, НЕ `<audio loop>` (ловушка 8, баг 2026-09-21):**
  `<audio loop>` вставляет разрыв ~0.3 с на стыке повтора (слышно «рвётся»),
  даже если файл склеен в бесшовный луп. Лечение: `AudioBufferSourceNode` с
  `loop = true`; остановка — ramp `GainNode` в 0 (без щелчка).
  **F5/автоплей (ловушка 7):** `AudioContext` стартует `suspended`; гул, стартовавший
  при инициализации, звучит только после `resume()` на первом жесте. При
  `activateSound()` вешается **одноразовый** слушатель первого жеста
  (`pointerdown`/`keydown`/`touchstart`): делает `resume()` и, если гул был
  запрошен (`humRequested`), поднимает его; после жеста снимает себя.
  Проверено 2026-09-21 (звук отклика и полёта).

- **`formationBlend` (прогулка по поверхности) со смесью `prev+cur+next` рвал
  рельеф на границах регионов.** `web/static/js/surface/surface_world.js`:
  на `local=1` региона `i` вес `wNext=1` давал формацию региона `i+1`, а на
  `local=0` региона `i+1` вес `wPrev=1` давал формацию региона `i` — скачок
  высоты до **~128 px** на 32 из 41 границы (комментарий обещал непрерывность).
  Последствие: парящий камень (`float`) привязан к `terrainHeight`, и на обрыве
  повисал ниже игрока — упор в видимую стену, а сам рельеф читался «обрывом
  мира» каждые 1400 px. Фикс (идея 2026-09-21 §4, 2026-09-21): смесь только
  `prev→cur` на входе региона (`wCur = 1 - wPrev`) — обе стороны границы дают
  одну высоту; смесь на входе (а не на выходе) выбрана, чтобы не менять высоту
  в точке спавна `x=0` (`local=0`). Проверено живым прогоном
  `tools/e2e/surface-walk-check.js` и покадровой симуляцией `Player`.

- **Спавн прогулки ниже корки поверхности = провал в пещеру.** `surface_player.js`
  ставил центр на `terrainHeight(0) − 4`, ноги — на `th+10`, ниже 8-px корки
  `isCave` (`d < 8`). Если под спавном пещера, игрок падал в неё и застревал в
  породе (10f «персонаж идёт» в e2e падал на биомах вроде «Планктонные моря» —
  старая и новая версия одинаково, баг не от правки стен). Фикс: центр на
  `th − h/2 − 2` (ноги у поверхности, корка держит). Проверено симуляцией
  `Player` (планктонные_моря: 28 px → 480 px пути).

- **Мировые сущности перебирать по экранной сетке = дёргание слоёв (прогулка по
  поверхности).** `drawDecor` (`web/static/js/surface/surface_render.js`) шёл по
  экранной сетке `sx += 4`, для точки брал мировую колонку `Math.floor(left + sx)`,
  а рисовал по экранной `sx`: при дробном сдвиге камеры набор опрошенных колонок
  менялся — дерево выпадало из выборки или попадало в соседнюю клетку (за 4 px
  хода ~527 «мерцаний», позиция «дрожала» до 0.9 px). `drawFarRelief` брал ту же
  мелкодетальную `terrainHeight(wx*1.4)` шагом 12 px по экрану — силуэт менял
  форму каждый кадр (до 4 px при 10 px хода). Правило: выборку/перебор мировых
  сущностей вести по **мировой** решётке (шаг в мире), экранную координату брать
  непрерывной `wx − camera.x + vw/2`; дальний план — своя низкочастотная функция
  высоты (`SurfaceWorld.farHeight`, только крупные октавы) на фиксированной
  мировой решётке, тогда при сдвиге камеры на Δ силуэт уезжает цельно на 0.35Δ.
  Проверено чистой геометрией (смещение и форма — бит-в-бит) и e2e
  `tools/e2e/surface-walk-check.js` (14/14) + `surface-admin-biome-check.js` (13/13).

- **Зум прогулки по поверхности: число рисуемых чанков — от ширины вьюпорта и
  зума, не константа.** `drawTerrain`/`drawCreatures`
  (`web/static/js/surface/surface_render.js`) рисовали ±`CHUNK_RADIUS`=3 чанка
  (~1792 px) вокруг камеры, а декор (`visibleDecor`) перебирался по всей ширине
  экрана. На экране шире ~1792 px за краями чанков земли не было, а деревья были —
  висели в пустоте (идея 2026-09-22 §8.3). Плюс общий визуальный масштаб `ZOOM`
  (1.8×, только отрисовка — трансформ камеры в `surface_main.js`; физика
  `PPM`/скорости/гравитация не меняются) сужает видимую ширину мира до `vw/ZOOM`.
  Правило: радиус считать `max(CHUNK_RADIUS, ceil(vw/(2·ZOOM)/CHUNK)+1)`. Канвас —
  в device-пикселях (`devicePixelRatio`), логика — в CSS-пикселях (базовый
  `ctx.setTransform(dpr,…)`, размеры `window.innerWidth/innerHeight`).

- **Апскейл 1:1 кэшированных чанков зумом даёт 1-px шов на стыках.** Билинейная
  выборка края канваса чанка (`drawImage` под `scale(ZOOM)`) на границе сэмплит
  «за» битмапом → полупрозрачная вертикальная полоса каждые `CHUNK·ZOOM` px
  (в скриншоте — тёмный столбец). Фикс: `getChunkCanvas` рендерит канвас на 1
  колонку шире (`CHUNK+1`) с реальными данными следующей мировой колонки —
  перекрытие без искажения. Растянуть `drawImage` (destination `CHUNK+1`) нельзя:
  сдвинет рельеф относительно декора на краю чанка. Проверено замером столбцов
  скриншота (было 2 столбца с перепадом ≥5 на ~460 px шага — стало 0).

- **Отрисовка твёрдого объёма грубым шагом = невидимые стены (парящая порода,
  прогулка по поверхности).** Растр парящей породы в `getChunkCanvas`
  (`web/static/js/surface/surface_render.js`) шёл по x шагом 3 px и рисовал блоки
  3×3 по сэмплу: у твёрдой области оставалась непокрашенной **левая кромка до
  3 px** (первый сэмпл внутри области рисует блок ВПРАВО от себя), плюс сетка
  сэмплов смещалась на `baseX % 3` в каждом чанке. Игрок, идя влево→вправо,
  упирался ровно в непокрашенную кромку — невидимая стена. Правка: растр —
  **надмножество** твёрдой области (`isSolid`). Шаг по x — 1 px, блок 3×3 со
  сдвигом −1 (запас ±1 px по x), по y — полоса сканируется шагом 1 px с запасом
  `FLOAT_BLEED`; у самых границ полосы (`y < th−FLOAT_GAP` / `y > th−FLOAT_SPAN`)
  обязательны **пробы, смещённые внутрь на ε** — граница обрезает блоб, оставляя
  субпиксельные твёрдые полоски, где ни один сэмпл сетки не твёрд. Замер (все 6
  категорий × все формации, все точки коллизий игрока: центр, `x±w/2`, `y±h/2`,
  ground truth — реальный `getChunkCanvas` + `isSolid`): было **5709**
  непокрашенных твёрдых точек (0.609 %, все 9 float-формаций 1.1–1.5 %), стало
  **0**. Цена: генерация чанка ~11.7 → ~20.0 мс (шаг по x 3→1 и по y 3→1);
  кэшируется, на спринте — единичный кадр ~33 мс на генерации нового чанка.

- **Бюджет вертикали чанка: профиль выше растра = твёрдая невидимая земля
  (2026-09-23, Э3 «Словарь профилей»).** Профиль прогулки — база (`large`/`detail`,
  вычитаются из `baseY`) плюс стек `relief.layers` (§3.1). У примитивов Δy
  **отрицательна = вверх**, поэтому слои **прибавляются** к `y`:
  `baseY + offset − scale·(large+detail) + scale·Σlayers`. Сложить `Σlayers`
  внутри отрицаемого `rise` — **перевернуть форму** (гребень → впадина,
  `carve` → вал); знак ловится тестом `tools/surface-profile-check.mjs` (P8),
  а не глазами — симметричные примитивы (`dome`) маскируют его.
  Вторая половина ловушки — сам запас. Растр чанка — `[baseY − CHUNK_TOP_MARGIN,
  baseY − CHUNK_TOP_MARGIN + CHUNK_HEIGHT]`; полоса `float` рисуется ещё на
  `FLOAT_SPAN` **выше** рельефа, поэтому для всех `x` обязано быть
  `terrainHeight(x) ≥ baseY − CHUNK_TOP_MARGIN + 24 + FLOAT_SPAN` и
  `terrainHeight(x) ≤ baseY − CHUNK_TOP_MARGIN + CHUNK_HEIGHT − 24` (формула
  §6 п.6 для низа — `baseY + CHUNK_HEIGHT − 24` — **завышена на `CHUNK_TOP_MARGIN`**,
  ею низ не проверить). Запас считается от `baseY + offset` (`offset −180`
  у гор = +180 headroom), **не** от `baseY`. Проверка — T-budget по свипу seed
  (`tools/surface-profile-check.mjs`, P1/P9), не арифметика на глаз.
  **Как лечится (порядок):** сначала `relief.scale`/`base` рецепта (у гор ЧК0
  `scale 0.55` при `CHUNK_TOP_MARGIN = 700` давал `y_min ≈ −281` при полу `−116`);
  но срезание `scale` до 0.22 убивало форму — **рабочий фикс: рост
  `CHUNK_TOP_MARGIN` 700 → 1200** (2026-09-23, Э3). Высота канваса та же, поэтому
  **память НЕ растёт** `(CHUNK+1)·CHUNK_HEIGHT·SS²·4`; меняется только `topY`
  (проверять низ: дно опускается на ту же величину). Если рамка растёт, глубинный
  градиент обязан остаться привязан к рест-линии (`DEPTH_TOP_MARGIN`), иначе весь
  кадр темнеет. Серверный `declaredReliefTop` (`biome_view.go`) этот запас пока
  **не** учитывает (нет `FLOAT_SPAN`, `step` берётся как `stepH`, а не `4·stepH`) —
  рецепт может пройти сервер и всё равно выйти за растр.

- **Слой среды прогулки (сутки) затемняет ближний мир, и абсолютный порог детекта
  игрока в e2e ломается.** `web/static/js/surface/surface_environment.js`
  (`drawEnvironmentFront`, спека 2026-09-22 §6.3) накладывает ночной тинт
  `alpha = 1 − lightMul` на всё ниже горизонта: тело игрока `#f8fafc` в ночи
  (lightMul 0.25 + пелена погоды) уходит в ~(71,59,65). `tools/e2e/surface-walk-check.js`
  пункт 10g искал визор по абсолютной разнице каналов (`dR >= 45`) от «самого белого»
  пикселя полосы — в ночи `dR ≈ 32` → тест падал, а «самый белый» пиксель мог
  оказаться не телом (декор/облако светлее затемнённого скафандра). Правило: детект
  игрока — по НАПРАВЛЕНИЮ «тело → визор» (ΔR:ΔG:ΔB = 192:61:4 — аффинный тинт его
  сохраняет) с низким порогом `dR ≥ 12`; эталон тела — пиксель в центре игрока
  (камера: центр по X, `0.58·vh` по Y), читается один раз в покое. Проверено 10g в
  фазах ночь/рассвет с пеленой погоды.

- **Настройки графики карты — в localStorage дашборда, и тумблер мерцания
  обязан гасить непрерывный кадр, а не только эффект.** Вкладка дашборда
  «⚙️ Графика» (`web/static/js/dashboard/graphics.js`, идея 2026-09-22) пишет
  ключи `starVisualPreset`, `starVisualTwinkle`, `starVisualIgnite`,
  `starVisualAdditive`, `starVisualExotic`, `starVisualPetals`,
  `radarBoundaryVariant`, `starVisualLite`; карта (`map/star_render.js`) их
  только читает — общий origin, сервер не участвует. Ловушка: `starVisualOptions()`
  управляет и видом, и эффектами, но непрерывный rAF-кадр поднимают
  `starNeedsAnim()`/`ensureStarAnimLoop()`. Если гасить мерцание только в
  `twinkleFactor()`, `starNeedsAnim()` продолжит поднимать кадр, пока
  `singles ≤ 400`, и слабый ПК будет крутить перерисовку на статичной картинке —
  экономия пропадёт. Режим «Для слабых ПК» (`starVisualLite='1'`) возвращает из
  `starVisualOptions()` `{mode:'sprite', все эффекты false}`, **не трогая**
