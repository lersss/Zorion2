# Ловушки: Go и конкурентность

- **Go: тег JSON на строке с несколькими полями применяется ко ВСЕМ полям
  строки.** `TMin, TMax float64 json:"t_min,omitempty"` — оба поля получают
  тег `t_min`: `TMax` молча не читает `"t_max"` из JSON (остаётся 0), а
  `TMin` конкурирует с `TMax` за ключ `t_min`. Проверено 2026-09-20
  (99.2.28, biome_catalog.go): T-диапазоны биомов читались как 0, крио-биомы
  не рождались. Правило: каждое поле — на своей строке со своим тегом
  (`TMin float64 json:"t_min,omitempty"` / `TMax float64 json:"t_max,omitempty"`).

- **Персистентность полёта игрока (97a): БД-строку `player_flights` удаляет
  ТОЛЬКО актуальный полёт и ПОСЛЕ onArrival.** Три правила
  (`internal/travel/manager.go`): (1) удаление до onArrival = краш между
  DELETE и апдейтом `users.current_world_id` теряет полёт — ровно баг 97a;
  (2) старая горутина редиректа (отменена через CancelChan) БД не трогает —
  строку уже заменил новый StartFlight (Upsert); (3) гвард после onArrival:
  если для пользователя уже зарегистрирован новый полёт — строку НЕ удалять
  (иначе удалишь строку нового сегмента), причём проверка актуальности и
  Delete — под ОДНИМ локом (TOCTOU-фикс ревью 97a: между проверкой и
  удалением новый StartFlight успел бы вставить полёт в map и сделать
  Upsert). `CancelFlight` чистит БД под локом — иначе DELETE мог бы снести
  строку нового полёта, стартовавшего между разблокировкой и удалением.

- **Композитный маршрут (99.2.30): Restore-колбэк межзвёздного полёта обязан
  идти через общий `TravelHandlers.ArrivalHandler`, а не через простой
  UPDATE.** Фаза 1 Restore (`travelManager.Restore` в main.go) передаёт
  onArrival-колбэк; если он делает только `UpdateCurrentWorldAndPosition`
  (как было до фикса ревью 2026-09-21), автостарт внутрисистемного сегмента
  по намерению (`users.pending_destination`) не сработает для восстановленного
  полёта: игрок прилетит к звезде, намерение останется в БД и «выстрелит»
  неожиданным intra-стартом при следующем рестарте (намерение-призрак, И6).
  Правило: live-onArrival и Restore-колбэк — один общий `ArrivalHandler`
  (ИП-2 + чтение намерения + автостарт). Вторая ловушка той же зоны:
  автостарт корректен только при `current_world_id == dest.WorldID` (прибытие
  засчитано onArrival до краша); краш между `CancelAtomicWithDestination` и
  `StartFlight` оставляет намерение при current_world_id мира отправления —
  фаза 3а Restore обязана очистить намерение, а не стартовать intra (иначе
  рассинхрон current_world_id/current_position, ИП-1 99.2.27).

- **gorilla/websocket: чтение с истёкшим дедлайном необратимо ломает
  соединение.** `Conn.ReadMessage` при ошибке (в т.ч. i/o timeout по
  `SetReadDeadline`) фиксирует `readErr` — все последующие `ReadMessage` на
  этом соединении сразу возвращают ту же ошибку, продление дедлайна не
  помогает. В тестах «сообщение не приходит в интервале» нельзя читать с
  коротким таймаутом, а потом продолжать читать то же соединение — для
  негативной проверки использовать отдельное соединение/тест, либо проверять
  дроссель на уровне логики (в Zorion — юнит-тесты `NotificationBatch`,
  `internal/npc/notification_batch_test.go`).

- **Кэш агентов для позиций (идея 26c A2): любая внешняя мутация `npc_agents`
  без `MarkDirty()` → позиции на карте устаревают НАВСЕГДА.** Позиции карты
  интерполируются из in-memory кэша менеджера (`internal/npc/agent_cache.go`),
  который перезагружается из БД только при dirty-флаге (или старте). Пока
  тик не трогает агента (нет стартов/прибытий), кэш не обновится — если
  хендлер изменил агента мимо тика и не поставил dirty, карта будет показывать
  старое состояние бесконечно (а не до следующего тика, как было при
  `ListAll` на каждый тик). Правило: **каждая точка записи в `npc_agents`
  вне тика обязана вызвать `manager.MarkDirty()`** (или `OnAgentsDeleted()`
  при массовом удалении). Текущие точки: `CreateAgent`/`PatchAgent`/
  `DeleteAgent`/`GenerateNPC` (`internal/handlers/admin_npc.go`),
  `ClearUniverse`/`GenerateUniverse` — TRUNCATE `npc_agents`
  (`internal/handlers/admin_universe.go`, через `SetNPCManager`). Кэш мутирует
  ТОЛЬКО тик (И1): хендлеры — только atomic-флаг, иначе data race (§0).

- **Балансировщик кривых (99.2.17): мини-R читают store на КАЖДОМ вызове,
  GetCurve обязан возвращать копию слайсов.** `HeatTemperatureChangeRate`/
  `ColdChangeRate`/`GravityChangeRate`/`RadiationChangeRate` зовут
  `GetCurve("heat"...)` из `ChangeComponents`, который выполняется во многих
  горутинах (пересчёт населения, смерть, проеция). Store — глобальный
  `RWMutex` (`internal/economy/settlement/balancer_store.go`); `GetCurve`
  возвращает **копии** `nodes`/`bends`, а не внутренние слайсы — иначе
  вызывающий код (напр. `evaluateCurve`) или мутация извне испортил бы store
  без блокировки. `SetCurve`/`ResetCurve` — `Lock` + атомарная замена всей
  кривой (клон). Экстраполяция кривых горизонтальная (константа крайнего
  узла): экстремальные входы (гравитация 1000 g) больше НЕ дают r ≥ 1 — гвард
  Population остаётся страховкой, но не срабатывает от перегрузки (см.
  `TestRGuardCap` в `mortality_test.go`).

- **Тип и переменная пакета не могут называться одинаково.** Спека `99.2.17`
  §5 показывает `type balancerStore struct {...}` + `var balancerStore = &balancerStore{...}`
  — это не компилируется. В коде переменная названа `balancerCurveStore`
  (конвенция как `settings.go`: тип `populationSettings` → var `popSettings`).

- **Пресеты балансировщика (99.2.17 итерация 7): не вызывать `SetCurve`/
  `ResetCurve` из пресет-операций — вложенный `Lock` = deadlock.**
  `SetCurve`/`ResetCurve` сами берут `balancerCurveStore.mu.Lock()`, а пресет-
  операции (`SavePreset`/`ApplyPreset`/`ResetDefaultPreset`) обязаны держать
  ту же блокировку, чтобы store и файл менялись согласованно (§5). Поэтому
  внутри пресет-операций кривая мутируется напрямую
  (`balancerCurveStore.curves[comp] = cloneCurve(...)`), а не через сеттеры.
  `sync.Mutex` не реентрабельный — вложенный Lock убьёт сервер. Файл
  пресетов пишется атомарно (tmp + `os.Rename`) под той же блокировкой;
  ошибка записи — лог, пресеты сессионные (сервер не падает).

- **`galaxy` не может импортировать `planet` (цикл через `planet/twin.go`).**
  Для сортировки пары «главная = самая массивная» (35c) galaxy нужно
  сравнивать массы, а при равенстве/отсутствии массы — светимости (tiebreak,
  `compMassiveThan` — единый источник правила) — но `luminosityBySpectral`
  живёт в `planet/physics.go`, а `planet` импортирует `galaxy` (`twin.go`,
  «Проверка гипотез»). Решение: таблица вынесена в `internal/astro` (единый
  источник), `planet/physics.go` использует её через обёртку
  `luminosityBySpectral` (fallback 1.0 закреплён тестами). Новый общий код
  звёздной физики — только в `internal/astro`.

- **`settlement.Suitable` вызывается в двух разных порядках аргументов.**
  Сигнатура — `Suitable(water, temp, ...)`, так вызывают `descriptions_tags.go`
  (inhabited) и `circumbinary.go` (35b §4.1); но `properties.go` и
  `generateOceanicPlanet` передают `(temp, waterPercent)` — при этом
  `suitable()` проверяет `water-slot < MinWater(10)` и `temp-slot ∈ [200,350]`,
  т.е. у стандартного пути «settleable» фактически всегда false (вода должна
  была бы быть 200–350%). Не-регрессия: менять существующие вызовы — вне
  скоупа; новый код (P-ветка) использует сигнатурный порядок, чтобы
  пригодные P-планеты (спека 35b §4.1) действительно могли быть пригодными.

- **Windows: `time.Now()` имеет гранулярность ~0.5 мс.** Два вызова подряд
  (в пределах одного тика системного таймера) возвращают **одинаковое**
  значение — в тестах сравнение `StartTime` двух последовательных запусков
  через `NotEqual` флейкает. Проверено 2026-09-16 (61a): шаг значений между
  итерациями ~512 мкс, иногда 0. Если тест обязан доказать, что время
  «продвинулось» (напр. полёт перезапущен с новым `start_time`), вставить
  `time.Sleep(5 * time.Millisecond)` между вызовами (см.
  `internal/handlers/travel_handlers_test.go`, `TestStartTravelRedirectInFlight`).

- **Каталог оборудования (спека 77a) — глобальное in-memory состояние
  `internal/ship`.** `RadarRadius`/`HasScanner` читают map, загружаемую
  `ship.LoadCatalog(db)` при старте (или `LoadDefaults()` при пустой БД).
  В юнит-тестах каталог пуст → `RadarRadius` молча возвращает минимум 200 px
  (не 800), тест «стартовый радар → 800» падает. Правило: тест, проверяющий
  радиус/сканер, обязан сначала вызвать `ship.LoadDefaults()` (или
  `LoadCatalog` с sqlmock) — как `newVisibilityHarness` в
  `internal/handlers/visibility_test.go`.

- **Новая колонка `users` в `userSelect`/`GetByIDWithPosition` — тройная правка
  тестов (sqlmock).** Список колонок `users` захардкожен в продакшене в ДВУХ
  местах (`userSelect` — 13 колонок; `GetByIDWithPosition` — своя строка
  `:212`), и в ~45 местах тестов (39 SELECT + 6 INSERT) лежат его КОПИИ: строка
  запроса-регекса, список колонок `sqlmock.NewRows([...])` и значения
  `AddRow(...)`. `AddRow` **паникует**, если число значений ≠ числу колонок
  (v1.5.2, `rows.go`). Добавляя колонку (пример — `race_id`, миграция `000074`),
  правь ВСЕ три слоя во всех файлах, иначе получишь либо «not expected»
  (регекс не совпал), либо панику. Второй подводный камень: `race_id` в тестах
  передают `nil`, а скан в `string` падает (`converting NULL to string is
  unsupported`) — скан `race_id` идёт через `sql.NullString` с проверкой
  `.Valid` (как `ship_model_id`). Порядок колонки в SELECT и в `Scan` обязан
  совпадать (в П1 `race_id` — ПОСЛЕ `pending_destination`).

- **`factions.homeworld_id` — это ПЛАНЕТА, не мир (`REFERENCES planets(id)`).**
  «Мир расы» для агента — мир родной планеты: `JOIN planets p ON
  p.id = f.homeworld_id`, берётся `p.world_id`. Прямой `SELECT race_id,
  homeworld_id FROM factions` в `npc_agents.current_world_id` даёт FK-нарушение
  (`current_world_id REFERENCES worlds(id)`) — массовая генерация падает целиком.
  Проверено 2026-09-23: все 28 фракций dev-БД ссылаются на планеты, на миры — 0
  (`internal/repository/npc_repository.go::RaceHomeworlds`; спека кораблей рас
  §5.1 предписывала прямой SELECT без джойна — исправлено).

- **Комбинаторный словарь форм арт-студии: полное произведение ~69M строк
  (F2) — юнит-тесту материализовать нельзя.** Спека 67a.1 §11.6 закладывала
  28×25×20×25 = 350k компонентов, но оси `forms.json` выросли (78a/88a/76a)
  до 130 shapes × 107 struct × 89 character × 105 parts — для F2 это
  ~69M комбинаций: `TestFormsFor` шёл 98 с и ел ~4 ГБ (под `-race` — таймаут).
  Вторая половина причины — `strings.NewReplacer` на КАЖДУЮ комбинацию
  (884 ns/ит, ~60% стоимости; разбор шаблона один раз + конкатенация —
  50 ns/ит, 17.7x, `parsePhraseTemplate` в `cmd/art-studio/generator/prompt.go`).
  Урок: юнит-тест проверяет ЛОГИКУ (шаблон + фильтр категорий), а не объём
  данных — ортогональные оси (struct/character/parts) в тесте урезаются до
  3 элементов, реальные shapes/template остаются (`prompt_test.go`,
  `TestFormsFor`).

- **`filterPool` арт-студии (98a) — чистый фильтр БЕЗ фолбека; фолбек — на
  вызывающей стороне.** Если «упростить» и вернуть исходный пул при пустом
  результате внутри `filterPool` (`cmd/art-studio/generator/prompt.go`), тихо
  сломаются две вещи: (1) структурное правило «раса-не-существо» (§5.3) —
  проверка `len(filterPool(anthro/beast, blocked)) == 0` перестанет срабатывать
  (пул «не пуст» из-за фолбека) и планктону/роям вернётся морф-ветка с лицом;
  (2) акценты палитры (§5.2 п.5) — «все отфильтрованы → акцент не добавляется»
  превратится в «вернулись тёплые акценты холодной расе». Фолбек применяется
точечно: character/parts → исходный пул, морф-пулы → глобальные формы морфа,
   акценты → НЕ фолбечат.

- **Windows: `os.Rename` поверх открытого файла падает «Access is denied» —
  атомарная запись `status.json` арт-студии застревает.** `WriteStatus`
  (`cmd/art-studio/generator/worker.go`) пишет tmp + rename; читатель
  (UI-поллинг `/status` каждые 3 с, тесты) держит `status.json` открытым
  микросекунды — rename в это окно падает, файл остаётся на старом значении:
  UI видит «running» вечно (финальная запись Running=false потеряна). Проверено
  2026-09-18 (98b-дополнение 2): воспроизводилось на `-race`-тестах джобов
  (n=3, 5 записей статуса за ~40 мс). Фикс: rename ретраится 5×5 мс (окно
  читателя короткое). Тест-хелпер `waitJobDone` дополнительно требует
  существования `status.json` — иначе при упавшей стартовой записи тест
  вернулся бы раньше, чем джоб дописал файлы пула (гонка с `t.TempDir()`
  cleanup).
  **Обратная сторона той же гонки (2026-09-20, флак TestHandleGenRefRace):**
  читатель тоже может попасть в окно rename — `os.ReadFile(status.json)`
  транзиентно падает, а `ReadStatus` проглатывает ошибку и возвращает нулевой
  `Status{}` с `Running=false`. Ждущий по `!Running` (тест-хелпер `waitJobDone`)
  возвращается раньше, чем джоб дописал `meta.json` — «кандидатов 1/2, want 3».
  Фикс: `waitJobDone` читает `status.json` напрямую и требует успешное чтение +
  валидный JSON + `Running=false` (не полагается на `ReadStatus`).
  **Третья грань (2026-09-20, 98c, последовательные джобы одного пула):**
  `waitJobDone` между двумя джобами одного пула возвращается по финальному
  статусу ПЕРВОГО джоба (`Running=false`, `Total>0`), пока второй джоб ещё не
  стартовал (его goroutine не написала стартовый статус) — чтение меты
  происходит ДО очистки пула вторым джобом («мета = 2 старые записи, want 1»,
  `TestGenShipsOverrideTags`). Фикс: ждать не статус, а целевое число записей
  меты (`waitShipMetaCount` в `ships_job_test.go`).
  **Четвёртая грань (2026-09-20, эскиз-ускорение кораблей):** `waitShipMetaCount`
  тоже не различает джобы, если оба дают ОДИНАКОВОЕ число записей (эскиз 1
  кандидат → мета 1, полный 1 кандидат → мета 1) — чтение возвращается по мете
  ПЕРВОГО джоба до старта второго, а после финальной меты джоб ещё пишет
  status.json (TempDir cleanup падает). Фикс: ждать финальный статус с
  различающим `Total` (`!Running && Total == N` второго джоба) —
  `TestGenShipsJobSizePropagates` в `ships_job_test.go`.

- **Арт-студия: чекпоинт SDXL читается джобами ТОЛЬКО под `r.mu`
  (`c.r.checkpoint()`), не напрямую из `c.r.cfg.Checkpoint`.** Селект «Модель»
  (2026-09-20) меняет `cfg.Checkpoint` в памяти через `Runner.SetCheckpoint`
  (под `r.mu`) — джобы (`race_job`/`ref_job`/`human_job`/`ships_job`) строят
  воркфлоу в воркер-горутинах, и прямое чтение `c.r.cfg.Checkpoint` дало бы
  data race с хендлером (Go убивает процесс, `-race` ловит). Правило: джобы
  читают актуальное значение на каждый воркфлоу через `c.r.checkpoint()`
  (паттерн `family()`), не кэшируют при старте — выбор модели применяется
  к следующим генерациям без рестарта.

- **`&m` в `for _, m := range` — общая переменная цикла при `go 1.21` в
  `go.mod` (Go 1.22 поменял семантику только при `go >= 1.22`).** Проверено
  2026-09-21 (ручная приёмка кораблей): `acceptShipFile`
  (`cmd/art-studio/handlers/ships_handlers.go`) брал `meta = &m`, и при
  нескольких кандидатах в пуле указатель всегда смотрел на ПОСЛЕДНЮЮ запись —
  приёмка `s01.png` писала чужую расу/seed/промпт (файл `race_deep_dwellers_01.png`
  для humans). Юнит-тесты с одной записью пула баг не ловили; e2e маскировал,
  дописывая проверяемый кандидат последним. Правило: брать адрес элемента
  среза по индексу (`for i := range all { if ... { meta = &all[i] } }`) либо
   копировать значение; тест на выбор записи — минимум ДВА кандидата
   (`TestShipsAcceptPicksOwnMeta`).

- **`sqlmock` не валит тест сам по себе на неожидаемый запрос — негативную
  проверку делай умышленно невыполненным ожиданием + `require.Error(ExpectationsWereMet())`
  (фича снимка, Э2/Э3, 2026-09-23).** Незарегистрированный запрос возвращает
  ошибку драйверу, но хендлер пишет снимок **best-effort** (ошибку логирует,
  полёт не роняет) — тест остаётся зелёным, хотя запрещённый запрос реально
  случился. Правило: чтобы доказать «запись НЕ происходит», зарегистрируй
  ожидание, которое обязано остаться невыполненным, и в финале потребуй
  `require.Error(t, mock.ExpectationsWereMet())` — образец
  `TestStartTravelDepartureNoFixateOffPlanet`
  (`internal/handlers/presence_snapshot_test.go`).

- **Тест, зовущий внешний интерпретатор/утилиту, обязан проверять ЗАВИСИМОСТИ,
  а не наличие команды (CI, коммит `9d0e501`, 2026-09-24).** На `ubuntu-latest`
  команда `python` есть (`python-is-python3`), а Pillow/numpy нет — тест
