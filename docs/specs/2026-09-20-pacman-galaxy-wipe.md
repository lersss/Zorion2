## 0. Резюме (одним абзацем)

В админке рядом с «🗑️ Удалить все миры» появляется кнопка «👾 Запустить Пакмана» — асинхронный
джоб `pacman` в StatusManager, который **порциями съедает миры целиком** (звёзды + планеты +
поселения + фракции + локации + NPC-агенты + знания игроков) по простой детерминированной
траектории — **полярной спирали от центра галактики** (сортировка по углу, затем по радиусу;
один sort на старте, O(N log N)). Цель — ~100 000 миров за ~60 секунд (~1700 миров/с, скорость
настраиваемая в теле запроса — первое приближение, потом уменьшим). Удаление — батчами по 200
миров в одной транзакции (каскады `worlds → planets → settlements → settlement_log / factions /
planet_resources` и `worlds → locations → production_units`, `worlds → assignments` работают;
явные DELETE только для FK NO ACTION: `npc_agents`, `player_planet_knowledge`, `UPDATE users
SET current_world_id = NULL`). Событие **видно всем игрокам на игровой карте в реальном времени**
(WebSocket Broadcast): огромный жёлтый пакман с анимированным ртом, миры исчезают по мере
поедания, счётчик «съедено N из M», баннер «галактику пожирают». Игроки (users) **остаются**:
у игрока, чей мир съеден, обнуляются `current_world_id`/`current_position` + личное уведомление;
полёт к съеденному миру прерывается с уведомлением (и дефенсив onArrival как страховка от гонки).
После полного вайпа галактика пуста — игроки видят пустую карту и ждут генерации админом.
Полностью опустевшие регионы исчезают вместе со своими мирами; частично съеденные —
пересчитываются.
Вайп — событие, не сущность: новой таблицы не требуется; состояние живёт в джобе + WS.

## 1. Концепция и термины

**Пакман** (термин, админ-инструмент) — асинхронный джоб `pacman` в StatusManager: «огромный
пожиратель», летает по карте по предвычисленной траектории и **съедает миры целиком** —
удаляет из БД всё, что ссылается на мир (как `clearUniverseTx`, но порциями по траектории, а не
TRUNCATE). Игроки (users) не удаляются.

**Поедание** — порционное удаление миров в порядке траектории: батч = 200 миров в одной
транзакции; между батчами джоб выдерживает темп `batch_size / worlds_per_second` (пауза, если
БД быстрее; без паузы, если БД медленнее — темп определяется фактической скоростью).

**Событие вселенной** (термин-кандидат, §10.3) — открытый класс видимых всем игрокам событий
галактического масштаба, транслируемых через WebSocket Broadcast с баннером и HUD-счётчиком.
Пакман — первый экземпляр; протокол WS (§5) и клиентский рендер (§6) — общий каркас класса.

**Съеденный мир** — мир, удалённый пакманом (вместе с планетами, поселениями, фракциями,
локациями, агентами, знаниями). У игрока, чей текущий мир съеден, `current_world_id` = NULL —
«без мира» (состояние 77a: карта без деталей, полёт к любой звезде разрешён).

### 2.2. Защита от двойного запуска и конфликты

- Двойной запуск: `statusManager.TryStart(JobPacman, …)` — атомарно, повторный → 409 (паттерн
  GenerateUniverse, `admin_universe.go:248`).
- **Пакман стартует, только если не крутится ни один джоб, пишущий в таблицы вселенной**:
  `generate_universe`, `generate_planets`, `regenerate_planets`, `generate_npc`, `hypothesis`
  (гвард у hypothesis есть — `TryStart` в `admin_hypothesis.go:57`), `generate_factions`,
  `generate_race_settlements`, `generate_settlements`. Любой running → 409 «Generation is running,
  cancel it first».
- **Обратное направление**: каждый из перечисленных хендлеров + `ClearUniverse` +
  **`GeneratePrototypePlanet`** (синхронный писатель в `planets`+`settlements`,
  `admin_universe.go:521-584`; вне StatusManager, как ClearUniverse — входит в схему гвардов,
  иначе админ вставит прото-планету в выживший мир посреди пакмана и она переживёт вайп)
  получает в свой существующий конфликт-гвард добавку
  `|| statusManager.IsRunning(generator.JobPacman)` → 409.
  Правки точечные, по одной строке: `admin_universe.go` (GenerateUniverse:241, GeneratePlanets:395,
  ClearUniverse:693, GeneratePrototypePlanet:521), `admin_regenerate_planets.go:51`,
  `admin_npc.go` (GenerateNPC/ClearAllAgents), `admin_hypothesis.go` (RunHypothesis),
  `admin_factions`/`admin_race_settlements`/`admin_settlements`.
- **Асимметрия с синхронным ClearUniverse** (он вне StatusManager): разделяемый мьютекс
  `var universeMutationMu sync.Mutex` в `admin_universe.go` (или рядом). Правила:
  - `ClearUniverse` берёт `TryLock` в начале (после своего гварда) и `Unlock` в конце (defer).
    Lock занят пакманом → 409 «Pacman is eating, stop it first».
  - `StartPacman` берёт `TryLock` до старта джоба и держит **до конца джоба** (освобождение в
    deferred-очистке done/cancel/fail). Lock занят ClearUniverse → 409.
  - Смысл: TRUNCATE (ClearUniverse) и порционный DELETE (пакман) не пересекаются; окно гонки
    «клик Clear в момент старта пакмана» закрыто мьютексом. Остаточная гонка «два джоба
    генерации стартуют одновременно» (не пакман) — существующее поведение проекта, не в скоупе.
- **Пакман и NPC-тик**: тик планировщика (`internal/npc/manager.go`) не блокируется — пакман не
  трогает менеджер напрямую; согласованность через снапшот карты (§4.3) и ретраи батча (§3.3).

### 2.3. Жизненный цикл джоба

```
StartPacman:
  1. TryLock universeMutationMu → иначе 409
  2. Проверка всех 8 джобов → иначе 409 (+Unlock)
  3. COUNT(*) worlds → total; total == 0 → 200 {done, eaten:0} (+Unlock), без джоба
  4. TryStart(JobPacman, total, cancel) → иначе 409 (+Unlock)
  5. go runPacman(ctx, cfg, total, cancel)  — deferred: Unlock + recomputeRegionCounts +
     npcManager.OnAgentsDeleted() + notifier.end(status)
  6. 202 {status:"started"}
```

`runPacman` (один цикл, одна горутина):
1. Загрузить миры из снапшота карты (`mapCache.Snapshot().Worlds()` — in-memory, без SQL):
   id, name, x, y, spectral. Построить траекторию (§4.1).
2. `notifier.start(total, wps)` → Broadcast `pacman_start`.
3. Цикл по батчам траектории (по 200 миров): проверить `ctx.Done()` (отмена) → выход;
   съесть батч (§3.2); `Progress(processed)`; `notifier.eaten(batch)`; пауза до конца
   батч-бюджета (`batch_size / worlds_per_second`).
4. Done: `SetReport` (сводка §3.4), `Done(JobPacman)`, `notifier.end("done")`.

Отмена (`CancelGeneration?job=pacman` → `statusManager.Cancel` → `CancelFunc`): цикл замечает
`ctx.Done()` между батчами → deferred-очистка (Unlock, пересчёт регионов, OnAgentsDeleted,
`notifier.end("canceled")`), `Cancel(JobPacman)` (статус «canceled», отчёт «Остановлено. Съедено
N из M»). Батч в полёте не прерывается — транзакция короткая (~30–80 мс).

### 3.2. Транзакция батча (200 миров, одна tx)

Порядок обязателен: зависимые NO ACTION удаляются ДО `worlds`.

```sql
BEGIN;
-- 1. Игроки в съеденных мирах: без мира и без внутрисистемной позиции.
UPDATE users SET current_world_id = NULL, current_position = NULL
WHERE current_world_id = ANY($1) RETURNING id;   -- PK users = id; вернувшиеся → персональные уведомления (§5.3)
-- 2. NPC-агенты в съеденных мирах / летящие в них — исчезают (решение создателя).
DELETE FROM npc_agents
WHERE current_world_id = ANY($1) OR from_world_id = ANY($1) OR target_world_id = ANY($1);
-- 3. Знания игроков о съеденных планетах стираются (решение создателя).
DELETE FROM player_planet_knowledge
WHERE planet_id IN (SELECT id FROM planets WHERE world_id = ANY($1));
-- 4. Внутрисистемные полёты в съеденных мирах — строки долой (in-memory самозалечивается, §7.2).
DELETE FROM player_intrasystem_flights WHERE world_id = ANY($1);
-- 5. Миры — каскад на всё остальное.
DELETE FROM worlds WHERE id = ANY($1);
COMMIT;

-- 6. ПОСЛЕ коммита, вне транзакции (in-memory + отдельное подключение; при rollback/ретрае
--    не выполняется — иначе полёты к выжившему миру отменились бы впустую, Н3 критика):
--    SELECT user_id FROM player_flights WHERE to_world_id = ANY($1)  (PK player_flights = user_id)
--    → travelManager.CancelFlight(userID) + pacman_notice «Полёт прерван — цель съедена» (§7.2).
```

`$1` — массив UUID батча (200). Счётчики удалённого — через `RowsAffected` (для отчёта §3.4).
Индексы: `worlds` PK, `planets.world_id` (000008), `locations.world_id`, `assignments.world_id`,
`settlements.planet_id`, `factions.homeworld_id`, `planet_resources.planet_id` — все есть.
`npc_agents`/`player_planet_knowledge` сканируются последовательно (индексов по world_id/planet_id
нет) — на 100к агентов и малых знаниях dev-масштаба приемлемо (~десятки мс на батч); при росте —
опциональный индекс `npc_agents(current_world_id)` (не в v1).

### 3.3. Откат и ретраи (поглощённость)

- Батч — **одна транзакция**: любой сбой → rollback, батч не применён, состояние БД не изменилось.
- **FK-violation (23503)** возможен от гонки с NPC-тиком (агент стартовал/прибыл в мир батча в
  окне между шагом 2 и шагом 5) или внутрисистемным прибытием. Обработка: **до 3 попыток** с
  бэкоффом 100 мс (на повторной попытке шаги 2–4 ловят новую строку). Исчерпаны → джоб
  `Fail(JobPacman, err)` с понятным отчётом: «Батч N не удалён (FK violation): {ошибка}.
  Съедено X из Y миров. Повторите запуск пакмана для остатка» + deferred-очистка (Unlock,
  пересчёт регионов, OnAgentsDeleted, `notifier.end("error")`).
- **Другие ошибки** (сеть, таймаут, lock): тот же ретрай; не-FK ошибка после 3 попыток → Fail.
- **Отмена полётов — только после успешного COMMIT** (шаг 6 §3.2): `CancelFlight` — in-memory +
  отдельное подключение, вне транзакции батча; при rollback/исчерпании ретраев шаг 6 не
  выполняется (иначе полёты к выжившему миру были бы отменены с уведомлением «цель съедена»
  впустую — Н3 критика).
- Снапшот карты пересобирается **после** коммита батча (§4.3) — при сбое батча снапшот не
  расходится с БД (миры остаются на карте, пока не съедены).

### 3.4. Регионы и отчёт

- **`regions` (решение создателя 2026-09-20: «регионы тоже должны куда-то деваться — съеденные»)**:
  регионы **не удаляются в батче** (удаление миров не каскадит на регионы); в конце джоба
  (done/cancel/fail) одной операцией: загрузить регионы (`loadRegionsWithProfiles`) + все миры
  (id, x, y), для каждого мира `regionprofile.NearestRegionIndex(x, y, regions)` → счёт по
  региону, затем `UPDATE regions SET world_count = $2, updated_at = now() WHERE id = $1` (по
  региону, ~200 апдейтов или один батч) и **`DELETE FROM regions WHERE world_count = 0`** —
  полностью опустевшие регионы (все миры съедены) **исчезают вместе со своими мирами**;
  частично съеденные остаются с актуальным счётчиком. Пересчёт, а не декремент — единый
  источник правила «мир принадлежит ближайшему региону» (чистый `NearestRegionIndex`; не
  совпадает с генераторным разбиением на краевых мирах — там кластерное разбиение +
  NearestRegionIndex для выбросов; счётчики пакмана самосогласованы); удаление — по
  пересчитанным нулевым счётчикам, в той же операции. Регион,
  бывший пустым и до вайпа (world_count = 0 после пересчёта), тоже удаляется — регион без
  миров не имеет смысла.
  Рестарт сервера посреди пакмана: пересчёт не выполняется (джоб in-memory) — регионы остаются
  неточными и не удалёнными до следующей генерации/очистки (принято для v1, §12).
- **Отчёт** (`SetReport`, показывается через `/admin/generate-status?job=pacman`):
  «Пакман съел миров: N, планет: P, поселений: S, агентов: A, записей знаний: K, игроков без
  мира: U, регионов удалено: R; время: T с (W миров/с)». Счётчики — сумма `RowsAffected` по
  батчам; R — `RowsAffected` от `DELETE FROM regions WHERE world_count = 0`.

## 4. Траектория

### 4.1. Траектория: жадный ближайший сосед через сетку (дефолт, решение создателя 2026-09-20)

- **Дефолт — `nearest`** (решение создателя 2026-09-20 «пусть он всё-таки как-то ближайшие
  кушает»): пакман ест **ближайшие** миры, а не «мечтает по всей галактике» (спираль прыгает
  между кольцами). Жадный ближайший сосед через пространственную сетку:
  - сетка `cell = 2·span/√N` (span = max разброса X/Y, мин 1.0; N = число миров), индекс
    `map[[2]int][]int` по ячейкам `floor(x/cell), floor(y/cell)`;
  - старт — мир, ближайший к центру (0,0) (евклид; tiebreak id);
  - от текущего мира — расширяющийся поиск по кольцам ячеек (Chebyshev r = 0,1,2,…):
    кандидаты — невизиченные миры в окрестности, выбирается минимальное евклидово расстояние
    (tiebreak id); остановка кольца: `(r−1)·cell > bestD` — дальше заведомо не ближе;
  - детерминизм: одинаковый вход → одинаковый порядок; суммарно ~O(N·k), k — кандидатов в
    окрестности (для плотных галактик мало); на 100к построение маршрута — секунды (в памяти,
    до цикла поедания).
- **Опции** (параметр `trajectory`):
  - `spiral` — полярная спираль от центра: сортировка по углу, затем по радиусу
    (`angle = atan2(y, x)`, `radius² = x² + y²`; ключ `(angle, radius²)`, tiebreak id). Один sort,
    O(N log N). Визуально — «космический пылесос»: кружит вокруг центра, расширяясь наружу.
  - `snake` — змейка строками: сортировка по x, затем по y (tiebreak id).
- **Честный «ближайший сосед» (O(N²) на каждый шаг) отклонён**: не влезает в минуту (оценка
  идеи). Сеточный NN (spatial hash) — **принят** (решение создателя 2026-09-20 «есть ближайшие»).

### 4.2. Движение пакмана

- Позиция пакмана — **центроид текущего батча**; между батчами линейная интерполяция от
  центроида предыдущего к центроиду текущего (по фактическому времени между батчами).
- События позиции — 10 Гц (§5.2): пакман «движется непрерывно», порция (батч) ≈ 2–3 кадра пути
  при дефолтах (8.5 батчей/с при 10 Гц позиции).
- Визуальная скорость адаптируется к фактической скорости БД (медленный батч → медленное
  движение): пакман всегда «у рта» — там, где сейчас ест. Отдельной кинематической скорости
  нет (v1, «не раздувать»).

### 4.3. Снапшот карты (окно «призраков»)

- После коммита каждого батча: **пересборка снапшота в памяти** — новый `Snapshot` из текущего
  `mapCache.Snapshot().Worlds()`, отфильтрованный по множеству съеденных id (`eatenSet`,
  in-memory map), `mapCache.Replace(...)`. O(N) на батч (100к × 200 батчей = 20М операций —
  тривиально), **без SQL**. Окно «призраков» = длительность одного батча (~120 мс).
- Устойчивость к параллельному `LoadAsync` (другой джоб): если LoadAsync вернул «призраков»
  (миры, съеденные после его чтения), следующий фильтр пакмана их уберёт — `eatenSet` растёт
  монотонно, фильтр всегда применяется к текущему снапшоту.
- NPC-сетка (`npc.Manager.refreshGrid`) перестраивается при смене снапшота (сравнение указателей)
  — агенты в съеденных мирах автоматически выпадают из позиций (`interpolatePosition` не находит
  мир в сетке → позиция не отдаётся). Призраки агентов — до следующего тика (≤5 с), принято для
  v1; в конце джоба `OnAgentsDeleted()` (очистка позиций + dirty-флаг → тик перезагрузит кэш).

## 5. WS-протокол

### 5.1. Канал

- Все события — через существующий `WebSocketHub` (`internal/handlers/websocket_hub.go`):
  `Broadcast` (всем, ролей нет — как 20a.1 §5) и `SendToUser` (персональные уведомления).
- Клиент подключается к `/ws?token=…` (существующий сокет карты, `npc_agents.js:107`); диспетчер
  `onmessage` дополняется ветками `pacman_*` (сейчас там только `npc_arrivals_batch`).
- **Дроссель обязателен** (паттерн `ws_notifier.go`: интервал + лимит деталей + total):
  нотификатор пакмана — отдельная горутина с тикером 100 мс, копит состояние
  {последняя позиция, последний батч, eaten_total, total} и шлёт с лимитами по типам:
  **позиция ≤10 Гц + поедание ≤1 событие/батч (≤8.5/с при дефолтах) — суммарно ≤~19 событий/с**
  (см. §5.2);
  джоб пишет в нотификатор неблокирующе (мутекс на состояние, Broadcast — в горутине
  нотификатора). **Джоб никогда не блокируется на WS** (медленный клиент не тормозит поедание).

### 5.2. События (JSON, все поля — только открытые данные миров)

| Событие | Триггер | Поля |
|---|---|---|
| `pacman_start` | старт джоба, 1 раз | `type`, `total`, `worlds_per_second`, `started_at` |
| `pacman_position` | тикер 100 мс (10 Гц) | `type`, `x`, `y`, `seq` |
| `pacman_eaten` | каждый батч (≤8.5/с при дефолтах) | `type`, `batch_index`, `eaten_total`, `total`, `x`, `y` (центроид батча), `worlds`: [≤200 записей `{id, name, x, y, spectral}` — **открытые данные** (77a: имя/координаты/спектр видны всем); детали систем (планеты, население, знание) НЕ передаются] |
| `pacman_end` | конец джоба, 1 раз | `type`, `status` (`done`/`canceled`/`error`), `eaten_total`, `total`, `duration_ms` |
| `pacman_notice` | персонально (`SendToUser`) | `type`, `message` («Ваш мир съеден пакманом», «Полёт прерван — цель съедена») |

Лимиты дросселя: позиция — 10 Гц (константа `pacmanPositionIntervalMs = 100`); поедание —
1 событие на батч, ≤ 200 миров в `worlds` (совпадает с `batch_size` дефолт; при большем батче —
обрезать до 200, счётчик `eaten_total` несёт остаток); start/end — по одному. Оценка нагрузки:
позиция ~60 Б × 10 Гц + поедание ~14 КБ × 8.5 Гц ≈ **~120 КБ/с на клиента** (~7 МБ за событие
минутой) — приемлемо для v1 (dev-масштаб); при десятках игроков — без изменений (Broadcast
пишет каждому клиенту независимо); «подкрутка» при необходимости — урезать `worlds` до id.

### 5.3. Персональные уведомления

- Игрок, чей мир съеден: `UPDATE users … RETURNING id` (шаг 1 §3.2; PK `users` = `id`) →
  `SendToUser` `pacman_notice` «Ваш мир съеден пакманом» (+ имя мира).
- Полёт к съеденному миру: `CancelFlight` (§7.2) → `SendToUser` «Полёт прерван — цель съедена».
- Персональные уведомления идут через тот же нотификатор (очередь userID+message, неблокирующе).

## 6. Фронт карты

### 6.1. Состояние клиента (`web/static/js/map/pacman.js`, новый файл)

```js
state.pacman = {
  active: false, x: 0, y: 0, prevX: 0, prevY: 0, targetX: 0, targetY: 0,
  movedAt: 0, eatenTotal: 0, total: 0, status: null
}
```
- `pacman_start` → active=true, баннер + HUD-счётчик «👾 N / M».
- `pacman_position` → prev/target/movedAt (интерполяция в render-цикле, как NPC-сэмплы).
- `pacman_eaten` → eatenTotal/total; удалить съеденные миры из локального списка разреженных
  звёзд (по id из `worlds`); **debounced перезапрос видимой области** (существующий debounce
  data.js, ~250 мс) — кластеры обновятся от свежего снапшота; вспышка в (x, y) (§6.3).
- `pacman_end` → active=false, финальный тост («Пакман съел N миров» / «Пакман остановлен» /
  «Ошибка пакмана»), HUD-счётчик скрывается.
- `pacman_notice` → тост; при «Ваш мир съеден» — перезагрузка `/me` (loadUserData) → состояние
  «без мира» (77a: карта без деталей, звёзды-огоньки).

### 6.2. Рендер (`map_render.js`, вызов в draw-цикле)

- Пакман — **классический жёлтый круг с ртом**: радиус на экране **34 px** (было 56 → 100 →
  создатель 2026-09-20: «сделаем меньше в 3 раза»), постоянный экранный размер — виден на
  любом зуме. **Без глаз и обводки** («классический пакман без глаз и без обводки»): только
  жёлтый круг + рот-сектор; заметность дают пульсирующий нимб (0.5+0.18·sin, радиус ×2.2)
  и след. Рот — сектор-клин **из центра** (`moveTo(px,py)` перед arc — иначе closePath
  соединяет дугу хордой, «отрезанный край»), **раскрытие от ~11° до ~69°** (0.10+0.50·|sin|,
  1.5 Гц — реальная «паку-паку»; база 11° — запас, чтобы клин не слипался в точку),
  ориентация — по направлению движения (prev → target).
- **Непрерывный rAF-цикл** при активном пакмане (`ensurePacmanAnimLoop`, паттерн
  ensureNpcAnimLoop): без него карта перерисовывается ~3 раз/с по событиям — рот «замирал»
  (создатель: «~3 фпс»). Пропускает кадр при `state.isFlying` (полёт игрока уже рисует).
- **Слежение «👾 Следить за Пакманом»** (кнопка в шапке карты `#pacmanFollowBtn`,
  показывается при активном событии): клик — камера центрируется на позиции пакмана каждый
  кадр (`offsetX/Y = canvas/2 − p·scale`), текст кнопки «⏹️ Не следить», отключается на end.
- **«Долетающие» звёзды** (2026-09-20, создатель: «не лопать, пока он до звезды не долетит»):
  съеденная звезда НЕ лопается сразу по `pacman_eaten` — добавляется в `pendingEaten`
  (видима), лопается в rAF, когда пакман добрался (dist < `PACMAN_SCREEN_PX/scale`) или по
  `maxDelay = 2×темп позиций + 500 мс` (быстрая скорость). Фильтр перезапроса области
  вычитает `eatenIds` КРОМЕ `pendingEatenIds` («долетающие» не «спойлерятся» и не
  возвращаются после лопания).
- Порядок отрисовки: поверх кластеров/звёзд, под баннером; не перехватывает клики (hit-тест
  не добавляется — пакман не интерактивен).

### 6.3. Эффект «поедания»

- На `pacman_eaten` в (x, y): расширяющееся кольцо + 8–12 частиц, разлетающихся и гаснущих за
  ~500 мс (простой массив частиц в render-цикле, без ассетов). Миры исчезают за счёт
  перезапроса видимой области (свежий снапшот).
- Баннер: постоянный overlay «⚠️ Галактику пожирает Пакман! N / M» + прогресс-бар; при
  `pacman_end` — финальный тост, баннер скрывается.
- Пустая галактика после вайпа: клиент видит 0 кластеров + `current_world_id = null` → лёгкий
  overlay «Галактика пуста — ждём генерации» (поверх существующего пустого состояния карты).

## 7. Игроки под поеданием

### 7.1. Игрок, чей мир съеден

- `current_world_id` = NULL + `current_position` = NULL (шаг 1 §3.2) + `pacman_notice` (§5.3).
- Интерфейс: клиент после перезагрузки `/me` показывает состояние «без мира» (существующее
  77a-поведение: карта без деталей, звёзды-огоньки, полёт к любой звезде разрешён) + тост
  «Ваш мир съеден пакманом».
- Дальше игрок может лететь к любой выжившей звезде: `StartTravel` уже обрабатывает
  `fromWorldID == ""` — берёт первый доступный мир и обновляет `current_world_id`
  (`travel_handlers.go:147-156`). Пустая галактика → «No worlds available» (500) — клиент
  показывает дружелюбное сообщение вместо паники (§6.3 overlay).
- **Автопереселение к ближайшему живому миру отклонено для v1** (доп. логика «ближайший живой»
  на каждого игрока; игрок без мира — допустимое состояние). Вариант для создателя — §12.

### 7.2. Полёты

- **Межзвёздный полёт к съеденному миру** (шаг 6 §3.2): **после коммита батча** —
  `SELECT user_id FROM player_flights WHERE to_world_id = ANY($1)` → для каждого
  `travelManager.CancelFlight(userID)` (in-memory отмена, строку удаляет runFlight; onArrival не
  вызывается — паттерн 97a) + `pacman_notice` «Полёт прерван — цель съедена». Игрок остаётся в
  своём текущем мире (или без мира, если он тоже съеден).
- **Дефенсив onArrival (страховка от гонки)**: полёт к миру, съеденному между запросом пакмана и
  прибытием, — `onArrival` в `travel_handlers.go:228` дополняется проверкой существования цели
  (`worldRepo.GetByID(worldID)` → nil) → обнулить `current_world_id`/`current_position` и
  залогировать, вместо FK-violation. Три строки, хирургически.
- **Внутрисистемные полёты** (99.2.27): строки `player_intrasystem_flights` в съеденных мирах
  удаляются (шаг 4 §3.2). In-memory полёт самозалечивается: прибытие в съеденную систему →
  `arrivalTargetValid` даёт фолбэк «орбита звезды» → FK-violation на `current_world_id` ловится и
  логируется; строка удаляется runIntraFlight; следующее действие игрока (старт межзвёздного)
  чистит позицию (`CancelAtomic`). Принято для v1.
- **Полёт игрока в момент поедания его мира**: игрок в полёте из съеденного мира — полёт
  продолжается (from — лишь стартовая точка); прибытие в живую цель — нормально. Видимость в
  полёте: `PlayerPosition` интерполирует по `flight.StartX/StartY` — не зависит от съеденного
  from-мира (77a §4.2).

### 7.3. NPC-агенты

- Агенты в съеденных мирах / летящие в них — удаляются (шаг 2 §3.2) — **исчезают с карты**
  (решение создателя). Позиции: сетка перестраивается по свежему снапшоту (§4.3) — агенты в
  съеденных мирах не интерполируются; кэш агентов инвалидируется `OnAgentsDeleted()` в конце
  джоба (призраки ≤5 с — принято для v1).
- Гонка с NPC-тиком (старт полёта в мир батча в окне транзакции) — FK-violation на шаге 6 →
  ретрай батча (§3.3); исчерпание ретраев → Fail с отчётом. Повреждённых данных не остаётся.

## 8. Числа и конфиг

| Параметр | Дефолт | Диапазон | Источник |
|---|---|---|---|
| `worlds_per_second` — скорость поедания | 1700 | **>0..10000, float64** (решение создателя 2026-09-20: «снизу не ограничивать — нормальный ивент»; 0.01 — «кинорежим») | тело запроса |
| `batch_size` — размер батча | 200 | 100–500 | тело запроса |
| `trajectory` — режим траектории | `nearest` (жадный ближайший сосед через сетку, решение создателя 2026-09-20 «есть ближайшие») | `nearest` \| `spiral` \| `snake` | тело запроса |
| `pacmanPositionIntervalMs` — частота позиции | 100 мс (10 Гц) | константа | код |
| `maxWorldsPerEatenEvent` — лимит деталей WS | 200 | константа | код |
| `batchRetries` / `batchBackoff` | 3 / 100 мс | константа | код |
| `PACMAN_SCREEN_PX` — экранный размер пакмана | **34 px** (было 56→100; создатель: «меньше в 3 раза», классика без глаз/обводки, 2026-09-20) | константа | клиент |

Производные: длительность = `total / worlds_per_second` (100к / 1700 ≈ 59 с); батч-бюджет =
`batch_eff / worlds_per_second` — **адаптивный батч** (2026-09-20): при `worlds_per_second <
batch_size` эффективный батч сжимается до `int(wps)` (минимум 1), иначе при 0.01 мир/с и
батче 200 пакман стоял бы 20 000 с, а потом «съедал» 200 миров рывком; для «кинорежима»
нужен батч ~1 мир. В `generation_config` (БД) параметры **не хранятся** (v1: тело запроса +
дефолты в коде). Температуры в фиче нет — правило °C не затрагивается.

## 9. Критерии приёмки / DoD (для @developer)

1. **Джоб и ручки**: `POST /admin/pacman/start` → 202; повторный запуск → 409; при идущем любом
   из 8 джобов генерации → 409; `ClearUniverse` при идущем пакмане → 409; старт пакмана при
   идущем ClearUniverse → 409 (мьютекс); статус/прогресс/отмена через `/admin/generate-status` и
   `/admin/generate-cancel?job=pacman`; отмена останавливает джоб между батчами с отчётом
   «Съедено N из M»; миров нет → 200 {done, eaten:0}.
2. **Поедание**: после джоба в БД нет строк `npc_agents`/`player_planet_knowledge`, ссылающихся
   на съеденные миры/планеты; `users.current_world_id`/`current_position` = NULL у затронутых;
   каскады отработали (settlements/settlement_log/factions/planet_resources/locations/
   production_units/assignments по съеденным — удалены); полностью съеденные регионы удалены,
   частично съеденные пересчитаны (`world_count` актуален); `events` не тронут; users не удалены.
3. **Видимость всем**: 2+ браузера (разные игроки) видят пакмана (рендер), миры исчезают в
   реальном времени (WS + перезапрос области), счётчик растёт, баннер/тосты приходят; детали
   систем (планеты/население/знание) в WS-событиях отсутствуют.
4. **Игроки под поеданием**: игрок, чей мир съеден, получает уведомление и состояние «без мира»;
   может лететь к выжившей звезде; полёт к съеденному миру прерывается с уведомлением;
   дефенсив onArrival не падает (битая цель → NULL, не FK-error); пустая галактика → дружелюбное
   сообщение, не 500-паника.
5. **Агенты**: агенты в съеденных мирах исчезают с карты; кэш позиций инвалидирован
   (OnAgentsDeleted в конце); призраки ≤ 5 с.
6. **Производительность**: 100к миров ≤ 90 с на dev-БД (цель ~60 с) — замер через отчёт джоба
   (длительность + миров/с); @tester на пресете 100к (47a).
7. **WS-нагрузка**: при 2+ клиентах сервер жив, дроссель держит лимиты (позиция ≤10 Гц, поедание
   ≤200 миров/событие); джоб не блокируется на WS (медленный клиент не тормозит поедание).
8. **TDD**: юнит-тесты — сортировка траектории (детерминизм, spiral/snake), SQL батча
   (sqlmock: порядок операций, RowsAffected; **мок не валидирует колонки RETURNING — реальная
   проверка SQL против БД обязательна**, иначе `RETURNING id` вместо `RETURNING user_id` не
   поймать, Н2 критика), ретраи батча (FK → 3 попытки →

## 11. История итераций (коротко)

- **Траектория**: перебраны честный NN (O(N²) — отклонён, не влезает в минуту), сеточный NN
  (кандидат подкрутки), змейка по координатам (альтернатива `snake`), полярная спираль
  (принято: один sort, детерминизм, «космический пылесос»).
- **WS-пейлоад поедания**: полный список миров батча (принято, ≤200, открытые данные) против
  «только счётчик + перезапрос области» (отклонено: теряется «мир X съеден» и мгновенное
  удаление разреженных звёзд); урезание до id — запасная подкрутка.
- **Игрок без мира**: NULL + уведомление (принято) против автопереселения к ближайшему живому
  (отклонено для v1 — доп. логика, состояние «без мира» допустимо).
- **Полёт к съеденному миру**: отмена + уведомление (принято) против «долетел в пустоту»
  (отклонено: глюк позиции — `PlayerPosition` откатывает к стартовой точке) — плюс дефенсив
  onArrival как страховка от гонки.
- **Снапшот карты**: пересборка в памяти по `eatenSet` на каждый батч (принято, без SQL) против
  пересборки из БД раз в N батчей (отклонено: SQL-сканы на 100к × 200 дорого) и против
  точечного вычёркивания из immutable Snapshot (невозможно — снапшот неизменяем, замена целиком).
- **Регионы (уточнение создателя 2026-09-20)**: «регионы тоже должны куда-то деваться —
  съеденные» — было «не удаляются, пересчёт счётчиков», стало: полностью опустевшие регионы
  удаляются (`DELETE FROM regions WHERE world_count = 0` после пересчёта), частично съеденные
  пересчитываются.
