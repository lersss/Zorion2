## 0. Резюме (одним абзацем)

Вводится сущность **«строение»** — постройка на планете с владельцем. Строения
делятся на **производителей** (есть вход и выход) и **другие** (ретранслятор и
пр.; отдельная постройка «склад» НЕ вводится — внутренние буферы/хранилища у
производителей, решение 3b.6.5). Производители — по классу выхода: **товары**
(объём+вес; поселение, фабрика — бывший «завод», автофабрика — «население» =
роботы, корзина: энергия + механика + электроника, добывающая платформа), **предметы**
(слот; три лаборатории: исследовательская → чертёж, корабельных модулей → модуль
корабля, инструментов игрока → кирка), **энергия** (отдельная сущность;
энергостанция).
Термин «завод» убирается из дизайна (омоним «заводские настройки» — factory
defaults — не трогается). У всех строений — владелец (игрок/фракция/агент) и
собственное население со своей корзиной потребностей (поселение — не
единственный источник труда). Разблокировка производства — **предмет-рецепт в
слоте строения + снабжение** (люди, расходники по рецепту, энергия); тир
остаётся внутренней величиной (тир товара в студии, расчётный тир поселения),
но **не является гейтом**. География производства держится **снабжением и
логистикой**: производство возможно где угодно при снабжении, но снабжение
дорогое и комплексное. Студия товаров получает ветку «Производители» (типы
производителей, цепочки, фильтры, расовые типы фабрик) и ветку «Предметы»
(слот, не объём/вес). Скоуп — каталог + студия + GDD (этап 1) и игра (этап 2).

## 1. Словарь новых терминов

Термины определяются здесь и вносятся в `docs/GLOSSARY.md` при терминологической
правке (этап 1). «Завод» как термин постройки **удаляется**; омоним «заводские
настройки» (factory defaults: R-кривые, биомы, пресеты) — не трогается.

| Термин | Определение |
|---|---|
| **Строение** | Постройка на планете; имеет владельца (игрок/фракция/агент); потребляет. Общий класс: производители + другие. |
| **Производитель** | Строение с входом и выходом. Класс выхода: товары (объём+вес), предметы (слот), энергия (отдельная сущность). |
| **Фабрика** | Производитель товаров (бывший «завод»). Один тип фабрики = товары одной категории. |
| **Автофабрика** | Фабрика, «население» которой — роботы: корзина НЕ из еды (энергия + механика + электроника). Входит в «Производители товаров» (решение 3b.6.1); бывший «автоматический завод» (`19_robots.md`). |
| **Добывающая платформа** | Производитель сырья: берёт ресурсы поверхности/недр, ест энергию и расходники, без переработки отдаёт на рынок/хранилище. Сырьё — позиция каталога `kind=resource`. |
| **Лаборатория** | Производитель предметов. Виды: исследовательская (чертёж), корабельных модулей (модуль корабля), инструментов игрока (кирка). |
| **Энергостанция** | Производитель энергии. Выход — энергия, отдельная сущность (не позиция каталога). |
| **Предмет** | Выход производителя предметов; занимает слот, не объём/вес. Виды: сертификат анализа, чертёж, модуль корабля, инструмент. Модуль корабля — **объект по чертежу** (решение 3b.6.3): лаборатория производит объект с указанными свойствами (куда ставится, на что влияет); предмет-модуль ведёт к записи `equipment` (77a/91a) через чертёж. Справочник `items` — **типы** предметов («что бывает»); экземпляры живут в инвентаре. |
| **Экземпляр предмета** | Отдельный предмет в штуках (сертификат, кирка, модуль). Хранится в **инвентаре** строения/игрока; ссылается на тип из справочника `items`. Не строка справочника. |
| **Инвентарь** | Место хранения экземпляров предметов: у строений — `buildings.data.inventory` (или отдельная таблица на этапе 2); у игрока — существующее `users.equipment` (модули) + будущий общий инвентарь игрока (вне скоупа). |
| **Расходники** | Общий термин снабжения: товары/ресурсы, расходуемые строением на производство (электроника, механика, сырьё, топливо). Для автофабрики конкретика — «механика + электроника» (как `19_robots.md` §19.1.1). |
| **Предмет-рецепт** | Предмет с ролью разблокировки: вложенный в слот строения, открывает производство категории на типе производителя. Разведён с «рецепт товара». |
| **Рецепт товара** | Существующий термин: компоненты × количество (`goods_slots`). |
| **Слот** | Многозначный термин (вносится в GLOSSARY §1 «Многозначные слова»): **слот строения** — позиция для предмета-рецепта (`buildings.slots`); **слот рецепта** — позиция компонента в рецепте товара (`goods_slots.pos`); **слот предмета** — занимаемое предметом место (не объём/вес). |
| **Снабжение** | Обеспечение строения: люди (или роботы для автофабрики), расходники по рецепту, энергия. |
| **Корзина строения** | Потребности населения строения (аналог корзины тира поселения, `13_tiers.md` §13.10.1). Для автофабрики — корзина роботов: энергия + детали + комплектующие, НЕ еда. |
| **Владелец строения** | Игрок/фракция/агент, владеющий строением. |

## 2. Модель: классификация строений

```
Строение (владелец: игрок/фракция/агент)
├── Производитель (вход и выход)
│   ├── Товаров (выход: объём+вес → каталог kind=good/resource)
│   │   ├── Поселение              — работники = жители, вход — ресурсы поверхности, выход — остаток
│   │   ├── Фабрика                — бывший «завод», нанятые работники, высокая эффективность
│   │   ├── Автофабрика            — «население» = роботы, корзина: энергия + детали + комплектующие (НЕ еда);
│   │   │                            работает где угодно (решение 3b.6.1)
│   │   └── Добывающая платформа   — сырьё поверхности/недр, ест энергию и расходники,
│   │                                без переработки → рынок/хранилище
│   ├── Предметов (выход: слот → предмет)
│   │   ├── Лаборатория исследовательская   → чертёж
│   │   ├── Лаборатория корабельных модулей → модуль корабля (объект по чертежу, 3b.6.3)
│   │   └── Лаборатория инструментов игрока → кирка
│   └── Энергии (выход: энергия — отдельная сущность, не позиция каталога)
│       └── Энергостанция
└── Другие (ничего не производят)
    ├── Ретранслятор
    └── … (склад как отдельная постройка НЕ вводится — внутренние буферы/хранилища
           входа/выхода у производителей, решение 3b.6.5)
```

Природа сущностей (архитектурный фильтр, PITFALLS «событие vs лог»):

1. **Строение** — лог/состояние (результат, в который перешло состояние), не
   событие. Экземпляров много (потенциально сотни тысяч) — таблица, не поля.
2. **Владелец** — у всех строений; владельцев три класса (игрок/фракция/агент) —
   закладываем `owner_type`+`owner_id` сразу, не «владелец-игрок».
3. **Тип производителя** — справочник каталога, открытый класс (kind:
   goods/items/energy; конкретные типы — данные студии, не enum в коде).
4. **Предмет** — справочник каталога: **типы** предметов («что бывает»), вид выхода
   производителей предметов. Схема переживает второй вид предмета (сертификат +
   чертёж + модуль + кирка) — это сигнал, что таблица `items` верна.
   **Экземпляры** предметов (сертификаты, кирки, модули в штуках) — не строки
   справочника, а записи **инвентаря** строения/игрока (§1 «Экземпляр предмета»,
   «Инвентарь»).
5. **Предмет-рецепт** — роль предмета (поле `unlocks`), не отдельная сущность:
   предмет с ролью разблокировки — это тот же предмет, что и выход лаборатории.
   Отдельная таблица «предмет-рецептов» не нужна — плодила бы сущность ради
   атрибута.
6. **Производство** (выработка строения) — вычисляемый результат, ленивый
   пересчёт по событию и при чтении (инвариант 2, паттерн энергии `11_production.md`
   §11.1.2): `выработка = скорость × (сейчас − last)`. Построчных записей
   «производство за тик» нет.

**Слоты строения и предмет-рецепт.** Слот строения — позиция, в которую
вкладывается предмет-рецепт (`items.unlocks`). Наличие предмета-рецепта в слоте
+ выполненное снабжение = строение производит. Замена предмета-рецепта в слоте —
операция (время/ресурсы), это и есть «модернизация» в новом виде (смена
категории фабрики = замена чертежа в слоте).

## 4. Студия товаров

Студия (`/studio`) получает две новые ветки рядом с существующими товарами.

### 4.1. Ветка «Производители» → пять разделов построек (дельта 2026-09-25)

**Дельта 2026-09-25 (спека `2026-09-25-студия-разделы-построек-по-видам.md`):** ветка
«Производители» в студии **заменена пятью разделами по видам построек** — **Колонии ·
Фабрики и автофабрики · Лаборатории · Добывающие платформы · Энергостанции** — плюс
служебный раздел **«Прочее»** (корни без раздела/с неизвестным значением; полноправный
активный раздел интерфейса, но **не значение БД** — `other` в колонку не пишется).
Привязка — **поле каталога `producer_types.section` (§3.1), а не имя типа-корня**:
переименование корня не ломает привязку (решение создателя «устойчивость сразу»,
2026-09-25). Носитель раздела — только тип-корень (`parent_id IS NULL`), подтипы
наследуют раздел своего корня; раздел меняется у любого типа-корня в карточке и
обязателен в форме «+ тип». Уровни «Строения» и фиксированные классы в UI сняты (спека
`2026-09-21-студия-дерево-построек-канвас.md`); ниже по тексту слово «ветка» читать как
«раздел построек».

- Список типов производителей (`producer_types`): карточка типа (имя, kind,
  категория, семейство рас, вход/выход, параметры, **раздел `section`**).
- **kind=goods:** тип привязан к категории (`category_id`) — «один тип фабрики —
  товары одной категории». Цепочки (граф `goods_slots`) привязываются к
  производителям: категория производителя — это категория его товаров; рецепты
  товаров категории — цепочка типа. **Автофабрика** — вид типа kind=goods с
  корзиной роботов: `input` = энергия + детали + комплектующие (НЕ еда), `params` =
  стоимость робота (решение 3b.6.1).
- **kind=items:** тип привязан к предметам (`producer_items`) — лаборатория
  производит перечень предметов; рецепт предмета — `requirements` (расходники из
  каталога товаров, энергия, люди).
- **kind=energy:** тип привязан к параметрам (`output.energy`) — энергостанция;
  продукт — энергия (отдельная сущность, в каталоге товаров/предметов не
  позиция).
- **Расовые типы фабрик:** поле `race_family` — у семейств рас свои типы
  фабрик и свои цепочки (кремниевым семействам не нужны фабрики пирожков).
  Фильтр по семейству в студии.

### 4.2. Ветка «Предметы»

- Справочник `items` — **единый справочник «что бывает»** (решение 3b.6.3):
  карточка предмета (имя, slot_type, unlocks, params).
- Отдельные ветки/фильтры от товаров: предметы занимают **слот**, не объём/вес.
- Предмет-рецепт: поле `unlocks` — выбор типа производителя и категории, которую
  предмет разблокирует.
- **Модуль корабля — объект по чертежу** (решение 3b.6.3): лаборатория
  корабельных модулей производит объект с указанными свойствами (куда ставится,
  на что влияет); предмет-модуль ведёт к существующим записям `equipment`
  (77a/91a) через чертёж — дублирования справочника нет, `equipment` остаётся
  единственным источником типов снаряжения.

### 4.3. Фильтры

- **Раздел вида постройки — первая ось фильтра** (дельта 2026-09-25): дерево и
  справочник построек показывают только корни активного раздела (`section`, плюс
  служебный «Прочее») и их потомков; переключение раздела не сбрасывает остальные
  фильтры.
- **«Что делает этот производитель»** — по типу производителя: категория товаров
  (kind=goods), предметы (kind=items), энергия (kind=energy).
- **«Какие производители потребляют товар X»** — обратный: типы производителей,
  у которых X входит в `input.расходники` или в рецепты предметов
  (`producer_items.requirements`), или в рецепты товаров категории.
- Ограничение видимости в каталоге: товары, не привязанные ни к одному
  производителю, помечаются (не контент производства).

## 5. Игра: население и владельцы строений

### 5.1. Владельцы

У **всех** строений есть владелец — игрок/фракция/агент (`owner_type`/`owner_id`).
Отменяет `13_settlements.md` §13.2 «поселение — чистый NPC без владельца».
Что владелец может: управлять производством (слоты, приоритеты, ставка),
получать доход. (Продажа/передача строения — механики перехода, вне скоупа.)

> В первой итерации релиза 2 (спека `2026-09-21-фабрики-релиз-2-столицы-фракций.md`)
> колонки владельца реализуются **только у `buildings`**; поселения `owner_type`/
> `owner_id` не получают — решение создателя 2026-09-21 (идея
> `2026-09-21_фабрики-релиз-2-строения-владельцы-столица-фракции.md` §2 п.5).
> Решение 3b.6.6 (вариант «а») остаётся дизайн-целью следующих итераций.

**Владелец сгенерированного контента** (уточнение решения 3b.6.9, создатель
2026-09-21): сгенерированные строения принадлежат **реальной сгенерированной
фракции** — владелец столицы = фракция, на чьей родной планете (`factions.homeworld_id`)
стоит строение. Единая фракция-заглушка «на всё» не вводится: она дала бы одну
столицу на галактику, мир не наполняется (идея `2026-09-21_фабрики-релиз-2-…`
§3). Владельцы поселений — отложены (см. оговорку выше).

⚠️ **Механики перехода/отжима — ВНЕ скоупа** (решение 3b.6.7): выкуп,
деградация, брошенное→переход, передача/продажа, период опеки, силовой захват —
НЕ проектируются в этой фиче. Фиксируется только НАЛИЧИЕ владельца у построек;
сами механики перехода — отдельная будущая фича. **Грифинг-риск §13.2.3**
(«уморить голодом» чужое поселение) — известный и отложенный: зафиксирован в
GDD-правке §8.3 как известный риск, решение — в будущей фиче механик перехода.

### 5.2. Население строений

- У каждого производящего строения **своё население** (`buildings.population`,
  у поселения — существующая `settlements.population`; у автофабрики — число
  роботов).
- **Поселение — не единственный источник труда.** Источники населения строений —
  канонические слои `13_settlements.md` §13.3.3 (рождаемость, переток, перевозка,
  сквоттинг), применённые к строениям:
  - **Переток** — из поселений рядом и между строениями (медленно, бесплатно);
  - **Перевозка/завоз** — с других планет (быстро, дорого);
  - **Рождаемость** — только там, где уже комфортно; свойство поселений (строения
    не рожают);
  - **Сквоттинг** — появление населения там, где работает подножный корм;
    свойство поселений (у строений подножного корма нет).
  Других слоёв не вводим (замечание критика: не выдумывать новые слои).
- **Корзина строения** — потребности населения строения (аналог корзины тира
  `13_tiers.md` §13.10.1): еда → корзина → излишек. Занятые покупают еду сами на
  местной бирже (§13.4) — правило сохраняется для любых строений с населением.
  **Корзина автофабрики — роботы:** энергия + детали + комплектующие, НЕ еда
  (решение 3b.6.1).
- Отменяет «завод нанимает из конкретного поселения» (`11_production.md` §11.1.1
  «Привязка к поселению», `13_settlements.md` §13.2.2): строение само носит
  население.

### 5.3. Тир

- Тир остаётся **внутренней величиной** (решение создателя 2026-09-20): тир
  товара в студии (`tier_override`, 99a.3) + расчётный тир поселения
  (`13_tiers.md` §13.9).
- **Тир НЕ является гейтом разблокировки производства.** Потолок новых товаров =
  наличие предмета-рецепта в слоте + выполнение снабжения.
- У строений тир не вводится как отдельная колонка: потребности населения
  строения задаются корзиной строения (данные), не гейтом.

## 6. Игра: разблокировка и снабжение

### 6.1. Разблокировка производства

Чтобы строение начало производить новые товары:

1. **Привезти предмет-рецепт** (предмет с `unlocks`) и положить его в **слот
   строения**;
2. **Удовлетворить снабжение**:
   - **люди** — население строения ≥ требование типа (для автофабрики — роботы,
     корзина: энергия + детали + комплектующие, НЕ еда);
   - **расходники по рецепту** — товары/ресурсы по рецепту (для товаров —
     `goods_slots` категории; для предметов — `producer_items.requirements`);
   - **энергия** — от энергостанций планеты (рынок энергии `11_production.md`
     §11.1.2).

Снабжение не выполнено — строение простаивает (бинарно, как смена §13.3.1;
градация — будущее). Замена предмета-рецепта в слоте = модернизация (время и
ресурсы) — сохраняет «перепрофилирование должно быть возможным, хоть и дорогим»
(§11.1.1).

### 6.2. Отменяемые правила

- «Сложность рецепта, запираемая тиром поселения» (`11_production.md` §11.1.1,
  `13_tiers.md` §13.9.1): сложность остаётся полем рецепта (данные), но не
  запирает производство.
- «Автозавод сложности N ест детали сложности ≥ N» (`13_tiers.md` §13.9.6):
  потоковый гейт переработан — автофабрика разблокируется предмет-рецептом и
  снабжением, как человеческая фабрика; география держится снабжением/логистикой
  (§7), а не тиром. Корзина автофабрики — роботы: энергия + детали + комплектующие,
  НЕ еда (решение 3b.6.1).
- «Завод нанимает из конкретного поселения» (§13.2.2) — отменено (§5.2).

## 7. Игра: география производства через снабжение и логистику

### 7.1. Принцип

Производство возможно **где угодно** при снабжении (решение создателя 2026-09-20:
«снабжение тоже сложное, плюс доп. затраты на логистику»). Карта производства
сохраняется естественно: снабжение дорогое и комплексное. Близко к принципу
«география живёт в снабжении» (`13_tiers.md` §13.9.6).

### 7.2. Структура логистических затрат (числа — @balancetester)

```
стоимость_снабжения(строение) = Σ по позициям снабжения (цена_позиции + транспорт_позиции)
транспорт_позиции = базовая_ставка × f(расстояние_до_источника)
f(расстояние) — балансная ручка (линейная/логарифмическая/ступенчатая)
```

Позиции снабжения: люди (завоз — «Перевозка» §13.3.3, быстро и дорого; переток —
бесплатно, медленно), расходники (рыночная цена + доставка), энергия (местный
рынок планеты). Для автофабрики позиция «люди» заменяется на «роботы»
(производятся людьми — инвариант 11, `19_robots.md` §19.5; корзина роботов —
энергия + детали + комплектующие). Комплексность: чем больше позиций снабжения у
типа, тем дороже и хрупче производство (перебой любой позиции останавливает
строение) — это и есть замена тир-гейта: сложное производство на фронтире
возможно, но дорого («цена, а не запрет», §13.9.6). Автофабрика работает где
угодно (§19.2), но её снабжение (роботы, детали, энергия) — то же комплексное
снабжение: география автофабрик держится логистикой, а не тиром.

### 7.3. Управление

Постоянные контракты на поставку + автоматический забор со склада + уведомления
о нехватке («управление по исключениям», `11_production.md` §11.1.3). Сто
строений с ручным снабжением — работа диспетчера, а не игра.

### 8.1. `11_production.md` §11.1.1 «Заводы» → «Фабрики»

## 11. Развилки для создателя

Все развилки закрыты решениями создателя (3b.6): §11.1 — вне скоупа, §11.2–11.5 —
закрыты, §11.6 — снести. Открытых развилок на гейт спеки нет.

### 11.1. Механики перехода/отжима — **ВНЕ СКОУПА (решение 3b.6.7)**

Механики перехода строений между владельцами (выкуп, деградация,
брошенное→переход, передача/продажа, период опеки, силовой захват) **НЕ
проектируются** в этой фиче и в бэклог не вносятся детально — отдельная будущая
фича. В спеке фиксируется только **наличие владельца** у построек (§5.1).
Грифинг-риск §13.2.3 — известный и отложенный (зафиксирован в §8.3, решение — в
будущей фиче механик перехода).

### 11.2. Модули корабля vs справочник `equipment` — **ЗАКРЫТО (решение 3b.6.3)**

Модель «объект по чертежу»: лаборатория корабельных модулей производит объект
по чертежу с указанными свойствами (куда ставится, на что влияет); единый
справочник «что бывает» (`items`) разрабатывается через студию; предмет-модуль
ведёт к существующим записям `equipment` (77a/91a) через чертёж. Дублирования
справочника нет. В спеке: §1 (Предмет), §3.1 (`items.params`), §4.2, §8.4.

### 11.3. Вес/объём товаров — **ЗАКРЫТО (решение 3b.6.4, вариант «а»)**

Поля `volume`/`weight` заводятся в `goods` СЕЙЧАС, **обязательные для
approved-товаров** (валидация: approved без веса/объёма не проходит — NULL-каталог
запрещён); draft может быть без значений. Механика грузов/трюма — потом (не
сейчас). В спеке: §3.1 (поля `goods`), §4.3 (фильтры/видимость), §12.1 (связь
на `goods`).

### 11.4. Склад — **ЗАКРЫТО (решение 3b.6.5)**

Отдельная постройка «склад» НЕ вводится. У производителей — внутренние
буферы/хранилища входа/выхода (`buildings.data`). «Другие»: ретранслятор и пр.
В спеке: §2 (схема), §3.2 (`buildings.data`).

**Вопрос:** Снабжение строений — дорогое и комплексное (§7). Не нужна ли
постройка, которая консолидирует грузопоток и снижает логистические затраты

**Ответ (кандидат на решение создателя):** логистический узел — будущая «Другая»
постройка (отдельная от склада: склад не вводится, 3b.6.5; узел — не хранилище,
а точка консолидации грузопотока), принимающая грузы нескольких строений и
снижающая транспортную составляющую снабжения для них (консолидация: одна
доставка на узел вместо N доставок на строения). Даёт игровое решение «где
поставить хаб» — география логистики становится выбором, а не данностью;
усиливает профессию роя (возить в узлы). В текущие числа спеки не входит
(анти-двойной учёт); решение за создателем.
