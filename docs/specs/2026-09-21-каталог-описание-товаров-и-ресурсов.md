## 0. Резюме (одним абзацем)

У каталога студии (`goods`, `kind = good | resource`) появляется одно текстовое
поле **«описание»** — многострочное, пустое по умолчанию, без обязательности:
игровой текст (увидят игроки, когда появится экран товаров) и одновременно
рабочий (различать записи в студии). Решение создателя 2026-09-21: **одно поле
для всех потребителей** — отдельного поля «заметка студии» нет. Поле проходит
сквозную нитку: миграция `000057` (`ADD COLUMN goods.description TEXT NULL`) →
модель → репозиторий → API → **три ИИ-потока** (описание для новых составляющих
при «заполнить комплектующие»; одиночный прогон по записи после ручного создания
и по кнопке; **разовый пакетный прогон** по всему, где описания нет) → UI студии
(`textarea` в попапе записи, галка «описание ИИ» в строке создания, третья колонка
массовой подгрузки, попап «Описания ИИ» с принять/пропустить/отредактировать).
Сегодня описание — только **хранение + студия**; показ игроку — будущая задача.
`props` ресурсов, экономика, граф/тир рецептов и игровой UI не затрагиваются.
Критика (@critic) по решению создателя не запускается.

## 1. Разворот подходов (пространство решений)

**Ключевой вопрос 1: как хранить описание.** (выбран класс А)

| Вариант | Суть | Цена | Итог |
|---|---|---|---|
| **А. Колонка `goods.description TEXT NULL`** | одна колонка на оба вида | одна миграция, `NULL` = «нет описания» | **выбран** — 1:1 с записью каталога, переживает второй тип текста (описание ресурса), не плодит сущность |
| Б. Ключ в `props` JSONB | без миграции | `props` — только ресурсы (`CHECK` 000045), товар не может; поле данных в JSONB не индексируется и не типизируется — расходитcя с нормой проекта (свойства записи — колонки) | отклонён — противоречит `CHECK` и природе `props` |
| В. Таблица `goods_descriptions` (1:1) | «расширяемо на несколько текстов» | лишняя сущность на один факт («сущность с двумя экземплярами — не сущность»); join на каждый `loadGoods` | отклонён — преждевременная расширяемость |
| Г. Контент-файл (`config/*.json`) | правится в редакторе | каталог живёт в БД (iterA), студия пишет в БД → два источника истины | отклонён |

**Ключевой вопрос 2: как ИИ предлагает описание.** (выбран класс В)

| Вариант | Суть | Цена | Итог |
|---|---|---|---|
| А. Синхронный ИИ в `POST /studio/api/goods` | описание в ответе создания | HTTP-ответ держится всю ИИ-латентность (таймаут `TIMEOUT_S` × ретраи); при сбое клиент не знает id созданной записи → слепой повтор; паттерн проекта — асинхронный fill (решение 2026-09-20) | отклонён |

## 2. Границы

**Делаем:** одну колонку описания (товары и ресурсы), ручной ввод в студии,
предложение описания ИИ в трёх потоках, третью колонку массовой подгрузки,
пакетный прогон по записям без описания — с принять/пропустить/отредактировать.

**Не делаем (границы фичи):**
1. **Показ описания игроку** — сейчас только `хранение + студия`; игрового экрана
   товаров/ресурсов не существует, показ — **будущая задача** (когда появится
   экран товаров). API описания в игровом контуре не вводим.
2. **`props`-логику ресурсов не трогаем** (оси, `t_melt_k`/`t_boil_k`, `family`,
   `closes`) — `CHECK ((kind='good' AND props IS NULL) OR kind='resource')`
   остаётся как есть; витрина 94a и слой 20 (`props ? 'family'/'closes'`)
   описание не читают.
3. **Экономику и граф не трогаем:** описание не влияет на `recipes` /
   `recipe_components` / `producer_recipes`, тир/сложность, валидаторы
   (`validate.Validate`), поиск/уникальность имён (`name_norm`).
4. **Согласование/статусы/скрытие** записей каталога не возвращаем.
5. Поиск по описанию не вводим (поиск справочника — по имени).

## 3. Инварианты

- **И1. Одно поле для всех потребителей.** `goods.description` — общий текст:
  игровое описание + рабочее различение записей. Отдельного поля «заметка студии»
  нет (решение создателя 2026-09-21; отклонено в §14).
- **И2. Поле у обоих видов.** `description` есть у `kind=good` и
  `kind=resource`; обязательности нет, значение по умолчанию — пусто.
- **И3. «Пусто» — одно представление.** В БД «нет описания» = `NULL`; пустая
  строка и строка из пробелов на запись нормализуются в `NULL`. На чтении `NULL`
  отдаётся как `""`. Двух состояний «пусто» (`''` и `NULL`) не существует.
- **И4. Пакетный прогон не пишет поверх непустого; явный поток переписывает.**
  Два режима джоба описаний:
  - **пакетный** (`fill {scope:"missing"}`): записи с непустым описанием не
    попадают в цель прогона, и **применение** пункта к записи с непустым
    описанием отклоняется (guard `onlyIfEmpty = true`; защита от гонки:
    пользователь вписал текст, пока джоб шёл);
  - **явный** (`fill {good_ids:[…]}` — одиночный прогон после создания или
    кнопкой «предложить описание», §8.3): переописание существующего описания
    **разрешено** (guard снят, `onlyIfEmpty = false`) — это и есть механизм
    «переописать».
  Режим определяется способом запуска джоба и передаётся в применение (§7.3).
- **И5. `kind=link` не меняет описание.** В fill-потоке описание применяется
  **только** к новым товарам (`kind=new`): у `kind=link` (существующая запись)
  `goods.description` не меняется ни при разборе, ни при применении.
- **И6. Один ИИ-джоб студии одновременно.** fill и описания не идут параллельно:
  старт атомарный (TryStart), второй старт — 409. Причина: один локальный
  opencode-канал + один общий индикатор `generating` в UI.
- **И7. Отмена пакетного прогона сохраняет предложения.** Остановка не сбрасывает
  уже полученные предложения (прогон дорогой; в отличие от fill-cancel).
- **И8. Описание — данные каталога.** Как `volume`/`weight`: не влияет на
  граф/тир/валидаторы; каталог — контент, `ClearUniverse` его не трогает
  (описание наследует это свойство таблицы `goods`).
- **И9. Предел длины.** Непустое описание ≤ **2000 символов** (руны, не байты).
  Ручной ввод длиннее — 400; ИИ-текст длиннее — обрезается по рунам до 2000 со
  строкой в отчёте (§8.2), потому что предел защищает хранение/UI, а не смысл.

## 6. Репозиторий (`internal/repository/goods_repository.go`)

1. **`loadGoods`** — в SELECT добавляется `g.description` (последней колонкой),
   в `Scan` — `var description sql.NullString`, в модель: `g.Description = description.String`.
   Итоговый текст SELECT (его сверяет sqlmock, §11.1):
   ```sql
   SELECT g.id, g.name, g.category_id, g.kind, g.source, r.id, r.complexity, g.created_at, g.volume, g.weight, g.description
    FROM goods g LEFT JOIN recipes r ON r.good_id = g.id
    ORDER BY g.id
   ```
2. **`CreateGood`** — не меняется (описание при создании не принимается, §7.1):
   новая запись получает `description = NULL`.
3. **`UpdateGood(id int64, name *string, categoryID *int64, volume, weight *float64, description *string) error`** —
   новый последний параметр, семантика как у `volume/weight`: `nil` = не трогать;
   непустое значение — `strings.TrimSpace`, проверка `> MaxDescriptionRunes` → 400
   «описание длиннее 2000 символов»; пустое/пробельное → `UPDATE goods SET
   description = NULL` (очистка, И3). Ресурсам разрешено (как сейчас).
4. **`BulkCreateGoods(lines []string)`** — строка разбирается как
   `strings.SplitN(trimmed, "|", 3)`:
   - 2 колонки — валидны (описание пустое);
   - 3 колонки — третья колонка = описание; может быть пустой; «|» внутри
     описания допустим (третья часть не режется дальше);
   - описание нормализуется (trim; пусто → `NULL`); длиннее предела → строка в
     `rep.Errors` («описание длиннее 2000 символов»), запись не создаётся
     (частичный успех, как у прочих ошибок строк);
   - `INSERT INTO goods (name, name_norm, category_id, kind, source, description)
     VALUES ($1, $2, $3, 'good', 'manual', $4)`.
   `BulkCreated`/`BulkSkipped`/`BulkError` не меняются.
5. **`ApplyProposals`** (write-back новых товаров от ИИ) — `INSERT` получает
   `description` из `item.Description` (нормализованный, §8.1):
   `INSERT INTO goods (name, name_norm, category_id, kind, source, description)
   VALUES ($1, $2, $3, 'good', 'ai', $4)`. Существующие записи (`kind=link`)
   не трогаются (И5).
6. **Новый метод — применение описаний** (один вход для одиночного и пакетного
   потоков):
   ```go
   // DescItem — принятый пункт попапа «Описания ИИ»: id записи каталога +
   // нормализованный текст (trim, непустой, ≤ MaxDescriptionRunes).
   type DescItem struct {
       ID   int64
       Text string
   }

   // UpdateDescriptions — запись описаний (спека §6.6): одна транзакция с
   // advisory lock (beginMutation). onlyIfEmpty — режим джоба (И4):
   //   true  — пакетный прогон (scope:"missing"): на каждый пункт SELECT name,
   //           COALESCE(description, '') FROM goods WHERE id = $1 FOR UPDATE —
   //           • записи нет        → «запись N не найдена — пропущено»;
   //           • описание непустое → «описание уже заполнено: <имя> — пропущено»;
   //           • иначе UPDATE goods SET description = $1 WHERE id = $2;
   //   false — явный прогон (good_ids: одиночный после создания / по кнопке):
   //           guard непустого описания снят — SELECT (наличие записи) и
   //           UPDATE поверх («запись N не найдена — пропущено» только если
   //           записи нет) — явное переописание.
   // Возвращает applied (фактически записанные) + отчёт по строкам.
   func (r *GoodsRepository) UpdateDescriptions(items []DescItem, onlyIfEmpty bool) (applied int, report []string, err error)
   ```
   Пустой/пробельный `Text` до репозитория не доходит (отсекается обработчиком,
   §7.3) — в `UpdateDescriptions` непустой `Text` ожидается как контракт.

## 7. API (`/studio/api/*`, JWT admin/skycomposer)

### 7.1. Ручное описание — `PUT /studio/api/goods/{id}` (расширение)

Тело дополняется необязательным полем (остальные поля без изменений):

```json
{ "name": "…", "category_id": 12, "volume": 1, "weight": 1, "description": "многострочный текст" }
```

- поле отсутствует (`null`) — описание не трогается;
- пустая строка / пробелы — **очистить** (в БД `NULL`);
- длиннее 2000 символов — 400 `{"error":"описание длиннее 2000 символов"}`;
- ответ без изменений: `{"id": N}`.

**`POST /studio/api/goods` описание не принимает** (отклонение от черновика ТЗ §2.4,
см. §14): единственная ручка ручной записи — `PUT`. `CreateGood` не расширяется.

### 7.2. Состояние — `GET /studio/api/state` (аддитивные поля `StateView`)

```go
DescGenerating bool               `json:"desc_generating"` // идёт джоб описаний
DescReport     []string           `json:"desc_report"`     // отчёт джоба/применения
DescProposals  []DescProposalView `json:"desc_proposals"`  // предложения (по одной строке на запись)
DescTotal      int                `json:"desc_total"`      // записей в прогоне
DescDone       int                `json:"desc_done"`       // обработано записей (прогресс)
```

`generating` (существующее поле) = «идёт **любой** ИИ-джоб студии» (И6) — UI уже
гасит кнопки по нему; `desc_generating` нужен попапу описаний, чтобы различать
«идёт прогон» и «прогон завершён».

### 7.3. Три роута описаний (новые, один блок в `main.go`)

```
POST /studio/api/descriptions/fill    {scope:"missing"} | {good_ids:["12","15"]}
POST /studio/api/descriptions/apply   {accepted:[{i:0, text:"…"}]}
POST /studio/api/descriptions/cancel  {}
```

**`fill`** (старт джоба; ровно одно из полей, иначе 400 «укажите scope или good_ids»):
- `{"scope":"missing"}` — **пакетный режим** (`onlyIfEmpty = true`): цель — все
  записи каталога, где `description IS NULL` или пусто (снимок на старте);
  записи с непустым описанием целью не являются (И4);
- `{"good_ids":[…]}` — **явный режим** (`onlyIfEmpty = false`, §8.3): цель —
  перечисленные записи (порядок = порядок в списке), в том числе с непустым
  описанием (переописание разрешено, И4); несуществующий id → 400 «запись не
  найдена: N»;
- пустая цель → 400 «нет записей без описания» (`scope`) / «good_ids пуст»;
- 409 `{"error":"уже идёт генерация"}` — занят общий флаг И6 (и fill, и описания);
- 202 `{"started":"true","total":N}`.
Режим джоба хранится в обработчике рядом с предложениями (`descExplicit bool`:
`false` — пакетный, `true` — явный): устанавливается на старте `fill`,
сбрасывается при старте нового `fill` и при `apply` (вместе с очисткой
применённых предложений), **на `cancel` не сбрасывается** — предложения
сохраняются (И7), значит и режим обязан дожить до применения. Запуск идёт в
горутине, `DescReport`/`DescProposals` канала описаний очищаются на старте.

**`apply`** (применение принятых пунктов):
- 400 — невалидный JSON / `accepted` пуст / индекс вне диапазона;
- 409 — идёт ИИ-джоб / нет предложений;
- 200 `{"applied":N}`; отчёт в `DescReport`: «пропущено: K (не принято)»,
  строки репозитория (§6.6), «Применено: N». Итог применяется
  `repo.UpdateDescriptions(items, !h.descExplicit)` — режим берётся из сохранённого
  `descExplicit` джоба, чьи предложения применяются (§8.3: явный поток
  переписывает, пакетный — нет); одной транзакцией; предложения после применения
  очищаются (вместе с `descExplicit`).
- пункт с пустым/пробельным `text` в `accepted` **не применяется** и даёт строку
  «пустой текст — пропущено» (не путать с очисткой: очистка — только через PUT
  пустой строкой, §7.1).

**`cancel`** (остановка длинного прогона):
- если джоб идёт — ставится флаг остановки: горутина завершает текущую порцию и
  останавливается; **предложения сохраняются** (И7) вместе с режимом
  (`descExplicit` не сбрасывается — `apply` после отмены применит верный
  `onlyIfEmpty`), отчёт «остановлено: M из N»,
  200 `{"cancelled":"true","done":M,"total":N}`;
- если джоб не идёт — 200 без изменений состояния (в отличие от fill-cancel,
  здесь 409 нет: смысл cancel — уметь остановить **идущий** прогон).

### 8.1. Поток 1 — описание новых составляющих при «заполнить комплектующие»

### 8.3. Поток 2 — явный прогон по записи (создание / кнопка), переописание разрешено

Ручное создание «+ товар»/«+ ресурс» **не** трогает ИИ в самом запросе: после
успешного `POST /studio/api/goods` клиент сам зовёт
`POST /studio/api/descriptions/fill {"good_ids":[id]}` (если галка «описание ИИ»
включена, §9.3). Тот же вызов — кнопка «предложить описание» в попапе записи
(единственный вход для ресурса: у ресурса нет «заполнить комплектующие»).
Порция = 1 запись, результат — одна строка в попапе «Описания ИИ» (§9.4);
текст можно отредактировать перед принятием.

Это **явный режим** (И4): джоб помечается `descExplicit = true`, применение идёт
с `onlyIfEmpty = false` (§6.6, §7.3) — переописание уже существующего описания
**разрешено**. Именно кнопка «предложить описание» (и автопрогон после создания)
является механизмом «переописать»: пакетный поток на непустые записи не идёт
(§8.4).

### 8.4. Поток 3 — пакетный прогон (`runDescriptions`)

- Порция — **10 записей** на один запрос ИИ (`descBatchSize = 10`); порции идут
  последовательно, один запрос за раз (И6). 131 запись ≈ 14 запросов.
- Режим — **пакетный** (`descExplicit = false`, `onlyIfEmpty = true`): цель — только
  записи без описания (§7.3), применение не пишет поверх непустого (И4).
- Прогресс после каждой порции: `desc_done += len(порции)` (под мьютексом) —
  UI видит «M из N» при опросе `state`.
- Ошибка порции (сеть/таймаут/мусор в ответе) **не прерывает прогон**: строка
  «порция X: ошибка ИИ: …» / «порция X: мусор в ответе ИИ» в `DescReport`, идём
  дальше (иначе сбой одного запроса из 14 терял бы весь результат).
- Предложения добавляются в `DescProposals` по мере готовности порций
  (`{id, name, kind, text}`), попап у пользователя обновляется опросом.
- Остановка: флаг `descCancel` проверяется между порциями; предложения
  сохраняются (И7), режим джоба тоже (`descExplicit` на `cancel` не сбрасывается,
  §7.3 — иначе `apply` после отмены применил бы неверный `onlyIfEmpty`).
- Записи, у которых описание появилось **во время** прогона (ручной ввод),
  отсекаются на применении (И4, `onlyIfEmpty = true`), но в отчёте не
  подсвечиваются — guard в §6.6. Для явного потока (§8.3) такого отсечения нет.
- Рестарт сервера: транзиентный джоб и предложения теряются (in-memory, как
  fill); в БД до `apply` ничего не записано.

Содержимое — `renderDescPopup()`:

- заголовок: «Описания ИИ (M из N)» (при `state.desc_generating` — со спиннером
  и текстом «идёт прогон…»);
- строка на предложение: имя записи (`· ресурс` для `kind=resource`),
  `textarea` со значением предложения (редактируемое), чекбокс «принять»
  (по умолчанию включён, если текст непустой);
- выбор хранится в `descAccepted[i] = {accepted, text}` (как `proposalsAccepted`
  у fill); устаревшие индексы чистятся при смене набора;
- футер: «Применить принятые (K)» (disabled при K = 0) / «Отмена»;
- список длинный (до 131 строки) — тело со скроллом (`max-height` + `overflow: auto`).

Поведение (реактивность, по образцу fill-попапа в `fetchState`):

- **авто-открытие** — когда `state.desc_proposals.length > 0` и открытие ещё не
  делалось для этого набора (ключ `JSON.stringify(desc_proposals) + desc_total`);
- во время прогона попап **не закрывается** и обновляет строки/прогресс
  (в отличие от fill-попапа, который открывается после завершения);
- «Применить принятые» → `POST …/apply {accepted:[{i, text}]}` → закрыть попап,
  `fetchState()`;
- «Отмена» → `POST …/cancel` → тост-отчёт, попап **остаётся** с уже полученными
  предложениями (И7), повторное применение доступно; полное закрытие — крестик.

### 9.7. Защита несохранённого текста от авто-обновления

`fetchState` перерисовывает UI каждые 3 с при изменениях `state.goods`. Правило:
в `renderAll()` вызовы `renderPopup()` и `renderDescPopup()` **пропускаются**,
если фокус находится в `textarea` соответствующего попапа (`document.activeElement`
— `#descInput` / textarea внутри `#descPopupBody`) и её значение отличается от
модельного. Иначе авто-обновление (например, во время пакетного прогона) стирало
бы несохранённый текст. Границы: кнопки/списки попапа обновляются как раньше.

## 10. Режимы отказа

| Ситуация | Поведение |
|---|---|
| ИИ недоступен / таймаут / мусор в ответе | строка в `DescReport`; прогон продолжается (пакетный) или завершается без предложений (одиночный); БД не тронута |
| Второй ИИ-джоб одновременно | 409 «уже идёт генерация» (атомарный старт, И6) |
| Запись удалена между фазами | `apply`: «запись N не найдена — пропущено», 200 (не ошибка — как М2 fill) |
| Описание появилось, пока шёл прогон | **пакетный** режим: `apply` → «описание уже заполнено: <имя> — пропущено» (И4, `onlyIfEmpty = true`); **явный** режим (кнопка/создание): перезапись допустима (§8.3, `onlyIfEmpty = false`) |
| Ручной ввод длиннее предела | 400 (ручная ручка); ИИ-текст обрезается до 2000 (И9) |
| Рестарт сервера во время прогона | джоб/предложения теряются (in-memory); в БД ничего не записано |
| Запись каталога правится параллельно (студия) | запись описания — своя транзакция с advisory lock (`beginMutation`), как прочие мутации каталога |

## 14. Отклонённые варианты (с причинами)

1. **Синхронный ИИ в `POST /studio/api/goods`** — блокирует ответ создания на
   всю ИИ-латентность; при сбое клиент не знает id записи (слепой повтор);
   расходится с паттерном асинхронного fill (решение создателя 2026-09-20).
2. **Однофазная автозапись описания без подтверждения** — ИИ ошибается;
   решение создателя: ИИ **предлагает**.
3. **Один запрос ИИ на всю пачку (131 запись)** — ~8–10k токенов вывода:
   обрезка, дрейф имён, непроверяемое сопоставление.
4. **Запрос ИИ на каждую запись** — 131 × ~10–20 с ≈ 20–40 мин против ~14
   запросов (2–5 мин) при порции 10.
5. **Отдельное поле «заметка студии» (`goods.note`) рядом с описанием** —
   кандидат ГД-сущности был предложен @designer и **отклонён создателем
   2026-09-21**: «нужно одно поле для всех потребителей» (зафиксировано И1).
6. **Приём `description` в `POST /studio/api/goods`** — UI не имеет поля при
   создании; одна ручка ручной записи (`PUT`) вместо двух.
7. **`textarea` описания в строке создания справочника** — строка создания
   должна остаться узкой; ручной текст пишется в попапе записи (где живут
   объём/вес/категория).
8. **Два представления «пусто» (`''` и `NULL`)** — расхождение выборок
   (`WHERE description IS NULL`) и guard’ов; единое представление — `NULL` (И3).
9. **Хранение описания в `props` JSONB / отдельной таблице 1:1 / контент-файле** —
   см. §1 (противоречие `CHECK`, лишняя сущность, два источника истины).
10. **Показ описания игроку сейчас** — игрового экрана товаров нет; фиксируется
    как будущая задача (§2 п.1).
