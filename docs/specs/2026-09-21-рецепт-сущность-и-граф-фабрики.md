## 0. Резюме (одним абзацем)

**Рецепт становится самостоятельной сущностью каталога**: запись «что из чего»
(выход — товар, состав — компоненты, сложность — свойство рецепта). Состав
переезжает из `goods_slots` в `recipes` + `recipe_components`; связь «фабрика ↔
рецепты» — `producer_recipes` (M:N): конкретная фабрика (подтип `producer_types`
kind=goods) держит **набор рецептов** — подмножество рецептов своей категории,
а не категорию целиком. Товар остаётся общим словарём-материалом (не принадлежит
фабрике): один рецепт может быть привязан к нескольким фабрикам (человеческой и
водной). Инвариант: **выход рецепта — всегда категория фабрики** (проверка 400
при привязке). Сложность переезжает на рецепт (`recipes.complexity`), тир товара
становится производным, `goods.tier_override` снимается миграцией `000055`
(данные переносятся в `recipes.complexity`). Ветка «Товары» получает **селектор
фабрики** (граф выбранной фабрики — замыкание вниз от её рецептов; граф может
быть несвязным) и **фильтр справочника по семейству рас** (канон «самая
конкретная побеждает»: на категорию — фабрика, которую семейство реально
получает). Спека одобрена создателем 2026-09-21 (§11 — принятые решения); гейт
UI-дизайна (идея §8) добавил в объём **привязку перетаскиванием карточки
справочника на канвас** (новая механика канваса, §4.4) и **роут копирования
набора рецептов** из универсальных фабрик категории (§5).
Релиз 2 (buildings, снабжение) не проектируется — фиксируются только дельты
(§7). Числа баланса не затрагиваются.

## 1. Разворот подходов (пространство решений)

**Ключевой вопрос: как хранить рецепт.** Классы подходов (не вариации одного):

| Вариант | Суть | Цена | Итог |
|---|---|---|---|
| **А. Рецепт — отдельная таблица + состав + M:N связь с фабрикой** | `recipes` / `recipe_components` / `producer_recipes` | 3 таблицы, миграция данных, проекция в модели (`Good.Recipe`) | **выбран** (решение создателя «да, красиво», идея §1.1) |
| Б. Рецепт — атрибут товара (`goods_slots` остаётся, «сущность» = 1:1) | минимум изменений | не переживёт альтернативные рецепты (заявлены как будущее); «фабрика держит рецепты» подменяется категорией | отклонён — противоречит решению создателя |
| В. Рецепт — запись `producer_types` | одна таблица | смешивает две оси (типология построек × правила производства), ломает дерево построек (глубина 1) | отклонён |
| Г. Рецепт — JSONB-документ в одной таблице (`components` JSONB) | меньше join'ов | нет FK на компоненты → теряются каскады «очистить ссылку при удалении товара» и индекс обратных рёбер; в проекте норма — ссылочная целостность на БД (`goods_slots` — отдельная таблица) | отклонён |
| Д. Рецепт — контент-файл (`config/*.json`), не БД | правится в редакторе | студия пишет в БД (каталог живёт в БД с iterA) → рассинхрон двух источников | отклонён |

**Решения внутри выбранного класса** (приняты создателем 2026-09-21 — §11):

## 2. Модель и БД

### 2.1. Природа сущности (архитектурный фильтр, PITFALLS «событие vs лог»)

1. **Рецепт** — **правило/состояние** (справочник «что из чего»), не событие и не
   лог. У него свои свойства (сложность), значит — самостоятельная сущность, не
   атрибут товара (идея §1.2 п.1).
2. **Владелец** — **у многих**: один рецепт нужен нескольким фабрикам → связь
   M:N закладывается сразу (идея §1.2 п.2).
3. **Расширяемость** — альтернативные рецепты на один товар лягут в ту же
   таблицу (снятие `UNIQUE (good_id)` — простая миграция, решение менеджера).
   Рецепты **предметов** (лаборатории, `producer_items.requirements`) — другая
   механика (другой выход), в одну таблицу с товарными НЕ смешиваются (идея
   §1.2 п.3).
4. **Состав рецепта** — строки-компоненты (позиция, ссылка на товар/ресурс,
   количество): у рецепта их много, у компонента есть свои атрибуты (количество,
   галка ИИ, обоснование) → таблица, не JSONB.
5. **Рецепт каталога — не запись производства.** Факт «фабрика произвела N
   единиц» — ленивый расчёт релиза 2 (инвариант 2, спека фабрик §2 п.6);
   построчных записей производства нет.

### 2.2. Терминология (разведение значений; дельта GLOSSARY — §8)

| Термин | Значение | Отношение |
|---|---|---|
| **Рецепт** | Запись каталога: выход (товар) + состав (компоненты) + сложность. «Что из чего» | **новое** значение (эта спека) |
| **Состав рецепта** | Компоненты рецепта: товар/ресурс + количество | новый термин |
| **Рецепт (старый GLOSSARY, `05_economy.md` §5.2.4)** | «Какие ресурсы по окнам свойств и в каком количестве нужны» | переформулируется: требования по **окнам свойств** — язык контрактов и предпочтений (§5.2.2), не структура рецепта каталога (§8.3) |
| **Предмет-рецепт** | Предмет с ролью разблокировки (`items.unlocks`), вкладывается в слот строения | **≠ рецепт**: предмет разблокирует, рецепт описывает |
| **Слот рецепта** (GLOSSARY §1) | Позиция компонента в составе (`recipe_components.pos`) | переименование источника: `goods_slots.pos` → `recipe_components.pos` |
| **Семейство рас (F)** | F0–F9 + `robotic` (канон; в UI — «F10 Роботы») | без изменений (спека `2026-09-21-люди-f0-отдельное-семейство`) |
| **Ресурсы — общий пул** | Строки `goods` c `kind='resource'` (НЕ новая сущность) | без изменений (GLOSSARY §5 «Оговорка студии») |

«Семейство» без уточнения — не пишем: хим-группы ресурсов и семейства рас —
разные вещи (решение менеджера по критике).

### 2.3. Таблицы (миграция `000055`)

Следуют паттерну каталога (000045/000048/000052): BIGSERIAL-ключи, `name_norm`
пишет приложение, каталог — **контент** (ClearUniverse не трогает, в
`truncateTables` не входит), мутации — под `pg_advisory_xact_lock`
(`catalogLockKey`), снимок — одна транзакция REPEATABLE READ.

**`recipes`** — справочник рецептов.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | BIGSERIAL PK | ключ рецепта |
| `good_id` | BIGINT NOT NULL FK → `goods(id)` ON DELETE CASCADE | **выход рецепта** — товар (kind=good) |
| `complexity` | INT NULL CHECK (≥ 0) | **сложность рецепта** (данные; не гейт — спека фабрик §8.2); NULL = вычисляется по графу |
| `created_at` | TIMESTAMPTZ | |
| `UNIQUE (good_id)` | | «один рецепт на товар» сейчас; снятие → альтернативные рецепты (решение менеджера) |

**`recipe_components`** — состав рецепта (замена `goods_slots`).

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | BIGSERIAL PK | |
| `recipe_id` | BIGINT NOT NULL FK → `recipes(id)` ON DELETE CASCADE | рецепт |
| `pos` | INT NOT NULL | порядок компонента (0-based) |
| `component_id` | BIGINT NULL FK → `goods(id)` ON DELETE SET NULL | составляющая (товар **любой категории** или ресурс); NULL = пустой компонент (заполняется ИИ/вручную) |
| `quantity` | INT NOT NULL DEFAULT 1 CHECK (≥ 1) | количество единиц |
| `reason` | TEXT NULL | ИИ-обоснование (тултип) |
| `allow_resource` | BOOLEAN NOT NULL DEFAULT false | **подсказка ИИ** для пустого компонента (см. §2.5) |
| `UNIQUE (recipe_id, pos)` + индекс по `component_id` | | как у `goods_slots` (обратные рёбра) |

**`producer_recipes`** — «фабрика ↔ рецепты» (набор рецептов фабрики).

| Колонка | Тип | Смысл |
|---|---|---|
| `producer_type_id` | BIGINT NOT NULL FK → `producer_types(id)` ON DELETE CASCADE | **конкретная** фабрика (подтип kind=goods) |
| `recipe_id` | BIGINT NOT NULL FK → `recipes(id)` ON DELETE CASCADE | рецепт из её категории |
| `created_at` | TIMESTAMPTZ | |
| PK | `(producer_type_id, recipe_id)` | повторная привязка — 409 |
| индекс по `recipe_id` | | обратный запрос «какие фабрики держат рецепт» |

**Дельта `goods`:** колонка `tier_override` **снимается** (`DROP COLUMN`);
значение переезжает в `recipes.complexity` (§3, миграция). **`goods_slots`
сносится** (`DROP TABLE`) после переноса данных.

### 2.4. Инварианты

| Инвариант | Где проверяется | Ответ |
|---|---|---|
| **Выход рецепта — всегда категория фабрики**: `category(recipes.good_id) = producer_types.category_id` при привязке | **Go** (репозиторий, транзакция под advisory lock) | 400 «выход рецепта — не категория фабрики» |
| **Смена категории фабрики при привязанных рецептах** запрещена (симметрия строке про смену категории товара, §5): если у конкретной фабрики есть `producer_recipes`, `category_id` не меняется | **Go** (`UpdateProducerType`, транзакция под advisory lock; клиентский путь смены — `changeProdCategory` в `web/studio.html`) | **409** «сначала отвяжите рецепты» |
| Рецепт привязывается только к **конкретной** фабрике: `producer_types.kind='goods'` + `parent_id IS NOT NULL` + `category_id IS NOT NULL` | Go | 400 |
| Выход рецепта — только товар (`kind='good'`); рецепт на ресурс не создаётся | Go (создание рецепта идёт только с kind=good) | 400 |
| Состав: компонент — **любой** товар или ресурс (в т.ч. другой категории), ресурсы — общий пул `kind='resource'` | по построению (FK на `goods`) | — |
| Цикл: компонент не может быть выходом самого себя (транзитивно) | Go (`graph.WouldCreateCycle`, как сейчас) | 409 |
| Дубликат рецепта на товар | БД `UNIQUE (good_id)` + Go-пречек | 409 |
| Дубликат привязки | БД PK + Go-пречек | 409 |
| «Один рецепт на товар» — **временное** ограничение (снятие под альтернативные рецепты) | БД `UNIQUE (good_id)` | решение менеджера; снятие — простая миграция |

**Две стороны инварианта «выход = категория» — обе закрыты явным правилом:**
смена категории **товара** при привязанном рецепте → 409 (§5, `UpdateGood`);
смена категории **фабрики** при привязанных рецептах → 409 (строка выше,
`UpdateProducerType`). Без второго правила инвариант тихо
нарушался бы: смена `category_id` разрешена при применяемом слоте
(`producer_repository.go`), а привязанные рецепты стали бы «выходом не
категории фабрики». Свободная смена (привязок нет) — как сейчас.

**Решение §11.1 (принято):** инвариант «выход = категория» — Go-only (вариант А,
как у инварианта С4 спеки скрытых §1.4 п.1), без составного FK (вариант Б
отклонён). Цена отклонённого варианта с FK: дублирование факта «категория
товара» в `recipes` (дрейф при смене категории товара) — против правила «один
факт — одно место»; выигрыш: гарантия переживает пути мимо Go (сид/булк).
Каталог пишется только через репозиторий под advisory lock — Go-проверки
достаточно.

### 2.5. Судьба `allow_resource` (уточнение по критику)

Старый смысл — **подсказка ИИ** («ИИ может заполнить пустой слот ресурсом»),
а не «компонент является ресурсом» (это выводится из `goods.kind`). Разводим:

- **флаг остаётся** на `recipe_components.allow_resource`, смысл и поведение **не
  меняются** (влияет только на пустой компонент; `false` у старых строк —
  миграция значений не нужна);
- **«компонент-ресурс»** — производное от `kind` составляющей, отдельным полем
  НЕ дублируется;
- в UI подпись уточняется: «разрешить ресурс в этом компоненте (для ИИ)».

Решение §11.6 (принято): снять флаг вовсе (ИИ работает без подсказки) —
отклонено; цена отклонённой альтернативы — регресс поведения «ресурсы в рецепт
только если прямо указано» (решение создателя 2026-09-19). Флаг сохраняется.

## 3. Миграция `000055` (в `migrations/` на 2026-09-21 последняя — `000054`
— снятие согласования каталога, `000055` — эта спека; сверено по `migrations/`)

```sql
-- 1) Таблицы рецептов (§2.3).
CREATE TABLE recipes (...); CREATE TABLE recipe_components (...);
CREATE TABLE producer_recipes (...);

-- 2) Рецепт — на каждый товар (kind='good'); сложность = старый tier_override.
INSERT INTO recipes (good_id, complexity)
SELECT id, tier_override FROM goods WHERE kind = 'good';

-- 3) Состав — из goods_slots.
INSERT INTO recipe_components (recipe_id, pos, component_id, quantity, reason, allow_resource)
SELECT r.id, s.pos, s.component_id, s.quantity, s.reason, s.allow_resource
FROM goods_slots s JOIN recipes r ON r.good_id = s.good_id;

-- 4) Привязка: ко ВСЕМ универсальным конкретным фабрикам категории товара.
INSERT INTO producer_recipes (producer_type_id, recipe_id)
SELECT pt.id, r.id
FROM recipes r
JOIN goods g ON g.id = r.good_id
JOIN producer_types pt
  ON pt.kind = 'goods' AND pt.parent_id IS NOT NULL AND pt.category_id = g.category_id
 AND pt.race_family IS NULL AND pt.race IS NULL;

-- 5) Снос старой структуры.
ALTER TABLE goods DROP COLUMN tier_override;
DROP TABLE goods_slots;
```

**Правила миграции (решения менеджера, идея §5):**

- **«где у категории есть универсальная дочка — товары к ней; где нет — товар
  „ничей“»**: товары категорий без универсальной конкретной фабрики остаются без
  привязок и помечаются в студии («не привязан»); правится через справочник.
- **Привязка ко ВСЕМ универсальным дочкам категории** (не только к «Фабрике»):
  если у категории есть и «Фабрика X», и «Автофабрика X» — рецепт доступен обеим
  (свойство модели: один рецепт — несколько фабрик). Ничего не теряется.
- **Сложность:** `goods.tier_override` → `recipes.complexity` (для товаров).
  **Оверрайды ресурсов теряются** (`SetTier` разрешал их и ресурсам, С3) —
  ресурс не имеет рецепта, его тир = 0 по определению. Решение §11.2 (принято:
  перенос в `recipes.complexity`; отклонённая альтернатива — сохранить оверрайд
  ресурсов: вторая запись тира = двойной источник).
- **Свежие БД:** на момент миграции `goods kind='good'` нет (131 ресурс —
  `kind=resource`; товары создаёт студия) → data-миграция холостая, обновлённый
  сид не требуется (в отличие от 000051/000052, где данные создавал Go-сид).
- **Идемпотентность:** миграция одноразовая (учёт в `schema_migrations`),
  `ON CONFLICT` не нужен; `DROP COLUMN`/`DROP TABLE` — в конце.

## 4. Студия: ветка «Товары»

### 4.1. Селектор фабрики

- В шапке ветки «Товары» (рядом с `#segGraph` 183; строки — на момент
  2026-09-21) — select **`#goodsFactorySel`**: список **конкретных фабрик**
  (`producer_types` kind=goods, `parent_id NOT NULL`, `category_id NOT NULL`) с
  категорией **`categories.kind='good'`**, сгруппированный (optgroup: родительский
  тип → «Категория · уровень расовости»; деталь раскладки — @uidesigner).
  Источник — существующий `state.producer_types` + новый `state.producer_recipes`
  (не новый эндпоинт).
- **Фабрики с ресурсной категорией в селектор не попадают** (условие
  `categories.kind='good'`): выход рецепта — только `kind='good'` (§2.4), рецепт
  у такой фабрики невозможен — любая привязка дала бы 400. Мёртвый путь устранён
  фильтром, а не пометкой: селектор «Товаров» перечисляет фабрики, для которых
  рисуется рецепт; фабрика-«добытчик» ресурсов рецептов не ведёт по определению.
- **Первый пункт — «Все товары (обзор)»** (дефолт, решение §11.8): текущее
  поведение (глобальный граф, `visibleGoods`). Отклонённая альтернатива —
  обязательный выбор фабрики: «ничей» товар и пустая студия не видны.
- Состояние — localStorage (`gs_goodsFactory`, как остальные переключатели).

### 4.2. Граф выбранной фабрики

- **Граф фабрики = замыкание вниз от выходов её рецептов** (`producer_recipes` →
  `recipes` → `recipe_components` рекурсивно; ресурсы — листья). Выходы её
  рецептов — корни; граф **может быть несвязным** (`computeLayout` 496 уже
  раскладывает лес: корни = глубина 0, слоты-плейсхолдеры работают).
- Компонент, произведённый **другой** фабрикой, в графе показывается как узел со
  своим составом (товар — общий словарь), но помечается «производится другой
  фабрикой» (деталь — @uidesigner). Решение §11.7 (принято — полное замыкание
  вниз; отклонённая альтернатива «один уровень вниз»: «вниз к компонентам/
  ресурсам» не выполняется).
- Пустые компоненты — существующие пунктирные плейсхолдеры (в `computeLayout`/
  `renderGraph`, на момент 2026-09-21 — 496/602).
- В режиме «Все товары» — как сейчас (`focusSubset`/`fullTree`).

### 4.3. Фильтр справочника по семейству рас

- В шапке ветки — select **`#goodsFamilySel`**: «Все семейства» (дефолт) + F0–F10
  (подписи «F0 Люди», …, «F10 Роботы»; данные — существующий
  `GET /studio/api/races`, `racesData` 352; строки — на момент 2026-09-21).
  localStorage `gs_goodsFamily`.
- **Правило (канон «самая конкретная побеждает»; решение менеджера — отменяет
  «своя + универсальная» из идеи §1.1).** Термин «исключающая лестница»,
  встречавшийся в первой редакции, — исторический синоним этого канона
  (переименован по спеке лестницы §12.2: канон проекта — «самая конкретная
  побеждает»). Для каждой категории и уровня L считаем **фабрику, которую
  уровень реально получает**:
  1. применяемые записи уровня L — по §2.4 спеки дерева: для **универсального**
     уровня — `race_family IS NULL`; для **семейства Fk** — `race_family IS NULL`
     **или** (`race_family = Fk` **и** `race IS NULL`); для **расы R** —
     `race_family IS NULL` **или** (`race_family = family(R)` **и** `race IS NULL`)
     **или** `race = R` (канон применяемости — §5.1 спеки лестницы);
  2. если применяемых записей нет → категория **не показывается**;
  3. если **самая конкретная применяемая запись-фабрика** скрыта
     (`producer_types.hidden`) **или** **самый конкретный применяемый слот**
     скрыт (`producer_slots.hidden`) → категория **исключена** (ни товары, ни
     граф) — это и есть «зачем роевым расам хлеб». Категория видима ⟺ **обе оси**
     не скрыты (полный канон двух осей, §5.3/§5.4 спеки лестницы, Р1/К1) — не
     только скрытость слота;
  4. иначе уровень получает **все** применяемые записи самой конкретной
     **ступени** (`race` > `race_family` > универсальная): если есть расовая —
     только она; иначе семейные; иначе все универсальные (их может быть
     несколько — это **разные типы-родители**, напр. «Фабрика X» и «Автофабрика X»).
- Показываются товары, чей рецепт привязан к полученной фабрике
  (`producer_recipes`). Универсальная фабрика «в довесок» к своей НЕ
  добавляется.
- Фильтр действует AND с селектором фабрики и с существующими фильтрами
  (категория/поиск/тиры/используемые).
- **Следствие (принято, §11.11):** создание расовой (или семейной) фабрики
  «обнуляет» видимость категории у уровня, пока в неё не привязаны рецепты (канон
  работает буквально — скрытая/пустая более конкретная запись перекрывает
  универсальную). Митигация — кнопка «скопировать набор рецептов универсальной
  фабрики категории»: **входит в эту задачу** (решение создателя, идея §8,
  вариант «а»; роут — §5). UI-элемент живёт в ветке **«Производители»** (ТЗ
  @uidesigner), **не** в ветке «Товары».

### 4.4. Создание и редактирование рецепта

- **Рецепт создаётся вместе с товаром** (`CreateGood`, `BulkCreateGoods`,
  ИИ-создание товара в `ApplyProposals`) — у каждого `kind='good'` ровно один
  рецепт (решение §11.3; отклонённая альтернатива «лениво при привязке»: «ничей»
  товар без рецепта неотличим от товара с пустым составом).
- **С фабрикой выбрано:** «+ товар» (`#spravNewName`/`#btnSpravAdd`, на момент
  2026-09-21 — 231–233) = создать товар **и** привязать его рецепт к выбранной
  фабрике (400, если категория нового товара ≠ категории фабрики — пречек в UI:
  селект категорий ограничивается категорией фабрики).
- **Без фабрики:** «+ товар» = создать товар без привязок («ничей»). «Ничей»
  товар виден **бейджем «не привязан»** в справочнике (ТЗ @uidesigner §6.5);
  warning `unbound_recipe` — уровень API, в UI студии **не рендерится** (см. §5).
- **Перетаскивание карточки из справочника на канвас = привязка рецепта**
  (решение создателя, идея §8) — **новая функциональность**, а не доработка
  существующей: сегодня канвас drop-обработчиков **не имеет** (комментарий в коде
  «drag&drop на канвасе не используется», `web/studio.html` 1019–1021; цель drop
  — слоты попапа). Семантика: привязка рецепта к **выбранной** фабрике
  (`POST /producers/{id}/recipes`, §5) — 400 при чужой категории, 409 при повторе;
  **без выбранной фабрики drop даёт тост-подсказку «выберите фабрику»** (канвас
  не подсвечивается, запроса на сервер нет) — канон **ТЗ @uidesigner §7.3.1**
  (обучение механике важнее «тишины»; решение менеджера, идея §9). Детали
  взаимодействия (подсветка, конфликт с пан/зумом, что при бросании на
  карточку/фон) — **ТЗ @uidesigner §7.3**, здесь не дублируются.
- **UI-добавки объёма** (решения менеджера, идея §9; новых роутов и механик нет,
  модель/API не меняются): (а) счётчик **«в наборе {N}»** в бейдже режима
  (`#modeBadge`) при выбранной фабрике; (б) пункт **«привязать к „{фабрика}“»**
  в существующем контекстном меню карточки справочника (`showSpravCtxMenu`) —
  путь привязки без перетаскивания, та же логика пречеков, что у drop. Детали —
  **ТЗ @uidesigner** (бейдж режима — §5.2, сноска §2 п.1; пункт меню — §7.3,
  сноска §2 п.2), здесь не дублируются.
- **Попап товара** (`renderPopup` 1040, строки — на момент 2026-09-21) — дельта:
  - секция слотов (1076–1091) переименовывается в **«Состав рецепта»**; поведение

    роуты — §5;
  - поле **«тир-оверрайд»** (`#tierInput` 1059–1065) заменяется на поле

  - новая секция **«Доступен фабрикам:»** — список привязок с «− отвязать» и

## 5. API студии

**Новые роуты** (все — JWT admin/skycomposer, `auth.AdminAuth`). Регистрация:
`/studio/api/recipes*` — новые строки в `cmd/server/main.go` рядом с
существующими `/studio/api/*`; роуты под `/studio/api/producers/` (в т.ч.
`…/recipes/copy-universal`) — внутри уже зарегистрированного префиксного
хендлера `ProducerByID` (маршрутизация по сегментам пути, как у
`…/recipes/{recipe_id}`), отдельной строки в `main.go` не требуется:

| Роут | Назначение |
|---|---|
| `POST /studio/api/recipes` | `{good_id, complexity?}` — создать рецепт (штатно создаётся с товаром; роут — для восстановления) |
| `PUT /studio/api/recipes/{id}` | `{complexity}` — сложность (null = вычисляемая) |
| `POST /studio/api/recipes/{id}/components` | добавить пустой компонент (pos = max+1, quantity 1) |
| `PUT /studio/api/recipes/{id}/components/{pos}` | `{good_id?, quantity?}` — поставить составляющую (цикл → 409) / количество |
| `DELETE /studio/api/recipes/{id}/components/{pos}` | удалить компонент (сдвиг pos) |
| `DELETE /studio/api/recipes/{id}/components/{pos}/component` | очистить компонент (товар остаётся в реестре) |
| `PUT /studio/api/recipes/{id}/components/{pos}/allow_resource` | `{allow_resource}` — галка ИИ |
| `POST /studio/api/producers/{id}/recipes` | `{recipe_id}` — привязать рецепт к фабрике (400: не конкретная фабрика / чужой выход; 409: повтор) |
| `DELETE /studio/api/producers/{id}/recipes/{recipe_id}` | отвязать |
| `POST /studio/api/producers/{id}/recipes/copy-universal` | скопировать набор рецептов в конкретную фабрику из **универсальных** фабрик её категории; тело пустое; `200 {added, skipped}`; идемпотентно; 400 — не конкретная фабрика / нет категории / категория ресурсная (детали — ниже) |

**Роут копирования набора рецептов** (решение создателя, идея §8, вариант «а»;
митигация развилки §11.11; UI-элемент — ветка **«Производители»**, ТЗ
@uidesigner):

- **Источник** — **все универсальные конкретные фабрики той же категории**
  (`producer_types`: `kind='goods'`, `parent_id NOT NULL`,
  `category_id = target.category_id`, `race_family IS NULL`, `race IS NULL`),
  **кроме самой цели**; их может быть несколько («Фабрика X» и «Автофабрика X» —
  правило миграции §3 п.4). Вставка — `INSERT … ON CONFLICT
  (producer_type_id, recipe_id) DO NOTHING` в транзакции под `pg_advisory_xact_lock`
  (`catalogLockKey`), как остальные мутации каталога.
- **Ответ `200 {"added": N, "skipped": M}`:** `added` — реально созданные
  привязки, `skipped` — рецепты источника, уже привязанные к цели (идемпотентно:
  повторный вызов — `added: 0`). Счётчики — для тоста (формулировка — @uidesigner).
- **Пустой источник — не ошибка:** `{"added": 0, "skipped": 0}` (UI скажет
  «нечего копировать»).
- **400:** цель — не конкретная фабрика (`parent_id IS NULL` / `kind != 'goods'` /
  `category_id IS NULL`) или её категория **не товарная**
  (`categories.kind != 'good'`) — у ресурсной фабрики рецептов не существует.
- **Инвариант «выход = категория фабрики» (§2.4) соблюдается по построению:**
  категория источника = категория цели, копируются только привязки этой категории
  — «чужой выход» на этом пути невозможен (доп. проверок не требуется).
- **Реализация:** `producer_repository.go` — метод вида
  `CopyUniversalRecipes(targetID) (added, skipped int, err error)`; в ветке
  «Товары» кнопки нет.

**Существующие роуты — сносятся** (решение §11.5): `POST /goods/{id}/slots`,
`PUT|DELETE /goods/{id}/slots/{n}`, `DELETE /goods/{id}/slots/{n}/component`,
`PUT /goods/{id}/slots/{n}/allow_resource`, `PUT /goods/{id}/tier`.
Причина: адрес кодирует неверную модель («слоты принадлежат товару») и создаёт
вторую запись того же действия. Отклонённая альтернатива — оставить алиасами
(быстрее, но два имени одного действия).

**`GET /studio/api/state`** — аддитивно:

- `GoodView`: `+ recipe_id` (id рецепта), `+ complexity` (сложность рецепта),
  `+ bound_factories: [producer_type_id]` (обратная привязка — для маркера
  «в наборе фабрики» / «не привязан»); `tier_override` **удаляется** (поля
  `tier`/`tier_computed` остаются, `tier` = `complexity ?? вычисленный`);
  `recipe` (состав) остаётся проекцией `recipe_components`.
- Новый верхнеуровневый `producer_recipes: [{producer_type_id, recipe_id,
  good_id}]` — привязки (для селектора, фильтра семейства, маркеров).
- Отдельный массив `recipes` **не вводится**: рецепт сейчас 1:1 с товаром
  (`recipe_id`/`complexity` в `GoodView`); при альтернативных рецептах появится
  `recipes[]` (аддитивно).
- `SlotView` остаётся (состав), источник — `recipe_components`.

**Влияния на существующие хендлеры/репозитории:**

| Место | Правка |
|---|---|
| `goods_repository.go` `Snapshot`/`loadSlots` | читает `recipes`/`recipe_components`/`producer_recipes`; собирает проекцию `Good.Recipe`, `Good.Complexity` и **список привязок** для `model.State`. Пакеты `graph`/`validate`/`ai` читают только проекцию (БД не видят) |
| `CreateGood` / `BulkCreateGoods` / `ApplyProposals` | вместе с товаром создают рецепт (пустой состав: один пустой компонент, как сейчас `goods_slots (good_id,0,1)`) |

### 6.1. Дельта спеки фабрик (`2026-09-20-фабрики-сущность-производства.md`)

**§4.1 (kind=goods):**
> ~~«тип привязан к категории… рецепты товаров категории — цепочка типа»~~ →
> «**Фабрика держит набор рецептов** (`producer_recipes`): конкретная
> фабрика-подтип (kind=goods) привязывает **подмножество** рецептов своей

> (один рецепт) может быть привязана к нескольким фабрикам (человеческой,

**§4.3 (фильтры):**
> «„Какие производители потребляют товар X“ — обратный: типы производителей, у

> помечаются в справочнике студии (не контент производства).»

**§6.1 (снабжение):**
> «**расходники по рецепту** — для товаров: компоненты рецепта, привязанного к

**Релиз 2 (buildings/снабжение) — влияние:**
- Экземпляр строения получает набор рецептов **от своего типа**
  (`producer_recipes`); вопрос «держит ли экземпляр подмножество (программа
  производства)» — **решается в релизе 2** (в этой спеке не проектируется).
- Снабжение считается по компонентам рецептов, которые экземпляр **реально
  ведёт**; `goods_slots` в формуле больше не участвует.
- `items.unlocks` (предмет-рецепт): структура **не меняется** —
  `[{producer_type_id, category_id}]`; предмет разблокирует **категорию** на
  типе, набор рецептов типа определяет, что реально производимо (решение
  §11.10, принято; отклонённая альтернатива — привязка `unlocks` к конкретным
  рецептам: предмет на каждый рецепт, меняется смысл модернизации).

## 7. Что НЕ входит

- **Альтернативные рецепты** (несколько на один товар) — схема готова
  (`UNIQUE (good_id)` снимается простой миграцией), сейчас — жёстко один.
- **Рецепты предметов** (лаборатории, `producer_items.requirements`) — другая
  механика, в таблицу рецептов не смешиваются.
- **Релиз 2**: `buildings`, владельцы, население строений, снабжение,
  производственная программа экземпляра, логистические затраты.
- **Игровое влияние сложности** (сложность — данные, не гейт; спека фабрик §8.2).
- Экспорт/импорт каталога; ИИ-fill для производителей/рецептов (fill остаётся
  для состава товара); ИИ-предложение новых рецептов.
- Голоса/личности рас, лор-контент; числа баланса.
- Терминологическая правка GLOSSARY/GDD — выполняется при сдаче (§6.4), не в
  этой задаче.
- Смежная идея «самая конкретная фабрика» (авто-согласование, закрытие попапа) —
  отдельная задача, от этой не зависит.

## 8. Риски

1. **Номер миграции:** в `migrations/` на 2026-09-21 последняя — **`000054`**
   (снятие согласования каталога); наша — **`000055`** (сверено по `migrations/`).
   Перед разработкой сверить рабочее дерево ещё раз (правило проекта: номер
   может уехать).
2. **`recipes` — каталог-контент:** в `truncateTables` (`admin_universe.go` 59)
   **НЕ добавляется**; FK на `worlds`/`planets` нет → каскады пакмана не
   затрагиваются (как `categories`/`goods`/`producer_*`).
3. **Не-регресс ИИ-fill:** `ApplyProposals` создаёт товары **без** `goods_slots`
   (проверено: слот создаётся только `CreateGood`/`BulkCreateGoods`) — при
   переходе рецепт для ИИ-товара обязан создаваться, иначе товар останется без
   рецепта и `recipe_id` в state будет пустым.
4. **Не-регресс валидаторов графа:** `validate.Validate` и `graph.Tier`/
   `WouldCreateCycle` читают `model.Good.Recipe` — проекция обязана заполняться
   в `Snapshot` и `snapshotState` (иначе тиры «схлопнутся» в 0, цикл-проверка
   ослабнет).
5. **Витрина «Ресурсы»** (`admin_resources`, `props ? 'closes'/'family'`) —
   читает только `kind='resource'`; рецепты её не касаются. Правка — не нужна
   (проверить на прогоне).
6. **`tier_override` → сложность:** потеря оверрайдов у ресурсов (§3, §11.2).
7. **UI-объём:** переписывание роутов слотов и попапа товара (вариант А §11.5) —
   крупнейшая часть работы; митигация — проекция `Good.Recipe` в state, из-за
   которой граф/канвас правятся минимально.
8. **Тесты:** sqlmock-ожидания на `goods_slots`/`tier_override` в четырёх
   тест-файлах — переписываются вместе с репозиторием (TDD: красный до, зелёный
   после).
9. **Решение §11.1 — вариант А (Go-only), вариант Б не выбран:** составного FK
   (`recipes.category_id`) и связанного дрейфа при смене категории товара **нет**;
   оставлено справкой, в работе не участвует.
10. **e2e-смоук `tools/e2e/goods-studio-server-check.js` — не-регресс.** Файл

    (`buildStateView` 192, `Validate`-хендлер 1395, `snapshotState` 1347); если
    хотя бы один не заполнить — warning не сработает или граф «схлопнется».
12. **Новая механика канваса (drag&drop = привязка) vs пан/зум.** Канвас сегодня
    drop-обработчиков **не имеет** (`web/studio.html` 1019–1021) — перетаскивание
    (§4.4) это **новая функциональность**; её обработчики
    (`dragover`/`dragleave`/`drop` на `#canvasWrap`) пересекаются с
    панорамированием/зумом и с drop в слоты попапа. Проверить **на прогоне**:
     пан/зум не ломаются, drop в слоты попапа работает, **без выбранной фабрики
     drop даёт тост-подсказку «выберите фабрику» и не отправляет запрос**,
     бросание на карточку/фон без побочных эффектов. Детали —
     ТЗ @uidesigner §7.3.

## 10. Отложенный кандидат ГД-сущности (в задачу НЕ входит)

**Вопрос:** рецепт сейчас даёт **один** выход. Не сделать ли у рецепта
**побочный выход** (сопродукт/отход) — вторую позицию, которая получается вместе
с основной?

**Ответ (кандидат на решение создателя):** **побочный выход рецепта** —
у рецепта, кроме основного выхода, может быть побочный (например, отход
переработки, шлак, побочный газ). Даёт игровое решение «что делать с побочным»:
продать, пустить в следующую цепочку (переработка отходов), выбросить за плату —
и создаёт спрос на «мусорные» цепочки и утилизацию. Модель к нему готова:
рецепт — сущность, выход у него — поле, расширяемое до списка выходов (при этом
основной выход остаётся «категория фабрики» — инвариант сохраняется). Цена
введения: снимается «один выход = один товар», `UNIQUE (good_id)` уступает
месту списку выходов — это тот же класс изменений, что альтернативные рецепты
(отложены).

**Статус:** **отложено до отдельного решения создателя** (гейт 2026-09-21: «в эту
задачу не входит»). Не «открытый вопрос гейта» — гейт пройден; кандидат ждёт
своего разговора. В текущие числа/схему **НЕ входит** (анти-двойной учёт).

|---|---|---|

| 11.3 | Рецепт создаётся **всегда вместе с товаром** (1:1 сейчас) | лениво при привязке — «ничей» товар без рецепта неотличим от пустого состава |

## 12. Итоговая сводка ключевых решений

1. **Модель:** `recipes` (выход-товар + сложность, `UNIQUE (good_id)`),
   `recipe_components` (замена `goods_slots`), `producer_recipes` (M:N
   «фабрика ↔ рецепты»); миграция **`000055`** (создание + перенос + DROP
   `goods_slots`/`tier_override`).
2. **Инвариант:** выход рецепта — всегда категория фабрики (Go 400); рецепт
   привязывается только к конкретной фабрике (подтип kind=goods).
3. **Товар — общий материал:** один рецепт — несколько фабрик; категория —
   классификация товаров; ресурсы — общий пул (`goods kind='resource'`).
4. **Сложность** — поле рецепта; тир товара производный; `goods.tier_override`
   снят.
5. **Студия:** селектор фабрики на «Товарах» (граф замыкания вниз, несвязный
   допустим; фабрики ресурсных категорий исключены) + фильтр справочника по
   семейству рас (канон «самая конкретная побеждает» на существующих правилах
   видимости/скрытости — обе оси).
6. **Дельта спеки фабрик:** фабрика держит **набор рецептов** (подмножество
   категории); снабжение релиза 2 — по компонентам рецептов; `items.unlocks`
   без изменений структуры.
7. **Инвариант «выход = категория» — с обеих сторон:** смена категории товара
   (при привязанном рецепте) и смена категории фабрики (при привязанных
   рецептах) → 409 до отвязки.
8. **UI-объём (гейт UI-дизайна, идея §8):** перетаскивание карточки справочника на
   канвас = привязка рецепта (**новая** механика канваса, §4.4) + роут
   `POST /producers/{id}/recipes/copy-universal` — копирование набора рецептов из
   универсальных фабрик категории (§5); детали взаимодействия — ТЗ @uidesigner.

пройден 2026-09-21 (идея §8; итерация 3 — §1) и передана в разработку; закрытие
