## 0. Резюме (одним абзацем)

Ветка «Производители» студии товаров получает **дерево построек на канвасе**
(как граф товаров: уровни-ряды, карточки, орто-рёбра, pan/zoom, клик = выбор,
двойной клик = попап детали типа — существующий `renderProdPopup`): 4 уровня —
**Строения** (корень) → **Классы** (Производители товаров/предметов/энергии,
Другие — фиксированные узлы) → **Типы** (записи `producer_types` без родителя:
Поселение, Фабрика, Автофабрика, Добывающая платформа, Лаборатория,
Энергостанция) → **Подтипы** (записи с родителем: Фабрика продовольствия,
лаборатории; плюс **автоматика категорий** — под Фабрикой/Автофабрикой/
Добывающей платформой раскрываются категории товаров/ресурсов, незаведённая
категория — узел-приглашение «создать»). В модель `producer_types` добавляется
поле **базового типа** `parent_id` (подтип → тип-родитель) и второй уровень
расовости `race` (семейство F0–F10 **и** конкретная раса 60 рас каталога;
названия фабрик и цепочки — данные каталога, не код). Три лаборатории
переименовываются по решению создателя (связи `producer_items` сохраняются).
Числа баланса не трогаются. Релиз 2 фабрик (buildings, владельцы, население) —
вне скоупа.

## 1. Модель и БД

### 1.1. Природа сущности (архитектурный фильтр)

1. **Базовый тип / подтип** — **атрибут** существующей сущности `producer_types`
   (справочник, лог/состояние), не новая таблица: правило «сущность с двумя
   экземплярами — не сущность» работает в обе стороны — не плодим таблицу
   «подтипов» ради одного поля.
2. **Владелец** — у многих типов: любой тип может иметь подтипы (Фабрика,
   Автофабрика, Платформа, Лаборатория) — расширяемость заложена самим полем.
3. **Расширяемость** — схема переживает второй уровень расовости (`race`),
   второй родительский тип и произвольное число подтипов. Глубина дерева
   фиксирована (тип → подтип, не глубже) — осознанное ограничение: дерево
   построек 4 уровня по решению создателя (идея §2 п.2).

### 1.2. Миграция `000051` (свободный номер: 000049/000050 — чужие)

```sql
-- 1) Базовый тип (родитель): подтип ссылается на тип-родителя.
ALTER TABLE producer_types ADD COLUMN parent_id BIGINT NULL
    REFERENCES producer_types (id);
-- 2) Второй уровень расовости: конкретная раса (id из config/races.json).
ALTER TABLE producer_types ADD COLUMN race TEXT NULL;
```

Семантика полей:

| Поле | Смысл |
|---|---|
| `parent_id` NULL | **тип** (узел уровня 3 дерева: Поселение, Фабрика, Автофабрика, Добывающая платформа, Лаборатория, Энергостанция) |
| `parent_id` NOT NULL | **подтип** (узел уровня 4: «Фабрика продовольствия» → Фабрика; «Лаборатория космических технологий» → Лаборатория) |
| `race_family` | семейство (F0–F10 / NULL = универсальный) — существующее поле, без изменений |
| `race` | конкретная раса (id: humans, oceanids, sulfur_swarms, …) / NULL; задана → `race_family` обязана быть задана и соответствовать семейству расы по `config/race_lore.json` |

**Инварианты (валидация в студии, Go-слой — как существующая проверка
kind=goods → category_id):**

1. `parent_id != id` (тип не может быть родителем сам себе).
2. **Глубина 1:** `parent_id` обязан указывать на запись с `parent_id IS NULL`
   (подтип подтипа запрещён).
3. **kind наследуется:** kind подтипа = kind родителя (Фабрика продовольствия
   kind=goods, родитель Фабрика kind=goods).
4. **Категория только у подтипов kind=goods:** у типа (parent_id NULL) с
   kind=goods `category_id` = NULL (тип абстрактен); категория — у подтипа
   («один тип фабрики — товары одной категории», спека фабрик §4.1).
   **Дельта (2026-09-21, спека скрытых):** категория подтипа kind=goods
   возможна **только при применяемом слоте родителя** (`producer_slots`,
   миграция 000052): создание/смена категории без слота → 400 «категория не
   настроена у родителя на этом уровне»; удаление слота при заводах → 409.
5. **Уникальность подтипа:** не существует второй записи с тем же
   `(parent_id, category_id, race_family, race)` — проверка в Go (409), как
   дубликат имени. Глобальный `UNIQUE(name_norm)` остаётся: имена типов —
   одно пространство имён (как у товаров); две расы не могут завести тип с
   одинаковым именем — осознанное ограничение модели.
6. **Раса → семейство:** `race` задана → `race_family` = family этой расы из
   `config/race_lore.json` (валидация по каталогу рас, §3).
7. **Удаление родителя** — RESTRICT: тип с подтипами не удаляется (в студии
   сообщение «сначала удалите подтипы»); каскад запрещён — случайный снос
   Фабрики не должен уносить все фабрики категорий.

### 1.3. Data-миграция (в `000051`, после ALTER)

Сид `producer_catalog_seed` уже отработал на существующих БД (маркер) — правки
каталога для текущих БД делает **data-миграция**, для свежих — обновлённый сид
(§1.4). Оба пути дают одинаковый результат. Все UPDATE — по `name_norm`
(устойчиво к переименованиям в студии: запись не найдена → пропуск, не падать).

1. **Создать тип «Лаборатория»** (kind=items, parent NULL) —
   `INSERT ... ON CONFLICT (name_norm) DO NOTHING` (если уже заведена вручную).
2. **Переименовать лаборатории** (решение создателя, идея §2 п.4):
   - «Лаборатория корабельных модулей» → **«Лаборатория космических технологий»**;
   - «Лаборатория инструментов игрока» → **«Лаборатория экипировки»**;
   - «Лаборатория исследовательская» → **«Исследовательская лаборатория»**.
   Связи `producer_items` не трогаются (связи по id, переименование их не
   затрагивает): «Лаборатория космических технологий» производит «Модуль
   корабля», «Лаборатория экипировки» — «Кирку», «Исследовательская
   лаборатория» — «Чертёж» + «Сертификат анализа» (маппинг подтверждается
   на гейте, идея §3 п.6).
3. **Проставить `parent_id`:**
   - три лаборатории → id типа «Лаборатория»;
   - «Фабрика продовольствия» (создана создателем) → id типа «Фабрика».
4. **«Добывающая платформа» — сбросить `category_id` в NULL** (она становится
   чистым типом уровня 3; категория «Минералы» из сида была «сид-приближением,
   студия уточняет» — по новому дереву категории живут в подтипах-платформах,
   §2.2). Подтип «Платформа минералов» не создаётся — остаётся
   узлом-приглашением, как остальные 5 ресурсных категорий.

### 1.4. Сид `seed_producers.go`

Обновить структуру `seedProducer`: добавить поле `Parent` (имя типа-родителя,
"" = NULL). В `seedProducers`:
- добавить тип «Лаборатория» (kind=items);
- переименовать три лаборатории в новые имена (как §1.3 п.2);

INSERT в `producer_types` дополняется колонками `parent_id`/`race` (NULL по

## 2. Дерево на канвасе (ветка «Производители»)

### 2.1. Структура (4 уровня, фиксированная)

```
Строения                                    ← корень (фиксированный узел UI)
├── Производители товаров (kind=goods)      ← класс (фиксированный узел UI)
│   ├── Поселение                           ← тип (parent_id NULL)
│   ├── Фабрика                             ← тип
│   │   ├── Фабрика продовольствия          ← подтип (запись; категория продовольствие)
│   │   ├── Фабрика топлива                 ← узел-приглашение «создать» (автоматика)
│   │   └── … 11 категорий товаров          ← автоматика (13 товарных категорий)
│   ├── Автофабрика                         ← тип; раскрытие по категориям (развилка §6.1)
│   └── Добывающая платформа                ← тип; раскрытие по ресурсным категориям (развилка §6.2)
├── Производители предметов (kind=items)    ← класс
│   └── Лаборатория                         ← тип
│       ├── Лаборатория космических технологий  ← подтип
│       ├── Лаборатория экипировки              ← подтип
│       └── Исследовательская лаборатория       ← подтип
├── Производители энергии (kind=energy)     ← класс
│   └── Энергостанция                       ← тип (лист)
└── Другие                                  ← класс-задел (пустой узел, §6.4)
```

> **Дельта 2026-09-25:** структура ниже — на момент 2026-09-21. Уровни **«Строения»**
> (корень) и фиксированные **классы** («Производители товаров/предметов/энергии»,
> «Другие») в UI **сняты**: первый ряд дерева — карточки **типов-корней** активного
> **раздела** (`producer_types.section`: Колонии · Фабрики и автофабрики · Лаборатории ·
> Добывающие платформы · Энергостанции + служебный «Прочее»). Модель `parent_id`
> (тип → подтип, глубина 1) **не менялась** — снят только фиксированный UI-каркас.

### 2.2. Правила построения

- **Корень и классы** — фиксированные узлы UI (не записи БД, не редактируются):
  «Строения», «Производители товаров» (kind=goods), «Производители предметов»
  (kind=items), «Производители энергии» (kind=energy), «Другие».
  **Снято дельтой 2026-09-25** (см. §2.1): в UI этих узлов больше нет — первый ряд
  дерева образуют типы-корни активного **раздела** (`section`).
- **Типы** — записи `producer_types` с `parent_id IS NULL`, разложенные по
  классам через `kind`.
- **Подтипы** — записи с `parent_id NOT NULL`, под своим типом-родителем.
- **Слоты категорий (конфигурация, дельта 2026-09-21 — спека скрытых
  `2026-09-21-студия-скрытые-категории-строений`):** автоматика категорий
  (привязка к имени типа) **заменена** конфигурацией слотов `producer_slots`
  (миграция 000052): под типом kind=goods раскрываются **настроенные** категории
  (база универсального уровня — 13 товарных для Фабрики/Автофабрики, 6 ресурсных
  для Добывающей платформы — из миграции/сида; семейные/расовые переопределения —
  поверх, §2.4). Для каждой категории:
  - есть запись-подтип с этим `parent_id` и `category_id` (и текущим уровнем
    расовости, §2.4) → **существующий узел** (карточка типа, клик → попап);
  - нет → **узел-приглашение** «создать» (пунктирная карточка, как
    плейсхолдеры слотов в графе товаров), клик → попап создания (§2.3).
  Скрытый слот (`hidden=true`) — категория не показывается (ни карточка, ни
  приглашение). **Дельта 2026-09-25 (вариант «б»; канон — спека скрытых
  `2026-09-21-студия-скрытые-категории-строений` §2.2 п.2):** при галке
  «показать скрытые» показываются **только скрытые записи и победитель
  лестницы** (затемнённые), видимые менее конкретные записи **не показываются**;
  записей нет — затемнённая карточка-заглушка категории. Категория вне набора
  слотов на уровне не рисуется вовсе.
- **Листья без слотов** — Поселение, Энергостанция, Лаборатория (подтипы
  заводятся вручную через «+ тип» в списке или попап типа).

### 2.3. Узел-приглашение «создать»

Клик по узлу-приглашению открывает попап создания записи `producer_types`
(тот же механизм, что `renderProdPopup`, в режиме создания) с предзаполнением:
`name` = «<Имя родителя> <имя категории>» (напр. «Фабрика топлива»),
`kind` = kind родителя, `category_id` = категория узла, `parent_id` = тип-родитель,
`race_family`/`race` = текущий уровень расовости (§2.4). Подтверждение —
`POST /studio/api/producers` (статуса нет — согласование снято, дельта
2026-09-21, миграция 000054). После создания узел
становится существующим; имя можно переименовать в попапе.

### 2.4. Расовость: два уровня в дереве

Дерево показывается для выбранного **уровня расовости** (переключатель в шапке
ветки, §5): **универсальный → семейство (F0–F10) → конкретная раса (60)**.
Правило видимости записи при выбранном уровне:

| Уровень | Видны записи с |
|---|---|
| Универсальный | `race_family IS NULL` |
| Семейство Fk | `race_family IS NULL` **или** (`race_family = Fk` **и** `race IS NULL`) |
| Раса R | `race_family IS NULL` **или** (`race_family = family(R)` **и** `race IS NULL`) **или** `race = R` |

**Канон «самая конкретная побеждает» (дельта 2026-09-21, спекa
`2026-09-21-студия-производители-лестница-предложения` §5):** на уровне расовости
побеждает самая конкретная ступень — раса → семейство → универсальная; на уровне
семейства расовые записи **не видны** (`race IS NULL`, вариант А), видимые
лосеры не рисуются. Универсальные **типы/подтипы** видны на всех уровнях (общие
для всех рас), **кроме** уровней, где запись/слот скрыты (`hidden=true`, спека
`2026-09-21-студия-скрытые-категории-строений` §2: самая конкретная применяемая
запись/слот решает — скрыта → категория не показывается, ни карточка, ни
узел-приглашение). Видимость по расовости (§2.4) и скрытость (hidden) — две оси,
применяются одновременно (AND).

### 2.5. Рендер и взаимодействие

- Переиспользуются общие механики канваса студии: pan/zoom (wheel),
  hitTest-карточки, тултип, клик = выбор, двойной клик = попап детали типа
  (`renderProdPopup`), сохранение вида (zoom/pan в localStorage).
- Раскладка — свой лейаут (не `computeLayout` графа товаров: структура
  фиксированная, 4 уровня-ряда): карточки уровней, орто-рёбра (как
  `orthoEdge`), константы CARD_W/CARD_H/GAP_X/ROW_GAP — общие.
- `renderGraph()` переключается по ветке: goods → граф товаров (как сейчас);
  producers → дерево построек. `applyBranchUI`: канвас показывается и в ветке
  «Производители» (сейчас скрыт).
- Правая панель в ветке «Производители» остаётся: список типов
  (`renderProdSprav`) + поиск + «+ тип» (существующие) — клик по карточке
  списка выбирает узел в дереве. Дерево — основной инструмент («список справа

## 6. Развилки: решения и варианты на гейт

### 6.1. Автофабрика — раскрытие по категориям товаров

**Решение: да, раскрывается** (13 товарных категорий, автоматика как у
Фабрики). Обоснование: автофабрика — вид фабрики (спека фабрик §1/§4.1,
«входит в производители товаров»), «один тип фабрики — товары одной категории»
применим; подтипы автофабрики — записи `parent_id=Автофабрика` + `category_id`.
На гейт — подтверждение (альтернатива: автофабрика — лист без категорий, но
тогда теряется «фабрика категории» для роботов).

### 6.2. Добывающая платформа — раскрытие по категориям ресурсов

**Решение: да, раскрывается** по 6 ресурсным категориям (Минералы, Органика,
Редкие, Топливо, Вода, Газы — kind=resource). Обоснование: платформа —
производитель сырья (спека фабрик §1), сырьё — позиция каталога kind=resource;
подтипы «Платформа минералов» и т.д. — записи `parent_id=Платформа` +
`category_id` (ресурсная категория). На гейт — подтверждение (альтернатива:
платформа — лист, категория остаётся у типа — но это противоречит инварианту
§1.2 п.4 «категория только у подтипов»).

### 6.3. Хранение расовости двух уровней (семейство + раса)

Варианты:

- **А. Два поля `race_family` + `race`** (выбран): существующее поле
  `race_family` сохраняется без изменений (обратная совместимость с БД/UI),
  добавляется `race` (id расы). Инвариант «раса → семейство» проверяется по
  каталогу рас. Цена: одно новое поле + валидация соответствия.
- **Б. Одно поле `race`** (универсальный = NULL, семейство = спец-код «F1»…,
  раса = id): меньше полей, но семейство и раса в одном поле — неоднозначность
  («F1» — это семейство или раса с id F1?), ломает существующее поле
  `race_family` в БД/UI/попапе. Отклонено.
- **В. Иерархия через `parent_id`** (расовые типы — подтипы универсальных):
  смешивает две оси (типология построек и расовость) в одном дереве,
  ломает автоматику категорий и глубину 4 уровней. Отклонено.

**Источник списков семейств/рас** — варианты: (а) Go-конфиг через новый
эндпоинт `/studio/api/races` (выбран: `internal/races` уже держит каталог,
один факт — одно место); (б) БД-таблица — дублирует `config/races.json`,
отклонено; (в) захардкодить в JS — дублирование, отклонено.

### 6.4. «Другие» — пустая ветка-задел или скрыть

**Решение: показывать пустой веткой-заделом** (узел «Другие» с пометкой
«задел», без типов). Обоснование: создатель нарисовал «Другие (задел; типы
появятся позже)» в структуре дерева (идея §2 п.2) — узел виден, дерево
показывает полную картину классификации построек. `kind` для «других» НЕ
расширяется (CHECK остаётся goods/items/energy): типы «других» (ретранслятор
и пр.) появятся позже — тогда и решится их модель (отдельная задача).
На гейт — подтверждение.

### 6.5. Классы «Производители…» и корень «Строения» — фиксированные узлы

**Решение: да, фиксированные** (не записи БД, не редактируются, не удаляются).
Обоснование: классификация из спеки фабрик §2 (Строение → Производитель →
класс выхода) — константа дизайна, не контент. На гейт — подтверждение.

**Снято дельтой 2026-09-25:** фиксированные узлы в UI **убраны** — дерево строится
по разделам от типов-корней (спека `2026-09-25-студия-разделы-построек-по-видам.md`).
Классификация из спеки фабрик §2 остаётся дизайн-моделью, но её носитель в студии —
поле `producer_types.section` (миграция `000085`), а не узлы-классы.
