## 0. Резюме (одним абзацем)

Разворот создателя (2026-09-21): **согласование как класс убирается** — статусы
`draft/approved/excluded` снимаются у товаров, ресурсов, производителей и
предметов (у категорий статуса не было — §2.2); всё заведённое «живое».
Остаётся **один обратимый флаг «скрыто»** (`hidden`, бывшее «забанено»),
причём — **уточнением создателя 2026-09-21** — он есть **только у записей
производителей** (`producer_types.hidden` — скрытость **записи-фабрики**) и на
**слоте** (`producer_slots.hidden` — скрытость **категории** на уровне
расовости). У товаров (`goods` kind=good), ресурсов (`goods` kind=resource) и
предметов (`items`) скрытия **нет** ни в каком виде — «убрать» такое можно
**только удалением** (с очисткой ссылок — уже есть); их колонки статуса
снимаются **без замены флагом**. Это **переоткрывает** решение спеки скрытых
(«одна ось», §1.4 п.6) **только для `producer_types`** — §1.5, дельты §12.
Сохраняется **инвариант «не дублировать неудачное»** — **про фабрики**: скрытая
запись-фабрика занимает своё имя (уникальность имён — **внутри своей таблицы**,
не зависит от `hidden`); у товаров/ресурсов/предметов уникальность имён
остаётся, но скрытия нет. Существующий контент становится «живым» (статуса
больше нет); `producer_types.status='banned'` → `hidden=true`. Валидатор
`non_approved_ref` удаляется; `incomplete_chain` снимается (причина — §4.3 п.2,
честно); требование «вес/объём у товара» заменено **дефолтом 1/1** (`volume`/
`weight NOT NULL DEFAULT 1`, миграция NULL → 1) — предупреждение
`missing_volume_weight` остаётся, но не срабатывает (Р2). Канон **«самая
конкретная побеждает»** сохраняется **без фильтра по статусу**: участвует всё
живое; скрытая самая конкретная **запись-фабрика** скрывает категорию на
уровне — симметрично скрытому слоту (**Р1**, вариант 1). Единая применяемость
уровня семейства (вариант А, Р5) сохраняется. Р6 (ИИ не предлагает скрытое) у
товаров **вырождается** — носителя скрытия нет, правила `ai/` удаляются (§4.1,
§8, §16 п.9). Пункты 1–2 прежней редакции (закрытие попапа по «Согласовать»,
авто-«согласовано») **отменены** — «Согласовать» не существует. Новых
сущностей нет; одна миграция DDL+data. Числа баланса, game-логика релиза 2,
рецепты — вне скоупа.

## 1. Разворот создателя — что именно меняется

### 1.1. Согласование снимается везде

- **Класс «согласование»** (`draft` / `approved` / `excluded`) убирается
  **везде в студии**: товары/ресурсы (`goods`), производители
  (`producer_types`), предметы (`items`). Категории (`categories`) статуса
  **не имели** (миграция `000045` — колонки нет) — §2.2.
- **Всё заведённое — «живое».** Нет «черновика, который не в игре» и нет
  «согласованного контента»: запись существует → она контент.
- Отсюда **отменяются** пункты 1–2 прежней редакции: кнопка «Согласовать»,
  закрытие попапа по ней, авто-`approved` при создании (§1.4).

### 1.2. Один обратимый флаг «скрыто» — только у записей-фабрик + слот (уточнение 2026-09-21)

| Ось | Носитель | Смысл |
|---|---|---|
| **Скрытость записи-фабрики** | `producer_types.hidden` | «запись-производитель скрыта»: не показывать по умолчанию, не предлагать (лестница) |
| **Скрытость категории на уровне** | `producer_slots.hidden` | «родитель предлагает категорию на уровне расовости, но скрыто на этом уровне» |

- **У товаров/ресурсов/предметов скрытия НЕТ** (ни `status`, ни `hidden`):
  `goods` (kind=good и kind=resource) и `items` — «убрать» можно **только
  удалением** (существующий `DELETE` с очисткой ссылок). Их колонки статуса
  снимаются миграцией **без замены флагом** (§3).
- **Обратимость:** снять флаг у записи-фабрики — один клик («показать»); при
  этом ничего не теряется (запись, её имя и связи целы).
- **Терминология:** «скрыто **на записи-фабрике**» и «категория скрыта **на
  уровне**» — разные вещи; не смешивать (§2.3; дельта GLOSSARY — §1 «Скрыто
  (студия)», §12).
- **`banned_at`** (метка времени бана) **не переносится**: он был только у
  `goods`; там скрытия нет, колонка снимается, её потребитель (сортировка
  списка «бан — новые сверху», `studio_handlers.go` 264–271) и сам список «бан»
  удаляются. Полный список точек — §4.5.

### 1.3. Убрать лишнее — удалением

- Механика удаления с очисткой ссылок **уже есть** (`DELETE` с `cleared_links`,
  второе подтверждение при `cleared_links > 0`) — не меняется.
- **Скрытие — не способ «начать заново» (правило про фабрики):** скрытая
  **запись-фабрика** занимает своё имя. **Инвариант «не дублировать
  неудачное»:** `UNIQUE (name_norm)` действует **внутри каждой таблицы**
  (`goods`, `producer_types`, `items` — три отдельных индекса,
  `000045`/`000048`) и **не зависит от `hidden`** — второй «Сталь»
  (`producer_types`) завести нельзя, пока первый скрыт, а не удалён. Для
  подтипов-фабрик аналог — `UNIQUE NULLS NOT DISTINCT (parent_id, category_id,
  race_family, race)` (уже есть, `000052`).
- **У товаров/ресурсов/предметов** уникальность имён — та же, но скрытия нет:
  «убрать неудачное» здесь = удалить (иного состояния, кроме «живого», нет).

## 2. Модель данных

### 2.1. Три таблицы: `status` → `hidden`, вес/объём — 1/1

| Таблица | Было | Стало |
|---|---|---|
| `goods` (товары и ресурсы) | `status TEXT DEFAULT 'draft' CHECK (draft/approved/excluded/banned)`, `banned_at TIMESTAMPTZ` | **обе колонки снимаются без замены**: скрытия у товаров/ресурсов нет, «убрать» — удаление |
| `producer_types` | `status TEXT DEFAULT 'draft' CHECK (...)` (и `hidden` первой волны, снятый `000052`) | `hidden BOOLEAN NOT NULL DEFAULT false` (статус снимается, `hidden` возвращается — К1; скрытие **только здесь**) |
| `items` | `status TEXT DEFAULT 'draft' CHECK (...)` | **колонка снимается без замены**: скрытия у предметов нет, «убрать» — удаление |
| `goods.volume`, `goods.weight` | `DOUBLE PRECISION NULL` (`000048`); `UpdateGood` пишет значение, `NULL` = «не задано» | `NOT NULL DEFAULT 1` у **всех** строк (`UPDATE ... SET 1 WHERE NULL`); новые строки получают 1 из `DEFAULT` (Р2, §4.4) |

`hidden=false` — «живое и видимое»; `hidden=true` — «живое, скрытое» (только
`producer_types`). `DEFAULT false` означает: любой прямой `INSERT`
(миграции, будущие булк-пути) родит **живую видимую** запись-фабрику —
расхождение «сид vs ручное создание» (находка v1 §1) снимается по построению.
У товаров/ресурсов/предметов состояния скрытия нет вовсе: запись существует →
она живая и видимая, удаление — единственный способ её убрать. `DEFAULT 1` у
веса/объёма — то же для данных груза.

### 2.2. Категории — статуса не было

Миграция `000045` создала `categories` **без** колонки статуса. Класса
«согласование категорий» в БД не существует → **в этой фиче у категорий ничего
не снимается**. Категория удаляется через очистку ссылок (существующий
`DELETE`), «скрытие категории» живёт **на слоте** (§2.3). Пометка, чтобы
будущий читатель не искал несуществующую колонку.

### 2.3. Слоты — вторая ось (К1), не меняется по механике

`producer_slots.hidden` (`000052`) — **другая ось**: «родитель предлагает
категорию, но скрыто на этом уровне расовости». Не путать с
`producer_types.hidden` («скрыта сама **запись-фабрика**»); у `goods`/`items`
скрытия нет (§1.2). Разведение — дельта GLOSSARY §1 («Скрыто»).

### 2.4. Инвариант имени сохраняется (по таблице)

`UNIQUE (name_norm)` — **отдельный индекс в каждой таблице** (`goods`,
`producer_types`, `items`); **не трогается** и не делается частичным
(`WHERE NOT hidden`). Формулировка «глобальная» (v2 §1.3/§9 п.4) — неточная
(M5): уникальность действует **в пределах таблицы**, между таблицами она не
сквозная (товар «Сталь» и тип «Сталь» сосуществуют). Скрытие имён не
освобождает: у `producer_types` скрытая запись держит имя (§1.3); у
`goods`/`items` скрытия нет, поэтому частичный индекс (`WHERE NOT hidden`)
неприменим в принципе. Проверка в Go (`graph.NormalizeName`) и обработка 409 —
как сейчас.

## 3. Миграция `000054`

**Номер `000054`** (рабочее дерево: последняя — `000053`, сверено 2026-09-21;
`000055` заявлена спекой рецептов — §12). Перед созданием файла сверить рабочее
дерево (`docs/PITFALLS.md`, «Номер миграции может быть занят»); при конфликте
взять следующий свободный (Р4).

Содержание (одна миграция, `000054_catalog_hidden.sql`):

```sql
-- 1) producer_types: статус-класс → единственный обратимый флаг hidden
--    (скрытие живёт ТОЛЬКО здесь). Колонка hidden первой волны снята 000052 —
--    возвращается (К1, переоткрытие «одной оси» спеки скрытых для записей-фабрик).
ALTER TABLE producer_types ADD COLUMN hidden BOOLEAN NOT NULL DEFAULT false;
UPDATE producer_types SET hidden = true WHERE status = 'banned';
ALTER TABLE producer_types DROP COLUMN IF EXISTS status;

-- 2) goods (товары и ресурсы): статус-класс снимается БЕЗ замены флагом —
--    скрытия у товаров/ресурсов нет, «убрать» = удаление.
ALTER TABLE goods DROP COLUMN IF EXISTS status;
ALTER TABLE goods DROP COLUMN IF EXISTS banned_at;

-- 3) items: то же — статус снимается без замены флагом.
ALTER TABLE items DROP COLUMN IF EXISTS status;

-- 4) volume/weight: значение есть всегда (Р2) — дефолт 1, NULL → 1, NOT NULL.
ALTER TABLE goods ALTER COLUMN volume SET DEFAULT 1;
ALTER TABLE goods ALTER COLUMN weight SET DEFAULT 1;
UPDATE goods SET volume = 1 WHERE volume IS NULL;
UPDATE goods SET weight = 1 WHERE weight IS NULL;
ALTER TABLE goods ALTER COLUMN volume SET NOT NULL;
ALTER TABLE goods ALTER COLUMN weight SET NOT NULL;
```

- `DROP COLUMN` снимает и `CHECK` вместе с колонкой (`status` — `NOT NULL
  DEFAULT 'draft' CHECK (draft/approved/excluded/banned)`); отдельного
  `DROP CONSTRAINT` не нужно. `hidden` — `BOOLEAN NOT NULL DEFAULT false`, свой
  `CHECK` не требуется (значение уже бинарно). `IF EXISTS` — как в `000052`.
- Перенос данных — **только у `producer_types`**: `status='banned'` →
  `hidden=true`. У `goods`/`items` переноса нет: `draft/approved/excluded/banned`
  **все** становятся «живыми» (поля нет — запись просто существует);
  `banned_at` снимается без следа. `draft/approved/excluded` у `producer_types`
  → `hidden=false`.
- **Вес/объём у ресурсов тоже станет 1** (`UPDATE ... WHERE ... IS NULL` без
  `kind`): ресурс объёма/веса как груз не имеет, но колонка одна на `goods`;
  единообразие дешевле исключения (ресурс в граф не въезжает, §4.4).
- **Все пути создания товара колонок `volume`/`weight` не перечисляют**
  (`goods_repository.go` 349/578/1071, сид 119, ИИ) → получают `DEFAULT 1`;
  отдельный код не нужен.
- Категорий миграция **не касается** (§2.2).
- `goods.tier_override`/`goods_slots` — **не трогаем** (зона спеки рецептов, её
  `000055`; порядок двух миграций на `goods` безразличен — разные колонки).
- Свежие БД: `000045`/`000048` создают колонки, эта миграция их снимает/правит —
  итог совпадает со свежим сидом (сид `status` в `INSERT` больше не пишет, §4.1;
  `hidden`/вес/объём — из дефолтов).
- **Сверка `DEFAULT`/`CHECK` перед сдачей:** после `DROP status` ни в `goods`,
  ни в `items`, ни в `producer_types` не остаётся `DEFAULT`/`CHECK`, ссылающихся
  на статус (проверка `\d goods`/`\d items`/`\d producer_types` в отчёте
  @developer); у `producer_types.hidden` — `DEFAULT false` («живая видимая» по
  умолчанию); у `goods`/`items` колонок `hidden` **нет** (проверка в отчёте).

### 4.3. Валидаторы (`validate/validator.go`)

1. **`non_approved_ref` (V3, 75–103) — удаляется целиком.** Проверка «ссылка на
   не-согласованное» без класса согласования смысла не имеет. Тест
   `TestNonApprovedRef*` удаляется.
2. **`incomplete_chain` (V2, 58–73) — снимается (Р3), с честным обоснованием.**
   В v2 было сказано «дублирует `missing_resource`» — **неверно** (M2):
   детекции **разные**.
   - V1 `missing_resource`: `kind != resource` **и** пустой рецепт **и**
     `inDegree > 0` (ссылаются рецепты) — **любой** статус;
   - V2 `incomplete_chain`: `kind != resource` **и** `Status == approved` **и**
     пустой рецепт — **без** условия `inDegree > 0`.
   То есть V2 дополнительно ловила **пустой товар-верхушку** (`inDegree == 0`,
   «заготовка»), которого V1 не ловит. Снятие V2 **убирает проверку пустого
   нового товара** — покрытие после снятия **отсутствует**.
   Почему всё равно снимаем: единственная опора V2 — статус `approved`; без
   статусов её формулировка вырождается в «любой пустой `kind=good`», а пустой
   товар — **штатное состояние создания** (`CreateGood` кладёт один пустой слот,
   §4.1): проверка горела бы на каждом «+ товар» (шум, режим отказа —
   усталость от warning'ов). Новой проверки не вводим.
   **Принято создателем:** пустой товар — «заготовка-намерение», не нарушение.
   Тест `incomplete_chain` удаляется.
3. **`missing_volume_weight` (V5, 125–143) — остаётся, но становится инертной

   → warning не срабатывает. **Статусный страж V5 (`g.Status != StatusApproved`,

### 4.4. Вес/объём: дефолт 1/1 (Р2) — вместо требования «участия в графе»

Было (v2): «`approved` без веса/объёма» → перевязка на «товар, участвующий в

- `missing_volume_weight` **не срабатывает** никогда (§4.3 п.3, §2.1);
- **требований к «участию в графе» больше нет** — и вместе с ними снимается
  зависимость от проекции `Recipe`/набора рецептов рецепт-спеки (риск v2 §8
  F-2 закрыт по существу, §16 п.6);
- миграция: `NULL → 1`, `NOT NULL`; новые товары — 1/1 (§3);
- UI: поля объёма/веса показывают 1 (пустой ввод трактуется как 1 —
  «значение есть всегда»); режим отказа — админ должен вручную поставить
  правдоподобное число, «пустого» состояния нет.

**Почему не варианты v2:** A («вес/объём у любого `kind=good`» — шум warning'ов)
и C («только участвующий в графе» — опора на проекцию рецептов, дырка до
заполнения) **сняты** вместе со требованием: дефолт дешевле и не зависит от
графа.

## 5. Канон «самая конкретная побеждает» (без статусного фильтра)

### 5.1. Применяемость на уровне расовости L (единая ось)

Применяемость **одна и та же** для записей `producer_types`, слотов
`producer_slots` и типов:

| Уровень L | Применяемые записи / слоты |
|---|---|
| Универсальный | `race_family IS NULL` |
| Семейство Fk | `race_family IS NULL` **или** (`race_family = Fk` **и** `race IS NULL`) |
| Раса R | `race_family IS NULL` **или** (`race_family = family(R)` **и** `race IS NULL`) **или** `race = R` |

**Дельта к коду:** уровень семейства больше не видит расовых записей/слотов.
Сейчас `prodVisible` (1889) и `prodSlotVisible` (1916) берут
`race_family === prodRaceFamily` **без** `!race`. После правки — не берут.

Следствия (из v1, сохранены):

1. **Вариант А создателя** — на **обеих** осях (записи и слоты) (Р5).
2. **Ничьи недостижимы:** на (родитель, категория, ступень) не более одной
   применяемой записи (`UNIQUE NULLS NOT DISTINCT`) → `prodMostSpecificSlot`
   (1934) детерминирован.
3. **Расовый ТИП** на уровне семейства тоже не показывается (иначе пустой узел:
   его расовые слоты там не применяются) — Р5.
4. **Универсальные ТИПЫ видны на всех уровнях** — клауза спеки дерева §2.4
   сохраняется (находка 4 критика).

### 5.2. Область лестницы

- Лестница — **только подтипы `kind=goods`** в паре (тип-родитель `kind=goods`,
  категория): у типов (`parent_id IS NULL`) категории нет, у подтипов
  items/energy категорий нет вовсе (находка 1 v1).
- **Типы** и **подтипы items/energy** лестницу не получают: видны **все**
  применяемые записи.
- **Победитель** на уровне L — применяемая запись категории самой конкретной
  ступени: раса → семейство → универсальная.
- **Одна предлагаемая фабрика на категорию**; прочие применяемые записи уровня
  **не предлагаются** (доступ — переключением уровня расовости).
- Записей нет → **узел-приглашение «создать»** (спека дерева §2.3), если
  категория в наборе родителя и **видима** по скрытости (§5.3).

### 5.3. Скрытость и лестница (Р1 — вариант 1, принят)

Статусов нет → **фильтра по статусу нет**; участвует всё живое. Скрытие в
лестнице — **только про записи-фабрики** (`producer_types.hidden`): в лестнице
участвуют именно записи `producer_types` (подтипы-фабрики, §5.2); у
товаров/ресурсов/предметов скрытия нет, и в лестнице они не участвуют.
Рассмотренные чтения (сохранены как история):

- **Вариант 1 — ПРИНЯТ (Р1).** Скрытая самая конкретная **запись-фабрика**
  работает так же, как скрытый **слот**: «самая конкретная применяемая
  запись-фабрика решает скрытость категории на уровне». Категория видима ⟺
  самая конкретная применяемая запись `hidden=false` **и** самый конкретный
  применяемый слот `hidden=false`. Скрытая самая конкретная запись → категория
  скрыта на этом уровне (ни победителя, ни приглашения; с галкой «показать
  скрытые» — затемнённые карточки всех применяемых записей категории с пометкой
  «скрыта»; записей нет — заглушка, состояние 2 спеки скрытых §2.2).
  *Цена:* скрытие конкретной фабрики скрывает **всю** категорию на этом уровне
  (в т.ч. перекрывает видимую менее конкретную) — ровно как скрытый слот.
  *Почему принято:* симметрия двух осей (одно правило «самая конкретная
  решает»), скрытие — реальный рычаг, состояние 2 переиспользуется, студийный и
  игровой отбор совпадают.
- **Вариант 2 (отклонён):** скрытые записи выпадают из лестницы — «скрыл
  расовую фабрику → тихо вернулась универсальная», скрытие как косметика;
  противоречит пожеланию «универсальная закрывает дырки **если категория не
  скрыта**».
- **Вариант 3 (отклонён):** скрытые участвуют и побеждают — скрытие не меняет
  отбор вообще.

### 5.4. Три состояния узла-категории (после Р1)

| Состояние | Что рисуется |
|---|---|
| Применяемых слотов нет | Категория не показывается вовсе (вне набора уровня) |
| Набор есть, **скрыто** (самая конкретная **запись-фабрика** `hidden` **или** самый конкретный слот `hidden` — К1/Р1) | Без галки «показать скрытые» — ничего; с галкой — затемнённые карточки **всех** применяемых записей категории с пометкой «скрыта» + заглушка, если записей нет (диагностический вид; лестница здесь не применяется) |
| Набор есть, **видимо** | **Лестница:** победитель (карточка) + затемнённые скрытые записи категории; лосеры-видимые не рисуются; нет победителя → узел-приглашение |

Скрытость — **OR двух осей** (запись-фабрика скрыта **или** слот скрыт);
в UI источник скрытия помечается (запись/слот) — деталь @uidesigner (§16 п.6).

7. Применяемость (§5.1) едина для записей, слотов и типов; уровень семейства не
   видит расовых; ничьи недостижимы.
8. Скрытость — **две оси**: «скрыта запись-фабрика» (`producer_types.hidden`) и
   «категория скрыта на уровне» (`producer_slots.hidden`); категория видима ⟺
   самая конкретная применяемая запись **и** самый конкретный применяемый слот
   не скрыты (Р1/К1).
9. «Клик не повисает»: каждая видимая в списке запись имеет узел в дереве.
10. `non_approved_ref` и `incomplete_chain` отсутствуют; `missing_volume_weight`
    присутствует, но инертна (Р2); валидаторных блоков — 3.
11. `volume`/`weight` у `goods` — `NOT NULL DEFAULT 1` (значение есть всегда).
12. `banned_at`, `tier_override`, `goods_slots`, `producer_slots.hidden`,
    game-логика релиза 2, числа баланса — не тронуты; DoD зелёный

## 15. Кандидат ГД-сущности (обязательное предложение)

**Вопрос:** канон «самая конкретная побеждает» + флаг «скрыто» создают у расы
**дырки в производстве**: более конкретная фабрика перекрывает универсальную, а
скрытие может убрать категорию у уровня вовсе. Не сделать ли из «перекрытия»
игровую механику — **«Лицензия на производство»**: раса/игрок может получить
право производить перекрытую или скрытую категорию у другой расы/фракции
(торговля, союз, трофей), и лицензия возвращает её в предложение?

**Ответ (кандидат на решение создателя):** лицензия — **отчуждаемое право**
(предмет-рецепт или контракт; данные студии), даёт игроку цель: «дырка в
производстве расы» становится торговым маршрутом, а не тупиком. Отличается от
«Производственной специализации рас» (спека скрытых §8 — профиль
«открыто/закрыто») и от «Уникальных построек рас» (спека дерева §9 —
эксклюзив): здесь — отчуждаемое право на существующую категорию. В текущие
числа **НЕ входит** (анти-двойной учёт), решение за создателем. FAQ-счётчик не
двигается (кандидат ГД-сущности, не эталон физики/мира).

## 16. Риски

1. **Номер миграции.** `000055` — за рецептами; наша — `000054`. Два
   параллельных DDL на `goods` (рецепты снимают `tier_override`/`goods_slots`,
   мы — `status`/`banned_at` и правим `volume`/`weight`) логически независимы,
   но **номер сверить с рабочим деревом перед созданием файла** (иначе падение
   старта «duplicate key schema_migrations», см. `docs/PITFALLS.md`). Р4.
2. **e2e-смоук `tools/e2e/goods-studio-server-check.js` — не-регресс.** Шаги 4 и
   6 жёстко ждут `status==='banned'`/`'draft'`/`'approved'` и кликают
   «Согласовать» — без правки смоук краснеет. Шаг 4 переписывается на `DELETE`
   товара / скрытие записи-производителя (§11). Правка шага 6 пересекается с
   `tier_override` (зона спеки рецептов) → **координировать правки одного файла**
   с той задачей (@manager), иначе конфликт диффов.
3. **Существующие тесты статусов.** Список — §11; их правка входит в объём
   (TDD: сначала красные). Формулировки ожиданий — дословные regex, риск
   разъехаться с кодом; править тест и код одним коммитом. **S2:** после
   удаления `model.Status` без правки `studio_handlers.go` 232/238/252/257–271/
   282/304–308 код **не соберётся** — объём не «косметический».
4. **Перенос данных при миграции.** Скрытие получает **только** `producer_types`:
   `status='banned'` → `hidden=true` — проверку
   `SELECT count(*) FROM producer_types WHERE status='banned'` до/после
   зафиксировать в отчёте @developer. У `goods`/`items` переноса нет — строки
   `banned` просто становятся «живыми» (поля нет), `banned_at` снимается;
   отдельно зафиксировать `SELECT count(*) FROM goods WHERE status='banned'`
   (ожидание: «сколько было — столько же живых, скрытых не появилось»).
   `producer_types.hidden` добавляется **заново** (§1.5) — на dev-БД колонка
   отсутствует (её снял `000052`), проверка «колонки нет до / есть после» и
   «у `goods`/`items` колонки `hidden` нет» — в отчёте.
5. **Риск «разъехавшихся» дельт.** Фича правит видимость, которую описывают ещё
   три спеки (дерево, скрытые, рецепты) — §12; если дельты не применить, доки
   будут противоречить коду. **S1** и дельты К1 (§12.1) — обязательны.
6. **Две оси скрытости → OR при решении «видима ли категория».** Категория
   скрыта, если скрыта самая конкретная **запись-фабрика** **или** самый
   конкретный **слот**. Риск: админ не понимает, какая ось скрыла категорию, и
   «возврат» не помогает (снял запись — остался скрытый слот). Митигация: в
   диагностическом виде и в карточке родителя помечать источник скрытия
   («скрыта запись» / «скрыта на уровне»), деталь — @uidesigner. Цена принята
   создателем (К1).
7. **«Дефицит по расе» vs инвариант #7 «Дефицит создаёт география»**
   (`docs/GD_PROMPT.md`, «Двенадцать инвариантов»). Скрытие категории у
   расы/семейства создаёт дефицит, заданный **культурой расы**, а не географией
   — напряжение с инвариантом **названо явно**. Смягчение: скрытие — конфигурация
   контента студии (инструмент админа), а в игре релиза 2 дефицит разыгрывается
   через географию/логистику (снабжение), скрытие задаёт «профиль производства
   расы» (кандидат спеки скрытых §8). Решение о развитии — за создателем.
8. **Р2 и целостность данных.** `volume`/`weight` теперь `NOT NULL` — любой
   будущий путь, пишущий `NULL` явно, получит ошибку БД вместо warning'а; риск
   снимается тем, что все текущие пути (`CreateGood`, сид, ИИ) колонок не
   перечисляют и берут `DEFAULT 1`. v2-риск «F-2 опирался на проекцию `Recipe`
   из рецепт-спеки» **снят** решением Р2 (требование больше не зависит от
   графа).
9. **Р6 вырождается (флаг для решения создателя/менеджера).** Правило «ИИ не
   предлагает скрытое» не имеет носителя у товаров (у `goods` скрытия нет) —
   правила дропа по `banned`/`excluded` в `ai/` и строка промпта **удаляются**
   (§4.1), отчётная строка «ИИ предложил скрытое» исчезает. Если создатель имел
   в виду выдачу ИИ по `producer_types` (скрытые записи-фабрики), это **новая**
   фича (сейчас ИИ заполняет только товары) — вынесено менеджеру как вопрос;
   дизайн не додумывает.
