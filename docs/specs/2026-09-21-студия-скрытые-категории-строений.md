## 0. Резюме (одним абзацем)

Категории строений (подтипы-заводы kind=goods) конфигурируются **слотами
родителя**: новая таблица `producer_slots` (родитель × категория × расовость
× флаг скрытости, миграция 000052) задаёт, **какие категории тип kind=goods
предлагает на каждом уровне расовости** (универсальный = база, наследуемая
всеми; семейные/расовые слоты — поверх). Автоматика категорий
(`prodAutoCategories`, привязка к имени типа) **удаляется** — дерево показывает
настроенные слоты, а не «всё подряд»; стартовая база = сид слотов (Фабрика/
Автофабрика — 13 товарных, Платформа — 6 ресурсных, универсальный уровень) —
поведение по умолчанию равно текущему. Скрытость живёт **на слоте** (флаг
`hidden` на `producer_types` первой волны **снимается** — одна ось): скрытая
категория на уровне не показывается (ни карточка завода, ни приглашение),
галку «скрытая» расставляют из **карточки родителя** (редактор слотов с
пометками «унаследован/переопределён»); галка «показать скрытые» в шапке ветки
показывает скрытые категории затемнёнными с пометкой «скрыта». Инвариант
**«подтип kind=goods без слота невозможен»** (по критику С4): создание/смена
категории завода требует существующего слота (400), удаление слота при
существующих заводах — 409 (RESTRICT). Правило «самая конкретная применяемая
запись решает», три состояния узла, фильтр списка/поиска — сохраняются,
переносятся с записей на слоты. Game-логика не трогается (релиз 2 фабрик —
отдельной задачей). Числа баланса не затрагиваются.

## 1. Модель и БД

### 1.1. Природа сущности `producer_slots` (архитектурный фильтр)

1. **Слот родителя** — **состояние/конфигурация**, не событие и не лог:
   настроенный список слотов-категорий типа-родителя. Реальное отношение
   (родитель × категория × расовость × скрытость), **не** «один атрибут»:
   правило «сущность с двумя экземплярами — не сущность» здесь НЕ нарушается
   (у каждого родителя много слотов; у одной пары — несколько уровней
   расовости). Плодить таблицу ради флага не нужно — таблица и есть конфигурация.
2. **Владелец** — у многих: каждый тип kind=goods имеет свои слоты; расовость —
   существующие `race_family`/`race` (семейство F0–F9 + robotic / раса 60).
3. **Расширяемость** — любое число слотов/категорий/уровней; вторая ось
   (напр. «слот активен/заблокирован») ложится колонкой в ту же таблицу.
4. **Семантика:** слот = «родитель **предлагает** категорию на уровне
   расовости»; `hidden` = «предлагает, но скрыто» (вариант б идеи §2 п.1:
   скрытость перекрывает наследуемое). Слот без записи-завода = приглашение
   (видимое) или скрытая пустая категория (скрытое) — главный кейс, ради
   которого модель переработана (идея §2a: «скрыть пустой слот, не создавая
   запись»).

### 1.2. Миграция `000052` (переписана; 000051 — дерево построек)

```sql
-- 1) Снять флаг hidden первой волны (фича НЕ релизнута; на свежей БД колонки нет).
ALTER TABLE producer_types DROP COLUMN IF EXISTS hidden;

-- 2) Слоты родителя: конфигурация категорий (спека скрытых §1.1).
CREATE TABLE producer_slots (
    id          BIGSERIAL PRIMARY KEY,
    parent_id   BIGINT NOT NULL REFERENCES producer_types (id) ON DELETE CASCADE,
    category_id BIGINT NOT NULL REFERENCES categories (id) ON DELETE CASCADE,
    race_family TEXT NULL,
    race        TEXT NULL,
    hidden      BOOL NOT NULL DEFAULT false,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CHECK (race IS NULL OR race_family IS NOT NULL),
    UNIQUE NULLS NOT DISTINCT (parent_id, category_id, race_family, race)
);
```

- **Уникальность — `UNIQUE NULLS NOT DISTINCT`** (выбрано; PostgreSQL 15+ —
  нижняя граница проекта, AGENTS.md §1): NULL-safe на уровне БД с рождения
  таблицы; жёсткая гарантия переживает будущие пути мимо Go (сид/булк);
  идемпотентная data-миграция использует этот же индекс как `ON CONFLICT`.
  Go-пречек с `IS NOT DISTINCT FROM` (паттерн кортежа подтипа,
  producer_repository.go 258–272) остаётся для человеческого 409-сообщения,
  БД-нарушение — запасной 409 (как дубликат имени). Альтернатива (Go-only,
  как у подтипов) — работает под advisory lock, но не защищает обходы — отклонена.
- **FK/каскады (по критику С5):**
  - слот → категория: **CASCADE** — конфигурация следует за категорией;
    подтипы-заводы и так заблокированы существующим FK 000048 без ON DELETE
    (NO ACTION) — не наша проблема;
  - слот → родитель: **CASCADE** — снос типа уносит его конфигурацию;
    подтипы — существующий RESTRICT 000051 (тип с подтипами не удаляется).
- **`CHECK (race IS NULL OR race_family IS NOT NULL)`** на БД + Go-валидация
  `validateRaceFamily` (как у записей, §1.2 п.6 спеки дерева).
- **Dev-инструкция (по критику М2):** 000052 уже применён на dev (колонка
  `hidden`). Снять строку `000052` из `schema_migrations` вручную, перезапуск
  применит переписанную миграцию заново (`DROP COLUMN IF EXISTS` безопасен).
  Прод-БД нет (фича не релизнута) — инструкция только для dev/локальной.

### 1.3. Data-миграция и сид (оба пути, паттерн 000051 §1.3 «одинаковый результат»)

Слоты создаются **двумя путями** (выбор обоснован ниже):

**Путь 1 — data-миграция (в 000052, существующие БД)** — сид
`producer_catalog_seed` уже отработал (маркер):

```sql
-- 1a) Слоты под ВСЕ существующие подтипы kind=goods (по их уровню расовости):
--     ничего не пропадает (инвариант С4 для существующих данных).
INSERT INTO producer_slots (parent_id, category_id, race_family, race)
SELECT DISTINCT parent_id, category_id, race_family, race
FROM producer_types
WHERE parent_id IS NOT NULL AND kind = 'goods' AND category_id IS NOT NULL
ON CONFLICT DO NOTHING;

-- 1b) Базовый сид универсального уровня (hidden=false): Фабрика/Автофабрика —
--     все товарные категории (kind='good', 13), Платформа — ресурсные
--     (kind='resource', 6); по name_norm родителя (паттерн 000051: переименованный
--     тип → слоты не создаются, риск зафиксирован в отчёте).
INSERT INTO producer_slots (parent_id, category_id)
SELECT p.id, c.id FROM producer_types p CROSS JOIN categories c
WHERE p.name_norm IN ('фабрика', 'автофабрика') AND c.kind = 'good'
ON CONFLICT DO NOTHING;
INSERT INTO producer_slots (parent_id, category_id)
SELECT p.id, c.id FROM producer_types p CROSS JOIN categories c
WHERE p.name_norm = 'добывающая платформа' AND c.kind = 'resource'
ON CONFLICT DO NOTHING;
```

**Путь 2 — обновлённый сид `seed_producers.go` (свежие БД):** на момент
миграции `producer_types` пуст (кроме «Лаборатории» из 000051) — типы
Фабрика/Автофабрика/Платформа создаёт Go-сид ПОСЛЕ миграций. После цикла
типов сид добавляет слоты: базовые 13/6 (по `name_norm` категорий и родителей,
`ON CONFLICT DO NOTHING`), плюс слот под сид-подтип «Фабрика продовольствия»
(категория «продовольствие» покрыта базовыми 13 — отдельный слот не нужен,
только если категория вне базы — тогда явный INSERT). Маркер
`producer_catalog_seed` исключает повтор. Сид-INSERT идёт напрямую в БД (мимо
валидации репозитория) — инвариант С4 к сиду не применяется (слоты создаются
в том же сиде/миграции).

**Обоснование «оба пути, а не один»:** только миграция → на свежей БД типов
нет в момент миграции (слоты не создадутся); только сид → на существующей БД
маркер уже отработал (слоты не создадутся, инвариант С4 для существующих
подтипов нарушится). Оба пути дают одинаковый результат (паттерн 000051 §1.3).
Сид слотов **идемпотентен** (`ON CONFLICT DO NOTHING`).

### 1.4. Инварианты и валидация (Go-слой, как существующие — не DB CHECK кроме §1.2)

1. **Слот обязателен для подтипа kind=goods (по критику С4 — ГЛАВНЫЙ):**
   `POST`/`PUT` подтипа kind=goods (создание и смена категории) требует
   существующего слота `(parent_id, category_id)`, **применяемого на уровне
   расовости записи** (по §2.1: слот с `race_family IS NULL`, или
   `race_family` = семейства записи, или `race` = расы записи) → иначе 400
   «категория не настроена у родителя на этом уровне». Наследуемый слот базы
   засчитывается (семейная запись возможна под универсальным слотом).
   **Скрытость слота НЕ блокирует** (ортогональна): скрытый слот прячет
   карточку уже созданного завода (идея §2a п.3), но завод существует.
2. **RESTRICT удаления слота (по критику С4):** `DELETE` слота при
   существующих подтипах kind=goods `(parent_id, category_id)`, применяемых к
   слоту (то же правило §2.1) → 409 «сначала удалите заводы категории».
   Записей нет → удаление свободно (снятие переопределения возвращает уровень
   к наследуемому; удаление из базы убирает категорию из набора родителя).
3. **Скоуп слотов (по критику С8):** слоты только у **типов** kind=goods
   (`parent_id IS NULL` + kind=goods; в сиде — Фабрика/Автофабрика/Платформа,
   любой новый тип kind=goods тоже). kind=items/energy — слотов нет (POST 400,
   UI не предлагает редактор). Соответствие kind категории ↔ kind родителя —
   **НЕ ужесточается** (текущая свобода: ресурсная категория у Фабрики возможна
   — как сейчас подтип с ресурсной категорией, buildProdTree 1822–1827; набор
   слотов — конфигурация, не имя) — см. развилку §5.2.
4. **Уникальность слота** — `(parent_id, category_id, race_family, race)`,
   NULL-safe (§1.2); `hidden` НЕ входит в кортеж (как М1 первой волны —
   смена флага не триггерит 409).
5. **Раса → семейство** — `validateRaceFamily` + DB CHECK (§1.2).
6. **hidden на записях УБИРАЕТСЯ** (одна ось, идея §2a п.3): поле
   `ProducerTypeRow.Hidden`, параметр Create/Update, JSON `hidden` в
   state/POST/PUT, чекбокс попапа записи, тесты — удаляются (миграция DROP,
   §1.2). `subtypeTupleChanged` не менялся и не меняется (hidden в него не входил).
7. **Смена категории у подтипа** (`changeProdCategory`) — слот старой
   категории остаётся (конфигурация независима от записей): категория снова
   может приглашаться, переименование/перенос не трогают слоты.

## 2. Правило видимости слота на уровне L (по С3 первой волны, источник — слоты)

### 2.1. Применяемые слоты и «самая конкретная решает»

Для типа `t` (kind=goods) на уровне расовости L **применяемые слоты** — слоты
`producer_slots` с `parent_id = t.id`, видимые по существующему §2.4 спеки
дерева (та же функция `prodVisible`, 1731 — теперь по слотам):

| Уровень L | Применяемые слоты |
|---|---|
| Универсальный | `race_family IS NULL` |
| Семейство Fk | `race_family IS NULL` **или** `race_family = Fk` |
| Раса R | `race_family IS NULL` **или** `race_family = family(R)` **или** `race = R` |

**Самая конкретная применяемая запись** — слот с самой специфичной привязкой:
`race = R` > `race_family = Fk` > `race_family IS NULL` (универсальная база).
`UNIQUE NULLS NOT DISTINCT` гарантирует: на уровне L для пары (родитель,
категория) каждой специфичности — **не более одного** слота; «самая
конкретная» определена однозначно.

**Правило:**

- **Применимых слотов НЕТ** → категория **не показывается вовсе** (не входит
  в набор родителя на уровне L). Это отличие от «тянуть всё»: автоматика
  категорий отменена, набор = конфигурация. Добавление категории — «+ слот
  категории» в карточке родителя (§3.2).
- Применимые слоты есть, **самая конкретная** `hidden=true` → категория
  **скрыта на уровне L** (вариант б): не показывается ни карточка завода, ни
  узел-приглашение. Работает поверх наследования: скрытая база скрыта у всех
  (кроме уровней с собственным видимым переопределением); скрытый слот уровня
  перекрывает видимую базу у этой расы/семейства, у остальных база видна.
- Применимые слоты есть, **самая конкретная** `hidden=false` → категория
  **видима на уровне L**: карточки применяемых записей (подтипы по §2.4,
  «своё + универсальное») + **узел-приглашение** «создать», если записей нет.

**Примеры:**
- База «Фабрика топлива» (слот universal, visible); у F4 слот
  `(Фабрика, топливо, F4)` hidden=true → на «Семейство F4» категория скрыта
  (ни карточка, ни приглашение); на «Универсальный» — видна; у F0/F1 без
  своего слота — видна (база).
- **Обратный кейс:** база скрыта (universal hidden=true), у F4 слот-переопределение
  `hidden=false` → «открыть» категорию одной расе: у F4 категория видна, у
  остальных — скрыта.
- Слот без записей: видимый → узел-приглашение; скрытый → скрытая пустая
  категория (главный кейс переработки: скрыть слот, не создавая завод).

### 2.2. Три состояния узла (перенос с записей на слоты)

1. **Видимый узел** — есть применяемые слоты, самая конкретная видима:
   карточки записей категории + приглашение, если записей нет.
2. **Скрыто** — есть применяемые слоты, самая конкретная скрыта: при
   выключенной галке **ничего не рисуется** (ни карточка, ни приглашение);
   при включённой галке — **затемнённые карточки записей категории с пометкой
   «скрыта»**; записей нет → затемнённая **карточка-заглушка категории** с
   пометкой «скрыта» (иначе скрытый пустой слот невидим даже при галке;
   деталь — @uidesigner). Видимые менее конкретные записи НЕ показываются
   (вариант б). Клик/двойной клик по затемнённой карточке → карточка родителя
   (§3.2, путь «открыть»).
3. **Узел-приглашение** — видимый слот без записей (как сейчас, спека дерева
   §2.3). Для скрытых категорий приглашение не строится ни при какой галке.

Три состояния не смешиваются с `prodVisible` (фильтр расовости §2.4 спеки
дерева) — обе оси применяются (AND).

### 2.3. Замена автоматики категорий

`prodAutoCategories` (1780, привязка к ИМЕНИ типа) **удаляется**: набор
категорий типа = его слоты (база + переопределения). Типы «Фабрика/Автофабрика/
Платформа» — не константы кода, а типы с базовыми слотами из миграции/сида
(§1.3): поведение по умолчанию равно текущему (13/6 категорий), но переименование
типа больше НЕ снимает раскрытие (слоты привязаны к id, не к имени). Новые типы
kind=goods получают пустой набор слотов (категории добавляются «+ слот»).
«+ тип» (`prodAdd`, 1690) создаёт типы (слотов нет — заводятся в карточке
родителя); узел-приглашение создаёт подтип (`doProdCreate`, 2023) — слот
существует по построению (иначе приглашения нет).

## 3. UI (ветка «Производители»)

### 3.1. Галка «показать скрытые» (сохраняется)

- В шапке ветки рядом с переключателем расовости (`#segProdRace`, 198–207):
  чекбокс `#prodShowHidden` (211), localStorage `gs_prodShowHidden` (346),
  дефолт выключена. Включена → скрытые категории затемнёнными карточками с
  пометкой «скрыта» (дерево) и записи скрытых категорий (список). Раскладка —
  @uidesigner.
- Действует AND с переключателем расовости: слоты, не применяемые на уровне,
  не показываются даже при галке (принадлежат другим уровням).

### 3.2. Карточка родителя — редактор слотов (по критику С7)

Двойной клик/ⓘ по узлу **типа kind=goods** → существующий `renderProdPopup`
(1532) + секция **«Слоты категорий»** (только типы kind=goods; items/energy —
без секции, §1.4 п.3). Содержимое на **текущем уровне расовости** (переключатель
шапки):

- Список категорий набора родителя на уровне: для каждой — галка «скрытая»
  (эффективная скрытость = самой конкретной применяемой, §2.1) + пометка
  **«унаследован»** (слот базы universal без переопределения уровня) /
  **«переопределён»** (слот текущего уровня).
- **Действие клика по галке:**
  - унаследованный слот → создать **переопределение текущего уровня**
    (`POST /studio/api/slots` с hidden = новое значение; база не трогается);
  - собственный слот (переопределение) → `PUT /studio/api/slots/{id}`
    {hidden} (правит только уровень);
  - на **универсальном уровне** галка правит базу (PUT — слот и есть база).
- **«− слот»:** собственный → `DELETE /slots/{id}` (снять переопределение,
  возврат к наследуемому); базовый (universal) → удаление из набора родителя
  (подтверждение-модалка; RESTRICT при записях — 409, §1.4 п.2).
- **«+ слот категории»:** select категории, **не входящей** в набор на текущем
  уровне → `POST /slots` (создание слота уровня/базы).
- **Обратный кейс «открыть»** (скрытая база + видимый слот уровня): в списке
  виден унаследованный скрытый слот и переопределение уровня visible — снять
  переопределение = возврат к скрытой базе; оставить = категория открыта у
  этого уровня.

### 3.3. Дерево на канвасе (слоты вместо автоматики)

`buildProdTree` (1805) / `renderProdTree` (1889):

- **Тип kind=goods:** категории = применяемые слоты на текущем уровне (§2.1);
  для каждой — по трём состояниям (§2.2): видимые карточки записей
  (`prodAppliedRecords` 1745, по категории) + приглашение; скрытая — ничего
  (без галки) / затемнённые карточки + пометка «скрыта» (с галкой). Категории
  вне набора на текущем уровне не рисуются.
- **Тип items/energy / без слотов:** подтипы как раньше (по `prodVisible`),
  без оси скрытости (у записей hidden снят).
- Затемнённая карточка: существующий стиль banned-карточки как база + пометка
  «скрыта» (бейдж/подпись; деталь — @uidesigner); клик/двойной клик → карточка
  родителя (§3.2). Тултип (`showProdTip` 2106) у скрытых узлов — пометка «скрыта».

### 3.4. Попап записи (по критику С6): чекбокс УДАЛЯЕТСЯ

- Чекбокс «скрытая» в `renderProdPopup` (1560–1563) и `saveProdHidden` (1639)
  **удаляются** — скрытость живёт на слоте; путь «открыть» скрытую категорию —
  **только через карточку родителя** (§3.2): тип не скрывается, всегда в дереве.
- `changeProdCategory` (1610): select категории ограничивается категориями с
  применяемым слотом на уровне записи (иначе 400, инвариант С4, §1.4 п.1).

### 3.5. Список справа и поиск (по С4 первой волны, перенос на слоты)

`renderProdSprav` (1487): фильтр по правилу видимости+скрытости дерева:

1. **Расовость** (`prodVisible`, 1731) — не применяемые записи не показываются.
2. **Скрытость категории** — запись категории, скрытой на уровне (самая
   конкретная решает), не показывается без галки; с галкой — показывается
   (узел затемнён в дереве), с пометкой «скрыта» (деталь — @uidesigner).
3. **Узел в дереве** (`prodNodeVisible`, 1762 — теперь слот-управляемый:
   категория записи входит в набор родителя на текущем уровне) — «клик не
   повисает».
4. **Поиск** — сужает (AND) поверх п.1–п.3.

## 5. Развилки на гейт (решения создателя 2026-09-21 — все по рекомендациям)

### 5.1. Обязательность слота для подтипа kind=goods (по критику С4)

**Решение: жёстко** — 400 на создание/смену категории без применяемого
слота, 409 на удаление слота с заводами (§1.4 п.1/п.2). Цена: модель целостна
(«категория не настроена у родителя» ≠ «нельзя построить»), скрытые категории
не получают заводов в обход конфигурации.

### 5.2. Скоуп слотов и соответствие kind (по критику С8)

**Решение:** редактор слотов у **всех** типов kind=goods (включая
«Поселение» и новые типы — пустой набор, категории через «+ слот»);
items/energy — без слотов. Соответствие kind категории ↔ kind родителя
**не ужесточается** (ресурсный слот под Фабрикой возможен — как сейчас подтип
с ресурсной категорией, buildProdTree 1822–1827): набор = конфигурация, не
имя. Цена: свобода данных, ровно как в текущем поведении.

### 5.3. «− слот» из базы (по критику С7)

**Решение:** подтверждение-модалка + RESTRICT при записях (409);
снятие переопределения уровня — без подтверждения (обратимо). Каскадный снос
слотов с заводами — отклонён (теряются заводы).

### 5.4. Перенос существующих записей без слота

**Решение:** data-миграция создаёт слоты под **все** существующие подтипы
kind=goods (§1.3, путь 1a) — ничего не пропадает, инвариант С4 держится для
текущих данных; «оба пути» миграция+сид (§1.3) — подтверждено (идемпотентно).

### 5.5. Скрытая пустая категория при включённой галке

**Решение:** карточка-заглушка категории с пометкой «скрыта» (§2.2 п.2) —
иначе скрытый слот без заводов невидим даже при галке (админ не увидит, что
скрыто). Раскладка — @uidesigner (сплошная затемнённая карточка, подпись
«нет заводов», бейдж «скрыта»; клик → карточка родителя).

## 8. Кандидат ГД-сущности (обязательное предложение)

**«Производственная специализация рас»** — профиль расы «что производит сама /
что закрыто (скрыто) и покрывается импортом или другими ветками», хранимый
конфигурацией слотов родителя (`producer_slots`: набор категорий + скрытость по
семействам/расам). Инструмент наполнения — эта фича; игровое воплощение —
релиз 2 фабрик (торговые зависимости: раса покупает то, что у неё скрыто; цена
импорта как функция закрытости; «проще удалить, чем добавить» = культура
производства расы складывается из скрытий базы и своих переопределений).
Отличается от принятого кандидата «Уникальные постройки рас» (спека дерева §9:
эксклюзивные строения-цепочки): здесь — профиль «открыто/закрыто» существующих
категорий, там — новые уникальные ветки. Кандидат на решение создателя, в
текущие числа НЕ входит (анти-двойной учёт).

## 10. Сводка ключевых решений (для создателя)

1. **Модель:** `producer_slots` (parent_id, category_id, race_family, race,
   hidden; миграция 000052 переписана). Слот = «родитель предлагает категорию
   на уровне расовости»; hidden = «предлагает, но скрыто». **hidden на
   `producer_types` снимается** (DROP, одна ось). Уникальность — `UNIQUE NULLS
   NOT DISTINCT` (PG 15+) + Go-пречек 409; FK: слот→категория/родитель CASCADE.
2. **Слоты — конфигурация родителя** (идея §2a п.1): у каждой расы свой конфиг
   (семейные/расовые слоты поверх универсальной базы); автоматика по имени
   (`prodAutoCategories`) удаляется; стартовая база = сид (13/6, универсальный).
3. **Наследование «проще удалить, чем добавить»** (§2a п.2): база видна всем;
   уровни переопределяют (скрытие/открытие).
4. **Правило видимости (С3):** применяемые слоты по §2.4; самая конкретная
   решает: hidden → категория скрыта на уровне (ни карточка, ни приглашение);
   visible → карточки + приглашение; применимых слотов НЕТ → категория не
   показывается вовсе.
5. **Инвариант С4 (главный):** подтип kind=goods без применяемого слота — 400;
   удаление слота при заводах — 409 (RESTRICT); data-миграция создаёт слоты под
   существующие подтипы.
6. **Карточка родителя — редактор слотов (С7):** галки «скрытая», пометки
   «унаследован/переопределён», «+ слот категории», «− слот» (подтверждение,
   RESTRICT); на универсальном уровне галка правит базу. Путь «открыть»
   скрытую категорию — только здесь (С6); чекбокс в попапе записи удаляется.
7. **Три состояния, галка «показать скрытые», затемнённые карточки, фильтр
   списка/поиска** — сохраняются, переносятся на слоты (§2.2, §3.1, §3.5).
8. **Сид/миграция — оба пути** (паттерн 000051 §1.3): миграция — для
   существующих БД (подтипы уже есть), Go-сид — для свежих (типов ещё нет);
   идемпотентно (ON CONFLICT), маркер `producer_catalog_seed` сохраняется.
