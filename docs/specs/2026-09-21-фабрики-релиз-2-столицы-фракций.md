## 0. Задача и границы

Дать в игре **первый настоящий экземпляр строения**: столицу фракции — постройку
с владельцем-фракцией, видимую в карточке планеты во вкладке «Фракции».

**Входит:** сущность «строение» (`buildings`) как факт мира; столица — по одной
на фракцию, на её родной планете; владелец-фракция; показ списка фракций планеты и
столицы во вкладке «Фракции» карточки планеты; клик раскрывает детали столицы.

**НЕ входит:** население строений, снабжение, разблокировка производства,
тир как гейт, механики перехода/отжима владения, владельцы поселений,
автофабрики/платформы/лаборатории/энергостанция/ретрансляторы, инвентарь
предметов, отдельная вкладка «Строения», моделирование «присутствия» фракции на
чужих планетах (`06_factions.md` §6.1), доход/управление строением, репутация и
война (§6.4).

**Настрой итерации — «попробовать»** (создатель, 2026-09-21): цель — увидеть
сущность и начать с ней взаимодействовать; многие решения принимаются после
пробы, поэтому итерация узкая и «щупаемая».

⚠️ Инвариант 10 («сущность оправдана решением») здесь **сознательно отложен на
итерацию**: строение пока не даёт игроку выбора (владелец только показывается).
Это прямое решение создателя «фундамент» (идея §2 п.1–2); первые решения игрока
появятся с населением/снабжением (этап 2 п.8–9 спеки фабрик).

## 1. Что такое «строение» в этой итерации (архитектурный фильтр)

Сверено со спекой фабрик §2 (природа сущностей) и с `GLOSSARY.md` §6
(«Строение», «Владелец строения» — термины уже есть, новых не вводим, кроме
«Столица фракции», см. §9).

1. **Природа — лог/состояние**, не событие: строение — результат («в мире есть
   постройка»), записей много, поле у планеты не переживёт второй тип. Таблица.
2. **Владелец — у строения, три класса сразу** (`owner_type`: player/faction/
   agent). В первой итерации фактически используется один класс (`faction`),
   но схема его не зашивает.
3. **Расширяемость — проверка второго типа:** столица (`building_type='capital'`)
   и будущая фабрика (`building_type='factory'` + `producer_type_id`, §2/§3.2
   спеки фабрик) ложатся в одну таблицу; второй тип требует только новых колонок
   и нового ключа `building_type` — переделки схемы нет. Значит, проектируем ту
   сущность.
4. **Столица — не `settlements`-строка.** Поселение физически остаётся в
   `settlements` (техдолг-идея переноса поселения в модель строений, спека
   фабрик §11.5); столица — обычное строение, к поселениям не привязана.

### 2.1. Колонки первой итерации

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | UUID PK DEFAULT gen_random_uuid() | |
| `planet_id` | UUID NOT NULL REFERENCES planets(id) ON DELETE CASCADE | планета, на которой стоит строение |
| `building_type` | TEXT NOT NULL | вид строения, свободный ключ (**`capital`** — столица фракции, §6) |
| `owner_type` | TEXT NOT NULL CHECK (owner_type IN ('player','faction','agent')) | класс владельца |
| `owner_id` | UUID NOT NULL | id владельца (`factions.id` при `owner_type='faction'`) |
| `created_at` / `updated_at` | TIMESTAMPTZ NOT NULL DEFAULT NOW() | как у `factions` |

Индексы:

```sql
CREATE INDEX idx_buildings_planet_id ON buildings (planet_id);
CREATE UNIQUE INDEX uq_buildings_capital_owner
    ON buildings (owner_type, owner_id) WHERE building_type = 'capital';
```

Первый — чтение карточки планеты (инвариант 2: стоимость не растёт с галактикой,
запрос идёт по планетам одной системы). Второй — «одна столица на фракцию» на
уровне БД: гарантия вместо соглашения об именах и страховка от гонки двух джоб
(инвариант 1: проверка и действие атомарны — `INSERT ... ON CONFLICT DO NOTHING`).

### 2.2. Колонки, отложенные до своих под-шагов

| Колонка из §3.2 спеки фабрик | Когда | Почему сейчас нет |
|---|---|---|
| `producer_type_id` BIGINT NULL FK | этап 2 п.8–10 (появление производителей) | у столицы он NULL по решению создателя; NULL-колонка без потребителя — мёртвый груз, добавление nullable-колонки дешёво |
| `population` | этап 2 п.8 (население строений) | механики населения в итерацию не входят |
| `slots` | этап 2 п.9 (предмет-рецепт в слоте) | разблокировки нет |
| `status` | этап 2 п.8+ (простой/повреждение) | строение всегда `active`, менять нечего |
| `data` | этап 2 п.10 (буферы входа/выхода) | буферов/инвентаря нет |
| `name` | этап 2 п.8+ | в первой итерации подпись строения берётся из словаря `building_type` (§6); хранить нечего |

### 2.3. Отличия от §3.2 спеки фабрик (дельты в спеку)

1. `owner_type`/`owner_id` — **NOT NULL** (в §3.2 `owner_type` без NOT NULL,
   `owner_id UUID NULL`). Причина: строение без владельца в модели не существует
   (§5.1: «у всех строений есть владелец»), запись всегда пишется с владельцем;
   NOT NULL делает инвариант проверяемым. Расширение под «брошенное строение»
   (если появится) — `DROP NOT NULL` в своей миграции.
2. `owner_id` — **без FK** (полиморфный владелец: users/factions/npc_agents).
   Целостность не гарантируется БД; для столиц её гарантирует генератор, а
   висячих владельцев не возникает, потому что `buildings` и `factions` чистятся
   одной операцией (§4.3).
3. Колонки §2.2 отложены (в §3.2 они заявлены сразу) — базовая спека §3.2
   синхронно правится: реализованные колонки берутся из §2.1 этой спеки,
   отложенные помечаются «отложено» (C2, §9.1 п.6).

## 3. Генерация: как столицы появляются в мире

**Одна столица на фракцию, на её родной планете** (`factions.homeworld_id` —
FK на `planets`; «мир» в проекте — звёздная система, M7), тип
«другое»: `building_type='capital'`, `owner_type='faction'`, `owner_id=factions.id`,
`producer_type_id` отсутствует (по решению создателя — не производитель, ничего
не производит).

**Столица создаётся вместе с фракцией — одним идемпотентным шагом в том же
джобе.** Существующая кнопка `/admin/generate-factions` («Генерация → Фракции»)
дополняется проходом `EnsureCapitals()`:

```sql
INSERT INTO buildings (planet_id, building_type, owner_type, owner_id)
SELECT f.homeworld_id, 'capital', 'faction', f.id
FROM factions f
WHERE NOT EXISTS (
    SELECT 1 FROM buildings b
    WHERE b.building_type = 'capital' AND b.owner_type = 'faction' AND b.owner_id = f.id
)
ON CONFLICT DO NOTHING;
```

Свойства решения:

- **Идемпотентность.** Повторный прогон не дублирует столицы; уникальный
  частичный индекс (§2.1) — вторая линия защиты.
- **Фракций 0** (`dev-БД` сейчас пуста, фракции генерируются только на планетах
  с населением > 0) → 0 столиц, не ошибка. Ответ:
  `{"status":"factions_generated","total":0,"capitals":M}` — `M` здесь число
  столиц, фактически созданных синхронным догоном (обычно 0, но может быть > 0
  на легаси-БД). Чтобы фракции появились, нужна вселенная с поселениями
  (существующее условие генератора).
- **`total` — число планет с населением** (знаменатель прогресса джоба и его
  `total` в `statusManager.TryStart`; M1), **не** число фракций. Отсюда разная
  судьба поля `capitals` в двух ветках (§7 п.2–3): в синхронной ветке `total == 0`
  оно идёт из возврата прохода (`EnsureCapitals() (int, error)`) прямо в HTTP-ответ;
  в асинхронной ветке HTTP отвечает `{"status":"started"}` до конца работы, поэтому
  число созданных столиц пишется в **лог/отчёт джоба** (`N factions, M capitals`),
  а не в ответ.
- **Существующая фракция без столицы** (легаси-БД, ручная правка) — закрывается
  тем же проходом: `EnsureCapitals()` выполняется в конце джоба **и** в ветке
  `total == 0` (синхронно, до старта джоба — один дешёвый запрос), поэтому догон
  не требует нового эндпоинта и новой кнопки.
- **Синхронный догон идёт под тем же гейтом, что и джоб (C3).** В коде сегодня
  ветка `total == 0` возвращает ответ **раньше** проверки занятости Пакмана
  (`statusManager.IsRunning(generator.JobPacman)`) и вне разделяемого мьютекса
  мутаций вселенной (`universeMutationMu`, `admin_universe.go:29`), поэтому
  `EnsureCapitals()` в ней писал бы в `buildings` поверх пакмана/ClearUniverse —
  гонка «проверка + действие» (инвариант 1; `EnsureCapitals` — синхронный писатель
  в `planets`-каскад, как `GeneratePrototypePlanet`). Проект: **проверку Пакмана
  и захват `universeMutationMu` перенести до ветки `total == 0`** (либо выполнять
  догон под тем же гейтом). Порядок: (1) посчитать `total`; (2) гейт
  (Пакман/мьютекс); (3) `total == 0` → синхронный догон → ответ; (4) иначе —
  обычный старт джоба.
- **Отчёт честный:** ответ и лог получают аддитивное поле `capitals` — сколько
  столиц реально создано (может быть больше числа новых фракций при догоне).
  `total` остаётся числом планет с населением (контракт не ломается; фронт админки
  читает прогресс джоба, поле игнорирует).
- **Транзакции:** проход — один запрос; частичный сбой (фракции записаны,
  столицы нет) лечится повторным запуском кнопки (идемпотентно). Отдельная
  транзакция на фракцию не нужна.

**Отвергнутая альтернатива:** отдельная админ-кнопка «Создать столицы» — лишний
эндпоинт ради легаси-состояния, которого на dev-БД нет; дубликаты фракций при
повторном нажатии «Сгенерировать фракции» — существующее свойство генератора,
наша итерация его не создаёт и не лечит.

## 4. Показ и минимальное взаимодействие

### 4.1. Куда показываем

Вкладка **«Фракции»** карточки планеты (`web/static/js/modal/panel.js:343`,
контент — `tabs.js`). Заглушка `renderFactionsStub()` («Данные о фракциях будут
доступны позже») заменяется рендером `renderFactions(planet)`. Отдельная вкладка
«Строения» не заводится (решение создателя §4.2), новых экранов и модалок нет —
всё внутри существующей карточки.

### 4.2. Что видно

```
Фракции (2)
родная планета — эта

● Аквилонский Синдикат
  Торговый синдикат
  «Аквилонский Синдикат — торговый синдикат, ведущая активную экспансию…»
  🏛 Столица · Другое (ничего не производит)          ▸ нажмите, чтобы раскрыть

● Дом Кхари
  Клан
  …
  🏛 Столица · Другое (ничего не производит)
```

- Список — фракции с `homeworld_id` этой планеты (генератор создаёт 1–3 на
  планету с населением). Подпись «родная планета — эта» честно называет
  ограничение: модель **присутствия** фракции на многих планетах
  (`06_factions.md` §6.1) не реализована (§9.5), вкладка показывает не
  «присутствие», а «кто здесь родом».
- Цвет фракции — точка перед именем (`factions.color`), тип — второй строкой,
  описание — приглушённым мелким текстом.
- **Сила (`strength`) не показывается:** генератор всегда пишет 1 — это
  заглушка, а не факт мира; показывать её значит врать игроку.
- У каждой фракции — строка столицы: нашлась по `buildings` планеты
  (`owner_type='faction'`, `owner_id=faction.id`, `building_type='capital'`).
  Нет столицы — строки нет (модель допускает; во вкладке такой случай просто
  не отображается, отдельного текста не вводим).

### 4.3. Что по клику (минимальное взаимодействие)

Клик по фракции раскрывает инлайновый блок деталей (без новых окон):

```
Столица (строение)
Тип: Другое — ничего не производит
Владелец: Аквилонский Синдикат (Торговый синдикат)
Планета: <имя планеты> — родная планета фракции
Управление появится позже: сейчас видно только владельца
```

Повторный клик сворачивает. Реализация — тоггл `display` у блока, как у
соседних блоков карточки; никаких серверных вызовов (данные уже приехали с
карточкой планеты). Последняя строка — честное обозначение границы итерации
(инвариант 3 «смотреть может каждый, управлять — владелец» пока не задействован).

### 4.4. Пустые состояния

| Случай | Что показываем |
|---|---|
| Игрок без знания о планете (и не админ) | «Нет данных — купить отчёт» (паттерн вкладки «Поселения», 77a §6.2) |
| Знание есть / админ, фракций у планеты нет | **«Фракции не отмечены»** (дельта 2026-09-23, §5; прежняя формулировка «в отчёте сканера фракции не значились» снята как устаревшая): игроку **никогда** не пишем «Фракций на планете нет»; для планеты со снимком фракции — из снимка (заморожены, на дату отлёта), для планеты без визита — как прежде (живые, по знанию). Отсутствие фракций не значит отсутствия их на планете: запись знания может быть устаревшей (§8.2, 7 дней) |
| Фракции есть, столицы нет | список без строки столицы |

## 5. Видимость (кто видит)

- **admin/skycomposer** — видят фракции и столицы всегда (существующее правило
  И7: фильтр видимости к ним не применяется).
- **player** — видит вкладку, если у планеты есть знание
  (`planet.knowledge != null`, появилось от сканера; может быть устаревшим — как
  и поселения). Без знания — «Нет данных — купить отчёт».

**Гейт — решение создателя 2026-09-21 (закрывает вопрос §12.1): политика
остаётся как в абзаце выше** — админ всегда, игрок только при наличии знания.
Инвариант 1 не нарушается: гейт — существующий флаг знания, одной строкой
правила.

**Глубина показа (C4) — выбран вариант «явная дельта в 77a», не «наличие без
деталей».** Обоснование: `77a` §6.2 даёт сканеру поверхность + наличие поселений
(есть/нет + число), а §8.1 — состав снимка знания (`surface_*`,
`settlements_count`); фракций в снимке нет (**на 2026-09-21**; отменено дельтой

## 6. Данные и подписи

- **Ключ типа:** `building_type = 'capital'` (латиница, свободный ключ, как
  `factory`/`relay` в §3.2 спеки фабрик). Класс — «Другое» (не производитель),
  `producer_type_id` отсутствует.
- **Подпись — из словаря ключа, единственное место:** словарь
  `BUILDING_TYPE_LABELS` в `tabs.js` (`{ capital: 'Столица' }`); неизвестный ключ
  показывается как есть (никаких выдуманных имён). В БД имя не хранится (§2.2).
- **Обязательные поля записи:** `planet_id`, `building_type`, `owner_type`,
  `owner_id` (NOT NULL, §2.1).
- **Поля ответа API** (`/api/worlds/{id}/planets`, объект планеты; аддитивно,
  старый контракт не ломается):
  - `planet.factions[]`: `{id, name, type, color, description}`;
  - `planet.buildings[]`: `{id, building_type, owner_type, owner_id}`.
  Строения — отдельный массив (не вложены в фракцию): следующий тип строения
  приедет тем же полем, а связь «владелец ↔ фракция» соединяется на клиенте по
  `owner_id`. Загрузка — по образцу поселений: два запроса на систему
  (`WHERE planet_id = ANY($1)` / `WHERE homeworld_id = ANY($1)`), без обхода
  галактики (инвариант 2). В `GetPlanetsLightByWorldID` (лёгкий путь) не
  добавляем.
- **Числа:** 1–3 фракции на обитаемую планету (генератор, без изменений) →
  столько же столиц; столица ничего не производит, население 0.
- **Содержание/снабжение столицы — отложено, не отменено** (решение создателя
  2026-09-21, закрывает С1). Правило `11_production.md` §11.1.3 «**все постройки
  потребляют постоянно**» и GLOSSARY §5 «Постройка» / §6 «Строение» **остаются в
  силе как целевая модель**; столица — не исключение из правила. Формулировка для
  ГДД: «снабжение отложено — полей пока нет»: в первой итерации у строения нет
  колонок содержания (`population`/`slots`/`data`/`status` — §2.2) и нет пересчёта
  потребления, поэтому потреблять ему физически нечем и нечего списывать.
  Писать в доках «столица ничего не потребляет» / «снабжение не требуется»
  **запрещено** — это зафиксировало бы исключение, которое придётся снимать
  обратно.

## 8. DoD и красные тесты

**Красные тесты (TDD, до кода — `AGENTS.md` §12):**

1. `internal/generator/faction` — `EnsureCapitals` вставляет по одной столице на
   каждую фракцию без столицы: `building_type='capital'`,
   `owner_type='faction'`, `owner_id=factions.id`, `planet_id=homeworld_id`
   (sqlmock).
2. Там же — идемпотентность: при наличии столиц у всех фракций запрос не
   создаёт записей (0); повторный вызов не дублирует.
3. Там же — фракций 0 → 0 столиц, без ошибки.
4. `internal/handlers` — ответ `POST /admin/generate-factions` содержит
   аддитивное поле `capitals`; ветка «нет обитаемых планет» (`total == 0`) отдаёт
   `total:0, capitals:M` **после** проверки Пакмана/мьютекса (C3): при занятом
   пакмане — 409, догон не выполняется; `M` — из возврата `EnsureCapitals`. Тест
   закрепляет **новый** порядок (гейт раньше ветки `total == 0`), а не старое
   расположение.

   привязываются к своим планетам; у планет без них — пусто; выборка идёт

6. `internal/handlers` — `stripPlanetDetails`: игрок без знания получает nil
   `Factions`/`Buildings`; со знанием — получает; admin (без фильтра) — получает.
7. Страховка от ловушки `TRUNCATE`: тест на состав `truncateTables`
   (содержит `buildings`) + комментарий-ссылка на ошибку
   `cannot truncate a table referenced in a foreign key constraint`.
8. e2e-смоук (playwright, `tools/e2e/`, образец `map-check.js`): вход админом →
   карточка планеты → вкладка «Фракции» → видна фракция и строка «Столица» →
   клик раскрывает блок с владельцем.

- Рестарт сервера → миграция `000056` применена, `buildings` пуста.
- «Генерация → Фракции» → в БД `SELECT building_type, owner_type, count(*) FROM

- «Удалить все миры» → `buildings` пуста, ошибки TRUNCATE нет; пакман съел мир

## 13. Кандидат ГД-сущности (Вопрос → Ответ; в текущие числа не входит)

**Вопрос:** столица сейчас — «молчаливая» постройка: показывает владельца и
ничего не предлагает. Не нужна ли отдельная постройка-посредник — **канцелярия
фракции** (тип «другое»)?

**Ответ (кандидат на решение создателя, в текущую итерацию НЕ входит — M6):**
канцелярия — строение, которое служит **точкой публикации уже существующей доски
контрактов** (`11_contracts.md` §11.3.1 «доска контрактов — это разведданные»,
§11.3.4 «публикуется в точке A»): контракт берётся там, где у фракции есть точка
(столица — канцелярия по умолчанию), а не «где угодно». Даёт игроку решение «куда
лететь за работой от фракции» и у карты — смысловую точку интереса.
**Границы (M6):** канцелярия — **только привязка контракта к месту**; второго
реестра контрактов и второго заказчика не заводится (заказчик — существующая
доска/фракция), дублирования сущности контракта нет.

числа/схему итерации не входит (анти-двойной учёт).
