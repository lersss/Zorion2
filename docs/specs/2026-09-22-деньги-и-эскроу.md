## 2. Пространство решений: где живут запертые деньги

Три класса. Выбран класс 2.

| # | Класс | Что даёт | Цена | Вердикт |
|---|---|---|---|---|
| 1 | **Один глобальный эскроу-счёт** (все залоги в одном счёте) | Просто | **Одна горячая строка**: каждый lock/release бьёт в одну запись — при высоком обороте (решение 1) это сериализация (инвариант 1/2) | Отклонён |
| 2 | **Залог хранится на самом контракте** (`contracts.escrow_amount`): при публикации сумма снимается со счёта автора, при выполнении начисляется исполнителю, при провале возвращается автору | Нет горячей строки; сумма уже привязана к контракту; переход статуса и движение денег — одна транзакция | Деньги «вне обращения», пока заперты (учитывается на контракте) | **Выбран** |
| 3 | **Эскроу-счёт на каждый контракт** (`accounts` с `owner_type='contract'`) | Аудит через `accounts` | Лишняя строка-счёт на каждый контракт = удвоение записей при высоком обороте; сумма дублирует `contracts.escrow_amount` | Отклонён |

**Сохранение массы.** Пока залог заперт, деньги вне обращения; их «местоположение» — `contracts.escrow_amount` живых контрактов. Аудит: сумма `escrow_amount` по `status IN ('open','taken')` = изъято из обращения. Это следствие канона «деньги имеют местоположение, но игрок им не управляет — их переносят контракты» (`14_money.md` §14.5.2).

## 3. Счёт: модель

### 3.1. `accounts` — счёт/казна/бюджет

| Поле | Тип | Смысл |
|---|---|---|
| `owner_type` | `text` NOT NULL, CHECK `player`/`faction`/`agent` | Владелец счёта (актор, который держит деньги) |
| `owner_id` | `uuid` NOT NULL | Полиморфно, FK нет |
| `balance` | `bigint` NOT NULL DEFAULT 0, CHECK `>= 0` | Баланс в кредитах (целое — деньги не дробим) |
| `withdrawable` | `bigint` NOT NULL DEFAULT 0, CHECK `>= 0` | Корзина **«заработанное»** (выводимое) — **подмножество** `balance`, а не отдельная сумма. Инвариант `CHECK (withdrawable <= balance)` (§3.3). Корзина «внесённое» отдельной колонки не требует: она не выводится никогда и лежит в обычном `balance` |
| `created_at` / `updated_at` | `timestamptz` | |

PK — **`(owner_type, owner_id)`** (один счёт на актора). Индексов сверх PK не нужно: доступ всегда по ключу.

**Инвариант `withdrawable <= balance` на всех ветках (арифметика).** Запирание: `e = LEAST(w, a) ≤ a` и `e ≤ w` → `w' = w − e ≥ 0`, `b' = b − a ≥ 0`; если `w < a`, то `w' = 0 ≤ b'`; если `w ≥ a`, то `e = a` и `w' = w − a ≤ b − a = b'`. Возврат: `w'' = w' + e ≤ b' + a = b''`. Трата: `w'' = LEAST(w, b − a) ≤ b − a`. Вывод: обе уменьшаются на одну сумму. Инвариант не нарушается нигде.

**Почему `player`/`faction`/`agent`, а не «поселение»/«постройка».** Канон `14_money.md` §14.3.0 и GLOSSARY «Кошелёк поселения»: **кошелёк поселения — лимит на период, а не счёт; баланса у поселения нет** (находка K2). Значит «казна/бюджет поселения» из решения 7 буквально реализовать нельзя. Разрешение — **решение 11: залог платит владелец**. Поселение/постройка как авторы **резолвятся к счёту своего владельца** (§4). Отдельные счёта поселений/построек в итерации 1 **не заводятся** (нет потребителя: у построек нет производства/экономики, находка C5).

### 3.2. `money_operations` — журнал движений по счёту

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `bigserial` PK | |
| `owner_type` / `owner_id` | `text` / `uuid` NOT NULL | Счёт, которого касается операция |
| `delta` | `bigint` NOT NULL | Знаковое изменение (`+`/`−`) |
| `balance_after` | `bigint` NOT NULL | Баланс после операции (снимок для аудита) |
| `kind` | `text` NOT NULL | Тип, **открытый список**: `escrow_lock`, `escrow_release`, `escrow_return`, `contract_work_earn`, `admin_seed`, (позже `mint`, `salary`, `transfer`) |
| `contract_id` | `uuid` NULL | Контракт-источник (FK нет — журнал переживает удаление) |
| `occurred_at` | `timestamptz` NOT NULL | |
| `created_at` | `timestamptz` DEFAULT `now()` | |

Индекс: `idx_money_operations_owner (owner_type, owner_id, occurred_at DESC)`.

**Зачем журнал, если есть `contract_log`.** Это **разные оси**: `contract_log` — жизнь контракта (что случилось с ним), `money_operations` — движение по счёту (что случилось с деньгами актора). Один залог даёт запись в обоих; журнал счёта нужен и для не-контрактных движений (будущие эмиссия/зарплата), и как «история операций» игрока. Балансы приватны (`14_money.md` §14.4), но **свою** историю игрок видеть вправе.

**Решение (О-д4):** игрок видит **свой баланс и свою историю `money_operations`** (`GET /me/money` — баланс + операции). Чужие балансы и чужие истории не видны никогда (`14_money.md` §14.4). Приватность соблюдена: доступ только по своему `owner_id`.

### 3.3. Две корзины (подряд)

Канон `15_monetization.md` §15.4.1: две корзины — **«внесённое»** (куплено за реальные деньги, не выводится никогда) и **«заработанное»** (получено за исполненный подряд, выводится). Метка снимается **ровно в момент оплаты чужого труда**, не передаётся и сгорает при трате.

**Решение (п. 4 правок): минимальный признак закладываем сразу.** Обоснование — **необратимость информации**: после того как выводимые и обычные кредиты смешаются в одном балансе, восстановить, какие были заработаны подрядом, невозможно. Поздняя миграция `accounts` не смогла бы пометить уже зачисленные награды, а `contracts.funding` нельзя достоверно бэкфиллить. Поэтому:

- `contracts.funding` (`2026-09-22-контракт-модель-сущности.md` §4.1) — признак финансирования, ставится при публикации;
- `accounts.withdrawable` — корзина «заработанное»;
- release залога по подряду зачисляет в `withdrawable` (лог `contract_work_earn`), обычный — в `balance`;
- **сама механика подряда** (внесение реальных денег, покрытие ≈ 50 %, доля оператора, вывод, `15.5`, интерфейс `15.4.4`) — **позже**, отдельной спекой; здесь только поля, чтобы счёт и контракт не переделывать.
- **Перелёт подрядом быть не может** (`15_monetization.md` §15.4.2: «нет» — малый профит намеренно). Для него `funding='regular'` всегда.

**Правило списания — явное (О-д6).** `withdrawable` — **не отдельная сумма, а потолок выводимого внутри `balance`** (инвариант `withdrawable <= balance`). Так «потолок» и канон «метка сгорает при трате» совместимы без второго курса внутри игры.

**Залог метку не сжигает (исправление п. 1).** Канон `15_monetization.md` §15.4.1: метка снимается **ровно в момент оплаты чужого труда**. Запирание залога — не оплата (деньги могут вернуться), поэтому статус «заработанности» запертых денег **сохраняется** и хранится на контракте:

- `contracts.escrow_withdrawable` (`2026-09-22-контракт-модель-сущности.md` §4.1) — выводимая доля залога на момент запирания;
- при запирании метка **переносится** с баланса автора на контракт (не сгорает);
- при возврате — **восстанавливается** автору;
- метку двигает только **выпуск залога** (реальная оплата труда) — тогда она сгорает вместе с ушедшими деньгами.

| Операция | `balance` | `withdrawable` | Метка |
|---|---|---|---|
| Зачисление обычной награды | `+reward` | без изменений | — |
| Зачисление награды подряда (`contract_work_earn`) | `+reward` | `+reward` | появляется |
| **Запирание залога** (`escrow_lock`) | `−amount` | `−e`, где `e = LEAST(withdrawable, amount)`; `e` пишется в `escrow_withdrawable` | **переносится на контракт** |
| **Возврат залога** (`escrow_return`: отмена/истечение/удаление мира) | `+amount` | `+escrow_withdrawable` | **восстанавливается** |
| **Выпуск залога** (`escrow_release`: оплата труда исполнителю) | автор уже списан | `escrow_withdrawable` **не возвращается** | **сгорает** (оплата чужого труда); исполнителю: подряд → `+withdrawable`, обычный → только `balance` |
| **Прочая трата** (покупка, обычный расход) | `−amount` | `min(withdrawable, balance_after)` | **сгорает** |
| **Вывод** (позже, `15.5`) | `−amount` | `−amount` | выводится |

Следствия:

- «Получил выводимое — либо выводи, либо трать как обычные деньги» (`15_monetization.md` §15.4.1) выполняется: трата урезает `withdrawable`, оплата труда сжигает его, возврат залога его сохраняет.
- Запирание/возврат/выпуск — **одним** `UPDATE` по `accounts` c проверкой (`balance >= $amount` для запирания), инвариант 1; `withdrawable` пересчитывается тем же оператором.
- Инвариант `withdrawable <= balance` держится на всех ветках: при запирании `e ≤ amount` и `e ≤ withdrawable`; при возврате `+e` приходит вместе с `+amount` (см. арифметику в §3.1-замечании ниже).
- «Внесённое» (куплено за реальные деньги) — просто `balance` без выводимой части: вывести нельзя никогда, потому что `withdrawable` растёт только от подряда.
- Недопустимое состояние `withdrawable > balance` невозможно (CHECK + пересчёт на каждой ветке).

> Это уточняет пример менеджера («`withdrawable` — только потолок, метка не сгорает») до самосогласованного вида: потолок урезается при **трате** и сгорает при **оплате труда**, но **восстанавливается** при возврате залога — иначе игрок, заперший залог из заработанного, навсегда терял бы выводимую часть (баг п. 1).

### 3.4. Создание счёта в жизненном цикле актора

**Проблема (п. 3 правок).** Бэкфилл в миграции покрывает только существующих игроков; новый игрок остаётся без счёта, и основная петля «новичок берёт перелёт → получает оплату» ломается на зачислении.

**Правило:** счёт создаётся **при первом участии** и **лениво гарантируется** (идемпотентно, `INSERT ... ON CONFLICT (owner_type, owner_id) DO NOTHING`).

| Актор | Момент | Действие |
|---|---|---|
| **Игрок** | Регистрация (`/register`, `internal/handlers/auth_handlers.go`) | `ensureAccount('player', userID)` в той же транзакции, что и создание пользователя |
| **Игрок** | Первый аутентифицированный запрос (страховка) | `ensureAccount` — покрывает старых игроков и сбои |
| **Игрок, фракция** | Миграция `000061` (§7) | Бэкфилл существующих |
| **Агент-исполнитель** | **Взятие контракта** (транзакция `take`) и **перед любым начислением** (`escrow_release`) | `ensureAccount('agent', agentID)` — **агент не аутентифицируется**, ленивая страховка «на запрос» его не покрывает; поэтому счёт гарантируется в пути контракта |
| Все | Старт сервера | Бэкфилл-проход (как `travel.Restore`) — страховка от рассинхрона |

**Бэкфилла счетов агентов нет намеренно:** агентов сотни тысяч (`npc_agents`), а счёт нужен только тому, кто реально взял контракт и получает деньги. Счёт появляется при первом участии — учёт массы сходится (доход агента не теряется: `ensureAccount` вызывается **в той же транзакции**, что и начисление, до `+balance`).

### 3.5. Кошельки при удалении контрактов и очистке вселенной

Инвариант возврата залога — `2026-09-22-контракт-модель-сущности.md` §6.5.

**Политика кошельков при полной очистке вселенной (выбор п. 1 правок):**

> **Кошелёк игрока сохраняется; залог живых контрактов возвращается автору; счета фракций удаляются.**

Обоснование:

- `users` при `ClearUniverse` **не очищаются** (очистка идёт `TRUNCATE` без `CASCADE` именно ради сохранения `users`, `admin_universe.go` §«ОБЩАЯ ОЧИСТКА»). Кошелёк — имущество игрока, и он должен переживать административную очистку так же, как сам аккаунт.
- Канон (инвариант 4, `GD_PROMPT.md`): «офлайн стоит прогресса, но не имущества» — потерять построенное можно от войны или своего решения, но не от чужого действия. Очистка вселенной — действие администратора, а не игрока.
- Счета фракций удаляются: фракции перегенерируются с новыми id, старые счета стали бы сиротами (у `accounts.owner_id` нет FK). Игроки и фракции — разные судьбы при очистке, это и есть причина выбора.

**Технически:** `accounts` **не входит** в `truncateTables` целиком; после `TRUNCATE` удаляются `accounts WHERE owner_type='faction'` (и, при появлении, `agent`). `money_operations` — очищается (журнал привязан к вселенной), либо сохраняется по игрокам; предложение: очищать (не хранить историю съеденной вселенной).

## 4. Резолв плательщика (автор → счёт)

Автор полиморфный (`contracts.author_type`), но платит **владелец** (решение 11):

| `author_type` | Кто платит залог | Как резолвится |
|---|---|---|
| `player` | сам игрок | `account('player', author_id)` |
| `faction` | сама фракция | `account('faction', author_id)` |
| `building` | **владелец постройки** | `buildings.owner_type`/`owner_id` → рекурсивно к `player`/`faction`/`agent` |
| `agent` | **фракция-владелец агента** | `npc_agents.owner_faction_id` → `account('faction', …)` (§6). В итерации 1 агент-автор не публикует — ветка не вызывается |

**Строки `settlement` в резолве нет.** Поселение не является плательщиком: канон `14_money.md` §14.3.0 — «кошелёк поселения — лимит на период, а не счёт; баланса у поселения нет». Счёта поселений/построек в итерации 1 не существует (решение 11), поэтому и резолвить нечего. Если поселение когда-нибудь получит владельца, платить будет **владелец** — новая строка резолва появится вместе с ним, а не сейчас (`GD_PROMPT.md`: сущность без потребителя не вводим).

Функция резолва — одна точка (`resolvePayerAccount(authorType, authorID)`); **рекурсия ограничена глубиной 1** (постройка → владелец; владелец — игрок/фракция/агент). Если владелец сам является постройкой — это ошибка данных, а не цепочка.

**Проверка платёжеспособности** — при публикации: `UPDATE accounts SET balance = balance - $amount WHERE owner_type=$1 AND owner_id=$2 AND balance >= $amount`; `RowsAffected == 0` → отказ «недостаточно средств». Проверка и списание — **одним** оператором (инвариант 1, `AGENTS.md` §0).

## 5. «Бесконечная» казна фракций (заглушка)

Решение 12: деньги фракций практически бесконечны на этот релиз.

- Счёт фракции заводится с балансом-заглушкой `FactionBalanceSeed = 10^15` кредитов (очень большое число, но **число**, не флаг и не спец-ветка — решение 12 дословно).
- Бэкфилл миграции: `INSERT INTO accounts (owner_type, owner_id, balance) SELECT 'faction', id, 10^15 FROM factions ON CONFLICT DO NOTHING`.
- Экономики фракций нет: наполнение/расход казны не моделируются (позже).

**Предупреждение (см. §9):** это осознанная заглушка, конфликтующая с замкнутой денежной массой канона.

## 6. Бюджет агента

Решение 11: агент берёт бюджет у фракции-владельца; бюджет агента — минимально.
**Решение создателя (новое, порция 1):** владельца-фракцию агенту **даём** (связь заводим), но в итерации 1 агент — **только исполнитель** (заказывать не может).

**Связь (новая).** У `npc_agents` (000026) связи с фракцией нет — модель мирокоординатная, без бюджета (находка C2). Заводим:

- `ALTER TABLE npc_agents ADD COLUMN owner_faction_id UUID NULL REFERENCES factions(id) ON DELETE SET NULL` (миграция `000061`, §7);
- заполняется при массовой генерации агентов (26a.1) и, при необходимости, лениво — фракция ближайшей планеты агента;
- `ON DELETE SET NULL`: фракция перегенерирована/удалена — агент остаётся без владельца, не ломая FK.

**Итерация 1 — агент только исполнитель:**

- Агент получает награду за исполненный контракт **на свой счёт** `account('agent', id)` — это не эмиссия (переток, канон `14_money.md` §14.3.0), денежная масса не растёт.
- Агент **не публикует** контракты → его бюджет (`owner_faction_id`) в итерации 1 не расходуется; поле заводится заранее, чтобы агент-автор не потребовал переделки счёта.
- **Позже** (агент-автор): бюджет агента = счёт владельца-фракции (резолв §4, `author_type='agent'` → `owner_faction_id` → `account('faction', …)`). Тогда резолв плательщика станет определён полностью; в итерации 1 он для агента-автора **не вызывается**.

## 7. Миграция `000061_money.sql`

1. `CREATE TABLE accounts` (§3.1) + `CHECK (balance >= 0)`, `CHECK (withdrawable >= 0)`, `CHECK (withdrawable <= balance)` (§3.3).
2. `CREATE TABLE money_operations` (§3.2) + индекс.
3. `ALTER TABLE npc_agents ADD COLUMN owner_faction_id UUID NULL REFERENCES factions(id) ON DELETE SET NULL` (§6).
4. **Бэкфилл:** счёт каждому существующему игроку (`owner_type='player'`) с балансом `PlayerBalanceSeed` и каждой фракции с `FactionBalanceSeed` (§5). `ON CONFLICT DO NOTHING` — идемпотентно.
5. Идёт **до** `000062_contracts.sql`.
6. Аддитивна для денег (новые таблицы); единственная правка существующей таблицы — колонка `npc_agents.owner_faction_id` (NULL, без бэкфилла — заполняется генератором/лениво).

### 7.1. Кошельки при очистке вселенной

См. §3.5: `accounts` **не** в `truncateTables`; после `TRUNCATE` удаляются счета фракций; залог возвращается до удаления (`2026-09-22-контракт-модель-сущности.md` §6.5).

## 8. Числа-заглушки (вход для @balancetester)

> **Все числа ниже — заглушки «калибровать позже»** (решение создателя: «неважно, потом сбалансируем»). Они **не** согласованы между собой и не являются эталоном; цены перелёта — `2026-09-22-контракт-перелёт-и-доска.md` §4.

| Параметр | Значение-заглушка | Почему | Эталон |
|---|---|---|---|
| `FactionBalanceSeed` | `10^15` | Решение 12 «очень большое число» | Решение создателя |
| `PlayerBalanceSeed` | `10^4` (10 000 кредитов) | Стартовый капитал новичка | **Нет эталона** — калибровать |
| Тип `balance` | `bigint`, целое | Деньги не дробим; масштаб кредита не задан | Предположение |
| Тип `withdrawable` | `bigint`, целое, DEFAULT 0 | Корзина «заработанное» (§3.3) | Канон `15_monetization.md` §15.4.1 |

**`PlayerBalanceSeed` и цена перелёта — независимые заглушки (исправление).** Прежняя редакция обосновывала `10^4` тем, что «цена ~10²–10³», но фактическая формула перелёта даёт ~1,65·10³ (короткий прыжок) — то есть `10^4` покрывает лишь ~6 коротких прыжков и **не покрывает дальний** (до ~1,8·10⁵, §4). Числа **не согласованы намеренно**: калибровать `k_price` и `PlayerBalanceSeed` **вместе**, позже. Масштаб кредита в проекте не задан (легаси-`reward` — `integer` без калибровки).

## 9. Конфликт с каноном эмиссии (warning для создателя)

Решение 12 (казна фракций ∞) противоречит канону, и это надо назвать явно (находка C1):

- `14_money.md` §14.1: система **замкнута** — «денежная масса задаётся один раз при генерации и дальше только перераспределяется». NPC-агент — не эмитент.
- §14.2 прямо **отклоняет** «награды за контракты NPC-фракций» как источник: это «тот же внешний покупатель в шляпе» и делает NPC привилегированными.
- Бесконечная казна фракции = **внешний эмитент** в обход §14.2: награда за контракт фракции создаёт деньги из ничего, ломая привязку эмиссии к реальному выпуску (§14.2) и «первый накопивший богатеет» (§14.1).

**Статус:** решение создателя принято сознательно («на этот релиз, экономика фракций позже»). Спека **не переписывает** канон молча: помечает расхождение и что делать (**распоряжение менеджера — внести в канон**, О-д3):

- в `14_money.md` §14.2 — пометка «временно, до экономики фракций: казна фракции — заглушка-источник» (дельта на @dispatcher);
- счётчик-наблюдение: сумма `money_operations` с `kind IN ('escrow_release')` от фракций = объём «напечатанного» — телеметрия для @balancetester.

## 10. Что не делать

- Не вводить вторую валюту, курсы, «деньги имеют место» (канон `14_money.md` §14.5.1; `GD_PROMPT.md` «не изобретать вторую валюту»).
- Не заводить счёт поселению/постройке (канон: кошелёк поселения — лимит, не счёт; §3.1).
- Не показывать балансы никому (канон §14.4); платёжеспособность доказывается эскроу.
- Не делать дробных денег (`float`) — только целые кредиты.
- Не строить эмиссию/зарплаты/налоги — итерация 1 это только счёт + залог.
- Не заводить «бюджет с пополнением» (канон §14.6.3) — форма эскроу позже.
