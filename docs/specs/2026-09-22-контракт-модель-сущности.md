## 1. Задача

Создатель (дословно, 2026-09-22): «*как нам сделать сущность "контракт"? как ее хранить, какие поля будут, типы — и тд?*».

Ответ — этот документ. Три опоры:

1. **Оборот высокий** (решение 1): контракты массово открываются/закрываются/выполняются/отменяются. Модель обязана держать поток записей и не деградировать по стоимости с ростом галактики (инвариант 2).
2. **Место — планета** (решение 4): витрина — карточка планеты, вкладка «Задания/Контракты»; привязка «к миру» убирается.
3. **Авторы — все сразу** (решение 3): игрок, фракция, постройка, агент; автор полиморфный.

Существующий муляж `assignments` (миграции `001_init`, `000010`, `000035`) — отправная точка, но его схема не выдерживает: место привязано к `world_id`, нет цены/залога/требований/исполнителя/журнала. Развиваем в `contracts`, а не латаем (`2026-09-22-контракт-перелёт-и-доска.md` §5).

## 2. Архитектурный фильтр: природа / владелец / расширяемость

Обязательная сверка (`.opencode/agents/designer.md` §3; `PITFALLS.md` «Событие против лог»).

| Вопрос | Ответ | Следствие для схемы |
|---|---|---|
| **Природа** | Контракт — **состояние** (живёт и меняет статус). Его жизнь — **лог** (взял/поставил/провалил/отменён) | Таблица `contracts` (состояние) + **отдельная** таблица `contract_log` (лог). В общий `events` не пишем — решение создателя 10: общую систему событий не строим, мёртвый общий журнал не оживляем |
| **Владелец** | Записей **много у разных объектов**: автор полиморфный (игрок/фракция/постройка/агент), исполнитель (игрок/агент) | `author_type`+`author_id`, `executor_type`+`executor_id` (полиморфно, без FK) — как `buildings.owner_type`/`owner_id` (000056) |
| **Расширяемость** | **Открытый список типов** (поставка, разведка, охрана, перевозка, операция…) | Не колонка-на-тип, а `type` + `payload JSONB` («нагрузка типа»). Второй тип влезает без миграции |
| **Требования** | Много строк на контракт, открытый список видов | Дочерняя таблица `contract_requirements` |

**Правило «сущность с двумя экземплярами — не сущность»** (`GD_PROMPT.md`): `contracts` — это поток записей (миллионы), `contract_requirements`/`contract_log` — тоже потоки. Отдельная сущность оправдана. `contract_log` — **по духу и структуре** как `settlement_log` (000024, «лог, не поля у поселения», решение создателя 2026-09-14, идея 18b), но **не буквально**: у `settlement_log` FK на владельца с `ON DELETE CASCADE`, у `contract_log` **FK намеренно отсутствует** — лог переживает удаление контракта (§4.3).

## 3. Пространство решений (разворот подходов)

Пять разных **классов** подхода к хранению (не вариации одного). Выбран класс 1.

| # | Класс | Что даёт | Цена | Вердикт |
|---|---|---|---|---|
| **1** | **Одна таблица `contracts` + `type` + `payload JSONB` + дочерние `requirements`/`log`** | Открытый список типов без миграций; горячий запрос «планета + статус» индексируется; требования машинно проверяемы; второй тип влезает в ту же схему | `payload` не типизирован БД (валидация в коде); связи внутри JSONB не защищены FK | **Выбран** |
| **2** | **Таблица на тип** (`travel_contracts`, `supply_contracts`, …) + общий заголовок | Типизация payload колонками, FK на связи | Каждый новый тип — миграция и второй `JOIN`; доска агрегирует все источники — `UNION` по N таблицам; **нарушает «открытый список»** (`GD_PROMPT.md` «Чего не делать») | Отклонён |
| **3** | **Event-sourcing**: состояние контракта выводится реплеем `contract_log` | Единый источник, полная история | Доска — реплей потока на каждое чтение (инвариант 2 нарушен); общую систему событий не строим (решение 10); «мёртвый груз» при высоком обороте | Отклонён |
| **4** | **EAV** для требований (свойство → значение отдельной строкой на каждую ось) | Максимальная гибкость | Проверка окна — N `JOIN`; инвариант 2 под вопросом; `requirements` и так строковый, EAV не добавляет ничего | Отклонён |
| **5** | **Контракт целиком в одной `JSONB`-колонке** | Просто писать | Нет индексов под горячий запрос «планета + статус» (GIN по JSONB дороже и хуже селективен); нет CHECK на деньги; доска — seq-scan | Отклонён |

Класс 1 держит три опоры: оборот (частичные индексы), открытые типы (`type`+`payload`), машинную проверку требований (`contract_requirements`).

## 4. Модель

### 4.1. `contracts` — состояние контракта

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `id` | `uuid` | PK, `gen_random_uuid()` | |
| `type` | `text` | NOT NULL | Тип контракта, **открытый список** (`travel` — первый). CHECK в БД **не ставим** (открытый список, `GD_PROMPT.md`); валидация — в коде по реестру обработчиков типа |
| `author_type` | `text` | NOT NULL, CHECK `player`/`faction`/`building`/`agent` | Полиморфный автор (решение 3). **Намеренно шире `buildings.owner_type`**: у `buildings` владелец — `player`/`faction`/`agent`, здесь добавлен `building` (заказчик-постройка). Не тот же класс значений, а расширение |
| `author_id` | `uuid` | NOT NULL | FK нет намеренно (полиморфизм) |
| `publication_planet_id` | `uuid` | NOT NULL, FK `planets(id) ON DELETE CASCADE` | **Место публикации — планета** (решение 4). Витрина — её карточка |
| `title` | `text` | NOT NULL | Заголовок |
| `description` | `text` | NOT NULL DEFAULT `''` | Описание |
| `payload` | `jsonb` | NOT NULL DEFAULT `'{}'` | **Нагрузка типа**: `travel` → `{dest_world_id, dest_planet_id, from_world_id}` (§4.4 спеки перелёта) |
| `reward` | `bigint` | NOT NULL, CHECK `>= 0` | Цена в кредитах. Валюта единая — **поля «валюта» нет** (решение 9, канон `14_money.md` §14.5.1) |
| `funding` | `text` | NOT NULL DEFAULT `'regular'`, CHECK `regular`/`contract_work` | **Признак финансирования**: обычный контракт / **подряд** (оплачен реальными деньгами). Канон `11_contracts.md` §11.3.1: подряд — не восьмой тип, а признак финансирования; `15_monetization.md` §15.4 — «две корзины». Минимальный признак закладываем сразу: без него нельзя восстановить, какие деньги выводимы (п. 4 правок) |
| `escrow_amount` | `bigint` | NOT NULL DEFAULT 0, CHECK `>= 0` | Запертая сумма (залог). Модель счёта — `2026-09-22-деньги-и-эскроу.md` |
| `escrow_withdrawable` | `bigint` | NOT NULL DEFAULT 0, CHECK `>= 0` | **Выводимая доля залога** — часть `escrow_amount`, которая была «заработанной» у автора в момент запирания. Нужна, чтобы возврат залога **восстанавливал метку**, а не сжигал её (`2026-09-22-деньги-и-эскроу.md` §3.3). `<= escrow_amount` |
| `escrow_kind` | `text` | NOT NULL DEFAULT `'deposit'` | Форма эскроу: `deposit` (залог) — итерация 1; `budget`/`share` — позже (канон `14_money.md` §14.6.2/§14.6.3) |
| `status` | `text` | NOT NULL DEFAULT `'draft'`, CHECK `draft`/`open`/`taken`/`completed`/`cancelled`/`expired` | Жизненный цикл, §5 |
| `visibility` | `text` | NOT NULL DEFAULT `'public'`, CHECK `public`/`direct` | Публичная доска / прямой контракт |
| `direct_target_type` | `text` | NULL, CHECK `player`/`faction`/`building`/`agent` | Адресат прямого контракта (только при `visibility='direct'`) |
| `direct_target_id` | `uuid` | NULL | Адресат прямого контракта |
| `executor_type` | `text` | NULL, CHECK `player`/`agent` | Исполнитель (решение 6: один). NULL = не взят |
| `executor_id` | `uuid` | NULL | |
| `taken_at` | `timestamptz` | NULL | Момент взятия |
| `expires_at` | `timestamptz` | NOT NULL | Срок. Тип может **перебазировать** его при взятии (правило типа: у `travel` срок исполнения отсчитывается от взятия — `2026-09-22-контракт-перелёт-и-доска.md` §4.3) |
| `created_at` | `timestamptz` | NOT NULL DEFAULT `now()` | |
| `updated_at` | `timestamptz` | NOT NULL DEFAULT `now()` | |

**Инварианты на уровне БД:**

- `CHECK (visibility = 'public' OR direct_target_id IS NOT NULL)` — прямой контракт без адресата невозможен.
- `CHECK (status NOT IN ('taken','completed') OR executor_id IS NOT NULL)` — взятый/выполненный контракт имеет исполнителя.
- `CHECK (status NOT IN ('open','taken') OR escrow_amount > 0)` — **живой** контракт всегда с залогом (публикация и запирание атомарны, §5). Ослаблено до «живых» статусов: закрытый контракт (залог уже возвращён/выпущен) CHECK не роняет.
- `CHECK (escrow_withdrawable <= escrow_amount)` — выводимая доля залога не больше самого залога.
- `escrow_amount` **не обнуляется** при release/return — это сумма, запертая при публикации (исторический факт). Состояние эскроу выводится из `status`; «живой залог» = `SUM(escrow_amount) WHERE status IN ('open','taken')`. Обнуление сломало бы CHECK и стёрло историю.

**Чего в таблице нет (и почему):**

- `world_id` — убран (решение 4). Система выводится из `publication_planet_id → planets.world_id`.
- `currency` — не вводим (решение 9).
- `effects JSONB` (как у муляжа) — заменён `payload` (нагрузка типа) + `contract_log` (след). `effects` был бесхозным мешком.
- `deliveries`/участники — **не заводим** (решение 6: исполнитель один; частичной поставки нет). Таблица появится вместе с операцией/мульти-исполнителем (`GD_PROMPT.md`: сущность без потребителя не вводим).

### 4.2. `contract_requirements` — окно свойств (требования)

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `bigserial` | PK |
| `contract_id` | `uuid` NOT NULL, FK `contracts(id) ON DELETE CASCADE` | |
| `pos` | `int` NOT NULL | Порядок; `UNIQUE (contract_id, pos)` |
| `kind` | `text` NOT NULL | Вид требования, **открытый список**: `axis` (ось свойств) / `goods` (товар/ресурс каталога) / `gear` (снаряжение, напр. двигатель) |
| `subject` | `text` NOT NULL | Код оси (`axis`) / id товара каталога строкой (`goods`) / **имя параметра** снаряжения (`gear`), напр. `speed_factor` — не имя слота (`engine`) |
| `op` | `text` NOT NULL, CHECK `ge`/`le`/`eq`/`in` | Сравнение |
| `threshold_num` | `double precision` NULL | Числовой порог (температуры — **в K**; UI — °C, §7) |
| `threshold_text` | `text` NULL | Порог вне чисел (код категории, класс) |
| `quantity` | `bigint` NULL | Объём требования (поставка); NULL — неприменимо |
| CHECK | `threshold_num IS NOT NULL OR threshold_text IS NOT NULL OR op = 'in'` | Требование без порога невалидно |

**Интервал = две строки.** Канон `05_economy.md` §5.2.2 формулирует требования как «твёрдость ≥ 70 **и** плотность ≤ 50» — это две односторонние границы, а не одна двусторонняя. Односторонняя строка проще, и интервал выражается без дополнительной семантики.

**Объём (`quantity`)**: для поставки несёт ровно одна строка требования (предмет поставки); строки-оси несут NULL. Это **временно**, до единого языка с рецептами (§7).

**Потребитель в итерации 1 — только `kind='gear'`** (требование к двигателю у перелёта, канон `11_contracts.md` §11.3.4). `axis`/`goods` проектируются, но их потребитель (поставка) — позже; таблица заводится целиком, потому что это одна схема и второй вид в неё влезает.

### 4.3. `contract_log` — история контракта

Структура — **по духу `settlement_log`** (000024): отдельная таблица записей, запись без даты не существует. **Отличие намеренное:** у `settlement_log` FK на владельца `ON DELETE CASCADE`, здесь FK **нет** — лог переживает удаление контракта (архив, §6.4).

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `uuid` PK `gen_random_uuid()` | |
| `contract_id` | `uuid` NOT NULL | FK нет намеренно: **лог переживает удаление контракта** (как история) |
| `type` | `text` NOT NULL | Тип записи, **открытый список**: `published`, `taken`, `completed`, `cancelled`, `expired`, `failed`, `escrow_locked`, `escrow_released`, `escrow_returned` |
| `actor_type` | `text` NULL | Кто вызвал: `player`/`agent`/`system` |
| `actor_id` | `uuid` NULL | |
| `data` | `jsonb` NOT NULL DEFAULT `'{}'` | Детали (сумма, откуда/куда) |
| `occurred_at` | `timestamptz` NOT NULL | Когда произошло |
| `created_at` | `timestamptz` DEFAULT `now()` | |

Индекс: `idx_contract_log_contract (contract_id, occurred_at DESC)`.

**`data.reason`** у `escrow_returned` различает причины возврата: `expired`, `cancelled`, `world_deleted` (принудительный возврат при удалении миров, §6.5). Новых типов ради этого не заводим.

## 5. Жизненный цикл

```
             создать
                │
            ┌───▼───┐   опубликовать (залог: lock)   ┌──────┐   взять   ┌───────┐
            │ draft │ ─────────────────────────────► │ open │ ────────► │ taken │
            └───────┘                                └──┬───┘           └──┬────┘
                                                        │                  │
                              отменить (залог: return)  │                  │ выполнить
                                        ┌───────────────┘                  │ (залог: release)
                                        ▼                                  ▼
                                  ┌───────────┐                     ┌───────────┐
                                  │ cancelled │                     │ completed │
                                  └───────────┘                     └───────────┘
                                                        │                  │
                                    истёк срок ─────────┘                  └──── истёк срок
                                  (залог: return, лог `expired`)           (залог: return, лог `failed`)
                                                        ▼
                                                   ┌─────────┐
                                                   │ expired │
                                                   └─────────┘
```

| Из | Действие | В | Кто | Деньги | Запись лога |
|---|---|---|---|---|---|
| — | создать черновик | `draft` | автор | — | — |
| `draft` | опубликовать | `open` | автор | залог: **lock** со счёта автора | `published` + `escrow_locked` |
| `draft` | удалить | — | автор | — | — |
| `open` | взять | `taken` | игрок/агент | — | `taken` |
| `open` | отменить | `cancelled` | **автор** | залог: **return** автору | `cancelled` + `escrow_returned` |
| `open` | истёк срок | `expired` | система (лениво, §6.3) | залог: **return** автору | `expired` + `escrow_returned` |
| `taken` | выполнить | `completed` | система (событие типа) | залог: **release** исполнителю | `completed` + `escrow_released` |
| `taken` | истёк срок | `expired` | система (лениво) | залог: **return** автору | **`failed`** + `escrow_returned` |
| `taken` | отменить | — | **никто** | — | — |

**Правила (канон `11_contracts.md` §11.3.1, `14_money.md` §14.5.3):**

- **Отмена только до взятия.** После взятия отмены нет — только провал.
- **Провал = истечение взятых.** Отдельного статуса `failed` нет: провал — это `expired` при `executor_id IS NOT NULL`. Различие живёт **в логе** (`failed` вместо `expired`): разные тексты, репутация, след исполнителя. Отдельный статус дублировал бы `expired` без новой информации.
- **Залог запирается при публикации**, не при взятии (канон §14.5.3).
- **Провал возвращает залог автору** (исполнитель теряет топливо/время, автор — время).

**Атомарность (инвариант 1, `AGENTS.md` §0).** Каждый переход — **один** `UPDATE ... WHERE id = $1 AND status = $old` в транзакции; `RowsAffected == 0` = гонка, действие отвергнуто. Никаких `if status == open { update }` в коде. Проверка+действие атомарны на уровне БД.

## 6. Оборот

### 6.1. Горячий запрос

Доска планеты: `WHERE publication_planet_id = $1 AND status = 'open' AND expires_at > now() ORDER BY created_at DESC`.

### 6.2. Индексы

| Индекс | Определение | Зачем |
|---|---|---|
| `idx_contracts_board` | `(publication_planet_id, created_at DESC) WHERE status = 'open'` | Горячий запрос доски; **частичный** — закрытые контракты не занимают индекс |
| `idx_contracts_expiry` | `(expires_at) WHERE status IN ('open','taken')` | Ленивое истечение (§6.3) и восстановление при старте |
| `idx_contracts_author` | `(author_type, author_id, status)` | «Мои контракты» (все статусы) |
| `idx_contracts_executor` | `(executor_type, executor_id) WHERE executor_id IS NOT NULL` | «Мои взятые» |
| `idx_contracts_direct_target` | `(direct_target_type, direct_target_id) WHERE visibility = 'direct'` | Прямые контракты адресату |

Частичные индексы — ключ к обороту: закрытые контракты (их большинство со временем) **не попадают** в индекс доски.

### 6.3. Ленивое истечение (без тика)

Как у населения и полётов (`PITFALLS.md`; `99.2.7` §«чем проверять»): тика нет, срок истекает **на чтении**, в области запроса.

`ExpireDue(scope)` — одна транзакция:

1. `UPDATE contracts SET status='expired', updated_at=now() WHERE status IN ('open','taken') AND expires_at <= now() AND <scope> RETURNING id, executor_id, author_type, author_id, escrow_amount` — `<scope>` = `publication_planet_id = $1` **или** `id = $1` (точечно, при проверке конкретного контракта).
2. Для каждой строки — возврат залога автору + запись `contract_log` (`failed` при непустом `executor_id`, иначе `expired`).

**Стоимость ограничена контрактами одной планеты** (или одного контракта) — не зависит от размера галактики (инвариант 2). `idx_contracts_expiry` делает выборку по сроку дешёвой.

**Кто вызывает:** чтение доски планеты (scope = планета); проверка перелёта при прибытии (scope = контракт); `Restore` при старте сервера (пакетно по `expires_at`, как `travel.Restore`).

### 6.4. Архив / чистка

- Закрытые контракты **не удаляются** в итерации 1: история = `contract_log` + строка состояния; частичный индекс держит их вне горячего запроса.
- **Предложение на потом** (не входит в итерацию 1): админ-чистка закрытых контрактов старше N дней. Так как `contract_log.contract_id` без FK, лог переживает чистку; контракт удаляется с `requirements` (CASCADE). Отдельный «архив» не заводим — `contract_log` и есть архив (`GD_PROMPT.md`: не плодить сущности).

### 6.5. Возврат залога при удалении контрактов (инвариант)

**Проблема (крупная, порция 1 п. 1).** Кошельки игроков переживают очистку вселенной, а контракты удаляются каскадом (`contracts.publication_planet_id → planets ON DELETE CASCADE`) — запертый залог **пропадает**. Деньги исчезают из мира без следа, ломая сохранение массы (`2026-09-22-деньги-и-эскроу.md` §2).

**Инвариант:** **любой** путь удаления контрактов сначала возвращает залог живых контрактов автору (одной транзакцией), потом удаляет.

**Обязательные пути (все — в списке потребителей, `2026-09-22-контракт-перелёт-и-доска.md` §5):**

| Путь | Код | Транзакция | Что делает |
|---|---|---|---|
| Очистка вселенной | `clearUniverseTx` (`admin_universe.go`) | уже внутри tx вызывающего (`Begin/Commit`) | возврат **до** `TRUNCATE`, в той же tx |
| Генерация вселенной | `GenerateUniverse` (`admin_universe.go`, через `clearUniverseTx`) | то же | то же |
| Гипотезы | `admin_hypothesis.go` (через `clearUniverseTx`) | то же | то же |
| Генерация планет | `GeneratePlanets` (`DELETE FROM planets`, `admin_universe.go`) | **`h.db.Exec` вне tx — обернуть в `Begin/Commit`** | возврат по затронутым планетам + `DELETE` в **одной** tx |
| Перегенерация планет | `RegeneratePlanets` (`DELETE FROM planets WHERE world_id = ANY($1)`) | **вне tx — обернуть** | то же |
| Удаление мира | `admin_worlds.go` (`DELETE FROM worlds WHERE id = $1`) | обернуть, если ещё нет | то же |
| Пакман | `admin_pacman.go` (`DELETE FROM worlds WHERE id = ANY($1)`) | батч-транзакция джоба | то же + очистка мёртвой цели (п. 5) |

**Реализация — атомарный статусный flip (исправление п. 4).** Хелпер `ReturnEscrowForContracts(scope, reason)` **не** делает «прочитал — вернул»: он переводит контракты **одним** оператором с проверкой статуса, как обычные переходы (§5):

```
UPDATE contracts
   SET status = CASE WHEN executor_id IS NULL THEN 'cancelled' ELSE 'expired' END,
       updated_at = now()
 WHERE <scope> AND status IN ('open','taken')
 RETURNING id, executor_id, author_type, author_id, escrow_amount, escrow_withdrawable
```

- `0 строк` → контракты уже закрыты (например, `ExpireDue` на чтении) → **двойного возврата нет**: оба пути «побеждают» только один раз, потому что оба flip'ают статус условно.
- Для каждой `RETURNING`-строки: возврат на счёт автора + `money_operations('escrow_return')` + `contract_log`.
- **Форма возврата зависит от статуса (п. 5):** `open` → **отмена** (`cancelled`, лог `cancelled`); `taken` → **принудительный провал** (`expired`, лог `failed`) — «отмена только до взятия; после — только провал» (канон `11_contracts.md` §11.3.1).

**Обязательное оборачивание в транзакцию.** Возврат и удаление — **одна** транзакция (`Begin` → `ReturnEscrowForContracts` → `DELETE`/`TRUNCATE` → `Commit`). `clearUniverseTx` уже вызывается внутри транзакции (`admin_universe.go`); `GeneratePlanets`/`RegeneratePlanets`/`admin_worlds` сейчас удаляют через `h.db.Exec` **вне** транзакции — обернуть. `ExpireDue` (§6.3) идёт на чтении и мьютекса чтения не берёт — именно поэтому защита не в мьютексе, а в **условном flip'е**: гонка «просрочился и удаляется одновременно» разрешается на уровне БД (ровно один `UPDATE` вернёт строку).

**Политика кошельков при полной очистке вселенной — см. `2026-09-22-деньги-и-эскроу.md` §7.1** (выбор и обоснование).

## 7. Требования (окно свойств): состыковка с рецептами

**Канон.** `05_economy.md` §5.2.2: язык профилей и язык контрактов — **один и тот же**; требование — жёсткий интервал по 1–3 осям. §5.2.4: рецепт — состав (компонент + количество) + сложность.

**Что есть в коде.** `goods.props` JSONB (000045) — профиль ресурса (оси + `T_melt`/`T_boil` + `family`). `recipes`/`recipe_components` (000055) — конкретные компоненты + количество. **Окна свойств как структуры в коде нет** (находка C4) — её проектируем здесь, впервые.

**Состыковка (предложение, не ломающее рецепты):**

| | Рецепт (`recipe_components`) | Требование (`contract_requirements`) |
|---|---|---|
| Ссылка на предмет | `component_id → goods(id)`, `quantity` | `kind='goods'`, `subject = goods.id`, `quantity` |
| Окно свойств | **нет** (конкретные компоненты) | `kind='axis'`, `subject = код оси`, `op`, `threshold_num` |
| Снаряжение | — | `kind='gear'`, `subject = параметр` |

Требование — **надмножество** компонента рецепта: та же пара «предмет + количество» плюс окно (`kind`/`op`/`threshold`). Единый язык = когда `recipe_components` научится окнам (`kind='axis'`), обе таблицы описывают одно; миграция сведёт их **без ломки**: `recipe_components` не трогаем, окно рецепта — будущая задача (`05_economy.md` §5.2.4).

**Проверка соответствия** — по канону `14_money.md` §14.6: сервер проверяет **сертификат**, а не истину (`10_exploration.md` §10.3.5). В итерации 1 проверяется только `gear` при взятии перелёта (двигатель не хуже X) — это дешевле всего (`14_money.md` §14.6.1).

**Температуры** — `threshold_num` в **K** (данные/модель); в UI — °C (`PITFALLS.md` «Температура: в данных — Кельвины, в UI — везде °C»; решение создателя 2026-09-18).
