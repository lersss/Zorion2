## 1. Тип «перелёт» — первый

Канон `11_contracts.md` §11.3.4: «Контракт на перелёт — инструмент миграции агентов. Не заработок, а проездной билет». Устройство:

```
публикуется в точке A  →  исполнитель летит  →  прибыл в B  →  контракт закрыт
```

Свойства (канон, буквально): цена = топливо A→B плюс **малая** надбавка (большой профит превратил бы перелёт в заработок и агенты летали бы ради перелёта); малый профит намеренно; **закрывается по прибытии** (не по времени); обратный перелёт не оплачивается; требования — окно (двигатель не хуже X); срок выводится сам (время полёта + запас); отмена только до взятия.

### 1.1. Опора на существующие полёты (не дублировать)

Контракт **не реализует полёт сам** — он опирается на готовое:

- `travel.Manager` (`player_flights`, 000044) — межзвёздный полёт игрока;
- `TravelHandlers.ArrivalHandler` (`travel_handlers.go`) — прибытие межзвёздного полёта игрока к **звезде** (live + `Restore`);
- `player_intrasystem_flights` (000046) + `IntrasystemManager` + `NewIntraArrivalHandler` — внутрисистемный сегмент (99.2.27) и автостарт композитного маршрута (99.2.30);
- `users.pending_destination` (000049) — намерение композитного маршрута;
- `NPCManager.processArrivals` (`internal/npc/manager.go`) — **свой** путь прибытия NPC-агента (не `ArrivalHandler`).

**Две точки подключения — по типу цели (исправление п. 2 правок).** Прежняя редакция закрывала контракт по одному `dest_world_id` — это закрыло бы контракт при прибытии к звезде, даже если цель задана планетой. Разделяем:

| Цель контракта | Точка закрытия | Код |
|---|---|---|
| **Цель — планета** (`payload.dest_planet_id` задан) | Прибытие **внутрисистемного** сегмента к планете-цели (композитный маршрут 99.2.30) | `NewIntraArrivalHandler` (99.2.27 §3.6) |
| **Цель — только система** (`dest_planet_id` NULL) | Прибытие **межзвёздного** полёта к звезде | `TravelHandlers.ArrivalHandler` |

**Условие в межзвёздной точке:** закрывать только контракты с `payload->>'dest_planet_id' IS NULL` — иначе игрок, летящий к планете (через композитный маршрут), закрыл бы контракт на звезде раньше времени.

**Условие во внутрисистемной точке:** закрывать контракты, где `payload->>'dest_planet_id'` = прибывшая планета. Точка `NewIntraArrivalHandler` уже вызывается для автостарта/прибытия — добавляется шаг закрытия.

Обе точки работают и в `Restore` (полёт пережил рестарт; `RestorePendingDestinations` фаза 3).

### 1.2. `payload` перелёта

```json
{
  "from_world_id": "<uuid системы A>",
  "dest_world_id": "<uuid системы B>",
  "dest_planet_id": "<uuid планеты B или null>"
}
```

- `from_world_id` дублирует систему `publication_planet_id` — но хранится явно: планета публикации может быть удалена/перегенерирована, а точка отправления должна читаться из контракта (и для аудита).
- `dest_planet_id` — необязательная точка (канон «точка — планета», решение 4); NULL = достаточно прибыть в систему (закрытие по §1.1).

### 1.3. Требование к двигателю

Одно требование: `kind='gear'`, `subject='speed_factor'`, `op='le'`, `threshold_num = 0.3` (референсный фактор скорости).

**Семантика:** `speed_factor` — **параметр** снаряжения (не слот `engine`); множитель длительности (`duration = dist * speed_factor`), **меньше — быстрее** (`internal/ship`, `engine_1 {speed_factor: 0.3}`). «Двигатель не хуже X» = фактор **не больше** референсного → `op='le'`. Проверяется **при взятии**, не при сдаче (канон `14_money.md` §14.6.1).

### 1.4. Замыкание (атомарно)

```
взятие:  UPDATE contracts SET status='taken', executor_type, executor_id, taken_at,
                              expires_at = now() + <срок исполнения>   -- перебазирование, §4.3
         WHERE id=$1 AND status='open' AND expires_at > now()           -- 0 строк = гонка/истёк
прибытие (по типу цели, §1.1):
         UPDATE contracts SET status='completed'
          WHERE id=$1 AND status='taken' AND executor_id=$2 AND <цель совпала>  -- 0 строк = не наш
          → + balance исполнителя, − escrow_amount с контракта, money_operations('escrow_release')
```

Оба перехода — **одним** оператором с проверкой статуса (инвариант 1). Провал (срок вышел до прибытия) — ленивое истечение (`2026-09-22-контракт-модель-сущности.md` §6.3), залог возвращается автору, лог `failed`.

### 1.5. Исполнители: игрок и NPC-агент

Решение 11: исполняют и игроки, и NPC-агенты. **Решение создателя (порция 1):** агент-исполнитель входит в итерацию 1; владельца-фракцию агенту заводим, но **агент-автор — позже**.

- **Игрок** — берёт контракт с доски (`POST /api/contracts/take`), летит обычным `/travel`, прибытие закрывает контракт в одной из двух точек (§1.1).
- **NPC-агент** — **свой путь**: у агентов нет `travel.Manager`/`ArrivalHandler`; их прибытия обрабатывает `NPCManager.processArrivals` (`internal/npc/manager.go`, `flying → idle`). Закрытие перелёта для агента — **шаг в `processArrivals`**: если агент был исполнителем взятого контракта и его `target_world_id` совпал с целью → `completed` + `escrow_release`.
- **Агент исполняет только контракты с целью-системой (`dest_planet_id IS NULL`)** (исправление п. 3). У агентов **нет внутрисистемного движения** (`npc_agents` хранит `from/target_world_id`, планетного слоя нет), поэтому достичь планеты-цели агент не может — иначе он закрыл бы контракт на звезде преждевременно. Условие зеркалит межзвёздную точку §1.1: закрывать только при `payload->>'dest_planet_id' IS NULL`. Агент **не берёт** контракты с целью-планетой.
- **Взятие агентом — только при совпадении маршрута** (распоряжение менеджера, О-п8): **отдельного поиска контрактов у агента нет.** Планировщик `NPCManager` выбирает следующий мир сам; если из текущей системы уже есть открытый перелёт с этим `dest_world_id` **и без планеты-цели**, агент берёт его — иначе летит как обычно. Требование к двигателю к агенту **не применяется** (у агентов своя `npcSpeedFactor`). Это минимальный объём: без аукциона, без приоритета контрактов над маршрутом.
- **Модель готова к агенту-автору:** `npc_agents.owner_faction_id` (`2026-09-22-деньги-и-эскроу.md` §6) даёт бюджет; в итерации 1 агент не публикует.
- **Интеграция с `NPCManager` — отдельный объём** (в коде контрактов нет): находка C2 закрыта связью владельца, но планировщик о контрактах ещё не знает.

## 2. Доска на карточке планеты

Решение 4: витрина — **карточка планеты**, вкладка «Задания/Контракты», агрегирует **все** источники (автор не важен).

### 2.1. Что показывает доска

| Что | Значение |
|---|---|
| Источник данных | `contracts WHERE publication_planet_id = $1 AND status='open' AND expires_at > now()` (частичный индекс, §6.2 модели) |
| Агрегация | Все авторы: игрок/фракция/постройка/агент — **без разделения** (решение 4) |
| Пометка автора | `author_type` → иконка/подпись («игрок», «фракция X», «постройка», «агент») + имя владельца |
| Строка | тип, заголовок, цена, «осталось N», требования (читаемо: «двигатель не хуже …») |
| Взятые/закрытые | **не показываются** на доске (уходят в «мои контракты» автора/исполнителя) |
| Прямые (`visibility='direct'`) | на доске **не показываются**; видны только адресату |

### 2.2. Видимость (что видит игрок)

- Доска планеты — только при **знании планеты** (77a: «открытая звезда, закрытая система»; образец — `2026-09-21-фабрики-релиз-2-столицы-фракций.md`, видимость «админ / знание планеты»). Не знаешь планету — не знаешь её доску (доска — разведданные, канон §11.3.1).
- **Доски нет на орбите звезды** (решение О-п1): контракты живут у планет, системной витрины не заводим. Игрок на орбите звезды видит только «мои контракты».
- **Балансы не видны никому** (канон `14_money.md` §14.4) — на доске видна только цена контракта.
- Кто взял контракт — на доске **не видно** (канон §14.4.2: «кто нанял и зачем — не видно»; присутствие скрыто).
- Автор видит свои контракты во всех статусах; исполнитель — свои взятые.

### 2.3. API (черновик)

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/planets/{planet_id}/contracts` | Доска планеты (знание планеты; ленивое истечение в scope планеты) |
| `GET` | `/api/contracts/mine` | Мои (автор + исполнитель) |
| `POST` | `/api/contracts/take` | Взять (атомарно) |
| `POST` | `/api/contracts/cancel` | Отменить (только автор, только `open`) |
| `POST` | `/api/contracts` | **Публикация игроком** (игровой UI, с планеты — О-п1/О-п9) |
| `POST` | `/admin/contracts` | Публикация вручную остальными авторами (фракция/постройка/агент) + отладка (§3) |

`GET /api/contracts` (старый, «контракты текущего мира») **заменяется** — контракты теперь у планеты, не у мира.

## 3. Публикация всеми авторами

Решение 3: авторы — **все сразу**. В итерации 1 — **ручной инструмент** (автогенерация/агенда позже, но модель обязана её выдержать).

| Автор | Откуда берётся место публикации | Плательщик залога |
|---|---|---|
| `player` | **только планета**, где стоит игрок (орбита/поверхность); на орбите звезды публикации нет (решение О-п1) | счёт игрока |
| `faction` | `factions.homeworld_id` (родная планета) | казна фракции |
| `building` | `buildings.planet_id` | владелец постройки (рекурсия 1) |
| `agent` | текущая планета агента | фракция-владелец (`npc_agents.owner_faction_id`). **В итерации 1 агент-автор не публикует** (только исполнитель) — строка зарезервирована |

Модель выдерживает автогенерацию: контракт — обычная запись, авторы полиморфны, `payload` открыт; агенда (постройка/фракция публикует по расписанию) — **добавление писателя**, а не изменение схемы. Кандидат на будущее — «Постоянный заказ» (§8).

**Ограничение построек (находка C5):** `buildings` (000056) — пока только столица фракции, без производства и денег. Публикация «от постройки» в итерации 1 возможна технически, но содержательно пуста — предложение: **инструмент поддерживает `building`/`agent` как тип, но рабочие сценарии — игрок и фракция**; постройки-заказчики — после появления у построек производства/казны.

**Кто и как публикует (решение О-п9):**

- **Игрок — сам, в игровом UI** (карточка планеты, вкладка «Задания/Контракты»: кнопка «Опубликовать», форма). Это основной путь.
- **Админ-инструмент** (`/admin/contracts`) — для остальных авторов (фракция/постройка/агент) и для отладки; не заменяет игровой путь.

**Публикация возможна только с планеты (решение О-п1):** игрок должен стоять на планете (орбита/поверхность). На орбите звезды — ни доски, ни публикации (канон §14.5.2 «опубликовал на планете, где стоишь»).

## 4. Числа для @balancetester

> **Все числа ниже — заглушки «калибровать позже»** (решение создателя: «неважно, потом сбалансируем»). Исправлено сломанное (п. 7 правок): капкан «взял перед истечением» (4.3), мёртвый `min_reward` (4.2), неверный масштаб карты (4.1), несогласованность с `PlayerBalanceSeed` (4.4).

**Эталон НЕ задан.** Топливной системы в игре **нет**: `travel_handlers.go` прямо пишет «Топливо/дальность — будущее ограничение (задел, не реализуется)». Значит каноническая формула «цена = стоимость топлива на плече + малая надбавка» (`11_contracts.md` §11.3.4) **не имеет референса**. Ниже — варианты, а не имплементированное правило.

### 4.1. Известные величины (факты кода)

| Величина | Значение | Источник |
|---|---|---|
| Длительность полёта | `duration = max(dist * speed_factor, 3 сек)` | `calcTravelDuration`, `travel_handlers.go` |
| `speed_factor` стартового двигателя | `0.3` (`engine_1`) | `internal/ship`, миграция 000043 |
| `dist` | евклидово расстояние между координатами миров (`CoordX/CoordY`) | `travel_handlers.go` |
| Единицы | **реальные секунды** (полёт аркадный, не «идеальные дни») | `calcTravelDuration` |
| Масштаб кредита | **не задан** (легаси-`reward` — `integer` без калибровки) | `001_init`/`000010` |

**Масштаб карты (исправление).** Прежняя редакция писала «радиус 2500» — это **не** масштаб карты. Верно:

- `MapSize` — **радиус круга карты** (`galaxy.go`: `MapSize float64 // радиус круга`), конфиг генерации, **дефолт `8000`** (`admin_universe.go`), тесты — до `100000`;
- `MinDist` — минимальное расстояние между звёздами, **дефолт `150`** (`poisson.go`), в конфигах 40–300;
- `ClusterRadius` (150–1500 в тестах) — радиус **кластера**, а не карты.

Отсюда диапазон `dist`: **от ~150** (соседние звёзды) **до ~2·MapSize ≈ 16 000** (прыжок через карту при дефолте) — цена различается на **два порядка**.

### 4.2. Цена — три варианта (нет эталона)

| # | Вариант | Формула | Цена | Вердикт |
|---|---|---|---|---|
| **А** | **Линейно от дистанции** (прокси топлива) | `reward = round(k_price · dist · (1 + margin))` | Числа — заглушки, калибровать; не отражает реальный расход топлива | **Предлагаемый** |
| **Б** | **Константа за прыжок** | `reward = const` | Не различает дальность — **противоречит канону** «цена = топливо на плече» | Отклонён |
| **В** | **Ввести топливо** (расход ресурса/товара в полёте) | `reward` = стоимость израсходованного топлива | Отдельная крупная механика (ресурс-топливо, расход, трюм) — вне этой спеки | Позже |

**Числа-заглушки варианта А (калибровать позже):**

| Параметр | Значение-заглушка | Обоснование |
|---|---|---|
| `k_price` (кредитов на единицу координаты) | `10` | Масштаб карты: `MinDist=150` → ~1,65·10³ за короткий прыжок; прыжок через карту (~16 000) → ~1,8·10⁵ |
| `margin` («малая надбавка») | `0.10` (10%) | Канон: «малая надбавка», «окупает перемещение, а не кормит» |
| ~~`min_reward` (пол)~~ | **УБРАН** | Мёртвая константа: при `k_price=10` и минимальном `dist` (150) пол = 1 650, а конфиги карты дают `dist ≥ 40` → минимум 440. Отдельный пол недостижим; настоящий пол задаётся физикой карты (`MinDist`) |

### 4.3. Срок

**Капкан «взял перед истечением» (исправление).** Если срок фиксирован от публикации, исполнитель может взять контракт за секунду до `expires_at` и физически не успеть — гарантированный провал и потеря топлива. Решение:

> **Срок исполнения отсчитывается от взятия** (`expires_at` **перебазируется** при взятии, §1.4): `expires_at = taken_at + flight_time_ref · (1 + reserve)`.

Обоснование: канон `11_contracts.md` §11.3.1 — «**взятие контракта = старт исполнения**»; срок описывает **время полёта**, а не «сколько лежал заказ». Тогда исполнитель всегда получает полное время на полёт, а ловушка исчезает **структурно** (проверка при взятии не нужна). Пока контракт `open`, `expires_at` — **срок жизни предложения** на доске (тоже заглушка, `offer_window`, калибровать).

Перебазирование — **правило, специфичное для перелёта**: у поставки срок задаётся условиями (канон §11.3.1) и не перебазируется.

| Параметр | Значение-заглушка | Обоснование |
|---|---|---|
| `speed_factor_ref` | `0.3` (стартовый двигатель, **самый медленный**) | Канон: «время полёта на референсной тяге + запас»; референс — медленный → у быстрого исполнителя запас больше |
| `reserve` (запас) | `0.50` (срок = `flight_time_ref · 1.5`) | Калибровать позже |
| `offer_window` (жизнь предложения на доске, пока `open`) | `flight_time_ref · 10` | Калибровать позже; не путать со сроком исполнения |
| Срок исполнения | `taken_at + max(dist · 0.3, 3 сек) · (1 + reserve)` | Выводится автоматически, заказчик не выбирает (канон §11.3.4) |

### 4.4. Что проверить @balancetester

- **`k_price` и `PlayerBalanceSeed` — независимые заглушки** (исправление). `10^4` покрывает ~6 коротких прыжков (1,65·10³) и **не покрывает дальний** (~1,8·10⁵). Калибровать **вместе** (`2026-09-22-деньги-и-эскроу.md` §8).
- Согласованность с будущей ценой топлива (вариант В) — заглушка А должна быть заменяема без переделки контрактов (цена хранится в `reward`, не вычисляется на чтении).
- **Инвариант 2:** цена зависит **только** от `dist` — не от размера галактики, не от числа контрактов.
- Проверить, что награда не превращает перелёт в заработок (канон: агент должен летать ради точки, не ради перелёта) — сравнить с ценой добычи/доставки (будущие типы).
- **Разброс цены на два порядка** (150 … 16 000) — решить, приемлемо ли; если нет, ограничить `dist` капом или нелинейностью (`√dist`) — заглушка.
- **Перелёт подрядом не бывает** (`15_monetization.md` §15.4.2) — `funding='regular'` всегда; выводимых кредитов перелёт не создаёт.

## 8. Кандидат ГД-сущности (+1 за задание)

**Вопрос:** нужен ли сущности контракта шаблон, порождающий контракты?

**Ответ (кандидат, не факт — отсев за создателем):** **«Постоянный заказ»** — запись-шаблон (автор, планета публикации, тип, `payload`-шаблон, цена за экземпляр, бюджет, период/триггер, флаг активности), которая по агенде порождает контракты-экземпляры.

Зачем: канон `11_contracts.md` §11.3.1 требует «постоянные заказы с автопродлением, условия, бюджетные лимиты, приоритеты» — без шаблона магнат не управляет империей. Модель контракта это **выдерживает** (шаблон — отдельная сущность, экземпляры — обычные `contracts`; при высоком обороте шаблонов мало, экземпляров много). Не входит в итерацию 1.
