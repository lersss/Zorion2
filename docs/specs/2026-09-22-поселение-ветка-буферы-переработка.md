## 1. Решение (суть)

У поселения появляется **ветка** — связь «поселение ↔ рецепт каталога» (`recipes`) с **входным** и **выходным буфером**. Вход — то, что ветка потребляет (состав `recipe_components`), выход — то, что даёт рецепт (его `good_id`). Ветка **медленно и лениво** (по прошедшему Δt, при обращении) превращает вход в выход: вход убывает по количеству компонентов, выход прирастает. Отдельного тика нет (инвариант 2 GD_PROMPT: расчёт по событию/при чтении).

Добыча из залежи — **не входит** (итерация 3): вход наполняется **админ-действием «добавить ресурсы»** (песочница). Потребление населением («уничтожение» части выхода) — итерация 4.

Пилот — **одна ветка**: «Пища» = Мясо + вода-ресурс → Пища (§0 п.1). Модель обязана поддерживать несколько веток на поселение (§0 п.3) и несколько поселений на планете.

**Выход ветки — «пол», а не конкурентный товар** (инварианты 11–12 GD_PROMPT; `13_tiers.md` §13.12.3). Переработку ведёт NPC-поселение, поэтому выход по определению **низкого качества**: он не проходит пороги качества и не берёт контракты «не меньше N» — «NPC — пол, а не потолок», всё, что требует качества, по-прежнему покупается у игроков. Механика качества/порогов — итерация 4+ (§15); в итерации 2 фиксируется **статус** выхода (пол), а не поле качества: поле/атрибут качества **не заводим** (анти-сущность до появления потребителя).

Вне объёма: добыча, потребление/голод/рост, потолки буферов, качество/пороги, рынки, «склад», удаление/правка ветки, расовые ветки, связь с `producer_recipes`/фабриками.

## 3. Модель данных

### 3.1. Форма буферов — **отдельная таблица записей** (выбор обоснован)

Буфер — это **поток записей «ресурс → количество»**, а не один факт: у ветки их много (по составу рецепта + выход), веток много, и записи меняются точечно. Выбрана **таблица записей** `settlement_branch_buffers` (вариант B в §7 F1), JSONB отклонён.

Обоснование (цена/инварианты):
- **Целостность с каталогом:** FK `good_id → goods(id) ON DELETE CASCADE` — удаление записи каталога сносит её остатки из буферов, как у `deposits`. В JSONB ключ-`good_id` остался бы мусором.
- **Атомарность при многопользовательском доступе:** `UPDATE ... SET amount = amount − $x` — одна строка, без чтения-изменения-записи всего документа (в JSONB два пишущих читателя теряют правку без `FOR UPDATE` на ветке; `AGENTS.md` §0).
- **Расширяемость:** второй вид буфера влезает значением `direction`; вторая ветка — строкой `branch_id`; итерации 3 (добыча → вход) и 4 (выход → потребление) не меняют схему.
- **Админ-действие** «добавить ресурсы» = upsert строки `(branch, 'input', good)`.

Цена: JOIN ради чтения буфера и `UNIQUE`-конфликт при upsert (закрыт `ON CONFLICT`). Альтернатива «две таблицы по направлениям» (вариант C) — дублирование кода ради косметики; «общий инвентарь по владельцу» (вариант D) — преждевременная сущность без второго потребителя (склад введён не будет, §11.4 фабрик).

### 3.2. DDL — миграция `000064_settlement_branches.sql`

```sql
CREATE TABLE settlement_branches (
    id            UUID PRIMARY KEY,
    settlement_id UUID   NOT NULL REFERENCES settlements (id) ON DELETE CASCADE,
    recipe_id     BIGINT NOT NULL REFERENCES recipes (id)     ON DELETE CASCADE,
    processed_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),   -- своя чек-точка (§4)
    created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (settlement_id, recipe_id)                   -- одна ветка на рецепт у поселения
);
CREATE INDEX idx_settlement_branches_settlement ON settlement_branches (settlement_id);
CREATE INDEX idx_settlement_branches_recipe     ON settlement_branches (recipe_id);

CREATE TABLE settlement_branch_buffers (
    id         BIGSERIAL PRIMARY KEY,
    branch_id  UUID   NOT NULL REFERENCES settlement_branches (id) ON DELETE CASCADE,
    direction  TEXT   NOT NULL CHECK (direction IN ('input', 'output')),
    good_id    BIGINT NOT NULL REFERENCES goods (id)               ON DELETE CASCADE,
    amount     DOUBLE PRECISION NOT NULL DEFAULT 0 CHECK (amount >= 0),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (branch_id, direction, good_id)               -- один ресурс — одна строка на буфер
);
CREATE INDEX idx_settlement_branch_buffers_branch ON settlement_branch_buffers (branch_id);
CREATE INDEX idx_settlement_branch_buffers_good   ON settlement_branch_buffers (good_id);
```

- **`amount DOUBLE PRECISION`**, как `deposits.amount`: переработка идёт **дробными** батчами (§4.2 — Δt не кратен батчу), поэтому дискретность записи была бы ложной. Отображение округляет. Граница БД `≥ 0`; движок не даёт уйти в минус (§4.2).
- **`UNIQUE (settlement_id, recipe_id)`** — одна ветка на рецепт у поселения; «веток несколько» (§0 п.3) достижимо разными рецептами. Повтор — 409. Удаление/пересоздание ветки — вне объёма (§15).
- **`direction`** — открытый маппинг-константами в коде; итерация 2 использует только `input`/`output`.
- **Носитель — не JSONB `settlements.*`** (структура «много записей на владельца», FK на каталог, точечные апдейты).
- **Не вводим:** `capacity`/потолок буфера (§15, итерация 4), `rate`/`workers` на ветке (скорость выводится, §4.1 — ручек на строке нет), `depleted`/статусы, `name` ветки.

### 3.3. Что ветка **читает** из каталога (live, без снимка)

Состав ветки не дублируется: на каждом пересчёте ветка читает **текущий** `recipe_components` рецепта (заполненные компоненты, `component_id IS NOT NULL`) и его `good_id` как выход.

- Компонент с `component_id IS NULL` (пустой слот студии) **пропускается** — потреблять нечего; если таких все — ветка ничего не делает (не ошибка).
- `quantity` (`INT ≥ 1`) — норма расхода на батч; в расчёт идёт как `float64`.
- **Следствие (названо):** правка рецепта в студии меняет поведение **работающей** ветки (следующий пересчёт пойдёт по новому составу); удаление рецепта/товара-выхода — `CASCADE` сносит ветку с буферами (§8). Снимок состава — отклонён (дублирование факта, §7 F2).
- **Новый заполненный компонент** (правка @critic №8): строки `input` у него ещё нет → `affordable = 0`, ветка «встала бы молча». Снимается дополнением строк входа в персистентном синке (§4.2 — `INSERT ... ON CONFLICT DO NOTHING` + лог).
- **Выпавший компонент** (удалён/очищен в студии): строка `input` с остатком **остаётся** в буфере и больше не потребляется (чистка буферов — вне объёма, §15). Ресурс виден в карточке у админа как «лежит без расхода» — это и есть диагностика.
- Выход рецепта — всегда `kind='good'` (`recipes.good_id`; канон 000055). **Компонент — любой `kind`**: вход принимается по `component_id` (заполненный компонент рецепта), **не** по `kind='resource'` (правка @critic №9) — в пилоте оба компонента ресурсы, но фильтр от `kind` не зависит.

## 4. Ленивая переработка вход → выход (§0 п.2, пункт 2.5 идеи)

### 4.1. Скорость — масштаб реальных поселений, формула и варианты (на гейт)

**Факт масштаба (сверка с кодом, @balancetester 2026-09-22, находка В1).** Население поселений генератора — `random 100_000 … 1_000_000_000` человек: `DefaultRacePreset` (`internal/generator/settlement/race_preset.go:66–75`, `Population{Kind:"random", Min:100_000, Max:1_000_000_000}`), тот же диапазон — в докстринге модели генерации (`internal/handlers/admin_settlements.go:30–31`; пресет 65a). Залежь итерации 1 — `amountBase = 1000`, диапазон `[500, 1500]` (спека итерации 1 §3.2). **Вывод:** линейная скорость ∝ населению **не имеет единого `k`** на четырёх порядках населения: цель «залежь живёт сутки–неделя» линейно достижима только при `P ≈ 100–700` (нерепрезентативно). Прежняя иллюстрация «100 человек» и ручка `0.06` **удалены** как подобранные под несуществующий масштаб.

Общий каркас переработки:

```
часы          = (now − processed_at) в часах                 # Δt, ≤ 0 → переработки нет
complexity    = max(1, COALESCE(recipes.complexity, 1))       # см. примечание про NULL
rate_батч/час = f(population) / complexity                    # f — вариант A/B/C/D ниже
desired       = rate_батч/час × часы
affordable    = min по компонентам (input_i / quantity_i)     # компонентов нет → 0
batches       = min(desired, affordable)                      # дробное
input_i      -= batches × quantity_i                          # по каждому заполненному компоненту
output_good  += batches                                       # один батч = одна единица выхода рецепта
processed_at  = now
```

**Примечание о `complexity` (правка @critic №7).** По канону студии `recipes.complexity NULL` = «вычисляется по графу», **не** «1» (`internal/goodsstudio/graph/tier.go` `EffectiveTier`: `Complexity != nil → *Complexity`, иначе вычисленный тир; спека `2026-09-21-рецепт-сущность-и-граф-фабрики.md` §2.3). Рантайм графа не считает → **временный фолбэк `NULL → 1`, названный** (пилот не затронут: «Пища» `complexity = 1`). `complexity = 0` и `1` дают одинаковую скорость (делитель `≥ 1`); более тонкая шкала — при калибровке. Когда у сложности появится рантайм-потребитель — считать граф или материализовать (дельта к студии, §19).

**Итоговый вариант — A (линейная `f(P) = P`), выбор создателя 2026-09-22 (О6).** Формула: `rate_батч/час = k · population / complexity`, **`k = 2.78·10⁻⁸` батч/(чел·ч)** — под цель «медиана `P_ref = 5·10⁸` → залежь `[500,1500]` за ~3 суток». `P_ref` — медиана генератора = 5·10⁸ (равномерный `[1e5, 1e9]`). ⚠️ Числа остаются **не калиброванными** (@balancetester — прогон по варианту A, §16). Рассмотренные семейства B/C/D сохранены ниже как история выбора; **в код идут только A и `k`**.

- Залежь `[500, 1500]` даёт дополнительно ±50 % к `T` — целимся в середину.
- **Принято: A (линейная) — осознанное решение создателя (2026-09-22).** Разлёт показан и **принят**: `T` при `P = 1e5` ≈ **41 год**, при `P = 1e9` ≈ **1.5 суток** (медиана ≈ 3 суток) — крайние поселения выпадают из такта, и это **задумка**, а не недосмотр: линейная зависимость самая простая и буквально читаемая («вдвое больше людей — вдвое быстрее»).
- **Отклонённые B/C/D** (сублинейные `√P`/лог, константа) сохранены выше как история выбора; аргументы дизайнера (разлёт, тестируемость) — названы, но **создатель выбрал A** (2026-09-22, §17 О6).

**Почему скорость вообще связана с населением/сложностью** (обоснование структуры, а не числа): население — единственный существующий ресурс-труд (`settlements.population`) и будущий потребитель выхода (итерация 4); сложность — готовое свойство рецепта (`recipes.complexity`, канон 000055), делитель без новых полей. Дефицит входа — естественный предел: `batches ≤ affordable`, выход «из ничего» не печатается. **Единицы:** «батч» = одно исполнение рецепта (расход `quantity` каждого компонента → 1 единица выхода; отдельного «выходного количества» в каноне 000055 нет).

**Цель калибровки (@balancetester) по варианту A:** `T` медианного поселения (`P_ref ≈ 5·10⁸`) — сутки–неделя на залежи `[500,1500]`. Широкий разлёт `T` по населению (≈10⁴×: 1e5 → ≈41 год, 1e9 → ≈1.5 суток) — **принят создателем осознанно (2026-09-22)**, не калибруется «в узкое окно». Шкала — условные единицы (единицы ресурса в игре нет; согласовано с §3.2 итерации 1).

**Сущности вне игры, влияющие на формулу — нет** (анти-ловушка «описываем то, чего нет»): `population`, `complexity`, компоненты рецепта — все существуют. Убежища/купола/склады в формулу **не входят**; «склад» каноном не вводится (§11.4 фабрик).

### 4.2. Дробные батчи, идемпотентность, безопасность

- **Дробный батч** — переработка непрерывна по времени: `batches` — `float64`, остаток выражается дробными `amount` (§3.2). Отдельного «прогресса батча» на ветке **нет** (анти-сущность), т.к. буферы уже дробные.
- **Идемпотентность:** переработка — чистая функция от `(processed_at, now, population, состав, буферы)`. После записи `processed_at = now`; повторный вызов с тем же `now` даёт `Δt = 0` → ничего. Два последовательных пересчёта = один (как у населения, `recompute.go`).
- **Конкурентность (`AGENTS.md` §0; правка @critic №2 — дыра блокировки закрыта).** **Единая точка сериализации — `FOR UPDATE` на строке ветки в обеих пишущих ручках.** И `SyncBranches`, и `AddBranchInput` первым действием в своей транзакции берут `SELECT ... FROM settlement_branches WHERE id = $1 FOR UPDATE`; только затем читают/меняют буферы. Порядок блокировок единый: **ветка → буферы** (по `(branch_id, direction, good_id)`).
  - **Почему так, а не «только относительные `UPDATE`»:** синк вычисляет `batches` **из прочитанных** буферов, т.е. это read-modify-write. Без блокировки ветки админский инкремент, пришедший между чтением и записью синка, будет затёрт абсолютным `UPDATE` синка (потерянный инкремент), а при `batches ≥ input` возможен минус и падение `CHECK (amount >= 0)`. Относительные `UPDATE` убирают минус, но не потерю — им всё равно нужно то же согласованное чтение. Поэтому блокировка берётся **на обеих сторонах**; админская ручка после неё делает **относительный** `UPDATE ... amount + EXCLUDED.amount`, синк — абсолютную запись под той же блокировкой.
  - **Путь записи («событие»):** транзакция, `FOR UPDATE` на ветке → пересчёт по **сохранённым** буферам → `UPDATE` буферов, `processed_at` → `COMMIT`. Второй одновременный синк ждёт строку, видит `processed_at = now'` → `Δt ≤ 0` → no-op. Потерянных правок нет.
  - **Путь чтения («простой визит»):** если `now − processed_at < MinPersistInterval` — пересчёт **в памяти**, без записи и без блокировки (картинка может быть «свежее» сохранённой на величину < кадэнса — намеренно). Так хот-пат чтения карточки не пишет в БД.
  - Общих `map` вне БД у механики **нет** (состояние — только строки БД); WS механике не нужен (одна пишущая горутина не затрагивается).
- **Кадэнс ленивых петель (правка @critic №10).** `MinPersistInterval` (30 мин) **переиспользуется намеренно**: это **один общий кадэнс** «простой визит vs событие» (`internal/economy/settlement/recompute.go`), а не два независимых числа одного смысла. Отдельную константу ветки **не заводим** (иначе два числа разойдутся — «один факт — одно место»). Если калибровка покажет, что ветке нужен свой кадэнс — вводим `BranchMinPersistInterval` явно, с обоснованием.
- **Дополнение строк входа при синке (правка @critic №8 — «молчаливая остановка»).** Состав читается «живой» (§3.3), а посев буферов был только при создании ветки; поэтому **новый заполненный компонент рецепта** дал бы `affordable = 0` (строки `input` нет) — ветка молча встала бы. **Решение:** в **персистентном** синке выполнять `INSERT INTO settlement_branch_buffers (branch_id, 'input', component_id, 0) ON CONFLICT DO NOTHING` по текущим заполненным компонентам; появление новой строки — `log.Printf`. Стоимость — O(компонентов) раз в кадэнс; нулевая строка не «плодит» данные сверх состава. Путь «в памяти» записи не делает — новая строка появится в карточке только после персистентного синка (названо).
- **Вход данных:** `population` берётся из поселения **после** его ленивого пересчёта в той же точке чтения (`attachSettlements`), т.е. та же цифра, что видит карточка; в БД-пути используется значение, загруженное вместе с поселением. Вложенных чтений поселения внутри пересчёта ветки нет.
- **Порядок в `attachSettlements`:** поселения → ленивый пересчёт населения → **загрузка веток и синк** → лог. Лог не затрагивается.
- **Без «каскадных» проходов:** пересчитываются только ветки поселений того мира, который открыли (инвариант 2).

## 5. API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/admin/settlements/{id}/branches` | создать ветку поселения (тело `{recipe_id}`) |
| POST | `/admin/branches/{id}/input` | **добавить ресурсы** во входной буфер (тело `{good_id \| good_name, amount}`) |
| GET | `/api/worlds/{id}/planets` | карточка: `settlements[].branches[]` (вход — только админ, §6) |

Новых прав игроку нет. Обе админ-ручки — JWT `admin`/`skycomposer`, зона `internal/handlers/admin_settlement_branches.go`; роуты — `cmd/server/main.go` (wildcard `"/admin/settlements/"`, `"/admin/branches/"`).

**Создание ветки (POST `/admin/settlements/{id}/branches`)**
- Поселения нет → 404; рецепта нет → 422; в рецепте **нет ни одного заполненного компонента** → 422 (нечего перерабатывать); ветка на этот рецепт уже есть → 409.
- Гейты мутаций вселенной (образец `AddDeposit`, `admin_deposits.go`): `statusManager.IsRunning(JobPacman)` → 409; `universeMutationMu.TryLock()` → 409 (проверка+действие атомарны).
- Одна транзакция: INSERT ветки (`processed_at = NOW()`) + **посев буферов нулями**: по строке `input` на каждый **текущий** заполненный компонент рецепта и одна строка `output` на `recipes.good_id`. Посев покрывает только момент создания; компоненты, добавленные в рецепт позже, дополняются при персистентном синке (§4.2 — `ON CONFLICT DO NOTHING`).
- Ответ: `{settlement_id, planet_id, branches[]}` — **полный** блок веток поселения в формате карточки (§6), клиент заменяет блок целиком (образец ответа залежей, §6 спеки итерации 1).

**Добавление ресурсов (POST `/admin/branches/{id}/input`)**
- Ветки нет → 404; `amount` отсутствует/≤ 0 → 422; `good_id` не существует → 422.
- **Ограничение:** во вход принимается только запись, **являющаяся компонентом рецепта этой ветки** — фильтр **по `component_id`** среди заполненных компонентов, **не** по `kind` (правка @critic №9: компонент может быть и ресурсом, и товаром) → иначе 422. Так входной буфер остаётся «тем, что ветка потребляет», и песочница не копит мёртвые записи. (Альтернатива «принимать любой `good`» — **отклонена**, О4, 2026-09-22.)
- `good_id` либо `good_name` (резолв `name_norm` Go-нормализацией `graph.NormalizeName`, как в `admin_deposits.go`; **не** SQL `lower()` — `PITFALLS`).
- **Блокировка (правка @critic №2):** первым действием транзакции — `SELECT ... FROM settlement_branches WHERE id = $1 FOR UPDATE` (единая точка сериализации с синком, §4.2), затем инкремент. Проверка+действие атомарны.
- Операция: `INSERT ... (branch_id,'input',good_id, amount) ON CONFLICT (branch_id,direction,good_id) DO UPDATE SET amount = settlement_branch_buffers.amount + EXCLUDED.amount, updated_at = NOW()` — атомарный инкремент под блокировкой ветки.
- Ответ: `{settlement_id, planet_id, branches[]}` — тот же контракт, что у создания ветки (клиент перерисовывает блок).

**Роут-схема:** плоские wildcard’ы вместо вложенного разбора пути — как `"/admin/planets/"` в итерации 1; `/admin/settlements/` (мн.) не пересекается с `/admin/settlement-settings` (ед.), `/admin/clear-settlements`, `/admin/generate-settlements`.

## 6. Отображение ветки в карточке поселения

**Где рендерится карточка поселения (проверено по коду):**

**Что показываем.** В карточке поселения — блок на каждую ветку:

| Поле | Кому |
|---|---|
| Имя рецепта/выхода, сложность | всем, кто видит детали поселения |
| **Выход**: товар → количество | всем, кто видит детали поселения |
| Вход: ресурс → количество | **только админ** (`isAdmin()`) |
| Чек-точка/скорость | админ (по желанию отображения) |

- **Вход — только админ.** Основной фильтр — серверный: `stripPlanetDetails` (`internal/handlers/planet_visibility.go`) для `role=player` **обнуляет `Input` каждой ветки** (защита в глубину, как `Deposits`/`Factions`/`Buildings`), затем, как и сейчас, `p.Settlements = nil`. Инвариант: **путь, отдающий планету игроку без `applyPlanetVisibility`, не несёт входных буферов**.
- **Выход — игроку.** Выходной буфер — часть деталей поселения: он остаётся в `branches[].Output`. Сегодня детали поселений игроку не отдаются вовсе (`p.Settlements = nil` в `stripPlanetDetails`; `77a` §6.2 — платные отчёты), т.е. фактически выход увидит админ и (позже) владелец поселения; спека фиксирует **правило видимости**, не текущую достижимость.
- Админ-блок под списком веток: «создать ветку» (рецепт — ввод `recipe_id`, подсказка про пилот 69) и «добавить во вход» (выбор ресурса из `/studio/api/resources`, как `loadDepositResources` в `tabs.js`, + количество). Число обновляется ответом ручки (§5) — как у залежей.
- **Клиентская чистота (PITFALLS):** новые модули карточки (`branches.js`) обязаны быть Node-безопасными на верхнем уровне (никаких `document`/`fetch` вне функций) — `modal/tabs.js` тянется в import-граф админки и исполняется в Node (`web/frontend_test.go`).

## 8. БД: миграция, `truncateTables`, каскады

- **Миграция `000064_settlement_branches.sql`** — DDL §3.2 (номер `000064` подтверждён менеджером, см. шапку).
- **`truncateTables` (`internal/handlers/admin_universe.go:59`)** — добавить **обе** таблицы: без `settlement_branches` упадёт `TRUNCATE settlements` (FK `settlement_id`), без `settlement_branch_buffers` — `TRUNCATE` на ветке. - **Каскады Пакмана:** отдельного шага не нужно — `worlds → planets → settlements → settlement_branches → settlement_branch_buffers` покрыт `ON DELETE CASCADE` (как `buildings`/`deposits`).
- **Студия:** удаление товара-выхода (`goods` DELETE) → `recipes` CASCADE → `settlement_branches` CASCADE → буферы; удаление ресурса-компонента → `recipe_components.component_id SET NULL` (ветка живёт, компонент выпадает из состава, остаток строки `input` не потребляется — §3.3). Молчаливый каскад веток — кандидат на симметричное предупреждение по образцу `deposits-count` (О3; ребро студии — §10).
- Каталог (`goods`/`recipes`/`recipe_components`) миграция **не трогает**; числа в миграции не задаются (ручки — константы кода §4.1).

| T5 | Переработка по времени: `Δt = 0` → буферы и `processed_at` не меняются; при `Δt > 0` вход убывает на `batches × quantity` по каждому компоненту, выход прирастает на `batches`; `processed_at = now` |
| T6 | Дефицит входа: при большом Δt и малом входе `batches = affordable`, вход по дефицитному компоненту обнуляется, `amount ≥ 0` (минуса нет), выход = `affordable` |
| T7 | Идемпотентность/порядок: два вызова с одним `now` = один; `Recompute(Recompute(now)) = Recompute(now)` (чистая функция — по образцу населения) |

| T9 | Скорость: `rate` **линейна по населению** (вариант A: `rate = k·P/complexity`, `k = 2.78·10⁻⁸`) и не возрастает по `complexity`; `complexity NULL → 1` (временный фолбэк) и `0 → 1` (юнит-тест формулы) |
| T10 | Несколько веток: два рецепта у одного поселения перерабатываются независимо; один и тот же ресурс как вход одной ветки и выход другой — конфликта `UNIQUE` нет |

| T14 | Состав (правка @critic №8): после добавления в рецепт нового заполненного компонента персистентный синк **создаёт** строку `input` с 0 (`ON CONFLICT DO NOTHING`) — ветка не встаёт молча; путь «в памяти» записей не создаёт |

## 13. Эталоны (FAQ) и счётчик открытых вопросов

**Вопрос:** с какой скоростью ветка превращает вход в выход (структура зависимости и числа)?
**Ответ:** формула — **линейная (вариант A)**, решение создателя 2026-09-22: `rate_батч/час = k · population / complexity`, `k = 2.78·10⁻⁸`. Диапазон населения (1e5–1e9) и принятый разлёт `T` (≈10⁴×) — §4.1. Числа **не калиброваны** (@balancetester по варианту A, §16); сам эталон скорости создателем не задан.

**Вопрос:** есть ли потолок выходного буфера?
**Ответ:** эталон не задан (2026-09-22) — открытый вопрос (в итерации 2 потолка нет; потребление/потолки — итерация 4).

**Дельта для счётчика (`docs/gamedesign/faq_counter.md`, владелец — @dispatcher): +2.** Вопросы О2–О5 (§17) — продуктовые/роадмапные, в счётчик **не входят** (только эталоны физики/мира; О6 закрыт решением создателя). Сам счётчик не трогаю.

## 14. ГД-сущность-кандидат (+1 предложение, не решение)

**Вопрос:** сделать ли ветке **смену** — долю населения, выделенную именно ей?
**Ответ-предложение (дизайнер, кандидат):** поле «доля людей» у ветки (0–100%, сумма по веткам поселения ≤ 100%); скорость переработки ∝ выделенным людям, а не всему населению. Даёт поселению **выбор** (какой товар производить: держать одну ветку на всех или развести труд между несколькими), связывает решение 23 («веток несколько») с трудом и с будущим потреблением (итерация 4), не требуя новой сущности — только доля на ветке. **В текущие числа не входит** (анти-двойной учёт: сейчас скорость берёт население целиком, §4.1); при принятии формулы пересчитываются. Отсев — за создателем.
