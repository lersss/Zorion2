## 0. Решения создателя (дословно; применять буквально)

Источник — уточнения приёмной 2026-09-22 (идея §3, пп. 24–26):

24. **Модель — «ровно под переработку», скорость зависит от населения.** Добыча НЕ идёт своим отдельным потоком: за один проход времени ветка берёт из залежи ровно столько, сколько готова переработать — та же скорость, что у переработки (`rate = k·population/complexity`, `k = 2.78·10⁻⁸`). Входной буфер остаётся **проходным**; единственный предел — запас залежи. **Второй ручки-скорости не вводим.** Вариант «независимый поток + растущий вход» — итерация 4.
25. **Связь ветка ↔ залежь — без настройки:** ветка черпает из залежей **своей планеты** (поселение → `planet_id`) и только по ресурсам из состава её рецепта (`recipe_components` с `component_id IS NOT NULL`). Ресурсы вне рецепта не трогает. Если на планете несколько залежей одного ресурса — берёт **по одной, от крупной к мелкой**; истощилась — переходит к следующей.
26. **Истощение:** запись залежи остаётся (запас 0, из данных не исчезает, в минус не уходит), но **выработанную залежь (запас 0) видит только админ**; игроку она не показывается вообще.
27. **Богатство залежи (`wealth`) — только показ; множителем добычи не является.** Объём добора задаёт только `batches` (п.24), выбор залежи — по запасу (п.25). Это **переопределяет** формулировку спеки итерации 1 («богатство — будущий множитель добычи»). **Закрыто решением гейта 2026-09-22.**

## 1. Решение (суть)

Добыча — **не отдельная петля**, а **первая половина того же прохода** переработки (§0 п.24). В существующем ленивом синке ветки (§4.2 спеки итерации 2) перед превращением вход → выход появляется шаг **добора недостающего из залежей планеты**: ветка «доливает» вход ровно тем, что ей не хватает до готовности переработать, и это ровно уменьшает запас залежей.

Формально:

```
desired       = BranchRate(population, complexity) · Δt         # как в итерации 2
stock_i       = input_i + Σ запас залежей планеты с good_id = i # что вообще доступно
batches       = min(desired, min_i(stock_i / quantity_i))       # дробное
потребление_i = batches × quantity_i                            # сколько компонента нужно
  из input_i (сначала), остаток — из залежей своей планеты, от крупной к мелкой
input_i   -= взятое из входа
deposit_j -= взятое из залежи j        (кламп ≥ 0, в минус не уходит)
output    += batches
processed_at = now
```

`batches` вычисляется **до** потребления; отдельной величины `need_i` нет — её роль играет `потребление_i`. `quantity_i` — **суммарная норма компонента** на батч (агрегация строк рецепта по `good_id`, см. ниже).

Суть для игрока/админа: вход перестаёт быть «складом под кнопку» и становится **проходным** (п.24) — при живой залежи он пуст, ветка работает «с колёс»; кнопка «добавить во вход» итерации 2 остаётся (песочница), но её содержимое расходуется **первым** (§4.3). Залежь — конечный источник: истощилась → ветка встаёт (пока ресурс не появится заново).

Модель обязана выдержать: **несколько веток на поселении** (п.23), **несколько поселений и веток на одной планете**, **несколько залежей одного ресурса** (п.25).

**Дубликат `component_id` в рецепте** (схема `000055` допускает один `component_id` на разных `pos`; уникальности `(recipe_id, component_id)` **нет**): строки рецепта **агрегируются по `good_id`** — повтор трактуется как **один компонент с суммарной нормой** `quantity_i = Σ quantity` по этому `good_id`. Норма на батч берётся от агрегата, запас списывается **один раз**, выход **не завышается**. Это **правка поведения `ProcessBranch` итерации 2** (там строки рецепта не сворачивались) — пометка для @developer (§10).

Вне объёма: второй поток добычи, потолки/склады, регенерация залежей, рецепт как ручка добычи, «прогулка»/видимый карьер, потребление и рост (итерация 4).

## 3. Модель данных

### 3.1. Миграции **нет** (подтверждено)

- `deposits` (миграция `000058`) уже несёт `amount DOUBLE PRECISION CHECK (amount >= 0)` и `updated_at TIMESTAMPTZ` — «Добыча итерации 3» прямо заложена в её комментарии (`CHECK >= 0 (ноль разрешён на добычу итерации 3)`).
- `settlement_branches` / `settlement_branch_buffers` (миграция `000064`) покрывают вход/выход и чек-точку.
- **Не вводим:** `depleted`/`status`/`discovered`/`extracted` у залежи, новых колонок у ветки, `capacity`. Состояние «выработана» — **производное от `amount = 0`**, не поле (п.26; анти-сущность).
- **Пометка к `docs/specs/99.2.5-resource-model.md`:** запланированный там **«признак выработки» как колонка отменяется** — состояние выработки **производно** от `amount = 0` (анти-сущность, п.26), отдельной колонки `depleted` не будет (дельта в §18).
- DDL не меняется → новый номер миграции **не нужен**, вопрос О1 итерации 2 не переоткрывается.

### 3.2. Что ветка читает из залежей (live, без снимка)

- **Область:** `deposits` планеты поселения ветки: `planet_id = settlement.planet_id`.
- **Фильтр ресурсов:** `good_id` ∈ заполненных компонентов рецепта (`recipe_components.component_id IS NOT NULL`) — фильтр по `component_id`, не по `kind` (как в итерации 2 §3.3).
- **Агрегация компонентов:** строки рецепта с одинаковым `good_id` (допустимо — уникальности `(recipe_id, component_id)` нет, `000055`) сворачиваются в **один компонент** с суммарной нормой `quantity_i = Σ quantity`; в залежь идёт один `good_id` → двойного списания запаса и завышения выхода нет (§1, T16).
- **Фильтр запаса:** берутся только `amount > 0` (нулевые не блокируются и не трогаются).
- **Порядок выбора:** внутри одного `good_id` — **от крупной к мелкой** по `amount` (`DESC`), ничья → `id ASC` (детерминизм, п.25).
- Залежь (`wealth`) на объём добычи **не влияет** — **только на показ**. Это **ПЕРЕОПРЕДЕЛЯЕТ** формулировку спеки итерации 1 («богатство — будущий множитель добычи», итерация 1 §2): по решению создателя на гейте 2026-09-22 (идея §3 п.27) `wealth` **не становится множителем добычи** — объём добора задаёт только `batches` (п.24). Выбор залежи — по запасу, не по богатству (F3, §13 С7).
- Дублирующей сущности нет: `deposits` итерации 1 переиспользуется целиком, состав не копируется.

## 4. Ленивая петля: точное место и механика

### 4.1. Где именно встраивается (пункт 1 задания)

**Точка запуска — не одна (полная поверхность).** Синк веток живёт в **`BranchRepository.SyncBranches` / `syncBranchTx`** (`internal/repository/branch_repository.go`). Его вызывает `attachBranches`, а `attachBranches` вызывается внутри `attachSettlements` — и из `GetPlanetsByWorldID`, и из **`GetPlanetByID`** (валидация `/travel`, прибытие, картинка). `GetPlanetByID` **не возвращает блок залежей** → **запись в `deposits` происходит и на путях без показа залежей**. Это **норма ленивой модели**: залежь — живое состояние, а не «результат открытия карточки».

Порядок «население → ветки (переработка + добыча) → залежи» сохраняется: в `GetPlanetsByWorldID` карточка показывает **уже уменьшенный** запас залежи.

**Оговорка (путь в памяти).** При `Δt < MinPersistInterval` выход ветки показывается **свежим** (считается в памяти), а запас залежи — **сохранённым** (отстаёт меньше кадэнса), потому что память в `deposits` не пишет. У админа это может выглядеть как «добыча не работает» — **это норма ленивой модели** (тот же механизм отставания, что у населения), не дефект; следующий персистентный синк закрывает разрыв (§4.1 ниже).

- **Персистентный путь** (`Δt ≥ MinPersistInterval`): всё в существующей транзакции `syncBranchTx` — `FOR UPDATE OF b` на ветке (уже есть) → топ-ап строк входа (уже есть) → **новое:** чтение залежей планеты под блокировкой → `ProcessBranch` с учётом залежей → запись входа, **залежей**, выхода, `processed_at` → `COMMIT`.
- **Путь «в памяти»** (`Δt < MinPersistInterval`): `applyProcessed(ProcessBranch(...))` c залежами, прочитанными **без блокировки**; **записи в БД нет** → `deposits.amount` **не уменьшается**. Карточка показывает расход входа/прирост выхода «свежее» сохранённого, а запас залежи — сохранённый (отстаёт на величину < кадэнса). Это **норма ленивой модели** (как и у населения); следующий персистентный синк посчитает Δt от сохранённого `processed_at` и заберёт ту же величину **один раз** (двойного учёта нет, потому что память не писалась).
- Чек-точка — прежняя **`settlement_branches.processed_at`**, своей чек-точки залежь **не получает** (`deposits.updated_at` — служебное, не чек-точка). Второй петли нет.

### 4.2. Источник `planet_id` (без нового JOIN-лока)

`attachBranches` уже обходит `planets[i].Settlements` — планета известна. `SyncBranches` получает рядом с населением **`planetID` поселения** (`map[string]settlementMeta{Population, PlanetID}` либо два map’а); join к `settlements` внутри ветки-транзакции **не добавляется** (не плодим порядок блокировок «ветка → поселение»).

### 4.3. Порядок расходования: **вход первым, залежь — добор** (пункт 2 задания)

Решение дизайнера, обоснование:

1. **Физика/бухгалтерия:** вход — уже добытое сырьё «на руках»; нет причины сыпать свежую руду поверх лежащей. Сток расходуется раньше источника (FIFO).
2. **«Проходной вход» (п.24):** если первым черпать залежь, ручное «добавить во вход» **никогда** не расходуется при живой залежи — вход превращается в склад, что прямо противоречит п.24.
3. **Админ видит эффект:** песочный инкремент входа немедленно превращается в выход (тот же проход) — кнопка итерации 2 остаётся рабочей и наблюдаемой.
4. **Цена:** при накопленном вручную входе залежь временно не расходуется — принято (песочный сценарий, воспроизводим).

Порядок внутри: по каждому компоненту — `min(input_i, потребление_i)` из входа, остаток — из залежей по правилу §3.2.

### 4.4. Конкурентность, порядок локов, отсутствие минуса (пункты 1, 3)

- **Порядок блокировок единый: ветка → залежи.** Сначала `FOR UPDATE OF b` на строке ветки (уже есть, точка сериализации итерации 2), затем `SELECT ... FROM deposits WHERE planet_id = $1 AND good_id = ANY($2) AND amount > 0 ORDER BY id FOR UPDATE` — **детерминированный порядок по `id`** (не по `amount`), чтобы две конкурирующие транзакции брали одни и те же строки в одном порядке → **дедлоков нет**.
- **Честная граница этого утверждения.** «Дедлоков нет» доказано **только для синка веток между собой**. Путь **удаления ресурса/товара в студии** (`DeleteGood`, **одна транзакция**) каскадом трогает и `deposits` (`goods → deposits` CASCADE), и `settlement_branches` (`goods → recipes → settlement_branches`); когда `good` выступает **в обеих ролях** (выход одного рецепта и компонент другого с залежами), порядок блокировок студии может **инвертироваться** против «ветка → залежи». **Явный риск** (отсутствие дедлока здесь не доказано). Решение — **рантайм-проверка @tester** (нагрузочный сценарий «`DeleteGood` идёт параллельно с синком веток», T15); дизайн-обход (упорядочить локи студии) — кандидат на §18, не в объёме.
- **Несколько веток на одном поселении / одной залежи.** Ветки синкаются **последовательно, каждая в своей транзакции** (как сейчас) → конкурентных блокировок между ними нет в одном запросе; при двух параллельных запросах на один мир работает правило «ветка1 → залежи по id» / «ветка2 → залежи по id»: пересекающиеся залежи берутся в одном порядке, потерь и дедлоков нет.
- **Суммарная убыль при дележе залежи = сумма переработок веток.** Каждая ветка в итерации 2 работает **всем населением** (принятая упрощёнка, §12 С7 итерации 2), поэтому две ветки на одной планете тянут из общей залежи с суммарной скоростью ≈ 2× «население». **Названо явно как принятое поведение** (п.23+п.24); дешёвая альтернатива — поле «доля людей»/приоритет (§7 F2, F4). Решение — за создателем (F2).
- **Почему нет двойного учёта:** `batches` считается один раз; потребность `batches × quantity_i` разбивается на источники **без пересечения** (вход ⊕ залежи); каждая единица списывается ровно из одного места. Сумма списаний = ровно потреблённому.
- **Почему нет минуса:** `batches ≤ stock_i / quantity_i`, а залежи обходятся до насыщения `need_i`, поэтому ни `input_i`, ни `deposit_j` не уходят ниже нуля; на всякий случай — кламп `max(0, …)` перед записью. БД-`CHECK (amount >= 0)` остаётся страховкой, не штатным путём.
- **Идемпотентность:** `ProcessBranch` при `Δt ≤ 0` возвращает состояние без изменений → ни вход, ни залежи не пишутся; после записи `processed_at = now`, повторный вызов с тем же `now` — no-op (как в итерации 2). `Recompute(Recompute(now)) = Recompute(now)`.
- **Стен-стенд:** состояние механики — только строки БД (`settlement_branches`, `settlement_branch_buffers`, `deposits`); общих `map` нет, WS не нужен (`AGENTS.md` §0).

### 4.5. Режим отказа (что ветка НЕ делает)

- Нет залежей нужного ресурса и пуст вход → `batches = 0`, ветка стоит (не ошибка).
- Залежь истощилась по одному компоненту → ветка встаёт **целиком**, даже если по второму компоненту запас есть (батч требует всех компонентов) — названо.
- Рецепт без заполненных компонентов / без `good_id`-выхода → как в итерации 2 (ветка не активна / создание отклоняется).
- Залежь удалена в студии (CASCADE по `goods`) → ветка просто теряет источник, не падает.

## 5. Ручки и видимость (пункты 4, 6)

### 5.1. Новых ручек нет

- Ветки/вход по-прежнему скрыты от player (`stripBranchInputs`, `p.Settlements = nil`) — **не трогаем**.

### 5.3. Прочие видимости

Выход ветки, вход «только админ», детали поселения — без изменений (итерация 2 §6).

## 9. Числа и цель калибровки

- **Скорость не меняется** — та же `k = 2.78·10⁻⁸` батч/(чел·ч), `rate = k·population/complexity` (итерация 2 §4.1, решение создателя О6). Второй ручки **нет** (п.24).
- **Время жизни залежи** = время переработки её содержимого: залежь `[500, 1500]` при медианном `P_ref ≈ 5·10⁸` (равномерный `[1e5, 1e9]`) — **≈ 3 суток** (рабочая оценка итерации 2, переносится без изменений). Разлёт по населению ≈ 10⁴× (1e5 → ≈41 год, 1e9 → ≈1.5 суток) — **принят создателем осознанно** (итерация 2 §4.1), не переоткрываем.
- **Связка компонентов:** батч требует всех компонентов, поэтому ветка останавливается по **наименьшей** залежи пары (`Мясо`/`вода-ресурс`); при двух ветках — по сумме (§4.4).
- **Цель калибровки:** `T` медианного поселения на залежи `[500,1500]` — сутки–неделя (как в итерации 2). Статус: **не калибровано** — отдельный прогон @balancetester по итерации 3 **может не потребоваться** (ни одного нового числа формула не вводит); при желании — подтверждающий прогон на сценарии «две ветки делят одну залежь» (§4.4).
- **Сущности вне игры, влияющие на формулу:** нет — `population`, `complexity`, состав рецепта, `deposits.amount` существуют; убежища/купола/склады в формулу не входят.

## 12. Критерии приёмки / тесты (красные до кода)

| # | Что проверяет |
|---|---|
| T1 | **Базовый добор:** залежь планеты, пустой вход, большой Δt → `deposits.amount` убыл на `batches × quantity`, выход вырос на `batches`; **вход не вырос** (проходной) |
| T2 | **Вход первым:** вход ≥ потребности за Δt → залежь **не тронута**, вход убыл на `batches × quantity` (F4-A) |
| T3 | **Добор остатка:** вход < потребности → вход обнулился, залежь убыла ровно на недостачу |
| T4 | **Нет минуса:** при огромном Δt малая залежь → `batches = affordable`, `deposits.amount = 0` (не ниже), `CHECK (amount >= 0)` не срабатывает; выход = `affordable` |
| T5 | **Порядок «от крупной к мелкой»:** две залежи одного ресурса → расходуется крупная до нуля, затем мелкая; ничья по запасу → меньший `id` первым |
| T6 | **Лимит по компоненту:** залежь одного компонента истощена → ветка стоит целиком, даже если второй компонент доступен (дефицит `batches = 0`) |
| T7 | **Идемпотентность:** повторный вызов с тем же `now` не меняет ни буферы, ни залежи, ни `processed_at`; `Recompute(Recompute(now)) = Recompute(now)` |
| T8 | **Память не пишет:** Δt < `MinPersistInterval` → `deposits.amount` в БД **не изменился**; отображение считает добор в памяти; записи нет |
| T9 | **Нет двойного учёта (память → персистент):** чтение «в памяти» + следующий персистентный синк забирают ровно один объём (суммарное списание = одному проходу) |
| T10 | **Одна залежь, две ветки:** обе ветки синкаются последовательно; суммарная убыль = сумме их переработок; потерь/минуса нет (принятое поведение §4.4 названо) |
| T11 | **Порядок локов/дедлок:** два параллельных синка веток с пересекающимися залежами → без дедлоков и потерянных обновлений (`-race`) |
| T12 | **Видимость:** player со знанием не видит `amount = 0` (активные видит); player без знания — залежей нет вовсе (правило итерации 1 цело); админ видит и выработанные |
| T13 | **Студия/каскады:** удаление ресурса-компонента сносит его залежи (итерация 1) и выводит компонент из рецепта; ветка живёт; новых предупреждений студии не появилось; удаление товара-выхода сносит ветку (итерация 2) |
| T14 | **Фронт (Node-смоук):** `groupDeposits` считает `depleted`; модуль исполняется в Node без DOM/сети на верхнем уровне; админ-рендер помечает «выработано» |
| T15 | **Студия + дедлок (риск §4.4):** параллельно идут синк веток и `DeleteGood` ресурса, который **в обеих ролях** (выход одного рецепта и компонент другого с залежами) → рантайм-проверка отсутствия дедлока/потерь под `-race`; если дедлок воспроизводится — блокер, фиксируется и уходит в дизайн (упорядочить локи студии) |
| T16 | **Дубликат `component_id`:** рецепт с одним `good_id` на двух `pos` (разные `quantity`) → компонент **один** с суммой норм; запас залежи списывается **один раз** на `quantity_i = Σ quantity`, выход = `batches` (не завышен); при нехватке считает по агрегату |

**Приёмка «добыча работает»:** админ ставит залежи `Мясо` и `вода-ресурс` на планету поселения → создаёт ветку «Пища» (id 69) → при повторном открытии карточки (Δt ≥ порога) вход пуст/проходной, выход («Пища») растёт, **запасы залежей уменьшились**; выработав залежь, игрок перестаёт её видеть, админ видит её с пометкой «выработано».

## 15. ГД-сущность-кандидат (+1 предложение, не решение)

**Вопрос:** сделать ли органические залежи **возобновляемыми**?
**Ответ-предложение (дизайнер, кандидат):** `растения`/`мясо` (органика) медленно восстанавливают запас до исходного/богатством ограниченного уровня, минеральные/водные — не восстанавливаются. Даёт стратегию «не выедать до конца», объясняет разницу органики и минералов и удерживает ветки живыми после первой выработки. **Цена:** свой чек-поинт у залежи (или вывод из `updated_at`) и своя скорость — второй источник, который при небрежном вводе применится **второй раз** поверх добора (двойной учёт). **В текущие числа не входит** (анти-двойной учёт: сейчас запас только убывает). Отсев — за создателем (F4).
