## 1. Решение (суть)

На астероиде-этапе экономики **залежь — объект поверхности**: при генерации планеты рождается
**случайное число залежей** из **трёх пилотных ресурсов каталога** (`planet + ресурс каталога + слой
+ богатство + конечный запас`), которые читаются карточкой планеты и **видны игроку только при
знании планеты**. Админ получает **инструмент добавить залежь на планету вручную** (песочница).

**Биомы в генерации залежей не участвуют** (решение создателя 2026-09-22, §0 п.1): залежь не зависит
от площадей/типов биомов. **«Что где» (какой ресурс в каких условиях) — временное**: до отдельной
задачи конфигурации на всех планетах с поверхностью рождается случайный набор из трёх пилотов
(§3.2, §7, §15).

Итерация 1 даёт **факты мира** (что и где лежит), а не петлю: запас конечен, но **никто его не
расходует** — добыча, ветка поселения, входной/выходной буфер и переработка по времени (итерации 2–4,
§7) в объём не входят.

Пилотные ресурсы — **три** (решение создателя, §0 п.3): `растения`, `мясо`, `вода-ресурс` (§3.1).
Прежняя редакция «пилот — один ресурс „пища“» и вопрос О1 отменены: «пища»/«Еда» — **товар**,
результат переработки ресурса (§7, §11.2).

Вне объёма: таблица ресурсов биома и задача конфигурации «что где»; ветка/буферы/рецепт/ленивая петля,
добыча (снижение запаса), рост/потребности/голод, товар-еда и рынки, истощение залежи видимое на
поверхности, постройка «склад».

## 2. Термины (точные; «один термин — одно понятие»)

| Термин | Смысл | Не путать с |
|---|---|---|
| **Залежь** (`deposits`) | Инстанс ресурса на планете: ресурс каталога + слой + **богатство** + **запас** | «месторождение» `99.2.5` (та же сущность, будущее расширение), легаси-сводка `planets.data.resources` |
| **Пилотный ресурс** | Ресурс каталога, включённый в генерацию итерации 1: `растения`, `мясо`, `вода-ресурс` (§3.1) | «продовольствие» — **товар**, не ресурс |
| **Богатство залежи** (`wealth`) | 0–1, качество залежи (будущий множитель добычи) | «богатство» сводки `resource.Summary` (иная величина); доля биома |
| **Запас залежи** (`amount`) | Конечный объём ресурса в залежи; добычей убывает (итерация 3) | доля биома `share`; «потолок» — раздел «Потолок» в `GLOSSARY.md` (шесть значений; ближайшее по имени — «Потолок естественного запаса», `13_tiers.md` §13.12.2 — иное понятие) |
| **Ресурс поверхности** | Ресурс, который рождается залежью на поверхности | легаси-категории поверхности (`surfaceToCategories`) |

**Целевая модель (итерации 2–4; термины фиксируем сейчас, нормативно не используем):** **ветка**
(связь поселение ↔ рецепт каталога), **входной/выходной буфер**, **припас** (накопление ветки),
**осадок** (результат сверхпереработки ресурса в товар, напр. «Еда»; §0 п.5). «Буфер» перегружен
(`18_needs` §18.3.2, `13_tiers` §13.12.4) — в нормативном тексте итерации 1 он не употребляется;
семантика — в идее §5. Термины «залежь/пилотный ресурс/богатство залежи/запас залежи» — кандидаты на
строки `GLOSSARY.md` (владелец — @dispatcher; дельта менеджеру, §17).

**Состыковка с `99.2.5`.** Залежь — это **та самая** планируемая `deposits` (`99.2.5` §1: «Планета,
ресурс, запас, богатство, поверхность/недра, признак выработки»), взятая минимальным набором колонок;
`99.2.5` позднее добавит признак выработки/сводку. **Признак выработки в игре отсутствует** —
влияние на числа итерации 1 **исключено** (анти-ловушка «описываем то, чего нет»).

## 3. Модель данных — итерация 1

### 3.1. Пилотные ресурсы (три; биом-конфиг не трогается)

Источник — **каталог `goods`** (БД = источник правды, `000045`). Сверено по каталогу 2026-09-22:

| Имя (в БД) | `id` | `name_norm` | Категория |
|---|---|---|---|
| `Растения` | 358 | `растения` | Органика |
| `Мясо` | 359 | `мясо` | Органика |
| `вода-ресурс` | 1 | `вода-ресурс` | Вода |

- Все три — `kind='resource'`; резолв **по `name_norm`** (`goods.name_norm UNIQUE`, `000045`).
- **Точка инъекции карты «имя ресурса → `goods.id`» (техническое).** Каталог биомов/генератор
  (`internal/generator/planet`) в БД не ходит (тесты идут `NewGenerator(nil, seed)`), поэтому карту
  подаёт вызывающий (админ-путь / генерация миров) **сеттером по образцу `SetMeans`/`SetRaceTuning`**
  (`planet_data.go`): `g.SetGoodsIndex(map[string]int64)` (ключ — `name_norm`). Без инъекции карта
  пуста → все имена «неизвестны» → залежей нет (покрыто T12); тесты T1/T3 подсовывают карту явно, а не
  полагаются на БД.
- **Список пилотов** — константы генератора (три имени `name_norm`); таблица ресурсов биома и её
  валидация **не заводятся** (§0 п.2). Неизвестное имя пилота → залежь **пропускается с логом** (не
  роняем генерацию из-за дрейфа контента).
- **Биом-конфиг не трогается:** `config/biome_catalog.json`, `BiomeDef`/`biome_catalog.go`,
  `admin_biome_catalog.go`, `web/static/js/admin/biomeCatalog.js` — вне объёма итерации 1.
  Конфигурация «что где» (какой ресурс в каких условиях) — отдельная задача (§7, §15).

### 3.2. Генерация залежей при генерации планеты (§1.2 идеи)

Залежи рождаются **на шаге генерации поверхности планеты**, **случайным числом**, **независимо от
биомов** (решение создателя, §0 п.1). Числа — ручки, калибровка @balancetester, §9.

**Предикат «у планеты есть поверхность» (точный; без «разработчик догадается»).** Залежь рождается,
если у тела есть поверхность: `data["surface_composition"]` **непуста** **и**
`data["is_gas_giant"] != true`. Критерий — **наличие поверхности**, а не биомы (биомы в генерации
не участвуют, §0 п.1; у экзотических остатков ключа `biomes` нет вовсе). Разбор случаев:

| Тело | Поверхность (данные) | Залежи |
|---|---|---|
| Каменистая/ледяная/океаническая планета общего пути | `surface_composition` есть | **да** |
| P-планета тесной двойной (`generateCircumbinaryPlanet`, `circumbinary.go`) | `surface_composition` есть | **да** |
| Газовый гигант (`planet_data_gas.go`) | `surface_composition` нет, `is_gas_giant: true` | **нет** (T2) |
| Экзотический остаток — мёртвое тело у ЧД/НЗ/БД (`exotic.go`, `buildExoticPlanet`) | `surface_composition` есть (камни/кратеры) | **да** (О7) |
| Спутник газового гиганта (`PlanetSatellite`) | поверхность (поля) есть, но **своей строки `planets` нет** | **нет** (структурно: `deposits.planet_id` — FK на `planets(id)`) |

- **Точка вызова одна** — `generateWorldWithCountIntoBuffer` (`planet_data.go`), после получения
  `*PlanetData` из **любой** ветки (общий путь / экзотика / P-планета): хелпер `g.generateDeposits(planet)`
  проверяет предикат **по данным** (`planet.Data`) и наполняет `PlanetData.Deposits`. Проверка по
  данным, а не по ветке кода: новый тип тела с поверхностью получит залежи без правки предиката.
- Спутники залежей не получают **структурно** — второй уровень (недра спутника) вне объёма (§15).

Форма:

```
если hasSurface(planet):                               # surface_composition непуста и не газовый гигант
    n = randInt(rng, depositsMin, depositsMax)          # число залежей; ноль достижим при depositsMin = 0
    для i в 1..n:
        r        = pilots[rng.Intn(len(pilots))]        # равновероятно из трёх пилотов
        wealth   = wealthMin + rng.Float64 · (wealthMax − wealthMin)   # 0..1
        amount   = amountBase × (1 + jitterRng)         # jitterRng ∈ [−jitter, +jitter]
        → залежь (planet, good_id(r), 'surface', wealth, amount)
```

**Дизайн-ручки — значения-заглушки** (⚠️ **не калиброваны**, калибровка — @balancetester, §9; иных
значений @developer не выдумывает — генерация и админ-добавление (§6) берут их отсюда):

| Ручка | Заглушка | Смысл |
|---|---|---|
| `depositsMin` | `0` | нижняя граница числа залежей (`0` — ноль залежей на планете **допустим**, см. ниже) |
| `depositsMax` | `4` | верхняя граница числа залежей |
| `wealthMin` | `0.2` | нижняя граница богатства |
| `wealthMax` | `1.0` | верхняя граница богатства (0–1, §3.3) |
| `amountBase` | `1000` | базовый запас, **условные единицы** (единицы ресурса в игре ещё нет) |
| `jitter` | `±0.5` | размах запаса: `amount = amountBase × (1 + rng.Float64()·2·jitter − jitter)` → `[500, 1500]` |

- Ноль залежей на планете — **допустим** и достижим: `n = randInt(rng, 0, 4)` при `depositsMin = 0`
  (согласовано с T1/T4; противоречия «ноль допустим / `min > 0`» нет).
- **Биомы не читаются:** `Biomes`/`share` в генерацию залежей не входят; «площадь биома → число и
  жирность» отменено (§0 п.1).
- **Выбор ресурса — равновероятно из трёх, независимо от типа поверхности/биома** (в т.ч.
  `вода-ресурс` может родиться на безводной планете). Это **временное** распределение «что где», а не
  модель мира: заменяется отдельной задачей конфигурации (§7, §15; вопрос О6).
- **Несколько залежей на один ресурс разрешено** (разные пятна): у `deposits` **нет** UNIQUE по
  `(planet, resource, stratum)`. Разворот A/B — §4 F2, подтверждение — §12 О2.
- **Правило `99.2.5` §4 снято для итерации 1** (дельта — §17): `99.2.5` требует «запас зависит от
  типа и доли источника, а не случайное число в фиксированном диапазоне». Итерация 1 — **случайная
  генерация** (решение создателя 2026-09-22, §0 п.1); правило **временно перекрыто** и вступает в силу
  в полной модели `99.2.5` (генератор полей «дом + радиус»). См. П4 (§11.2).
- **Новые роллы и `PITFALLS` «Дизайн и числа»** (пункт «**Точные значения планет НЕ
  детерминированы между прогонами одного seed**»): детерминизм держится лишь на уровне «тот же
  seed → то же распределение/те же ручки», а порядок потребления `rng` плавает (итерация map в
  `resolveConflicts`/`applyRandomJitter`); «золотых» значений планет по seed нет, тесты сравнивают
  вывод подкрутки (`raceTunePlanet`) или RNG-поток, не `planet.data` целиком. Новые роллы залежей
  идут в **главный поток** `rng` как есть; seed-зависимые тесты **перепроверяются** (T10). Разворот
  «главный поток vs изолированный суб-RNG» — §4 F3.

### 3.3. Залежь — объект: таблица `deposits` (§1.3 идеи)

Носитель — **отдельная таблица**, не JSONB `planets.data` (ловушка whitelist-маппера
`populatePlanetFromJSON`, `PITFALLS`; задача прямо запрещает JSONB). Формат 1:1 ложится на
планируемую «месторождение» `99.2.5` — второй слой (недра) влезает в ту же схему (значение `stratum`).

```
deposits (
  id            uuid PK,
  planet_id     uuid  NOT NULL FK planets(id) ON DELETE CASCADE,
  good_id       bigint NOT NULL FK goods(id) ON DELETE CASCADE,   -- удаление ресурса в студии сносит залежи (§0 п.4)
  stratum       text  NOT NULL DEFAULT 'surface' CHECK (stratum IN ('surface','subsurface')),
  wealth        double precision NOT NULL CHECK (wealth >= 0 AND wealth <= 1),
  amount        double precision NOT NULL CHECK (amount >= 0),   -- запас (конечный)
  created_at    timestamptz NOT NULL DEFAULT NOW(),
  updated_at    timestamptz NOT NULL DEFAULT NOW()
)
+ индекс (planet_id), индекс (good_id)
```

- FK на `goods(id)` — **`ON DELETE CASCADE`** (решение создателя, §0 п.4): студия удаляет ресурс —
  его залежи уходят вместе с ним (T8). «Ресурсность» (`kind='resource'`) проверяется при создании
  (проверка в коде/вводе, §3.1/§6) — составного FK «`(good_id,'resource')`» не вводим (минимализм).
- **Предупреждение при удалении ресурса (одобрено создателем 2026-09-22; FK CASCADE — §0 п.4).**
  Сейчас FK `CASCADE` сносит залежи удаляемого ресурса **у всех планет молча**. Требование: перед
  удалением студия получает и показывает **число залежей этого ресурса во всех мирах** (`COUNT(*)` по
  `deposits.good_id`), удаление **подтверждается вместе с этим числом**; ответ удаления несёт счётчик.
  Число берётся **одним источником** — метод репозитория залежей `CountDepositsByGood(goodID)`
  (используется и предпроверкой, и удалением). Файлы и тест — §8.1, §8.3, T14.
- `amount`: граница БД — **`CHECK (amount >= 0)`** (ноль разрешён на будущее: добыча итерации 3
  истощает залежь до нуля); **генерация** при заглушках (§3.2) даёт строго `amount > 0` (`[500, 1500]`).
  Границы согласованы с T4: «БД `≥ 0`» и «генерация `> 0`» — один инвариант, не противоречие.
- `depleted`/`amount_initial` **не вводим** — выработки в итерации 1 нет (анти-двойной учёт); появятся
  с добычей (итерация 3) или в `99.2.5`.
- Каталог (`goods`) миграция не трогает; числа в миграции не задаются.

### 3.4. Пути записи залежей

Залежь генерируется **вместе с планетой** и **обязана записаться там же, где записалась планета**
(иначе инвариант «залежь рождается с планетой» держится не везде). Известные пути вставки планет:

| Путь | Файл | Как пишутся залежи |
|---|---|---|
| Массовая генерация (COPY, батч 500) | `internal/generator/planet/planet_data.go`, `planet_data_batch.go` | второй COPY-буфер `deposits` рядом с `planets` в той же транзакции |
| Прототип (1 планета) | `internal/handlers/admin_universe.go` (`GeneratePrototypePlanet`) | INSERT из `PlanetData.Deposits` в той же tx |
| Гипотезы/близнецы | `internal/handlers/admin_hypothesis.go` | INSERT из `PlanetData.Deposits` (консистентность) |

Генератор уже владеет БД и транзакциями (`flushBatch(tx)`), поэтому залежи несутся в `PlanetData`
как `[]DepositData` (в памяти) и пишутся вызывающим. `PlanetData.Resources` (легаси-сводка) — не трогаем.

### 3.5. Легаси-сводка `planets.data.resources` — решение (не дублировать молча)

Легаси-сводка (`internal/resource/generator.go`/`summary.go` → `data["resources"]`; маппинг
`surfaceToCategories` в `internal/resource/categories.go`) **читается картой** (`mapcache/snapshot.go`)
и **силой фракций** (`generator/faction/faction.go`).

**Решение итерации 1:**
- Генерация залежей **не читает** легаси-сводку и **не читает биомы** (§3.2).
- Генерация залежей **не пишет** в `planets.data.resources` — дублирования нет (T11).
- Легаси-сводка **остаётся как есть** и продолжает кормить карту/силу фракций; её смысл не меняется.
- Две привязки поверхности сосуществуют **осознанно и названо**: легаси — «форма → *категории*»,
  новая — «планета → *конкретные залежи*» (случайные). Сведение в одну модель — задача `99.2.5`
  (там же `substances` и место сводки). Молчаливого дубля нет: итерация 1 новую сводку не строит.

## 5. Видимость и просмотр (§1.4/§1.5 идеи)

### 5.1. Только при знании планеты (решение создателя «а», идея §3 п.8)

Единый чок-пойнт — `stripPlanetDetails` (`internal/handlers/planet_visibility.go`): для `role=player`
без записи в `player_planet_knowledge` залежи **обнуляются** (`p.Deposits = nil`), как фракции/строения;
при наличии знания — остаются. `admin`/`skycomposer` — без фильтра (И7).

**Инвариант «залежи не утекают» (точки вызова `attachDeposits` — закрытый список).** `attachDeposits`
вызывается **ровно в одном методе репозитория** — `GetPlanetsByWorldID` (`planet_repo.go`): он кормит
**единственный** endpoint карточки `GET /api/worlds/{id}/planets`, и **только** этот путь проходит
`applyPlanetVisibility` → `stripPlanetDetails` (`planet_handler.go:117` — единственная точка фильтра).

| Метод репозитория | Залежи | Почему |
|---|---|---|
| `GetPlanetsByWorldID` (карточка) | **подтягивает** `attachDeposits` | единственный путь, сериализуемый игроку, и уже фильтруется `stripPlanetDetails` |
| `GetPlanetsLightByWorldID` (лёгкий; `/travel`, `/api/intrasystem-flight`, surface) | **не подтягивает** | идёт только в валидацию/радиус цели, игроку не сериализуется; light-путь остаётся light |
| `GetPlanetByID` (валидация `/travel`, `arrivalTargetValid`, картинка планеты, админ-смертность) | **не подтягивает** | результат игроку не сериализуется; залежи там не нужны |

- `stripPlanetDetails` всё равно чистит `p.Deposits` для `role=player` без знания — **защита в
  глубину** (как `Biomes`/`Factions`/`Buildings`), на случай будущего потребителя.
- **Инвариант:** путь, отдающий планету игроку **без** `applyPlanetVisibility`, залежей не несёт
  (`Deposits == nil`). Новый потребитель списка планет обязан либо идти через `stripPlanetDetails`,
  либо не вызывать `attachDeposits`.
- Закрепляется T6 (в т.ч. на light-путях: `GetPlanetsLightByWorldID`/`GetPlanetByID` → `Deposits` nil).

### 5.2. Карточка планеты

В ответ `GET /api/worlds/{id}/planets` добавляется блок `deposits` — **построчно** (`deposits[]`,
без серверной группировки):

| Поле | Смысл |
|---|---|
| `deposits[].good_id`, `good_name` | ресурс каталога |
| `deposits[].stratum` | слой (итерация 1 — `surface`) |
| `deposits[].wealth` | богатство 0–1 |
| `deposits[].amount` | запас (конечный) |

## 6. Инструмент админа: добавить залежь вручную (§1.6 идеи)

**`POST /admin/planets/{id}/deposits`** (JWT `admin`/`skycomposer`), файл `internal/handlers/admin_deposits.go`.

Тело: `{ good_id | good_name, stratum? (дефолт 'surface'), wealth?, amount? }`.
- `wealth`/`amount` **не заданы** → берутся **значения-заглушки дизайн-ручек** (§3.2): `wealth` —
  равномерно в `[wealthMin, wealthMax]`, `amount` — `amountBase × (1 + jitterRng)`; заданы — песочная
  правка. Отдельных «своих» дефолтов у админ-ручки нет (один источник чисел — §3.2).
- `stratum` не задан → `'surface'`; итерация 1 — только `'surface'` (иное значение → 422, задел
  `'subsurface'` живёт в DDL §3.3, но не принимается).

Действие (одна транзакция):
1. Гейты: `statusManager.IsRunning(JobPacman)` → 409; `universeMutationMu.TryLock()` → 409 (образец —
   `GenerateFactions`, `admin_universe.go`). Планеты нет → 404; ресурса нет или `kind != 'resource'` → 422.
2. INSERT залежи (несколько пятен допустимы, §3.2) во вселенной и её `truncateTables`/каскадах (§8).
3. **Контракт ответа (200).** Одиночной ручки «планета» нет — карточка world-scoped
   (`GET /api/worlds/{id}/planets`). Поэтому ответ собирается так: `world_id` планеты — запросом
   `SELECT world_id FROM planets WHERE id = $1` (та же tx; планеты нет → 404 шага 1), затем полный блок
   залежей планеты отдаётся в формате `deposits[]` карточки (§5.2):

   ```json
   { "planet_id": "...", "world_id": "...",
     "deposits": [ { "good_id": 1, "good_name": "вода-ресурс", "stratum": "surface",
                     "wealth": 0.5, "amount": 1000 } ] }
   ```

   Клиент (админ-карточка) заменяет блок `deposits` этим значением; отдельный GET планеты не заводим.

Существующие ручки не трогаются; удаление/правка залежи в песочнице — **вне объёма** (кандидат позже).
**Размещение кнопки** (карточка планеты / отдельная вкладка «Залежи») — §12 О3 (финально @uidesigner).

## 7. Целевая модель (итерации 2–4 эпика; нормативно НЕ входит)

Полный план — идея §2. Кратко, для контекста:

- **Итерация 2.** Ветка поселения ↔ **рецепт каталога**; **входной и выходной буфер**; рецепт реально
  превращает вход в выход; админ-действие «добавить ресурсы» во вход (без добычи).
- **Итерация 3.** **Добыча — отдельная механика**: ветка черпает из залежи во вход и **уменьшает
  `deposits.amount`**; ленивый пересчёт по Δt (свой таймстамп, не `settlements.computed_at`).
- **Итерация 4.** Ленивая петля вход → рецепт → выход; часть уничтожается, часть в выходном буфере;
  видимая петля в карточке.

**Переработка ресурса в товар** (решение создателя 2026-09-22, §0 п.5): ветка перерабатывает **ресурс**
(напр. `мясо`) в **товар** (напр. «Еда» / Food); **сверхпереработка = «осадок»**. **Залежь к «осадку»
отношения не имеет** — залежь самостоятельный объект поверхности; прежнее противопоставление
«конечный запас залежи vs возобновляемый осадок» снято.

**Конфигурация «что где»** (какой ресурс в каких условиях рождается) — **отдельная задача** после
итерации 1; в итерации 1 генерация случайна и от биомов не зависит (§3.2). Биом-конфиг при этом не
трогается (§3.1).

Схемы ветки/буферов здесь **не фиксируются** (итерация 2 даст свою спеку): не плодить сущность под
факт, которого ещё нет. `settlement_branches`/«припас» из прежней редакции этой спеки переносятся в
итерацию 2 (история — §16).
