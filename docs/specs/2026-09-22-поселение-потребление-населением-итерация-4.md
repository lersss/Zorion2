## 1. Решение (суть)

1. **Потребление** — вторая половина **того же ленивого прохода** ветки (спека итерации 2 §4.2, итерация 3 §1). Сначала ветка перерабатывает вход → выход (`output += batches`, как сейчас), затем **население съедает часть выхода**: `eaten = min(eat_k(товар ветки) · население · Δt, output)`; `output -= eaten`. **Норма берётся по товару-выходу ветки** (п.45): ветка «Вода» ест по норме товара «Вода», ветка «Пища» — по норме «Пищи»; нормы **изолированы** (не суммируются). Кламп `≥ 0` — выход в минус не уходит. Отдельной чек-точки, тика и кнопки нет.
2. **`eat_k` живёт у типа поселения, но отдельно на каждый товар.** Тип поселения — **подтип** справочника строений (`producer_types`): родитель «Поселение», дочка (пилот — «Обычное поселение»), нормы — в `params.eat` (JSONB, существующее поле), **гибкая структура** `{"eat": {"<товар-выход>": <k>}}` (п.45). Поселение получает **настоящую ссылку** на тип: новая колонка `settlements.settlement_type_id` (FK → `producer_types.id`), миграция `000067`.
3. **Съеденное не исчезает молча:** остаток (сделано − съедено) — это видимый выходной буфер, он же **«осадок»** (п.33). Отдельного механизма «осадка»/«сверхпереработки» **не вводим**; слово «осадок» здесь означает остаток буфера ветки и **разводится** с «осадком подножного корма» канона `13_tiers.md` §13.12 (та механика **не отменяется**, §13 С4/С5, дельта §20).
4. **Петля видна в карточке** (§6): вход (админ) / выход-остаток («осадок») / **сделано** и **съедено за последний проход** + **текущая скорость поедания (единиц/сек)** — `eat_k(товар ветки) · население / 3600` (п.39).
5. **Голод — вне объёма** (п.35/п.43): если съесть нечего, `eaten = 0` — последствий нет. **Потолка буфера нет** (п.36) — выход копится неограниченно.
6. **Эффект при нехватке — только направление** (п.42): механизм проектируется **широко** (цель эффекта — не только население), но **в этой итерации не применяется** (применение — отдельная задача после чекпоинта, п.43). Задел описан словами (§4.6); неиспользуемых полей/таблиц/типов **не вводим**.

Пилот — одно поселение людей, **две отдельные ветки** (п.41, каталог заведён п.44), один тип поселения «Обычное поселение»:
- **«Вода»** — рецепт **73**: вход `вода-ресурс` → выход товар **«Вода»** (остаток на выходе — «на продажу»; продажа — будущее, механики нет);
- **«Пища»** — рецепт **69**: вход `Мясо` → выход **«Пища»** (вода из рецепта **убрана** п.44).

Каждая ветка ест **по своей норме для своего товара-выхода** (решения О2 «на ветке» + п.45 «на товар»): ветка «Вода» — норма товара «Вода», ветка «Пища» — норма товара «Пища»; нормы **изолированы** (не суммируются между ветками). Модель обязана выдержать **несколько типов поселений** (п.31), **несколько поселений на планете** и **несколько веток на поселении** (п.23), а также **новые товары без переделок** (расширяемая структура `params.eat`, п.45).

```sql
-- Дефолтный тип (существующие БД, где сид producer_catalog_seed уже отработал):
-- подтип под «Поселением», БЕЗ товарной категории (Поселение — тип без слотов, §5.1).
-- Свежая БД: «Поселения» ещё нет (сид идёт после миграций) → 0 строк, тип
-- создаст Go-сид (seed_producers.go, §5.3). Оба пути дают один результат.
-- ⚠️ Число 2.5e-08 — ОДНО утверждённое (см. §8): то же в сиде (§5.3 п.1) и в

-- Структура норм — на товар-выход ветки (п.45): ключ — name_norm товара-выхода.
INSERT INTO producer_types (name, name_norm, kind, parent_id, output, input, params)
SELECT 'Обычное поселение', 'обычное поселение', 'goods', p.id, '{}', '{}',
       '{"eat": {"вода": 2.5e-08, "пища": 2.5e-08}}'
FROM producer_types p
WHERE p.name_norm = 'поселение' AND p.parent_id IS NULL
ON CONFLICT (name_norm) DO NOTHING;

-- Бэкфилл существующих поселений на единственный дефолтный тип (§3.4).

UPDATE settlements SET settlement_type_id = (
    SELECT id FROM producer_types WHERE name_norm = 'обычное поселение'
) WHERE settlement_type_id IS NULL;
```

- **`NULL` разрешён** (легаси-строки до бэкфилла, ручные фикстуры тестов); «тип не задан / нормы для товара нет» → ест по `DefaultEatK` (не «не ест», §3.2/§4.3) — не ошибка.
- **`ON DELETE RESTRICT`**, не CASCADE: удаление типа не должно сносить поселения (канон `producer_types.parent_id` — RESTRICT, спека дерева §1.2 п.7). Требует доработки `DeleteProducerType` (§5.4).

### 3.2. Где живёт норма (`params.eat`)

`producer_types.params` (JSONB, миграция `000048`; правится студией через `PUT /studio/api/producers/{id}` — поле `params`, `saveProdJSON`). Норма — **гибкая структура** (п.45): `{"eat": {"<товар-выход>": <k>}}`.

- **Ключ — товар-выход ветки** (п.45), в той же нормализации, что и `goods.name_norm` (напр. `"вода"`, `"пища"`). Обоснование выбора ключа (одной строкой): **товар-выход и есть то, что ветка «выдаёт» и что население ест** — норма привязана к потребляемому товару, а не к рецепту, поэтому одна норма действует на любой рецепт, дающий этот товар, и новые рецепты товара не требуют правки норм (расширяемость п.45).
- **Значение** — число (батч/(чел·час)) для этого товара.
- **Приоритет — единая семантика (один смысл на всех путях, §3.3/§4.2/§4.3):**
  1. `params.eat.<товар ветки>` **задан** → берём буквально, **в т.ч. явный `0`** = «этот тип не ест этот товар»;
  2. ключ `params.eat` / запись для товара **отсутствует/NULL** → константа кода `DefaultEatK` (в `internal/economy/settlement`), названная, как фолбэк `complexity NULL → 1` (спека итерации 2 §4.1).
  Каноничные числа живут в типе (студия); константа — страховка для типов/товаров, заведённых без настройки. «Не настроено» (нет записи) и «отказ от еды» — **разные состояния**; отказ задаётся только **явным `0`**, не пустым значением.
- **Нормы изолированы** (п.45): ветка «Вода» читает `params.eat["вода"]`, ветка «Пища» — `params.eat["пища"]`; значения **не суммируются** и не делятся между ветками. Нет записи для товара ветки → эта ветка ест по `DefaultEatK` (другие ветки это не затрагивает).
- **Расширяемость** (п.45): структура принимает **новые товары без переделок** — добавили рецепт нового товара и запись `params.eat.<новый товар>` в студии; новые **типы поселений** — соседние подтипы со своей структурой. Схема БД (`params` JSONB) не меняется.
- **Не вводим** отдельную таблицу типов, отдельную колонку `k`, поле на поселении/ветке, отдельную таблицу норм — тип уже несёт `params`, достраивать сущность не нужно (правило «сущность с двумя экземплярами — не сущность»).
- **Единицы:** батч/(чел·час) — те же условные единицы, что у `BranchRateK` (спека итерации 2 §4.1/§12 С5); единицы ресурса в игре нет.

### 3.3. Как читается норма на проходе

`GetSettlementsByPlanetIDs` (`internal/repository/economy_repository.go`) получает `LEFT JOIN producer_types pt ON pt.id = s.settlement_type_id` и тянет `pt.name` и **сырую** структуру `pt.params->'eat'` (JSONB-объект, **без `COALESCE`**): «записи для товара нет» обязано приехать как **отсутствие ключа** (иначе фолбэк `DefaultEatK` из §3.2 недостижим, и семантика расходится с §4.3). Фолбэк применяет **Go** на проходе ветки: `eatK = params.eat[<товар-выход ветки>]`, если запись есть (в т.ч. `0`); иначе `DefaultEatK`. Далее `attachBranches` (`planet_repo.go`) кладёт структуру норм в `eatBySettlement` и передаёт в `SyncBranches` рядом с населением и `planet_id`; **норма для конкретной ветки выбирается в `ProcessBranch` по товару-выходу её рецепта** (§4.1). **Новых JOIN-локов нет** (чтение вне транзакции ветки, как население). Модель: `models.Settlement.SettlementTypeID`/`TypeName` (JSON) + `EatByGood map[string]float64 \`json:"-"\`` (внутреннее поле для синка; JSON-вывод норм в карточку не добавляем — §6).

### 3.4. Бэкфилл и новые поселения

- **Существующие** поселения — бэкфилл миграцией `000067` (§3.1).
- **Новые** поселения должны получать тип **при создании** (иначе останутся без еды) — **решение гейта п.40 (ответ «а»): все 5 точек INSERT** (настоящая связь, не заглушка). Точки INSERT: `internal/generator/settlement/generator.go` (`copyInRows`, легендарный путь), `internal/generator/settlement/races.go` (`copyInRows`, расовый — основной), `internal/repository/economy_repository.go` (`CreateSettlement`), `internal/handlers/admin_universe.go` (прототип-планета), `internal/handlers/admin_hypothesis.go` (гипотезы) — **5 мест**. Помощник `ResolveDefaultSettlementTypeID(db)` (по `name_norm = 'обычное поселение'`, `0` если нет) вызывается один раз на джоб; колонка добавляется в списки `copyInRows`.
- Почему не «лазить по `NULL` на чтении»: это заглушка, прямо запрещённая п.32 («костыли не нужны»); связь обязана быть настоящей и заполненной. Цена — 5 точек INSERT (названо, F-backfill §7).

### 3.5. Что ветка читает о типе (live, без снимка)

`params.eat` берётся «живой» из `producer_types.params` на каждом проходе — как состав рецепта (итерация 2 §3.3). Правка нормы в студии меняет поведение **работающих** веток со следующего прохода. Снимок норм на ветке/поселении — отклонён (дублирование факта).

## 4. Потребление: формула, место в проходе, безопасность

### 4.1. Формула

Дополняет формулы итераций 2–3 (там — производство и добыча; здесь меняется **только хвост** прохода):

```
часы        = (now − processed_at) в часах                  # Δt ≤ 0 → без изменений
# --- производство (итерации 2–3, без изменений) ---
batches     = min(BranchRate(population, complexity) · часы, affordable)
output      = output + batches                              # выход растёт
# --- потребление (новое, п.31; норма — по товару ветки, п.45) ---
eat_k       = eat_k(товар-выход ветки)                      # params.eat[<товар>] типа, иначе DefaultEatK
eat_desired = eat_k · population · часы                     # линейно от населения
eaten       = min(eat_desired, output)                      # кламп ≥ 0
output      = output − eaten                                # «осадок» = остаток
processed_at = now
```

- `eat_k(товар ветки)` — норма типа для **товара-выхода этой ветки** из `params.eat` (или `DefaultEatK`, §3.2). **Нормы веток изолированы** (п.45): ветка «Вода» берёт норму товара «Вода», ветка «Пища» — норму «Пищи»; значения не суммируются и не делятся. **Порядок жёсткий:** производство → потребление (п.4.1 идеи: «сначала выход растёт на `batches`, затем убывает на `eat`»).
- **Население** — то же `population`, что у переработки (значение после ленивого пересчёта населения в той же точке чтения, итерация 2 §4.2); второго источника нет.
- **Сложность рецепта на потребление не влияет** (п.31: только тип и население). Следствие: отношение «еда/производство» = `eat_k(товар) · complexity / BranchRateK` — **не зависит от населения** (обе величины линейны по населению). При `complexity = 1` (пилот) оно постоянно для любого поселения; при `complexity > 1` производство медленнее, и отношение растёт (возможен дренаж буфера) — названо (§8).

### 4.2. Место в проходе и в коде

Потребление — **хвост той же чистой функции** `ProcessBranch` (`internal/economy/settlement/branch.go`), после `out.Output = b.Output + batches`. Норма выбирается **внутри `ProcessBranch` по товару-выходу рецепта ветки** из переданной структуры норм типа (п.45). Никаких новых петель, чек-точек, ручек и кнопок (п.31–34: скорость от населения и типа, не по кнопке). Поля `Branch`: + `EatByGood map[string]float64` — структура норм типа (уже разрешённые значения, §3.2/§3.3: явный `0` = «не ест этот товар», отсутствие записи → `DefaultEatK` к моменту вызова), + транзитные результаты прохода `ProducedLast`, `EatenLast float64` (для карточки, §6).

### 4.3. Идемпотентность, кламп, режим отказа

- **Идемпотентность:** как в итерациях 2–3 — `ProcessBranch` при `Δt ≤ 0` возвращает состояние без изменений; после записи `processed_at = now` повторный вызов с тем же `now` — no-op. `Recompute(Recompute(now)) = Recompute(now)`.
- **Кламп:** `eaten = min(eat_desired, output)`; `output ≥ 0` всегда; БД-`CHECK (amount >= 0)` (`000064`) — страховка, не штатный путь.
- **Режим отказа (согласован с §3.2):** норма для товара ветки `= 0` (явный) → `eaten = 0` (этот товар не едят); тип не задан / записи для товара нет → `eaten` считается по `DefaultEatK` (ест по фолбэку, не «не ест»); `output = 0` → `eaten = 0`, население «не ест» — **голода нет** (п.35, отдельная задача); население 0 → `eaten = 0`; ветка стоит по дефициту входа/залежи → производство 0, но накопленный выход **всё равно съедается** (названо: буфер выедается, если добыча встала).
- **Дренаж буфера** (питание накопленным при остановленном производстве) — штатное поведение, не ошибка (п.33/п.36).
- **Эффект при нехватке — задел без применения (решение гейта п.42, вариант «а»):** при нехватке выхода ветка **может** наложить эффект; механизм широкий (цель — не обязательно население). В итерации 4 **не применяется** — только направление, без новых полей/таблиц (§4.6). Применение — отдельная задача после чекпоинта (п.43, §16).

### 4.4. Конкурентность и локи

- **Порядок локов не меняется:** ветка (`FOR UPDATE OF b`) → залежи (`FOR UPDATE ORDER BY id`) — как в итерациях 2–3 (§4.2/§4.4). Потребление живёт внутри уже существующей транзакции `syncBranchTx` и **новых блокировок не вводит**.
- Абсолютная запись выходного буфера (`ON CONFLICT ... DO UPDATE SET amount = EXCLUDED.amount`) уже под локом ветки → потерянных правок нет; админ-ручка «добавить во вход» выход не трогает, конкуренции по выходу нет.
- Состояние механики — только строки БД (`settlement_branches`, `settlement_branch_buffers`, `deposits`, `producer_types`); общих `map` и WS у механики нет (`AGENTS.md` §0).

### 4.5. Путь «в памяти»

При `Δt < MinPersistInterval` (30 мин, `recompute.go`) пересчёт идёт **в памяти без записи и без блокировки** (итерации 2–3): потребление считается той же чистой функцией, `output` в БД **не меняется**, карточка показывает выход и «съедено» свежими. Следующий персистентный синк спишет ту же величину **один раз** (память не писалась) — двойного учёта нет.

### 4.6. Направление: эффект при нехватке — задел, без применения

**Решение гейта п.42 (вариант «а»).** Если население не может съесть норму (выхода не хватает), ветка — в перспективе — **накладывает эффект**. Механизм проектируется **широко**: целью эффекта может быть **не только население** (в будущем — что угодно: стабильность, рост, ресурс ветки/поселения, качество и т.п.). Поэтому задел не сводим к «голоду».

**В итерации 4 эффект НЕ применяется** — это **только направление**, зафиксированное словами:

- **никаких новых полей/таблиц/типов** под эффект **не вводим** (анти-спекулятивность; «сущность с двумя экземплярами — не сущность»);
- потребление (списание выхода) — есть; **эффект при нехватке — нет**; при нехватке `eaten = min(...)`, голода нет (§4.3, п.35);
- **применение эффекта — отдельная задача после чекпоинта** (п.43) — в роадмап/трекер, **не потерять** (§16).

Почему не «полголода» сейчас: применение эффекта требует своей сущности (что за эффект, на что, сила), а п.42/п.43 явно откладывают его. Задел словами фиксирует замысел, не создавая мёртвого кода/схемы.

## 5. Тип поселения и студия

### 5.1. Ключевая развилка: «дочка Поселения» и правила студии

**Факт (сверка по коду).** `CreateProducerType` (`producer_repository.go`) требует: подтип `kind=goods` — **обязательно** `category_id` и **применяемый слот родителя** (`producer_slots`, инвариант С4, спека `2026-09-21-студия-скрытые-категории-строений` §1.4 п.1). У типа «Поселение» слотов **нет** (`seed_producers.go`; `seedProducerSlots` даёт слоты только Фабрике/Автофабрике/Платформе) и категория товаров `NULL`. Значит, **создать подтип под «Поселением» существующим путём нельзя** (400). Дополнительно `buildProdTree` (`web/studio.html`) для `kind=goods` рисует детей **только из слотов** → подтип без товарной категории не показался бы и в дереве. Наконец, `CreateProducerType` **не принимает** `output/input/params` (params пишет только `PUT`).

**Развилка (варианты и цена) — решена гейтом: принят вариант B (решение п.37 — «без категорий, да; привязка к категориям — исключение, только для фабрик»; §18 О1→B):**

| Вариант | Что делаем | Цена |
|---|---|---|
| **B (принят гейтом, п.37)** | **Сужаем С4:** подтип `kind=goods` требует категорию товаров+слот **только если у родителя есть слоты**; у типа без слотов (Поселение) подтип — **без товарной категории**. Уникальность подтипа по кортежу применяется только при непустой категории товаров. Студия: рендер подтипов без товарной категории + путь создания | Правка инварианта С4 в `producer_repository.go`, уникальности, рендера дерева и попапа создания (`web/studio.html`) |
| **A (отклонён п.37)** | Дать «Поселению» **синтетическую категорию** + слот, подтип с `category_id`; путь создания — существующий узел-приглашение | Фальшивая категория в каталоге (`categories.kind` только `good`/`resource`); риск трактовки подтипа как «товарной фабрики» в `concreteGoodsFactories`/`BindRecipe`; скрытый слот скрыл бы и путь создания |
| **C** | Свой справочник типов поселений (вне `producer_types`) | **Противоречит п.32** («подтип справочника строений») — отклонён |

**Принцип варианта B (две разные проверки — не смешивать):**
1. **Нужна ли привязка к категории товаров** решает **наличие хотя бы одного слота родителя** (`EXISTS (SELECT 1 FROM producer_slots WHERE parent_id = parent)`, «есть слоты вообще») — не уровень расовости, не конкретная категория.
2. **Если категория задана** (у родителя слоты есть) — работает **прежний** `producerSlotApplied` на **уровне расовости записи** (применяемый слот, канон «самая конкретная побеждает») — как в `CreateProducerType`/`UpdateProducerType` сейчас.

Инвариант С4 защищает «фабрика категории должна быть предложена родителем». У типа, который ничего не предлагает (нет слотов), товарной категории **нет по определению** — подтип без товарной категории не ослабляет инвариант, а сужает его до применимой области. Escape hatch (удалить все слоты Фабрики) самозапирается: `DeleteSlot` запрещён при существующих подтипах-фабриках категории (`RESTRICT`).

## 8. Числа (предложение; **не калибровано**, @balancetester)

Производство при `complexity = 1` (пилот): `rate_prod = BranchRateK · P = 2.78·10⁻⁸ · P` батч/ч. Цель п.34: **еда чуть медленнее производства** — `eat_k < rate_prod/P`, т.е. `eat_k < 2.78·10⁻⁸`. Норма теперь **на товар** (п.45), поэтому провизорные числа даются **отдельно для «Воды» и для «Пищи»**.

**Предложение (провизорно): обе нормы `2.5·10⁻⁸`** батч/(чел·час) — старт одинаковый для «Воды» и «Пищи» (≈89.9 % от скорости производства при `complexity = 1`; «осадок» копится со скоростью ≈10.1 % производства по каждой ветке). **Помечено: не калибровано, @balancetester** (§17). Одинаковый старт выбран сознательно: обе ветки пилота — продовольственные товары одного порядка, эталона «вода дороже/дешевле еды» нет (п.45 задаёт структуру, не соотношение); разные нормы — вопрос калибровки, а не замысла. **Коридор В4 сохраняется** (`[2.363·10⁻⁸ … 2.641·10⁻⁸]`, +5…+15 % к остатку при `complexity=1`) — он применяется к норме **каждой** ветки.

| Норма (товар) | Значение | Доля от производства (`complexity=1`) | Прирост остатка | Медиана `P_ref ≈ 5·10⁸`: сделано/съедено/остаток в сутки |
|---|---|---|---|---|
| **«Вода»** (провизорно) | **2.5·10⁻⁸** | 89.9 % | +10.1 % | 333.6 / 300.0 / **+33.6** |
| **«Пища»** (провизорно) | **2.5·10⁻⁸** | 89.9 % | +10.1 % | 333.6 / 300.0 / **+33.6** |
| 2.64·10⁻⁸ (граница коридора) | — | 95 % | +5 % | 333.6 / 316.8 / +16.8 |
| 2.36·10⁻⁸ (граница коридора) | — | 85 % | +15 % | 333.6 / 283.2 / +50.4 |
| `DefaultEatK` (фолбэк кода) | — | — | — | **то же утверждённое число** — `2.5e-08` (не отдельная ручка) |

- **Один источник числа.** `2.5e-08` фигурирует в трёх местах — SQL-миграции (§3.1), сиде (§5.3 п.1) и константе `DefaultEatK` (§4.2) — и это **одно утверждённое** (после калибровки @balancetester) число, а не три независимых. В структуре `params.eat` оно стоит **под каждым товаром** («вода», «пища»); совпадение закрепляется тестом **T18** (§12); расхождение = баг. Меняется число — меняются все места синхронно (кандидат в `PITFALLS`, §20).

- **Свойство (не зависит от населения):** при `complexity = 1` отношение еда/производство `= eat_k(товар) / BranchRateK` **постоянно для любого населения** (обе величины линейны). Требование п.34 «для медианы» выполняется автоматически и для всех поселений — разлёт по населению (спека итерации 2 §4.1, ≈10⁴×) здесь **не проявляется** (в отличие от времени жизни залежи).
- **Граница:** при `complexity > 1` производство замедляется (делитель), еда — нет; при `eat_k(товар) · complexity ≥ BranchRateK` буфер **дренажится** (питание накопленным, §4.3). Названо; тонкая настройка по сложности — при калибровке.
- **Залежь/буферы — те же условные единицы** (итерации 2–3, §12 С5). Залежь `[500,1500]` при медиане — ≈3 суток производства (итерации 2–3); остаток растёт +33.6/сутки → «осадок» 1000 единиц ≈ за месяц. **Чисел новых, кроме норм `eat_k`, не вводится.**
- **Цель калибровки @balancetester:** подтвердить/подобрать нормы **по каждому товару** («Вода», «Пища») в коридоре «+5…+15 % к остатку при `complexity=1`» и проверить на диапазоне населения 1e5–1e9; проверить дренаж при `complexity = 2`; решить, нужны ли **разные** нормы для «Воды» и «Пищи» (пока обе `2.5·10⁻⁸`).
- **Сущности вне игры, влияющие на формулу:** нет — `population`, `producer_types.params.eat`, состав рецепта существуют; убежища/купола/склады в формулу **не входят** (склад каноном не вводится, §16).

## 15. ГД-сущность-кандидат (+1 предложение, не решение)

**Вопрос:** не сделать ли потребление **не только списанием, а потребностью с эффектом** (что даёт еда, кроме убыли буфера)?
**Ответ-предложение (дизайнер, кандидат, +1):** норма еды типа поселения — это **потребность** (не просто списание): у каждой записи `params.eat.<товар>` есть **вторая ось** — что товар даёт поселению (рост населения, удовлетворение, стабильность, ресурс и т.п.). Форма **«товар → норма»** уже принята п.45 (`params.eat`), поэтому кандидат — **расширение той же структуры** (напр. `{"eat": {"<товар>": {"k": <норма>, "effect": "<задел>"}}}`), без новой сущности. Симметрично корзине тира рас (`94a`). Даёт: разные типы поселений не только едят разное, но и **получают разное** от еды; связь с будущим ростом/потребностями (пожелание создателя §0 идеи: «что-то идёт в рост и удовлетворение потребностей»). **В текущие числа не входит** (анти-двойной учёт); пересекается с эффектами при нехватке (§4.6/§16 — отдельная задача после чекпоинта); отсев — за создателем.

**Рядом (уже названо, не считаю своим +1):** голод (п.35) — отдельная задача; «еда → рост населения» — следующий шаг после неё; форма «товар → норма» (`params.eat`) — **уже принята п.45**, не кандидат.
