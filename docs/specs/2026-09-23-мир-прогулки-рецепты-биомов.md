## 0. Одним абзацем

Форма рельефа, декор и цвет в прогулке сегодня заданы **шестью наборами на шесть категорий** (`FORMATIONS` в `surface_config.js`, `LIFE_DENSITY` там же), поэтому 12 литосферных биомов делят один силуэт, «дерево» в пустыне песочное, а поле `color` каталога (уже существует и валидируется) пусто у всех 57 биомов. Решение создателя по ЧК0 — «**надо всё брать, что украсит, а не выбирать**»: подход не выбираем, берём все украшающие слои (цвет/жизнь + ярусный горизонт + словарь профилей + скульптурный объём), от дешёвого к дорогому, объём — последним.

Эта спека делает из этого **один механизм**: **рецепт вида биома** — данные в справочнике биомов (`BiomeDef.view`), собираемые из **общей грамматики** (9 «семейств вида» + библиотека из 8 примитивов рельефа, 15 декора, 3 правил размещения, палитры и ярусного горизонта), **резолвится на сервере** и приезжает в пакет прогулки аддитивным полем `biome_view`. Клиентская константа `FORMATIONS` перестаёт быть источником правды и становится **фолбэком** для биомов без рецепта (до Э4 — поведение 1:1). Пять этапов: Э0 данные → Э1 цвет и жизнь → Э2 ярусный горизонт → Э3 словарь профилей (силуэт + снеговая линия) → Э4 раскатка ЧК1–ЧК5 → Э5 скульптурный объём (отдельным поздним решением).

## 1. Что решаем и что НЕ решаем

**Решаем (ЧК0):**
1. Схему рецепта вида как **данных справочника биомов** + правило слияния «семейство + дельта».
2. Доставку рецепта в клиент (**аддитивное поле пакета**, резолв на сервере).
3. Единую грамматику: примитивы рельефа/декора, правила размещения, палитру, ярусный горизонт — и **проверку покрытия 57 биомов**.
4. Рецепты трёх образцов (пески, джунгли/лес, горы) — сверенные с §11.
5. План этапов с ценой/риском/видимым результатом; границы и инварианты.

**Не решаем:**
- **Воду** — не раньше ЧК6 (решение создателя: «последним, подумаем, может лодку выдадим надувную»). Оазисы и русла в образцах — **сухие**, отрисовки жидкости нет.
- **Объёмный рельеф (2D)** — Э5, отдельным решением создателя после ЧК5.
- **Физику игрока** — не меняется (§6 п.3).
- **Раскатку на все 57** — ЧК1–ЧК5, по категориям, каждый со своим гейтом.
- **Полную админ-UI рецепта** — если создатель захочет править вид из админки на ЧК0, нужен @uidesigner (§7); на ЧК0 достаточно ручной правки JSON справочника (как сегодня правится остальной справочник).

## 2. Решение: рецепт вида как данные

### 2.1. Где живёт рецепт — один источник правды

**Рецепт — атрибут биома в справочнике `config/biome_catalog.json`.** Никакого второго реестра в JS (прямое следствие В9 спеки прогулки и §1.3 направления @gdesigner).

Справочник получает **три дополнения**:

1. **`BiomeDef.view`** — рецепт конкретного биома: `{family, …дельта}`.
2. **`view_families`** — новая секция справочника (рядом с `subterrain_types`/`planet_types`): 9 «семейств вида», каждое — полный рецепт-пресет (общая грамматика семейства).
3. **`view_primitives`** — новая секция: реестр допустимых `id` примитивов с их видом — **ровно четыре вида: `relief1d` / `relief2d` / `decor` / `placement`**. Нужен **валидации**: сервер проверяет, что рецепт ссылается на известные примитивы и ставит их в правильный блок. Список — данные (не дублируется в Go-коде); **реализации** примитивов — функции в клиенте (функция не может быть данными).

**Отдельного вида `horizon` НЕТ (ревизия 3, находка @critic М4).** Ярусы горизонта **переиспользуют профильные примитивы `relief1d`** (`wave`/`crest`/`dome`/`spike`) в роли «далёкого силуэта»: `horizon.layers[].profile.prim` обязан иметь `kind = "relief1d"`. Роль задаёт **блок**, а не примитив: одна и та же `wave` даёт и дюну под ногами, и гряду дюн на горизонте — разница в частоте, амплитуде, палитре и в том, что ярус **декоративен** (не твёрд, §6 п.1–3). Отдельный `kind: "horizon"` дублировал бы те же силуэты вторым реестром и разъехался бы с библиотекой §3.1.

**Почему в справочнике, а не в отдельном файле `biome_view_catalog.json`:** отдельный файл — это второй реестр, который надо синхронизировать по `id` биома; справочник уже правится в админке, валидируется, hot-reload'ится и уже отдаёт биому `name`/`category`/`description`/`liquid_medium` в пакет. Второй файл не даёт ничего, кроме риска расхождения. *(Цена выбора: файл справочника растёт; см. §2.2 — поэтому рецепт биома — дельта к семейству, а не 57 полных рецептов.)*

### 2.2. Схема рецепта

```jsonc
// config/biome_catalog.json → biomes[] → один биом
{
  "id": "пески_пустыни", "name": "Пески пустыни", "category": "литосфера",
  "color": "#cfa96a",                  // ← поле УЖЕ существует (валидируется как #RRGGBB);
                                       //    заполняется рецептом (Э1). См. §2.5 — влияет на картинку планеты
  "view": {                            // ← НОВОЕ: рецепт вида биома (дельта к семейству)
    "family": "песчаные",              // ссылка на view_families; можно опустить (тогда только дельта)
    "relief": {
      "ridge": 0.20, "flatten": 0.35, "offset": -10, "caves": 0.05, "float": false,
      "base": 1.0,                     // доля базовой fbm-составляющей (0–1), дефолт 1
      "scale": 1.0,                    // общий множитель амплитуд всех слоёв (§6 п.6 — бюджет)
      "layers": [ /* см. §3.1; порядок = порядок суммирования */ ]
    },
    "palette": { "base": "#cfa96a", "dark": "#9e7c45", "light": "#ecd6a4",
                 "accent": "#b8925a", "rock": "#7d6b57" },
    "decor":   [ /* см. §3.2 */ ],
    "hang":    [ /* декор, привязанный к другому декору: лианы к дереву */ ],
    "placement": { "mode": "clustered", "tile": 260, "gap": 16 },
    "horizon": { "layers": [ /* см. §3.6 */ ] },
    "landmark": { "prim": "oasis_dry", "perRegion": 6000 },
    "snowLine": null,                  // px ниже местного максимума; null = нет (§4.3)
    "life_density": 0.05
  }
}
```

**Секция `view_families`** — тот же объект, но без `family` (пресет сам себе семейство) и с обязательными `id`/`name`:

```jsonc
{ "id": "песчаные", "name": "Песчаные",
  "relief": { "ridge": 0.20, "flatten": 0.35, "offset": -10, "caves": 0.05, "float": false,
              "layers": [ /* … */ ] },
  "palette": { "base": "#cfa96a", "dark": "#9e7c45", "light": "#ecd6a4", "accent": "#b8925a" },
  "decor": [ /* … */ ], "placement": { "mode": "clustered", "tile": 260, "gap": 16 },
  "horizon": { "layers": [ /* … */ ] }, "life_density": 0.05 }
```

**Секция `view_primitives`:**

```jsonc
[ { "id": "wave",   "kind": "relief1d" }, { "id": "crest", "kind": "relief1d" },
  { "id": "cactus", "kind": "decor" },    { "id": "clustered", "kind": "placement" },
  { "id": "overhang", "kind": "relief2d" }, /* … 26 записей + 4 поздних 2D */ ]
```

**Ключи — ASCII** (`lambda`, не `λ`; `angleMax`, не `angle_max` — верблюжий регистр как в остальном клиенте). `λ` в документе направления — обозначение, не имя поля.

### 2.3. Правило слияния «семейство + дельта»

Сервер резолвит `view_families[family]` ⊕ `biome.view` **до** упаковки в пакет. Правило ровно из трёх пунктов:

| Тип значения | Правило | Пример |
|---|---|---|
| **скаляр** (число, булево, строка) | дельта перекрывает пресет | `life_density`, `ridge`, `snowLine`, `family` |
| **карта** (`palette`, `placement`, `horizon`, `landmark`) | слияние по ключам, дельта поверх; отсутствующий ключ берётся из пресета | «лес» меняет 3 цвета палитры, остальные наследует |
| **список** (`relief.layers`, `decor`, `hang`) | **замена целиком** (дельта задаёт список сама) | «танцующие пески» = свой список слоёв |

**Почему списки заменяются, а не склеиваются:** склейка делает результат зависящим от порядка и от того, «чей» элемент дублируется по `prim`; замена — предсказуема, проверяема и не даёт скрытых зависимостей. Цена: биом, меняющий одно число в слое, повторяет список (5–8 строк) — принято осознанно.

**Отсутствие `view` у биома** → фолбэк: сегодняшние `FORMATIONS[biome_category]` + `LIFE_DENSITY[category]` (поведение 1:1, §6 п.10). Так раскатка идёт по одной категории без «большого взрыва».

**Палитра — неполная допустима:** любой отсутствующий ключ клиент выводит из `base` существующим `shade()` (как сегодня `shade(world.color, …)`), поэтому минимальный рецепт — это `base` + пара оттенков.

### 2.4. Три развилки о природе сущности (ответы до показа)

1. **Природа:** **атрибут существующей сущности** (биом) — описание его вида. Не событие, не лог: ничего не «происходит», запись существует ровно одна на биом и меняется правкой справочника.
2. **Владелец записей:** у **одного** объекта — `BiomeDef.view` 1:1. Семейства — 1:N (9 семейств ← 57 биомов), это осознанная нормализация общей грамматики, а не отдельная сущность-жизненный-цикл.
3. **Расширяемость:** переживёт ли схема второй тип? Да: `relief.layers`/`decor`/`horizon.layers` — **открытые списки** с `prim` id; новый примитив = запись в `view_primitives` + функция в клиенте; новое семейство = запись в `view_families`, **код не меняется**. Если появится второй *класс вида* (например, вид «изнутри пещеры» с потолком и 2D-полем) — он входит секцией 2D-примитивов и/или отдельным блоком рецепта, не ломая текущую схему.

### 2.5. Политика применения к уже сгенерированным мирам

**Бэкфилл не нужен и запрещён не будет — потому что он не требуется.** Рецепт нигде не «запекается» в планету: `planets.data.biomes` хранит только `{form, share}`, а рецепт резолвится **в момент `land`** из живого справочника. Следствие: **правка рецепта действует на все миры сразу, включая давно сгенерированные, без миграции и без перегенерации.** Это самое дешёвое возможное поведение и оно же — аргумент за «рецепт в справочнике».

**Две оговорки, обе обязательные:**
- **Генерация не должна замечать рецепт.** `view`/`view_families`/`view_primitives` не участвуют в классификации биомов, недр, типов планет и **не сдвигают поток RNG генератора** (добавление полей в JSON роллов не делает; запрещено вводить в справочник поля, читаемые генератором). Иначе «золотые» миры по seed поедут.
- **Заполнение `color` у биома меняет и картинку планеты с орбиты** — `SurfaceBiomeColorHex` → `biomeColorFor` обслуживает **и** пакет прогулки, **и** изображение планеты (сущность реестра — **`planet_image`**, файл `internal/generator/planet/planet_image_v2.go`; id в `docs/impact_map.json` — именно `planet_image`, не `planet_image_v2`). Это осознанное следствие принципа «та же палитра, что у картинки планеты с орбиты» (спека прогулки §7.2), и оно **желательно** (игрок видит планету с орбиты и садится в тот же цвет). Но у картинок есть **дисковый кэш с ключом `(planet|mode|size|v4)`** — правка `color` его не инвалидирует, орбита покажет старый цвет. **Требование:** при заполнении `color`/палитры — бампнуть версию генератора картинки (`ImageGenVersion`, `v4` → `v5`), иначе расхождение «орбита ≠ прогулка». Внесено в §5 (Э1), §8, §10 п.13 и §13.

### 2.6. Доставка: аддитивное поле пакета

Пакет прогулки (`SurfacePackage`, `surface_handlers.go`) получает **три аддитивных поля** (старые не меняются, старые клиенты не ломаются):

| Поле | Тип | Смысл |
|---|---|---|
| `biome_view` | object, `omitempty` | **резолвленный** рецепт (семейство ⊕ дельта), ровно в форме §2.2. Пусто → клиент работает по фолбэку |
| `view_source` | string | `"catalog"` \| `"fallback"` — для админ-чипов, тестов и отладки |
| `view_version` | int | версия схемы рецепта (начинается с 1) — чтобы клиент умел игнорировать незнакомую версию |

**Резолв — на сервере, а не на клиенте.** Клиент не получает ни `view_families`, ни справочник: он получает готовый рецепт. Это сохраняет действующий инвариант спеки прогулки — **«пакет — единственный вход клиентского генератора; клиент не читает систему/справочник сам»** — и не создаёт второй источник правды на клиенте. Цена: пакет растёт на ~1–3 КБ JSON, один раз на высадку (не в хот-пате) — пренебрежимо.

**`FORMATIONS` и `LIFE_DENSITY` в `surface_config.js`** остаются на Э0–Э3 как фолбэк и **не удаляются**. Их удаление — отдельная мелкая уборка после Э4 (когда рецепт есть у всех 57 биомов), только по «го» создателя: это удаление кода, а не дизайн-решение.

### 2.7. Две копии справочника и заводской сид

Справочник существует **в двух копиях** (факт из кода, `biome_catalog_seed.go`):

| копия | файл | роль |
|---|---|---|
| **рабочая** | `config/biome_catalog.json` | грузится при старте (`LoadBiomeCatalog`), правится в админке, пишется `SaveBiomeCatalog` (tmp + rename) |
| **заводская (сид)** | `internal/generator/planet/biome_catalog_seed.json` | `go:embed`; store стартует с него, пока рабочая не загружена; к нему возвращает «Сбросить к заводским» (`ResetBiomeCatalogToSeed`/`SeedBiomeCatalog`) |

**Гарантия (обязательная):** новые секции `view_families`/`view_primitives` и блоки `view` у биомов — **часть справочника**, а значит обязаны присутствовать **в обеих копиях**. Рецепт — не «локальная настройка рабочего файла».

- **Правило синхронизации:** добавление/правка рецепта = правка **рабочего файла и сида в одном изменении** (как для остальных полей справочника; «один факт — одно место» — один факт, две копии одного файла, расхождение недопустимо).
- **Поведение при отсутствии рецепта — явное, не тихий фолбэк.** Отсутствие `view` у биома — легальное состояние (фолбэк вида), но оно обязано быть **видимым**: счётчик и список биомов без рецепта в диагностике вида (§2.8) + `view_source = "fallback"` в пакете. После Э4 критерий приёмки — **0 биомов без рецепта** (§10 п.12).
- **Почему это отдельный пункт:** сегодня расхождение копий уже возможно по любому полю, но для рецептов цена ошибки выше — «Сбросить к заводским» или битый рабочий файл (сервер стартует на сиде) **молча** вернули бы все 57 биомов к категорийному фолбэку, и это выглядело бы как «фича не работает», а не как ошибка данных.

### 2.8. Диагностика вида и нефатальная валидация

**Валидация вида — нефатальная** и **отдельная от `Validate()`** (факт из кода: `Validate()` фатальна — её провал в `LoadBiomeCatalog` оставляет store на сиде, а в `defaultBiomeCatalog` — `log.Fatal`; то есть ошибка рецепта уронила бы **всю генерацию планет**, что прямо противоречит §6 п.14).

Правило:

1. **Рецепт не входит в `Validate()`.** Структурная проверка каталога (биомы, недра, правила типов, `color`) — как есть, фатальна.
2. **Проверка вида — отдельный нефатальный проход** после загрузки/перестройки каталога, **два уровня строгости** (единый уровень для `palette.base` vs `color` — находка @critic М6):
   - **Ошибка** — рецепт **не применяется**, биом уходит в фолбэк вида: `family` не существует; `prim` отсутствует в `view_primitives` или его `kind` не соответствует блоку; цвет не `#RRGGBB`; диапазон `[lo,hi]` пуст или `lo > hi`; выход за бюджет вертикали (§6 п.6).
   - **Предупреждение** — рецепт **применяется**, админ видит замечание: `palette.base` ≠ `biome.color`. Источник истины — **`color`** (серверный `biome_color` не переписывается, §3.4 п.3); расхождение косметическое и **не** отправляет биом в фолбэк, иначе правка вида блокировалась бы из-за одного оттенка.
3. **Ошибка одного рецепта не роняет ничего:** биом с неверным рецептом получает **фолбэк вида** (`view_source = "fallback"`), остальные 56 работают; каталог и генерация планет не падают, сервер не падает, `LoadBiomeCatalog`/`RebuildBiomeCatalog` не возвращают ошибку из-за вида.
4. **Диагностика видима и разделена по уровню.** Две группы — `view_errors` (биом + поле + причина) и `view_warnings` (то же) — отдаются админу: в ответе GET/PATCH `/admin/biome-catalog` (поле `view_diagnostics`) и строкой в лог при загрузке. Никакого «тихо ушло в фолбэк без следа».
5. **PATCH не принимает молча неверный рецепт:** админ видит диагностику в ответе и решает (сохранить/поправить). Сохранение не блокируется — приоритет «не терять работу админа»; но факт неприменения рецепта зафиксирован.

**Требование к диагностике:** она обязана называть **биом и поле**, а не только факт ошибки (иначе автор рецепта не найдёт причину).

## 3. Единая грамматика мира

Цель — покрыть 57 биомов **переиспользуемыми кусками**, а не 57 генераторами. Проверка @gdesigner (§4 его документа) и уточнения — ниже.

### 3.1. Библиотека примитивов рельефа — 8 (ярус 1, 1D)

Все восемь — **чистые функции `(x, seed, params) → Δh`**, складываются с базой. База остаётся: `terrainHeight = baseY + offset − large(ridge·base) − detail(flatten) + Σ layers`, то есть `ridge/flatten/offset/caves/float` — **не выбрасываются**, а становятся скалярами базы (вырожденные случаи новых примитивов).

| id | что даёт силуэту | параметры | вычисления |
|---|---|---|---|
| `wave` | асимметричная волна: пологий наветренный + крутой подветренный склон — дюны, барханы, снежные гряды, валы, зыбь, кочки | `lambda, amp, skew, dir, leeMaxDeg, share, viewOnly` | **новые** (асимметрия + клэмп уклона по углу откоса) |
| `crest` | гребень/хребет: острые пики из ridged-шума | `lambda, amp, sharpness, share` | **новые** (ridged noise `1−|2n−1|`; ось `ridge` — частный случай) |
| `spike` | отдельные узкие пики/шпили/иглы/гейзерные конусы/худу | `count, h, w, taper, cluster, share` | **новые** |
| `step` | террасы/пласты/меса/соляные чаши/термальные террасы | `stepH, stepW, jitter, edge, share` | **новые** (квантование высоты) |
| `dome` | купол/всхолмление — корневые всхолмления, вулканические купола, пинго, тумули | `lambda, amp, squash, share` | **новые** |
| `carve` | вырез: каньон/русло/трещина/воронка/кратер | `lambda, depth, w, rim, shape(V/U), closed, share` | **новые** (вычитание + борт) |
| `fan` | осыпь/конус с пределом угла — щебень, курумы, лавовые конусы, конусы выноса | `angleMax, h, w, roughness, share` | **новые** (клэмп уклона ≤ угла откоса) |
| `flow` | язык потока (лава/грязь/лёд/сель) | `len, w, lobes, levees, slope, share` | **новые** |

**Семантика общих параметров слоя** (обязательно к фиксации, иначе числа нечитаемы):
- `amp` — **полуразмах** в px (отклонение от среднего), не полная амплитуда;
- `share` — доля регионов (0–1), в которых слой включён; детерминированно от `seed` и индекса региона; дефолт 1.0;
- `viewOnly: true` — слой входит **только в отрисовку** (`viewHeight`), физика (`terrainHeight`/`isSolid`) его не знает. Так работает рябь и любая «мелочь для глаза»;
- `dir` — направление асимметрии (`+1` = пологий склон слева, срыв справа).

**Уточнение к @gdesigner (обязательное):** в §3.1 его рецептов фигурируют `dune` и `ripple`, а в §4.1 библиотеки — `wave`. Это **три имени одной сущности**. Фиксируется одно: **`wave`** (асимметричная волна), а «бархан» и «рябь» — её параметризации (`amp/λ ≈ 0.09`, `skew ≈ 0.85` — бархан; `λ 22–44, amp 1.5–3, viewOnly` — рябь). Иначе два рецепта, написанные разными людьми, разъедутся по имени примитива.

### 3.3. Правила размещения — 3 режима + находки

| режим | смысл |
|---|---|
| `uniform` | как сегодня — по мировой колонке (для разреженного декора пустошей) |
| `clustered` | рощи/кучки: грубый тайл `tile` px, внутри — сгусток, между сгустками — `gap` px пусто (чинит «частокол» А6) |
| `line` | вдоль русла/берега/трещины (`follow` — по `carve`-слою или по уровню) |

`landmark` — **редкая находка** (уже есть механизм `rareDecorAt`, период 6000 px): расширяется до per-biome `landmark.prim` + `perRegion`. Кандидат в ГД-сущности — §12.

### 3.4. Палитра

**Обязательный минимум:** `base`. **Рабочий набор:** `base` (земля), `dark` (тень/подветренный склон), `light` (освещённая грань/гребень), `accent` (линии ряби, прожилки). **Спец-ключи по семейству:** `rock`, `trunk`, `moss`, `haze` (влажная дымка, α), `snow`, `snowShade`, `ice`, `strataA`/`strataB` (пласты), `glow`, `ember`.

**Правила:** (1) отсутствующий ключ выводится из `base` через `shade()` — минимальный рецепт валиден; (2) `biome_color` остаётся **серверным** и **не пересчитывается** палитрой (инвариант спеки погоды §5.1 п.4); (3) палитра — **расширение** цвета, а не второй источник: `palette.base` и `biome.color` — **одно и то же значение**, источник истины — `color`. Если оба заданы и различаются — это **предупреждение** админу (`view_warnings`, §2.8 п.2), **не ошибка**: рецепт применяется, биом в фолбэк не уходит. Единый уровень строгости зафиксирован в §2.8 п.2 (ревизия 2, находка @critic М6).

### 3.6. Ярусный горизонт (направление C)

**Закрывает находку М4:** блок `horizon` в схеме §2.2 больше не «висячий» — ниже его поля и правило силуэта.

**Что это.** 2 промежуточных пояса параллакса между дальним силуэтом (`farRelief`, 0.35 — **не трогается**) и основным рельефом. Ярусы **декоративны**: игрок по ним не ходит, физика их не знает — «невидимых стен» по построению быть не может (§6 п.3, п.4, п.8). Решение создателя 2026-09-23: **2 пояса**.

**Поля:**

| поле | смысл |
|---|---|
| `layers[]` | список поясов, **не более 2** (потолок 3 — только отдельным решением) |
| `layers[].parallax` | множитель сдвига от камеры: **меньше — дальше**; рекомендовано **0.50** (**дальний** ярус) и **0.70** (**ближний**, рисуется поверх); обязан быть между `farRelief` (0.35) и миром (1.0) |
| `layers[].profile` | `{ prim, …params }` — силуэт пояса; **`prim` обязан иметь `kind = "relief1d"`** (§2.1) и оценивается на низкой частоте (крупные `lambda`, большие `amp`), без мелкой детализации |
| `layers[].fill` | цвет заливки силуэта — берётся из палитры биома (`dark`/`base`), не литералом |
| `layers[].haze` | доля дымки пояса (0–1): `0` — ярус читается отдельным слоем, `1` — растворяется в воздухе |
| `layers[].step` | шаг мировой решётки выборки (px), по умолчанию `FAR_STEP = 24`: силуэт считается на фиксированной решётке и «уезжает цельно», а не перерисовывается покадрово |

**Правила:**
1. **Силуэт — из библиотеки §3.1, не из отдельного набора.** «Пустыня — три гряды дюн» = пояса `wave` с разными `lambda`/`amp`/`haze`; «лес — линии крон» = `dome`; «горы — планы хребтов» = `crest`/`spike`. Новых примитивов не требуется, отдельного `kind` нет (§2.1).
2. **Палитра яруса — из палитры биома** (`dark`/`base`/`haze`), иначе горизонт не сменит цвет вместе с биомом.
3. **Дымка согласована со слоем суток** (`surface_environment`, `lightMul`): ярус темнеет вместе с миром; ночью светлее неба быть не должно (§8).
4. **Порядок отрисовки** — сразу после `drawFarRelief`, до `drawEnvironmentMid` (§6 п.1).
5. **Бюджет:** 2 пояса × (ширина мира / `FAR_STEP`) точек — при `FAR_STEP = 24` и ширине 1920 px это ~80 точек на ярус, ~160 на два; в кап §6 п.8 не упирается.

### 3.7. Что в грамматику не входит

- **Жидкость** (уровень, зеркало, плавание) — ЧК6.
- **Погода/сутки** — уже сделаны (`surface_weather`, `surface_environment`), не трогаются, кроме взаимодействия с ярусами (§6 п.8).
- **Животные** (`creaturesFor`) — вне ЧК0; правило плотности наследуют от `life_density` рецепта (аддитивно, отдельным шагом Э4).
- **Физика игрока** — не входит нигде.

## 4. Рецепты трёх образцов — сверенные с наукой §11

Образцы: **пески пустыни**, **джунгли** (+ «лес» как дельта того же семейства — решение создателя «и джунгли, и лес»), **горы**. Числа @gdesigner — **гипотеза**, ниже — сверка и правки.

### 4.1. Пески пустыни (`пески_пустыни`, литосфера)

**Форма.** `ridge 0.20, flatten 0.35, offset −10, caves 0.05, float false, base 1.0`.

| слой | параметры | что даёт |
|---|---|---|
| `wave` | `lambda [320,640], amp [26,64], skew 0.85, dir +1, leeMaxDeg 34, share 1.0` | крупные барханы |
| `wave` | `lambda [90,180], amp [6,14], skew 0.80, share 0.5` | вторичные гряды |
| `wave` | `lambda [22,44], amp [1.5,3], viewOnly true, share 1.0` | рябь — **только вид** |

**Сверка с §11 — здесь правка @gdesigner.** Наука: наветренный склон **5–15°**, подветренный — **обрыв по углу откоса 32–34°**, `высота/шаг ≈ 1/10–1/15`. При `skew` = доле длины волны на пологом склоне:

| величина | @gdesigner (`skew 0.68`, `amp/λ≈0.09`) | правка (`skew 0.85`) | наука |
|---|---|---|---|
| наветренный | `atan(0.09/0.68) ≈ 7.5°` ✓ | `atan(0.09/0.85) ≈ 6.1°` ✓ | 5–15° |
| подветренный | `atan(0.09/0.32) ≈ 15.7°` ✗ | `atan(0.09/0.15) ≈ 31°` ✓ | 32–34° |
| `amp/λ` | 0.09 ✓ | 0.09 ✓ | 1/10–1/15 |

**Вывод:** `amp/λ ≈ 0.09` уже верна, а `skew 0.68` даёт подветренный склон **вдвое положе** науки (15.7° против 33°). **Решение создателя 2026-09-23 (утверждено, не открытый вопрос):** `skew` = **0.85** **и** вводится `leeMaxDeg: 34` — жёсткий клэмп уклона по углу естественного откоса: выше него гребень «срезается» (это и есть модель лавинного срыва, а не просто крутая линия). Так форма **физически не может** стать круче, чем держит песок. Статус согласован с §11 (решение №3).

**Палитра:** `base #cfa96a` (палевый кварц + оксиды железа), `dark #9e7c45` (подветренный склон), `light #ecd6a4` (гребень на солнце), `accent #b8925a` (рябь), `rock #7d6b57` (ветрогранник). Сверка §11: кварц палевый / оксиды железа красные / гипс белый — взята **палево-тёплая** база (смешанный состав), осознанно, не белая и не красная.

**Декор:** `cactus p 0.020 h[20,52]`, `bush p 0.030 h[6,14]`, `rock p 0.010 h[6,20]`, `bone kind skeleton p 0.004 h[8,16]`. **Ни одного дерева** (чинит А5). Сверка §11: «растительность только на закреплённых дюнах и у воды» → плотность 0.05 и `placement clustered` (кучки, а не ровный ковёр).

**`placement`:** `clustered tile 260 gap 16`. **`landmark`:** `oasis_dry perRegion 6000` (сухая котловина — вода ЧК6). **`life_density`:** 0.05.

### 4.2. Джунгли (`джунгли`, биосфера) и лес

**Форма.** `ridge 0.55, flatten 0.45, offset 0, caves 0.35, float false`.

| слой | параметры | что даёт |
|---|---|---|
| `dome` | `lambda [180,340], amp [26,60], squash 1.6, share 1.0` | холмы под пологом |
| `carve` | `lambda [500,900], depth [40,90], w [120,220], rim 0.25, shape U, share 0.7` | прорезанное русло с подмытыми берегами |

**Сверка с §11 — вторая правка.** Наука: уклоны под пологом **10–30°**. Средний уклон `dome` ≈ `atan(2·amp/λ)`:

| | @gdesigner `amp [10,22]` | правка `amp [26,60]` | наука |
|---|---|---|---|
| уклон | `atan(2·10/180) ≈ 6.3°` … `atan(2·22/340) ≈ 7.4°` ✗ | `atan(2·26/180) ≈ 16.1°` … `atan(2·60/340) ≈ 19.4°` ✓ | 10–30° |

**Вывод:** амплитуда холмов занижена в **~2.5 раза** — джунгли получались почти плоскими. Правится `amp → [26,60]`. `rim 0.25` на `carve` — это и есть «подмытые берега-обрывчики» §11 ✓.

**Палитра:** `base #41382a` (почва), `dark #1c4322` (глубина кроны), `light #2c6330` (середина), `accent #86bd5f` (подсвеченные листья), `trunk #463726`, `moss #37602b`, `haze #8fae86` (α 0.15). Сверка §11: света до земли 1–5%, поэтому стволы голые, а зелень — в кроне ✓ (рецепт даёт три яруса, а не «стену зелени»).

**Декор:** `tree p 0.090 h[70,160] crown[2,3] buttress true species broadleaf`, `palm p 0.030 h[60,130] fronds[6,9]`, `fern p 0.160 h[12,30]`, `bush p 0.120 h[8,22]`, `lichen p 0.040 w[6,18]`. `hang`: `liana from tree p 0.35 len[20,70]`.

**Сверка §11 (контрфорсы):** наука — корни-подпорки 1–3 м при дереве 25–45 м, то есть **3–10 % высоты дерева**, вынос в 2–2.5 раза больше высоты. В рецепте `buttress` — **вынос 0.30·h** (при `h` 100 px — 30 px): это **преувеличение в ~4 раза ради читаемости** (при 3–10 % контрфорс был бы 3–10 px и не читался как признак джунглей). Отклонение **осознанное и названное**; толщина — `0.10·вынос`.

**`placement`:** `clustered tile 220 gap 14`. **`life_density`:** 0.62 (доля **кластерных** колонок — чинит А6).

**Лес = дельта того же семейства** (решение создателя «и джунгли, и лес»): `life_density 0.40`, `tree h[50,110] crown 2`, `fern p 0.08`, `hang` — пусто, `dome amp [18,40]`, палитра `dark #1e3a1e / light #3a6b33 / accent #9fcf6a`, `haze` α 0.08 (суше), `placement clustered tile 300 gap 26` (светлее и просторнее). Код не меняется — только данные.

### 4.3. Горы (`горы`, литосфера, высоты)

**Форма.** `ridge 1.80, flatten 0.15, offset −180, caves 0.55, float true, base 1.0, scale 0.55`.

| слой | параметры | что даёт |
|---|---|---|
| `crest` | `lambda [420,900], amp [90,220], sharpness 0.75, share 1.0` | гребни/хребты |
| `spike` | `perRegion [1,3], h [120,260], w [30,70], taper 0.25` | шпили, обрывы |
| `step` | `stepH [40,90], stepW [140,320], jitter 0.30` | пласты-уступы |
| `fan` | `angleMax 34, h [40,110], roughness 0.2` | конусы осыпей |

**Сверка с §11.** Уклон `crest` от впадины к пику `≈ atan(2·amp/λ)`: `atan(2·90/420) ≈ 23°` … `atan(2·220/900) ≈ 26°` — **ниже** науки «30–45° норма». Ступень добирается `sharpness 0.75` (заостряет пики локально) и `spike` (обрывы **>60°** — §11 «круче 60° — обрывы» ✓). `fan angleMax 34` — прямо из §11 «осыпи по углу откоса щебня 30–35°» ✓. `step` — §11 «скалы выходят пластами-уступами по напластованию» ✓.

**`relief.scale 0.55` — не косметика, а требование бюджета (§6 п.6).** Сумма заявленных амплитуд (base ≈ 205 + detail ≈ 35 + crest 220 + spike 260 + step 90 + fan 110 ≈ **920 px** вверх) не помещается в запас вертикали чанка; без масштабирования высокие участки окажутся **выше верха растра** — то есть твёрдая, но **невидимая** земля (ровно класс бага «невидимые камни», `cf76e06`). `scale 0.55` приводит худший случай в бюджет. **Точная граница — за тестом T-budget (§10 п.7), а не за арифметикой на глаз.**

**Снеговая линия.** `snowLine: 140` (px ниже местного максимума профиля), `snowLineShadow: 0.85` (на теневой стороне линия ниже на 15 % — §11: «южный склон поднимает снег на 300–800 м»).

**Сверка §11 — расхождение названо.** Наука: снеговая линия — **климат, не высота** (экватор 5000–5500 м, средние широты 2500–3500 м). В прогулке **абсолютной шкалы высот нет**: `PPM = 40` объявлен «визуальным масштабом, не физическим», рельеф колеблется в ±230 px ≈ ±5.75 м. Абсолютная линия физически непредставима. Поэтому принята **локальная относительная** линия (от местного максимума) — это **отклонение от эталона, внесённое осознанно**, и оно вынесено в вопрос создателю (§11 вопрос 1) и в FAQ (§9).

**Палитра:** `base #726c64` (серый гранит), `dark #4b4741`, `light #948d82`, `strataA #7d7263` / `strataB #5d564c` (пласты), `snow #eef3f7`, `snowShade #b3c6d6` (синева в тенях — §11 ✓), `ice #a9c6dc`, `haze #8ba0b6`. Сверка §11: серый гранит/светлый известняк/тёплый песчаник/тёмный базальт — взята **серая** база (гранит) с пластами; тёплый песчаник — дельта для `венерианских_плоскогорий`.

**Декор:** `conifer p 0.040 h[40,90] where maxAlt 260` (только нижние склоны), `lichen p 0.050 w[6,22]`, `rock p 0.040 h[8,26]`, `crystal p 0.002 h[10,24]` (жилы, редко). **`life_density`:** 0.06.

### 4.4. Сводка сверки с @scientist (§11): что совпало, что отклонено

| Факт §11 | В рецепте | Вердикт |
|---|---|---|
| дюны: наветренный 5–15°, подветренный 32–34° | `skew 0.85` + `leeMaxDeg 34` → 6.3° / 31–33.7° | ✅ **совпало после правки** (было 7.5°/15.7° ✗) |
| дюны: высота гряд ≈ 1/10–1/15 шага | `amp/λ ≈ 0.09` | ✅ совпало |
| дюны: лавинные язычки на срыве | `leeMaxDeg` (срез гребня) + `accent` на подветренном | ✅ форма; язычки — деталь отрисовки |
| дюны: небка/шлейф у препятствий | не в ЧК0 | ⏳ кандидат (Э4, требует локальной привязки к декору) |
| осыпи: угол откоса щебня 30–35° | `fan angleMax 34` | ✅ совпало |
| горы: склон 30–45°, круче 60° — обрывы | `crest` 23–26° + `sharpness` + `spike` >60° | ⚠️ **частично**: базовый гребень положе науки; ступень добирается заострением и шпилями — принято |
| горы: пласты-уступы | `step` | ✅ совпало |
| горы: снег белый с синевой в тенях | `snow #eef3f7` / `snowShade #b3c6d6` | ✅ совпало |
| горы: снеговая линия — климат/абсолютная высота | `snowLine` — **локальная** от максимума | ❌ **отклонено осознанно**: абсолютной шкалы в прогулке нет (§4.3) |
| джунгли: уклоны 10–30° | `dome amp [26,60]` → 16–19° | ✅ **совпало после правки** (было 6.3–7.4° ✗) |
| джунгли: русла с подмытыми берегами | `carve rim 0.25` | ✅ совпало |
| джунгли: ярусность 45–60 / 25–45 / 5–20 м | `tree h[70,160]` + `crown` + `fern`/`bush` (три яруса) | ⚠️ **масштаб не сохранён** (см. ниже), структура — да |
| джунгли: корни-подпорки 1–3 м / вынос 2–5 м | `buttress` вынос `0.30·h` | ❌ **преувеличено ~4×** осознанно (читаемость) |
| джунгли: света 1–5 %, пятнами | три яруса + голые стволы + `haze` | ✅ совпало |
| «снеговая линия — да» (создатель) | `snowLine 140` | ✅ принято |

**Общее расхождение, названное явно: масштаб прогулки не физический.** `PPM = 40` — визуальный масштаб; рельеф ±230 px ≈ ±5.75 м, дерево 160 px ≈ 4 м, тогда как в жизни гора 2000 м, дерево 30 м. Сжатие **неравномерное** (гора ~350×, дерево ~7×). Поэтому из §11 берутся **отношения и углы внутри одной формы** (дюна 1:10–1:15, откос 30–35°, пропорции контрфорса), а **абсолютные высоты/метры — нет**. Это не дефект, а свойство стилизованного вида сбоку; зафиксировано, чтобы числа §11 не «применялись дважды» (сначала как метры, потом как px).

## 5. План этапов

Подход не выбирается — берутся **все четыре** направления @gdesigner (A профили, B объём, C ярусы, D цвет/жизнь), от дешёвого к дорогому, **ничего не выбрасывается** (решение создателя).

| Этап | Что | Видимый результат | Цена | Риск |
|---|---|---|---|---|
| **Э0** | **Данные и резолвер.** Секции `view_families`/`view_primitives` **в обеих копиях справочника** (§2.7 — рабочий файл + заводской сид), поле `BiomeDef.view`, **нефатальная валидация вида + диагностика** (§2.8), серверный резолв, поля пакета `biome_view`/`view_source`/`view_version`, **GET/PATCH переносят новые секции** (§7), клиент читает рецепт с фолбэком на `FORMATIONS`. Рецептов биомов нет | **Нет** (поведение 1:1). Это фундамент: без него Э1–Э3 некуда писать | малая (данные + Go-резолв + ~30 строк JS) | очень низкий |
| **Э1** | **Цвет и жизнь** (направление D). Заполняется `color` у 3 образцов **+ бамп версии картинки планеты `ImageGenVersion` `v4` → `v5`** (§2.5, §10 п.13), палитра, библиотека декора (15), правила `clustered`/`line`, `life_density` по биому | «Пески — песочные, джунгли — зелёные, горы — серые»; декор узнаваем (кактус, лиана, хвоя), **кучки с зазорами** вместо частокола; в пустыне **нет деревьев**; орбита и прогулка одного цвета | низкая (декор ~200–300 строк + размещение ~50–80 + один бамп константы) | низкий |
| **Э2** | **Ярусный горизонт** (C, §3.6). 2 пояса (параллакс 0.50/0.70) с силуэтом из **профильных** примитивов `relief1d` (отдельного `kind` нет — §2.1), палитрой и дымкой; существующий `farRelief` (0.35) **не трогается** | Глубина сцены: пустыня — гряды дюн в дымке, лес — линии крон, горы — планы хребтов | низкая (~100–150 строк, переиспользует `farReliefProfile`/`FAR_STEP`) | очень низкий (ярусы декоративны — «невидимых стен» не бывает по построению) |
| **Э3** | **Словарь профилей** (A). 8 примитивов, `terrainHeight` → стек слоёв, рецепты формы 3 образцов, `leeMaxDeg`, `fan`, снеговая линия, `viewOnly`-слой ряби | **Силуэт**: «дюны ≠ гребни»; асимметричные дюны со срывом, ступени-пласты, конусы осыпей, снеговые шапки | средняя (~150–250 строк профилей + переработка `terrainHeight`/растеризатора) | низкий (`isSolid`/растр уже вызывают `terrainHeight`; **бюджет вертикали** — §6 п.6) |
| **Гейт** | **«Офигеть»** на 3 образцах (создатель). Возможен уже после Э2 — решает создатель | | | |
| **Э4** | **Раскатка:** ЧК1 литосфера (12) → ЧК2 биосфера (13) → ЧК3 вулканизм (7) → ЧК4 крио (5) → ЧК5 экзотика (10). Заполняются 9 семейств + дельты, каждая категория — свой гейт | Каждый биом читается своим силуэтом, палитрой и жизнью | средняя на категорию (данные + редкие новые примитивы) | низкий |
| **Э5** | **Скульптурный объём** (B). 2D-поле твёрдости: `overhang`, `void`, `crack2d`; арки, нависания, гроты, грибные башни, `пещерный_мир_с_потолком` | Настоящий объём, а не силуэт | **высокая** (структурная переработка `terrainHeight`/`isSolid`/растеризатора; сэмплы ×`CHUNK_HEIGHT`; агрессивные кэши, вероятно снижение `SS`) | **высокий** — «невидимые стены», если растр и физика разойдутся (класс бага `2026-09-21` §2.1) |

**Матрица «слой × чекпоинт»** — этапы Э0–Э3 применяются к трём образцам (ЧК0); Э4 разворачивает **все слои** по категориям; Э5 — после ЧК5.

**Семейства не совпадают с категориями — правило раскатки (находка @critic М8).** Раскатка Э4 идёт по **6 категориям**, а семейств **9** — значит одно семейство «дозревает» на нескольких ЧК (пример: **лесные/чащи** — 11 биомов в биосфере (ЧК2) + 4 в экзотике (ЧК5) + 1 дельта в литосфере; **травяные** — луга/степь в литосфере (ЧК1) + тундры в крио (ЧК4) + пружинная тундра в экзотике (ЧК5); **водные/берег** — вода (ЧК6) + коралловые рифы в биосфере (ЧК2); **скальные пустоши** — 6 в литосфере (ЧК1) + щетинные поля в экзотике (ЧК5)). Правило, чтобы дельты не потерялись и уже сданное не поехало:

1. **Пресет семейства вводится один раз** — на первом ЧК, где появляется его первый биом, и **дальше не переписывается**.
2. **Последующие ЧК только добавляют дельты** своих биомов (`BiomeDef.view`), не трогая `view_families`.
3. **Правка уже введённого пресета** — это изменение вида **уже сданных** биомов → отдельный гейт (не «побочный эффект раскатки»).
4. **В спеке раскатки каждого ЧК** — таблица «пресеты: не трогаем» + список дельт этого ЧК, чтобы при переносе данных не потерять дельту биома из другой категории.
5. **Проверка:** после каждого ЧК `view_diagnostics` не даёт новых ошибок, а биомы предыдущих ЧК **не меняют вид** (сравнение замороженного кадра до/после).

**Почему такой порядок (и альтернатива).** Порядок Э1→Э2→Э3 — от самого дешёвого видимого результата к самому дорогому, ровно как «от дешёвого к дорогому» у создателя. **Альтернатива:** Э2 (горизонт) первым — он ещё дешевле Э1 и не требует библиотеки декора; **цена альтернативы:** горизонт без правильного цвета земли даёт «красивую раму для грязной картины» (А4 не починен), поэтому Э1 раньше. **Вторая альтернатива:** Э3 первым — **отвергнута**: силуэт без палитры и декора всё равно даёт «пески и горы близнецами по цвету» (А4), а риск бюджета вертикали проверяется лучше, когда виден результат Э1/Э2.

**Общая цена (JS, клиент):** примитивы рельефа ~150–250 строк, горизонт ~100–150, декор ~200–300, размещение ~50–80, чтение рецепта ~30–60. **Данные рецептов 57 биомов — 0 строк JS** (справочник + пакет).

## 6. Границы и инварианты

1. **Порядок кадра не меняется.** `drawSky → drawEnvironmentBack → drawWeatherBack → drawFarRelief → [новые ярусы] → drawEnvironmentMid → drawWeatherMid → drawTerrain → drawDecor → drawShip → drawCreatures → drawPlayer → drawWeatherFront → drawEnvironmentFront → drawEmissive`. Ярусы вставляются **между `drawFarRelief` и `drawEnvironmentMid`**; порядок прочих не трогается.
2. **Один трансформ.** Мир рисуется под единым `DPR`+`ZOOM = 1.8`; повторного масштаба нет; ярусы — в тех же мировых/экранных координатах.
3. **Физика игрока не меняется.** `PPM = 40`, `WALK_SPEED/SPRINT_SPEED/JUMP_SPEED`, клип гравитации 0.2–2.5, `w = 12`, `h = 28`, спавн на корке. Меняется **форма земли**, а не законы движения. `viewOnly`-слои и все ярусы/декор — **вне** `terrainHeight`/`isSolid`.
4. **«Что твёрдо — то видно».** Растр чанка — **надмножество** твёрдой области; «невидимых стен» быть не должно.
5. **Полоса `float`.** `FLOAT_GAP = 48 > h = 28`; `FLOAT_SPAN`/`FLOAT_GAP` не уменьшать. Под парящей породой всегда проход.
6. **Бюджет вертикали (новый инвариант, обязательный).** Сумма новых слоёв **не должна выводить профиль за растр чанка**: для всех `x` выполняется `terrainHeight(x) − FLOAT_SPAN ≥ baseY − CHUNK_TOP_MARGIN + 24` и `terrainHeight(x) ≤ baseY + CHUNK_HEIGHT − 24`. Иначе земля твёрдая, но не нарисована (игрок идёт по воздуху). Инструменты: `relief.base`/`relief.scale` рецепта; при систематической нехватке — рост `CHUNK_TOP_MARGIN` (цена: память чанка растёт как `CHUNK_HEIGHT·(CHUNK+1)·SS²`) или **динамический `topY` по чанку** (структурно, кандидат в Э5). Проверка — тест T-budget (§10 п.7), не арифметика на глаз.
7. **Детерминизм.** Только `hash1`/`hash2`/`mulberry32`. `Math.random` запрещён — иначе мир пересобирается при повторном входе. Разворот диапазонов `[lo,hi]` — детерминированно от `seed` (как в погоде).
8. **Чанк-кэш и бюджет отрисовки.** `CHUNK = 256`, `CHUNK_HEIGHT = 1700`, `CHUNK_TOP_MARGIN = 700`, `SS ≤ 2`; никаких `shadowBlur`; никаких покадровых градиентов на сотни элементов; ориентир — **кап ~600 отрисовок/кадр** (текущая метель ≈ 350). Декор — с LOD: при превышении капа мелкие примитивы (`grass`, `lichen`, `bush`) отбрасываются в порядке возрастания размера. Ярусы — **2 пояса** (решение создателя 2026-09-23; потолок 3 — только по отдельному решению), сверх существующего `farRelief`. Рецепт — константа мира: **ключ чанк-кэша не меняется**.
9. **Декор не твёрдый и не перекрывает игрока.** Крона/лианы — выше роста игрока (28 px); декор рисуется за игроком; плотность — по правилу размещения, не «каждый пиксель».
10. **Рецепт — данные, а не второй реестр в JS.** `FORMATIONS`/`LIFE_DENSITY` — **фолбэк** до Э4; источник правды — справочник. Удаление константы — отдельная уборка по «го».
11. **`biome_color` — серверный.** Палитра — расширение, не пересчёт; повторный сдвиг по `liquid_medium`/температуре запрещён (сделан сервером).
12. **Вода не вводится раньше ЧК6.** Оазисы/русла в образцах — сухие.
13. **Контракты не переименовываются.** `biome`, `biome_category`, `biome_color`, id явлений погоды — как есть.
14. **Рецепт не влияет на генерацию.** `view`-поля не читаются генератором и не сдвигают RNG; классификация биомов/недр/типов планет не меняется.
15. **Выход за канвас.** Декор/крона не обрезаются краем чанка/экрана (запас по краям, как `margin = 8` в `visibleDecor`).

## 7. Админка и правка данных

- **Источник правды — `config/biome_catalog.json`**, правится в админке (вкладка «Основное», подразделы «Биомы»/…), PATCH `/admin/biome-catalog`, hot-reload store, атомарная запись — как сегодня. **Проверка вида — нефатальная, отдельная от `Validate()`, два уровня строгости (§2.8 п.2):** *ошибки* (рецепт не применяется → фолбэк биома) — `family` не существует; `prim` отсутствует в `view_primitives` или `kind` не соответствует блоку; цвет не `#RRGGBB`; `[lo,hi]` пусты или `lo > hi`; выход за бюджет вертикали (§6 п.6). *Предупреждения* (рецепт применяется) — `palette.base` ≠ `biome.color`, источник истины `color`.
- **ПОЛНАЯ ЗАМЕНА — главная ловушка (находка @critic С3).** `PATCH /admin/biome-catalog` — **полная замена** справочника (`json.Unmarshal` в `BiomeCatalog` → `SaveBiomeCatalog`), а GET-ответ (`biomeCatalogResponse`) сегодня отдаёт только `biomes`/`subterrain_types`/`planet_types`/`fallback_type`/`params`. **Требование:** GET и PATCH обязаны **нести и переносить** `view_families` и `view_primitives`; **любое сохранение из админки не теряет их**. Иначе правка одного цвета биома (а это ровно Э1) затрёт всю грамматику вида — и это будет выглядеть как «рецепты пропали сами».
- **Админ-UI (`web/static/js/admin/biomeCatalog.js`) — часть требования, а не «UI потом».** Редактор правит только известные подразделы; состояние и сохранение обязаны **сохранять незнакомые секции как есть** (переносить без потерь). Проверка — в критериях приёмки (§10 п.14): после сохранения из админки `view_families`/`view_primitives` на месте, побайтово эквивалентны.
- **Сид синхронизируется (находка @critic С2, §2.7).** Рецепты трёх образцов и новые секции обязаны быть **и в рабочем файле, и в `biome_catalog_seed.json`**: «Сбросить к заводским» и старт на сиде не должны обнулять вид в фолбэк. Расхождение копий = дефект данных.
- **На ЧК0** достаточно ручной правки JSON (правится в админке как обычный справочник) — **отдельный редактор вида не обязателен** (решение создателя 2026-09-23: редактор — позже).
- **Подраздел «Вид биомов» — позже, не на ЧК0** (решение создателя 2026-09-23): по образцу существующих подразделов (`biomes`/`subterrain`/`planetTypes`/`bands`/`compat`/`params`) — выбор биома → выбор `family` → 5–8 полей дельты. **UI-работа**: по правилу ролей — @uidesigner **после** @designer, **до** @developer, когда создатель скажет.
- **Превью:** правка рецепта видна при следующей высадке (рецепт читается в момент `land`, §2.5) — перегенерация миров не нужна.

## 10. Критерии приёмки ЧК0

**Замороженный кадр, биом выбран админ-чипом:**
1. **Пески пустыни** — асимметричные дюны (пологий наветренный ~6°, крутой подветренный ~31–33° с видимым срывом), светлые гребни, тёмные срывы; **ни одного дерева**; тёплый песочный `#cfa96a`; рябь видна, но **не твёрдая**.
2. **Джунгли** — три яруса (папоротники → стволы с контрфорсами и лианами → сомкнутые кроны), влажная дымка, русло с подмытыми берегами; плотность — рощами, а не частоколом; **лес** — то же семейство, светлее и просторнее.
3. **Горы** — гребни + шпили + ступени-пласты + конусы осыпей; **снеговые шапки** выше локальной снеговой линии; серый камень `#726c64`, синева в тенях снега.

**Проверка «было → стало»:**
4. Пески и горы рядом **больше не близнецы** — ни силуэтом, ни цветом (было `#968672` против `#91816f`).
5. Горизонт перестал быть одной тёмной полосой: дальний план биом-специфичен (ярусы).

**Регрессия, перф, данные:**
6. **Детерминизм:** тот же `seed` → тот же кадр (сравнение двух прогонов).
7. **T-budget (§6 п.6):** для каждого биома с рецептом на `x ∈ [0, 20·region]` выполняется `min(terrainHeight) − FLOAT_SPAN ≥ baseY − CHUNK_TOP_MARGIN + 24` и `max(terrainHeight) ≤ baseY + CHUNK_HEIGHT − 24`.
8. **Игрок проходит все три образца:** нет невидимых стен, нет застреваний, декор не блокирует.
9. **Бюджет кадра** в норме (§6 п.8); `tools/e2e/surface-walk-check.js` и `surface-admin-biome-check.js` — зелёные, 0 pageerror.
10. **Пакет:** `biome_view` присутствует при `view_source = "catalog"`, отсутствует при `"fallback"`; старые поля пакета не изменились; **старый мир** (сгенерированный до правки) получает новый рецепт **без перегенерации**.
11. **Генерация не сдвинулась:** набор биомов и «золотые» миры по seed воспроизводятся после добавления `view`-полей в справочник.

**Данные и админка (внесено порцией 1):**
12. **Покрытие семействами = 57/57** (§3.5): ни один `id` справочника не остаётся без семейства; после Э4 `view_diagnostics` даёт **0 биомов без рецепта** (`view_source = "fallback"` не встречается на трёх образцах ЧК0).
13. **Бамп версии картинки планеты** (§2.5): в Э1 `ImageGenVersion` переведён `v4` → `v5`; изображение планеты с орбиты после заполнения `color` **совпадает по цвету** с землёй прогулки (нет «орбита старая, прогулка новая»).
14. **Сохранение из админки не теряет вид** (§7): после PATCH `/admin/biome-catalog` (в т.ч. при правке одного `color` биома) секции `view_families`/`view_primitives` и блоки `view` на месте, **побайтово эквивалентны**; GET-ответ их несёт.
15. **Обе копии справочника** (§2.7): `view`-секции есть и в рабочем файле, и в `biome_catalog_seed.json`; «Сбросить к заводским» и старт на сиде **не переводят вид в фолбэк** (проверка: рецепт трёх образцов резолвится после сброса).
16. **Валидация вида нефатальна** (§2.8): каталог с намеренно битым рецептом одного биома **загружается** (генерация планет жива), битый биом уходит в фолбэк, диагностика называет биом и поле; сервер не падает.
17. **Тест синхронизации сида (§2.7) — механическая гарантия вместо дисциплины.** Автотест сравнивает `view`-часть **заводского сида и рабочего файла** (`view_families`, `view_primitives` и блоки `view` по каждому `id` биома) и **падает на расхождении**; допустимая альтернатива — гвард в `ResetBiomeCatalogToSeed`/`LoadBiomeCatalog` (расхождение → лог + `view_warnings`, не тишина). Цель — расхождение двух копий ловится, а не живёт тихо (§2.7, находка порции 2).

## 12. Кандидат ГД-сущности: «примета биома»

*Кандидат на решение создателя. Не факт, в текущие числа не входит (анти-двойной учёт).*
