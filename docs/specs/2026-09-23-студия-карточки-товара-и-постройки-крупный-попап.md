### 3.3 Canvas-текст (дерево построек и граф товаров) — поднимаем

**Сейчас:** имя `12px`, подпись/«производит» `10px` (873/876, 911/914, 2958/2960,
2972/2975, 2994/2997, 3018). 10 px на карточке 190×86 — мелко, это и есть «где мелко».

**Решение: поднимаем, `CARD_W`/`CARD_H` НЕ меняем.** Проверка по коду: карточка
`190×86`; в графе товаров содержимое занимает только `y+18…y+56` (низ до `y+86` пуст),
в дереве есть строка «производит» на `y+68` — вертикальный запас есть. Значит рост
кегля вписывается без перекомпоновки (координаты, `ROW_GAP`, панорамирование, зум
`computeLayout`/`prodTreeLayout`/`fit` — не трогаем).

|---|---|---|
| имя узла (граф 873, дерево 2994, заглушка 2972, плейсхолдер/создать 911/2958) | `12px` | **14px** |
| подпись/категория/тип (876, 914, 2975, 2997, 2960) | `10px` | **12px** |
| «производит» (3018) | `10px` | **11px** |
| текст бейджа (тир/скрыта/др. фабрика) | `10px` | **11px** |

**Цена (низкая, но обязательны две оговорки):**
1. **Ужать `trunc`.** При большем кегле те же лимиты начнут вылезать за 190 px:
   имя `trunc(name, 26)` при 14 px ≈ 26×7 = 182 px > доступных 174 px → **снизить до 24**;
   «производит» `trunc(produces, 34)` при 11 px ≈ 187 px → **снизить до 28**; подпись
   категории сейчас **без** `trunc` — добавить `trunc(catName(...), 22)`, иначе длинная
   категория нарисуется за границей карточки.
2. **Бейджи.** Текст бейджа 11 px в рамке высотой 16 px — тесно; поднять высоту бейджа
   до **18 px** (строка `y+40`, текст `y+53`) — это не трогает `CARD_H`.
**Что НЕ делаем:** не меняем `CARD_W`/`CARD_H`/`GAP_X`/`ROW_GAP`/`SLOT_H`/`PAD` (425)
и координаты раскладки. Если создатель захочет имя крупнее 14 px (напр. 15–16) — тогда
понадобится `CARD_H 86→96` и пересмотр `ROW_GAP`; это **отдельная** правка компоновки
(высокая цена), в объём не берём.

## 4. Карточка постройки — раздельные блоки (сверху вниз)

Порядок подтверждён создателем: **«Производит», затем «Потребляет», далее остальные**.
Пустые блоки **не показываются** (кроме «Производит» — см. ниже).

1. **Шапка** — имя (20 px, inline-переименование как сейчас) + строка служебного:
   «товары»/«скрытая»-галка, родитель, семейство/раса, категория товаров.
   Оформляется как один компактный `.pblock` без заголовка.
2. **Производит** (`.pblock`) — главный блок:
   - выводы назначенных рецептов `prodOutputs(p)`: строки `имя · тN` + кнопка `− отвязать`
     (из `recipesBlock`, 2378);
   - плюс `output.energy` / `output.items` (если есть) — строкой `энергия — N`, `предмет …`;
   - **если пусто** — блок **показывается** с подсказкой «перетащите рецепт из справочника
     (режим «Товары»)»: это точка входа в назначение, прятать нельзя;
   - под блоком — существующая кнопка «скопировать набор универсальной фабрики»
     (`copyRecipesBlock`) со своей подсказкой.
3. **Потребляет** (`.pblock`) — `params.eat` (нормы — итерация 2) + `input.consumables`.
   Пусто → блок скрыт.
4. **Условия работы** (`.pblock`) — «Нужно» (`input.energy/fuel/robots`), «КПД»
   (`params.efficiency`), «цена робота» (`params.robot_cost`), «При нехватке»
   (`params.effects`). Пусто → скрыт.
5. **Люди** (`.pblock`) — «Вмещает людей» (`input.people.capacity`). Пусто → скрыт.
6. **Слоты категорий** (`prodSlotEditor`, 2486) — редактор родителя; оформляется тем же
   блоком (заголовок + список + «+ слот»). Пусто у типа без слотов → скрыт (как сейчас).
7. **Производит предметы** (только `kind=items`) — блок со списком + «отвязать» + «+ предмет».
8. **Служебные параметры (JSON)** — остаётся в `<details>` (свёрнуто), стиль крупнее.
9. **Кнопки** — «удалить» (и «+ подтип», если применимо).

`prodSpecRows` (2147) расщепляется на источники для блоков 2–5 (сама функция может
вернуть структуру `{produces, consumes, conditions, people}` или вызывающие возьмут
поля напрямую — на выбор `@developer`, важно: **тексты строк не меняются**, меняется
только их группировка).

> **Принято дизайнером (2026-09-23), при желании меняется одной правкой:** «Условия
> работы» и «Люди» — **отдельными** блоками (не сливаем в один «Условия»). Объединить —
> слияние двух `.pblock` в разметке `renderProdPopup`.

## 5. Карточка товара — тот же крупный язык

1. **Шапка** — имя (20 px), категория-селект, сложность рецепта (+ предупреждение

3. **Объём и вес** (`.pblock`) — два поля в ряд, подписи 13 px, значения 14 px.

## 6. Состояния и реактивность

- **Загрузка.** Отдельного оверлея у попапа нет; попап открывается по данным `state`.
  Если запись не найдена (`renderPopup` 1429 / `renderProdPopup` 2182) — закрыть попап
  (как сейчас). Во время `state.generating` кнопки «заполнить комплектующие» /
  «предложить описание» остаются `disabled` с прежними `title`.
- **Пусто.** Пустые блоки постройки скрыты (кроме «Производит»); пустой состав рецепта —
  пунктирные слоты; «Используется в» — «нигде не используется».
- **Ошибка.** Ошибки API показываются существующим `#report`/тостом — не меняем.
- **Реактивность (что обновляется при действии):**
  - «− отвязать» рецепт (`unbindFactoryRecipe`) → `fetchState()` → `renderProdPopup`
    перерисовывается, блок «Производит» обновляется;
  - «− отвязать» постройку от товара (`unbindFactory`) → `fetchState` → `renderPopup`;
  - сохранение объёма/веса/описания/сложности → `PUT` → `fetchState` → перерисовка
    (описание — с защитой несохранённого, 3849);
  - переименование (inline) → `PUT` → `fetchState`;
  - переключение семейство/раса в попапе постройки → `PUT` → `fetchState`;
  - копирование набора → подтверждение (`copyRecipes`) → `POST` → тост «добавлено K,
    пропущено M» → `fetchState`.
  Всё это **сохраняется без изменений** — крупный попап лишь перерисовывается тем же
  `innerHTML`-циклом.
