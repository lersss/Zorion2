## 1. Модель: новый инвариант привязки

**Инвариант (канон после шага 2):**

> Любая **запись-подтип** каталога строений (`producer_types.parent_id IS NOT NULL`) держит
> **любой** рецепт каталога (`recipes`). Ограничения по товарной категории, по `kind` подтипа и
> по виду выхода рецепта — **сняты**.

`BindRecipe` после правки (единственный содержательный guard — «это конкретная запись, а не
абстрактный узел»):

1. `producer_types.id` найден → иначе **404** «тип не найден» (как сейчас).
2. `parent_id IS NOT NULL` → иначе **400** «рецепт назначается записи-подтипу (дочке), не типу/классу».
3. `recipes.id` найден → иначе **404** «рецепт не найден» (как сейчас).
4. привязки нет → иначе **409** «рецепт уже назначен этой постройке» (как сейчас).

**Почему сохраняем «только подтип».** Постройка в мире ссылается на запись-подтип
(`buildings.producer_type_id` — отложенная колонка, спека фабрик §3.2). Привязка к
абстрактному типу не имеет смысла сегодня и **опасна завтра**: при появлении наследования
наборов (кандидат §13) тип-набор и подтип-набор начнут складываться — двойной учёт. Решение
создателя говорит «постройке-дочке», а не «классу». *Альтернатива* (отклонена): разрешить и
типам, трактуя «дочка наследует, если у неё пусто» — это уже механика наследования, отдельная
фича.

**Почему сняты `kind`/категория/вид выхода.** Дословно: «Разрешаем любым постройкам назначать
любые рецепты. Остальное - на совести того, кто конфигурирует постройки». Категория —
классификация/визуальная ось студии (слоты родителя, фильтр семейства), а не ограничение
набора. Рецепт на ресурс, привязанный вручную, — мусор конфигуратора, а не поломка инварианта:
потребителей у привязки сегодня нет (релиз 2 фабрик ещё не читает `producer_recipes`), поле
`recipes.good_id` остаётся FK на `goods` — целостность держит БД.

**Роуты и контракты не меняются — подтверждаю.** Изменяется **только семантика проверок**
(раньше 400 — теперь 200) и тексты ошибок. Тело ответов `GET /studio/api/state` уже отдаёт всё
нужное (`producer_recipes` — `RecipeBindingView`, `goods.recipe_id`/`tier`) — **новых полей не
добавляем**. Единственный контракт, который «поехал бы», — расширение ответа
`DELETE /studio/api/goods/{id}` предупреждением о привязках (каскады, §6); поэтому в шаге 2
каскад остаётся как есть.

## 3. UI: сценарий назначения и видимый список

### 3.1. Перетаскивание рецепта на постройку (новое)

- **Источник переноса** — карточка каталога в справочнике при `branch === 'producers' &&
  spravMode === 'goods'` (шаг 1). Атрибут `draggable`/`dragStart` уже есть.
- **Drop-таргет** — `#canvasWrap` в ветке «Производители» при `spravMode === 'goods'`.
  Обработчики `dragenter/dragover/drop` зеркалят существующие для ветки «Товары»
  (`web/studio.html:1291–1328`), но **цель определяется узлом под курсором**: `hitTest(ev)` →
  `prodNodeById(id)`.
- **Подсветка цели:** карточка-подтип под курсором подсвечивается (тот же визуальный язык, что
  `.drop-target` у слотов / `.dnd-over` у канваса); «можно/нельзя» — через `dropEffect`.
- **Матрица дропа:**

| Что под курсором | `dropEffect` | Действие |
|---|---|---|
| карточка **подтипа** (`parent_id` задан) | `copy` | `POST /producers/{node_id}/recipes {recipe_id}` → `fetchState()`; тост об успехе **не нужен** (визуальная обратная связь — надпись «производит» и список) |
| карточка **типа** (`parent_id` NULL) или фиксированный узел (root/class) | `none` | тост-подсказка: «Рецепт назначается конкретной постройке (дочке), не классу» |
| узел-приглашение (`invite:`), заглушка (`hstub:`) | `none` | тост: «Сначала создайте постройку» |
| пустое место канваса | `none` | ничего (инертно, без тоста — случайный промах) |
| карточка **ресурса** из справочника | `none` | тост: «ресурс нельзя назначить как рецепт» |
| товар **без рецепта** (`recipe_id` пуст) | — | тост: «рецепт не создан» |
| рецепт уже назначен этой постройке | — | тост: «уже в наборе постройки» |

- **Два разных смысла drop (важно, см. ловушку §10):** в ветке «Товары» бросок в **любую**
  точку канваса привязывает к **выбранной фабрике**; в ветке «Производители» (режим «Товары») —
  к **узлу под курсором**. Оба пути идут через единый `bindRecipeToFactory(g, id)`.
- **Мелкая правка:** `bindingInFlight` сейчас ключуется по `recipe_id`; при быстрых бросках одного
  рецепта на две разные постройки второй бросок молча отбросится. Ключ → `producerId + ':' + recipeId`.
- **Пан во время drag:** `mousedown` не должен запускать пан (`dndActive`), как в ветке «Товары».

### 3.2. Видимый список назначенных рецептов (текст, не JSON)

Одно и то же производное в трёх местах (выводы назначенных рецептов = товары, чей `recipe_id`
присутствует в `state.producer_recipes` для этой постройки):

1. **Карточка узла в дереве** (канвас, 190×86): третья строка под именем (12px) и подписью
   (10px) — на свободном месте `y+64…y+76`: перечисление имён выходов, обрезанное по ширине
   (`trunc`). Пустой набор — **строку не показываем**. Для узла без набора карточка визуально
   не меняется (0 регрессий для класс/тип/приглашение).
2. **Список справа** (`renderProdSprav`, карточка `.card`): в `.meta` добавляется фрагмент
   « · производит: Пища, Вода · т1». Пустой набор — фрагмент не добавляется.
3. **Карточка постройки** (`renderProdPopup`): блок набора рецептов **рисуется у любого
   подтипа** (не только с категорией) и перестаёт быть «только числом»:

```
набор рецептов: 2
 · Пища · т1        [− отвязать]
 · Вода · т1        [− отвязать]
[скопировать набор универсальной фабрики]   ← только если категория есть (как сейчас)
```

- **Отвязка** — только здесь: `DELETE /producers/{id}/recipes/{recipe_id}` (существующий роут);
  на карточке дерева и в списке справа отвязки нет (мелкий UI, клик по канвасу конфликтует с
  выбором/паном).
- **Пусто в карточке** — «набор рецептов: 0» + строка подсказки «перетащите рецепт из
  справочника (режим «Товары»)».

## 4. Надпись «производит» на карточке подтипа

**Формулировка:** `производит: <имя выхода> · т<tier>`; несколько выходов — через запятую, каждый
со своим тиром: `производит: Пища · т1, Вода · т1`.

- `<имя выхода>` — `goods.name` товара, чей `recipe_id` назначен постройке;
- `т<tier>` — эффективный тир товара (`GoodView.tier` = `complexity ?? вычисленный`), в UI —
  только цифра (`т1`), без K/°C (температур в задаче нет);
- порядок — устойчивый: по тиру, затем по имени (иначе текст «плавает» между перерисовками);
- **пустой набор — строку не показываем вовсе** (не «производит: —»);
- источник — производная набора рецептов, **отдельного поля «что производит» не заводим**.

Место надписи (одна формулировка, разные носители): в карточке постройки (пункт 3 §3.2) —
полная форма; в дереве/списке — компактная (те же имена + « · тN»).

**Вопрос:** заводим ли «**набор рецептов типа**» (наследование)? Сейчас набор живёт только на
подтипе; конфигуратор, у которого 13 категорий × 9 семейств × 60 рас, будет назначать рецепты
каждой дочке вручную.

**Ответ (кандидат, не факт, в текущие числа не входит):** «Набор рецептов типа» — набор на
**типе** (`producer_types.parent_id IS NULL`), который **подтип наследует, если у него своего
набора нет** (у подтипа непустой набор — переопределяет; «самая конкретная побеждает» — тот же
канон, что у слотов). Цена: новая семантика чтения набора (тип → подтип), запрет привязки к типу
из §1 придётся снять/переосмыслить, у существующих подтипов поведение не меняется (пусто =
наследует, что для категорийных подтипов даёт **смену поведения** — их наборы появятся
«из ниоткуда»). Режим отказа: пустой тип-набор → подтип остаётся пустым (не ломается).
*Источник:* спека фабрик §3.2 (типы абстрактны) + правило «самая конкретная побеждает»
(`2026-09-21-студия-производители-лестница-предложения`). **Требует решения создателя; вне
шага 2.**
