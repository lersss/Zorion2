## 0. Задача и решения создателя

Создатель настраивает контент (справочники студии) прямо в **dev-базе** через `/studio`; прод
(Amvera, PostgreSQL) наполняется из **миграций + сидера**, поэтому dev-настройки туда не попадают.
Нужен механизм переноса контента dev → прод.

Решения создателя (2026-09-24, дословно/точно — идея §5, §8):

1. Переносим **только контент** (справочники студии), не игровую вселенную.
2. Направление — **только dev → прод**.
3. Режим — **только по требованию, кнопкой** (автоматики и фоновой синхронизации нет).
4. Источник истины — **dev** (прод игроков не ждёт).
5. «**конфиг вгрузить** было бы здорово» — кроме выгрузки из студии нужна **загрузка конфигурации из файла**
   (воспроизводимость свежей базы/прода).
6. Новые имена — **канон** (§8): класс «Колония», ступени Форпост → Поселение → Городок → Город →
   Мегаполис → Метрополия → Экуменополис. Сидер уже правится отдельной задачей (`@developer`, путь 1).

**Ключевая находка (`@reviewer`), учитывается спекой:** на свежей БД рассинхрона «сид ↔ миграции» нет,
но на **существующей** БД (dev/prod с маркером `producer_catalog_seed`) сид не запускается, а
data-миграции `000051`/`000077` знают **старые** имена. Без data-миграции переименования канон-имена
и dev-настройки на прод так не доедут → §6.

### Решения создателя на гейте дизайна (2026-09-24, дословно/точно)

1. **Настройки генерации не переносим** — только контент (+ ссылка-якорь `default_settlement_type_id`).
   *Закрывает §12 О1: дефолт подтверждён.*
2. **Импорт — ПОЛНАЯ ЗАМЕНА:** контент, которого нет в файле, **удаляется** (прод = точная копия dev).
   *Закрывает §12 О2: принят не дефолт, а «да».*
3. **Правки прода импорт перезаписывает** (dev — источник истины, last-write-wins).
   *Подтверждает решение дизайнера §5.3 (прямое следствие решения 4 «источник истины — dev»).*
4. **Проверка целостности — минимальные проверки + атомарность**, полную валидацию студии не
   дублируем. *Закрывает §12 О5: дефолт принят.*
5. **Метка записи — ЦИФРОВАЯ/номерная** (`p_0001`, `g_0142`; бессмысленная, НЕ из имени, НЕ слаг).
   Создатель отверг описательную метку: «при радикальном переименовании метка перестаёт что-то
   говорить и начинает путать». `id` для переноса **отвергнут** (номера не совпадают между базами;
   по `id` ссылаются объекты мира — поселения/строения/залежи). *Закрывает §12 О3/О4.*

**Связка, определяющая порядок итераций (§9):** полная замена (решение 2) безопасна **только** при
надёжном сопоставлении записей — то есть **по метке, а не по имени**. При сопоставлении по
`name_norm` переименование записи в dev выглядит как «запись исчезла из файла + появилась новая» →
на проде старая будет **удалена вместе со связями**, а новая создана с новым `id` (ровно ловушка,
ради которой заведена задача, идея §1.3). Отсюда: **метка обязана существовать до включения полной
замены**; промежуточная «импорт по имени с удалением» **не выпускается** (§9).

## 1. Что такое «контент»: точная граница

**Контент** — справочники студии: «что бывает в мире». **Объекты мира** — «что стоит/живёт сейчас».
Экспорт и импорт работают **только** с контентом.

### 1.1. Входит (переносим)

| Таблица | ~строк (dev) | Что | Ключ сопоставления (метка, §3) |
|---|---|---|---|
| `categories` | ~19 | товарные и системные ресурсные категории | `(kind, name_norm)` — **метки нет** (§3.4) |
| `goods` | ~131+ | ресурсы и товары | `code` (`g_NNNN`) |
| `recipes` | по числу `goods.kind='good'` | рецепт товара (1:1 к `goods`) | `code` товара-родителя |
| `recipe_components` | ? | состав рецепта (позиции) | `(code рецепта, pos)` |
| `producer_types` | 42 | дерево построек (класс, ступени, фабрики, лаборатории; **раздел вида — поле `section`**) | `code` (`p_NNNN`) |
| `producer_slots` | ? | слоты родителя (категория × расовость) | `(code родителя, category, race_family, race)` |
| `producer_recipes` | ? | привязки «фабрика × рецепт» + число `rate` | `(code постройки, code товара)` |
| `producer_items` | ? | связи «лаборатория → предмет» | `(code постройки, code предмета)` |
| `items` | ~4+ | справочник типов предметов | `code` (`i_NNNN`) |
| `effect_types` | ~2 | типы эффектов (голод/жажда) | `code` (`e_NNNN`) |

Плюс **ссылка контента из `generation_config`**: ключ `default_settlement_type_id` (id записи-якоря
базового типа `producer_types`) — переносится **как ссылка** (в файле — **метка `code`** записи-якоря),
не как сырой id (§1.3, §4).

### 1.2. Не входит (не переносим)

- Объекты мира: `worlds`, `planets`, `regions`, `factions`, `npc_agents`, `settlements`, `buildings`,
  `deposits`, `system_belts`, `contracts`, `money_operations`, `accounts`, `active_effects`,
  `player_cargo`, `player_planet_knowledge` и прочее «что стоит и у кого».
- **Настройки и служебные ключи `generation_config`:** маркеры сидов (`goods_catalog_seed`,
  `producer_catalog_seed`), `settlement_arithmetic_visible_to_player` (настройка показа),
  `generation_started_at` (runtime-состояние), ручки генерации (`star_weights`, `planet_means` —
  баланс/операционка, не справочники). Обоснование: это **поведение и баланс**, а не контент;
  молчаливый перенос менял бы прод иначе, чем задумано при настройке контента.
  *(Решено создателем 2026-09-24 — «не переносим»; §12 О1 закрыт.)*

### 1.3. Почему `default_settlement_type_id` — контент-ссылка

Ключ хранит **id** записи `producer_types` — **якоря базового типа** (рантайм резолвит по нему корень
ладдеры: `settlement_stage.go`, «якорь → `parent_id`»). Id **не переносим** между базами, поэтому в файле
ключ несётся как **ссылка по метке** (§3) той записи, на которую якорь указывает сейчас
(`code` записи-якоря); при импорте ключ переустанавливается на **локальный** id найденной
записи. Это тот же приём, что «резолв по ключу» в сиде (`settlementFloorStageConstant`).

**Якорь ≠ «ступень-пол» по определению.** В сиде якорь сегодня ставится на ступень-пол
(`settlementFloorStageName`), но это **текущее совпадение, а не инвариант**: спека стадий
(`2026-09-23-стадии-поселения-и-скорость-производства.md` §7 п.5) отдельно предупреждает, что нижняя
ступень ладдеры **может не совпадать** с `default_settlement_type_id`. Поэтому снимок несёт **текущее
значение якоря** (какую запись он называет), а не «ищется ступень-пол»: искать пол и переставлять на него
якорь при импорте — значит молча сдвинуть якорь.

### 1.4. Развилки о природе сущности (обязательная сверка)

1. **Природа.** Экспорт — **лог** (результат-состояние): сериализованный снимок справочников, файл,
   не таблица. Импорт — **операция** (событие применения), не новая сущность. Отдельной таблицы у
   механизма **нет** (v1): журнал переноса — кандидат ГД-сущности (§11, кандидат 2), не факт.
2. **Владелец.** Записи принадлежат **таблицам каталога** (многие владельцы), сам снимок — один файл.
3. **Расширяемость.** Формат — секции по таблицам (§4); новый справочник = новая секция, схема
   переживает второй и третий тип. Секции упорядочены (родители раньше детей) — порядок импорта
   из файла, а не хардкод в коде.
4. **Метка (§3) — атрибут существующих сущностей, не новая сущность.** Колонка `code` на контентных
   таблицах (у многих владельцев, одна метка на запись), неизменная по смыслу. Отдельной таблицы
   меток/реестра кодов **не вводим**: метка не несёт данных сверх тождества («сущность с двумя
   экземплярами — не сущность»: один факт — одна колонка).

## 2. Разворот подходов (пространство решений)

Пять разных классов (не вариации одного) — цена и режим отказа:

| Класс | Что это | Цена | Режим отказа | Итог |
|---|---|---|---|---|
| **A. Файл-снимок контента (JSON) + кнопочный импорт** | Студия сериализует справочники; ссылки — по метке (§3); импорт — идемпотентный upsert + полная замена | средняя (формат + импортёр + ручки) | ссылки по имени ломаются при переименовании (лечится меткой — она вперёд импорта, §9) | **принят** |
| **B. SQL data-миграции в репо** (образец `000051`/`000077`) | каждая порция правок → data-миграция, применяется при деплое | низкая сейчас, но ручной SQL на каждую правку; история миграций растёт | не «по требованию»; ошибка в миграции — блок деплоя | отклонён как *механизм переноса* (остаётся только для ренейма, §6) |
| **C. Прямая синхронизация dev → прод по сети** (кнопка «выгрузить на прод») | dev пишет в прод-БД/прод-API | высокая (доступ/секреты к проду из dev, канал, деплой-обвязка) | компромисс прод-БД одним сетевым сбоем | отклонён (риск выше выгоды; прод пока не в бою) |
| **D. `pg_dump` контентных таблиц + `psql` на проде** | классический дамп таблиц | низкая на разработку | **переносит `id`** (коллизии/перепутанные ссылки), нет upsert-идемпотентности, порядок FK | отклонён (id не переносимы — идея §2) |
| **E. «Контент как код»: экспорт в Go-сид** (`seed_*.go`) | экспорт генерирует Go-файлы сида | средняя; прод наполняется при старте | creator **отклонил** «занести в сид» (идея §0) | отклонён по решению создателя |

**Принят A.** Он единственный даёт «по требованию кнопкой» (решение 3), воспроизводимость из файла
(решение 5) и не переносит `id` (корень проблемы). **B** остаётся точечно — только для ренейм-миграции
(§6), где файл бессилен: правку имён на существующей БД делает только миграция. **D** отклонён именно
потому, что `pg_dump` тянет `id`; метка (§3) делает переносимой ту же идентичность, не перенося `id`.

## 3. Стабильная идентичность записи: номерная метка `code`

**Проблема.** Экспорт переносит ссылки (состав рецепта, родитель постройки, привязки). Id **не
переносимы** (автоинкремент, в каждой базе свой; по `id` ссылаются объекты мира). `name_norm` меняется
при переименовании. Значит нужен переносимый ключ — **метка**.

**Решение создателя (2026-09-24).** Метка — **цифровая/номерная** (`p_0001`, `g_0142`), **бессмысленная**:
не из имени, не слаг. Описательная метка отвергнута: «при радикальном переименовании метка перестаёт
что-то говорить и начинает путать». `id` отвергнут. *(История: варианты «`name_norm` как ключ v1» и
«авто-слаг И3» — отклонены; см. §13.)*

### 3.1. Формат

- Колонка `code TEXT NULL` + **частичный `UNIQUE` (`WHERE code IS NOT NULL`)** на таблицах с
  самостоятельной идентичностью: `goods`, `producer_types`, `items`, `effect_types`.
- Значение — префикс таблицы + номер: `g_0001` (`goods`), `p_0001` (`producer_types`),
  `i_0001` (`items`), `e_0001` (`effect_types`). Номер — минимум 4 цифры, растёт без обрезки
  (`g_10001`). Префикс — только для читаемости и различимости секций в файле; **уникальность
  обеспечивается в пределах своей таблицы** (не «глобально по строкам»).
- Метка **необязательна** (`NULL` допустим схемой), но норма — заполнена у всех контентных записей
  (§3.2); `NULL` трактуется импортом как «запись вне управления» (§5.4, отказ).

### 3.2. Как заводится (счётчик, не генератор из имени)

- **Счётчик — последовательность в БД** (`SEQUENCE` на таблицу: `goods_code_seq`, …): монотонная,
  безопасная при параллельных правках студии (двое одновременно — разные номера, как `id`).
  Генератор «из имени» не используется принципиально (метка бессмысленна).
- **Новая запись** (студия): метка присваивается при создании — `'g_' || lpad(nextval('goods_code_seq')::text, 4, '0')`.
- **Существующие записи** (бэкфилл, одна миграция): номера раздаются последовательно в порядке `id`
  (детерминированно), последовательность сдвигается на максимум. Бэкфилл — разовый, до включения
  импорта (§9).
- **Сид** свежей БД присваивает метки тем же способом и в том же порядке вставки, что даёт на свежей
  БД ту же нумерацию, что бэкфилл на dev (сид-записи — первые по `id`). Точное соответствие «dev ↔
  свежая БД» гарантируется только этим совпадением порядка; расхождение ловится первичной накаткой
  (§3.5), а не молчаливым удалением.

### 3.3. Уникальность, отображение, редактируемость

- **Уникальность** — в пределах таблицы (частичный `UNIQUE`). Не глобальная: префикс разводит таблицы,
  но конфликтов между таблицами у нас нет по построению (`g_` ≠ `p_`).
- **Отображение в студии** — **справочное**: мелким текстом в карточке записи («метка переноса»);
  служит для сверки отчётов/диффа, не для работы. Скрывать допустимо, но в отчёте импорта метка
  указывается всегда (§5.5) — иначе оператор не поймёт, что удаляется.
- **Редактируемость — нет.** Метка неизменна по смыслу: её правка = разрыв тождества между средами.
  Поле в студии — только для чтения.

### 3.4. Границы метки

- **`categories` — метки нет.** У таблицы уже есть колонка `code` (`000045`), но она **семантическая**
  (water/gas/mineral/…, только ресурсные категории) — это не переносная метка, и заполнять её номерами
  значило бы смешать два разных смысла в одном поле. Идентичность переноса `categories` — **`(kind, name_norm)`**.
  Переименование категории полной заменой **не поддерживается**: импорт увидит «удаление» и упрётся
  в защиту по ссылкам (на категорию ссылаются `goods`) → отказ (§5.4); лечение — парная data-миграция
  имён (приём §6). Категорий ~19, они устойчивы — цена приемлема.
- **`recipes`/`recipe_components` — своей метки нет.** Идентичность рецепта — метка его товара (`good`),
  компонента — `(рецепт, pos)`. Это листья (на них никто не ссылается) → заменяются целиком (§5, п.5).

### 3.5. Выравнивание меток между базами (критично для полной замены)

Полная замена (решение 2) удаляет то, чего нет в файле — **по метке**. Значит у целевой базы метки
должны совпадать с dev. Два режима импорта:

1. **Штатный (по метке).** У целевых записей метки есть → сопоставление по метке; расхождения → отказ
   (§5.4).
2. **Первичная накатка (bootstrap, по имени).** Разрешена **только** если в целевых контентных
   таблицах **нет ни одной непустой метки** (чистая цель) и оператор подтвердил явно. Тогда записи
   сопоставляются по `(kind, name_norm)`, метки **впечатываются из файла** в найденные записи
   (их локальные `id` сохраняются — мировые FK целы), недостающие создаются. Именно этот шаг
   **впечатывает тождество**: после него все последующие импорты — по метке, и переименования
   безопасны.
   - Цена bootstrap — он **сопоставляет по имени**: переименование в dev, не снятое data-миграцией,
     на первичной накатке выглядит как удаление+создание. Защита: сухой прогон с диффом (§5.2),
     отказ по мировым ссылкам (§5.4), второе подтверждение. Поэтому ренейм-миграция (§6) идёт
     **до** (§9).
   - Если цель не пуста по меткам → bootstrap **запрещён** (иначе смешаются два режима) — только
     штатный, и расхождение меток даёт отказ.
3. **Пустая прод-подобная БД.** `id` контента назначает она сама из файла — выравнивание не нужно
   вовсе; полная замена безопасна тривиально (мировых ссылок нет).

### 3.6. Что метка снимает (известные ограничения прошлых редакций)

- `producer_types.params.effects` хранит **имя** `effect_types` — привязка ломается при переименовании
  эффекта. Импорт по метке **лечит это**: эффект находится по метке, `params.effects` резолвится в
  ту же запись; полный отчёт о сиротах `active_effects` не нужен (мировые ссылки проверяются до
  удаления, §5.4). Прежняя «минимальная защита v1 warning'ом» снимается вместе с v1.
- Константа `settlementFloorStageName` и резолв `default_settlement_type_id` **по имени** в сиде
  заменяются резолвом по метке записи-якоря (§8).

## 4. Экспорт

**Формат — JSON-снимок контента** (класс A). Файл: `content/catalog.json` в репозитории.
`schema_version: 1` (отдельный от `model.State` — `model.State` id-ключевой и содержит вычисляемые поля;
снимок контента — натурально-ключевой и без вычисляемого).

**Структура (секции упорядочены — порядок импорта из файла):**

```
{
  "schema_version": 1,
  "generated_at": "<UTC RFC3339>",
  "source": "dev",
  "counts": { "categories": 19, "goods": 131, "producer_types": 42, ... },
  "categories":        [ { "name", "kind", "code", "is_system" } ],
  "goods":             [ { "name", "kind", "category", "description", "volume", "weight",
                           "props", "source", "code" } ],
  "recipes":           [ { "good", "complexity" } ],
  "recipe_components": [ { "good", "pos", "component", "quantity", "reason", "allow_resource" } ],
  "producer_types":    [ { "name", "kind", "category", "parent", "race_family", "race",
                           "output", "input", "params", "hidden", "section", "code" } ],
  "items":             [ { "name", "slot_type", "unlocks", "params", "code" } ],
  "producer_slots":    [ { "parent", "category", "race_family", "race", "hidden" } ],
  "producer_recipes":  [ { "producer", "good", "rate" } ],
  "producer_items":    [ { "producer", "item", "requirements" } ],
  "effect_types":      [ { "name", "impact", "params", "code" } ],
  "generation_config": { "default_settlement_type_id": "<метка записи-якоря>" }
}
```

- **Никаких `id`** ни в записях, ни в ссылках. Ссылки — метки (§3) и натуральные ключи
  (`category` — по `categories` без метки, `pos` — позиция компонента).
- **`unlocks` (`items`) — по метке/натуральному ключу, не по id.** В БД `items.unlocks` хранит
  **внутренние `id`** (`[{producer_type_id, category_id}]`, `000048:37`) — это неустранимо: в БД ссылки
  id-ключевые, как везде. В **снимке** поле несётся переносимо:
  `[ { "producer": "<code p_NNNN>", "category": { "kind": "good|resource", "name": "<имя>" } } ]`
  (`producer` — метка `producer_types.code`, §3; `category` — натуральный ключ `(kind, name_norm)`,
  как у остальных ссылок на `categories`, §3.4). Экспорт резолвит локальные id → метку/ключ, импорт —
  обратно (карты §5 п.6). Элемент, который не резолвится (при экспорте — несуществующий id; при импорте —
  чужой ключ вида `producer_type_id`/`category_id` или неизвестная метка/имя), — **отказ**, не молчаливый
  пропуск: `id` в снимок не попадает никогда.
- **`code` (метка) — обязательное поле** контентных записей (`goods`/`producer_types`/`items`/
  `effect_types`). Для `categories` `code` — по-прежнему **семантический** (water/gas/…), не метка;
  `categories` идентифицируется `(kind, name_norm)` (§3.4).
- **Порядок секций — топологический по FK** (родитель раньше ребёнка): `items` идёт **после**
  `producer_types` (его `unlocks` ссылается на `producer_types`/`categories`) и **раньше**
  `producer_items` (`item_id` FK → `items`); внутри `producer_types` родители раньше детей (self-FK `parent_id`).
- **Ключ `categories` — составной** `(kind, name_norm)`, а ссылки несут «голое» имя. Правило резолва:
  `goods.category` — по `goods.kind` (совпадает с `categories.kind`); `producer_slots.category` — по `kind='good'`.
- `props` (`goods`) переносятся **дословно** (в т.ч. `t_melt_k`/`t_boil_k` — внутренние единицы в K;
  снимок — данные модели, не интерфейс; правило «в UI только °C» здесь ничего не меняет).
- `hidden` у `producer_types`/`producer_slots` переносится (скрытие — часть контента, `000052`/`000054`).
- `section` у `producer_types` (дельта 2026-09-25: раздел вида постройки студии — `colony`/`factory`/
  `lab`/`mining`/`energy`; миграция `000085`) переносится **как есть** — это значение-ключ, **не ссылка**
  (в БД хранится только у типов-корней, подтипы наследуют через `parent`). Список значения **открытый**
  (данные интерфейса, без `CHECK`): импорт значение не ограничивает (§5 п.4, §9 И2/И3), неизвестное
  клиент относит в служебный «Прочее». Спека `2026-09-25-студия-разделы-построек-по-видам.md` §2.

**Куда сохраняется.** Кнопка «Экспорт контента» в студии → `GET /studio/api/content/export`:
- сервер **пишет** `content/catalog.json` в рабочей директории (dev = корень репозитория;
  прод — эфемерная ФС, запись не значима);
- и **отдаёт** тот же JSON на скачивание (`catalog-YYYYMMDD.json`) — рабочий путь создателя.
Файл коммитит создатель/менеджер (репозиторий — канал доставки на прод, как остальной код).

**Доступ:** `auth.AdminAuth` (admin/skycomposer) — как все ручки студии.

**Обновление.** Файл — не «синхронизация в фоне»: новый снимок пишется каждый раз при нажатии кнопки
(в dev), прод видит его только после коммита/деплоя и нажатия «Импорт» (§5).

## 5. Импорт («конфиг вгрузить») — полная замена

**Канал.** Файл в репозитории `content/catalog.json` (прод получает его при деплое) **и** загрузка файла
через студию (аварийный/ручной путь). Оба — по кнопке, без автоматики (решение 3).
**Правка `Dockerfile` обязательна:** образ копирует только `/server`, `/web`, `/config` — каталога
`content/` в образе нет, и штатный импорт «из файла» на проде упрётся в «файла нет». Добавить
`COPY --from=builder /app/content ./content` (вторая ступень) **или** класть снимок внутрь уже
копируемого `config/`. Альтернатива без образа — разовая загрузка файла через студию (ручной путь выше).
Дельта — `docs/DEPLOY.md` (состав образа, шаг импорта).

**Ручки и кнопки:**
- `POST /studio/api/content/import` — тело либо `{}` (взять `content/catalog.json` с диска сервера),
  либо `{ "snapshot": { ... } }` (загруженный файл). Параметр **`dry_run=true`** — сухой прогон (§5.2).
  Ответ — отчёт (§5.5).
- Кнопка «Импорт контента» в шапке студии: **два шага** — «Проверить (сухой прогон)» → попап-дифф →
  второе подтверждение → «Применить»; после применения — попап-отчёт.

**Алгоритм (одна транзакция + `pg_advisory_xact_lock` — как `beginMutation`, §9.1 каталога). При
`dry_run=true` — тот же алгоритм, но транзакция завершается `ROLLBACK` (в БД ничего не пишется):**

1. Разобрать и проверить `schema_version` (не выше поддерживаемой) и наличие всех секций.
2. Определить режим сопоставления (§3.5): если в целевых контентных таблицах **все** записи без
   метки → **первичная накатка (по `(kind, name_norm)`)**; если **у всех** метки есть → **штатный (по
   метке)**; смесь (часть с меткой, часть без) → **отказ** (нельзя смешивать два тождества).
3. Порядок (родитель раньше ребёнка): `categories` → `goods` → `recipes`/`recipe_components` →
   `producer_types` (**внутри — родители раньше детей**: self-FK `parent_id`) → `items`
   (`unlocks` ссылается на `producer_types`/`categories`) → `producer_slots`/`producer_recipes`/
   `producer_items` (`item_id` FK → `items`) → `effect_types`.
4. **Upsert по метке** (первичная накатка — по `(kind, name_norm)`, метка впечатывается из файла):
   запись есть → UPDATE полей; нет → INSERT. **`id` существующих записей не меняются** — мировые FK
   (`settlements.settlement_type_id`, `buildings.producer_type_id`, `deposits.good_id`,
   `settlement_branch_buffers.good_id`) остаются валидными.
   **Дельта 2026-09-25:** `producer_types.section` входит в набор обновляемых полей
   (last-write-wins, решение 3 создателя); при первичной накатке (§3.5) значение впечатывается из
   файла. Поле обновляется и у существующих канон-корней — иначе назначенный в dev раздел не доедет
   на прод.
5. **Дочерние наборы заменяются целиком** (идемпотентность): состав рецепта, `producer_slots`,
   `producer_recipes`, `producer_items` — для затронутой записи `DELETE` + `INSERT` из файла
   (эти таблицы — листья, на них никто не ссылается).
6. Ссылки резолвятся по картам (метка → id), собранным в той же транзакции. `items.unlocks` —
   `producer` (метка) → локальный `producer_type_id`, `category` `(kind, name_norm)` → локальный
   `category_id`; в БД пишется id-форма (`[{producer_type_id, category_id}]`), в снимке — метка/ключ (§4).
7. **Полная замена: удаление того, чего нет в файле** (решение 2). Что удаляется — §5.3; защита от
   сноса живого — §5.4.
8. `default_settlement_type_id` — резолв **по метке записи-якоря из файла** (§1.3) и upsert на
   локальный id этой записи; метка не найдена → ошибка импорта (не молчаливый пропуск: новые
   поселения остались бы без типа — известный класс бага). Якорь на «ступень-пол» **не переставляется**.

**5.1. Идемпотентность.** Повторный импорт того же файла: 0 созданных, 0 изменённых, 0 удалённых
(сравнение полей). Изменённый файл — только дельта обновляется/удаляется.

**5.2. Сухой прогон (обязательный первый шаг).** `dry_run=true` считает **дифф** и возвращает его без
записи:
`{ "mode": "managed|bootstrap", "create": {...}, "update": {...}, "delete": {...}, "blocked": [...],
"unmatched": [...] }`, где `delete` — перечень удаляемых записей (таблица, метка, имя), `blocked` —
удаления, упёршиеся в мировые ссылки (§5.4), `unmatched` — расхождения тождества (§5.4). Оператор
видит **что именно исчезнет с прода** до применения. Применение без сухого прогона в UI не предлагается
(ручка остаётся, но кнопка ведёт двумя шагами).

**5.3. Правки и удаления «на проде руками».** Источник истины — dev (решение 4): импорт **перезаписывает**
поля записей, присутствующих в файле (last-write-wins, решение 3), и **удаляет** контент, которого в
файле нет (полная замена, решение 2) — «прод = точная копия dev». Записей, которых нет в файле, на
проде после импорта не остаётся (кроме заблокированных, §5.4 — они дают отказ, не частичное состояние).
Что считается «нет в файле»: **метка есть в целевой таблице, но отсутствует среди меток
соответствующей секции файла**.

**5.4. Защита от сноса живого (ключевой вопрос безопасности).**

- **Мировые ссылки блокируют удаление.** Для каждой удаляемой записи импорт **явно считает ссылки** во
  всех таблицах, где на неё есть FK, **независимо от `ON DELETE`**. Любая ссылка ≥ 1 → запись попадает
  в `blocked` и **импорт отказывает целиком** (409, транзакция откатывается), с перечнем:
  таблица, метка, имя, род и число ссылок. Оператор разрешает конфликт вручную (убрать удаление из
  файла или развязать мировую ссылку) и повторяет.
  - **Почему не полагаемся на FK:** у `deposits.good_id` и `settlement_branch_buffers.good_id` стоит
    **`ON DELETE CASCADE`** — «просто `DELETE`» **молча унесёт залежи/буферы мира**. У
    `settlements.settlement_type_id`/`buildings.producer_type_id` — `ON DELETE RESTRICT` (транзакция
    упала бы, но без внятного отчёта). Явный предсчёт — единственная надёжная защита для обоих случаев;
    каскад как путь удаления контента **не используется**.
- **Записи без метки в целевой БД** (расхождение бэкфилла/частичный импорт) — в `unmatched` и **отказ**
  (не молчаливое удаление и не молчаливое создание дубля). Bootstrap (§3.5) допустим только на цели,
  где меток нет вовсе.
- **Никакого частичного применения.** Ошибка на любом шаге → откат всей транзакции, БД не изменена.

**5.5. Отчёт и режим отказа.** Атомарный: ошибка на любом шаге → **откат всей транзакции**, БД не
изменена, ответ `400/409` с причиной и местом (секция + метка). Успех → отчёт
`{ "created": {...}, "updated": {...}, "deleted": {...}, "warnings": [...] }` (числа по секциям, формат —
как у `BulkReport` студии). Частичного применения нет (в отличие от `BulkCreateGoods`: тут ссылочная
целостность, «половина контента» хуже отсутствия). Решение зафиксировано здесь и архитектурным
паттерном каталога (`beginMutation`: одна транзакция + `pg_advisory_xact_lock`).

**Транзиент (ожидаемо, не ошибка).** Импорт сразу меняет `params`/номенклатуру, а очистка сирот
`active_effects` и пересчёт норм идут в **owner-проходе**; до его первого прохода карточка/сводка могут
показывать расхождение. Окно закрывается следующим owner-проходом.

## 6. Переименование-миграция (находка `@reviewer`)

**Роль под полную замену (переосмыслено).** С полной заменой (решение 2) канон-имена **могли бы**
доехать на прод сами — импорт несёт `name` из файла. Но миграция остаётся, потому что: (а) она
приводит **существующие** БД с маркером сида к канону **до** метки, а первичная накатка/бэкфилл
сопоставляют по именам (§3.5) — без неё переименованный узел на цели не найдётся и метка в него не
впечатается; (б) прод может быть задеплоен **раньше** первого нажатия «Импорт» — до тех пор имена
должны быть согласованы с кодом/тестами; (в) она снимает коллизию «класс ↔ вторая ступень» до того,
как по именам начнёт сопоставлять импорт. Идёт **в И1, до миграции меток** (§9). Номер **`000083`**
(последний в `docs/DB.md` — `000082`; `000072` забронирован под спеку орбиты) — оставить за собой;
миграция меток — следующим номером. **Согласовать оба номера с `@manager`** (бронь номеров —
`docs/COORDINATION.md`).

**Что делает (идемпотентно, по данным, не по литералам-двойникам):**
1. **Класс-корень** → «Колония»: `UPDATE producer_types SET name='Колония', name_norm='колония'
   WHERE parent_id IS NULL AND name_norm='поселение';` (на dev уже «колония» → no-op).
2. **Ступень-пол** → «Форпост»: `... SET name='Форпост', name_norm='форпост'
   WHERE name_norm='аутпост' AND parent_id = (SELECT id FROM producer_types WHERE name_norm='колония');`
3. **Вторая ступень** → «Поселение»: `... SET name='Поселение', name_norm='поселение'
   WHERE name_norm='посёлок' AND parent_id = (SELECT id FROM producer_types WHERE name_norm='колония');`
   — **строго после шага 1** (иначе `UNIQUE(name_norm)` конфликтует с ещё не переименованным корнем;
   на dev вторая ступень уже «поселение» (`id 155`) → no-op).
4. `generation_config.default_settlement_type_id` **не трогаем**: он хранит **id**, а переименование
   id не меняет; связь `settlements.settlement_type_id` тоже id-ключевая — обе целы.
5. Шаги «Городок/Город/Мегаполис/Метрополия/Экуменополис» уже совпадают с каноном после `000077`
   (кроме имён пола/второй ступени выше) — миграция их не касается.

**Коллизия `name_norm='поселение'` (класс ↔ вторая ступень) — обязательный учёт.** До этой миграции имя
`поселение` носят **два разных узла**: класс-корень (`parent_id IS NULL`) и вторая ступень ладдеры. Отсюда:
(а) **опасность**: резолв класса-корня по литералу имени после ренейма вернёт «не тот» узел (вторую
ступень) или ничего; (б) **правило**: класс-корень **после миграции запрещено резолвить по имени** — только
по данным/якорю (`generation_config.default_settlement_type_id` → `parent_id`, как в рантайме
`settlement_stage.go`); (в) **место будущей правки**, если такие литералы ещё читаются:
`migrations/000077:61` и `migrations/000079:44` (шаблонные предикаты), а также тест
`internal/goodsstudio/supply_effects_consistency_test.go:262` (пинит литерал `name_norm = 'поселение'`).
Сама миграция `000083` правит по данным (§шаги 1–3) и на литералы не опирается.

**Граница ответственности.** Само приведение сида, тестов-фикстур, комментариев и доков к канону —
задача `@developer`/`@dispatcher` (уже запущена, путь 1); моя часть — **миграция для существующих БД**
и её согласованность с сидом. Согласованность **сида ↔ константы-пола** стережёт существующий
`TestSeedSettlementFloorStageConstant` (проверяет константу `settlementFloorStageName` против сида,
**не** данные БД после миграции — это отдельный тест T14, ещё не написанный).

отдельной правкой.

- **«Экспорт контента»** → `GET /studio/api/content/export`: скачивание `catalog-YYYYMMDD.json`
  (+ запись `content/catalog.json` в dev).
- **«Импорт контента»** → `POST /studio/api/content/import` **двумя шагами**:
  (1) «Проверить» (`dry_run=true`) — предпросмотр источника (файл репозитория — размер/дата/`counts`,
  либо выбор файла на диске) + попап-**дифф** (§5.2): режим (`managed`/`bootstrap`), создать/обновить/
  **удалить**/заблокировано; (2) «Применить» — второе подтверждение (операция пишет в БД, включая
  удаления), затем попап-отчёт (§5.5).
- **`blocked`/`unmatched` непусты** → кнопка «Применить» неактивна, показывается причина (какая запись
  и на что ссылается) — удаление живого невозможно «в один клик».
- **Состояния:** нет файла в репозитории → кнопка импорта неактивна с подсказкой; ошибка → красный
  тост + причина в отчёте; успех → зелёный тост + числа.
- В карточке записи — поле `code` (**метка переноса, только чтение**, §3.3); у `categories` поля метки
  нет (там `code` — семантический).

## 8. Что уходит/осиротеет, риски, «один факт — одно место»

**Уходит / становится ненужным:**
- Константа `settlementFloorStageName` и резолв `default_settlement_type_id` **по имени** в сиде —
  заменяются резолвом **по метке записи-якоря** (снимает известный компромисс `seed_producers.go`).
- Класс B (data-миграции) как способ переноса **нового** контента больше не нужен: остаётся только
  для разовых структурных/переименовательных правок (включая §6).
- Отклонённая «минимальная защита v1» (warning о сиротах `effect_types`) — не нужна: импорт по метке
  находит эффект сам (§3.6).

**Риски и защита:**

| Риск | Защита |
|---|---|
| Полная замена сносит живое (запись не выгружена/потеряна при экспорте и её нет в файле) | Экспорт — **полный** снимок (не частичный), потеря возможна только от ошибки выгрузки; **сухой прогон/diff** (§5.2) показывает список удаляемых до применения; **бэкап `pg_dump` контентных таблиц** перед первым применением (шаг `DEPLOY.md`); удаление — только по метке |
| `ON DELETE CASCADE` у `deposits.good_id`/`settlement_branch_buffers.good_id` молча уносит объекты мира | Импорт **не удаляет** без явного предсчёта ссылок (§5.4); каскад как путь удаления не используется; любая ссылка → отказ |
| Удаляемая запись, на которую ссылается объект мира | Отказ импорта (409) с перечнем (таблица, метка, имя, род ссылки) — не «выборочное удаление» |
| Переименование в dev при сопоставлении по имени | Штатный режим — **по метке** (переименование безопасно); первичная накатка (§3.5) — по имени, но с ренейм-миграцией (§6) до неё и сухим прогоном; промежуточный «импорт по имени с удалением» **не выпускается** (§9) |
| Записи целевой БД без метки (расхождение бэкфилла) | `unmatched` + **отказ**; bootstrap — только на цели без меток вовсе |
| Импорт меняет `params`, а сироты/нормы чистятся в owner-проходе | транзиент назван (§5.5): расхождение карточки/сводки до первого owner-прохода |
| Импорт портит мировые FK | upsert не меняет `id`; дочерние наборы — листья; удаления — только с предсчётом ссылок |
| Гонка «импорт ↔ правка в студии» | единый `pg_advisory_xact_lock` каталога (`beginMutation`) + одна транзакция |
| Конкурентное чтение каталога игроком | `CatalogSnapshot` — REPEATABLE READ; импорт не блокирует чтение дольше транзакции |
| Ручка импорта доступна не тому | `auth.AdminAuth` (admin/skycomposer), как остальные ручки студии |
| Ошибка в имени/поле → часть ссылок «висит» | отказ всей транзакции + ошибка с местом (секция + метка) |
| `items.unlocks` хранит внутренние `id` (`000048`) — при дословном переносе чужие id уехали бы на прод | Снимок несёт `unlocks` **по метке/натуральному ключу** (§4); экспорт резолвит id → метку, импорт — обратно; элемент с `*_id` или нерезолвимой меткой → **отказ**, id в снимок не попадает |

**Риск-точки, требующие отдельной подписи создателя:** включение **полной замены** (И3, удаления на
проде необратимы без бэкапа); политика **первичной накатки** на непустую цель (§3.5, §12 В1); судьба
**ренейм-миграции** (§6, §12 В2); **бэкап `pg_dump`** перед первым применением как обязательный шаг.

**«Один факт — одно место».** Источник истины — **dev-БД**. Файл `content/catalog.json` — **артефакт
переноса** (сериализованный снимок), не второй источник: он не авторитетен, а воспроизводим из dev.
Сид остаётся **базовым слоем свежей БД**; контент создателя — слой поверх (импортом). Три места
(dev-БД ↔ файл ↔ прод-БД) сходятся после импорта; придумывать четвёртое (журнал/кэш) в v1 не нужно.

**12 инвариантов `GD_PROMPT`** фича не задевает — это операционка контента, не механика мира.

## 9. Итерации и чекпоинты

Порядок переопределён решениями гейта (полная замена + номерная метка): **метка — вперёд**, импорт —
после экспорта, полноценная замена — только там, где есть метка.

| И | Объём | Чекпоинт (готово, когда…) |
|---|---|---|
| **И1. Номерная метка + ренейм-миграция** | миграция колонок `code` (`goods`/`producer_types`/`items`/`effect_types`, частичный `UNIQUE`) + `SEQUENCE` на таблицу + бэкфилл существующих (по `id`) + сид с метками + поле метки в студии (только чтение); data-миграция `000083` (канон-имена для баз с маркером) | у всех контентных записей dev непустая уникальная метка; на свежей БД метки совпадают с dev; на копии dev-БД после `000083` имена класса/ступеней совпадают с сидом; `TestSeedSettlementFloorStageConstant` зелёный |
| **И2. Экспорт-снимок** | `GET /studio/api/content/export`, формат `content/catalog.json` (несёт метки; у `producer_types` — и `section`, §4), кнопка «Экспорт» | файл снимка генерируется из dev и диффом читаем; метки и `section` в файле совпадают с БД |
| **И3. Импорт с полной заменой** | `POST /studio/api/content/import` (+`dry_run`), сопоставление по метке, первичная накатка (§3.5), **удаление** по метке с защитой по мировым ссылкам, атомарность, отчёт, кнопка «Проверить → Применить»; `section` применяется **дословно, без строгого списка значений** (открытый список интерфейса; неизвестное клиент относит в «Прочее») | сухой прогон показывает дифф; повторный импорт того же файла = 0/0/0; прод-подобная БД становится точной копией dev; залежи/строения/поселения не пострадали; удаление живой записи невозможно (отказ) |

**Без метки полная замена включать нельзя** — поэтому И3 не выпускается раньше И1; промежуточной
(«импорт по имени с удалением») **не существует**. И1+И2 полезны сами: вытаскивают работу создателя
из dev-БД в репозиторий и фиксируют канон ещё до первого удаления.

**Тесты (для `@developer`/`@tester`):**
- T1 (И1): бэкфилл даёт непустые уникальные метки; повторный прогон идемпотентен; на свежей БД из
  сида метки совпадают с dev.
- T2 (И2): экспорт несёт метки; повторный экспорт того же состояния даёт тот же состав (отличия —
  только `generated_at`).
- T3 (И3): экспорт → импорт в **пустую** БД даёт тот же контент (по метке + состав рецептов).
- T4 (И3): повторный импорт того же файла — 0 created / 0 updated / 0 deleted (**идемпотентность**).
- T5 (И3): запись, удалённая в целевой БД, восстанавливается импортом.
- T6 (И3): ссылки резолвятся (`recipe_components` → `goods`; `producer_types.parent`; `producer_recipes`;
  `producer_slots.category`; `producer_items.item`).
- T7 (И3): после импорта `default_settlement_type_id` указывает на **ту же запись-якорь**, что в
  источнике (резолв по метке) — а не «на ступень-пол».
- T8 (И3, **полная замена**): запись, которой нет в файле и на которую **не** ссылаются объекты мира,
  **удаляется**; запись, на которую ссылаются (поселение/строение/залежь), **блокирует импорт** —
  отказ, БД не изменена.
- T9 (И3, **dry_run**): дифф совпадает с фактическим результатом применения; при `dry_run` БД не изменена.
- T10 (И3, **первичная накатка**): на цели без меток записи сматчиваются по имени, метки впечатываются,
  `id` сохранены; при наличии любой метки bootstrap запрещён.
- T11 (И3, **unmatched**): запись целевой БД без метки → отказ с перечнем (не молчаливое удаление/создание).
- T12 (И3, **атомарность**): ошибка в файле/блок удаления → откат, БД не изменилась.
- T13 (И3, тождество): переименование записи в источнике (та же метка) обновляет **ту же** запись
  (без сироты и без нового `id`).
- T14 (И1, миграция `000083`): идемпотентна; `settlements.settlement_type_id` после неё цел.
- T15 (И2/И3, **`unlocks`**): экспорт пишет `unlocks` по метке/ключу (`producer` = `code`, `category` =
  `(kind, name_norm)`), не по `id`; импорт в базу с другими `id` даёт ссылки на **локальные** записи;
  элемент с `producer_type_id`/`category_id` или нерезолвимой меткой → отказ (не молчаливый пропуск).

## 11. Кандидат ГД-сущности (предложение, вне текущих чисел)

**Вопрос:** нужна ли товару **марка (товарный знак)** — устойчивая производственная идентичность
(кто/где выпустил), влияющая на качество, цену и контракты?

**Ответ:** эталон не задан (2026-09-24) — открытый вопрос. Кандидат: марка — запись справочника (ещё
один **контент**, переносимый тем же механизмом), а один рецепт у разных владельцев даёт разные марки;
игрок видит «Очищенная вода, марка Колонии X», марка несёт репутацию/тир и участвует в контрактах.
**В счётчик эталонов (`docs/gamedesign/faq_counter.md`) не входит** (это кандидат роадмапа, не эталон
физики/мира). В текущие числа и в объём И1–И3 не входит.

**Кандидат 2 — журнал переноса контента (лог импорта/экспорта).**

**Вопрос:** нужен ли **журнал переносов** — запись «кто/когда/из какого файла/что создано-изменено-
**удалено**», видимая оператору?

**Ответ:** эталон не задан (2026-09-24) — открытый вопрос. Природа — **лог** (результат-состояние
операции), владелец — **многие** (каждый прогон импорта — запись), расширяемость — да (второй тип
записи: экспорт, откат). Кандидат: таблица записей с типом операции и диффом, у **удалений** — причина
и результат guard'а (§5.4). В v1 **не вводится** (§1.4): сухой прогон + отчёт (§5.2/§5.5) закрывают
потребность; журнал нужен, когда переносов станет много и потребуется аудит «что пропало и когда».
**В счётчик эталонов не входит** (кандидат роадмапа); в текущие числа и объём И1–И3 не входит.

### 12.2. Осталось открытым (к создателю)

1. **Первичная накатка на непустую цель при расхождении меток (§3.5).** *Предложение по умолчанию:
   **отказ** — если в целевых контентных таблицах есть хоть одна непустая метка (не совпадающая при
   этом с файлом), bootstrap запрещён, импорт возвращает `unmatched` и не меняет БД. Одноразовое
   сопоставление по имени (bootstrap) разрешаем **только** на цели без меток вовсе + сухой прогон +
   подтверждение. Цена альтернативы (разрешить bootstrap на частично размеченной цели) — риск
   смешать два тождества.*
2. **Судьба ренейм-миграции `000083` под полную замену (§6).** *Предложение по умолчанию:
   **оставить** в И1 (до меток) — она нужна первичной накатке/бэкфиллу (сопоставление по именам) и
   закрывает окно «прод задеплоен раньше первого импорта». Альтернатива — убрать (импорт перекрывает
   её), но тогда прод до первого импорта несёт старые имена.*
3. **Метка у `categories` (§3.4).** *Предложение по умолчанию: **не вводить** (у таблицы уже есть
   семантический `code`; смешивать два смысла в одном поле нельзя), идентичность — `(kind, name_norm)`.
   Альтернатива — отдельное поле метки у `categories` ради единообразия; цена — второе поле, дублирующее
   смысл.*
4. **Бэкап перед первым применением (§8).** *Предложение по умолчанию: **да, обязательный шаг** —
   `pg_dump` контентных таблиц прод-БД перед первым «Применить» (и перед каждым, где дифф содержит
   удаления); шаг в `docs/DEPLOY.md`. Цена — ручная операция на прод-стенде.*

**Решения дизайнера (косметика/механика, не на гейт):** формат — JSON, файл `content/catalog.json`,
секции упорядочены топологически (§4); экспорт = скачивание + запись `content/catalog.json` в dev;
доступ — `auth.AdminAuth`; `@uidesigner` для v1 не нужен; журнала переноса в v1 нет (§11);
**атомарный режим импорта** (ошибка/блок → откат, §5.5) — следует из паттерна `beginMutation`;
**last-write-wins** и **удаление отсутствующего** — из решений 2/3 «прод = копия dev»;
**сухой прогон обязателен** в UI (кнопка ведёт двумя шагами, §5.2/§7); **`blocked`/`unmatched`
блокируют «Применить»** (§7); **каскад FK не используется как путь удаления** (§5.4);
**сид остаётся базовым слоем**, файл применяется поверх (§8).
