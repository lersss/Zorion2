## 0. Зачем (цель)

Создателю нужен инструмент: **админ прямо из игры ставит на планету любую структуру**
из дерева производителей (в т.ч. форпост — поселение), чтобы собирать сцены под
проверку механик, не гоняя массовую генерацию. Первый сценарий — поставить форпост
на планету без воды и прогнать цикл «привёз воду → поселение потребляет».
Отсюда: структура **сразу живая** (потребляет по своему типу) и у неё есть
**владелец** — норма мира, а не атрибут инструмента (канон `13_settlements.md` §13.2:
«у поселения есть владелец… владелец отвечает за снабжение»).

## 3. Модель данных (миграция `000082_structures_owner.sql`)

Третья таблица не вводится: пишем в два существующих носителя (§2.1).

### 3.1. `settlements` — владелец

```sql
ALTER TABLE settlements ADD COLUMN IF NOT EXISTS owner_type TEXT NULL;
ALTER TABLE settlements ADD COLUMN IF NOT EXISTS owner_id   UUID NULL;

-- Идемпотентность CHECK: ALTER TABLE ... ADD CONSTRAINT IF NOT EXISTS в PG НЕ существует (M1) —
-- проверяем pg_constraint по имени.
DO $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = 'settlements_owner_type_chk') THEN
    ALTER TABLE settlements ADD CONSTRAINT settlements_owner_type_chk
      CHECK (owner_type IS NULL OR owner_type IN ('player','faction','agent'));
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = 'settlements_owner_pair_chk') THEN
    ALTER TABLE settlements ADD CONSTRAINT settlements_owner_pair_chk
      CHECK ((owner_type IS NULL) = (owner_id IS NULL));
  END IF;
END $$;

CREATE INDEX IF NOT EXISTS idx_settlements_owner
    ON settlements (owner_type, owner_id) WHERE owner_id IS NOT NULL;
```

- Классы владельца — те же (`player`/`faction`/`agent`), что у `buildings.owner_type`:
  полиморфный владелец читается одинаково у обеих таблиц. **`owner_type` ≠ `active_effects.owner_type`**
  (`'settlement'`) — омоним, разводим в GLOSSARY §1 (M5, §12.4).
- Пара «оба или ни одного» держится CHECK; `owner_id` — без FK (полиморфный), как у `buildings`.
- Колонки **nullable — обязательное условие** (Г1): существующие поселения остаются без владельца,
  `NULL` легален и штатен; чтение и витрина его обрабатывают (§10.3/§10.2). **Бэкфилла в миграции нет.**

### 3.2. `buildings` — связь с деревом

```sql
ALTER TABLE buildings ADD COLUMN IF NOT EXISTS producer_type_id BIGINT NULL
    REFERENCES producer_types (id) ON DELETE RESTRICT;
CREATE INDEX IF NOT EXISTS idx_buildings_producer_type_id
    ON buildings (producer_type_id) WHERE producer_type_id IS NOT NULL;
```

- `RESTRICT` — как у `settlements.settlement_type_id` (миграция `000067`): тип в использовании
  удалить нельзя (студия отдаёт 409).
- Столицы (`building_type='capital'`) сохраняют `producer_type_id = NULL` (ничего не производит);
  `building_type` остаётся свободным ключом.

### 3.3. Что НЕ меняется

- `buildings`, `settlements` уже в `truncateTables` (`admin_universe.go`) — каскады чистки/пакмана
  работают; правок не требуется.
- `settlements` — данные вселенной; `producer_types` — каталог-контент (не чистится).

### 3.4. Владелец при генерации (Р8) — только новым поселениям (Г1)

**Кто проставляет владельца — генератор фракций, не генератор поселений.** Причина —
порядок: `GeneratePlanets` создаёт поселения (с `race_id` из региона), и только потом
`GenerateFactions` создаёт фракции (одна на расу) и столицы. На момент генерации поселений
фракций ещё нет — владельца взять неоткуда. Поэтому проход владельца живёт в джобе фракций,
рядом с `EnsureCapitals` (`internal/generator/faction/faction.go`).

Новый проход `EnsureSettlementOwners(since time.Time)`:

```sql
UPDATE settlements s
SET owner_type = 'faction', owner_id = f.id, updated_at = NOW()
FROM factions f
WHERE s.owner_id IS NULL
  AND s.created_at >= $1                        -- только поселения текущей генерации (Г1)
  AND s.race_id IS NOT NULL AND s.race_id <> ''
  AND f.race_id = s.race_id;
```

- **Скоуп — только новые поселения (Г1).** `$1` (`since`) — метка начала текущей генерации;
  её передаёт вызывающий (галактика/планеты), поэтому `created_at` поселений текущего прогона
  не раньше неё. **Легаси-поселения (в dev — 33 481, созданы прошлыми генерациями) имеют
  `created_at < since` и не трогаются:** остаются без владельца осознанно (решение создателя, Г1).
  Миграция `000082` их тоже не бэкфиллит.
- **Нет метки генерации** (джоб фракций перегнали отдельно, вне генерации) → проход
  **не выполняет `UPDATE`**: легаси-владельцы не появляются (Г1). Источник метки `since` —
  за @developer (§18, остаточный пункт 1).
- **Владелец нового поселения = фракция его расы.** Это ровно канон «одна фракция на расу»
  (`faction.go`: кандидат = поселение с этим `race_id` и `population > 0`) и решение 2026-09-21
  «единая фракция-заглушка не вводится».
- **Порядок для будущих галактик:** `GeneratePlanets` (поселения с расой) → `GenerateFactions`
  (фракции → `EnsureCapitals` → `EnsureSettlementOwners`). Идемпотентность: повторный прогон
  в рамках той же генерации добивает недостающее; легаси не затрагивает.
- **`race_id = NULL` (легаси/люди):** фракции для такой расы не создаётся — поселение остаётся
  `NULL`-владельцем (канон `settlements.race_id NULL = легаси/люди`).

## 4. Класс производителя: «поселение» vs «строение»

Структура создаётся по `producer_type_id`; сервер решает, **куда писать**, по **корню дерева**
типа (класс = корень `parent_id IS NULL`), а не по имени ступени.

- **Резолв корня — по данным, без имени (M4).** Единственный источник: якорь
  `generation_config.default_settlement_type_id` (`ResolveDefaultSettlementTypeID`, миграция `000075`)
  → рекурсивный обход `parent_id` вверх до корня. Тот же приём уже применяется в стадиях
  (`settlement_stage.go`, «rename-safe, по id, НЕ по name_norm»).
- **Fallback по `name_norm = 'поселение'` снят** (M4): имя может устареть/переименоваться, а якорь
  — контракт данных. Якорь не найден → **422** «класс типа не определён» (не молчаливая запись не туда).
- `root(type) == settlementRoot` → пишем в **`settlements`**; иначе → в **`buildings`**.

**Почему не колонка-маркер.** Класс выводим из `parent_id`; отдельная колонка дублировала бы дерево
(инвариант 10). Если понадобится маркер — дельта к спеке студии, не сейчас.

## 5. Создание структуры — API

### 5.1. `POST /admin/planets/{id}/structures`

Права — `auth.AdminAuth` (`admin`/`skycomposer`). Гейты мутаций вселенной — как у `AddDeposit`:
пакман крутится → **409**; `universeMutationMu.TryLock` не взят → **409** (проверка и действие атомарны).

```json
{ "producer_type_id": 152,
  "owner_type": "faction",          // player | faction | agent
  "owner_id": "<uuid>",
  "population": 1000 }              // только для класса «Поселение»; необязательно (§8)
```

Проверки (порядок): `producer_type_id` обязателен и существует → иначе 422; тип **не скрыт**
(`producer_types.hidden = false`) → иначе 422; **класс резолвится по якорю** (§4) → иначе 422;
`owner_type` ∈ {player,faction,agent} → иначе 422; `owner_id` непуст и **существует** в своей
таблице (`users` / `factions` / `npc_agents`) → иначе 422 (висячий владелец сломал бы плательщика ЧК2);
для класса «Поселение» `population` — по §8.

Запись (одна транзакция):

- **Поселение:** `INSERT INTO settlements (id, planet_id, population, population_exact, stability,
  computed_at, race_id, settlement_type_id, owner_type, owner_id, created_at, updated_at)`;
  `race_id = <раса региона планеты>` (Р9, §8), `settlement_type_id = producer_type_id`,
  `population_exact = population`, `computed_at = NOW()`.
- **Строение:** `INSERT INTO buildings (id, planet_id, building_type, owner_type, owner_id,
  producer_type_id, created_at, updated_at)`; `building_type = 'producer'` (§5.3).

Ответ — по образцу `AddDeposit` (клиент заменяет блоки карточки, без перезагрузки системы):
`{ "planet_id", "world_id", "created": {"kind":"settlement|building", "id", "type_name", "owner_name"},
"buildings": [...], "settlements": [...] }` — свежие блоки, как их отдаёт карточка
(`attachFactionsAndBuildings` + `attachSettlements`).
**`created.type_name` — запрошенная ступень** (то, что выбрал админ), **не** фактическая.
**Внимание (M6):** админ-путь карточки зовёт owner-проход, поэтому уже в ответе поселение может
стоять на **другой** ступени ладдеры (§9.3) и иметь добранные ветки. **Фактическую** ступень
клиент берёт из свежего блока `settlements[]` по `created.id` (Р15).

### 5.2. `GET /admin/planets/{id}/build-options` — данные формы (§11)

Права — `auth.AdminAuth`. Отдаёт `types`, `factions`, `default_owner`, `default_race`,
`population_fallback`; форма — §11. Реализация: рекурсивный CTE по `producer_types`
(корень каждого типа → класс/`target`), фильтр `hidden = false`, исключение класс-корня «Поселение»;
**порядок `types[]` — серверный, в порядке отображения** (§11).

### 5.3. `building_type` для созданных строений

Для строений инструмента `building_type = 'producer'` (грубое значение), **конкретный тип несёт
`producer_type_id`**; класс (фабрика/лаборатория/…) выводится из корня типа. Отдельные класс-ключи
(`factory`/… из §3.2 спеки фабрик) вводятся вместе с производством (релиз 2): до него у них нет
потребителя, а `name_norm`-маппинг был бы вторым источником истины.

## 6. Владелец — правила (Р13)

- Классы владельца — `player` / `faction` / `agent` (тот же CHECK, что у `buildings.owner_type`).
- **Инструмент требует владельца** (Р13): без владельца структуру через «Построить» не создать.
  Пункта «без владельца (NPC)» в форме нет.
- **Владелец — норма, а не исключение** (канон `13_settlements.md` §13.2, `GLOSSARY` §7):
  у новых сгенерированных поселений владелец — фракция расы (§3.4); `NULL` — у существующих
  поселений (Г1: не бэкфиллим) и у легаси `race_id = NULL`.
- Владельцем может быть **любая** реальная сущность класса, не обязательно привязанная к планете
  (фракция другой планеты, игрок, агент). Валидация — существование записи, не близость.
- Список для выбора — §11; фракции сервер отдаёт целиком (их ~29–60), игроков/агентов — поиском.

## 7. Типы для постройки и ступени поселения

- **Список — дерево** `producer_types` (`hidden = false`), **кроме класс-корня «Поселение»** (M3):
  корень — класс, не экземпляр, и не несёт норм (`params.eat`/`params.effects`) — его выбор создал бы
  «поселение без нужд» (живую заглушку). Ступени ладдеры (Аутпост → … → Экуменополис) и остальные
  классы/подтипы — выбираемы (7 ступеней).
- **Живые vs «заглушки»** — флаг `live` в `build-options`:
  - `live = true` — тип несёт нормы потребления (`params.eat` или `params.effects`), т.е. класс
    «Поселение»: есть население, нужды, эффекты, ветки, владелец; сценарий «привёз воду → потребляет» работает (§9);
  - `live = false` — остальные классы: строение создаётся с типом и владельцем, но **производства/буфера
    нет** (релиз 2). Форма честно помечает «механики производства ещё нет».
- **Ступень поселения — любая** (Р2). Выбранная ступень задаёт `settlement_type_id` и нормы
  `params.eat/effects` (§9). ⚠️ Ступень не «заморожена»: первый owner-проход может перевести поселение
  по населению (§9.3). Инструмент задаёт **стартовую** ступень и население (§8); расхождение осознанно (Р15).

## 8. Население, раса и стартовые значения поселения

- **Население задаёт админ** (поле формы, Р15). Правила однозначны (M2):
  - поле **не передано/пусто** → дефолт: `stage.enter` выбранной ступени, если `enter ≥ 1`, иначе **1000**
    (песочная заглушка под первый сценарий «форпост 500–1000 человек»; не калибровка);
  - передано и **`< 1`** (`0`, отрицательное) → **422** («население должно быть больше нуля»);
  - передано и `≥ 1` → берётся как есть.
- **Раса — по региону (Р9).** `race_id` создаваемого поселения = `regions.race_id` ближайшего региона
  мира планеты (`regionprofile.NearestRegionIndex(worlds.coord_x, worlds.coord_y, regions)` — тот же
  резолв, что у генерации планет/профилей). Регион без расы (`NULL`/пусто) → `race_id = NULL` (легаси/люди).
  **Не «люди по умолчанию»**, если регион даёт расу.
- Запись: `population = population_exact = <введённое/дефолт>`, `computed_at = NOW()`, `race_id` — §выше.
- `stability = 100` — песочная заглушка (сгенерированные стартуют 40–80). Пересчёт стабильности этой
  фичей не вводится; значение живёт до первой правки механикой стабильности. Помечено как некалиброванное.
- Для класса «Строение» население не задаётся (поля нет) — строения несут население с релиза 2.

## 9. Потребление и первый owner-проход (Р4)

### 9.1. Немедленное потребление

Р4 **не требует новой механики**: нужда поселения производна от `population × норма(позиция)` и типа
(`producer_types.params.eat/effects`), а пересчёт ленивый — на первом чтении карточки (owner-проход
`settlement_owner_pass.go`, спека `2026-09-24-потребление-по-товарам`). Созданное поселение с
`population > 0` и `settlement_type_id = <ступень>` на первом чтении получает нужду «жажда» («очищенная
вода») и «голод» («пища») по нормам своей ступени. Форпост без воды → дефицит → эффект «Жажда» →
гибель примерно через сутки (принятый риск).

**Условие корректности:** `computed_at = NOW()` (иначе owner-проход увидит отрицательный Δt и вернёт
`p0` без нужды) и `settlement_type_id` проставлен (иначе нормы по `DefaultEatK`).

### 9.2. Строения

Для **строений** (неживые классы) потребления нет — модель `buildings.data` отложена; Р4 к ним не
применяется (известная граница, не регресс).

### 9.3. Побочные эффекты первого персистентного прохода (M6)

Создание только пишет строку. Первый **персистентный** owner-проход (на первом чтении карточки)
выполняет переход стадии (`settlement_stage.go`), а он:

- **добор недостающих веток** набора новой ступени (`producer_recipes` с ≥1 заполненным компонентом;
  существующие/ручные ветки не удаляются; рецепт без компонентов пропускается);
- **очистку складов** веток (все буферы → 0);
- **сброс нагрузки** эффектов (`DELETE FROM active_effects WHERE owner_type='settlement' AND owner_id=…`)
  и корневую очистку сирот `active_effects` по типу эффекта;
- запись новой `settlement_type_id`.

Следствия для инструмента, называемые явно: (а) выбранная ступень может смениться уже в ответе
`POST` (§5.1); (б) у созданного поселения могут появиться ветки ступени; (в) эффекты/нагрузка
стартуют с чистого листа. Это не регресс, а нормальная работа стадий; учтено тестом T17 (§19).

## 10. Показ структур на планете

### 10.1. Новая вкладка «Строения» (Р11, Р14) — единая матрица видимости

- Вкладка «Строения» в карточке планеты: **все** `buildings` планеты (Р14, без фильтра по «живости»),
  включая столицы. Строка: имя типа (`type_name` по `producer_type_id`), владелец (`owner_name`),
  пометки: столица (`producer_type_id IS NULL`) — «не производит»; созданное строение с типом, но
  без рантайм-производства — «производство ещё не реализовано».
- Вкладка «Фракции» **не трогается**: строка столицы остаётся (контекст фракции). Дублирование строки
  столицы в двух вкладках — осознанно.
- **Видимость игроку — единая матрица (сведение противоречий §10.1–§10.3 прошлой ред.):**

| Режим | Поверхность | Поселения | Фракции | Строения | Новые поля (`type_name`/`owner_name`) |
|---|---|---|---|---|---|
| `none` (знания нет) | — | — | — | — | — |
| `scan` (знание без снимка) | ✅ | счётчик | ✅ (как сегодня, §2.2 спеки 2026-09-23) | ✅ (как сегодня) | ✅ (внутри строений) |
| `snapshot` | из снимка | из снимка, без эффектов/лога | из снимка | из снимка | из снимка (заморожено) |
| `presence` | ✅ | полные | ✅ | ✅ | ✅ |
| admin/skycomposer | всё | всё | всё | всё | всё |

  Правило одно (**Г2**): **новые поля (`type_name`, `owner_name`) живут внутри блоков
  `buildings`/`settlements` и уходят ровно тогда, когда уходят сами блоки** — значит видны игроку
  при `presence`/`snapshot` (как сами поселения/строения) и не отдаются в `scan`/`none` (поселений
  в ответе нет; без знания `Buildings`/`Factions` обнулены). Точки очистки названы явно (§10.4).
  Именно `scan` (где `p.Buildings`/`p.Factions` остаются, а `p.Settlements = nil`) и создавал
  противоречие прошлой ред.

### 10.2. Владелец в карточке поселения

- Строка «Владелец: <имя>» в карточке поселения. Присутствие/снимок — **показывается игроку** (Г2:
  это часть «полных данных присутствия», GLOSSARY §1; как и само поселение); `scan`/`none` — поселений
  в ответе нет, значит нет и строки. `NULL` (существующее/легаси поселение, Г1) → **«NPC (без владельца)»**.

### 10.3. Дельта моделей/репозитория (для @developer)

- `models.PlanetBuilding`: +`ProducerTypeID *int64` `json:"producer_type_id"` (**без `omitempty`** —
  у столиц эмитится `null`, чтобы метка «не производит» отличалась от «поля нет»), +`TypeName string`,
  +`OwnerName string`.
- `models.Settlement`: +`OwnerType string`, +`OwnerID string`, +`OwnerName string`.
- `attachFactionsAndBuildings` — `LEFT JOIN producer_types` (имя типа) + пакетный резолв имени владельца;
  `attachSettlements`/`loadSettlements` — чтение `owner_type`/`owner_id` + резолв имени владельца.
  Имя резолвится **пакетно** (users.username / factions.name / npc_agents.name) — не по строке на
  запись (инвариант 2).
- **`NULL`-владелец (Г1) не должен ронять чтение.** `settlements.owner_type/owner_id` nullable:
  скан через `COALESCE(owner_type, '')`/`COALESCE(owner_id, '')` (или `sql.NullString`) — прямое
  `Scan` в `string` на `NULL` падает. Пустой владелец → витрина «NPC (без владельца)» (§10.2), не ошибка.
- **Снимок:** `PlanetBuilding` в снимке — та же структура, новые поля проезжают **автоматически**
  (аддитивно; старые снимки без полей десериализуются в пустые). **Но поселения снимка — отдельная
  структура `snapshotSettlement`** (`knowledge_repository.go`): владелец **не проезжает сам** —
  добавить `OwnerName string` `json:"owner_name"` (замороженный) и заполнять в `buildPresenceSnapshot`;
  иначе игрок в `snapshot` увидит поселение без владельца (Г2).

### 10.4. Где именно чистятся новые поля (явно)

- `stripPlanetDetails` (`planet_visibility.go`): ветка `default` при `view == nil` (`none`) уже
  обнуляет `p.Buildings`/`p.Factions` — новые поля (`type_name`/`owner_name`) уходят вместе с ними;
  `p.Settlements = nil` во всех `scan`/`none` — владелец поселения не течёт. `scan` (`view != nil`)
  оставляет `p.Buildings`/`p.Factions` — поведение канона 2026-09-23 §2.2, **не менять**.
- `playerSettlements` (presence) — **не** вычищает `owner_*` (владелец показывается игроку при
  присутствии, §10.2/Г2); в режиме без арифметики владелец остаётся.
- `stripSnapshotSettlementSecrets` — работает с поселениями снимка; владелец приходит из
  `snapshotSettlement.OwnerName` (заморожен), живой резолв не подставляется.
- `GET /admin/.../build-options` и `POST /admin/.../structures` — `auth.AdminAuth`, игроку не отдаются.

## 11. Интерфейс — вход для `@uidesigner` (обновлено под Р11–Р15, Г1–Г4)

Внешний вид и взаимодействие — за `@uidesigner`. Контракт данных и рамки:

**Кнопка (Р12).** «Построить» — в **шапке карточки планеты** + открывает **панель** формы. Видна только
`isAdmin()` (`admin`/`skycomposer`). Если при вёрстке окажется тесно — место переносится (создатель:
«ок, если что перенесём»).

**Форма (данные из `GET /admin/planets/{id}/build-options`):**
1. **Тип структуры** — дерево/селект по `types`, сгруппировать по `class_name`; ступень поселения —
   внутри класса «Поселение»; у `live=false` — пометка «производство ещё не реализовано».

3. **Население** — числовое поле, только для `target="settlement"`; префилл — `stage.enter` выбранного

4. Кнопка «Построить» → `POST /admin/planets/{id}/structures`.

`planet.buildings`/`planet.settlements` и перерисовываем вкладку: поселение → «Поселения», строение →
«Строения». Показать строку результата (имя типа, владелец, ступень **фактическая** — берётся из
свежего `settlements[]` по `created.id`; `created.type_name` — **запрошенная** ступень, ступень могла
смениться owner-проходом, §9.3). Строка статуса/ошибки — текстом (образец: «добавить залежь»);
422 — понятное сообщение: «тип скрыт», «владелец не найден», «класс не определён», «население > 0».

**Вкладка «Строения» (Р11, Р14).** Список всех `buildings` планеты (включая столицы): имя типа,
владелец, пометки «не производит» / «производство ещё не реализовано». Клик по строке — раскрытие
владельца (как у строки столицы во «Фракциях»).

**Строка владельца в карточке поселения.** «Владелец: <имя>»; `NULL` → «NPC (без владельца)».

**Контракт `build-options` (ответ на запрос `@uidesigner`):**

```json
{
  "planet_id": "<uuid>",
  "types": [
    { "id": 152, "name": "Аутпост",
      "class_id": 148, "class_name": "Поселение",
      "target": "settlement",                 // settlement | building
      "stage": { "enter": 0 },                // null, если типа нет в ладдере
      "live": true }                          // true = есть params.eat/effects
  ],
  "factions": [
    { "id": "<uuid>", "name": "Люди", "type": "Корпорация", "color": "#ff6b6b" }

  "default_owner": { "owner_type": "faction", "owner_id": "<uuid>", "name": "Люди" },
  "default_race": { "race_id": "humans", "race_name": "Люди" },

```

- `types[]` — **сервер отдаёт в порядке отображения** (группы как в дереве, внутри «Поселения» —
  по возрастанию `stage.enter`); клиент не сортирует.
- `factions[]` **несёт `color` и `type`** (обе колонки есть в `factions`: `type`, `color`) — UI может
  красить строку владельца.
- `default_owner` — **фракция расы региона планеты** (Р8/Р9), не «фракция этой планеты» как прежде;

- **UI не нужны** (можно не отдавать): `types[].kind`, `stage.exit`,

- Метка «не производит» — по `producer_type_id IS NULL` в **списке строений** (§10.1), не в `types`.

**`GET /admin/owner-candidates?type=player|agent&q=&limit=50`** — поиск владельца:
`{ "items": [ { "id": "<uuid>", "name": "<username|имя агента>", "subtitle": "игрок|агент" } ] }`,

панель, форма «тип/владелец/население», вкладка «Строения», строка владельца) и вернуть: (1) каких полей

ЧК1 даёт владельца-актора (фракция/игрок/агент) — кандидата в плательщики; **кто и как платит по
контрактам — ЧК2 (§17)**, отдельная спека. ЧК1 в эту механику не входит (Г3).

### 12.4. `GLOSSARY` §1 «Многозначные слова» — развести омоним `owner_type` (M5)

`buildings.owner_type` / `settlements.owner_type` = **домен владельца-актора** (`player`/`faction`/`agent`);
`active_effects.owner_type` = **домен владельца эффекта** (`'settlement'`). Разные смыслы — добавить
строку в §1. Дельта — `@designer`/`@dispatcher` (владелец GLOSSARY).

### 12.5. `13_settlements.md` §13.4 «владелец еду не поставляет» — формулировка разницы (Г4, принята)

Канон §13.4: «рабочие покупают еду сами; владелец фабрики еду не поставляет». Контракт на снабжение
этому **не противоречит**: контракт — **оплата завоза**, а не выдача пайка. Владелец платит
перевозчику за доставку товара (воды/пищи) на планету/в буфер; товар попадает в обычный оборот
(покупка/потребление по правилам §13.4). Формулировка (решение создателя Г4, 2026-09-24): **«владелец
финансирует логистику, но не кормит рабочих напрямую — еда остаётся товаром на бирже/в буфере»**.

## 15. Кандидат новой ГД-сущности (+1, правило создателя)

не входит** (анти-двойной учёт); в этой спеке — только кандидат, реализация вне объёма.

## 17. ЧК2 — контракты: владелец поселения как заказчик/плательщик (задел, отдельная спека)

Р10/Г3 переносят сюда «владелец-поселение платит по контрактам на снабжение». **ЧК1 не блокируется.**
Что нужно для ЧК2 (коротко, для дизайна отдельной спеки):

- **Схема автора.** `contracts.author_type` CHECK сегодня = `player`/`faction`/`building`/`agent`
  (`models.ContractActor*`). Добавить `settlement` (`ContractActorSettlement`); `author_id` = `settlements.id`.
- **Интерфейс «владелец поселения → плательщик контракта».** `resolvePayerAccountQ`
  (`contract_repository.go`) при `author_type='settlement'` читает `settlements.owner_type/owner_id`
  и резолвит счёт владельца (владелец ∈ `player`/`faction`/`agent`, глубина 1). `owner_id IS NULL`
  (легаси-поселение без владельца, Г1) → `ErrPayerUnresolved` (поселение не может быть заказчиком, пока
  владельца нет).
- **Планета публикации.** `resolvePublicationPlanet` для автора-поселения → `settlements.planet_id`.
- **Доска нужд.** `boardNeedsFor` (форма нужды из `needs_layer` §11 / И4) — поселение-заказчик
  публикует заказ на снабжение (вода/пища) на доске своей планеты.
- **Эскроу.** Залог — со счёта владельца (`money_account`).
- **Чего ЧК2 не делает:** не вводит счёт-поселение (поселение не кошелёк; платит владелец) и не
  меняет механику контрактов.

## 19. Критерии приёмки (TDD, до кода — красные)

- **T1** `POST /admin/planets/{id}/structures` без прав (player) → 403.
- **T2** Скрытый тип (`hidden=true`) → 422.
- **T3** `owner_type` вне {player,faction,agent} → 422; `owner_id` несуществующий → 422.
- **T4** Поселение: строка `settlements` с `settlement_type_id`, `owner_type/owner_id`,
  `population=population_exact`, `computed_at≈NOW`, `race_id = раса региона планеты` (Р9; регион без расы → NULL).
- **T5** Строение: строка `buildings` с `building_type='producer'`, `producer_type_id`, владельцем.
- **T6** Класс «Поселение» резолвится по корню **от якоря `default_settlement_type_id`** (M4); якорь
  не найден → 422. Fallback по `name_norm` не используется (проверка: переименование типа не ломает резолв).
- **T7** Гейты мутаций: пакман/`universeMutationMu` занят → 409, ничего не создано.
- **T8** Ответ несёт свежие `buildings`/`settlements` + `created` планеты (формат карточки);
  `created.type_name` = **запрошенная** ступень; фактическая ступень читается из `settlements[]` по `created.id`.
- **T9** Р4: созданное поселение с `population>0` на первом чтении получает нужду/эффект (owner-проход;
  тест с инъекцией `now`, без реального Δt — PITFALLS «тест ленивого пересчёта»).
- **T10** `build-options`: типы с `target`/`live`/`stage`/`class_name`; скрытые не отдаются;
  **класс-корень «Поселение» отсутствует** (M3); **порядок — группы дерева, внутри «Поселения» по
  `stage.enter`**; `factions` c `color`/`type`; `default_owner`/`default_race` — ключи **всегда**
  (`null` при отсутствии); `population_fallback`.
- **T11** Миграция `000082` идемпотентна (повторный прогон/`IF NOT EXISTS` + `DO $$` для CHECK, M1);
  `settlements.owner_*` — пара или NULL (CHECK); `buildings.producer_type_id` FK RESTRICT (удаление типа
  в студии → 409); **бэкфилла нет** — после миграции существующие поселения остаются `owner_id IS NULL` (Г1).
- **T12** Показ: вкладка «Строения» рисует **все** `buildings` (Р14) с именем типа и владельцем;
  без знания — «нет данных» (§10.1 матрица); столица видна и во «Фракциях».
- **T13** Каскады: `TRUNCATE planets` не падает; снимок не теряет `type_name`/`owner_name`
  (в т.ч. `snapshotSettlement.owner_name` — §10.3).
- **T14** Р8/Г1: `EnsureSettlementOwners` проставляет владельца-фракцию поселению текущей генерации
  (`created_at >= since`) и **не трогает легаси** (`created_at < since` — остаётся NULL); повторный
  прогон идемпотентен; нет метки `since` → проход не выполняет `UPDATE`.
- **T15** M2: `population` пусто → дефолт `stage.enter`/1000; `0`/отрицательное → 422; валидное — как есть.
- **T16** §10.1 матрица: `none` → `Buildings`/`Factions`/`Settlements` пусты; `scan` → `Buildings`/`Factions`
  есть, `Settlements` пуст; `presence`/`snapshot` → `owner_name`/`type_name` присутствуют (у снимка — замороженные).
- **T17** M6: первый owner-проход после создания поселения с выбранной ступенью применяет переход
