## 0. Резюме (одним абзацем)

Создатель ставит форпост туда, где воды нет, и снабжает его по контракту; но сказать «нужна
именно вода» сегодня **нельзя** — позиция потребления (`params.eat`/`params.effects`) ключуется
**категорией** справочника, а «Очищенная вода» лежит в «продовольствии» рядом с едой. Спека
меняет **ключ позиции** на **товар** (`goods.name_norm`): категория как ключ **снимается**
(решение создателя 2026-09-24, О2), пилот «голод» мигрирует с категории «продовольствие» на
товар «пища». Нужда = **одна позиция** (тип эффекта); формула покрытия/дефицита остаётся
**сегодняшней** (`w = 1 − покрытие/спрос`) — ничего не переписывается. Альтернативы («1000 воды
**или** 500 соков», покрытие = Σ долей) вынесены в **будущее расширение** (§7.5), в текущий
объём не входят. Для воды заводится **свой эффект «Жажда»** (свой текст гибели), норма
`20 000 000` ед/сутки/млрд. Нужда включается на **всей ладдере** ступеней, и пока цепочка
(лёд/доставка/контракты/темп пары) не готова — поселения будут гибнуть от жажды; это
**осознанный принятый риск** создателя (§6.4). Код не пишется; §17 — вопросы.

## 1. Цель и скоуп

**Цель.** Дать модели потребности выразить «нужна вода» — чтобы мини-луп создателя («форпост без
воды ← лёд в поясе ← трюм ← контракт») имел работающий триггер дефицита и понятную форму нужды
для доски поставки.

**В скоупе:**
1. **Ключ позиции потребления = товар** (`goods.name_norm`); категория как ключ **снята**.
2. **Совместимость и миграция** старых записей (категорийные ключи → товарные; §6).
3. **Каскад стадий**: нужда живёт на **всей ладдере** ступеней (иначе форпост «перестаёт пить»
   на пороге 1000 чел), миграция по классу, а не по списку имён (§6.3).
4. **Влияние на слой эффектов**: эффект **«Жажда»**, причина гибели (`DeathCause`), `source_position`.
5. **Студия**: селект «Потребляет» = товары; валидация/предупреждения.
6. **Витрина арифметики** (дельта к И2.3): строки по позициям + строка нужды (покрытие %).
7. **Форма нужды для команды контрактов** (интерфейс, не реализация доставки).
8. **Числа**: норма воды для «Аутпоста» (`20 000 000`) — гипотеза к калибровке.
9. **Impact map** (§13).

**Вне скоупа (явно, делают другие / будущее):**
- **альтернативы и Σ долей** — **будущее расширение** (§7.5), в текущий объём не входят;
- добыча льда в астероидах (создатель) и цепочка «лёд → вода» (`2026-09-24-ледяные-астероиды-вода.md`);
- контракты поставки, **доставка** и **зачёт привезённого** (другая команда) — здесь только форма нужды;
- трюм/модули кораблей (создатель);
- «местное покрытие планеты» и «склад» как источники покрытия (точки подключения, §11.3);
- рынок/перевозка между поселениями, найм, тиры.

## 4. Разворот подходов — пространство решений (история выбора)

Классы **разные**, не вариации одного. Цена — по GD_PROMPT (чем платим и как ломается).
Выбор сделан создателем 2026-09-24 (О2): **К1 без категории-сахара**, альтернативы — будущее.

### К1. «Позиция = товар; нужда = позиция с типом эффекта» — **ПРИНЯТ**
Ключ `params.eat`/`params.effects` → `goods.name_norm`. Товар с одним эффектом = одна нужда.
- **Цена:** один товар — одна нужда (ограничение вытекает из карты ключей); «любой товар
  категории» больше не выразить (О2 — сознательно).
- **Плюс:** **ноль новых сущностей, таблиц и ключей**; формула **тождественна** сегодняшней
  (§7) → пилот «голод» не переезжает по числам; студия — тот же блок «Потребляет».
- **Отказ:** нет стабильного имени нужды, независимого от эффекта; две нужды не могут делить эффект.

### К2. «Явная сущность нужды» (`params.needs` или таблица `need_options`)
Нужда = именованная запись с позициями `[{товар, норма}]` и опциональным эффектом.
- **Плюс:** стабильное имя нужды для контрактов и `source_position`; нужда без эффекта; две нужды —
  один эффект; один товар — две нужды.
- **Цена:** новая структура/таблица + миграция + второй словарь к синхронизации; вторая форма
  редактора в студии. **Путь роста** (§17 В3) — пока нужд единицы.

### К3. «Нужда по свойству товара» (`goods.props.need_value`)
Поселение объявляет нужду **тегом**; товар несёт коэффициент закрытия.
- **Плюс:** новый питьевой товар закрывает нужду **всем** поселениям без перенастройки.
- **Цена:** непрямота (создатель сказал «товар», не «свойство»); обслуживание тегов; второй словарь
  «нужда → тег». Как надстройка над К1 возможна позже.

### К4. «Приоритетные альтернативы» (ИЛИ с порядком, «любой закрывает целиком») — **отклонён**
Разрывность (999 воды + 499 соков = не покрыто), произвольный порядок в данных. Отнесён к
будущему обсуждению альтернатив (§7.5).

### К5. «Решить каталогом» (фиктивная категория «Питьевая вода») — **отклонён**
Категория — **контент**, а не механика; альтернативы не выражает; хрупко.

## 5. Решение (суть)

1. **Позиция = товар.** Ключ `params.eat`/`params.effects` — `goods.name_norm` (не `goods.id`:
   JSONB-ключ — строка; FK в JSONB невозможен и не нужен). `goods.id` резолвится на выходе
   (нужда для контрактов, §11).
2. **Категория как ключ — не допустима** (О2). Ключ, не совпавший с `goods.name_norm`, —
   `position_unknown` (WARN, привязка no-op), как сегодня для неизвестных ключей.
3. **Нужда = тип эффекта; сегодня — одна позиция на нужду.** Группировка позиций по эффекту в
   коде остаётся (механизм не удаляем), но контент объявляет по одной позиции на эффект.
4. **Покрытие и дефицит — сегодняшняя формула:** `coverage = p_K` (скорость, батч/сек),
   `w = clamp01(1 − coverage/D)`, `D = PerSecond(норма, P)` (§7.3). Ничего не обобщается.
5. **Позиция-товар закрывается только своим товаром** (точное совпадение `goods.name_norm`
   товара-выхода ветки). «Привезённый товар» закрывает нужду, когда попадает в источник покрытия
   (§11.3) — сегодня это только выход ветки.
6. **Числа** (Р7/О5): «Аутпост» получает позицию **«очищенная вода»** с нормой `20 000 000` и
   эффект **«Жажда»**; «голод» мигрирует с категории «продовольствие» на товар **«пища»** (§6.2).
7. **Альтернативы** («или» + своё количество) — **будущее расширение** (§7.5), не проектируется здесь.

## 6. Совместимость и миграция

### 6.1. Разрешение ключа (единственное правило)

```
ключ K (строка params.eat/effects) →
  1) есть товар с goods.name_norm = K   → позиция-ТОВАР {K}
  2) иначе → позиция НЕИЗВЕСТНА: WARN `position_unknown`, привязка — no-op (как сегодня)
```

- **Категория больше не разрешается** (О2) — прежний шаг «иначе категория → сахар» **снят**.
- **Коллизия «и товар, и категория»** перестаёт существовать как класс: ключ читается **только**
  как товар; при совпадении строки с именем категории — это по-прежнему позиция-**товар**, а если
  товара с таким именем нет — `position_unknown` (категория не подставляется).
- **Отвергнуто:** префиксные ключи (`"g:очищенная вода"`) — миграция всех ключей, уродливы в UI;
  **отдельные карты** (`params.good_eat`) — второй словарь к синхронизации.

### 6.2. Старые записи — миграция категорийных ключей в товарные

Проверено 2026-09-24 на dev-БД: тип с `params.eat` **один** — «Аутпост» (`id=148`):
`eat={вода:600, пища:600, продовольствие:600}`, `effects={продовольствие: голод}`, `stage={enter:0}`,
`eat_units=per_day_per_billion`. Категория «продовольствие» (`categories.id=7`, kind=good) содержит
**три** товара: «Пища» (`378`), «Бытовая техника» (`414`), «Очищенная вода» (`422`).

| Ключ | Сегодня | После правила §6.1 | Действие миграции |
|---|---|---|---|
| `продовольствие` | категория, живая привязка «голод» | категория — **не позиция** | **заменить на товар «пища»** (378): `effects.пища = голод` |
| `вода` | категория (kind=**resource**), мёртвый ключ | не позиция | **удалить** (О6) |
| `пища` | мёртвый ключ (`eat.пища` без `effects.пища`) | **живой** ключ-товар | **сохранить** — цель миграции категории; норма 600 переиспользуется |

**Почему именно «Пища» (378), а не остальные товары категории:**
- «Очищенная вода» (422) уходит в **отдельную** нужду **«жажда»** (свой эффект, О3) — не в «голод»;
- «Бытовая техника» (414) — каталогная случайность (товар в категории «продовольствие»),
  закрывать ею голод нельзя; категорийный «сахар» ранее позволял это молча — ещё один довод за снятие.

**Результат миграции (целевые `params` — единые для всей ладдеры, §6.3):**
`eat = {"пища": 600, "очищенная вода": 20000000}`,
`effects = {"пища": "голод", "очищенная вода": "жажда"}`, `eat_units = "per_day_per_billion"`.

**О6 применяется так:** удаляется только **«вода»**; **«пища» не удаляется** — она перестаёт быть
мёртвой, став живым ключом нужды «голод» (цель миграции категории). Это названное применение
буквального решения создателя (см. В12).

> **Названное следствие.** Целевые `params` задаются **на всех семи ступенях** (§6.3), поэтому нужда
> «голод» тоже расширяется на всю ладдеру (раньше жила только на «Аутпосте»). Если создатель захочет
> оставить «голод» только на «Аутпосте», а на верхние ступени поставить лишь «жажду» — SQL и сид
> правятся точечно; вынесено в **В14** (рекомендация — единые `params`, как ниже).

**Две точки, иначе пилот молча no-op** (урок `000070`, finding 1/9):
1. **Go-сид** (`internal/goodsstudio/seed_producers.go`) — для свежей БД: целевые `params` задаются
   **на всех семи ступенях ладдеры**, а не только на «Аутпосте» (иначе T16 «сид ↔ миграция» не сходится).
2. **Data-миграция** — для существующих БД (сид пишет `ON CONFLICT DO NOTHING` и строку **не
   обновит**): **слиянием объектов-обёрток**, не `params || '{"eat": …}'` (затирает **весь** `eat` —
   урок `000070`). Плюс строка каталога `effect_types` («Жажда», §8.2) — `ON CONFLICT (name_norm) DO NOTHING`.
   **Строка в миграции — не доказательство:** проверять на живой БД (правило PITFALLS).

**SQL миграции `000079` (черновик; покрывает ВСЮ ладдеру — предикат класса, не список имён).**
Резолв ступеней — **по данным** (правило спеки стадий §4.3 «данные, не имя»): `params ? 'stage'` +
`parent_id` типа-родителя «Поселение». **Имена семи ступеней в предикате не участвуют** — иначе
пропущенный «Мегаполис» (152) выпал бы (§6.3). Вложенные `eat`/`effects` собираются слиянием `||`
с объектом-обёрткой (`jsonb_build_object`), **не** `jsonb_set` (урок `000070`: `jsonb_set` по
отсутствующему промежуточному объекту — молчаливый no-op).

```sql
-- 1) Эффект «Жажда» — общая кривая 'hunger' (О3, §8.2); идемпотентно.
INSERT INTO effect_types (name, name_norm, impact, params)
VALUES ('Жажда', 'жажда', 'population_rate', '{"curve": "hunger"}')
ON CONFLICT (name_norm) DO NOTHING;

-- 2) Целевые params — на ВСЕЙ ладдерe класса «Поселение» (7 ступеней).
--    Предикат класса: params ? 'stage' AND parent_id = id типа-родителя «Поселение».
--    Ключи: категория «продовольствие» → товар «пища» (378); мёртвый ключ «вода» —
--    удаляется (О6); добавляется товар «очищенная вода» (422) + эффект «жажда».
WITH ladder AS (
    SELECT id FROM producer_types
    WHERE params ? 'stage'
      AND parent_id = (SELECT id FROM producer_types WHERE name_norm = 'поселение')
)
UPDATE producer_types pt
SET params = COALESCE(pt.params, '{}'::jsonb) || jsonb_build_object(
      'effects', COALESCE(pt.params->'effects', '{}'::jsonb)
                 - 'продовольствие'
                 || jsonb_build_object('пища', 'голод', 'очищенная вода', 'жажда'),
      'eat',     COALESCE(pt.params->'eat', '{}'::jsonb)
                 - 'вода' - 'продовольствие'
                 || jsonb_build_object('пища', 600, 'очищенная вода', 20000000),
      'eat_units', 'per_day_per_billion')
FROM ladder
WHERE pt.id = ladder.id;
```

**Идемпотентность:** повторный прогон снимает те же ключи и пишет те же значения; `ON CONFLICT DO
NOTHING` — для `effect_types`. Тип-родитель резолвится по `name_norm = 'поселение'` (стабильный
корень класса из `000077`) — **не** по именам ступеней.

### 6.3. Каскад стадий: нужда живёт на КАЖДОЙ ступени ладдеры

**Факт кода.** Нужда рождается только там, где есть `params.effects` (`buildBindings` идёт строго по
`EffectsByPosition`); `DefaultEatK` — фолбэк **нормы**, но **не** создаёт привязку. Проверено на
dev-БД: `params.eat`/`effects` есть **только** у «Аутпоста» (148).

**Ладдера на dev-БД — СЕМЬ ступеней** (резолв **по данным**, не по именам — правило спеки стадий
§4.3 «данные, не имя»): предикат класса `producer_types.params ? 'stage' AND parent_id =
(SELECT id FROM producer_types WHERE name_norm = 'поселение')` (тип-родитель «Поселение»; на dev-БД
`id=1`, но **резолвится по данным**, а не хардкодом), а **не** `name_norm IN (...)`:

- **миграция `000079` покрывает всю ладдеру** (предикат класса, §выше), а не только «Аутпост»;

- студия обязана **предупреждать**, если позиция объявлена не на всех ступенях ладдеры.

### 6.4. **ПРИНЯТЫЙ РИСК: массовая жажда** (решение создателя 2026-09-24, О1)

Нужда включается **на всей ладдере** — и это произойдёт **раньше**, чем готова цепочка снабжения:

| Звено | Состояние | Следствие |
|---|---|---|
| Добыча льда в поясе | **не готова** (`2026-09-24-ледяные-астероиды-вода.md` — дизайн/разработка) | нечего перерабатывать |
| Доставка/контракты/зачёт | **не готовы** (`boardNeedsFor` пуст) | привезённое не закрывает нужду |

успеем :)»). **Гейт/«выключатель» нужды не вводим.** Числа темпа пары и набор пар у верхних
ступеней **настроит создатель в студии** — это не часть этой спеки (§12.3).

## 7. Логика: нужда, покрытие, дефицит, буфер

### 7.1. Вход (что читает слой потребности)

На тип поселения — карты `eat` (позиция → норма) и `effects` (позиция → тип эффекта) **как сегодня**.
Дополнительно нужно **одно новое имя**: `goods.name_norm` товара-выхода ветки (заменяет
`categories.name_norm` в роли позиции). В запрос веток (`branchSelectBySettlementsSQL`) `JOIN goods og`
уже есть → отдавать `og.name_norm` вместо (или вместе с) `c.name_norm`.

### 7.2. Нужда и позиции

- Нужда = `effect_type_id` (группа как в `needsGroup` сегодня).
- Позиция `K` = ключ `params.eat`/`params.effects`; норма `norm_K = EatK(eat, K)` (нет записи →
  `DefaultEatK`, семантика сохранена); **явный 0 = «не ест»** (покрытие 0).
- Сегодня у нужды **одна** позиция; механизм группы (несколько позиций с одним эффектом) не
  удаляется, но контент его не использует.

### 7.3. Покрытие и дефицит (формула **не меняется**)

Единица покрытия — **скорость** (батч/сек); запас (батчи) в покрытие **не входит** — он живёт в
`t*` (§7.4). Это и есть «одна единица на строку»: устранено смешение скорости и запаса прежней
редакции (`avail_K = Σ_batches + Σ_buffer_basis`).

```
p_K        = Σ p_b по веткам K                 # выработка веток K, батч/сек (СКОРОСТЬ)
D          = PerSecond(norm_K, P)              # спрос позиции, батч/сек (СКОРОСТЬ)
coverage   = p_K                               # покрытие — скорость, не запас
w1         = clamp01(1 − coverage / D)         # дефицит — безразмерная доля [0,1]
```

- **Как ветка попадает в позицию `K`:** товар-выход ветки `g` относится к `K`, если
  `K = g.name_norm` (**точное совпадение товара**). Категория не участвует.
- **Двойного счёта нет by construction:** каждая ветка относится не более чем к одной позиции;
  правило «самая конкретная побеждает» (§7.3 прежней редакции) **снято как ненужное** — оно
  требовалось только при категорийном «сахаре».
- **`consumed` в витрине** = фактическое списание (как в И2.3), не норма.

### 7.4. Буфер и `t*` (без изменений)

Запас — в **батчах** (не скорость); `t*` — деление запаса на нетто-скорость.

```
buf        = Σ O0_b по веткам K                # базис буфера, БАТЧИ (запас)
p          = Σ p_b по веткам K                 # текущая выработка, батч/сек (СКОРОСТЬ)
t*         = (p < D) ? buf/(D − p) : +∞        # СЕК = БАТЧИ / (батч/сек)
w(t)       = (t < t*) ? 0 : w1                 # w1 = 1 − p/D из §7.3
```

Прочие правила прежние: точки разбиения по `Since` веток, кусочная `w`, `recovery`/`load`/порог
кривой — **без изменений**.

**Решение по `mergeTrajectories` (группировка позиций одной нужды).** Сегодня нужда = **одна**
позиция, поэтому `mergeTrajectories` (объединение по `max`) — тождественный проход; менять его
семантику (`max → Σ`) **сейчас не нужно и не делаем** — код оставляем как есть. Переход на **Σ
долей** — только вместе с будущим расширением «альтернативы» (§7.5), отдельной спекой. Так §7.3/§7.4
(сегодняшняя односоставная модель) и §7.5 (будущее) не расходятся.

### 7.5. Будущее расширение: альтернативы и Σ долей (**кратко, без проектирования**)

Отложено решением создателя (О2). Контур на будущее, чтобы не потерять находки:
- нужда = **несколько** позиций-товаров с одним типом эффекта; у каждой — **своя** норма
  («1000 воды **или** 500 соков»);
- покрытие нужды = **Σ долей** (`доля = наличие/спрос(позиции)`), `w = clamp01(1 − Σ долей)`;
- `mergeTrajectories` (max) → **Σ**; списание по позициям пропорционально базису;
- если категорийный «сахар» когда-нибудь вернётся — правило «самая конкретная побеждает»
  (товар изымается из категорийной позиции) берётся из студийного канона
  (`2026-09-21-студия-производители-лестница-предложения`).

Открывается **отдельной спекой**, когда появится реальная потребность в «или».

## 8. Влияние на слой эффектов

### 8.1. `active_effects.source_position` — **конфликт снят в пользу спеки стадий**

Спека `2026-09-23-стадии-поселения-и-скорость-производства.md` §5.4/§14 п.14 **фиксирует**:
`source_position` **остаётся первой позицией группы** (витринное поле админ-карточки), а гварды и
сверки строятся **по `effect_type_id`**, не по `source_position` (гвард по позиции несостоятелен:
один эффект покрывает несколько позиций). **Побеждает спека стадий** — это решение **отменяет**
прежнюю редакцию §8.1 этой спеки («`source_position` = ключ нужды»). Схема не меняется
(колонка `TEXT` без FK).
- **Сегодня** (одна позиция на нужду) `source_position` = **ключ позиции-товара**; при будущих
  альтернативах — первая сортированная позиция группы (как в спеке стадий).
- `load`/`load_at`, кривые, `recovery` — **не меняются**.

### 8.2. Тип эффекта для воды — «Жажда»

- Сегодня `effect_types` — одна строка («Голод», `curve='hunger'`). Питьевой нужде нужен **свой**
  эффект (О3), иначе игрок увидит «Голод» при нехватке воды.
- **Решение:** добавить строку `effect_types` «Жажда» (`name_norm='жажда'`, `impact='population_rate'`,
  `params.curve='hunger'`) — **та же кривая** `hunger` (отдельной компоненты «Балансировки» и правки
  админ-UI **не заводим**; кривая универсальна по нагрузке). `thresholdsFor`/`recoveriesFor` ключуются
  кривой → обе нужды получают один порог и один `recovery` — **названное следствие**.
- **Альтернатива (отвергнута):** отдельная компонента `thirst` в «Балансировке» — плюс правки
  `effectComponents`, пресетов и админ-UI ради одного числа; отложено до контент-прохода.

### 8.3. Причина гибели — `DeathCause` различает «Голод» и «Жажду»

**Факт кода.** `internal/economy/settlement/death.go` (`DeathCause`) при доминировании вклада
эффекта **жёстко** отдаёт код `"hunger"` (`:71-80`). Эффект передаётся в `PlanetInput.Effects`
(`[]EffectForcePoint`, `projection.go:18/29`), который несёт **только `Rate`/`Since`/`Until`** —
**идентичности эффекта нет**. Кривая у «Голода» и «Жажды» **общая** (`hunger`, §8.2), поэтому по
`Curve` их тоже не различить.

**Правка (дизайн; код — @developer):**
- дать эффекту идентичность в `PlanetInput`: `EffectForcePoint` (или `PlanetInput`) получает
  **имя/код типа эффекта** (напр. `EffectTypeName` = `effect_types.name_norm`), заполняемое
  владельцем (owner-проход, `collectForce`);
- `DeathCause` маппит тип эффекта → **код причины**: `голод` → `hunger`, `жажда` → **`thirst`**
  (новый код); при доминировании эффекта возвращается код **его** типа, а не всегда `"hunger"`;
- **при двух активных эффектах** доминирует тот, чей вклад больше; равенство — по тому же принципу
  argmax (порядок между эффектами задать детерминированно — @developer, тест T19).

**Дельта доков:** `18b_settlement_log.md` §«Причина» — новая строка таблицы
`| thirst | Жажда | вклад эффекта «Жажда» строго больше прочих |`; `18_needs.md` §18.3.1 — флавор
причины «Вымерло · <дата> · Жажда» (текст — за `@writer`, место — там же).

### 8.4. Инвариант `w` и анти-абьюз

- Анти-абьюз «крошка» **сохраняется**: малая подача → покрытие ≈ 0 → `w ≈ 1` → нагрузка растёт.
- `w = 1` при отсутствии источника — как сегодня.

### 10.2. Строка нужды (покрытие %)

```
Need {

  effect: "жажда",
  covered_share: 0.42,           # покрытие/спрос, кламп [0, 1] для показа

```
Показ (формулировка — за `@uidesigner`, вид для ориентира):
`Жажда · покрытие 42 % · очищенная вода 8.4/20 т/сут (дефицит 11.6 т/сут)`.

> Полная форма с **несколькими** позициями одной нужды — **будущее расширение** (§7.5); в текущей

### 10.3. Игрок

Те же правила видимости, что у блока арифметики (спека стадий §8.3): админ — полный вид; игрок
(`presence`) — **под настройкой** `settlement_arithmetic_visible_to_player`; снимок — блок
**не несёт** (`stripSnapshotSettlementSecrets` чистит и строки позиций, и строку нужды).

## 11. Интерфейс для команды контрактов (форма нужды)

### 11.1. Нужда на выходе (ленивая, не хранится — инвариант 2)

**Инвариант формы:** объект нужды — **одна нужда** (= один `effect_types.name_norm`); в его
`positions` лежат позиции **только этой** нужды. Позиции разных нужд (вода/еда) **не смешиваются** в
одном объекте — каждая нужда отдаётся **своим** объектом. В текущей редакции у нужды **одна**
позиция; `positions` — массив «на будущее» (несколько позиций = альтернативы, §7.5).

```jsonc
{
  "owner_type": "settlement",
  "owner_id": "<uuid>",
  "planet_id": "<uuid>",
  "need": "жажда",                  // идентичность нужды (= effect_types.name_norm)
  "effect": "жажда",
  "covered_share": 0.42,            // покрытие/спрос (0..1 для показа)
  "deficit_share": 0.58,            // = w — доля нужды, не закрытая
  "positions": [
    { "kind": "good", "key": "очищенная вода", "good_id": 422,
      "norm_per_day_per_billion": 20000000,
      "demand_per_day": 20.0,       // PerDay(norm, P) — сколько закроет нужду ЦЕЛИКОМ
      "deficit_per_day": 11.6 }     // deficit_share × demand_per_day
  ],
  "computed_at": "<ts>"
}
```
> Нужда «голод» отдаётся **отдельным** объектом (свои `need`/`effect`/`positions` на товар «пища»).
> Форма с **несколькими** позициями одной нужды — будущее расширение (§7.5), не проектируется здесь.

### 11.2. Как этим пользуется доска (их зона)

Доска выбирает **позицию**, режет `deficit_per_day × окно` на доли (`contracts.SliceShares`),
публикует контракт на **товар** позиции. Награда/окно/каталог — их спека.

### 11.3. Точка подключения «завоз» (не реализуется здесь)

Сегодня покрытие = **только выход веток**. Источники покрытия — уже названные точки подключения
(спека эффектов §4.2/§17, канон `18_needs` §18.1.2): местное покрытие планеты, естественный запас,
**завоз извне**, склад. Форма источника (единая для всех):
```
CoverageSource { owner, position_key, good_name_norm, batches, delta_sec, buffer_basis, since, sink }
```
`sink` — куда списывать при потреблении (сегодня — выходной буфер ветки). Завоз товара = источник с
`good_name_norm` доставленного товара; **модель его не знает** и ничего не дублирует.

## 12. Числа

### 12.1. Норма воды (гипотеза создателя, калибрует `@balancetester`)

| Величина | Значение | Вывод |
|---|---|---|
| Быт | ≈20 л/чел/сут (экономный) | 1000 чел → 20 т/сут |
| Норма позиции «очищенная вода» | **20 000 000** ед/сутки/млрд | `PerDay(2e7, 1000) = 20` ед/сут |
| Единица товара | `goods.weight = 1` (проверено: 422, weight 1) | 1 ед ≈ 1 т → 20 т/сут |
| Форпост 500 чел | норма **та же** `2e7` (от населения не зависит) | `PerDay(2e7, 500) = 10` ед/сут = 10 т/сут |
| Трюм 20 т / рейс 1/сутки | совпадает с суточной нуждой 1000 чел | один рейс закрывает сутки |

**Норма — «ед/сутки/млрд» и от населения не зависит** (§6.3, О4): население меняет только
**произведение** `PerDay(2e7, P)`, а не саму норму. 500 чел дают `PerDay(2e7, 500) = 10` ед/сут
(не «норму 10 000 000»); «половина» относится к **расходу** (10 т/сут), а не к норме.

**Осознанное расхождение единиц не вводится:** 1 ед = 1 т только при `weight = 1`; для другой
позиции (напр. «сок» с иным `weight`) норма задаётся так, чтобы `PerDay(norm, P)` совпало с нужной
массой — **число нормы и есть место, где живёт масса**, отдельного пересчёта по `weight` в модели
потребности **нет** (отвергнуто: второй конвертер к `units.go`).

### 12.2. Сверка с независимыми шкалами

Пакет `@writer`/`@scientist` менеджером **не передавался** — сверять нечего. Норма воды
(20 л/чел/сут) — **бытовой эталон создателя** (Р7), не гипотеза дизайнера; физика (температуры)
не затрагивается.

### 12.3. Какой товар пьёт форпост

- **«Очищенная вода»** (`goods.id=422`, `kind='good'`, «продовольствие») — питьевой **товар**;
  «Вода неочищенная» (`426`, ресурс, «Минералы») — **сырьё** рецепта 98. Нужда — на **товар** (О5).
- **Путь создателя:** лёд → «Вода неочищенная» → ветка рецепта 98 («Аутпост» × 98) → «Очищенная
  вода» в выходном буфере → покрытие нужды. **Внимание:** текущий `rate=10000` даёт 0.01 ед/сут —
  это **заглушка** (§6.4); для нужды 20 т/сут число скорости пары должно быть ≈ `2e7` (настраивается
  в студии).
- Доставка **готового** товара (или ресурса во вход ветки) — путь другой команды (§11.3).

### 12.4. Анти-ловушка «сущность, влияющая на формулу, но отсутствующая в игре»

| Сущность | В игре? | Влияние на текущие числа |
|---|---|---|
| **Завоз извне** (доставка контрактом) | **нет** (доска без нужд, зачёт не реализован) | **исключено** из калибровки. Число `2e7` откалибровано под путь «ветка/поставка в буфер»; при появлении источника «завоз» он подключается слагаемым — **двойного учёта нет** (норма одна, позиция одна) |
| **Местное покрытие планеты** | **нет** | **исключено**; при появлении — слагаемое `coverage`, норму не пересчитывать |
| **Регенерация (замкнутый цикл)** | **нет** (в таблице создателя — режим «5 л/чел/сут») | **исключена** из `2e7`; кандидат ГД-сущности, §14 |
| **Склад/резервуар** | **нет** | **исключён** |

Правило: пока сущность не принята создателем, она **не входит** в текущие числа (иначе при
имплементации применится второй раз).

    **будущее расширение** (§7.5, кратко). Ядро спеки упрощено до сегодняшней формулы (§7.3).
  - **Миграция категорийных ключей:** `продовольствие` → товар **«пища»** (378); «вода» удалена;

  - **О1:** массовая жажда — **принятый риск** (§6.4): заглушка `148×98 rate=10000` (0.01 против
    20 т/сут), отсутствие пар у верхних ступеней; гейт нужды не вводим.
  - **`source_position`:** конфликт со спекой стадий §5.4/§14 п.14 снят — **побеждает спека стадий**
    (первая позиция группы, гварды по `effect_type_id`); прежняя §8.1 отменена.
  - **Ладдера:** резолв **по данным** (`params.stage` + `parent_id` типа-родителя «Поселение»),
    а не по именам; ступеней **семь** (добавлен пропущенный «Мегаполис» 152) (§6.3).
  - **`DeathCause`:** жёсткий `"hunger"` заменяется на код по типу эффекта (`жажда` → `thirst`),
    идентичность типа — в `PlanetInput`/`EffectForcePoint` (§8.3).
  - **Словарь товаров в owner-проходе:** `buildBindings` резолвит по `goods.name_norm` (иначе фича —
    no-op); словарь — один запрос на пачку (§9.4).
- **Порция 2 (2026-09-24, остаток находок @critic).**
  - **`max→Σ` — решение:** `mergeTrajectories` (`max`) **не трогаем** (нужда = одна позиция, проход
    тождественный); переход на **Σ долей** — только с будущими альтернативами (§7.5). Расхождение
    §7.3/§7.4 снято.
  - **Единицы §7.3/§7.4:** покрытие — **скорость** (`p_K`, батч/сек), запас — **батчи** (`buf`,
    `t* = buf/(D − p)`); смешение скорости и запаса прежней редакции устранено.
  - **Норма и население (§12.1/В9):** норма `2e7` «ед/сутки/млрд» **от населения не зависит**;
    500 чел → `PerDay(2e7, 500) = 10` ед/сут (было ошибочно «норма 10 000 000»).
  - **Пример §11.1:** одна нужда = один объект, `positions` — только позиции **этой** нужды;
    позиции разных нужд (вода/еда) не смешиваются; несколько позиций — будущее (§7.5).
  - **SQL миграции `000079`** внесён в §6.2: покрывает **всю** ладдеру предикатом класса
    (`params ? 'stage'` + `parent_id` типа-родителя «Поселение»), а не списком имён.
  - **Факт сверки по поселениям** (§6.3): колонка «Поселений (dev-БД)» — перепроверено 2026-09-24
    (аутпост 33 435; посёлок/городок/город 0; мегаполис 2; метрополия 6; экуменополис 38).
