## 0. Задача

Кнопки студии («заполнить комплектующие», «описания ИИ») ходят в локальный `opencode serve`
(`OPENCODE_URL`, дефолт `http://127.0.0.1:3456`). Помощник не запущен → сырое
`connection refused`. Нужно: из студии видеть состояние помощника и управлять им (запуск/остановка),
плюс автозапуск вместе с остальными локальными сервисами.

**Вне объёма:** поведение ИИ-клиента (`internal/goodsstudio/ai` не меняется), basic-auth opencode
(`OPENCODE_SERVER_PASSWORD` считается не заданным — иначе и клиент, и проба не работают),
управление помощником с удалённой машины.

## 1. Факты-источники (проверено, читать как данность)

- opencode server API: `GET /global/health` → `{ healthy: true, version: string }`;
  `GET /config` → конфиг. Источник: `docs.opencode.ai/docs/server/` (прочитано 2026-09-24).
  ⚠️ Точный эндпоинт подтвердить живой пробой на установленной версии; фолбэк — `GET /config`.
  Если ни один из них не отвечает 2xx, но владелец порта подтверждён как помощник — состояние
  всё равно `running` (без `version`), см. §2.
- Команда запуска: `npx -y opencode-ai serve --port 3456` (идея `99a`, «Работа над ошибками»;
  CLI `opencode` в PATH нет, есть `npx`).
- Дефолт `OPENCODE_URL=http://127.0.0.1:3456` — `internal/config/config.go:95–97`.
- Порт для управления берётся **из `OPENCODE_URL`** (не хардкодится 3456), чтобы запуск и проба
  не разъехались.

## 2. Состояние помощника — выводится по факту, не по памяти

`managed` (можно ли управлять) — отдельный флаг, не состояние. **Состояние выводится по факту
доступных проб, а не по памяти; область процессных проб — Windows.** На Windows источник — порт +
health + список процессов; **вне Windows (прод) список процессов (PowerShell) недоступен**, поэтому
выводятся только `stopped`/`running`/`foreign` (ветки «живой процесс помощника» — только Windows),
и там всегда `managed=false`.

| Состояние | Условие |
|---|---|
| `stopped` | порт из `OPENCODE_URL` не слушается и процесса помощника нет |
| `starting` | порт **не** слушается, но есть живой процесс помощника на этом порту (§3.4, метод Б — внешний запуск, напр. `npx` первый раз качает; только Windows) **либо** идёт наш джоб запуска (п. 6) |
| `running` | порт слушается и (**HTTP-проба дала 2xx JSON** **или** владелец порта подтверждён как помощник — помощник жив, проба не ответила) |
| `foreign` | порт слушается, но владелец порта — не помощник (или владельца не определить) |

Порядок вычисления:
1. Разбор `OPENCODE_URL` (`net/url`): схема `http`/`https`, host, **явный порт**. Нет порта или
   схема иная → `managed=false`.
2. Гейт `managed` = `host` loopback (`127.0.0.0/8`, `::1`, `localhost`) **и** ОС Windows **и**
   `npx` найден в PATH. Иначе `managed=false` + `reason` (человеческий текст).
3. TCP-проба порта (таймаут 1 с). Отказ → шаг 5. Успех → HTTP-проба health (таймаут 2 с).
4. Health 2xx JSON → `running` (+`version`). Иначе — опознание владельца порта (§3.4, метод А):
   владелец подтверждён помощником → `running` **без `version`** (помощник жив; проба не ответила —
   не подтверждён эндпоинт, F7, либо идёт инициализация); чужой/не опознан → `foreign`.
   **`starting` здесь не выставляется** — иначе живой помощник застревал бы в `starting` навсегда.
5. Порт свободен: на Windows — есть живой процесс помощника на этом порту (§3.4, метод Б) →
   `starting` (внешний запуск, порт ещё не поднят); иначе → `stopped`. Вне Windows — сразу `stopped`.
6. In-memory джоб запуска активен → `starting` безусловно (перекрывает п. 4–5).

**Кэш и конкурентность:** вердикт по процессам (`opencode`+`serve` на нашем порту, п. 4–5, только
Windows) кэшируется 5 с. **Кэш вердикта и in-memory состояние джоба живут под `sync.RWMutex`**
(чтение — `RLock`, обновление — `Lock`; `AGENTS.md` §0, инвариант 1): проба вызывается параллельно
из `GET /studio/api/state` (несколько клиентов раз в 3 с) и `/studio/api/ai/status`. Проба
порта/health не кэшируется.

## 3. Контракты ручек

Роуты — три явных, `auth.AdminAuth` (роли `admin`/`skycomposer`), регистрируются в `cmd/server/main.go`
рядом с остальными `/studio/api/*`.

**`StatusView`** — общая форма ответа (пример значений — при дефолтном `OPENCODE_URL`):

```json
{ "state": "stopped|starting|running|foreign",
  "managed": true, "reason": "",
  "detail": "ИИ: не запущен",
  "url": "http://127.0.0.1:3456", "port": 3456, "version": "1.1.20",
  "starting_since": "2026-09-24T12:00:00Z", "last_error": "",
  "log": "logs/opencode_serve.log" }
```

`detail` — человеческий текст для строки UI (генерит сервер, фронт не сочиняет); `version` — из
health, **пусто при `running` по владельцу порта** (проба не ответила, §2); `last_error` — только
после неудачного действия (гасится успешным действием / сменой состояния). `starting_since` —
**только для запуска, инициированного студией** (наш джоб): у внешнего `starting` (поднят
`start-all.cmd`/вручную, в т.ч. после рестарта игрового сервера) метки старта нет — поле пустое, и
UI показывает состояние **без «N с»**.

### 3.1 `GET /studio/api/ai/status`

→ 200 `StatusView`. Другие методы → 405.

### 3.2 `POST /studio/api/ai/start`

| Условие | Код | Тело |
|---|---|---|
| `managed=false` | 409 | `{"error":"управление недоступно: <reason>", "status":{…}}` |
| `running` | 200 | `{"started":false, "status":{…"detail":"уже запущен"…}}` |
| `starting` | 202 | `{"started":false, "status":{…}}` — второго процесса не плодим |
| `foreign` | 409 | `{"error":"порт <port> занят другим процессом (PID <pid>, <name>)", "status":{…}}` |
| `stopped` | 202 | `{"started":true, "status":{"state":"starting",…}}` |

`<port>` — порт из `OPENCODE_URL`; `<pid>`/`<name>` — из опознания (§3.4).
Запуск `stopped` → 202: процесс стартует отдельно, джоб опрашивает готовность (до
`OPENCODE_START_TIMEOUT_S`, дефолт 300 с), состояние в статусе меняется само. `cmd.Start()`
не удался → 500 `{"error":"не удалось запустить: …", "status":{…"state":"stopped"…}}`.
Таймаут готовности → `last_error="не дождались готовности за N с; смотрите logs/opencode_serve.log"`,
состояние — по факту пробы; **запущенный процесс не гасим** (может дозагрузиться).

Спавн (Windows): `cmd.exe /c npx -y opencode-ai serve --port <port>` с `DETACHED_PROCESS`
(без окна, переживает рестарт игрового сервера), stdout+stderr в `logs/opencode_serve.log`
(append, один файл с `start-all.cmd`), `CREATE_NEW_PROCESS_GROUP`. `<port>` — из `OPENCODE_URL`.
Single-flight: `TryStart`-паттерн под тем же `sync.RWMutex` из §2 (флаг нашего джоба + кэш
вердикта — под одним замком, `AGENTS.md` §0); `starting_since` ставится в момент спавна (см. §3).

### 3.3 `POST /studio/api/ai/stop`

`managed=false` → 409 (как выше). Порядок: **сначала блокировка ИИ-прогона (№4)** → собрать
кандидатов (§3.4: метод А — владелец порта, метод Б — процесс помощника на нашем порту) → погасить
**только кандидатов** → дождаться освобождения порта (до 10 с).

| Условие | Код | Тело |
|---|---|---|
| `managed=false` | 409 | `{"error":"управление недоступно: <reason>", "status":{…}}` |
| идёт ИИ-прогон студии (`fillGenerating`) | 409 | `{"error":"идёт ИИ-прогон студии — сначала остановите прогон", "status":{…}}` |
| наш джоб запуска активен | 200 | отменить джоб + погасить своё дитя (tracked PID/дерево) → `{"stopped":true}` |
| кандидатов нет, порт свободен (`stopped`) | 200 | `{"stopped":false, "status":{…"detail":"уже остановлен"…}}` |
| есть кандидаты (`running` и/или внешний `starting`, порт свободен) | 200 | погасить всех кандидатов → дождаться освобождения порта (до 10 с) → `{"stopped":true,"status":{…"state":"stopped"…}}` |
| кандидатов нет, порт занят чужим | 409 | `{"error":"порт <port> занят процессом <name> (PID <pid>) — это не помощник, не гашу", …}` |
| опознание не удалось (нет прав и т.п.) | 409 | `{"error":"не удалось опознать процесс помощника — не гашу", "status":{…}}` |
| после гашения порт всё ещё слушается (чужим) | 409 | `{"error":"порт <port> остался занят чужим процессом — не трогаю", "status":{…}}` |
| kill не удался (нет прав) | 500 | `{"error":"не удалось остановить: <причина>", "status":{…}}` |

«Идёт ИИ-прогон» — общий признак любого ИИ-джоба студии `fillGenerating` (`studio_handlers.go:38`:
«любой ИИ-джоб студии (И6): fill ИЛИ описания»; его же ставит и джоб описаний, `tryStartDesc`).
Запрет останавливать помощника во время прогона — **решение создателя 2026-09-24 (вариант 1)**.
Порт не освободился за 10 с → 500, состояние — по факту (вероятно `running`/`starting`), `last_error`.

### 3.4 Опознание процесса помощника (безопасность; порт — из `OPENCODE_URL`)

Единая функция опознания используется и в §2 (состояние), и в §3.3 (гашение) — один факт, одно место.

- **Метод А (владелец порта):** `netstat -ano -p tcp` → строка `LISTENING` с `:<port> `
  (последняя колонка = PID) → командная строка PID:
  `powershell -NoProfile -NonInteractive -Command
  "(Get-CimInstance Win32_Process -Filter \"ProcessId=<pid>\").CommandLine"`.
- **Метод Б (процессы):** тот же скан процессов, что и в §2 (`Get-CimInstance Win32_Process`),
  отбор по командной строке; даёт кандидатов даже когда порт **ещё не слушается** (внешний
  `starting`, в т.ч. после рестарта игрового сервера, §7.3).
- **Помощник подтверждён** ⇔ командная строка (регистронезависимо) содержит `opencode` **и**
  `serve` **и** порт `<port>` как отдельный токен (`--port <port>` или `:<port>`). Без токена порта
  — это другой экземпляр opencode на другом порту: **не наш, не гасим**. Для метода А (порт уже
  наш) достаточно `opencode` + `serve`.
- **Гашение** только подтверждённых кандидатов: `taskkill /PID <pid> /T /F`. `/T` гасит **сам
  процесс и его потомков** — `node`, который держит порт, и всё, что он породил. Обёртки `cmd`/`npx`
  — **предки** `node` и в это дерево **не входят**: они завершатся сами, когда `node` умрёт (они его
  ждут), а если задержатся — порт они не держат. Критерий успеха гашения — **освобождение порта**
  (поллинг до 10 с, §3.3), а не смерть обёрток.
- При любом сомнении — честная ошибка, чужое не гасим. Имя процесса (`tasklist`) — только для
  текста ошибки.

## 4. UI студии (`web/studio.html`, inline-JS)

**Индикатор + кнопки** — в шапке (`head-row head-title`, рядом с `#modelInfo` «Модель ИИ»), т.к.
ИИ-кнопки разбросаны по разделам и попапам:

```html
<span id="aiStatus">
  <span id="aiStatusText">ИИ: проверка…</span>
  <button id="btnAiStart" title="Запустить локальный ИИ-помощник (opencode serve)">запустить</button>
  <button id="btnAiStop" title="Остановить локальный ИИ-помощник">остановить</button>
</span>
```

Тексты `detail` (сервер) → `#aiStatusText`; кнопки/дизейбл — от `state`+`managed`
(`<port>`/`<pid>`/`<name>` — из `StatusView`):

| Состояние | Текст | «запустить» | «остановить» |
|---|---|---|---|
| `stopped`, managed | «ИИ: не запущен» | вкл | выкл |
| `starting`, managed | «ИИ: запускается… (первый запуск качает пакет, до 5 мин)» + «N с» (только если есть `starting_since`) | выкл | вкл¹ |
| `running`, managed | «ИИ: работает (v1.2.3)» — версия в скобках, если `version` непуст | выкл | вкл¹ |
| `foreign`, managed | «ИИ: порт <port> занят другим процессом (PID <pid>, <name>)» + подсказка «освободите порт вручную» | выкл | выкл |
| `foreign`, `managed=false` | «ИИ: порт <port> занят другим процессом (PID <pid>, <name>)» + «освободите порт вручную» | выкл | выкл |
| `starting`, `managed=false` | «ИИ: запускается… (управление недоступно)» — без «N с» | выкл | выкл |
| `running`, `managed=false` | «ИИ: работает (управление недоступно)» | выкл | выкл |
| `stopped`, `managed=false` | «ИИ: недоступен» | выкл | выкл |
| `last_error` непуст | «ИИ: <last_error>» | по состоянию | по состоянию |

¹ «Остановить» выключается, пока идёт ИИ-прогон студии — если в `/studio/api/state`
`generating` или `desc_generating`; тултип «идёт прогон — сначала остановите прогон». Сервер в этом
случае отвечает 409 (§3.3) — UI лишь показывает то же правило, гарантия на сервере.

**Обновление без перезагрузки:** `ai`-объект кладётся в ответ `GET /studio/api/state` (существующий
цикл `fetchState` каждые ~3 с — `web/studio.html:562/582`), отдельного таймера нет. После
`start`/`stop` — немедленный `GET /studio/api/ai/status` и перерисовка; ошибку действия показываем
человеческим текстом (`showReport`/тост), не сырой простыней.
**Опционально (развилка F5):** при `state≠running` ИИ-кнопки студии (`#btnDescBatch`, «заполнить
комплектующие») дизейблим с тултипом «Сначала запустите помощника» — ровно против исходного инцидента.

## 5. `start-all.cmd`

Кодировку **cp866 не менять**. По образцу `:comfy`/`:dash`:

1. Переключатель в шапке: `set "AI=1"` (рядом с `COMFY`/`STUDIO`/`DASH`).
2. Новый сервис `:ai` — последним ([7/7]); `call :portcheck 3456` → «уже работает»; иначе
   `start "ИИ-помощник" /min cmd /c "npx -y opencode-ai serve --port 3456 >> logs\opencode_serve.log 2>&1"`,
   затем **короткое** `call :wait_port 3456 15` (не 300: первый `npx` качает долго, а студия
   показывает прогресс сама); не поднялся — «поднимается в фоне (первый запуск качает пакет),
   статус — в студии», не ошибка.
3. Обязательно: пересчитать нумерацию `[N/6]` → `[N/7]` во всех строках (включая ветки
   «выключено») и добавить строку-заглушку для `AI=0`.
4. В `:summary` — `call :report 3456 "ИИ-помощник"` (и строка URL при желании).

Строки писать в cp866 (как соседние). Порт 3456 в `start-all.cmd` и в `OPENCODE_URL` — два места;
при смене порта править оба (см. §9, DEPLOY).

## 6. Прод (Amvera)

`managed=false` (не Windows / нет `npx`) → кнопки всегда выключены, `detail` — по фактическому
состоянию (§4: «ИИ: недоступен» / «работает (управление недоступно)» / «порт занят…» /
«запускается… (управление недоступно)»). Ручки отвечают 409 с `reason`. Спавн чужих процессов на
проде невозможен: гейт по loopback + Windows. Ничего не ломается.

## 7. Краевые случаи

1. **Порт занят чужим** → `foreign`; `start` 409, `stop` 409, не гасим (§3.4).
2. **Процесс умер между прогонами** (рестарт сервера / `npx` упал) → состояние всегда из живой
   пробы; никакого «мы запускали, значит работает»; `stop` ищет процесс помощника заново по порту
   и/или по командам процессов, а не по памяти.
3. **Рестарт игрового сервера** → in-memory `starting` и `starting_since` теряются; помощник жив →
   статус `running` по пробе; `stop` — по владельцу порта или по процессу; дубликата нет (перед
   спавном ищем живой процесс помощника на нашем порту).
4. **Параллельные вызовы** (`AGENTS.md` §0) → `sync.RWMutex` (инвариант 1): второй `start` при
   `starting`/`running` не плодит процесс (`TryStart`), `stop` во время нашего джоба отменяет джоб,
   двойной `stop` идемпотентен, кэш вердикта и обновления из `/state` + `/status` не гоняются.
5. **Таймаут готовности** → джоб закрывается, `last_error` в статусе, состояние по пробе, процесс
   не гасим (§3.2).
6. **Нет `npx`** → `managed=false`, `reason` «npx не найден в PATH (установите Node.js)», `start` 409.
7. **`OPENCODE_URL` без порта / не-loopback / не http(s)** → `managed=false`, `reason` по причине.
8. **Внешний запуск ещё качает пакет** (порт свободен, процесс помощника жив — Windows) → `starting`,
   а не `stopped`; «запустить» не создаёт второй процесс, «остановить» гасит по методу Б (§3.4).
   Без процессной пробы (не Windows) это состояние неотличимо от `stopped` — честный предел области.
9. **Опознание не удалось** (нет прав на `Get-CimInstance`, гонка PID) → 409, падаем на безопасную
   сторону; `opencode` на **другом** порту нашим кандидатом не считается (токен порта, §3.4).
10. **Остановка во время ИИ-прогона студии** (`fill`/`описания`) → `stop` 409 «идёт ИИ-прогон
    студии — сначала остановите прогон» (решение создателя, вариант 1); в UI «остановить» в это
    время выключена с той же подсказкой. Признак — `fillGenerating` (§3.3).

## 8. Тесты и критерии приёмки (@tester)

**Go, unit (без спавна, `-short`-безопасно):** T1 разбор `OPENCODE_URL` (дефолт; явный порт;
без порта; не-loopback → `managed=false`); T2 таблица §2 на фейковой пробе (stopped/starting/running/
foreign; вне Windows — без процессной ветки; **`running` по подтверждённому владельцу порта при
неответившей health-пробе — не `starting`**); T3 single-flight: два параллельных `start` → ровно
один спавн; T4 `stop` не гасит чужое (владелец без `opencode` → ошибка, kill не вызван) — на
инъектируемом «опознавателе процесса»; T5 таймаут → состояние + `last_error`; T6 `managed=false` →
`start`/`stop` 409; T7 хендлеры: метод не разрешён → 405, форма `StatusView`, `player` → 403
(уровень роута); T8 парсинг `netstat`-строки и `CommandLine` (канонические образцы, включая
`opencode-ai serve` и посторонний `node`); **T9 `stop` внешнего `starting` при свободном порте →
кандидат найден методом Б и погашен, 200**; **T10 `stop` при активном `fillGenerating` → 409, kill
не вызван**; **T11 параллельные `GET /studio/api/state` + `/studio/api/ai/status` + `stop` под
`-race` → кэш вердикта не гоняется (DoD `AGENTS.md` §2)**; **T12 опознание не берёт `opencode serve`
на другом порту (токен порта)**.

**e2e-смоук студии** (`tools/e2e/goods-studio-server-check.js`, без требования живого помощника):
E1 в шапке есть `#aiStatusText`, текст один из допустимых; E2 `GET /studio/api/ai/status` → 200 и
`state` из множества; E3 клик «запустить» при `managed=false`/`foreign` не роняет страницу,
показывает человеческий текст и не создаёт процесса; E4 состояние обновляется без перезагрузки
(индикатор меняется после ручного старта/остановки помощника, если он есть); **E5 во время активного
ИИ-прогона (`generating`/`desc_generating`) кнопка «остановить» выключена с подсказкой**.

**Ручной чек-лист создателя:** `start-all.cmd` с `AI=1` → индикатор «работает»; убить процесс →
«не запущен» в пределах тика; «запустить» → «запускается» → «работает»; «остановить» → «не запущен»;
занять 3456 посторонним `node` → «занят другим процессом», кнопки выключены; рестарт игрового
сервера — индикатор и остановка сохраняются; остановка во время прогона описаний → подсказка
«идёт прогон», кнопка выключена.
