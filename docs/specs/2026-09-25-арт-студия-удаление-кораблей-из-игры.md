## 0. Резюме (одним абзацем)

Реестр кораблей игры переезжает из Go-констант `internal/models/race_ship_sprites.go` в **статичный файл данных** `config/ships_registry.json` (решение создателя 2026-09-25, п. 6). Игра читает файл **при старте** (без пересборки, только перезапуск) в те же package-переменные `models`, поэтому поведение остаётся 1:1. Арт-студия получает на вкладке «В игре» действие **«Удалить»** — физическое удаление одного корабля: запись реестра, PNG из `web/static/sprites/`, PNG из `ai_drafts/final_accepted/ships/` и запись из `ships_meta.json` (решение создателя В2: «картинки удаляются только если это мусор, зачем коллекционировать»). Нейтральный корабль и людской дефолт неудаляемы; **последний корабль расы удалять МОЖНО** (решение создателя В1: «Увидел мусор — убрал») — рассинхрон фолбэков игрока/агента при пустом пуле расы назван штатным **известным поведением** (§5), новой игровой логики при этом не вводится. Игрокам с удалённым кораблём — тихая подмена на людской дефолт существующим резолвером; агенты расы с пустым пулом — нейтральный (тоже существует). Окно рассинхрона «PNG уже нет, реестр ещё в памяти игры» названо и ограничено (§7).

## 1. Цель и скоуп

**Цель.** Дать создателю из витрины «В игре» убирать из игры неудачные/дублирующие корабли, чтобы в игровом наборе оставались только хорошие картинки (цель создателя, п. 3). Сейчас витрина только для чтения, а удаление требует ручной правки Go-исходника, тестов и файлов.

**В скоупе:**
- переезд реестра кораблей игры в файл данных + чтение игрой при старте (поведение 1:1);
- эндпоинт удаления в студии + физическая чистка (запись реестра, PNG игры, PNG accepted, мета);
- защита фолбэков (нейтральный корабль и людской дефолт; пул расы чистится целиком, включая последний корабль);
- UI вкладки «В игре» (кнопка «Удалить» + подтверждение + пересчёт);
- правка `tools/import_ship_sprites.ps1` (пишет файл данных) и `tools/import_ship_sprites_smoke.ps1` (переводится на JSON-фикстуру), `data-agnostic` тесты реестра;
- дельта `docs/DEPLOY.md` (файл в образе).

**Вне скоупа:** удаление пакетом; редактирование/поворот кораблей игры из витрины; возврат корабля из UI (страховка — git); БД-таблица реестра; изменение `spriteForAgent`/`pickVariant` кроме теста деградации; любые изменения боевой/игровой логики, кроме чтения данных.

**Эталоны мира/физики фичу не затрагивают** — калибровки, числа баланса и `@balancetester` не требуются. Пакет `@writer`/`@scientist` менеджером не передан — сверка не проводилась (не применима).

## 2. Разворот подходов (пространство решений)

Требование создателя (идея, п. 6) уже отсекло БД и правку Go веб-инструментом. Ниже — классы подходов с ценой, чтобы выбор был осознанным (фиксирован вариант **C**).

| # | Подход | Как работает | Цена / режим отказа | Итог |
|---|---|---|---|---|
| A | Точечная правка Go-исходника студией | Студия удаляет строку литерала в `race_ship_sprites.go` + PNG | Веб-инструмент правит код игры; серия перезаписей одного файла (сторож зацикливания); эффект — только после пересборки; реестр и код связаны | отклонён (решение создателя п. 6) |
| B | `//go:embed` JSON | Данные встроены в бинарь | Статично и коммитится, но правка требует **пересборки** — противоречит «без пересборки»; embed не видит родительские каталоги (`config/` из `internal/models` недоступен) | отклонён (решение создателя п. 6) |
| C | **Файл данных на диске, читается при старте** | `config/ships_registry.json`; студия правит файл; игра при рестарте перечитывает | Нужны: путь в образе прода, фолбэк при отсутствии/битом файле, тесты data-agnostic. Путь на прод уже попадает (`COPY config`) | **принят** |
| D | Таблица в БД (игровой сервер) | Реестр в Postgres | «Один факт — одно место» под вопросом (реестр статичен, коммитится с ассетами); студия — отдельный процесс без доступа к БД; миграция + репозиторий + кэш на 118 строк ради статичного списка | отклонён (решение создателя п. 6) |
| E | Реестр только на клиенте (`ship_options`) | Сервер не хранит реестр, клиент строит из ответа | Не решает: серверу всё равно нужен источник для `/me.ship_options`, резолвера, валидации `PUT /me/ship-icon` | отклонён |

**Почему C выигрывает:** статичный список из ~120 строк — это данные, а не код; путь `config/` уже канон данных игры (`races.json`, `race_lore.json`, `planet_archetypes.json`) и уже копируется в образ прода (`Dockerfile`: `COPY config ./config`); студия и игра читают один и тот же файл из корня репозитория; удаление перестаёт быть правкой кода.

## 3. A. Реестр кораблей как данные

### 3.1. Путь, имя, формат

- **Файл:** `config/ships_registry.json` (новый; коммитится вместе со спрайтами — в одном коммите).
- **Обоснование выбора `config/`, а не `web/static/sprites/`:** `web/static` отдаётся публично по `/static/` (`cmd/server/main.go:665`), реестр — служебные данные, а не веб-ассет; `config/` уже копируется в образ прода и уже читается игрой при старте (`config/races.json`); студия уже читает `config/races.json` при старте. Отклонённая альтернатива `web/static/sprites/ships_registry.json` — рядом со спрайтами, но публично по `/static/sprites/…` и смешивает данные с отдаваемыми ассетами.
- **Формат:** JSON-объект (`version` — задел), массив `ships`; элемент — сериализованный `models.ShipSprite` (переиспользуем тип, второй модели не заводим):
  - обязательные в файле: `id`, `name`, `file`, `race` (поле `race` **всегда присутствует**, в т.ч. пустое у нейтрального — N12);
  - `angle`/`flip`/`scale_human` — по тегам модели (`omitempty`): отсутствие = `0`/`false`/дефолт `DefaultShipScaleHuman` (12);
  - порядок в массиве = порядок реестра: **людской блок первым** (тип `starship → cruiser → carrier → fighter`, внутри типа `base → _02 → _03`), затем расовые в порядке `ships_meta.json`, **нейтральный последним** (как `ShipOptions` сегодня).
- **Кодировка:** UTF-8 **без BOM** (Pitfall: PowerShell 5.1 `Set-Content -Encoding UTF8` пишет BOM — читать/писать через `[System.IO.File]` с `UTF8Encoding($false)`; загрузчик BOM снимает защитно).
- **Образец записи:**

```json
{
  "version": 1,
  "ships": [
    {"id":"race_humans_starship","name":"Звёздный корабль (люди)","file":"race_humans_starship.png","race":"humans","angle":21.1},
    {"id":"race_coastal_02","name":"Прибрежные · 2","file":"race_coastal_02.png","race":"coastal","angle":-38},
    {"id":"neutral","name":"Нейтральный","file":"neutral.png","race":""}
  ]
}
```

- **Миграция данных:** файл создаётся однократно из текущего литерала `RaceShipSprites` + `NeutralShip` (117 + нейтральный = 118, порядок и пары сохраняются дословно). Это механическая операция реализации, отдельного решения не требует.

### 3.2. Как игра читает файл (старт, кэш, потокобезопасность, фолбэк)

**Контракт в `internal/models` (новый файл `ship_registry.go`; литерал из `race_ship_sprites.go` убирается):**

- `func ReadShipRegistry(path string) ([]ShipSprite, error)` — чистое чтение + валидация, без побочных эффектов (нужна студии и тестам).
- `func LoadShipRegistry(path string) error` — читает файл и **заполняет package-переменные**: `RaceShipSprites` (записи файла без нейтральной), `ShipOptions` (= `RaceShipSprites` + `NeutralShip`), индексы `shipSpriteByFile`, `shipFilesByRace`; проверяет наличие нейтральной и людского дефолта.
- `LoadShipRegistry` вызывается **один раз при старте** игры — в `cmd/server/main.go` **сразу после `config.Load()` и ДО `bootstrapSkycomposer`** (сейчас bootstrap на `:132`, загрузка конфигов — позже, `races.LoadCatalog` на `:206`). Причина порядка: `bootstrapSkycomposer` создаёт первого skycomposer через `models.RandomShipForRace` (`cmd/server/bootstrap.go:61`) и обязан видеть настоящий реестр, а не аварийный минимум. Путь — относительный `config/ships_registry.json` (как канон соседних конфигов).
- **Потокобезопасность (инвариант 1 GD_PROMPT / §0 AGENTS.md):** после старта переменные **только читаются** (игра файл не перечитывает — так устроен заявленный режим «эффект после перезапуска»), поэтому гонки нет и мьютекс не нужен; это фиксируется комментарием у `LoadShipRegistry`. Если в будущем появится горячий перезагруз, его обязан сопровождать `sync.RWMutex`/`atomic.Pointer` — сейчас не закладываем (правило «сначала простота»). Тесты, которым реестр нужен, вызывают `LoadShipRegistry("../../config/ships_registry.json")` **в setup** до чтения (тот же паттерн, что `races.LoadCatalog` в тестах).
- **Отсутствие/битый файл — фолбэк, игра не падает:** `LoadShipRegistry` возвращает ошибку, `main.go` пишет `log` уровня ERROR (`реестр кораблей не загружен: <путь>: <err>`) и **оставляет аварийный минимум**, вписанный в коде. Состав минимума однозначен: `RaceShipSprites = [запись DefaultHumanShip]` (пара ориентации `Angle: 0`, `Flip: false` — **допустимая деградация**, названа), `ShipOptions = RaceShipSprites + NeutralShip` (нейтральный входит **ровно один раз** — в `RaceShipSprites` его не кладём, дубля нет), `shipFilesByRace[""] = [NeutralShip]`. Игра работоспособна: `ResolveShipIcon` → людской дефолт (файл на месте), агенты → нейтральный. Деградация явная и громкая в логе, но не падение и не «пустой реестр, молча».
- **Аварийный минимум — не второй источник реестра**, а страховка: в нормальной работе список берётся из файла; тест реестра проверяет, что файл содержит обе защищённые записи (страховка от дрейфа).

**Валидация при загрузке (отказ → фолбэк):**
1. непустой массив; `version` (если есть) поддерживается;
2. `id`, `name`, `file`, `race` непусты (кроме `race` у нейтрального — она пустая, но присутствует);
3. `ID == File` без `.png`; `file` заканчивается на `.png`; `-180 < Angle ≤ 180`;
4. `File` уникальны;
5. **людской блок первым** (все записи `race=="humans"` идут подряд в начале, порядок тип→вариант), после него людей нет;
6. нейтральная запись (`file == NeutralShip.File`, `race==""`) присутствует **ровно одна** и последняя;
7. запись `DefaultHumanShip` присутствует.

### 3.3. Что обязано остаться идентичным (чек-лист 1:1)

Публичный API `models` не меняется — меняется только источник данных: `RaceShipSprites` (117), `ShipOptions` (118, нейтральный последним), `NeutralShip`, `DefaultHumanShip`, `shipSpriteByFile`, `shipFilesByRace`, `RandomShipForRace`, `ResolveShipIcon`, `IsValidShipIcon`, `ShipRaceByFile`, `ShipOrientByFile`, `ShipScaleHuman`, `SHIP_VARIANT_SLOTS = 9`. Пары `(Angle, Flip)`, порядок, поле `race` в JSON — как сегодня (тест `TestShipOptionsRaceFieldAlwaysPresent` остаётся).

### 3.4. Импортёр «принятое → игра» пишет данные (C5)

`tools/import_ship_sprites.ps1` обязан **писать `config/ships_registry.json`**, а не печатать Go-строки руками (иначе поток «принятое → игра» рассыпается: C1/C5).

- Параметр `-Registry` меняет смысл: дефолт `config/ships_registry.json` (был `internal/models/race_ship_sprites.go`).
- Скрипт читает файл (`ConvertFrom-Json`), копирует PNG по sha256 (как сейчас) и для каждого импортируемого файла, которого **нет** в файле (сверка по `file`, а не по тексту `File: "…"`), создаёт запись `{id, name, file, race, angle, flip}` и **дописывает в конец** (И7: «только в конец»).
- После дописывания скрипт **переустанавливает канонический порядок** стабильной сортировкой: людской блок первым (тип→вариант), остальные — в текущем относительном порядке; нейтральный — последним. Пишет файл UTF-8 без BOM.
- **Неизвестные поля сохраняются.** При перезаписи `config/ships_registry.json` скрипт не «пересобирает» записи с нуля, а правит существующие: поля, которых он не понимает (в частности `scale_human` — сейчас пустой, но объявленный задел `ShipSprite.ScaleHuman`, дефолт `DefaultShipScaleHuman=12`), переносятся в выход без потерь. Смоук это проверяет.
- **`tools/import_ship_sprites_smoke.ps1` переводится на JSON-фикстуру** (сейчас он передаёт Go-файл-фикстуру и проверяет паттерны `File:`/`{ID:` — при переезде реестра в данные это неверно): temp-реестр создаётся как JSON, проверки читают `ConvertFrom-Json` (порядок записей, дописывание в конец, идемпотентность, отсутствие BOM, сохранение `scale_human`).
- **Шапка `tools/import_ship_sprites.ps1` переписывается:** сейчас она утверждает «реестр скрипт НЕ переписывает» (`:6–7`) — после фичи это неверно (скрипт пишет файл данных) и вводит в заблуждение.
- Идемпотентность сохраняется (повторный прогон ничего не добавляет и не копирует повторно).

## 4. Б. Механизм удаления в студии

### 4.1. Эндпоинт и контракт

- **`POST /ships/ingame/delete?file=<name>`** → удаление одного корабля.
- Почему `POST`, а не `GET` как у `/ships/act`: операция разрушительная и необратимая, GET-семантика допускает предзагрузку/повтор браузером. Контракт-ответ:

```json
{"ok":true,"file":"race_coastal_02.png","race":"coastal",
 "ships_left":117,"race_ships_left":2,
 "steps":{"registry":true,"meta":true,"accepted":true,"sprite":true}}
```

- Ошибки (тело `{"ok":false,"error":"…"}`): `405` не POST; `400` пустой/некорректный `file`, попытка обхода пути (`filepath.Base(file) != file`); `409` защищённый корабль (нейтральный/людской дефолт, §4.5); `500` ошибка записи (в теле — какой шаг сорвался); `404` — **только** если по имени файла удалять нечего ни на одном шаге (нет записи реестра, записи меты, PNG accepted и PNG игры). Повторный вызов по уже частично удалённому файлу — **не 404**: домешивает оставшиеся шаги по имени файла (§4.4).

### 4.2. Пути как поля `Server` (M6)

Три точки инъекции (образец `gameSpritesDirPath`), дефолты в аксессорах, в тестах переопределяются:

| Поле | Дефолт | Назначение |
|---|---|---|
| `shipRegistryPath` | `config/ships_registry.json` | файл реестра (чтение витрины + запись при удалении) |
| `gameSpritesDirPath` (есть) | `web/static/sprites` | PNG игры (удаление) |
| `acceptedShipsDirPath` (новое) | `ai_drafts/final_accepted/ships` | PNG приёмки + `ships_meta.json` |

### 4.3. Что именно удаляется (M4) — решение

Удаляются: **(1) запись реестра** (`config/ships_registry.json`), **(2) запись из `ships_meta.json`**, **(3) PNG из `ai_drafts/final_accepted/ships/`**, **(4) PNG из `web/static/sprites/`** — решение создателя **В2 = ДА**: «картинки удаляются только если это мусор, зачем коллекционировать». Раньше дизайн оставлял accepted PNG «сиротой», ссылаясь на то, что запись меты уже закрывает канал восстановления; решение создателя это упрощение снимает.

**Канал восстановления закрывается полностью.** Удаление записи меты закрывает импортёр (`import_ship_sprites.ps1` берёт только записи меты, §6.1 п.1 спеки-источника), а удаление accepted PNG убирает и сам artifact: после удаления ни один шаг «принятое → игра» не может вернуть корабль. Восстановление остаётся только через git (страховка, согласованная создателем п. 2).

**Как связаны имена (важно для шагов 2–3).** Запись реестра адресуется **игровым** именем файла (`<name>`), а `ships_meta.json` и принятый PNG — **именем приёмки**; импортёр сопоставляет их **по sha256, а не по имени** (шапка `import_ship_sprites.ps1`: «имена принятых `race_<slug>_NN.png` и файлов реестра `race_<slug>_<word>.png` не совпадают»). Поэтому запись меты и accepted PNG ищутся **по хэшу игрового PNG** (вычисляется до шага 4, пока файл ещё на месте), с фолбэком **по имени** `<name>`, если игровой PNG уже удалён (повторный вызов). Иначе при расхождении имён мета/accepted не удалились бы и канал «принятое → игра» остался бы открыт — то есть В2 не выполнялся бы. В текущем наборе имена совпадают (проверено: 0 расхождений), но инвариант должен держаться и при будущих импортах. Заодно это корректно закрывает границу M4: если несколько принятых файлов с одним sha256 легли в одно игровое имя, удаляются **все** такие записи меты и PNG (это и есть чистка дублей).

**Порядок (в согласовании с §4.4):** реестр → мета → PNG accepted → **PNG игры последним**. PNG accepted удаляется **до** PNG игры, чтобы частичный сбой не оставлял записи реестра без PNG игры (инвариант §4.4), а канал восстановления при этом был уже закрыт удалением меты и accepted.

**Граница M4 — закрыта связыванием по sha256 (§выше).** Сценарий M4: два разных принятых файла с одинаковым содержимым (sha256) импортировались в **одно** имя игры; повторный импорт после удаления мог бы вернуть содержимое под именем соседней записи. Удаление меты/accepted **по хэшу** убирает **все** записи и PNG с этим хэшем, поэтому канал закрыт и в этом случае. Случай в текущем наборе не встречается (каждой записи меты соответствует своё имя), но правило его покрывает без отдельной работы. Остаётся только несвязанное ограничение: если содержимое уже удалено из accepted, связь восстанавливается по имени (фолбэк) — а имя у текущих данных совпадает.

### 4.4. Порядок и атомарность (M5)

Инвариант безопасности: **никогда не оставлять запись реестра без PNG игры** (иначе красный `TestRaceShipSpritesFilesExist` и битая картинка в игре). Отсюда порядок **данные → PNG игры**, при этом PNG accepted удаляется до PNG игры:

1. **Реестр:** прочитать, убрать запись (если есть), записать атомарно (temp в том же каталоге + `os.Rename`; на Windows `os.Rename` заменяет существующий файл — при сомнении fallback «temp → remove → rename»).
2. **Мета:** прочитать `ships_meta.json`, убрать записи, связанные с `<name>` — **по sha256 игрового PNG, фолбэк по имени** `file == <name>` (§4.3), записать так же; файла/записей нет — шаг пропускается (не ошибка).
3. **PNG accepted:** `os.Remove` принятых PNG, связанных с `<name>` тем же правилом (по хэшу, фолбэк по имени), только после проверки, что путь внутри каталога; файлов нет — пропуск.
4. **PNG игры:** `os.Remove` файла в `gameSpritesDir()` **последним**, только после проверки, что он внутри каталога; файла нет — пропуск.

Операция адресуется **именем файла**, а не «членством в реестре», поэтому **идемпотентна и домешивается**: если предыдущий вызов сорвался после шага 1, повтор не отдаёт глухой `404`, а выполняет оставшиеся шаги 2–4 по имени файла — так удаление гарантированно закрывает канал восстановления (мета + accepted). Ответ `404` — только когда удалять нечего ни на одном шаге; защищённое имя — `409` всегда. Любой промежуточный сбой возвращает `ok:false` с номером шага; повтор — кнопкой «Обновить»/повторным вызовом завершает удаление.

Пометка «гипотеза к проверке»: порядок шагов «реестр → мета → accepted → PNG игры» выбран из инварианта выше; если на реализации окажется, что частичный сбой меты хуже частичного сбоя PNG, порядок 2↔3 меняется — инвариант «реестр без PNG игры невозможен» сохраняется.

## 5. В. Согласованность фолбэков игрок/агент (C2) — известное поведение (решение создателя В1)

**Решение создателя (2026-09-25, В1): последний корабль расы удалять МОЖНО.** «Увидел мусор — убрал». Блокировка «последний корабль расы» из дизайна убрана; чистить пул расы целиком — штатное действие. Сценарий пустого пула (C2) становится **достижимым** и описывается ниже как известное поведение, а не как то, что надо предотвращать.

**Сценарий пустого пула расы X (назван явно, достижим):**
- агент расы X → `spriteForAgent` даёт пустой пул → **нейтральный** (`neutral.png`);
- игрок расы X, у которого стоял удалённый файл → `ResolveShipIcon` (файла нет в реестре) → **людской дефолт** (решение создателя п. 4 — оставляем, резолвер уже есть);
- `PUT /me/ship-icon` не даёт выбрать нейтральный (у нейтрального `Race==""`, а белый список требует `race(file)==race_id` игрока), а селектор расы игрока пуст — выбрать нечего;
- новый игрок расы X при регистрации → `RandomShipForRace` → пул пуст и раса не `humans` → **нейтральный**.

**Видимые последствия (известное поведение, не баг):** игрок расы X с пустым пулом видит людской корабль и не может выбрать свой (селектор пуст); выбрать нейтральный нельзя. Агент X и новый игрок X — нейтральный. Игра при этом **не ломается**: все три исхода — существующие фолбэки, новых падений/пустых картинок нет.

**Что осознанно НЕ делаем:**
1. **Новой игровой логики не добавляем** (простота): не «выравниваем» агента и игрока, не разрешаем выбирать нейтральный, не пишем в БД из студии. Выравнивание поведения при пустом пуле — **отдельная работа по слову создателя**, если он её захочет.
2. **Нейтральный игроку не выбираем:** нейтральный — это **фолбэк-идентичность**, а не расовый корабль; разрешить его выбор значит пустить игрока летать «ни на чём» и обойти правило «игрок выбирает только корабль своей расы» (§6.5 спеки-источника). Запрет остаётся.
3. **Остаточный риск (честно):** `users.ship_icon` игрока продолжает указывать на удалённый файл (студия не имеет доступа к БД — резолвер только при чтении). Если новый импорт когда-нибудь займёт **то же имя** (`race_<slug>_NN.png` — «первый свободный номер» переиспользуется после удаления), игрок молча получит новый корабль с тем же именем. Вероятность мала, но риск назван; цена устранения (запись в БД из студии) несоразмерна — не делаем.

**Если игроку нужен вид расы обратно** — сначала принять замену, потом удалить слабую картинку (порядок действий создателя, не код).

## 6. Г. Сдвиг вида агентов при удалении (C3) — решение

**Факт.** `pickVariant` (клиент, `web/static/js/map/ship_sprites.js`) берёт файл `_0<v>` по слоту `v = 1 + хэш % 9`; если точного суффикса нет — **наименьший суффикс пула**. И7 («вид уже нарисованных агентов не сдвигается при росте пула») покрывал только **добавление** `_0<w>`: меняется ровно слот `w`. **Удаление** даёт иной эффект:
- удалили `_0<w>`, уцелевшие слоты с точным совпадением не меняются → меняется только слот `w` (переходит на наименьший суффикс);
- если удалили **наименьший** суффикс пула, «наименьший» смещается — на новый наименьший переезжают **все** слоты, которые на него опирались (в разреженном пуле это может быть большинство: `{_02,_03}` → удалили `_02` → 7 из 9 слотов меняют вид).

**Решение: принять, с тестом деградации.** Обоснование:
- И2 («детерминизм, ноль хранилища») — ценность выше; закрепление варианта за агентом требует хранилища (`npc_agents.…`), то есть смены канона модели агента ради косметики одного админ-действия;
- удаление — **намеренное действие человека** (чистка), а не автоматический рост; смена вида затронутых агентов ожидаема и ограничена: `% len` не используется, «лавины по всей расе» нет — меняются только слоты, опиравшиеся на удалённый файл;
- И7 уточняется: «рост — только слот `w`; удаление — слоты, опиравшиеся на удалённый файл (в пределе — наименьший суффикс)» (дельта спеки-источника, §10).

**Тест деградации:** расширить `tools/e2e/race-ships-variant-check.js` (чистый node-прогон клиентского модуля, без браузера) — при `setShipOptions` без `_0<w>`: точные слоты не изменились, изменился только `w`; удаление наименьшего суффикса — меняются слоты, опиравшиеся на наименьший; агент **никогда** не уходит в нейтральный при непустом пуле (инвариант §6.4 спеки-источника сохраняется).

## 7. Д. Окно рассинхрона (C4) — решение

**Факт.** Студия — отдельный процесс; игра держит реестр в памяти с момента старта. После удаления: PNG из `web/static/sprites/` исчезает **сразу**, а игра отдаёт клиенту старое имя корабля **до перезапуска** → клиент на 404 рисует **примитив** (И4: `getShipImage` → `null` → примитив/ромб), а не «тихую подмену».

**Решение: принять окно как заданное свойство режима «эффект после перезапуска» и не менять игровой клиент.** Обоснование:
- «Тихая подмена» гарантируется **после перезапуска игры**: реестр перечитывается, `ResolveShipIcon` для удалённого имени отдаёт `DefaultHumanShip`, агент расы с пустым пулом — нейтральный (и то, и другое уже работает);
- во время окна поведение — **существующий фолбэк И4** (нет картинки → примитив), а не новый режим отказа; менять фолбэк на «тихо подставить другой корабль» нельзя — это скроет реальные пропажи спрайтов и нарушит смысл И4 (фолбэк обязан быть нейтральным/примитивом, а не «другим кораблём»);
- порядок удаления (§4.4) делает **персистентное** состояние согласованным (нет записи реестра без файла); рассинхрон существует только между диском и памятью уже запущенного процесса;
- UI студии **обязан** предупредить: «изменения вступят в силу в игре после перезапуска сервера игры» (и то же в подтверждении). Это делает окно осознанным, а не молчаливым.

**Не делаем:** клиентскую подмену на людской спрайт при 404 (маскировка), автоперезагрузку реестра игрой (горизонтальный scope, инвариант 1), переупорядочивание «PNG последним» как способ убрать окно (не убирает: память игры всё равно старая).
