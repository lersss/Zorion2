## 0. Решения создателя (нормативно; источник — идея-интервью §0–§1, §10.1–§10.2)

1. **Контракт закрывает текущую потребность** — «сколько не хватает во внутреннем хранилище»; объём — разовый заказ на текущий дефицит, **не подряд** (§1.1).
2. **Внутреннее хранилище — новая сущность.** Ячейки создаются автоматически под **каждую** потребность (не только ингредиенты рецептов), **изолированы**; у каждой ячейки свой максимальный порог как **доля от общего размера**, **Σ долей = 100 %**; ячейка может быть недозаполнена (§1.4).
3. **Размер хранилища — свойство постройки** (поле объекта), **растёт со ступенью — ручкой студии; от населения не зависит** (уточнение 2026-09-25, §10.3 идеи-интервью); категория/тип постройки — классификация, размер — её свойство (§1.4).
4. **Выходной продукт (пища, очищенная вода) — в своей ячейке**, население ест из неё (§1.4).
5. **Два вида потребности** (зонтик «потребность постройки»): **потребность населения** (позиция с эффектом; дефицит бьёт по людям) и **потребность производства** (ингредиент/вход рецепта; дефицит = простой производства, без эффекта) (§1.2/§1.3).
6. **Заказы рождает сама постройка**, глядя на свои потребности; автоматически, владелец руками не жмёт (§1.2).
7. **Платит владелец**. **Эскроу снимается заранее** (при публикации). **Нет денег → контракт публикуется бесплатно** (биржа/NPC не возьмут 0-профит). Игрок-владелец тоже авто-заказывает со своего счёта; привёз сам себе — деньги идут ему (§1.5).
8. **Пока по нужде едет взятая доля — новых долей на ту же нужду нет** («нет места в хранилище под две доли») (§1.7).
9. **Минимальный UI нового входит в объём ЧК2а** (ячейки хранилища, строка нужд/дефицита, рождённые заказы на доске) — живое уточнение 2026-09-25 (§10).
10. **Владелец без поселений не бывает** — только видение; легаси-поселения без владельца существуют (решение Г1) и заказчиком быть не могут (§1.10, §2 п.5 идеи).

### 0.2. Решения гейта 2026-09-25, вторая порция (ревизия 4; F1–F4)

17. **F2 — пропорциональное деление входного ресурса между потребителями.** «Входной ресурс должен пропорционально поделиться между двумя его потребителями». Если на одну входную ячейку (один товар) претендуют **несколько потребителей** (несколько веток и/или население) — доступный запас делится **пропорционально их потребности** (не по порядку, не поровну) (§1.4, §4.4, §5.7).
18. **F3 — доля входного товара ∝ вхождениям в рецепты.** Доля ячейки при делении хранилища **пропорциональна числу вхождений товара во входы рецептов** (чем в больше рецептов входит — тем крупнее доля); один товар — одна ячейка (§1.3, §9). Прежняя эвристика «у неизвестного — вес 1» **отменяется**. **Подстраховка (принято, §18 п.30):** товар с эффектом (потребность населения) получает минимальный ненулевой вес `max(occurrences, 1)` — ячейка и заказы есть всегда (§1.3/§4.2/§9).
19. **F4 — цепочка внутри пересчёта, вариант A.** В одном пересчёте каждая ветка стартует от состояния на начало; свежий выход одной ветки становится входом другой при **следующем** пересчёте (§5.7, §18 п.27).

## 1. Решение (суть)

### 1.1. Внутреннее хранилище — новая сущность

**Архитектурный фильтр (обязательные развилки):**

| Развилка | Ответ |
|---|---|
| **Природа** | **Состояние-хранилище** (текущее количество товара), не событие и не лог. Записей у объекта много (по одной на товар) → это **таблица записей**, а не поля объекта. |
| **Владелец** | Записи у **многих** объектов: поселение сейчас, постройка-производитель (релиз 2 фабрик), флот — будущее → **полиморфный владелец** `owner_type`/`owner_id` (по образцу `buildings`). |
| **Расширяемость** | Второй **владелец** — значение `owner_type`; второй **вид потребности** (население/производство) — **производная классификация** (от `params.effects` и состава рецептов), а не тип записи. Схема переживает и то, и другое. |

**Внутреннее хранилище** — физический запас объекта: один товар — одна ячейка. Сумма порогов ячеек = размер хранилища.

### 1.2. Отношение к `settlement_branch_buffers` — **замена**, а не надстройка

**Решение: ячейки — единственный физический запас объекта; `settlement_branch_buffers` как носитель остатков ретайрится** (принято, F1 — §3; полный перечень потребителей и план замены — §4.4).

- вход ветки (компоненты рецепта) — списание из **ячеек компонентов**;
- выход ветки (товар-выход) — приход в **ячейку товара-выхода**;
- население ест из **ячейки** выходного товара (слой потребности `needs.go`), а не из буфера ветки;
- добор из залежей — списывается из `deposits` **в производство** (уменьшенный остаток пишется обратно); **в ячейку не кладётся** (иначе двойной учёт: залежь — отдельный запас планеты, не хранилище постройки).

**Причина (названная цена надстройки):** два хранилища одного товара = двойной учёт («один факт — одно место»); товар без ветки (напр. «пища» форпоста без рецепта) не имел бы носителя для привоза. Разбор — §3, развилка F1.

**Что физически меняется:** таблица `settlement_branch_buffers` (000064) выводится из обращения; данные мигрируют в ячейки (агрегация по `good_id` через ветки поселения), затем таблица ретайрится (§4 — безопасный порядок). `ProcessBranch` (чистая функция) **не меняется по математике** — репозиторий собирает `Branch.Input` из ячеек компонентов и пишет результат обратно в ячейки. Обход веток — детерминированный (по `settlement_branches.id`); несколько потребителей одного входного товара делят запас **пропорционально заявке** (F2 — §1.4/§5.7), а не «первому по порядку»; порядок нужен только для детерминизма тай-брейков (равные заявки) и записи.

### 1.3. Ячейка: порог-доля, размер, дефицит

- `cap_i = storage_size × cap_share_i / Σ cap_share` — порог ячейки; нормализация гарантирует **Σ порогов = 100 % размера** (защитный инвариант, §4.2).
- `deficit_i = max(0, cap_i − amount_i)` — **складской** дефицит (не суточный расход): объём заказа = `⌊deficit_i⌋`.
- `storage_size` — свойство экземпляра (`settlements.storage_size`), записывается owner-проходом из ручки каталога `producer_types.params.storage.size` **типа поселения** (текущей ступени ладдеры); у типа без ручки — дефолт-константа `StorageSizeDefault` (§9). Размер — ручка студии по типу/ступени; роста от населения нет (решение создателя 2026-09-25).
- Порог ячейки — `cap_share` (доля/вес) ячейки. Источник веса (**F3**): (1) явная ручка `producer_types.params.storage.shares` (карта `товар → доля`); (2) иначе — **число вхождений товара во входы рецептов** (`recipe_components`, входы; чем в больше рецептов входит — тем крупнее доля). Прежняя эвристика «у неизвестного — вес 1» **отменяется**. Один товар — одна ячейка. Нормализация (§4.2) сохраняется: `Σ порогов = storage_size`.

**Подстраховка от «веса 0» (F3, принято — §18 п.30).** Товар, не входящий ни в один вход рецепта, даёт вес `0` → порог `0` → ячейки/заказов по нему нет — молчаливая дыра в основном цикле для **потребности населения** (позиция с эффектом; напр. выходной продукт, в рецептах-входах не встречающийся). Правило: **товар с эффектом (потребность населения) всегда получает минимальный ненулевой вес** — `weight = max(occurrences, 1)`; ячейка и заказы у него есть всегда. Товар-компонент без эффекта и без вхождений вес 0 сохраняет (порог 0, заказов нет — не дыра). Явная ручка `params.storage.shares` по-прежнему побеждает (`max` применяется к дефолту вхождений, не к ручке).

### 1.4. Два вида потребности

| | **Потребность населения** | **Потребность производства** |
|---|---|---|
| Что это | позиция (`goods.name_norm`) с эффектом (`params.effects`) | позиция-компонент рецепта (`recipe_components`), вход |
| Дефицит | бьёт по людям (эффект «голод»/«жажда» через `needs.go`) | простой производства (ветка инертна), **эффекта нет** |
| Кто ест из ячейки | население (слой потребности) | ветка-потребитель |

Классификация **выводится**, не хранится: товар с привязкой к эффекту — потребность населения (она же может быть и входом); товар-компонент без эффекта — потребность производства. Один товар — одна ячейка.

**Несколько потребителей одной ячейки (F2).** Если на одну входную ячейку (товар) претендуют несколько потребителей — несколько веток и/или население — доступный запас делится **пропорционально потребности** потребителей, а не по порядку и не поровну. Потребность ветки — скорость потребления компонента рецепта; потребность населения — суточный спрос позиции. Формула/атрибуция — §5.7, чистые функции — §4.2. При единственном потребителе его доля = весь базис (§5.7) — конкуренции нет.

**Комбинированный случай (товар одновременно выход/потребность населения и вход рецепта).** Двойного счёта нет при **одной формуле и одном базисе** (§5.7, §7.1). Все потребители ячейки берут из **базиса** — количества на начало прохода; **F4 (вариант A):** свежий выход текущего прохода становится входом только при **следующем** пересчёте, в этом же проходе потребителям не виден. Производство в том же проходе **прибавляет** выход в ячейку. Итог ячейки за проход — `basis + ΣProduced − Σconsumed_by_branches − drawn_total` (кламп ≥ 0); базис берётся на начало прохода **один раз**, «доступный объём» не считается дважды.

### 1.5. Автор-поселение и плательщик

- `contracts.author_type = 'settlement'`, `author_id = settlements.id`; CHECK расширяется (миграция).
- Плательщик резолвится от владельца: `settlement → settlements.owner_type/owner_id → счёт владельца` (глубина 1). `owner_id IS NULL` (легаси, Г1) → `ErrPayerUnresolved` — поселение не заказчик.
- **D4: владелец-агент платит со счёта фракции.** `settlements.owner_type='agent'` → `npc_agents.owner_faction_id` → `account('faction', …)` (канон `2026-09-22-деньги-и-эскроу` §4/§6). Если `owner_faction_id IS NULL` (фракция перегенерирована/удалена) → `ErrPayerUnresolved`. **Сужение формулировки (N6):** «`account('agent', id)` плательщиком быть не может» ложно как общее утверждение — ветка `authorType='building'` при `owner_type='agent'` уже возвращает счёт агента (`contract_repository.go:784–786`). Сужено до **`settlements.owner_type='agent'`**: там платим со счёта фракции по D4, а не со счёта агента.
- Планета публикации — `settlements.planet_id`.
- Эскроу запирается **заранее** при публикации. Владелец не в силах покрыть пакет → **пакет публикуется бесплатно** (награда 0, эскроу 0) — канон-правка §5.2, код-обход §5.5. Игрок-владелец авто-заказывает со своего счёта; сам себе привёз — эскроу возвращается ему (существующий `Complete`), спец-кода не нужно.

### 1.6. Рождение заказов из дефицита (ленивая доска)

`boardNeedsFor` наполняется реальным источником: для каждой планеты — поселения на ней, для каждого поселения — ячейки и их складской дефицит; дефицит → `BoardNeed` (автор — поселение) → существующая материализация доски (`MaterializeBoard`, кадэнс `MinPersistInterval`, порядок `contract_board_state → contracts → accounts`). Ничего «реактивного» не заводится: **стоячее правило владельца — порог ячейки, датчик — дефицит ячейки, доска материализуется лениво на чтении** (канон §0.4 сохраняется по существу; уточняется источник целевого уровня — §5.1).

**Свежесть источника (**F1**).** Доска перед материализацией **пересчитывает** хранилище поселений планеты, а не читает ячейки «как есть»: витрина и материализация видят числа на момент чтения (создатель: «30-минутная информация при прямом наблюдении неприемлема»). Пересчёт идёт **до** транзакции доски, по поселению (свой tx, advisory-лок + `FOR UPDATE`), запись — только при изменении чисел. Порядок и блокировки — §7 пп.1–2, §10.

**Устойчивость материализации к одному проблемному автору (N1).** `boardNeedsFor` **исключает ownerless-поселения** (`owner_id IS NULL`) из нужд — они не заказчики по Г1 (§1.5), их `resolvePayerAccountQ` = `ErrPayerUnresolved`. Дополнительно материализация **устойчива к отказу отдельной нужды**: ошибка резолва плательщика / публикации одной доли логируется и **пропускается**, не роняя публикацию остальных (не откатывает `MaterializeBoard` целиком). Иначе любой единичный сбой = **молчаливая блокада** доски всей планеты, включая владельческие поселения.

### 1.7. Правило «доля в работе — новых долей нет»

Публикуемая цель пакета — **`0` при непустых `taken`** (N5): пока доля пакета `taken`, целевой набор открытых долей **пуст** — существующие открытые снимаются сверкой с возвратом залога, новые **не публикуются** (совпадает с T9 и правилом «пока доля taken — новых нет»). При отсутствии `taken` цель = складской дефицит (нарезка `SliceShares`). Витрина при этом продолжает показывать **физический дефицит** и строку «в работе (курьер)». Это смена канона §5.8 (P1 → P2 для публикации) — §5.3.

**Бесплатно опубликованная доля остаётся бесплатной до протухания (M2, названное следствие).** Сверка `reconcileShares` (`contract_board_repository.go:302`) сравнивает текущую открытую долю с целевой только по `(share_index, объём)`. Значит, если пакет был опубликован с `reward = 0` (у владельца не было денег), а к следующему чтению баланс восстановился — сверка **не переиздаст** долю с наградой: она доживёт до истечения окна (`SupplyOfferWindow`), после чего `ExpireDue` её снимет, и следующая материализация выпустит новую — уже с наградой. Последствие **принято** в ЧК2а: цена — ЧК2в, окно короткое; альтернатива (включать `reward` в ключ сверки) — §18 В12.

## 4. Модель данных и миграция (номер `000086`, бронь `@manager` — `COORDINATION.md`)

### 4.1. Таблицы/колонки

```sql
-- Размер хранилища — свойство экземпляра (F2-A). Пишет owner-проход.

    cap_share   DOUBLE PRECISION NOT NULL DEFAULT 0 CHECK (cap_share >= 0),

    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),

);
CREATE INDEX IF NOT EXISTS idx_storage_cells_owner ON settlement_storage_cells (owner_type, owner_id);

```

**Миграция данных:** создать ячейки для поселений, агрегировав `settlement_branch_buffers` по `good_id` (сумма `amount` по веткам и направлениям одного поселения); проставить `storage_size` из ручки/дефолта; `cap_share` — из ручки, иначе **вес = число вхождений товара во входы рецептов (F3, §1.3)**. Идемпотентность — по `IF NOT EXISTS`/`ON CONFLICT DO NOTHING`; порядок «ALTER … REFERENCES до первого CREATE TABLE» (`PITFALLS` «БД и шелл»).

**Каскады:** `owner_id` без FK (полиморфный, как `buildings.owner_id`); `good_id` FK CASCADE; удаление поселения — **явный DELETE ячеек** (нет FK на `settlements`), включить в проходы удаления/очистки; таблица — в `truncateTables` (`admin_universe.go:62`).

### 4.2. Чистые функции (`internal/economy/settlement/storage.go`, новый)

- `StorageCaps(size float64, weights map[int64]float64) map[int64]float64` — пороги; Σ порогов = `size` (нормализация весов; Σ весов = 0 → пороги 0).
- `GoodWeights(explicit map[int64]float64, occurrences map[int64]int, effectBound map[int64]bool) map[int64]float64` — вес ячейки (**F3**): явная ручка `params.storage.shares` побеждает, иначе `occurrences` — число вхождений товара во **входы** рецептов, а для товара с привязкой эффекта (потребность населения) — **`max(occurrences, 1)`** (подстраховка от «веса 0», §1.3). Детерминирована (без RNG).
- `AllocateProportional(available float64, needs map[consumer]float64) map[consumer]float64` — пропорциональное деление входной ячейки между потребителями (**F2**): при одном потребителе — весь `available`; при нескольких — `alloc_c = available × need_c / Σ need`; `Σ need = 0` → потребители инертны (ячейка не трогается). Потребитель не берёт больше своей заявки (`claim_c = need_c × Δt_c`). Детерминирована; тай-брейки (равные потребности) — по стабильному порядку потребителей (ветка — `settlement_branches.id`, население — после/перед ветками, порядок фиксирован); без RNG.
- `CellDeficit(cap, amount float64) float64` — `max(0, cap−amount)` (без ссылки на `contracts.Deficit` — разные величины: там суточный, здесь складской).
- Классификация ячейки: `population` (есть привязка эффекта) / `production` (компонент рецепта) — функция от привязок и состава рецептов, **не колонка**.

### 4.3. Реестр нужд (авто-создание ячеек)

Набор нужд поселения = `keys(params.effects)` ∪ `goods_id(recipe_components веток)`. Сверка (образец `topUpBranchInputs`):
- нет ячейки → создать (`amount = 0`, `cap_share` = `GoodWeights` — ручка, иначе вхождения, для товара с эффектом — `max(occurrences, 1)`, **F3**);
- ячейка вне набора нужд → **сохранить остаток** (это реальный запас), заказов по ней нет; удалить, когда `amount = 0`;
- при переходе ступени склады сбрасываются (существующее поведение `applyStageTransition` заменяется — §5.6): ячейки обнуляются, размер пересчитывается (веса — по F3).

### 5.7. Базис, деление входной ячейки и порядок (F2, F4; дельта к потреблению §7.3/§7.4)

При нескольких ветках с одним товаром-выходом общая ячейка делает запись **складского базиса один раз на позицию**, а не суммой по веткам (иначе двойной счёт одного запаса). Формула **скорости** (§7.3) не меняется; меняется источник запаса (§7.4), деление входного ресурса между потребителями (**F2**) и цепочка (**F4**):

```
# 0) Базис ячейки товара K на НАЧАЛО прохода — ОДИН раз (не Σ O0_b).
#    F4 (вариант A): ветка стартует от начала прохода; свежий выход этого прохода
#    потребителям в этом же проходе НЕ виден.
basis_K   = amount ячейки товара K НА НАЧАЛО прохода

# 1) Потребности потребителей ячейки K за проход (F2):
#    ветка b (K — компонент её рецепта): need_b   = скорость потребления компонента, ед/сек
#    население (K — позиция с эффектом):  need_pop = D = PerSecond(norm_K, P), ед/сек
# 2) Деление базиса ПРОПОРЦИОНАЛЬНО потребности (F2):
#    один потребитель  → alloc_c = basis_K
#    несколько         → alloc_c = basis_K · need_c / Σ need   (Σ need = 0 → потребители инертны)
#    потребитель не берёт больше своей заявки: consumed_c = min(alloc_c, need_c · Δt_c)
alloc_b   = доля ветки b в базисе (F2)
alloc_pop = доля населения в базисе (F2); при отсутствии веток-потребителей = basis_K
# 3) Слой населения — на СВОЕЙ доле (формула скорости/порога не меняется):
p_K       = Σ_b p_b                       # покрытие = СКОРОСТЬ, по веткам (Σ Batches_b/DeltaSec_b)
D         = PerSecond(norm_K, P)
w1        = clamp01(1 − p_K / D)
t*        = (p_K < D) ? alloc_pop/(D − p_K) : +∞
w(t)      = (t < t*) ? 0 : w1
drawn_pop = alloc_pop − остаток доли населения   # фактическое списание из ячейки
# витрина ветки (детерминированно, без RNG): доля выработки; все ветки инертны → равные доли
drawn_b   = drawn_pop · Batches_b / Σ Batches_b   # Σ Batches_b = 0 → drawn_pop / n
```

- `NeedsSource.OutputBase` (`needs.go:56`) **убирается**; `NeedsInput` получает базис позиции (`BasisByPosition map[string]float64`, из ячеек на начало прохода) и **потребности потребителей** (ветки/население) для деления (F2); `positionTrajectory` получает `basis` позиции — для населения его **долю** `alloc_pop` (при конкуренции), а не `o0Sum = Σ OutputBase`. `drawn_b` атрибутируется ∝ `Batches` (витрина), физически списывается из общей ячейки.
- Дельта к спеке потребления §7.4: строка `buf = Σ O0_b по веткам K` заменяется на `buf = amount ячейки товара K`; при нескольких потребителях — `alloc_pop` (F2); точки разбиения по `Since`, кусочная `w`, `t*`, `recovery/load/порог` — без изменений. §7.3 (`coverage = p_K`, скорость) и §11.2 (вход доски) правятся дельтой §17.
- **Единая формула итога ячейки за проход (N3 + F2 + F4):** все потребители и производители работают от **базиса** на начало прохода (F4: свежий выход не виден в том же проходе); вход-ячейка делится между потребителями **пропорционально потребности** (F2). Итог ячейки товара = `basis_K + Σ Produced − Σ consumed_by_branches − drawn_pop`; для компонента — `basis_c − Σ consumed_by_branches`. Клампы ≥ 0. Базис берётся на начало прохода **один раз**; доли потребителей покрывают базис в сумме ровно один раз — двойного счёта товара «выход/потребность населения И вход рецепта» нет (`PITFALLS` «производство и потребность — разные слои; писать буфер дважды = двойной учёт»).

## 7. Рождение заказов (материализация)

**Порядок чтения доски (F1):** `ExpireDue(scope=планета)` → **пересчёт хранилища поселений планеты** (пп.1–2) → `MaterializeBoard` (пп.3–7) → `ListBoard`.

1. **Свежесть (F1, новая ступень — до открытия транзакции доски).** Для каждого поселения планеты **с непустым владельцем**, в детерминированном порядке `settlement_id`, выполняется **пересчёт хранилища** — owner-проход (`SyncSettlements`-совместимый), **своя транзакция**: `pg_advisory_xact_lock(hashtext(settlement_id))` + `FOR UPDATE settlements` (и ветки/залежи — как в owner-проходе). Транзакция пересчёта **закрыта до** открытия транзакции доски (§10). Результат — свежие ячейки (в памяти); они же — вход `boardNeedsFor`. Чтение ячеек «как есть» (последняя запись owner-прохода, лаг до 30 мин) **отменено** — создатель: «30-минутная информация при прямом наблюдении неприемлема».
2. **Запись при изменении (F1).** Пересчёт на пути доски идёт в режиме **`commitIfChanged`**: пишет в БД **только если числа изменились** (сравнение свежего состояния с хранимым). Изменилось — **полный owner-tx** (ячейки **и** чек-точки вместе — инвариант когерентности чек-точек `load_at ≈ processed_at ≈ computed_at` частичной записью не нарушается); не изменилось — no-op без записи. Пустые записи не плодятся: ячейка — только под потребность (§4.3), строка `contract_board_state` — только при непустых нуждах (§3.1 канона). Путь карточки планеты сохраняет канон 18a («простой визит» не пишет) — режим доски это **отдельное** поведение того же прохода.
3. `boardNeedsFor(planetID, fresh)` — реальный источник: поселения планеты (`settlements.planet_id`) с непустым владельцем (ownerless исключены — N1) → **свежие ячейки** (из п.1) + `storage_size` + веса → `BoardNeed{AuthorType: settlement, AuthorID, PlanetID, GoodID, Target: cap, Actual: amount, Capacities, BaseReward, WindowPreset}`. Ячейки/`settlements` в транзакции доски **не читаются** (они получены до неё).
4. Пакет — существующий ключ `<kind>:<planet>:<author_id>:<position>`; ячейки → складской дефицит → `SliceShares` (та же нарезка/округление вниз).
5. **Взятые доли:** перед сверкой по каждому ключу читаются `taken`-доли пакета; **при непустых взятых цель пакета = `0`** — существующие открытые доли пакета снимаются (`superseded`), новые **не публикуются** (N5). При отсутствии взятых — цель = складской дефицит.
6. **Бесплатная доля:** если владелец не покрывает пакет — весь пакет публикуется с `reward = 0`, `escrow_amount = 0`; остаётся бесплатной до протухания (§1.7, M2). Режим определяется предварительной развилкой ДО INSERT (§5.5).
7. **Отзывчивость:** кадэнс `MinPersistInterval` (30 мин) **сохраняется** (§18 п.20): он гейтит **материализацию** (публикацию долей), **не** пересчёт хранилища. Второго кадэнса/форс-материализации ЧК2а **не вводит**. Остаточное следствие (названо): при переходе ячейки через порог **появление нового заказа** всё ещё ждёт истечения кадэнса материализации (≤ 30 мин), тогда как **сами числа** уже свежие (F1).

### 7.1. Порядок прохода при общей ячейке (owner-проход)
1. Загрузка: поселения/ветки/залежи под `FOR UPDATE`, ячейки — в той же tx (advisory-лок поселения).
2. Деление входных ячеек (**F2**): для каждой входной ячейки считаются потребности потребителей (ветки-компоненты + население), базис делится пропорционально потребности (§5.7); кэш аллокации — на проход.
3. Производство (**F4**): ветки по `id`; `Branch.Input` — из **базиса** компонентов на начало прохода и распределённой доли (F2); свежий выход этого прохода потребителям не виден (F4). `ProducedLast` суммируется в ячейку выхода.
4. Потребность: население рисует `drawn_pop` из **своей доли** базиса (§5.7, F2); при единственном потребителе доля = весь базис.
5. Запись: компоненты = `basis − Σ распределённое_потребление`; выход = `basis + Σ ProducedLast − drawn_pop`; залежи — уменьшенные остатки; счётчики веток (`Eaten`, `EatenRate`) — по атрибуции ∝ `Batches`.

## 10. Инварианты и конкурентность

- **Писатели ячеек (N4/F1, честная формулировка):** **(1) owner-проход** поселения (свой tx под `pg_advisory_xact_lock(hashtext(settlement_id))`, `settlements`/ветки/залежи `FOR UPDATE`); **(2) админ-ручка правки входа** (`AddBranchInput` → инкремент ячейки); **(3) F1 — owner-проход, вызванный чтением доски**, тот же путь (1) в режиме `commitIfChanged` (§7 пп.1–2). Все три берут **тот же advisory-ключ владельца**.
- **Порядок локов админ-ручки входа (`AddBranchInput`, N4):** сейчас берёт только `LockBranchTx` (`branch_repository.go:449`, `FOR UPDATE` на строке ветки). Нужно: **сначала `LockOwnerTx`** (advisory-ключ владельца, `branch_repository.go:441`) — но `settlement_id` известен лишь из ветки, поэтому порядок: (1) читающий `SELECT settlement_id FROM settlement_branches WHERE id=$1` (без лока) → (2) `LockOwnerTx(settlement_id)` → (3) `LockBranchTx(branchID)` (`FOR UPDATE`) → (4) инкремент ячейки. Иначе админ-правка входа гоняется с owner-проходом (потеря/задвоение инкремента). `AddBranch` уже берёт `LockOwnerTx` первым (`admin_settlement_branches.go:105`) — эталон.
- **F1: разведение блокировок доски и пересчёта (анти-дедлок).** Пересчёт хранилища (F1) выполняется **до** открытия транзакции доски, **по поселению, последовательно** (`settlement_id` по возрастанию), каждый — в **своей** транзакции; лок `settlements`/ветки/залежи живёт **только внутри** транзакции пересчёта и снимается до начала транзакции доски. Транзакция доски сохраняет порядок `contract_board_state → contracts → accounts` и **не трогает** `settlements`/`settlement_storage_cells` (свежие ячейки получены до её открытия). Множества блокировок не пересекаются во времени → цикла/дедлока нет. **M4 снят/уточнён:** материализация доски `settlements` в tx не берёт; `FOR UPDATE settlements` берёт только пересчёт, и только в своём tx.
- **Детерминизм общей ячейки (F2/F4):** ветки обрабатываются по `settlement_branches.id`; вход-ячейка общего компонента делится **пропорционально потребности** (`alloc_c = basis · need_c / Σ need`, F2), тай-брейки при равных потребностях — по стабильному порядку (ветка — `id`); выход пишется после производства и в том же проходе потребителю не виден (F4).
- **Проверка + действие атомарно:** публикация доли — `INSERT` контракта/требования и запирание эскроу в одной tx (как сегодня); бесплатная публикация — тот же tx с `reward = 0` без `lockEscrow` (§5.5).
- **Карты под замком:** любые общие `map` (кэш ячеек, каталог) — под `sync.RWMutex`; per-pass карты owner-прохода — в одной горутине на поселение (advisory-лок), но общий кэш — только под мьютексом (`AGENTS.md` §0).
- **Идемпотентность:** повторный owner-проход с тем же `now` даёт `Δt = 0` (без изменений); повторная материализация в кадэнсе — no-op; повторное чтение доски без изменения чисел — no-op без записи (F1); нормализация порогов — детерминирована (без RNG).
- **Округление:** складской дефицит (DOUBLE) → `⌊⌋` до целого; `Σ долей = ⌊дефицит⌋`; сравнение масс — нестрогое (образец §5.7 спеки контрактов).
- **Честная дельта экономики чтения (F1, названная цена).** Было: чтение доски = plain SELECT нужд (вне tx) + одна материализация по кадэнсу (30 мин). Стало: чтение доски = **пересчёт хранилища каждого поселения планеты** (N owner-проходов, каждый — свой tx с advisory-локом) + материализация по кадэнсу. **Кадэнс доски не продлевается** (правило «разные чек-точки» и `MinPersistInterval` материализации сохранены), но стоимость чтения растёт **∝ числу поселений планеты**; при активном производстве числа меняются на каждом чтении → пересчёт пишет на каждом чтении. Это осознанная цена решения F1 (идея §10.2 п.11: «расход на многопользовательскую нагрузку — на контроле; при возражении создателя — переиграть»). Кандидат оптимизации (батч/порог дельты/кэш «недавно считали») — вне ЧК2а, для `@developer`/`@balancetester`; **не влияет** на состав ЧК2а и не отменяет F1.
- **Пометка (следствие F1, не отмена):** стоимость чтения доски растёт **∝ числу поселений планеты**; замер и оптимизация — на этапе разработки (`@developer`), при регрессии — вынести создателю.

## 12. Критерии приёмки (TDD; тест до кода; DoD — `AGENTS.md` §2, `-race -short`)

- **T1.** Миграция `000086` идемпотентна; данные `settlement_branch_buffers` агрегированы в ячейки по товару; таблица ретайрена безопасно (§4.1/§18 В16), данные старого буфера сохранены.
- **T2.** `resolvePayerAccountQ('settlement', id)`: владелец `player`/`faction` → его счёт; владелец `agent` → счёт фракции (`owner_faction_id`); `owner_id IS NULL`/`owner_faction_id IS NULL` → `ErrPayerUnresolved`; поселение без владельца **не публикует** заказы.
- **T2a (N1).** **Ownerless не блокирует владельческие:** планета с ownerless-поселением и владельческим — `boardNeedsFor` не включает ownerless в нужды; материализация публикует заказы владельческого; отказ одной нужды (искусственный `ErrPayerUnresolved`) **не роняет** публикацию остальных (доска не блокируется молча).
- **T3.** `ResolvePublicationPlanet('settlement', id)` → `settlements.planet_id`.
- **T4 (F3).** Вес ячейки: явная ручка `params.storage.shares` побеждает; иначе вес = **число вхождений товара во входы рецептов**, для товара с эффектом — **`max(occurrences, 1)`** (подстраховка от «веса 0», §1.3); `StorageCaps`: Σ порогов = `storage_size`; нулевые веса (у товара без эффекта и без вхождений) → пороги 0; повторный вызов детерминирован.
- **T5.** Авто-создание: ячейки появляются под каждую потребность (эффекты + компоненты рецептов); товар с эффектом классифицируется `population`, компонент без эффекта — `production`.
- **T6.** Складской дефицит = `max(0, cap − amount)`; заказ нарезается `SliceShares`; `⌊дефицит⌋ = 0` → пакета нет.
- **T7.** Публикация: `author_type='settlement'`, `publication_planet_id = settlements.planet_id`, эскроу заперт со счёта владельца; планета не `factions.homeworld_id`; `direct_target_type` не расширен.
- **T8.** Нет денег: владелец не покрывает пакет → весь пакет публикуется с `reward = 0`, `escrow_amount = 0`; CHECK не падает; записи `money_operations` нет; `escrow_locked` не пишется; guard `ErrInvalidReward` не срабатывает (D5). **Развилка режима — ДО INSERT (§5.5):** контракт вставляется уже с `reward = 0` (не «переписывается» после INSERT).
- **T9.** «Доля в работе»: при `taken`-доле пакета **цель = 0** — новые открытые доли не публикуются, существующие открытые снимаются с причиной `superseded` (залог возвращён); витрина показывает физический дефицит и «в работе».
- **T10 (F1).** Кадэнс материализации: повторное чтение доски в пределах `MinPersistInterval` — ноль публикаций; при этом пересчёт хранилища (F1) выполняется в **своей** tx до открытия tx доски, tx доски ячейки/`settlements` не читает; порядок локов доски `contract_board_state → contracts → accounts` не ломается (репродукция — `@tester`).
- **T11 (F2).** Замена буферов: выход ветки приходит в ячейку товара-выхода; компоненты списываются из ячеек; **несколько потребителей одного компонента делят запас пропорционально потребности** (F2), детерминированно (тай-брейк по `id`); залежь-добор списывается из `deposits` в производство и **не** кладётся в ячейку; двойного учёта нет.
- **T12.** Население ест из ячейки: `needs.go`-покрытие считается от ячейки; базис — ячейка (один раз; при конкуренции — доля `alloc_pop`, F2), `Batches` — покрытие; при пустой ячейке `w` растёт (эффект), при заполнении — падает (инъекция `now`, без реального Δt — `PITFALLS` «тест ленивого пересчёта»).
- **T13.** Переход ступени: ячейки обнуляются (`storageCellsClearSQL`), `storage_size` и веса (F3) пересчитаны; ячейка вне набора нужд с остатком сохраняется, пустая — удаляется.
- **T14.** Каскады/очистка: удаление поселения/планеты/товара убирает ячейки; `settlement_storage_cells` в `truncateTables` (иначе `TRUNCATE planets` падает).
- **T15.** Видимость: `storage` есть у админа и (под настройкой) у игрока в `presence`, включая производственные ячейки; в `snapshot`/`scan`/`none` блока нет; при `arithmeticVisible=false` блок пуст; `planetsHaveSettlementArithmetic` учитывает `Storage` (иначе гейт не применяется).
- **T16.** Детерминизм: два наблюдателя в один момент видят одинаковый набор заказов/порогов (RNG отсутствует); при нескольких ветках с одним выходом базис ячейки считается один раз (нет двойного счёта); деление входной ячейки при равных потребностях детерминировано (тай-брейк по `id`).
- **T17.** Потребители буферов (§4.4): снимок не несёт `Output` (старый снимок с `output` парсится); контент-импорт `guardGood` проверяет `settlement_storage_cells`; `settlement_stage.go` очищает ячейки; админ-ручка входа инкрементит общую ячейку (порядок локов `LockOwnerTx → LockBranchTx` — N4); `stripBranchInputs` отсутствует.
- **T18 (N3).** Комбинированный товар (выход/потребность населения И вход рецепта): все потребители берут из базиса, поделённого ∝ потребности (F2); итог ячейки = `basis + ΣProduced − Σconsumed_by_branches − drawn_pop`; двойного счёта нет (ячейка не уходит в минус клампом).
- **T19 (N7-доп.).** DTO ячейки несёт `code` (`goods.code`); поле аддитивно, старые потребители не ломаются.
- **T20 (F1).** **Свежесть доски:** чтение доски пересчитывает хранилище поселений планеты — витрина/материализация видят числа на момент чтения, а не последнюю запись owner-прохода; запись — **только при изменении** чисел (пустые записи/строки не создаются); повторное чтение без изменения — no-op без записи; пересчёт (свой tx, advisory + `FOR UPDATE settlements`) и tx доски **разведены** — дедлок не воспроизводится (репродукция — `@tester`).
- **T21 (F2).** **Пропорциональное деление входной ячейки:** несколько потребителей (две ветки и/или ветка+население) делят запас ∝ потребности; не по порядку, не поровну; при единственном потребителе доля = весь базис; детерминизм (равные потребности → тай-брейк по стабильному порядку).
- **T22 (F3).** **Вес ячейки = число вхождений товара во входы рецептов;** явная ручка `params.storage.shares` побеждает; Σ → `storage_size` нормализацией; товар с эффектом (потребность населения) при нулевых вхождениях получает **вес 1** (`max(occurrences, 1)`) — ячейка и заказы есть всегда (§18 п.30).
- **T23 (F4).** **Цепочка:** в одном пересчёте ветка-потребитель **НЕ** видит свежий выход ветки-производителя того же прохода; выход становится входом при **следующем** пересчёте.
