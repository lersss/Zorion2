## 0. Резюме и решения создателя

Одно полотно дерева построек («Производители») разбивается на **пять одинаковых разделов**:
**Колонии · Фабрики и автофабрики · Лаборатории · Добывающие платформы · Энергостанции**.
Кнопка «Производители» убирается; «Товары» и «Предметы» остаются рядом.

**Решение создателя (2026-09-25): «устойчивость сразу».** Раздел вида построек — **свойство
каталога**, а не сравнение имён: переименование типа-корня **не должно ломать** привязку к разделу.
Поэтому привязка — **поле данных `producer_types.section`**, а не нормализованное имя корня
(вариант черновика `@uidesigner` отклонён).

**Второе решение (форма управления).** Активных разделов — пять канонических плюс служебный
«Прочее» (корни без раздела/с неизвестным разделом). «Прочее» — **полноправный активный раздел
интерфейса** (можно встать на него), но **не значение БД** (`other` в `producer_types.section` не
пишется). Ряд «Постройки» (`#segBuildings`) виден **всегда** — это единственная точка входа в
разделы построек после удаления кнопки «Производители»; клик по разделу переключает ветку на

## 2. Модель каталога

### 2.1. Развилки о природе сущности (обязательная сверка)

1. **Природа.** `section` — **атрибут существующей сущности** (`producer_types`), не событие и не
   лог: это классификация типа-корня, с которой связан выбор интерфейса (раздел студии). Отдельной
   таблицы нет — «один факт — одна колонка».
2. **Владелец.** Записи принадлежат **многим** типам-корням (у каждого своё значение); носитель —
   только тип-корень (`parent_id IS NULL`).
3. **Расширяемость.** Одно поле со значениями из **открытого** списка (раздел интерфейса): новый
   раздел — правка клиентской константы + значения в данных, **без миграции**. Схема второй и
   третий раздел переживает без изменения таблиц.

### 2.2. Поле

| Свойство | Значение |
|---|---|
| Колонка | `producer_types.section TEXT NULL` |
| Хранимые значения | `colony` · `factory` · `lab` · `mining` · `energy` |
| Пустое/неизвестное | `NULL` или значение вне списка → клиент относит корень в раздел «Прочее» |
| «Прочее» | **активный раздел интерфейса**, но **не значение БД**: `other` в `producer_types.section` не пишется |
| Носитель | только тип-корень (`parent_id IS NULL`); у подтипов — `NULL` |
| Наследование | раздел подтипа = раздел его корня (через `parent_id`); клиент вычисляет, в БД не дублируется |
| `CHECK` в БД | **нет** (список разделов — данные интерфейса; новый раздел не должен требовать миграции) |
| Валидация | **в хендлере** (§5.2): значение из пяти или пусто; иное непустое → 400. Репозиторий хранит как есть |
| Уникальность/индекс | не нужны (≈42 строки, не ключ) |

Соответствие «канон-имя → `section`» (только на момент бэкфилла миграции; не правило привязки):

| `name_norm` (тип-корень) | `section` | Раздел кнопки |
|---|---|---|
| `колония` | `colony` | Колонии |
| `фабрика` | `factory` | Фабрики и автофабрики |
| `автофабрика` | `factory` | Фабрики и автофабрики |
| `лаборатория` | `lab` | Лаборатории |
| `добывающая платформа` | `mining` | Добывающие платформы |
| `энергостанция` | `energy` | Энергостанции |

### 2.3. Отклонения от модели менеджера (обоснованы)

- **«Прочее» — достижимый активный раздел интерфейса, но не значение БД.** Если бы `other`
  писался в БД, то «вернуть корень в канон» означало бы правку данных; сейчас достаточно поменять
  раздел в карточке. Термин «виртуальный» к «Прочее» означает только «значение не хранится», а не
  «недостижимый».
- **Одно место правды — корень.** Значение у подтипа не хранится: копия ломала бы привязку при
  смене родителя.
- **Правка `internal/goodsstudio/model/types.go` не требуется** (уточнение факта): модель
  `model.State` несёт товары/категории/привязки рецептов, а тип производителя живёт в
  `repository.ProducerTypeRow` (`internal/repository/producer_repository.go`). Реальная правка
  модели — там (§5), плюс DTO состояния в `studio_handlers.go`.

## 3. Миграция `000085` (единственная новая)

**Файл:** `migrations/000085_producer_sections.sql`. Последняя в дереве — `000084`; `000083` —
ренейм канон-имён; `000085` — бронь менеджера (в `docs/DB.md` строка `000085` ещё не заведена —
вносится дельтой, §13). **Вторая миграция не заводится.**

Состав (идемпотентно, только `NULL`, без `CHECK`, без индекса):

```sql
-- 1) Колонка раздела (значения — данные интерфейса; CHECK не ставится).
ALTER TABLE producer_types ADD COLUMN IF NOT EXISTS section TEXT;

-- 2) Бэкфилл канон-корней по name_norm (только типы-корни, только NULL — повторный прогон no-op).
UPDATE producer_types pt SET section = m.section
FROM (VALUES
    ('колония','colony'),
    ('фабрика','factory'),
    ('автофабрика','factory'),
    ('лаборатория','lab'),
    ('добывающая платформа','mining'),
    ('энергостанция','energy')
) AS m(name_norm, section)
WHERE pt.parent_id IS NULL AND pt.name_norm = m.name_norm AND pt.section IS NULL;
```

Правила:
- бэкфилл **только по данным** (`parent_id IS NULL`), не по литералам-двойникам: подтипы
  («Фабрика продовольствия», лаборатории-подтипы, ступени ладдеры) не трогаются;
- корень с переименованным на dev именем (не канон) остаётся `NULL` → «Прочее»; данные целы,
  создатель назначает раздел в карточке;
- отсутствие корня — no-op;
- идемпотентность: заполняются только `section IS NULL`; повторная накатка/накатка после сида
  ничего не меняет.

## 5. Модель и API

**Адрес валидации (однозначно):** проверка значения `section` — **только в хендлере** (§5.2),
репозиторий хранит значение **как есть**. Репозиторий не возвращает 400 и не фильтрует список.

### 5.1. Репозиторий (`internal/repository/producer_repository.go`)

- `ProducerTypeRow`: `+ Section sql.NullString`.
- `loadProducerTypes`: в `SELECT` добавляется `section` (снимок каталога → `CatalogSnapshot`,
  откуда поле уезжает и в состояние студии, и — позже — в экспорт контента).
- `CreateProducerType(...)`: сигнатура `+ section *string`; INSERT пишет `section` **как есть**
  (без проверки списка значений и без проверки «корень/подтип» — это делает хендлер).
- `UpdateProducerType(...)`: сигнатура `+ section *string` (nil = не менять); `UPDATE
  producer_types SET section = $1`; смена раздела **не** входит в кортеж уникальности подтипа
  (`subtypeTupleChanged`) и **не** влияет на слот-инвариант С4.
- `ProducerTypeView` (DTO состояния, `studio_handlers.go`): `+ Section string json:"section,omitempty"`;
  `buildStateView`/`producerTypeView` заполняют из `Section.String`.

### 5.2. Хендлеры (`internal/handlers/studio_handlers.go`)

| Ручка | Изменение |
|---|---|
| `POST /studio/api/producers` | тело `+ section *string`; валидация (§5.2 ниже) → передаётся в `CreateProducerType` |
| `PUT /studio/api/producers/{id}` | тело `+ section *string`; валидация → передаётся в `UpdateProducerType` |
| `GET /studio/api/state` | `producer_types[].section` — аддитивно к `ProducerTypeView` |

**Валидация `section`** (одна функция на обе ручки, **в хендлере**):
- допустимы `colony|factory|lab|mining|energy` или пусто/`null`; иное непустое → **400**
  «неизвестный раздел постройки»;
- значение непусто и `parent_id != NULL` (тип — подтип) → **400** «раздел задаётся у типа-корня и
  наследуется подтипами».

Обоснование «без CHECK»: список разделов — данные интерфейса; новый шестой раздел не должен
требовать миграции. Импорт контента переносит `section` **дословно** (без строгого списка): прод
не должен падать на новом значении, придуманном в dev (клиент отнесёт неизвестное в «Прочее»).

  `PROD_SECTION_KEYS` или `"other"` (раздел «Прочее»).
- `prodSectionOf(p)` — раздел записи: у корня — `p.section`, если он в `PROD_SECTION_KEYS`,
  иначе `"other"`; у подтипа — раздел его корня (по `parent_id`), иначе `"other"`.
- `prodSectionRoots()` — корни текущего раздела (проходят `prodVisible`, как сейчас); для
  `"other"` — корни с `prodSectionOf === "other"`.
- `renderBuildingsTabsUI()` — `.on` у активной кнопки (для `"other"` — у `#branchProdOther`),
  видимость `#branchProdOther` (есть ли хоть один корень вне канонических значений). Если ветка
  не `"producers"`, `.on` снимается со всех кнопок раздела.
- `setProdSection(key)` — принимает любой из шести ключей (включая `"other"`; **не клампится**),
  ставит `branch="producers"` (техническое имя группы), активный ключ, пишет `gs_prodSection`,
  сбрасывает выбор/попап, `renderAll()`.

- «Прочее»: «Корни без раздела. Откройте карточку типа и выберите раздел.» — раздел показывает
  корни без раздела/с неизвестным значением и позволяет назначить им раздел через карточку
  (незнакомые/переименованные до привязки значения не теряются).

### 6.6. Состояние вида

- Активный раздел — `gs_prodSection`; допустимые значения — пять канонических ключей или
  `"other"`. Дефолт `"colony"`; легаси `gs_branch === "producers"` → «Колонии»; значение вне этих
  шести → `"colony"`. **`"other"` не клампится к `"colony"` ни при клике, ни при восстановлении из
  `gs_prodSection`** (исключение — §7: раздел «Прочее» опустел, тогда откат на «Колонии»).
- Все пять разделов — одна рабочая область: общий `gs_prodZoom/gs_prodPanX/gs_prodPanY`
  (переключение раздела масштаб не меняет), при смене раздела pan центрируется `centerProdTree()`;
  условия `branch === "producers"` в `saveView` (1226)/`centerTop` (1243)/`centerOn` (1283) и
  восстановление вида при входе остаются.
- **Выбор узла при смене раздела сбрасывается** (`selected = null`, попап закрыт): узел другого
  раздела на новом полотне недостижим.

## 7. Краевые случаи

- **Переименование корня** («Колония» → «Поселение»): раздел **не меняется** (цель фичи) — корень
  остаётся в «Колониях». Кнопка «Прочее» не появляется.
- **Корень без раздела (`NULL`)**: «Прочее»; кнопка показывается, пока такой корень есть; данные целы.
- **Расовый/новый корень**: раздел задаёт создатель в форме «+ тип» (обязателен, предзаполнен
  активным) или в карточке; расовость и скрытость (`prodVisible`, `prodCatHidden`, `prodCatWinner`,
  лестница скрытости) работают как раньше.
- **Активен «Прочее», корней без раздела не осталось**: откат на `gs_prodSection="colony"` +
  `renderAll()`, кнопка «Прочее» скрывается (раздел опустел — это не кламп `"other"` при
  восстановлении).
- **Нет ни одного корня вообще**: все разделы пусты, «Прочее» скрыто, каждый показывает
  сообщение §6.5; «+ тип» работает.
- **Корень скрыт уровнем расовости**: раздел пуст, сообщение отличается от «типов нет».
- **Переименован подтип или сменился его корень**: раздел подтипа = раздел нового корня (наследование).
- **«Товары»/«Предметы»**: не меняются; ряд `#segBuildings` на них **остаётся видимым**, но ни одна
  кнопка раздела не подсвечена; клик по кнопке раздела переключает на постройки. Позиция графа
  товаров (`gs_zoom/pan`) сохраняется отдельно.

   переименования). Цена: создатель может увести «Фабрику» в «Лаборатории» — это его
   ответственность, инварианты каталога (kind/слоты) не задеваются.
2. **Раздел при «+ тип» обязателен.** Селект раздела **обязателен**, предзаполнен **активным**
   разделом; «Прочее» в селекте **отсутствует** (служебный раздел не создаётся руками).
3. **Порядок корней внутри раздела — по заведению (`id`).** Как сейчас дерево: «Фабрика», затем
   «Автофабрика» (порядок вставки).
4. **Импорт контента и неизвестное значение `section` — переносить дословно, без блокировки.**
   Прод не должен падать на новом значении, придуманном в dev; клиент относит неизвестное в
   «Прочее».

Открытых вопросов к создателю **не осталось**.
