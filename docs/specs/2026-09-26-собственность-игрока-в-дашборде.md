## 0. Резюме (одним абзацем)

В дашборде игрока (`web/index.html`) появляется **отдельная вкладка «Собственность»** (ЧК1): серверный список единиц собственности, где владелец — сам игрок (поселения и строения с `owner_type='player'`), и действие **«Посмотреть»** — переход к попапу системы, сфокусированному на нужной планете. Список отдаёт новая read-модель **`GET /me/property`** (новых сущностей владения нет — `owner_type`/`owner_id` уже есть), а «Посмотреть» — **стык «дашборд ↔ карта»**: дашборд переходит на карту с параметрами `/map?system=<world_id>&planet=<planet_id>`, карта на старте открывает попап системы (вариант A разворота подходов). Строка владения видна **всегда** (решение создателя §1 п.6), а состояние планеты — **только по знанию** (плашка `presence`/`snapshot`/`scan`/`none`, решение §1 п.5); неизвестная планета не раскрывается. Действие **«Перелететь»** (ЧК2) — задел: тот же стык с флагом `&fly=1`, доводящий до планеты на **существующей** цепочке полётов (межзвёздный + внутрисистемный), без новой механики. Пока игрок не владеет ничем, вкладка показывает **пустое состояние** — это норма.

## 2. Цель и «зачем»

- Игрок открывает дашборд и **видит всё, чем владеет в мире**, одним экраном (сейчас такого экрана нет).
- Одним действием **«Посмотреть»** — перейти к своей планете и увидеть её в рамках уже известного.
- Задел: одним действием **«Перелететь»** — довести корабль до нужной планеты откуда угодно.

Граница ценности: это **индекс владения и точка входа к своим объектам**, а не панель управления имуществом (см. §11).

## 3. Разворот подходов: стык «дашборд ↔ карта» (ключевая развилка)

Дашборд (`/`) и попап системы (`openSystemModal`) живут на **разных страницах**: попап — на карте (`map.html`), дашборд — отдельная страница. Известная точка интеграции: попап умеет открываться из админки/поиска (по `adminToken`), но **по URL-параметру не открывается** (в `map/data.js` разбора `location.search` нет). Классы решения:

| Вариант | Как | Цена | Риск |
|---|---|---|---|
| **A. Переход на карту с авто-открытием попапа (рекомендация)** | `/map?system=<world_id>&planet=<planet_id>`; карта на старте читает параметры и вызывает `openSystemModal(worldId, …, {planetId})`; параметры затираются (`history.replaceState`) | Один новый хук в инициализации карты; поведение попапа, камеры и полёта — существующее; **один** хост попапа | Стык с зоной карты (средний риск, назван критиком) — изолируется в отдельном модуле `map/deeplink.js` |
| B. Встроить попап в дашборд (импорт `openSystemModal`) | дашборд тянет весь import-граф попапа (текстуры, звук, слои, `map/config.js` с гейтом `#mapCanvas`) | Тяжёлый импорт в 900-строчный `index.html`; камера/слежение/полёт на дашборде отсутствуют или дублируются | **Второй хост одного попапа** → расхождение поведения; отклонено |
| C. Отдельная лёгкая страница-карточка планеты | новый read-only маршрут «карточка планеты» | Новый роут + новый рендер карточки; дублирует попап | Второй рендер того же знания — расхождение; отклонено |
| D. Только список, без «Посмотреть» | вкладка без действия | Дёшево | Противоречит пожеланию создателя; отклонено |

**Выбрано: A.** Одна точка входа «дашборд → карта» обслуживает оба действия (ЧК1 «Посмотреть» и ЧК2 «Перелететь» через `&fly=1`), попап остаётся один, полёты не дублируются. Разворот зафиксирован здесь; вариант B/C — отклонённые альтернативы.

> **Решение (В1, 2026-09-26): переход на карту как поведение «Посмотреть» подтверждён** (вариант A); вариант B (попап поверх дашборда) отклонён. См. §14.

## 4. Данные и природа сущности

### 4.1. Обязательный разбор (природа / владелец / расширяемость)

1. **Природа.** Список собственности — **не событие, не лог и не новая сущность**, а **производное представление (read-модель)** уже существующих записей владения. Ничего не хранится: результат вычисляется на чтении из `settlements`/`buildings` по владельцу из JWT. Новых таблиц нет.
2. **Владелец.** Записи владения уже есть у **многих** объектов (`settlements.owner_type/owner_id`, `buildings.owner_type/owner_id`, миграция `000082`, полиморфный владелец `player`/`faction`/`agent`). Новая фича только **читает** их по `owner_type='player'` + `owner_id` **из токена** (id игрока из запроса не принимается).
3. **Расширяемость.** Второй тип собственности (позже) ложится в ту же форму ответа: `items[]` с полем `kind` (открытый список) — **без смены схемы** API. Поэтому форма — единый список элементов с типом, а не два раздельных массива (`settlements[]` + `buildings[]`).

### 4.2. Источники данных

| Поле строки | Источник |
|---|---|
| `kind` | ветка запроса: `settlement` / `building` |
| `id` | `settlements.id` / `buildings.id` |
| имя единицы | поселение: `race_name` (каталог рас, как в моделях) + тип поселения (`producer_types.name` по `settlement_type_id`); строение: `producer_types.name` по `producer_type_id` (у строений-игрока `building_type='producer'` и `producer_type_id` **обязателен** — fallback фактически недостижим; `building_type='capital'` — столицы фракций с владельцем-фракцией, в выдачу игрока не попадают) |
| `planet_id` / `planet_name` | `planets.id` / `planets.name` |
| `world_id` / `world_name` | `planets.world_id` → `worlds.name` |
| `knowledge.mode` / `knowledge.at` / `knowledge.fresh` | `player_planet_knowledge` игрока по `planet_id` + присутствие игрока (см. §4.3) |

Именование единицы собирается **на сервере** (`name` + `subtitle`), клиент имена не конструирует — один источник подписи.

### 4.3. Режим знания строки

**Факт кода (почему не «берём существующим резолвом»):** `applyPlanetVisibility` (`internal/handlers/planet_visibility.go`) читает знание **по одной планете и в рамках одной системы** — пакетного метода нет; на отсутствии знания он отдаёт `Knowledge = nil` и **не выставляет** `mode = "none"`. Поэтому read-модель ЧК1 **не переиспользует** per-planet резолв, а делает **одно пакетное чтение знания в своём новом файле** `internal/repository/property_repository.go` (`WHERE user_id = $1 AND planet_id = ANY(...)`) и **повторяет ту же семантику режимов** — источник истины семантики зафиксирован в резолве видимости, правила ниже сверяются с ним:

- `presence` — игрок физически на орбите/поверхности планеты (или её спутника) → «● Свежие данные», **без даты** (`at = null`);
- `snapshot` — есть замороженный снимок (`data.snapshot`) → «📷 Данные на <дата>», `fresh` = не старше `KnowledgeTTL` (7 дней);
- `scan` — запись знания без снимка → «🔍 Данные сканера на <дата>»;
- `none` — записи знания нет → «Нет данных»; `mode = "none"` выставляется **явно** (`at = null`, `fresh = false`) — в отличие от резолва, который в этом случае оставляет `Knowledge = nil` (строка при этом всё равно есть, решение §1 п.6).

Только **одна** планета может быть в `presence` (позиция одна).

**Границы правки (важно):** `internal/handlers/planet_visibility.go` и `internal/repository/knowledge_repository.go` **не трогаем** — они заняты другой задачей. Весь доступ к знанию для этой фичи живёт **только** в новом `property_repository.go`. Дублирование семантики — осознанное (пакетность нужна для инварианта 2); при расхождении правил источник истины — резолв видимости, а не копия.

### 4.4. Индекс под запрос (миграция)

`settlements` уже имеет индекс владельца (`idx_settlements_owner (owner_type, owner_id) WHERE owner_id IS NOT NULL`, миграция `000082`), а у `buildings` **индекса владельца нет** (только `idx_buildings_planet_id` и частичный UNIQUE на столицу, миграция `000056`). Запрос «мои строения» без индекса = последовательное сканирование `buildings` — расходится с инвариантом «стоимость не зависит от размера галактики».

**Предложение:** миграция `000090_buildings_owner_index.sql` — **обычный** индекс `CREATE INDEX idx_buildings_owner ON buildings (owner_type, owner_id)` (номер **уже забронирован** @manager 2026-09-26). Поправка к прежней формулировке: частичный индекс `WHERE owner_id IS NOT NULL` у `settlements` осмыслен, т.к. `settlements.owner_id` — nullable (`000082`), а у `buildings.owner_id` — `NOT NULL` (`000056`), поэтому тот же предикат вырожден (всегда истинен) и индексы **не эквивалентны** — «паритета» нет, частичный предикат здесь не нужен. Миграция входит в **ЧК1** (без неё API масштабируемо не работает).

## 5. API-контракт `GET /me/property`

**Природа:** игровая ручка, авторизация игровым JWT (как `/me/money`, `/api/cargo`). «Моя собственность» = владелец из токена; `owner_id` из запроса **не принимается**.

**Метод/путь:** `GET /me/property` — по образцу `/me/money` (роут в `cmd/server/main.go` рядом с `/me/money`; хендлер `internal/handlers/property_handlers.go`).

### 5.1. Ответ (форма ЧК1, она же ЧК2-задел — не переделывать)

```json
{
  "items": [
    {
      "kind": "settlement",
      "id": "<settlements.id>",
      "name": "Люди",
      "subtitle": "Поселение",
      "planet_id": "<planets.id>",
      "planet_name": "Кеплер-3 b",
      "world_id": "<worlds.id>",
      "world_name": "Кеплер-3",
      "knowledge": { "mode": "snapshot", "at": "2026-09-23T12:00:00Z", "fresh": true }
    },
    {
      "kind": "building",
      "id": "<buildings.id>",
      "name": "Аутпост",
      "subtitle": "Строение",
      "planet_id": "<planets.id>",
      "planet_name": "Кеплер-3 c",
      "world_id": "<worlds.id>",
      "world_name": "Кеплер-3",
      "knowledge": { "mode": "none", "at": null, "fresh": false }
    }
  ]
}
```

Поля: `kind` ∈ {`settlement`,`building`} (открытый список — задел расширения); `name`/`subtitle` — серверные подписи; `planet_id`/`world_id` — адрес для «Посмотреть»/«Перелететь»; `knowledge` — режим строки (§4.3), `at` в UTC (игроку показывается через общий форматтер `gameDate`, год +1000), `at = null` для `presence`/`none`.

**Никаких других полей нет.** Живое население/стабильность/поверхность в список **не входят** (см. §7.3 и §14 В2): они живут в попапе, который сам решает, что показать по знанию.

### 5.2. Инварианты API

- **И-1 (свой):** выборка строго `owner_type='player' AND owner_id=<id из JWT>`; чужая собственность не отдаётся ни при каких параметрах.
- **И-2 (пакетно):** число запросов не растёт с числом планет/галактики: два запроса по владельцу (поселения/строения) + один запрос имён (`planets`/`worlds`) + **один пакетный запрос знания** (реализация — `internal/repository/property_repository.go`, §4.3; per-planet резолв `applyPlanetVisibility` **не вызывается**). Число строк ∝ числу объектов игрока.
- **И-3 (без утечки):** API не возвращает данные планеты вне знания; `knowledge.mode/at/fresh` — только то, что игрок уже знает.
- **И-4 (пусто):** нет объектов → `200` с `{"items": []}` (не `404`), пустое состояние — норма (§6.3).
- **И-5 (сироты):** полиморфный владелец без FK — строки-сироты чужого владельца в выдачу не попадают по построению (фильтр по своему id).

### 5.3. Порядок строк

Детерминированный: сначала поселения, затем строения; внутри — по `world_name`, `planet_name`, `name` (стабильный порядок для тестов и UI). Группировка/сортировка на клиенте не обязательна.

## 6. Вкладка «Собственность» (поведение; пиксели — @uidesigner)

### 6.1. Тонкий HTML (обязательно)

`web/index.html` уже ~900 строк (ориентир 200–300), поэтому в HTML — **только**:

- кнопка в ряду вкладок: `<button class="tab-btn" data-tab="tab-property">🏠 Собственность</button>` (место — перед вкладкой «💳 Счёт»);
- пустой контейнер: `<div class="tab-pane" id="tab-property"></div>` (одна строка-плейсхолдер).

Вся разметка и логика — в **новом модуле** `web/static/js/dashboard/property.js` (по образцу `dashboard/money.js`: чистые хелперы + `initProperty()`, DOM трогается только внутри init — модуль Node-безопасен для тестов). Паттерн вкладок — существующий (`activateDashboardTab`, `.tab-btn`/`.tab-pane`, ключ `dashboardActiveTab`), нового механизма вкладок не вводим.

### 6.2. Загрузка и живость списка (решение вопроса §3.4)

- `initProperty()` запрашивает `GET /me/property` **при открытии вкладки** (клик по `.tab-btn[data-tab="tab-property"]`) и **один раз при старте**, если вкладка активна из `localStorage`.
- Повторная загрузка — при каждом повторном открытии вкладки и по `visibilitychange` (игрок вернулся в окно) — «живость» без WebSocket и без тика (инвариант 2).
- Изменения (сменился владелец, поселение вымерло, мир съеден/очищен) отражаются **следующей загрузкой**: строка исчезает из выдачи (мир/строение удалены каскадом; владелец сменился — фильтр её больше не берёт). Отдельных событий/уведомлений нет (вне скоупа).
- Ошибка загрузки (`!res.ok`, сеть) не ломает страницу: в панели — текст ошибки; `401/403` — очистка токена и переход на `/login-page` (как `money.js`).
- Защита от гонки/дубля: один in-flight запрос; повторный клик во время запроса не плодит запросы.

### 6.3. Пустое состояние (обязательно)

Нет объектов → в панели текст: **«У вас пока нет собственности. Здесь появятся ваши поселения и строения.»** Без «заглушек-интриг» и без кнопок «приобрести» (путь приобретения — зависимость, §11).

### 6.4. Строка списка

Строка: `kind`-иконка (🏠 поселение / 🏗 строение), имя (`name`), подпись (`subtitle`), адрес (`world_name › planet_name`), плашка знания (§4.3) и две кнопки: **«Посмотреть»** (ЧК1) и **«Перелететь»** (ЧК2, §8). Кнопки строят URL стыка (§7.2). Точные подписи/иконки/стиль — @uidesigner; поведение и состав данных — здесь.

## 7. Действие «Посмотреть» по знанию (ЧК1)

### 7.1. Принцип

«Посмотреть» открывает **существующий попап системы**, сфокусированный на планете единицы. Что именно видно — решает **серверный слой знания** (77a + `2026-09-23-орбита-планеты-присутствие-и-снимок`), а не вкладка. Вкладка **никогда** не показывает то, чего нет в знании.

### 7.2. Стык (форма фиксируется здесь)

Дашборд формирует переход:

```
/map?system=<world_id>&planet=<planet_id>&wname=<world_name>          // «Посмотреть» (ЧК1)
/map?system=<world_id>&planet=<planet_id>&wname=<world_name>&fly=1     // «Перелететь» (ЧК2, §8)
```

`world_id`/`planet_id`/`wname` — из `GET /me/property` (`wname` — только для честного сообщения, см. ниже); значения через `encodeURIComponent`.

**Порядок инициализации (детерминированный, С3).** `loadUserData` fire-and-forget запускает отложенные авто-открыватели — `checkCompositeArrival` (маркер `sessionStorage.compositeRoute`) и `checkBeltReturn` (маркер `sessionStorage.beltReturn`); их маркеры **переживают переход «дашборд → карта»** и могут асинхронно открыть/закрыть модалку поверх нашей. Приоритет фиксируем явно:

- **Явный deeplink важнее неявных авто-открывателей** (игрок только что нажал «Посмотреть»/«Перелететь»; автоприбытие — фоновая подсказка). При наличии intent'а первый `loadUserData` **подавляет** `checkCompositeArrival`/`checkBeltReturn` и **очищает оба маркера** (сам полёт серверный — не трогается; теряется только автопопап).
- Порядок в `initMap` (`web/static/js/main.js`):
  1. `deeplink.parseIntent()` — разобрать `location.search`, выставить модульный intent и флаг подавления (нет `system` — no-op);
  2. `await loadUserData()` — при флаге подавления авто-открыватели пропускаются (С3);
  3. `await loadClusters()` — кэш миров карты наполнен;
  4. `handleDashboardDeepLink()` — открыть попап (при `fly=1` — ещё и маршрут), потребить intent, `history.replaceState({}, '', '/map')`;
  5. нет intent — штатное поведение карты без изменений.

**Разрешение мира (С2 — только реально доступное).** `starInfo` попапа ждёт поля `stype/stemp/systype/smods/x/y`; их даёт **кэш кластеров** (`state.worlds`) для миров на карте. `fetchWorldByID` при `403` (вне радиуса/знания) отдаёт `null`. Поэтому:

- мир найден в `state.worlds` → `openSystemModal(world_id, name, spectral_class, { planetId }, null, starInfo)` по существующему паттерну открытия из кластера (полей `starInfo` достаточно; при `403` попап честно покажет карточку звезды — ровно как при клике по этой звезде с карты);
- мир не в кэше, но `fetchWorldByID` вернул мир (`200`; в ответе есть имя/класс/координаты, но **нет** `stemp/smods`) → открываем попап с тем, что есть; система известна — `/planets` обычно отдаёт `200`, карточка обычная. Если всё же придёт `403` — карточка звезды может быть неполной (та же деградация, что у любого `403`-пути); полноту не обещаем;
- мир **не найден** и `fetchWorldByID` → `null` (`403`) → **попап не открываем** (данных звезды нет — обещать нечего): тост **«<wname>: система вне зоны видимости — данных нет»**, остаёмся на карте; ничего не раскрываем (согласуется с В3).

Знание и режим строки попап резолвит сам (`GET /api/worlds/{id}/planets`); deeplink знание не дублирует.

### 7.3. Что видно без наблюдения (закрытие остатка вопроса §3.3)

- **Строка владения есть всегда** (решение §1 п.6) — игрок знает, чем владеет.
- **Состояние планеты** в попапе — по режиму знания: `presence` — живая картина; `snapshot` — замороженная с датой; `scan` — скан-уровень; `none` — заглушка «Нет данных — купить отчёт» (существующее поведение модалки).
- **Система вне радиуса/знания.** Если мир есть в кэше карты — попап откроется карточкой звезды с заглушкой вместо планет (77a §5.5, `starInfo` из кластера доступен); детали планеты не раскрываются. Если мир **не в кэше** и `/worlds/{id}` отдаёт `403` — попап не открываем, показываем тост «<wname>: система вне зоны видимости — данных нет» (§7.2). Обе ветки честные, без утечки; появление карточки звезды **не гарантируется** и зависит от кэша карты.
- **Намеренное исключение к правилу «видно только известное».** Строка владения **раскрывает адрес объекта** (`world_name`/`planet_name`) даже при `mode="none"` и даёт кликабельный путь к системе, которую с карты игрок мог бы и не открыть (её может не быть в кэше). Это разрешено решением создателя §1 п.6 («игрок знает, чем владеет») и является осознанным исключением, а не следствием попапа. Граница чёткая: **адрес владения — раскрываем (по решению), состояние планеты — нет** (только по знанию). «Посмотреть» само по себе — тот же попап, но **вкладка добавляет путь к объекту**, и это признано прямо.

> **Замечание дизайна:** в режиме `none` игрок увидит по своей планете «нет данных». Это осознанно (эталон 2026-09-23: «игрок ничего не видит, пока не получит информацию, присутствуя сам»); альтернатива (выдать владельцу минимум без присутствия) нарушила бы решение §1 п.5. **Решено (В3, 2026-09-26): честное «данных нет», без раскрытия и без утечки.**

## 8. Действие «Перелететь» (ЧК2 — задел, отдельная разработка)

Форма ниже **зафиксирована**; **реализовано 2026-09-26** (ЧК2, коммит `65d6e8c`). Отклонение от
исходной формулировки одно: если целевой планеты в попапе нет (пустая/ограниченная система) —
deeplink молча ничего не делает, тост не показывается (попап сам честно показывает «нет данных»);
подробности — в §8.2.

### 8.1. Принцип

Новой механики полёта нет. Кнопка — это тот же стык с флагом `&fly=1`; маршрут запускает карта **существующими** средствами.

### 8.2. Ветвление (решение принимает существующая логика модалки; С4/С5)

Deeplink **не выводит «своя/чужая система» сам**. Косвенный признак `state.currentWorldId === world_id` неверен: в окне активного межзвёздного полёта `current_world_id` уже может совпасть с целью → ошибочно выберется внутрисистемный старт → сервер `400` «Already in this world» (исправленный баг 2026-09-22).

Правильный источник — **серверный флаг** модалки: `flightModeForSystem()` (`web/static/js/modal/state.js`) = `modalState.inOwnSystem && !modalState.interstellarFlight` → `'intra'` (своя система, 99.2.27), иначе `'composite'` (чужая система **или** активный межзвёздный — редирект `/travel`, 99.2.30 §3.4/§3.5). `inOwnSystem` приходит с сервера (`data.in_own_system` в ответе планет), `interstellarFlight` — из `/me`.

**ЧК2 не вызывает низкоуровневый `startFlight`/`startIntraFlight` напрямую (С5):** прямой `startFlight` не ставит сессионный маркер `compositeRoute`, не закрывает модалку и не включает слежение камеры → по прибытии пропадут авто-открытие и ведение камеры. Используется **существующая обёртка** — то же действие, что пункт «🚀 Лететь» карточки планеты:
- `startCompositeFlight('planet', planet_id)` (`modal/events.js`) — ставит `compositeRoute`, закрывает модалку, `returnToMapInFlight()` (слежение);
- `startIntraFlight('planet', planet_id)` — внутрисистемный (своя система).

**Как deeplink задействует обёртку:** после `openSystemModal(...)` дождаться готовности попапа — заполнены `modalState.worldId` и список планет и отработал `/me` (флаг `modalState.meLoaded`; нужен, чтобы `interstellarFlight` успел загрузиться и режим не выбрался ошибочно как `'intra'`), затем вызвать **то же действие**, что меню планеты — общий экспортируемый хелпер `flyToPlanet` в `modal/events.js` (меню и deeplink зовут его; предикат `flightModeForSystem()` и обёртки не дублируются). **Нет двигателя → тост**, как у меню. **Целевой планеты нет в попапе** (пустая/ограниченная система, битая/съеденная планета) → deeplink молча ничего не делает: попап уже честно показывает «нет данных», а тост «планета не найдена» вводил бы в заблуждение.

Новой цепочки не изобретаем: два плеча, автостарт, разворот (61a), Restore, очистка намерения пакманом — существующие.

### 8.3. Ограничения (кто и когда отменяет)

| Ситуация | Поведение | Источник |
|---|---|---|
| Активный **межзвёздный** полёт, чужая система | Работает: `/travel` → 202/редирект (существующий путь) | `99.2.30` §3.4/§3.5 |
| Активный **внутрисистемный** полёт, своя система | Старт отменяет прошлый intra атомарно (`CancelAtomic`) | `99.2.27` §3.2 |
| Активный межзвёздный, своя система | Режим остаётся `composite` (`flightModeForSystem` возвращает его при `interstellarFlight`) — это редирект `/travel`, работает; внутрисистемный старт в этом окне запрещён (иначе 400) | `99.2.30` §3.4/§6.2 |
| **Нет двигателя** | Кнопка скрыта/disabled с тултипом «Двигатель не установлен — полёт невозможен»; сервер валидирует тоже | `91a` §6.1, `/travel` |
| Игрок **на поверхности** планеты-цели / **уже на орбите** | Кнопка скрыта («уже на месте»); с чужой поверхности — обычный внутрисистемный старт | `99.2.27`, `99.2.30` §6.6 |
| Мир-цель съеден/удалён между списком и кликом | Объект не найден → тост с текстом сервера; список обновится следующей загрузкой | `99.2.30` §5 |
| Цепочка прервана (новый `/travel`, intra уже идёт, пакман) | Отменяет/очищает **сервер** существующими путями; новой отмены не вводим | `99.2.30` ИН-3, §5 |

«Кто и когда отменяет» — **сервер**, теми же правилами, что у полёта из модалки; клиент только показывает тост об ошибке.

### 8.4. Доступность (ЧК2)

Дашборд узнаёт о двигателе/активном полёте из `/me` (существующие поля: `equipment.engine` + `ship_catalog` → наличие двигателя — тем же правилом, что `state.hasEngine` карты, `map/data.js`; `flight`, `current_position`, `pending_destination`; `index.html` и так вызывает `/me`). Гейт кнопки — клиентский (скрыть/disabled), серверная валидация — обязательна и остаётся. Детали UX (где именно скрывать, тултипы) — @uidesigner в итерации ЧК2.

### 8.5. Статус в списке

Показ статуса маршрута («в пути к…», «прибыли») в строке списка — **не ЧК1 и не обязательный ЧК2**: это доводка интерфейса (ЧК3). В ЧК1 список статус полёта не показывает; источник статуса на будущее — `/me` (без новой сущности).

## 10. Что НЕ делаем (границы)

- Не переписываем полёты и знание — только используем существующее.
- Не вводим новых сущностей/таблиц владения (только read-модель; единственная схема-правка — индекс §4.4).
- Не раскрываем неизвестную планету через вкладку (знание — только из `player_planet_knowledge`/присутствия).
- Не дублируем попап вторым хостом (вариант B отклонён).
- Вне скоупа (идея §4): продажа/дарение собственности, управление имуществом из вкладки, рейтинги, доходность, уведомления о нападении.
- Не показываем в списке живое состояние планеты (население/стабильность/поверхность) — это попап (§5.1, §14 В2).

Это нормальное состояние (§6.3), но фича «повиснет» до появления пути приобретения. Не проектируем приобретение здесь — выносим как кандидата (§14, кандидат новой ГД сущности) и заметку менеджеру.

Дополнительно: дополнение impacts у `structure_ownership` (новый потребитель — вкладка собственности) и `planets`/`worlds` (чтение имён). Новых дублей нет. Реестр правит **@manager**.

**Обратные рёбра (со стороны существующих узлов → новым), обязательны критиком:** без них обход «меняем X → смотрим на Y» слепнет — изменение старого узла не приведёт к новым потребителям.

| Обратное ребро (существующий узел → новый) | kind | Почему (что ломается при правке старого) |
|---|---|---|

## 13. Тест-критерии

**Сервер (`property_handlers`)**
- T1. `GET /me/property` без токена → 401.
- T2. Игрок A владеет поселением + строением; игрок B — своими: A видит **только свои** (И-1).
- T3. Форма ответа: `items[]`, поля §5.1; значение `kind` соответствует объекту; `id`/`planet_id`/`world_id` заполнены.
- T4. Порядок строк детерминирован (поселения → строения; по world/planet/name) (§5.3).
- T5. Пусто → `200 {"items":[]}` (И-4).
- T6. Режимы знания: `presence` (`at=null`), `snapshot` (`at` = `snapshot.at`, `fresh`), `scan` (`at` = `scanned_at`), явный `none` (`at=null`, `fresh=false`) — семантика совпадает с резолвом видимости; чтение — **одним пакетным запросом** (`property_repository.go`), `applyPlanetVisibility` не вызывается (§4.3).
- T7. Планета без знания: `knowledge.mode="none"`, в ответе **нет** данных планеты (И-3).
- T8. Число SQL-запросов не зависит от числа планет/галактики (И-2, смоук/счётчик).
- T9. Строение-сирота чужого владельца не попадает в выдачу.

**БД/миграция**
- T10. `000090` создаёт `idx_buildings_owner`; `EXPLAIN` запроса по владельцу использует индекс (или `Index Scan`), не `Seq Scan`.

**Клиент (`property.js`, Node-тесты как у `money.js`)**
- T11. Хелперы: сборка URL «Посмотреть» `/map?system=..&planet=..&wname=..` (экранирование); сборка URL «Перелететь» с `&fly=1`.
- T12. Пустой список → текст пустого состояния; ошибка → текст ошибки, страница жива (§6.3).
- T13. Плашка знания по режиму: presence/без даты, snapshot/с датой (+«устарело»), scan/с датой, none/«Нет данных».

**E2E (смоук)**
- T14. Вкладка «Собственность» есть в ряду; открывается; при пустой собственности — текст; список рендерится при наличии объектов; 0 `pageError`.
- T15. Клик «Посмотреть» → переход на `/map?...`; если мир в кэше карты — попап системы с фокусом на планете; если нет (`403`) — тост «система вне зоны видимости — данных нет», попап не открывается; URL затирается (`history.replaceState`); F5 повторно попап не открывает; при живом маркере `compositeRoute`/`beltReturn` авто-открыватель не перебивает deeplink (§7.2).
- T16. (ЧК2) `&fly=1` выбирает режим серверным флагом (`flightModeForSystem`): своя система — внутрисистемный, чужая/активный межзвёздный — композитный; маршрут идёт через обёртку (маркер `compositeRoute`, закрытие модалки, слежение); без двигателя — тост; уже на месте — тост.

## 14. Решения по вопросам и кандидат ГД сущности

> **Закрыто менеджером 2026-09-26** (создатель делегировал решения): В1–В4 ниже — закрытые решения, не вопросы.

**В1. ✅ Стык «Посмотреть» — переход на карту (вариант A), оставляем.**
Переход на карту с авто-открытием попапа; вариант B (попап поверх дашборда) отклонён. Причина: один хост попапа, нет дублирования полёта/камеры. Цена: «Посмотреть» = уход с дашборда.

**В2. ✅ Числа (население/стабильность) в списке не показываем.**
Список — индекс; числа живут в попапе, где слой знания сам решает, что показать. Показ чисел потребовал бы живого пересчёта (против «стоимости по событию») либо второго формата. В §5.1 состав строки закрыт.

**В3. ✅ Система вне знания → честное «данных нет», без раскрытия и утечки.**
Карточка звезды гарантируется только если мир есть в кэше карты; иначе — тост «система вне зоны видимости — данных нет», попап не открываем (§7.2/§7.3).

**В4. ✅ Вымершее поселение остаётся в списке.**
Владение не снимается автоматически (факт вымирания — в попапе, лог). Точка снятия владельца — вне скоупа ЧК1.

**Кандидат новой ГД сущности (пожелание: каждое задание = +1 сущность; не факт, вне чисел):**

**Вопрос:** Как игрок **приобретает** собственность в игре, если сейчас владельца-игрока ставит только админ? Без этого вкладка «Собственность» у обычного игрока всегда пуста.

**Ответ (кандидат, решение создателя не запрошено, дата 2026-09-26 — «эталон не задан»):** предлагается сущность **«Заказ на создание объекта»** — контракт (на существующем движке контрактов, инвариант 8 «контракт — единственный рычаг удалённого действия»), по выполнению которого построенный объект переходит в собственность заказчика-игрока. Это оживляет вкладку, связывает её с экономикой (деньги покупают чужое время, инвариант 11) и не вводит второй системы заказов. В текущие числа/скоуп **не входит**; отсев — за создателем.

Счётчик открытых эталонов (`docs/gamedesign/faq_counter.md`) **не меняется**: кандидат-вопрос про приобретение собственности — это ГД-кандидат роадмапа, а не эталон физики/мира; В1–В4 закрыты как дизайн-решения.
