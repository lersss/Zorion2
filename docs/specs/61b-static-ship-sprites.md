## 0. Резюме (одним абзацем)

Параметрический генератор визуала кораблей (99.2.15) **убирается целиком** как легаси:
пакет `internal/generator/ship/`, таблица `ship_parts`, колонка `users.ship_visual`, каталог
в памяти, вкладка «Корабли» в админке, `GET /api/ship-parts` — всё удаляется из кода.
Вместо схем корабль — **статичный спрайт**: цельный PNG 200×200 (21 ассет из
`ai_drafts/final_accepted/`, копируются в `web/static/sprites/`), выбор — как раньше через
`users.ship_icon` (значения — имена PNG). Старые значения `ship_icon` (21 SVG-имя) маппятся
на новые PNG таблицей §4, неизвестные — на дефолт `crescent.png`. Создатель хочет сохранить
выбор **доминирующего цвета** поверх градиентов/текстуры AI-арта: рекомендация — тонирование
через `globalCompositeOperation='hue'` (вариант «в» §5, ~10 строк, GPU, акценты принимают
цвет корпуса; альтернатива с сохранением акцентов — пиксельный HSL-сдвиг с маской, «б»).
Цвет игрока хранится в новой колонке `users.ship_color` (NULL = «оригинал», без перекраски).
Агенты NPC получают спрайт **детерминированной чистой функцией от id** (FNV-1a(id) % 21,
ноль хранилища), ромб на карте заменяется мини-спрайтом, повёрнутым по курсу; функция
выбора — отдельная точка замены под будущий расовый визуал. Полёт игрока и механика
не меняются (поворот по курсу, пламя, размер `shipSize*3.2`). Старые 21 SVG + `ships.json`
удаляются из репо (отменяет прежнее «оставить до 1.0»).

## 3. Новая модель: 21 статичный спрайт

**Термин (GLOSSARY-кандидат, фиксируется в `21_ships.md`):** *статичный спрайт корабля* —
цельный PNG 200×200 (нос вправо, как legacy), не схема; единственный источник визуала
корабля игрока и агента. *Перекраска* — тонирование спрайта доминирующим цветом с
сохранением градиентов/текстуры (§5). *Оригинал* — спрайт без перекраски.

### 3.1. Ассеты

- 21 PNG из `ai_drafts/final_accepted/` копируются в `web/static/sprites/` и коммитятся:
  `anchor, book, boomerang, crater, crescent, crystal, drop, egg, heart, helmet, jellyfish,
  manta, mushroom, octopus, pyramid, shark, shell, spiral, star_celestial, trident, volcano`
  (все — `.png`, 200×200).
- Файлы `race_*.png` (6 шт. из той же папки) **не копируются** — это задел расового визуала,
  вне скоупа (создатель: «расы не проектировать сейчас»).
- **Проверка на этапе ассетов:** ориентация каждого PNG — нос вправо (как legacy-спрайты и
  рендер `drawFlight`, который поворачивает по курсу от угла 0 = «вправо»). Если какой-то
  ассет ориентирован иначе — фиксированная константа поворота на спрайт в `ship_sprites.js`
  (не переэкспорт, не правка арта).

### 3.2. Реестр спрайтов (один источник на сервере)

`internal/models/ship_sprites.go` (новый, Go-константы, не конфиг — список статичен и

- `ShipSprites` — массив из 21 записи `{id, name, file}`: `id` = имя без `.png`

  Полумесяц, Кристалл, Капля, Яйцо, Сердце, Шлем, Медуза, Манта, Гриб, Осьминог, Пирамида,
  Акула, Ракушка, Спираль, Звезда, Трезубец, Вулкан), `file` = `"<id>.png"`.
- `LegacyShipIconMap` — маппинг 21 старого SVG-имени → новое PNG-имя (§4, биекция).
- `DefaultShipIcon` — `"crescent.png"` (§4.1).
- `ShipColorPalette` — 9 хроматических цветов (§5.5).
- Порядок массива **фиксирован** — он же источник индексов для `spriteForAgent(id)`

  запрещена без осознанного решения).

### 3.3. Хранение выбора игрока

- `users.ship_icon` (существующая колонка, миграция 000011) — имя файла: теперь PNG-имя

## 4. Маппинг legacy → PNG и дефолт

### 4.1. Дефолт

**Дефолт: `crescent.png` (Полумесяц).** Обоснование:

- **Читается на малом размере:** компактный симметричный силуэт без мелких деталей —
  на размере полёта (~9 px) и иконки агента (7–14 px) не превращается в кашу.
- **Нейтрален по характеру:** не хищный (не `shark`/`trident`), не «органический»
  (не `mushroom`/`octopus`), не агрессивный — подходит и игроку-новичку, и агенту.
- **Не сливается со звёздами карты:** в отличие от `star_celestial` (звезда-корабль
  будет путаться с фоновыми звёздами на близком зуме), серповидная форма уникальна.

## 5. Цвет: разворот подходов (перекраска PNG на клиенте)

Проблема: спрайты — AI-арт с градиентами и текстурой; «залить одним цветом» нельзя.
Создатель хочет выбор **доминирующего цвета** (оттенок поверх градиентов). Четыре класса
подхода, от дешёвого к дорогому. **Перекраска применяется только к кораблю игрока и
превью дашборда; агенты НЕ перекрашиваются** (§6.2) — поэтому вопрос производительности
перекраски вторичен, а вот производительность рендера 30k агентов решается кэшем
исходных PNG (§8, И6).

### 5.1. (а) Hue-rotate через `ctx.filter` / CSS filter

Как: `ctx.filter = 'hue-rotate(' + deg + 'deg)'` перед отрисовкой (или CSS на `<img>`).

- **Даёт:** весь спрайт поворачивается по цветовому кругу на фиксированный угол; градиенты
  и текстура сохраняются идеально (S/L пикселей не меняются).
- **Ломается:** (1) угол зависит от исходного оттенка спрайта — «красный» = поворот на
  `(targetHue − baseHue(спрайт))`; нужна калибровка `baseHue` для каждого из 21 спрайта
  (21 константа, измерение по арту), у многоцветных спрайтов результат непредсказуем
  («красный» на разных спрайтах — разные красные); (2) акценты (стекло, огни, свечение)
  сдвигаются вместе с корпусом; (3) `ctx.filter` не поддерживается в Safari до 18.0
  (2024) — риск совместимости; (4) filter на каждый `drawImage` дорог — обязателен
  пре-рендер в кэш.
- **Цена:** ~5 строк + 21 константа калибровки + риск совместимости.
- **Вердикт:** слабый — калибровка и непредсказуемость на многоцветном AI-арте.

### 5.2. (б) Пиксельный HSL-сдвиг (`getImageData`)

Как: для каждого пикселя RGB→HSL, `H := targetHue` (или `H += delta`), S/L сохранить,
HSL→RGB, `putImageData`; один раз на (спрайт, цвет) → кэш. Улучшение — **маска по
hue-дистанции**: перекрашивать только пиксели, чей `H` в ±30° от доминантного оттенка
спрайта (доминанта — из гистограммы или константа на спрайт) — акценты не трогаются.

- **Даёт:** полный контроль; акценты (стекло, огни, свечение) сохраняют свои цвета;
  детерминированный результат.
- **Ломается:** (1) ~40–60 строк кода; (2) доминантный оттенок надо вычислять или задавать
  константой на спрайт; (3) многоцветные спрайты: маска может перекрасить часть корпуса
  неравномерно или зацепить акцент — хрупко к разнобою AI-арта; (4) `getImageData` — CPU:
  40 000 пикселей × 21 спрайт × 9 цветов ≈ 7.6 млн операций суммарно, но лениво и разово
  (порядка 100–300 мс, размазано по мере появления комбинаций).
- **Цена:** ~40–60 строк, самый дорогой и хрупкий.
- **Вердикт:** «самый правильный» при требовании сохранить акценты; иначе избыточен.

### 5.3. (в) Тонирование через `globalCompositeOperation='hue'` — **РЕКОМЕНДАЦИЯ**

Как: offscreen canvas → `drawImage(спрайт)` → `gCO='hue'` → `fillRect(выбранный цвет)` →
результат в кэш. Один раз на (спрайт, цвет).

- **Даёт:** hue каждого цветного пикселя заменяется на hue выбранного цвета, S/L пикселя
  сохраняются — **градиенты и текстура полностью сохраняются**, результат = «корабль в
  выбранном цвете с исходной текстурой». Детерминированно и одинаково для всех 21 спрайтов
  (ноль калибровки: цвет палитры и есть целевой hue). Ахроматические пиксели (тёмный
  контур, белые блики, серые панели, S≈0) не меняются — контур и металл сохраняются,
  силуэт читается на тёмном фоне карты.
- **Ломается:** цветные акценты (стекло кабины, навигационные огни, свечение двигателей)
  тоже принимают выбранный оттенок — теряют цветовую идентичность. На размере полёта
  (~9 px) и иконки агента это незаметно; на превью дашборда (52 px+) заметно. Многоцветный
  спрайт становится однооттеночным (текстура через S/L сохраняется).
- **⚠️ Обязательно: восстановление альфы.** Blend-режим 'hue' НЕ сохраняет прозрачность
  фона: для прозрачных пикселей композит берёт цвет заливки, фон закрашивается
  непрозрачным. После `fillRect` обязателен `globalCompositeOperation='destination-in'` +
  `drawImage(оригинал)` — вернуть альфу спрайта (найдено на живом демо 2026-09-16;
  без шага — цветные квадраты вместо кораблей).
- **Цена:** ~10 строк, GPU-композит (быстро), canvas-бленды поддерживаются во всех
  современных браузерах (в отличие от `ctx.filter`).
- **Вердикт:** **принято создателем 2026-09-16** (живой показ: тонирование работает
  хорошо; спрайты в основном ахроматические — 'hue' их не портит, только тонирует
  цветные зоны). Вариант (б) с маской и (г) комбинированный — отклонены как избыточные.
  Вариант С ('color'-композит, перекраска серого металла) показан на демо, отклонён
  создателем — сильнее запрошенного.

### 5.4. (г) Комбинированный

Тонирование (в) + поверх оригинал с маской акцентов (или маска по S/L: яркие насыщенные
пиксели — акценты, рисуются из оригинала).

- **Даёт:** акценты сохраняются при дешёвом тонировании корпуса.
- **Ломается:** определение маски акцентов по S/L — хрупко на AI-арте (яркие участки
  корпуса попадут в «акценты»), ~30 строк сверх (в); результат хуже предсказуем, чем у (б).
- **Вердикт:** компромисс без выигрыша — если акценты критичны, честнее (б).

### 5.5. Палитра

- **9 хроматических цветов** (hex, из которых берётся hue): красный `#ef4444`, оранжевый
  `#f97316`, жёлтый `#eab308`, зелёный `#22c55e`, бирюзовый `#14b8a6`, голубой `#0ea5e9`,
  синий `#3b82f6`, фиолетовый `#8b5cf6`, розовый `#ec4899`. Критерии: читаемость на тёмном
  фоне карты, различимость между собой.
- **+ «Оригинал»** (`NULL`) — спрайт без перекраски. Обязателен: AI-арт — эталон красоты,
  и у игрока должен быть выбор «не трогать».
- Серые/металлические «цвета» в палитру **не входят**: у ахроматических цветов нет hue,
  тонирование 'hue' их не выражает (для «металлика» нужен отдельный режим 'color'-композита
  с десатурацией — вне скоупа, не усложняем).
- Состав палитры — предложение дизайнера, подтверждается на гейте (§11, вопрос 3).

### 5.6. Реализация перекраски (клиент)

`web/static/js/map/ship_sprites.js` (новый, заменяет `ship_render.js`):

- `getShipImage(name)` — кэш `Map<name, Image>` (21 шт), загрузка `/static/sprites/{name}.png`;
  `onload` → `scheduleRedraw` (паттерн из текущего `ship_render.js`).
- `recolorShipSprite(name, color)` — кэш `Map<"name|color", canvas>`: offscreen canvas →
  `drawImage` → `gCO='hue'` → `fillRect(color)` → вернуть canvas. `color = null` → исходный
  `Image`. Лениво: комбинация создаётся один раз при первом запросе.
- Фолбэк (И4): спрайт не загрузился / неизвестное имя → `null`, рисующий код использует
  примитив-корабль (текущий `bodyGrad` в `map_render.js`, без изменений).
- `spriteForAgent(id)` — детерминированный выбор: `ShipSprites[FNV-1a(id) % 21]`
  (FNV-1a — существующий `hashSeed` из `ship_render.js`, переносится). **Единственная точка
  замены под расы**: будущий расовый визуал меняет тело этой функции (например,
  `raceOf(id)` → подмножество спрайтов), сигнатура и потребители не меняются.
- **Агенты перекрашиваются (уточнение создателя 2026-09-16).** `spriteForAgent(id)`
  возвращает пару `{file, color}`: `file = ShipSprites[FNV-1a(id) % 21]`,
  `color = ShipColorPalette[FNV-1a(id+1) % 9]` (детерминированно, 189 различимых
  комбинаций). Отрисовка — `recolorShipSprite(file, color)` **из кэша** (перекраска
  не в хот-пате, а при первом запросе комбинации; см. прелоадер ниже).
- **Прелоадер всех вариантов (создатель 2026-09-16).** `preloadShipSprites()` —
  прогревает кэш `recolorShipSprite` для всех 21×9 = 189 комбинаций + 21 оригинал
  (Image) при старте клиента (вызов из `main.js` init, после `/me` и получения
  `ship_options` — порядок реестра). После прелоада отрисовка агентов/игрока — всегда
  из готового кэша, ноль ленивых перекрасок в рантайме. Стоимость: 189 офскрин-канвасов
  (200×200), однократно, фоном; загрузка 21 PNG параллельно.

## 8. Инварианты и числа

**Числа:**

- Спрайтов: **21** (PNG 200×200, нос вправо — проверить на этапе ассетов, §3.1).
- Палитра: **9 хроматических** + «Оригинал» (NULL).
- Кэш перекраски: **≤ 21×9 = 189** вариантов, лениво, один раз на комбинацию.
- Рендер полёта: `shipSize*3.2` ≈ **9 px** (`shipSize = 2.8`, текущий; спека 30b — корабль
  игрока вровень с агентами). Иконка агента: `max(3.5, 4.5×scale)`, порог
  `nameDisplayThreshold = 0.5`.
- Агент: `FNV-1a(id) % 21`; при 100k агентов ~**4 762 агента на спрайт** в среднем.
  На галактическом обзоре агенты скрыты (порог 0.5); в типичном вьюпорте — десятки,
  дубли редки. Принятое следствие (21 спрайт — решение создателя).
- Маппинг: **21 биекция** (§4.2) + правило «неизвестное → дефолт».

**Инварианты:**

- **И1 (новый):** статичный спрайт — цельный PNG, не схема; реестр `ShipSprites` —
  единственный источник имён (сервер), клиент не дублирует список/маппинг.
- **И2:** детерминизм агента — `spriteForAgent(id)` чистая функция, стабильный хеш
  (FNV-1a), порядок массива фиксирован; один и тот же визуал на любом клиенте, ноль
  хранилища.
- **И3:** полнота маппинга — все 21 legacy-имени смапплены (биекция), неизвестное →
  дефолт; тест на полноту (§10, этап 1).
- **И4:** фолбэк без падений — спрайт не загрузился/имя неизвестно → примитив-корабль
  (полёт) / ромб (агент); цвет вне палитры или `null` → оригинал.
- **И5:** косметичность — спрайты и цвет **не влияют на механику** (скорость, груз,
  контракты, население); сущностей вне игры, влияющих на формулы, фича не вводит
  (анти-двойной учёт не требуется — влияния нет по построению).
- **И6:** производительность — агенты рисуются из **кэша 189 прелоаженных вариантов**
  (21 спрайт × 9 цветов, перекраска один раз на комбинацию при прелоаде, не в хот-пате);
  30k `drawImage` в кадре при плотном вьюпорте — как сейчас ромбы, но одной операцией
  вместо двух; перекраска игрока — тоже из того же кэша; стоимость не от размера
  галактики (инвариант 2 проекта).
- **И9 (уточнение 2026-09-16):** разнообразие агентов — `spriteForAgent(id)` даёт пару
  (спрайт из 21, цвет из 9) → 189 различимых комбинаций; детерминизм — та же чистая
  функция, ноль хранилища.
- **И7:** полёт не меняется — поворот по курсу, пламя, размер, интерполяция — как сейчас;
  полёт неотменяем и детерминирован (`06_factions.md` §6.7.7).
- **И8:** расширяемость — `spriteForAgent` — единственная точка замены под расовый визуал
  (тело функции, сигнатура фиксирована); реестр спрайтов открыт (добавление — PNG в
  `web/static/sprites/` + строка в `ShipSprites`, индексы существующих не сдвигаются —
  добавление только в конец).

**Риски и режимы отказа:**

- **Перекраска 'hue' сдвигает акценты** (стекло, огни, свечение принимают цвет корпуса) —
  принятое следствие; проверка глазами на превью дашборда (гейт §11, вопрос 1);
  альтернатива — (б) с маской.
- **Многоцветные спрайты при 'hue' становятся однооттеночными** — текстура (S/L)
  сохраняется, характер силуэта не теряется; если на конкретном спрайте результат
  некрасив — игрок всегда может вернуть «Оригинал».
- **Ориентация PNG ≠ нос вправо** — фиксированная константа поворота на спрайт (§3.1),
  проверка на этапе ассетов.
- **30k+ агентов в одном вьюпорте** (плотное скопление) — `drawImage` с поворотом может
  просесть; cull по вьюпорту уже есть; будущая оптимизация (атлас/слой) — вне скоупа,
  фиксируется как известное ограничение.
- **БД-мёртвые схемы** (`ship_parts`, `users.ship_visual`) остаются — не удаляются
  (согласовано), не используются; путаницы не возникает, т.к. код удалён.
- **Маппинг по смыслу, а не по виду** — дизайнер не видит PNG; визуальная сверка пар —
  за создателем (§11, вопрос 2).

## 12. Предложение новой ГД-сущности (FAQ-кандидат, в числа не входит)

Правило «каждое задание = +1 предложение новой ГД-сущности» (создатель 2026-09-14).
Кандидат по теме фичи (визуал корабля игрока):

**Вопрос:** нужна ли игроку персональная **эмблема корабля** — выбираемый значок (герб/лого
из набора), наносимый на корпус спрайта и видимый в полёте и на превью дашборда?
**Ответ (решение создателя, 2026-09-20):** «Не в MVP точно, косметика» — эмблема —
косметический слой поверх спрайта+цвета, **не в MVP** (решение роадмапа, в FAQ не входит —
не эталон физики; счётчик не двигает).

Почему это повышает игровой интерес: в многопользовательской игре визуальная идентичность
корабля — способ «узнать конкурента/партнёра в трафике» (радар, `07_ui.md` §7.1.3);
эмблема — косметический слой поверх уже выбранного спрайта+цвета, без новых механик.
Цена: набор значков (10–20 SVG-оверлеев) + точка наложения на спрайт в `ship_sprites.js`
+ выбор в дашборде; режим отказа — оверлей ломает читаемость силуэта на ~9 px (ограничить
размер/контраст). В текущие числа фичи **не входит** (анти-двойной учёт): реализация —
отдельным этапом при планировании (**решение создателя 2026-09-20: не в MVP**).
