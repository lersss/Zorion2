## 0. Резюме (одним абзацем)

Вводятся три сущности: **модель корабля** (рамка механики: слоты под оборудование; визуал 61b
остаётся отдельной системой, «пакетом» станет позже), **оборудование** (справочник типов:
радар / сканер / двигатель; стартовая комплектация — радар + сканер) и **радар** как
ограничитель **детальной** видимости игрока. Видимость звёзд — **гибрид «звёздное поле»** (решение
создателя 2026-09-17): все звёзды галактики видны с первого экрана (масштаб вселенной и «объём
контента» видны сразу). **Открытая информация о звезде** (решение создателя 2026-09-17, §5.5):
имя, спектральный класс, внешний вид (цвет, размер — как видит админ), температура, тип
звезды/системы, компаньоны, координаты — видна игроку **везде**, без знания и без радара
(«видно в телескоп»). Радиус радара (старт **800 px** ≈ 25–50 систем по плотности боевых
пресетов; минимум **200 px** без радара) решает **только** для деталей системы: модалка
(планеты, число планет, поселения — 403 вне радиуса/знания), скан (сканер, личный каталог),
чужие игроки и NPC-агенты. **Полёт к любой звезде разрешён** (решение создателя 2026-09-17,
«слепой прыжок» отменён): дальность будет ограничиваться топливом позже — задел на будущее,
сейчас без ограничений. Радар — **одна модель, без прогрессии уровней** (кривая
400/600/900/1400/2000 вернётся с рынками и ценами, вне скоупа). Скрыты за радаром без
купленной/добытой информации — поселения, поверхность/недра/атмосфера планет, число планет,
корабли (NPC-агенты + чужие игроки). Сканер автоматически даёт личное знание о **поверхности** (чем
покрыта: вода/ледники/пустыня/скалы) и **наличии поселений** (есть/нет + число) в радиусе
радара (с датой актуальности, личный каталог игрока; недра/атмосфера/детали поселений —
платные отчёты; не дублирует рынок отчётов — зазор «свежесть/глубина» держит рынок).
Протухание знания — **7 дней** (принято). Админ и skycomposer видят всё навсегда (исключение).
Видимость применяется на сервере (клиент не получает скрытых данных): `/api/worlds/filter`
отдаёт полный вид звезды всем (как админу) — радиус не режет звёзды, только детали систем;
детали планет в модалке — за радиусом/знанием (403), `/api/npc/positions`, новый эндпоинт
позиций чужих игроков; `/travel` валидирует только существование цели. Хранение
знания — таблица `player_planet_knowledge` (одна запись на (игрок, планета), дата скана,
протухание — статус актуальности на чтении, без фоновых джобов). Транспондер — вынесен в
сырую идею 77b, в 77a не входит. Визуал границы видимости — тестовая переключалка 2–4
вариантов (функциональное требование §9), сами варианты — ТЗ для @gdesigner (§9.2).

## 2. Сущность «модель корабля»

**Термин (GLOSSARY-кандидат, фиксируется в `21_ships.md`):** *модель корабля* — рамка
механических характеристик корабля (слоты под оборудование), НЕ визуал; визуал игрока
(`users.ship_icon`/`ship_color`, 61b) — отдельная система, «пакетом» (вид + механика) модель
станет позже.

### 2.1. Природа сущности (обязательный разбор)

1. **Природа** — справочник/каталог (атрибут-справочник), не событие и не лог: модель не
   «происходит», она описывает корабль. Записей мало (стартовая одна, ассортимент прирастёт
   с рынками).
2. **Владелец** — общий справочник для всех игроков (у многих игроков может быть одна модель).
   Связь «игрок → модель» — атрибут игрока (`users.ship_model_id`), а не запись у модели.
3. **Расширяемость** — много типов моделей позже (с рынками); схема `ship_models` (таблица)
   переживает второй тип без изменений. Правило «сущность с двумя экземплярами — не сущность»
   работает в обе стороны: справочник моделей — полноценная таблица (каталог), а не атрибут
   игрока, потому что модели — общие объекты с собственными полями (слоты), а не личные данные.

### 2.2. Поля

| Поле | Тип | Назначение |
|---|---|---|
| `id` | TEXT PK | ключ модели (стартовая — `'starter'`) |
| `name` | TEXT | имя модели (например, «Стартовый разведчик») |
| `slots` | JSONB | слоты под оборудование: `{"radar": 1, "scanner": 1, "engine": 1}` |
| `created_at` | timestamptz | служебное |

Скорость/загруженность в модель **не входят** (замысел «скорость = двигатели + загруженность» —
реализация вне скоупа). Модель — только рамка слотов; двигатель как механика скорости не
реализуется в этой фиче (слот `engine` существует, но пуст).

### 2.3. Слоты: по одному каждого типа (решено, развилка из идеи)

**Решение: по одному слоту каждого типа** (3 слота: радар, сканер, двигатель). Обоснование:

- Стартовая комплектация «радар + сканер» заполняет ровно 2 из 3 слотов — по одному на тип;
  несколько слотов одного типа сейчас нечем заполнить (двигатель не реализован, рынков нет).
- Несколько слотов одного типа порождают нерешённые вопросы баланса (складываются ли два
  радара? как считать радиус?) — цена без пользы в этом скоупе.
- Схема расширяема: `slots` — JSONB-объект «тип → количество»; добавление второго слота радара
  будущей моделью не требует миграции (правило «не закрывать открытые списки»).

Разворот подходов (отклонённые):

- **B. Несколько слотов одного типа** (2 радара, 2 сканера): цена — баланс сложения радиусов,
  UI установки, рынок; пользы сейчас нет (двигатель не реализован, рынков нет). Отклонено.
- **C. Слоты с размерами** (малый/большой радар в один слот): цена — лишняя ось сложности,
  не проговорена на интервью. Отклонено.

## 3. Сущность «оборудование»

**Термин (GLOSSARY-кандидат):** *оборудование* — устанавливаемый на корабль предмет из
справочника типов (радар / сканер / двигатель), определяющий механические возможности корабля.

### 3.1. Природа сущности (обязательный разбор)

1. **Природа** — справочник/каталог (типы и экземпляры), не событие. Записей мало
   (стартовые радар+сканер; уровни радара — предметы будущего рынка, в 77a не проектируются).
2. **Владелец** — общий справочник; установленное оборудование — атрибут игрока
   (`users.equipment` JSONB: ссылки на id справочника по слотам). Расширяемость: второй тип
   (двигатель) и уровни ложатся в ту же таблицу без изменений схемы.
3. **Правило «не зажимай поток записей в атрибуты»:** оборудование — каталог (таблица), потому
   что оно будет покупаться/меняться на рынках (много записей-уровней); но установка на игрока —
   атрибут (ровно 3 слота, один корабль у игрока).

### 3.2. Поля

| Поле | Тип | Назначение |
|---|---|---|
| `id` | TEXT PK | ключ предмета (например, `'radar_1'`, `'scanner_1'`) |
| `type` | TEXT + CHECK | `radar` / `scanner` / `engine` |
| `name` | TEXT | имя предмета («Радар-1», «Сканер-1») |
| `params` | JSONB | параметры типа: радар — `{"radius": 400}`; сканер — `{"depth": "surface", "settlements": true}`; двигатель — задел (пусто) |
| `created_at` | timestamptz | служебное |

### 3.3. Стартовая комплектация и крепление

- Стартовая комплектация: **радар-1 + сканер-1** (решение создателя). Заполняют слоты
  `radar`/`scanner` стартовой модели; слот `engine` — пуст.
- Крепление: `users.ship_model_id` (какая модель) + `users.equipment` (что в слотах):
  `{"radar": "radar_1", "scanner": "scanner_1", "engine": null}`. Валидация: тип предмета

### 5.1. Видимость звёзд: гибрид «звёздное поле» (решено, создатель 2026-09-17)

**Решение:** гибрид «звёздное поле» (заменяет рекомендацию «радар-фонарь»):

- **Все звёзды галактики видны** сразу на старте — масштаб вселенной и «объём контента» видны
  с первого экрана (осознанная ценность фичи).
- **Вид звезды — открытая информация везде** (уточнение 2026-09-17, §5.5): имя, спектральный

## 6. Сканер

**Термин (GLOSSARY-кандидат):** *сканер* — оборудование, автоматически дающее игроку личное
знание о планетах в радиусе радара: видимость поверхности (с датой актуальности) и наличие
поселений.

### 6.1. Режим работы (разворот подходов)

| Вариант | Как | Плюсы | Минусы / цена |
|---|---|---|---|
| **A. Ленивый прогон при запросе (рекомендация)** | при открытии модалки системы, находящейся в радиусе радара, сервер обновляет знание игрока о планетах этой системы (дата = now) | ноль фоновой нагрузки; знание всегда свежее «в момент взгляда» (согласуется с 10.3.3: присутствие свежее сети); просто | знание не обновляется, пока не смотришь (это и есть «возраст данных», честно) |
| **B. Постоянный фон** | серверный тик сканирует всё в радиусе радара каждого игрока | данные «всегда свежие» | фоновая нагрузка ∝ игроки × планеты в радиусе; обновление без пользы (игрок не смотрит на всё сразу) |
| **C. Интервальный** | раз в N минут | компромисс | сложнее объяснить; та же нагрузка, что B, но реже |

**Принято: A** — ленивый прогон при запросе. «Автоматически в радиусе радара» (решение
создателя) выполнено: игроку ничего нажимать не надо, скан происходит сам при взгляде на
систему в радиусе.

### 6.2. Глубина скана (решено, создатель 2026-09-17)

**Решение:** сканер вскрывает **поверхность** — чем покрыта планета (вода/ледники/пустыня/
скалы — видимое с орбиты) + **наличие поселений** (есть/нет + число). **НЕ вскрывает:** недра,
состав атмосферы, детали внутри поселений (население, раса, состав) — это платные отчёты
(10.3.4) / физическое присутствие. В UI модалки при отсутствии знания: «нет данных — купить
отчёт» (заглушка вместо деталей).

Обоснование:
- `10_exploration.md` §10.2.2: недра — длительная разведка, отдельный уровень; поверхностное
  сканирование даёт лишь «вероятностную подсказку о недрах». Сканер = поверхностный уровень.
- Рынок отчётов живёт на зазоре «личное знание vs полные данные» (10.3.3): если сканер даёт
  недра/атмосферу бесплатно, отчёты о них обесцениваются.
- Полные данные = присутствие + покупка свежих данных (решение создателя) — недра/атмосфера/
  детали поселений остаются за этой механикой.

Сканер даёт: поверхность (тип/формы поверхности, поверхностные месторождения — как
поверхностный уровень разведки 10.2.2, без мини-игры) + наличие поселений (есть/нет + число,
без деталей: население/раса — только присутствие/отчёт). Дата актуальности = момент скана.

### 6.3. Личный каталог и синергия с рынком отчётов

- Скан пишется в **личный каталог игрока** (`player_planet_knowledge`, §8): одна запись на
  (игрок, планета), обновляется при новом скане, дата = now.
- Синергия с рынком отчётов (`10_exploration.md` §10.3.4): сканер = генератор **личного**
  присутствия; отчёты = **торгуемое** знание. Зазор: отчёт может быть свежее/глубже/о чужом
  районе; личный скан — только там, где игрок был. Сканер **не дублирует** торгуемые отчёты
  (не копирует их, не заменяет покупку) — рынок отчётов сохраняет ценность (инвариант И9).
- Сущность «рынок отчётов» в игре отсутствует (кода нет, только дизайн 10.3) — **влияние
  исключено из чисел 77a**: сканер даёт только личное знание, отчёты — будущая система;
  двойного учёта нет (анти-ловушка, §13).

## 7. Полёт в невидимое

### 7.1. Правило

**Полёт к любой звезде разрешён** (решение создателя 2026-09-17: «оставим возможность полёта к
неизвестной звезде. Романтично»). «Слепой прыжок» (запрет полёта за радар) **отменён**:
- система в радиусе радара — цель доступна (модалка/детали доступны);
- система за радаром — звезда видна полноценно (имя/спектр/внешний вид/координаты, §5.5),
  полёт-цель **доступна**; модалка (детали системы) — 403 вне радиуса/знания;
- знание координат (личный каталог/отчёт) для полёта **не требуется** — оно остаётся
  механизмом доступа к деталям системы (модалка, §6.2) и к поиску планет (§10).

**Координаты системы не протухают** (звезда не двигается): координаты — открытая информация
(§5.5); протухают детали планеты (поверхность/поселения, §8).

### 7.2. Нацеливание (упразднено 2026-09-17)

Развилка «как игрок нацеливается по координатам из отчёта (кнопка в карточке отчёта?)».
**Решение (2026-09-17):** полёт к любой звезде разрешён — механизм «нацеливание по знанию»
(кнопка «Лететь» как обход радара) **не нужен**; полёт из карточки системы/поиска работает
как обычно (клик/кнопка), валидация видимости убрана (§7.3). Гейт §16.7 закрыт. Топливо —
будущее ограничение дальности (задел, не реализуется в 77a).

### 7.3. Серверная валидация

`/travel` для `role=player` **не проверяет видимость цели**: полёт к любой звезде разрешён
(решение 2026-09-17); блок «403 цель вне зоны видимости» **удаляется** — валидация остаётся
только на существование мира (404, как сейчас). Длительность полёта **сохраняется** (66a):
`0.3 сек × дистанция, мин 3`; полёт переживает рефреш (42a); `current_world_id` — рамки полёта
уже есть. В полёте радар «едет» по интерполяции (центр = текущая позиция) — для детальной
видимости (модалка/скан/чужие игроки), не для вида звёзд.

**Будущее ограничение (задел, не реализуется в 77a):** дальность полёта будет ограничиваться
топливным баком («У нас дальность полёта по топливному баку ещё будет ограничиваться. Пусть
летит, если хочет» — решение создателя 2026-09-17). Сейчас полёт — без ограничений дальности;
при реализации топлива (будущая фича) полёт получит проверку «хватит ли топлива».

## 8. Хранение знания о планете на дату и протухание (техническое ревью)

Интервью: «у игрока есть информация о каждой планете на какую-то дату… как и где ее хранить,
чтобы это не стало узким горлышком… после истечения срока она будет "протухать" — нужно
техническое ревьюирование». Предложение (детальная схема — с @manager при разработке):

### 8.1. Хранение

Таблица `player_planet_knowledge`:

| Колонка | Тип | Назначение |
|---|---|---|
| `user_id` | UUID | игрок-владелец знания |
| `planet_id` | UUID | планета |
| `data` | JSONB | снимок знания: поверхность, наличие поселений, источник |
| `scanned_at` | timestamptz | дата актуальности (момент скана/отчёта) |
| `source` | TEXT | `scanner` / `report` (задел под отчёты) |
| PK | `(user_id, planet_id)` | одна запись на (игрок, планета), обновление при новом скане |

Почему так (разворот подходов):

| Вариант | Как | Плюсы | Минусы / цена |
|---|---|---|---|
| **A. Таблица, одна запись на (игрок, планета) (рекомендация)** | выше | индексируемый PK; рост ограничен числом планет, которые игрок реально сканировал; обновление — UPSERT | — |
| **B. JSONB-массив на users** | вся информация в одной колонке игрока | нет новой таблицы | не масштабируется (весь массив переписывается при каждом скане), нет индексов по планетам, узкое горлышко растёт с числом планет |
| **C. Таблица-история (каждый скан — запись)** | append-only | полная история | растёт бесконечно (каждый взгляд на модалку = запись), нужен архив/VACUUM — это и есть узкое горлышко, которого боялся создатель |

**Принято: A.** Оценка риска узкого горлышка: рост таблицы ∝ (число игроков) × (число
сканированных планет). Сканер работает только в радиусе радара (~25–50 систем на старте) →
игрок сканирует десятки–сотни планет за сессию. При 100k игроков × 100 планет = **10M строк** —
терпимо для Postgres с PK-индексом; фоновых джобов нет (актуальность считается на чтении).
Запись пишется только при реальном скане (ленивый прогон §6.1), не при каждом открытии
модалки без скана.

### 8.2. Протухание

**Что протухает:** детали планеты (поверхность, наличие поселений) — динамические данные.
**Что не протухает:** координаты системы — открытая информация (§5.5), стабильны по
определению (звезда не двигается); протухание касается только деталей планет.

**Как считается актуальность:** на чтении, без фонового джоба: запись «актуальна», если
`scanned_at ≥ now − срок`; иначе «устарело (дата)». Срок — **7 дней** (решение создателя 2026-09-17; аналог
«отчёт недельной давности стоит копейки», 10.3.4).

**Что делает протухание:** (1) визуальная пометка «устарело (дата)» в модалке (требование
10.3.1 «возраст данных всегда виден»); (2) устаревшее знание не считается «свежим» для
отображения как текущего состояния (показывается с датой, не как «сейчас»). Физического
удаления **нет** (история игрока остаётся; удаление — отдельное решение, не в этой фиче).

Разворот подходов по протуханию:

| Вариант | Как | Плюсы | Минусы / цена |
|---|---|---|---|
| **A. Статус на чтении (рекомендация)** | данные остаются, актуальность считается при чтении | ноль фоновых джобов, история сохраняется, «возраст всегда виден» | — |
| **B. Физическое удаление** | запись удаляется после срока | «чисто» | фоновый джоб (узкое горлышко), потеря истории игрока |
| **C. Без пометок** | данные остаются навсегда | просто | нарушает 10.3.1 (возраст не виден) — игрок действует на устаревшем, чувствуя себя обманутым |

**Принято: A.**

## 9. Визуал границы видимости

### 9.1. Функциональное требование (переключалка)

- На карте для `role=player` рисуется **граница видимости** — круг радиуса радара вокруг
  текущей позиции игрока (центр движется с кораблём, включая полёт).
- **Тестовая переключалка**: временный UI-элемент на карте (в меню видов/настроек карты),
  переключающий 2–4 варианта отрисовки границы. Выбор хранится в `localStorage` (тестовый
  инструмент, не в БД). Назначение — создатель смотрит варианты и выбирает один.
- После выбора создателя: фиксируется один вариант, переключалка убирается (решение о
  сохранении/удалении переключалки — за создателем на гейте §16.6).
- Переключалка доступна и для `admin`/`skycomposer` (им тоже смотреть), но на их видимость
  (видят всё) не влияет — только на отрисовку границы.

### 9.2. ТЗ для @gdesigner (варианты границы)

Что нужно отрисовать: **4 варианта** визуализации границы видимости (круг радиуса радара
вокруг корабля игрока) на тёмном фоне карты со звёздами. Учесть гибрид «звёздное поле» (§5.1)
и открытую информацию о звёздах (§5.5): за кругом звёзды **видны полноценно** (имя/спектр/
цвет/размер — открытая информация; скрыты только детали системы: модалка/скан/чужие игроки) —
варианты различают подачу границы «зона детальной видимости ↔ остальная карта», а не
«полные данные ↔ точки». Формат: статичные превью (скриншоты карты с наложением варианта,
2 масштаба: стартовый радиус 800 px, без радара 200 px) + описание реализации (canvas-слой,
прозрачность, цвета, анимация при движении).

Варианты (предложение дизайнера, финальные — за @gdesigner):

1. **«Туман войны»** — полупрозрачное затемнение вне круга (звёзды за кругом приглушены, но
   видны с именами/спектром); внутри — нормальная яркость и полные данные системы. Классика,
   читается мгновенно.
2. **«Светящийся контур»** — тонкая светящаяся окружность границы (неоновый обод), внутри —
   лёгкая подсветка; вне круга — обычный фон со звёздами. Минимализм.
3. **«Градиентное затухание»** — мягкий градиент от края круга к периферии (звёзды за кругом
   плавно приглушаются, но остаются с именами/спектром). Мягче, но граница менее чёткая.
4. **«Пикселизация/шум»** — за пределами круга звёзды приглушены шумом/сеткой («сырой
   сигнал»), внутри — чёткая карта. Стилистически выразительно.

Требования к любому варианту: не мешает чтению карты внутри радиуса; граница различима на
тёмном фоне; при движении корабля граница едет плавно (без мерцания); производительность —
один canvas-слой поверх карты (без перерисовки кластеров).

## 11. Серверное применение радиуса

### 11.1. Принцип

**Сервер — единственный источник видимости.** Для `role=player` сервер вычисляет круг
(центр = текущая позиция игрока, радиус = текущий радар из `users.equipment`) и **не отдаёт**
детали системы вне круга: модалка (403), скан/знание, чужие игроки, NPC-агенты. Сам **вид
звезды** (имя/спектр/внешний вид/координаты) — открытая информация (§5.5), отдаётся везде,
радиусом не ограничен (§11.2). Клиент не получает скрытых данных ни в одном ответе
(консистентность по построению); клиентская отрисовка границы — косметика поверх, не источник
правды. `admin`/`skycomposer` — без фильтра (видят всё).

### 11.2. Точки применения

| Точка | Что делается для `player` |
|---|---|
| `/api/worlds/filter` (кластеры карты) | гибрид «звёздное поле» (§5.1) + открытая информация (§5.5): **все** кластеры отдаются полным видом звезды — SampleID/SampleName/SampleSpectral/температура/тип звезды/системный тип/smods/координаты (как для админа); радиус на вид звезды **не влияет** (решение 2026-09-17). «Точка-огонёк» и «зажигание знанием» — отменены. Админ/skycomposer — всегда полные |
| `/api/worlds/{worldID}/planets` (модалка системы) | система вне радиуса и без знания → 403/«вне зоны видимости» (для player) — **НЕ меняется** (открывается только сама звезда, не её содержимое); система в радиусе — планеты отдаются с полями видимости: детали (поверхность/поселения) — только при знании в `player_planet_knowledge` (с датой), иначе — заглушка «нет данных — купить отчёт»; недра/атмосфера/детали поселений — всегда скрыты для player (сканер их не вскрывает, §6.2) |
| `/api/npc/positions` (агенты) | агенты вне радиуса отбрасываются (для player) — **НЕ меняется** |
| `/api/npc/search` | агент вне радиуса — найден, но без координат («вне зоны видимости») — **НЕ меняется** |
| `/api/entities/search` | звёзды — всегда полные (имя/спектр/координаты открыты, §5.5); планеты/спутники систем вне радиуса/знания — без имени звезды и координат (И11 в части содержимого) (§10) |
| **новый** `/api/players/positions` | позиции чужих игроков в радиусе радара запрашивающего (§5.3) — **НЕ меняется** |
| `/travel` | валидация цели: мир существует (404); ограничений видимости НЕТ — полёт к любой звезде (§7.3, решение 2026-09-17) |

### 11.3. Производительность

- Кластеры карты — в Go по снапшоту mapcache (как сейчас `FilterWorldsHandler`),
  O(кластеры в viewport), без SQL в хот-пате. Инвариант 2 проекта (стоимость не от размера
  галактики) держится: отдаётся только viewport; для player вид звёзд — как для админа
  (фильтр видимости звёзд снят решением 2026-09-17 — стоимость не выросла относительно
  админского пути, кластеры viewport ограничены).
- Позиции чужих игроков: кэш в памяти (как `PositionCache` NPC, 20a.1 §2.2.B) + фильтр по
  радиусу на чтении; при малом числе онлайн-игроков — просто запрос с фильтром.
- `player_planet_knowledge`: чтение по PK `(user_id, planet_id)` — O(1); запись — UPSERT.

## 12. Данные и API (миграция 000040)

Миграция `000040` **забронирована** за 77a (`docs/DB.md`). Предложение по таблицам/колонкам
(детальная схема SQL согласуется с @manager при разработке):

```sql
-- Справочник моделей кораблей
CREATE TABLE ship_models (
    id         TEXT PRIMARY KEY,          -- 'starter'
    name       TEXT NOT NULL,
    slots      JSONB NOT NULL,            -- {"radar":1,"scanner":1,"engine":1}
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Справочник оборудования
CREATE TABLE equipment (
    id         TEXT PRIMARY KEY,          -- 'radar_1', 'scanner_1' (одна модель радара; уровни — будущее с рынками)
    type       TEXT NOT NULL CHECK (type IN ('radar','scanner','engine')),
    name       TEXT NOT NULL,
    params     JSONB NOT NULL,            -- радар: {"radius":400}; сканер: {"depth":"surface","settlements":true}
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Игрок → модель и установленное оборудование
ALTER TABLE users ADD COLUMN ship_model_id TEXT REFERENCES ship_models(id);
ALTER TABLE users ADD COLUMN equipment JSONB;  -- {"radar":"radar_1","scanner":"scanner_1","engine":null}

-- Личный каталог знания о планетах (на дату)
CREATE TABLE player_planet_knowledge (
    user_id    UUID NOT NULL REFERENCES users(id),
    planet_id  UUID NOT NULL REFERENCES planets(id),
    data       JSONB NOT NULL,            -- поверхность, наличие поселений, источник
    scanned_at TIMESTAMPTZ NOT NULL,
    source     TEXT NOT NULL DEFAULT 'scanner',  -- 'scanner' | 'report' (задел)
    PRIMARY KEY (user_id, planet_id)
);
```

Бутстрап: стартовые записи справочников (`ship_models: starter`, `equipment: radar_1,
scanner_1`) + выдача новым игрокам (`ship_model_id='starter'`, `equipment={radar:radar_1,
scanner:scanner_1, engine:null}`) — при регистрации/бутстрапе (как дефолты 61b).

API:

| Метод | Путь | Авторизация | Назначение |
|---|---|---|---|
| `GET` | `/me` | игровой JWT | расширяется: `ship_model_id`, `equipment`, `radar_radius` (вычисленный) |
| `GET` | `/api/players/positions` | игровой JWT | **новый**: чужие игроки в радиусе (§5.3) |
| `GET` | `/api/worlds/filter` | игровой JWT | кластеры для player: полный вид звезды (имя/спектр/внешний вид/координаты — открытая информация, §5.5); радиус не влияет на вид звезды (§11.2) |
| `GET` | `/api/worlds/{worldID}/planets` | игровой JWT | скрытие деталей системы за радаром/знанием (§11.2) |
| `GET` | `/api/npc/positions` | игровой JWT | фильтр агентов по радиусу для player |
| `POST` | `/travel` | игровой JWT | валидация цели: существование мира; полёт к любой звезде (§7.3) |

Ошибки — JSON `{"error": "..."}`, как существующие.

## 13. Инварианты и числа

**Числа (решены создателем 2026-09-17):**

- Радиус радара: **200** (без радара) / **800** (старт, одна модель `radar_1`; увеличен с 400 px,
  миграция `000042`). Старт 800 px ≈ **25–50 систем** (сверка: плотность боевых пресетов
  dense/sparse/compact в круге 800 px — площадь ×4 от 400 px; 100k миров, MapSize 36–50k,
  MinDist 150–200). Прогрессия (600/900/1400/2000, «почти сектор») — **вне скоупа**, вернётся
  с рынками и ценами.
- Срок протухания знания: **7 дней** (решение создателя 2026-09-17).
- Полёт: `0.3 сек × дистанция, мин 3` (66a) — сохраняется без изменений; полёт к любой звезде
  (решение 2026-09-17); топливо/дальность — будущее ограничение (задел, не реализуется).
- Слоты: 3 типа × по 1 слоту (радар/сканер/двигатель); стартовая комплектация: радар-1 +
  сканер-1; двигатель не установлен.

**Инварианты:**

- **И1 (сервер — источник видимости):** клиент `role=player` не получает скрытых данных
  (детали системы) ни из одного эндпоинта (фильтрация на сервере по кругу радиуса);
  клиентская отрисовка границы — косметика, не источник правды. Вид звезды (имя/спектр/
  внешний вид/координаты) — открытая информация (И11).
- **И2 (стоимость не от размера галактики):** фильтр видимости — O(данные в viewport/круге)
  по снапшоту mapcache/кэшам; за-радарные кластеры отдаются полным видом звезды (как для
  админа — фильтр звёзд снят решением 2026-09-17, стоимость не выросла относительно
  админского пути); `player_planet_knowledge` читается по PK. Инвариант 2 проекта держится.
- **И3 (модель = рамка механики):** модель корабля не содержит визуала; визуал 61b
  (`ship_icon`/`ship_color`) — отдельная система, «пакетом» станет позже; 77a не отменяет 61b.
- **И4 (радар — единственный источник радиуса детальной видимости):** радиус, внутри которого
  доступны детали системы (модалка), скан/знание, чужие игроки и NPC-агенты, определяется
  только установленным радаром (без радара — минимум 200 px); не зависит от viewport/зума;
  слот `engine` на радиус не влияет (двигатель вне скоупа). Вид звезды радиусом не ограничен
  (И11).
- **И5 (знание ≠ видение, 10.3.3):** сканер даёт личное знание с датой; полные данные =
  присутствие + покупка свежих данных; никакая сеть/скан не дают данных свежее присутствия.
- **И6 (полёт к любой звезде):** полёт разрешён к любой (в т.ч. неизвестной) звезде — слепой
  прыжок отменён (решение создателя 2026-09-17); знание координат для полёта не требуется;
  дальность — будущее ограничение по топливному баку (задел, в 77a не реализуется).
- **И7 (админ видит всё):** `admin`/`skycomposer` — без фильтров видимости, навсегда
  (исключение, подтверждено).
- **И8 (возраст данных всегда виден, 10.3.1):** любое знание из каталога показывает дату
  актуальности; устаревшее помечается.
- **И9 (сканер не дублирует рынок отчётов):** сканер — личный слой присутствия; торгуемые
  отчёты (10.3.4) сохраняют зазор (свежесть/глубина/чужой район); сущность «рынок отчётов» в
  игре отсутствует — влияние исключено из чисел 77a (анти-двойной учёт).
- **И10 (координаты не протухают):** координаты системы — открытая информация (§5.5),
  стабильны; протухают детали планеты (поверхность/поселения) — статус актуальности на
  чтении, без фоновых джобов.
- **И11 (открытая звезда, закрытая система):** клиент `role=player` получает имя, спектральный
  класс, внешний вид (цвет, размер — как у админа) и координаты **любой** звезды — открытая
  информация (решение 2026-09-17, §5.5); **детали системы** (планеты, их поверхности/состав,
  поселения, число планет) — только в радиусе радара или при знании (модалка 403, §11.2);
  спектр за-радарной звезды не даёт ничего о её планетах.

**Риски и режимы отказа:**

- **Прогрессия радара вернётся с рынками** — уровни/цены/радиусы не проектируются сейчас
  (§4.2); при реализации рынков потребуется отдельная балансировка (осознанно отложено).
- **Сканер вскрывает недра/атмосферу** — решено: НЕ вскрывает (§6.2, 2026-09-17); если позже
  создатель расширит глубину — рынок отчётов теряет часть зазора (осознанное решение, не молча).
- **Маршрут чужих игроков виден** (§16.3) — бесплатные разведданные; если создатель решит
  иначе — добавляется линия полёта (дешёво, но меняет баланс информации).
- **Протухание без пометок** — нарушение 10.3.1 (игрок действует на устаревшем); защищено И8.
- **`player_planet_knowledge` растёт** — ограничено радиусом сканера (десятки–сотни планет на
  игрока); при 100k игроков ~10M строк — терпимо; детальная схема с @manager.
- **Детали системы утекают клиенту** — нарушение И11 (обход через поиск планет/модалку);
  закрыто: планеты/спутники неизвестных систем — без имени звезды/координат, модалка 403
  (§10, §11.2).
- **Фильтры кластеров по планетам** (`has_planets`/`has_life`/`has_habitable`/`planet_type`/
  `resource_category` в `/api/worlds/filter`) косвенно раскрывают наличие планет/жизни у
  за-радарных звёзд (существующее поведение, не менялось этим решением) — осознанный зазор,
  вопрос к создателю на гейте (§16.9).

## 14. Чего не делать (границы из идеи)

- **Не реализовывать рынки** (`11_markets.md`) — только привязка: справочник оборудования +
  стартовая выдача; покупка/вкладка «Оборудование» — будущее.
- **Не реализовывать двигатель как механику скорости** (формулы, загруженность) — замысел
  «скорость = двигатели + загруженность» вне скоупа; слот `engine` существует, пуст.
- **Не реализовывать «полные данные планеты»** (физическое присутствие + покупка свежих
  данных) — «потом подумаем как именно»; 77a закладывает хранилище (source), не механику.
- **Не вводить ассортимент моделей** — одна стартовая модель; прирастает с рынками.
- **Не менять визуал 61b** — модель корабля не трогает `ship_icon`/`ship_color`.
- **Не менять механику полёта** (66a: длительность, рефреш-переживание) — только снята
  валидация видимости цели (§7.3).
- **Не реализовывать топливо/дальность полёта** — будущее ограничение (решение создателя
  2026-09-17: «дальность полёта по топливному баку ещё будет ограничиваться»); в 77a полёт
  без ограничений дальности, задел фиксируется в спеке (§7.3).
- **Не удалять знание физически** (протухание = статус, §8.2); удаление — отдельное решение.
- **Не фильтровать звёзды для admin/skycomposer** — видят всё (И7).
- **Не реализовывать миникарту 51a** — только правило наследования видимости (§10).
- **Не делать видимость клиентской** — только серверная фильтрация (И1); клиентская отрисовка
  границы — косметика.
- **Не проектировать рынок отчётов** (10.3.4) — только зазор и поле `source` в каталоге.
- **Не проектировать прогрессию радара** (уровни, цены, «почти сектор») — вне скоупа, вернётся
  с рынками и ценами (§4.2).
- **Не проектировать транспондер** — сырая идея 77b, в 77a не входит (§17).
- **Не отдавать клиенту детали системы (планеты/поселения/число планет) вне радиуса/знания** —
  модалка 403, планеты неизвестных систем в поиске — без имени звезды/координат (И11);
  вид звезды (имя/спектр/внешний вид/координаты) — открыт (§5.5).
