## 0. Резюме (одним абзацем)

Вводится **личный дашборд игрока** — расширение существующей страницы `/` (`web/index.html`, уже озаглавлена «Дашборд»): шапка профиля (ник, корабль-превью, текущий мир, статус полёта), статистика (изучено систем, полётов, «открыто X из Y» по разделам) и **Энциклопедия** из шести разделов. Реальный контент — там, где данные уже есть: **расы** (новый серверный эндпоинт `GET /api/encyclopedia/races`: публичный срез каталога без админ-полей + лор из нового `config/race_lore.json` — машиночитаемая проекция `22_races.md`; эталон `config/races.json` не трогается), **звёзды** (переиспользование фронтового справочника `getSpectralInfo`/`exoticStarInfo`, дополненного температурой), **планеты** (фронт-реестр типов — заготовка с реестром). Пустые разделы — **заготовки с реестром будущего содержимого**: ресурсы/сырьё (99.2.5), корабли/оборудование (77a), лор-термины/существа (76a.1). Открытие — **смешанное (в)**: звёзды и планеты показывают базовое сразу (публичный справочник), детали (экзотика, карточки типов) открываются действием; **расы — силуэтами «—» до встречи** (решение создателя 2026-09-17, гейт 1: имя, класс, окна, атрибуты, лор открываются по действию — встреча расы в модалке поселения; люди открыты по умолчанию; будущее — отчёт рынка 10.3.4). Хранение открытий — **клиентский журнал** (`localStorage`), без новых таблиц и миграций; договорённость с 77a: `player_planet_knowledge` — будущий серверный источник знания, энциклопедия — слой отображения (дублирующую таблицу не создаём). Открытие — презентационный слой (в отличие от 77a, где видимость — серверная защита данных: у энциклопедии нет экономического веса). Никаких покупок в этой фиче (рынок отчётов — заготовка).

## 2. Природа сущностей — разбор по правилу «сущность с двумя экземплярами»

1. **Энциклопедия** — **справочник-каталог** (атрибут-справочник), не событие и не лог: это личная панель отображения данных, существующих в каталоге рас, справочнике звёзд и реестрах. Своей таблицы не имеет.
2. **Журнал открытий** — **личные данные игрока** (что он встретил), но **не сущность БД**: хранится клиентски (`localStorage`), потому что (а) серверного источника персональной истории сейчас нет, (б) у открытий нет экономического веса (никто их не видит, не торгует, не влияет на баланс — инвариант «знание не покупается» не затронут: энциклопедия — отображение знания, не хранилище). Владелец — один игрок, один браузер; расширяемость — через будущий серверный источник 77a (§7).
3. **`config/race_lore.json`** — **справочная запись каталога** (проекция лора `22_races.md` §3/§4), не событие и не лог. Владелец — общий справочник для всех игроков (одна раса — одна запись лора). Расширяемость: 60 записей сейчас, 61-я раса = новая запись, схема не меняется.

**Анти-ловушка «сущность вне игры»:** сущность «рынок отчётов» (10.3.4) в игре отсутствует (кода нет, только дизайн) — **влияние исключено из чисел 86a**: энциклопедия показывает видовую справку (кто раса) — и только после встречи (до неё — силуэты), а не локации (где раса живёт); локации остаются за отчётами (будущая система) — двойного учёта нет, рынок отчётов не обесценивается (обоснование §5.1.4). Сущность «личное знание» (`player_planet_knowledge`, 77a) в игре отсутствует (спека в дизайне, не в коде) — энциклопедия живёт без её таблицы (клиентский журнал, §7).

## 3. Маршрут и вход

### 3.1. Решение: `/` — существующая страница «Дашборд» расширяется

**URL дашборда — `/`** (`web/index.html`): страница уже существует, озаглавлена «Дашборд», служит посадочной после логина/регистрации (`login.html`/`register.html` → `window.location.href = '/'`). Отдельный маршрут `/dashboard` **не вводится** — дублирование страницы без пользы (одна точка входа, «один факт — одно место»).

Разворот подходов:

| Вариант | Как | Итог |
|---|---|---|
| **A. Расширить `/` (принято)** | index.html дорастает до полного дашборда: шапка профиля, статистика, энциклопедия; блок «Корабль» (селектор спрайта/цвета 61b) остаётся | принято: страница уже «Дашборд», логин уже ведёт на `/`; ноль новых маршрутов |
| **B. Новый `/dashboard`** | отдельная страница, `/` остаётся минимальной | отклонено: две страницы личной зоны, дублирование кнопок и логики; вход на `/` уже есть |
| **C. Вкладка в модалке** | дашборд внутри модалки системы | отклонено решением создателя (отдельная личная панель) |

### 3.2. Вход с других страниц

- **Карта** (`web/map.html`): кнопка «🏠 Дашборд» в шапке **уже есть** (`location.href='/'`) — не трогаем.
- **Контракты** (`web/assignments.html`): кнопка «← Назад» (`location.href='/'`) **уже есть** — не трогаем.
- **`web/contracts.html`**: кнопки возврата на дашборд нет — **добавить** «🏠 Дашборд» в шапку (минорная правка, косметика, §10).

### 3.3. Не-регрессия флоу

Дашборд — отдельная страница; карта, модалка системы и полёт **не меняются** по флоу. Единственная правка в модалке — **аддитивный хук журнала** (§4.3): при открытии карточки системы клиент записывает в журнал встреченное (миры, расы поселений, типы планет, тип звезды). Хук ничего не блокирует, не перехватывает ответы — только читает уже полученные данные и пишет в `localStorage`.

## 4. Состав дашборда

### 4.1. Шапка (профиль)

Из `/me` (существующая ручка, без изменений): ник (`username`), корабль-превью (спрайт `ship_icon` + цвет `ship_color` через `recolorShipSprite` из `web/static/js/map/ship_sprites.js` — переиспользование), текущий мир (`current_world_name`), статус полёта (`flight`: «в полёте из X в Y» / «на месте»).

### 4.2. Статистика

| Метрика | Источник | Смысл |
|---|---|---|
| Изучено систем: N | журнал (`visitedWorlds`) | число миров, карточку которых игрок открывал (модалка системы) |
| Полётов: M | журнал (`flights`) | число завершённых полётов (событие прибытия на карте) |
| Расы: открыто X из 60 | журнал (`metRaces`) | расы, чьи карточки открыты встречей (имя+числа+лор; до встречи — силуэт) |
| Экзотика: открыто X из 4 | журнал (`seenStarTypes`) | экзотические типы звёзд, встреченные игроком |
| Планеты: открыто X из 9 | журнал (`seenPlanetTypes`) | типы планет, чьи карточки открыты первым посещением |
| Ресурсы / Корабли / Лор | — | «заготовка» (раздел наполнится с 99.2.5 / 77a / 76a.1) |

**Числа Y (знаменатели):** 60 рас (каталог `config/races.json`), 4 экзотических типа звёзд (`star_type`: `white_dwarf`/`neutron`/`black_hole`/`protostar`, 29a/41a), 9 типов планет (реестр фильтра карты `web/map.html`: землеподобная, газовый гигант, пустынная, ледяная, вулканическая, океаническая, радиоактивная, органик, скалистая). Знаменатели — константы фронт-реестров (§5), не серверные числа.

**Пометка «заготовка»:** разделы без контента не участвуют в «открыто X из Y» — показывают статус «заготовка» с реестром будущего содержимого (§5.4–§5.6).

### 4.3. Журнал открытий (клиентский, `localStorage`)

Ключ `zorion.journal`, структура:

```json
{
  "metRaces": ["ammonia", "sulfur_nests"],
  "seenStarTypes": ["black_hole"],
  "seenPlanetTypes": ["землеподобная", "газовый гигант"],
  "visitedWorlds": ["<world_id>", ...],
  "flights": 3
}
```

Точки записи (аддитивные хуки, не меняют флоу):

| Событие | Где | Что пишется |
|---|---|---|
| Открытие модалки системы | `web/static/js/modal/index.js` (загрузка данных системы) | `visitedWorlds += world_id`; `seenStarTypes += star_type` (если экзотика); `seenPlanetTypes += type` каждой планеты; `metRaces += race_id` каждого поселения (поле `settlements[].race_id`, `models/economy.go`; пусто = люди — люди уже «встречены» по умолчанию, §5.1.3) |
| Прибытие полёта | `web/static/js/map/flight.js` (событие прибытия, 33b) | `flights += 1` |

Журнал — **единственный источник «открыто X из Y»** и состояния открытия лора. Правка через JS-модуль `web/static/js/dashboard/journal.js` (единая точка чтения/записи; другие модули вызывают `journal.record(...)`).

### 4.4. Блок «Корабль»

Существующий селектор спрайта/цвета (61b, `web/index.html`) **остаётся как есть** — не переносится и не меняется.

## 5. Энциклопедия — разделы

### 5.1. Расы (реальный контент)

#### 5.1.1. Источник данных

Новый серверный эндпоинт **`GET /api/encyclopedia/races`** (игровой JWT). Возвращает **публичный срез каталога** (`config/races.json` через `internal/races.Catalog()`, read-only) **без админ/баланс-полей** + **лор** из нового файла **`config/race_lore.json`** (машиночитаемая проекция `22_races.md` §3/§4, загружается при старте тем же пакетом `internal/races` или отдельным лоадером — решение при разработке).

**Публичный срез (whitelist):**

| Поле | Отдаётся | Комментарий |
|---|---|---|
| `id`, `name`, `basis` | ✅ | идентификация, основа существования |
| `conditions` (temperature/pressure/atmosphere/radiation/heat_flux/gravity/liquid_water) | ✅ | «справочные числа» — окна opt/surv; клиент показывает после встречи (до встречи — силуэт, §5.1.2) |
| `attributes` (6 атрибутов) | ✅ | «справочные числа» (идея: атрибуты в базовом) |
| `home` (star_classes, planet_niche), `bulge` | ✅ | справочные |
| `forage.source` | ✅ | текст «что ест» (без `basic_resources` — пусто до 99.2.5) |
| `robotic` (power_source, heat, materials.categories/axes) | ✅ | у роботов вместо consumption; **без** `robotic.heat_twist` (флаг механики-кандидата) |
| `consumption` (13 осей) | ❌ | баланс-данные; семейство уже сводит их в ярлык F1–F9 (лор) |
| `territory`, `dormancy`, `famine_aggression`, `off_cascade`, `tuning` | ❌ | внутренние флаги/механики-кандидаты (в числа не входят, 99.2.24 §6 п.8) |

**`config/race_lore.json`** — новая запись на расу:

```json
{
  "races": [
    {
      "id": "humans",
      "family": "F1",
      "character": "середина по всем осям — эталон, от которого считаются все расы",
      "how_live": "кислородно-водная биохимия, едят биосферу, строят поселения",
      "why": "дом расы №1; люди — точка отсчёта галактики (и игрок)",
      "coexistence": "несовместимы с серными, аммиачными, метановыми, небесными, углекислыми (O₂ — яд для неводных)"
    }
  ]
}
```

Поля лора — проекция карточек `22_races.md` §3/§4: `family` (F1–F9 / `robotic`), `character` («характер» словами), `how_live` («как живут»), `why` («зачем»/ниша), `coexistence` («сосуществование»); у роботов дополнительно `origin` («происхождение»: люди/самозародившийся/другие био/другие ИИ, §4.2). **Правило синхронизации:** `22_races.md` остаётся человекочитаемым источником лора; `race_lore.json` — его машиночитаемая проекция; правка лора вносится в оба места (пометка в шапке `22_races.md` — дельта §14). Эталон `config/races.json` **не трогается** (решение создателя).

**Разворот подходов по источнику лора:**

| Вариант | Как | Итог |
|---|---|---|
| **A. Отдельный JSON `config/race_lore.json` (принято)** | машиночитаемая проекция `22_races.md`; сервер отдаёт её в ручке | принято: лор извлекается один раз, формат валидируется при старте (как каталог рас), `22_races.md` не парсится |
| **B. Парсинг `22_races.md` при старте** | markdown → структура | отклонено: хрупкий парсинг прозы, разметка не предназначена для машинного чтения |
| **C. Лор в Go-коде** | map в хендлере | отклонено: дублирование контента в коде, правки лора = пересборка |
| **D. Расширить `config/races.json`** | добавить лор-поля в карточки | **запрещено** решением создателя (эталон не трогаем) |

#### 5.1.2. Отображение

- Сетка карточек 60 рас: **все расы показаны силуэтами «—»** (без имени и чисел) — решение создателя 2026-09-17 (не-регрессия 2026-09-16: «игрок вообще ничего не видит, пока не купит информацию»). Силуэт подписан «???» и плейсхолдером «Раса не встречалась — посетите её поселение».
- **Открытая карточка** (раса в `journal.metRaces`): имя, бейдж семейства (F1–F9 / «Роботы»), основа (`basis`), ключевые окна (T в °C — конверсия как в модалке `kelvinToCelsius`; P в атм; g в земных), мини-бары атрибутов, дом (типы звёзд + ниша) + **лор-блок** (характер/как живут/зачем/сосуществование).

#### 5.1.3. Что «открывает» расу (сейчас и потом)

| Источник открытия | Статус | Механика |
|---|---|---|
| **Встреча расы** — игрок открыл модалку системы, где есть поселение с `race_id = X` | ✅ сейчас | модалка уже показывает `race_name` (`web/static/js/modal/tabs.js:366`); хук журнала пишет `race_id` в `metRaces` |
| **Люди** | ✅ по умолчанию | `race_id` пусто = легаси/люди; люди «встречены» изначально (игрок — человек) |

#### 5.1.4. Не-регрессия решения 2026-09-16

Решение создателя 2026-09-16 (`22_races.md` §2.6): «игрок вообще ничего не видит, пока не купит информацию; расы открываются через рынок отчётов». **Решение создателя 2026-09-17 (гейт 1):** расы в энциклопедии — **только силуэты «—»** до встречи; имя, класс, окна, атрибуты, лор открываются по действию (встреча расы; люди — по умолчанию; будущее — отчёт 10.3.4). Это **полная не-регрессия решения 2026-09-16**:

- **Карта не получает ярлыков рас** — без изменений (никаких правок карты/регионов).
- **Энциклопедия не раскрывает рас до встречи** — силуэты без имён/чисел; видовая справка (кто раса) открывается только после того, как игрок увидел расу в модалке поселения.
- **Локации рас остаются за отчётами** (10.3.4): где раса живёт, доминанта планеты, подселения — будущая платная информация. Энциклопедия не отвечает на «где», только на «кто» (и только после встречи) — рынок отчётов не обесценивается (зазор «свежесть/глубина/район» держится).

- **Звёзды и планеты** (публичные справочники, не расы) — базовое видно сразу: решение 2026-09-16 касается рас; спектральные классы и типы планет — общий референс карточки, как в модалке.

## 7. Хранение открытий (архитектурный фильтр)

### 7.1. Решение: клиентский журнал, без таблиц и миграций

**Открытия хранятся в `localStorage` (журнал §4.3). Новая таблица НЕ создаётся, миграция НЕ пишется.** Проверка по фильтру менеджера:

- **«Нужна ли таблица?»** — нет: у открытий нет потребителя вне личной панели (никто не читает чужие открытия, нет торговли, нет баланса). Таблица оправдана решением (инвариант 10 GD_PROMPT: «сущность оправдана решением»); решения с открытиями сейчас нет — только отображение.
- **«Выводятся ли из существующих данных?»** — частично: «встреча» происходит в модалке (данные уже у клиента); серверного следа встреч нет (персональной истории в БД не существует). Поэтому открытия — клиентский журнал (локализованно).
- **«Не плодим ли дублирующие таблицы?»** — да, таблица открытий дублировала бы будущую `player_planet_knowledge` (77a): обе писали бы «игрок видел планету/расу». Дублирующую таблицу не создаём.

### 7.2. Договорённость о разделении с 77a

| Слой | Кто | Что хранит |
|---|---|---|
| **Хранилище знания** | 77a (`player_planet_knowledge`, миграция `000040` — за 77a) | серверное знание о планетах (поверхность, поселения, дата) — **будущий источник правды** |
| **Слой отображения** | 86a (журнал клиента + чтение) | состояние «открыто X из Y» и показ лора — личная панель |

Когда 77a войдёт в код: энциклопедия **читает** `player_planet_knowledge` (через `/me` или новую ручку — решит 77a) как источник «встреченных» планет/рас; клиентский журнал остаётся кэшем отображения. **86a не создаёт свою серверную таблицу знания** — это и есть «не крадём миграцию у 77a» и «не плодим дублирующие таблицы».

### 7.3. Открытие — презентационный слой (осознанное отличие от 77a)

В 77a видимость — **серверная защита данных** (клиент не получает скрытое; знание имеет экономический вес: полёт, рынок отчётов). В 86a открытие — **презентационный слой** (подтверждено решением гейта 1, §12 п.2): сервер отдаёт публичный срез + лор в ответе ручки (публичный контент проекта), клиент показывает карточки рас (имя/числа/лор) по журналу — до встречи силуэт «—». Обоснование: у энциклопедии нет экономики (не торгуется, не влияет на баланс, не даёт преимуществ в мире); «открытие» — игровое ощущение заполнения справочника, а не граница доступа. Если создатель захочет серверную защиту (силуэты на сервере) — это потребует таблицы (отдельное решение, не этой фичи).

### 7.4. Риск клиентского журнала (режим отказа)

- **Per-browser:** открытия и статистика привязаны к браузеру (другой браузер/устройство — пустой журнал). Осознанно: до серверного знания 77a серверной истории нет в принципе; метка «журнал этого браузера» в UI дашборда (мелкая пометка).
- **Очистка localStorage:** журнал теряется (открытия сбрасываются). Не критично: открытия набираются заново действиями; потери имущества/прогресса нет (инвариант 4 проекта: офлайн не отнимает имущество; здесь и имущества нет).

## 13. Кандидат ГД-сущности (Вопрос → Ответ)

Каждое задание приносит +1 кандидата; в текущие числа **не входит** (анти-двойной учёт):

- **«Хроника открытий»** — личный журнал первых встреч как игровая сущность: каждая первая встреча (раса, экзотическая звезда, тип планеты) фиксируется записью с датой и координатами системы; дашборд показывает «ленту первооткрывателя» (история игрока как рассказ, а не счётчик). Игровой вес: хроника — будущий сырьевой материал для **авторских отчётов** (10.3.4: отчёт заверяется системой по фактическому результату — хроника фиксирует факты, из которых отчёт собирается); мотив исследовать новое (заполнить книгу). **Статус: принят как кандидат (решение создателя 2026-09-17, гейт 1)** — записан, НЕ реализуется в этой фиче. **Зависимость:** реализация после рынка отчётов (10.3.4); в числа 86a не входит — сейчас хроника существует как клиентский журнал (§4.3), сущность оформляется отдельной фичей.
