## 0. Резюме (одним абзацем)

Корабль перестаёт быть цельным SVG-спрайтом и становится **схемой**: ровно одна
деталь каждой категории (корпус, нос, крылья, двигатели, хвост — предложение,
FAQ В1) + один цвет из палитры (предложение: 12 цветов, FAQ В2). Детали —
параметрические SVG-фрагменты в общем холсте 200×200 (нос вправо): основная
масса — `fill="currentColor"` (цвет из схемы, инвариант «один основной цвет на
корабль»), внутри деталей — фиксированные акцентные элементы с явным `fill`
(кабина, иллюминаторы, огни, тёмное сопло, свечение сопел) — для красоты (уточнение эталона
2026-09-15, FAQ `21_ships.md` §21.7). **Любая допустимая комбинация деталей —
цельный правдоподобный силуэт, «не франкенштейн»** (уточнение эталона 2026-09-15:
зоны и стыки категорий согласованы, габариты форм ограничены, общие правила
стиля; §3.1–§3.2, инвариант И9). Каталог деталей генерируется в
админке («теневой генератор», вкладка «Корабли») и хранится в таблице `ship_parts`
(предложение, FAQ В3). Игрок собирает корабль в дашборде (`users.ship_visual`),
агент получает сборку детерминированной функцией от seed (предложение, FAQ В4).
Рендер на карте — композиция фрагментов на клиенте с кэшем по схеме. Существующий
блок (`ships.json`, 21 SVG, `users.ship_icon`) заменяется с мостом (FAQ В5).
Детали — чисто косметические (эталон: тех-характеристики не проектировать).

## 1. Контекст и решения создателя

Цитаты и решения — в идее `24a` и в FAQ `21_ships.md` §21.7. Ключевое:

1. Текущие модели кораблей не нравятся — нет разнообразия; 100к агентов не
   должны быть «точками».
2. Подход: детали (двигатели, крылья, носы + предложить) × ~10 форм × цвета;
   инвариант «весь корабль — один цвет» (уточнено 2026-09-15: один основной
   цвет + фиксированные акцентные элементы внутри деталей — «кабина может иметь
   внутренние детали другого цвета, для красоты»).
3. Детали чисто косметические; тех-характеристики — далёкое будущее.
4. «Теневой» генератор в админке → агенты собирают себе корабль; игроки — в
   дашборде.
5. Строим поверх существующего блока (21 SVG + `ships.json` +
   `users.ship_icon` + `flight.js`); совместимость продумать.

Открытые вопросы эталонов — FAQ В1–В5 (`21_ships.md` §21.7): категории, палитра,
хранилище деталей, способ сборки агента, судьба legacy-блока. Рабочая
конфигурация спеки — предложения дизайнера (как вариант A в `20a.1` §3.3);
финальное решение за создателем на гейте.

## 2. Модель данных

### Миграция `000027_create_ship_parts.sql` — каталог деталей

```sql
CREATE TABLE IF NOT EXISTS ship_parts (
    id         TEXT PRIMARY KEY,          -- "hull_arrow", "nose_spike", ...
    category   TEXT NOT NULL CHECK (category IN ('hull','nose','wings','engine','tail')),
    name       TEXT NOT NULL,             -- человеческое имя ("Стрела", "Клин")
    svg        TEXT NOT NULL,             -- SVG-фрагмент (без <svg>-обёртки), viewBox 200×200
    params     JSONB NOT NULL DEFAULT '{}', -- параметры генерации (для перегенерации)
    created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_ship_parts_category ON ship_parts (category);
```

- `CHECK` на категории — как `users_role_check` в `99.2.14` §2 (дешевле кода).
  Список категорий — константа в одном месте; расширение списка — осознанная
  правка (категории открыты, FAQ В1).
- `id` генерируется как `{category}_{slug}` от параметров (детерминизм: та же
  генерация с тем же seed → тот же id, `INSERT ... ON CONFLICT DO UPDATE` при
  перегенерации категории).

### Миграция `000028_add_users_ship_visual.sql` — схема корабля игрока

```sql
ALTER TABLE users ADD COLUMN ship_visual JSONB;
```

- `ship_visual`: `{"color": "#3b82f6", "parts": {"hull": "hull_arrow",
  "nose": "nose_spike", "wings": "wings_delta", "engine": "engine_dual",
  "tail": "tail_twin"}}`.
- `NULL` = «ещё не собирал»: рендер и `/me` отдают дефолтную сборку от
  (id игрока, legacy `ship_icon`) — см. §8. `ship_icon` не удаляется (мост, §8).
- Валидация на сервере при записи (`PUT /me/ship-visual`, §10): все категории
  заполнены, id ∈ каталог, цвет ∈ палитра. Иначе 400. (Инвариант И2, И4.)

### Конфиг `config/ship_visual.json` (новый)

- `palette`: массив из 12 цветов (предложение, FAQ В2).
- `accents`: фиксированные акцентные цвета + границы площади/размера акцентов
  (стекло, свечение, огни, тёмное сопло; §4, числа §9).
- `accentRules`: какие акценты каким категориям положены (нос — кабина, корпус —
  иллюминаторы, крылья — огни, двигатели — свечение, хвост — без; §3.3).
- `categories`: зоны холста, границы параметров и **габариты форм** по категориям
  (стыки/достижение, инвариант И6);
- `style`: общие правила стиля — обводка, скругления, сегменты, заполненность,
  база, акценты (§3.2, инвариант И9);
- `layerOrder`: корпус → крылья → нос → двигатели → хвост.
- Палитра и акценты read-only в админке (правка — будущее, не сейчас).

### Go-типы

`internal/models/ship_part.go`, `internal/models/ship_visual.go` — зеркала таблиц;
`internal/repository/ship_repository.go` — CRUD каталога + запись/чтение
`users.ship_visual` (схема игрока) + загрузка каталога в память.

## 3. Каталог и генератор форм

### 3.1. Категории, зоны, стыки, габариты (инвариант И6, И9)

Факты — `21_ships.md` §21.2 (категории и зоны холста 200×200, нос вправо,
порядок слоёв). Холст 200×200, центральная ось y=100. **Целостность сборки**
(эталон создателя 2026-09-15: «не франкенштейны, но красивые», FAQ
`21_ships.md` §21.7) держится тремя механизмами: (а) каждая деталь полностью
помещается в свою зону; (б) база придатка попадает в **гарантированную область
корпуса** (x [65,130], y [79,121] — пересечение всех допустимых корпусов) +
требования достижения — придаток всегда лежит на корпусе, а не рядом; (в)
габаритные ограничения форм — база придатка не больше минимального тела корпуса,
вылет не больше его длины.

| Категория | Зона (bbox) | Сторона стыка с корпусом | Габариты формы (min–max, px) |
|---|---|---|---|
| **Корпус** | x 45–155, y 70–130 (центрирован на оси y=100) | якорь: к нему стыкуются все придатки | ширина 60–110; высота 42–60; **min x ≤ 65** (корма достаёт до зоны двигателей); **max x ≥ 130** (нос достаёт до зоны носа) |
| **Нос** | x 125–200, y 70–130 | левая (к правому торцу корпуса) | база — y-протяжённость у x≈130: **24–40** (центрирована на y=100); длина (x): **55–70**; **bbox max x ∈ [185, 197]** (нос тянется вперёд, обводка 3 px не выходит за холст) |
| **Крылья** (верх/низ, зеркальные) | x 55–145, y 0–80 и y 120–200 | внутренняя (к борту корпуса) | хорда у борта: **6–38**; вылет от борта: **15–50**; размах (x): **20–65**; **max x ≤ 150** (крылья не залезают на нос); база достигает **y ≥ 79** (верх) / **y ≤ 121** (низ) — лежит на корпусе |
| **Двигатели** | x 0–70, y 75–125 | правая (к кормовому торцу) | база — y-протяжённость у x≈65: **22–40** (центрирована на y=100); длина (x): **30–60**; **bbox max x ≥ 65** (база на корпусе); левый край ≥ 3 px (запас под обводку) |
| **Хвост (киль)** | x 25–110, y 0–85 | нижняя (к палубе кормы) | ширина базы: **18–40**; высота: **15–55**; размах (x): **20–60**; **max x ≥ 65** (сидит над кормой, а не сбоку); база достигает **y ≥ 79** — лежит на корпусе |

Почему эти числа исключают «франкенштейна»:

- **Гарантированная область корпуса.** Корпус центрирован на оси y=100, высота
  42–60, min x ≤ 65, max x ≥ 130 → **любой допустимый корпус покрывает
  прямоугольник x ∈ [65,130], y ∈ [79,121]** (пересечение всех корпусов: min x ≤ 65
  и max x ≥ 130 дают покрытие x от 65 до 130; высота ≥ 42, центрированная на
  y=100, даёт y от 79 до 121). Любой придаток, базовая кромка которого попадает в
  эту область, лежит на корпусе **при любой форме корпуса** — «парящий» придаток
  невозможен по построению.
- **Стык каждой категории гарантирован попаданием базы в область корпуса:**
  - *Нос:* bbox min x ≤ 130, база y 24–40 центрирована на y=100 → база в
    [65,130]×[79,121].
  - *Крылья верх/низ:* база достигает y ≥ 79 / y ≤ 121; по x размах (20–65) в зоне
    [55,145] ⊇ [65,130] всегда пересекает область корпуса (размах ≥ 20 не
    помещается в зазоры [55,65) и (130,145] целиком).
  - *Двигатели:* bbox max x ≥ 65, база y 22–40 центрирована на y=100 → база в
    [65,130]×[79,121].
  - *Хвост:* база достигает y ≥ 79, max x ≥ 65 → размах пересекает область корпуса
    по x.
- **База любого придатка ≤ 40 px < минимальная высота корпуса 42 px** — ни один
  придаток не бывает «шире/выше» тела корпуса в точке стыка: гигантский нос на
  тонком корпусе невозможен по построению; база любой категории целиком помещается
  в гарантированную область корпуса по y (высота области 42 px).
- **Вылеты соразмерны корпусу:** крыло 15–50, киль 15–55, двигатель 30–60 против
  ширины корпуса 60–110 px — крыло не торчит «оторванной доской», двигатель не
  длиннее половины корпуса; при этом ни один придаток не выходит за холст с учётом
  обводки 3 px (левый край двигателя ≥ 3, нос max x ≤ 197, крылья max x ≤ 150).
- **Стыки согласованы между категориями:** у каждого придатка ровно одна прямая
  база (см. §3.2 п.5), и она гарантированно лежит на корпусе через область
  [65,130]×[79,121] (выше); требования достижения (min/max x корпуса, база носа
  min x ≤ 130, база двигателей max x ≥ 65, базы крыльев/хвоста по y) закрывают
  крайние случаи смещения.
- Контрольная проверка генератора: при генерации детали её bbox обязан пересечь
  **область корпуса-эталона [65,130]×[79,121]** на своей стороне стыка (база —
  на требуемую величину: нос min x ≤ 130, двигатели max x ≥ 65, крылья/хвост по
  y — см. таблицу) (И6, §11 Этап 2).

### 3.2. Единство стиля (общие правила генератора форм)

Любая комбинация читается «одним автором»: правила ниже применяются ко **всем**
категориям (и к акцентам), задаются в конфиге (`style`), проверяются тестами
(§11 Этап 2). Это минимум, гарантирующий целостность силуэта (И9):

1. **Обводка:** ширина **3 px**, цвет `#0b1220` — одинаковая у всех деталей и
   всех акцентных элементов (единый контур).
2. **Скругления:** внешние углы **r=6 px**, внутренние/вырезы **r=3 px**,
   минимум **r=2 px** — никаких нулевых «инопланетных» углов-игл.
3. **Контур основной массы:** **4–8 сегментов**, не более **1 дуги** (остальное —
   прямые фаски) — единая фасеточная геометрия, деталь не «блоб» и не «шестерня».
4. **Заполненность:** площадь заливки детали ≥ **55%** её bbox — никаких
   скелетных/решётчатых форм, выглядящих сломанными.
5. **Ровная база:** у каждого придатка ровно **1 прямая базовая кромка**
   (сторона стыка, §3.1) — чистое прилегание к корпусу без «органических» швов.
6. **Акценты:** строго внутри силуэта детали, отступ от контура ≥ **3 px**,
   радиус скругления **6 px** (как п.2), площадь одного акцента **≤ 6% площади
   заливки детали** (не более **90 px²**), суммарно на деталь **≤ 10% площади
   заливки детали** (не более **240 px²**) — лимит считается от самой детали, а не
   от холста: минимальный корпус (60×42) остаётся «однотонным с акцентами»
   (заливка ≥ 1386 px² → акценты ≤ ~139 px² ≈ 5.5% bbox), акцент не «торчит» из
   детали и не «расползается» по ней (§4/§9).
7. **Общая ориентация:** все части лежат носом вправо (горизонтальный размах по
   x), вертикальные выносы (крылья/киль) — перпендикулярно оси; наклонные кромки
   берутся из одного семейства углов (20°/25°/30°) — детали не «разнонаклонены».

### 3.3. Пакет `internal/generator/ship/`

```
GeneratePart(category string, seed int64) (Part, error)
```

- RNG от seed (локальный `rand.New`, правило `AGENTS.md` §0);
- параметры из границ категории (`config/ship_visual.json`), **габариты формы —
  из §3.1** (bbox ⊆ зона + требования достижения/базы), **стиль — из §3.2**
  (обводка 3 px, скругления 2/3/6 px, 4–8 сегментов, заполненность ≥ 55%,
  прямая базовая кромка, акценты с отступом ≥ 3 px);
- эмиссия SVG-фрагмента: основная масса — `fill="currentColor"`, обводка —
  фиксированная `#0b1220` шириной 3 px (как в текущих спрайтах), фон отсутствует;
- **акцентные элементы** — узлы с явным `fill` (не `currentColor`): цвет и
  границы размера из секции `accents` конфига, позиция — из зоны категории
  (И6), площадь — по §4/§9 (малая, от площади заливки детали; основная масса
  детали — `currentColor`); распределение по категориям — `accentRules`: нос —
  кабина (обязательно), корпус — иллюминаторы 0–3 (случайно), крылья — парные
  навигационные огни (красный — левый борт, зелёный — правый), двигатели —
  тёмное сопло (акцентный цвет `#1f2937`, §4) + свечение (обязательно), хвост —
  без акцентов;
- `id` = `{category}_{slug(params)}` — акценты входят в параметры генерации (те
  же параметры → та же деталь с теми же акцентами), `name` — из словаря имён
  категории (`internal/names/`, как имена регионов/ресурсов);
- детерминизм: `GeneratePart(cat, seed)` → один и тот же фрагмент всегда
  (включая акценты).

Шаблоны генерации по категориям — контур/полигон с параметрами
(длина, ширина, сужение, кривизна, число элементов и т.п.); точную форму
шаблонов уточняет разработчик при реализации (зона дизайна — формы, а не код).
Минимум: генератор обязан давать **10 визуально различимых форм** на категорию
при 10 разных seed (эталон «~10 форм»). Различимость меряется по **силуэту**
(очертанию основной массы детали), а не по акцентам: совпадение акцентов у двух
форм не конфликт, две формы с одинаковым силуэтом, различающиеся только
акцентами, — это одна форма.

### 3.4. Каталог в памяти

Загрузка всех деталей при старте + инвалидация/перезагрузка после генерации в
админке (паттерн mapcache: immutable snapshot + `atomic.Pointer`). Чтение
каталога — O(1), без БД в хот-пате рендера (И7).

## 4. Цвет и палитра

- Палитра — 12 цветов из конфига (предложение, FAQ В2): светлый металл, серый,
  тёмно-серый, красный, оранжевый, жёлтый, зелёный, бирюзовый, голубой, синий,
  фиолетовый, розовый. Критерии для баланс-проверки: читаемость на тёмном фоне
  карты, различимость цветов между собой, читаемость тёмных цветов.
- **Акцентная палитра — 5 фиксированных цветов** (вне 12-цветной палитры
  корабля; уточнение эталона 2026-09-15, FAQ `21_ships.md` §21.7): стекло
  `#e0f2fe` (кабина, иллюминаторы), свечение `#60a5fa` (сопла двигателей),
  огонь красный `#ef4444` (левый борт), огонь зелёный `#22c55e` (правый борт),
  тёмное сопло `#1f2937` (двигатели — тёмная заливка сопла, как в legacy-спрайтах).
  Плюс обводка `#0b1220` (общая, как сейчас). Критерий для баланс-проверки:
  читаемость акцентов на всех 12 цветах корпуса (тёмная обводка акцента
  обязательна).
- Цвет — свойство схемы; основная масса деталей — `currentColor`; композиция
  кладёт цвет в `style="color:#X"` корневого `<svg>` (И1 — конструктивно, см.
  §5). Акценты — явный `fill` в фрагменте, цвет схемы их не трогает.

## 5. Схема корабля и рендер

### 5.1. Композиция (клиент)

- `GET /api/ship-parts` → каталог (id, category, name, svg-фрагмент). Один запрос,
  кэш на клиенте; инвалидация не нужна в рамках сессии (каталог меняется редко;
  после перегенерации — обычный рефреш страницы).
- Схема → строка:
  `<svg viewBox="0 0 200 200" style="color:{color}"><g>{hull}</g><g>{wings}</g><g>{nose}</g><g>{engine}</g><g>{tail}</g></svg>`
  (порядок слоёв из конфига).
- Акцентные элементы — часть фрагмента детали (явный `fill`), цвет схемы их не
  перекрашивает; кэш по ключу (color + отсортированные id деталей) остаётся
  корректным: акценты входят в id детали (параметры генерации), а color трогает
  только `currentColor`.
- Кэш спрайтов по ключу схемы (Map: ключ = color + отсортированные id деталей):
  один раз скомпонованный SVG → `Image` (data URL) / offscreen-canvas.
- Фолбэк: деталь из схемы отсутствует в каталоге → дефолтная деталь категории
  (первая в каталоге); цвет вне палитры → дефолтный цвет; каталог пуст →
  примитив-корабль (как текущий фолбэк `bodyGrad` в `map_render.js`) (И4).

### 5.2. Полёт и карта

- `map_render.js`: глобальный `shipImg` заменяется на `getShipSprite(schemaKey)`
  из кэша; полёт игрока использует схему из `/me` (или дефолт от id);
  поворот по курсу, пламя, размер `shipSize*3.2` — без изменений.
- `npc_agents.js`: ромб заменяется мини-спрайтом схемы агента
  (`assemblyFromSeed(id)`), повёрнутым по вектору движения; порог видимости
  `nameDisplayThreshold` — без изменений; клик-панель — без изменений.
- `07_ui.md` §7.1.3 «корабли в пути» (будущий слой трафика) использует тот же
  механизм схем — в спеке только зафиксировать совместимость.

## 6. Теневая генерация в админке (вкладка «Корабли»)

- Таблица деталей по категориям (фильтр/группировка), миниатюра каждой
  (композиция фрагмента одного цвета — серый превью).
- Кнопки: «Сгенерировать 1» (seed рандом), «Сгенерировать 10» (пачка на
  категорию), «Перегенерировать категорию» (удалить + 10 новых / `ON CONFLICT
  DO UPDATE`), «Удалить».
- Предпросмотр — **гейт целостности сборки (И9, эталон «не франкенштейн»)**.
  Обязан показать:
  1. выбранную деталь **отдельно, крупно** (проверка формы и акцентов);
  2. **сетку ≥ 12 случайных собранных кораблей** (случайные схемы из каталога,
     разные детали) в **≥ 6 цветах палитры** — статистическая проверка «любая
     комбинация цельная», а не подобранные вручную примеры;
  3. каждый корабль **в двух масштабах**: детальный (200×200 — проверка стыков и
     акцентов) и **в масштабе карты (~12–38 px, размер полёта `shipSize*3.2`)** —
     именно так корабли видны в игре (красота на малом зуме и есть критерий);
  4. **стрип по категориям**: каждая из 10 форм категории в сборке на общем
     корпусе и цвете — видна отдельная «битая» деталь; корпусы стрипа — три:
     нейтральный + **минимального габарита** (60×42) + **максимального**
     (110×60) — стык проверяется на корпусах крайних размеров, а не только на
     среднем;
  5. **сэмплер крайних сочетаний (worst-case)**: max-нос × min-корпус,
     max-крылья × min-корпус, max-двигатели × min-корпус, max-хвост — сборки у
     границ габаритов §3.1; если они цельны, границы затянуты правильно.
  После перегенерации предпросмотр обновляется автоматически.
- Палитра — read-only из конфига.
- Фронт: `web/static/js/admin/ships.js` (новый) + регистрация в `tabs.js`/
  `main.js`, `web/admin.html`.

## 7. Потребители

### 7.1. Агент: детерминированная сборка от seed

`assemblyFromSeed(seed []byte) ShipVisual` — чистая функция (И3, И7):

- хеш seed (стабильный, напр. SHA-256; первые байты — индексы) → цвет из
  палитры + индекс детали по каждой категории (всегда 5 деталей, И2);
- используется для NPC-агентов (id) и для дефолта игрока (id + legacy icon, §8);
- не сохраняется нигде; перегенерация каталога меняет схемы агентов (принятое
  следствие, `21_ships.md` §21.3).

### 7.2. Игрок: конструктор в дашборде

Блок «Корабль» на `/` (заменяет текущую сетку из `ships.json`):

- превью текущей схемы (композиция, §5);
- палитра — 12 свотчей (один цвет на корабль — по построению);
- на каждую категорию — селектор детали (сетка миниатюр или ←/→ по 10 формам);
- кнопки: «Случайный корабль» (случайная схема), «Сохранить»
  (`PUT /me/ship-visual`), «Сброс» (к дефолтной сборке);
- `users.ship_visual` отдаётся в `/me` (и в `GET /admin/users` — превью в
  разделе «Пользователи»).

## 9. Инварианты и числа (для баланс-проверки)

Источник фактов — `21_ships.md` §21.5 (инварианты И1–И9) и §21.6 (числа).
Короткая сводка для проверки `@balancetester`:

**Числа:**
- Категорий: **5** (предложение, FAQ В1) — корпус, нос, крылья, двигатели, хвост.
- Форм на категорию: **10** (эталон создателя); различимость форм — по силуэту
  (очертанию основной массы), не по акцентам (§3.3).
- Цветов: **12** (предложение, FAQ В2).
- Акцентных цветов: **5** (фиксированные, вне палитры корабля; уточнение эталона
  2026-09-15): стекло `#e0f2fe`, свечение `#60a5fa`, огонь красный `#ef4444`,
  огонь зелёный `#22c55e`, тёмное сопло `#1f2937` (двигатели); обводка `#0b1220`
  (как сейчас).
- Акцентных элементов на деталь: **0–3**; площадь одного акцента **≤ 6% площади
  заливки детали** (не более **90 px²**); суммарно на деталь **≤ 10% площади
  заливки детали** (не более **240 px²**) — лимит считается от самой детали, а не
  от холста (минимальный корпус 60×42, заливка ≥ 1386 px² → акценты ≤ ~139 px² ≈
  5.5% bbox, «однотонный с акцентами»; при 4% холста было бы 1600 px² ≈ 63% —
  «пёстрое нечто»). Акцент внутри силуэта детали, отступ от контура **≥ 3 px**,
  радиус скругления **6 px** (стиль §3.2).
- Распределение акцентов: нос — кабина (обязательно); корпус — иллюминаторы
  0–3; крылья — парные огни (красный слева/зелёный справа); двигатели — тёмное
  сопло + свечение (обязательно); хвост — без акцентов.
- Акценты — часть детали: пространство схем не меняется.

**Целостность сборки (новые числа, эталон «не франкенштейн» 2026-09-15, §3.1):**
- Гарантированная область корпуса (пересечение всех допустимых корпусов):
  **x ∈ [65,130], y ∈ [79,121]** — база любого придатка, попадающая в неё, лежит
  на корпусе при любой форме корпуса.
- Зоны и габариты: **корпус** x 45–155, y 70–130 (центр y=100); ширина **60–110**,
  высота **42–60**, min x ≤ 65, max x ≥ 130. **Нос** x 125–200: база **24–40**
  (центр y=100), длина **55–70**, max x ∈ **[185, 197]**. **Крылья** x 55–145,
  y 0–80/120–200: хорда у борта **6–38**, вылет **15–50**, размах **20–65**,
  max x ≤ 150, база достигает y ≥ 79 / y ≤ 121. **Двигатели** x 0–70: база
  **22–40** (центр y=100), длина **30–60**, max x ≥ 65, левый край ≥ 3 px.
  **Хвост** x 25–110, y 0–85: ширина базы **18–40**, высота **15–55**, размах
  **20–60**, max x ≥ 65, база достигает y ≥ 79.
- Ключевое правило пропорций: **база любого придатка ≤ 40 px < минимальная
  высота корпуса 42 px** (база любой категории помещается в гарантированную
  область корпуса по y); вылеты **15–55 px** против ширины корпуса **60–110 px**.
- Единство стиля (§3.2): обводка **3 px** `#0b1220`; скругления **6/3 px**
  (минимум 2 px); контур **4–8 сегментов**, ≤ 1 дуги; заполненность bbox
  **≥ 55%**; ровно **1 прямая база** у придатка; наклонные кромки из семейства
  **20°/25°/30°**.
- Глобальный инвариант собранного корабля: отношение bbox **ширина/высота
  ∈ [0.8, 3.5]** (корабль длиннее, чем выше; «башня» — признак франкенштейна).
  Крайние сочетания: мин. высота ~72 px (корпус 42 + вылет крыльев 15 сверху и
  снизу) при макс. ширине ~192 (нос ≤ 197 − левый край двигателя ≥ 5) →
  ~2.7 < 3.5; макс. высота ~147 (хвост 55 + корпус 42–60 + вылет нижнего крыла
  50) при мин. ширине ~145 (нос ≥ 185 − левый край двигателя ≤ 40) →
  ~1.0 > 0.8.
- Комбинаций: **10⁵ × 12 = 1 200 000**.
- 100k агентов: ожидаемые пары-дубли ≈ **4 200** из ~5·10⁹ пар — незначимо.
- Холст 200×200; рендер полёта `shipSize*3.2` (как сейчас); порог видимости
  иконок агентов `nameDisplayThreshold`.

**Инварианты:** И1 один основной цвет на корабль + фиксированные акцентные
элементы внутри деталей (уточнение эталона 2026-09-15: «кабина может иметь
внутренние детали другого цвета, для красоты»; `21_ships.md` §21.7); И2 ровно
одна деталь категории на корабль; И3 детерминизм сборки (включая акценты — они
в параметрах детали); И4 каталог — единственный источник (фолбэк, не ошибка;
акценты — часть svg-фрагмента каталога); И5 косметичность (без геймплея); И6
деталь и её акценты в своей зоне холста, стык с корпусом гарантирован
(база придатка попадает в гарантированную область корпуса x [65,130] ×
y [79,121], требования достижения §3.1); И7 стоимость не от размера галактики;
И8 совместимость legacy-блока; **И9 целостность сборки (эталон «не франкенштейн»
2026-09-15): любая допустимая комбинация деталей даёт цельный правдоподобный
силуэт** — держится гарантированной областью корпуса и габаритами зон (§3.1),
единством стиля (§3.2), глобальным соотношением bbox (ширина/высота ∈ [0.8, 3.5])
и гейтом предпросмотра в админке (§6); акценты — часть детали, критерий И9
применяется и к ним (уместность, отступ ≥ 3 px, лимит площади от заливки детали
§4/§9).

**Чего не делать (режимы отказа):**

- Не проектировать тех-характеристики деталей (эталон: далёкое будущее).
- Не менять схему корабля во время полёта (полёт неотменяем и детерминирован,
  `06_factions.md` §6.7.7; перекраска/пересборка — только на земле/в дашборде).
- Не красить детали по отдельности (нарушение И1) и не давать в UI выбор цвета
  на деталь. Акценты — это НЕ покраска частей по отдельности: грань в том, что
  акцент добавляется только генератором (в параметрах детали), цвет акцента —
  фиксированный из `accents` (вне палитры корабля), игрок акцентами не
  управляет, суммарная площадь акцентов детали ≤ 10% её заливки (не более
  240 px²). Сверх этого — акцент
  становится «второй краской на корпус» и нарушает И1.
- **Не допускать несоразмерных пар (нарушение И9):** деталь с базой/вылетом вне
  габаритов §3.1 (гигантский нос на тонком корпусе, оторванно торчащее крыло,
  двигатель длиннее половины корпуса) — генератор таких форм не эмитит
  (границы — часть шаблонов, тест §11 Этап 2).
- **Не нарушать единство стиля (И9):** разная толщина обводки, нулевые углы,
  «скелетные» формы (заполненность < 55%), разнонаклоненные кромки, акцент,
  торчащий из силуэта детали или налезающий на контур (отступ < 3 px).
- Не делать детали товаром/рынком (косметика; нет решения игрока — инвариант 10).
- Не вводить запрос каталога на каждый рендер (И7): каталог — один запрос с
  кэшем, спрайты — кэш по схеме.
- Не падать при битой детали/пустом каталоге — только фолбэк (И4).
- Не добавлять «дым»/«пушку» как категории (`21_ships.md` §21.2: дым —
  анимация, пушка — намёк на боевку).
