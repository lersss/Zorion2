## 1. Проблема

Компоненты изменения населения (`change_components.go`) заданы аналитическими
формулами с зашитыми константами. Калибровка идёт через контрольные точки
создателя (99.2.12, 99.2.13), но визуально кривые не видны — создатель
работает с таблицами чисел и формулами. Нужен инструмент, который:

1. **Показывает** кривую R(X) для каждой компоненты на графике.
2. **Даёт редактировать кривую мышкой** — двигать «ключевые изгибы» (точки)
   и форму переходов между ними. Это ОСНОВНОЙ способ балансировки.
3. **Сохраняет** изменения — они применяются к рантайму (влияют на расчёт
   населения) без рестарта.
4. **Отображает** эталоны создателя как фиксированные крестики-цели.

> **Архитектурная модель (решение создателя 2026-09-15):** кривая каждой
> компоненты = **набор сегментов**. Каждый сегмент (между парой точек) имеет
> СВОЙ параметр «изгиб» (bend): 0 = прямая; < 0 = вогнутая (логарифм);
> > 0 = выпуклая (экспонента). Точки — «ключевые изгибы» текущего поведения.
> Инструмент изменяет их: добавляет/удаляет/двигает мышкой.
>
> **Архитектура мини-R сохраняется как в коде:** `ChangeComponents` вызывает
> по очереди `HeatTemperatureChangeRate`, `ColdChangeRate`, `GravityChangeRate`,
> `RadiationChangeRate` — каждая получает ОДИН параметр (T/g/rad), возвращает
> r. Меняются ВНУТРЕННОСТИ каждой мини-R: вместо аналитической формулы —
> сегментная кривая из конфигурации. Ядро сборки (`ChangeComponents`) и
> сигнатуры мини-R НЕ трогаем. Будущие компоненты (кислотная атмосфера) —
> той же схемой.

## 2. Модель кривой: сегменты с изгибом (bend)

### Формат кривой

Кривая компоненты — **упорядоченный массив узлов** + **массив изгибов сегментов**:

```
nodes = [{x₀, y₀}, {x₁, y₁}, ..., {xₙ, yₙ}]   — узлы, n+1 штук
bends = [k₀, k₁, ..., kₙ₋₁]                    — изгибы, n штук
```

- `x` — значение оси X компоненты (°C / K / g / rad), строго возрастает;
- `y` — значение R в точке x, ∈ [0, 0.999);
- `k` — изгиб i-го сегмента (между узлами i и i+1).

### Математика сегмента (классика, принята)

Для точки x ∈ [xᵢ, xᵢ₊₁]:

```
t = (x − xᵢ) / (xᵢ₊₁ − xᵢ)          — нормализованное положение, ∈ [0, 1]
tₖ = (e^{k·t} − 1) / (e^k − 1)       — подмена параметра (bias-функция)
y(x) = yᵢ + (yᵢ₊₁ − yᵢ) · tₖ
```

**Свойства формулы:**

| k | tₖ | Форма | Пример |
|---|----|-------|--------|
| 0 | t | прямая (линейная интерполяция) | комфортные границы |
| > 0 | tₖ > t | выпуклая (экспонента) | растёт «с ускорением» |
| < 0 | tₖ < t | вогнутая (логарифм) | растёт «с замедлением» |

- k → 0: tₖ → t (непрерывность при малых k) ✓;
- на узлах (t = 0 и t = 1): tₖ = 0 и tₖ = 1 всегда → кривая **непрерывна**
  (по значению; наклон на узле может изламываться — допускается);
- y(x) монотонна внутри сегмента и **не выходит за пределы [yᵢ, yᵢ₊₁]**:
  tₖ монотонен по t → значение сегмента всегда между значениями узлов.
  Это ключевое свойство для гварда R < 1 (§2 «Гвард»).

### Ограничение изгиба: |k| ≤ 10

**Обоснование.** Значение tₖ на середине сегмента (максимальное отклонение
от прямой):

```
tₖ(0.5) = (e^{k/2} − 1) / (e^k − 1) = 1/(1 + e^{k/2})
k = 10  → tₖ(0.5) ≈ 0.0067   (кривая «прилипает» к началу, резкий подъём в конце)
k = −10 → tₖ(0.5) ≈ 0.9933   (кривая наоборот)
```

При |k| > 10 форма практически вырождается в ступеньку («порог-переключатель»,
который запрещён эталоном 18a); при k → ∞ появляются численные артефакты
(e^k переполнение). Диапазон |k| ≤ 10 покрывает полный спектр осмысленных
форм: от почти-ступеньки (k = ±10) до прямой (k = 0).

### Экстраполяция за края узлов — горизонтальная

**Решение: за краями кривая = константа (значение крайнего узла):**

```
x < x₀        → y = y₀    (первый узел)
x > xₙ        → y = yₙ    (последний узел)
```

**Обоснование.** Три альтернативы и их цена:

- **Линейная экстраполяция по наклону последнего сегмента** — опасна:
  жара в 2000→4000 °C растёт круто (0.47 → 0.98); продолжение наклона за
  4000 °C дало бы R > 1 — гвард Population сработал бы на «мгновенную
  гибель» вне допустимого диапазона. Режем по корню.
- **Обрезка до диапазона** (x < x₀ → y = 0) — для жары x₀ = 30 °C даёт
  «ниже 30 нет жары» — верно, но для радиации x₀ = 0 и радиации «нет»
  (R = 0) — тоже верно. Однако для гравитации x₀ = 0 (невесомость, R = 1.04e-7)
  обрезка «в ноль» была бы ложью.
- **Горизонтальная (константа крайнего узла)** — безопасна всегда: y не может
  покинуть [y₀, yₙ] ⊆ [0, 0.999) (монотонность + гвард). Для жары за 4000 °C
  кривая «стабилизируется» на R = 0.98 — консервативно, без перехода через 1.
  Принимается.

### Гвард R ≤ 1

Тройная защита (никаких новых веток в коде):

1. **Валидация узлов:** y ∈ [0, 0.999) на входе (PUT, §6) — ошибка 422,
   значение не сохраняется.
2. **Монотонность сегмента:** значение y(x) внутри сегмента всегда между
   yᵢ и yᵢ₊₁ (свойство tₖ) → max по всей кривой = max по узлам ≤ 0.999.
3. **Экстраполяция горизонтальная:** за краями y = крайний узел ≤ 0.999.
4. Существующий гвард в `Population` (r ≥ 1 → мгновенная гибель, без NaN)
   остаётся как финальная страховка (не меняется).

## 4. Эталоны — фиксированные крестики-цели

### Что это

Эталоны создателя (18a §Эталоны FAQ, 99.2.12, 99.2.13) — **фиксированные
крестики-цели** на графике. Их нельзя редактировать инструментом. Они
показывают, ГДЕ кривая должна быть, по мнению эталона, и позволяют видеть
отклонение текущей кривой.

> **Жара не держит эталоны — калибровку 99.2.12 не трогаем** (решение
> создателя 2026-09-15): контрольные точки формулы (те, что в §3) и
> эталонные маркеры (цели из 18a: «+500 °C → 95% за секунды» → R = 0.4507)
> могут не совпадать. Это ОК: инструмент показывает РАЗНИЦУ (кривая vs
> крестик-цель), и создатель решает, двигать ли кривую к цели. Инструмент
> НЕ фитит кривую к маркерам автоматически — фита больше нет.

### Метод трансляции эталона в R (значения маркеров)

Как и прежде: `t_вымир = ln(p₀)/|ln(1−R)|` при p₀ = 10⁹ и логика «X% за t».

## 5. Хранение и применение

### In-memory store — паттерн settings.go

```go
// internal/economy/settlement/balancer_store.go (новый файл)
package settlement

type SegmentNode struct {
    X float64 // °C / K / g / rad, строго возрастает
    Y float64 // R ∈ [0, 0.999)
}

type ComponentCurve struct {
    Nodes []SegmentNode
    Bends []float64 // len = len(Nodes) − 1, |k| ≤ 10
}

type balancerStore struct {
    mu     sync.RWMutex
    curves map[string]*ComponentCurve // "heat" | "cold" | "gravity" | "radiation"
}

var balancerStore = &balancerStore{
    curves: map[string]*ComponentCurve{
        "heat":      defaultHeatCurve(),     // §3
        "cold":      defaultColdCurve(),
        "gravity":   defaultGravityCurve(),
        "radiation": defaultRadiationCurve(),
    },
}
```

- **Чтение** (мини-R на каждом вызове): `RLock`, возврат копии слайсов.
- **Запись** (админка, редко): `Lock`, атомарная замена всей кривой +
  валидация §6.
- **Горячая подмена:** мини-R читают store на КАЖДОМ вызове → сохранение из
  админки применяется к следующему расчёту без рестарта.
- **Рестарт → активные пресеты из файла** (итерация 7, §5 «Слой пресетов»):
  при старте активные кривые восстанавливаются из последних применённых
  пресетов (`config/balancer_presets.json` — дефолт; env `BALANCER_PRESETS_FILE`
  переопределяет, §8); файла нет → дефолты §3. In-memory,
  не таблица БД (решение создателя 2026-09-15). Тот же паттерн, что у
  `LifeExpectancySeconds()` (99.2.16 §3.7) и `internal/npc/settings.go`.

### Математика: evaluateCurve (сервер)

```go
// internal/economy/settlement/balancer_curve.go (новый файл)
func evaluateCurve(nodes []SegmentNode, bends []float64, x float64) float64 {
    if x <= nodes[0].X { return nodes[0].Y }             // экстраполяция влево (горизонтальная)
    if x >= nodes[len(nodes)-1].X { return nodes[len(nodes)-1].Y } // вправо
    for i := 0; i < len(bends); i++ {
        if x <= nodes[i+1].X {
            t := (x - nodes[i].X) / (nodes[i+1].X - nodes[i].X)
            return nodes[i].Y + (nodes[i+1].Y-nodes[i].Y) * bendTransform(t, bends[i])
        }
    }
    return nodes[len(nodes)-1].Y // safety, недостижимо
}

func bendTransform(t, k float64) float64 {
    if math.Abs(k) < 1e-10 { return t } // k ≈ 0 → прямая (устойчивость)
    return (math.Exp(k*t) - 1) / (math.Exp(k) - 1)
}
```

Конвертация единиц — на уровне вызова: жара — кривая в °C, мини-R принимает K
→ `evaluateCurve(curve, tempK − 273.15)`; холод — K напрямую.

### Применение к мини-R: механизм (а) — всегда из store

**Решение: (а) всегда из store.** Каждая мини-R вычисляет R только через
`evaluateCurve(GetCurve("heat"), ...)` и т.д. Аналитические формулы и их
константы удаляются из `change_components.go`. Дефолты store = сегментные
кривые, совпадающие с текущими формулами в контрольных точках (§3), поэтому
баланс смертности на старте сохраняется в пределах допуска теста (§9).

**Почему (а), а не (б) «флаг переопределено»:**

| Критерий | (а) всегда из store | (б) флаг «переопределено» |
|----------|---------------------|---------------------------|
| Источник правды | один — store | два: формула (пока не тронута) + store (после правки) |
| Правда на графике | всегда store = всегда реальный расчёт | формула рисуется ОДНОЙ формой, но при первой же правке скачком становится сегментной — «эффект скачка» на UI |
| Новые компоненты | добавляются одной кривой в store | нужно решать: формула-дефолт ИЛИ кривая-дефолт для каждого нового фактора |
| Код | формулы удаляются (меньше кода, одна математика) | формулы остаются навсегда (мёртвый код, две математики) |
| Риск «молча изменить баланс» | управляется тестом допуска старта (§9, 5%) | нулевой до первой правки — но плата — дублирование |

Цена (а) — стартовая аппроксимация должна держать контрольные точки с
допуском (это РАБОТА теста §9, а не молчаливое допущение). Принимается (а).

### Слой пресетов (итерация 7, решение создателя 2026-09-15)

**Пресет = полный набор точек (узлы + изгибы) КОНКРЕТНОЙ R-компоненты.**
У каждой компоненты свой список пресетов; пресет жары не содержит кривых
других компонент. Store (in-memory) остаётся как есть — пресеты — это слой
**поверх** store: они дают имя и файловую персистентность кривым.

**Природа сущности (развилка):** пресет — **запись-состояние** (лог
конфигурации кривой под именем), не событие. **Владелец — глобальный сервер**
(один набор пресетов на все учётки админов; per-user пресеты — отдельная
большая фича с владельцем, не здесь). **Расширяемость:** схема
`{name, component, nodes, bends}` переживает и второй «тип» (например профиль
ВСЕХ компонент — §13-кандидат будет отдельной записью, не ломает пресеты),
и 5-ю компоненту (кислотная атмосфера — просто новые записи + ключ в
`active`, миграция не нужна).

**Формат записи пресета:**

```json
{
  "name": "жесткая-жара",
  "component": "heat",
  "nodes": [{"x": 30, "y": 0}, {"x": 70, "y": 5.94e-9}, "..."],
  "bends": [2.1, 10.0, 2.05, "..."],
  "updated_at": "2026-09-15T12:30:00Z"
}
```

- `name` — 1..32 символа, `[\p{L}\p{N}_\- ]` (буквы любых алфавитов, включая
  кириллицу; пробел и дефис допустимы). Уникальность — в рамках
  `(component, name)`.
- `nodes`/`bends` — тот же формат и та же валидация, что в PUT §6.
- `updated_at` — RFC3339, ставит сервер при сохранении (не из тела запроса).

**Формат файла** `config/balancer_presets.json` (дефолт; путь — §8):

```json
{
  "presets": [
    {"name": "default", "component": "heat", "nodes": [...], "bends": [...], "updated_at": "..."},
    {"name": "default", "component": "cold", "nodes": [...], "bends": [...], "updated_at": "..."},
    {"name": "default", "component": "gravity", "nodes": [...], "bends": [...], "updated_at": "..."},
    {"name": "default", "component": "radiation", "nodes": [...], "bends": [...], "updated_at": "..."}
  ],
  "active": {"heat": "default", "cold": "default", "gravity": "default", "radiation": "default"}
}
```

- `presets` — плоский список (а не map по компонентам): проще CRUD, совместим
  с расширением числа компонент.
- `active` — имя пресета, применённого последним для каждой компоненты
  («активные кривые = последние применённые пресеты», решение создателя).
  Прямое редактирование кривой (PUT/кнопка «Сохранить») НЕ меняет `active` —
  см. §15 вопрос 2.

**Жизненный цикл:**

| Операция | Store (in-memory) | Файл |
|----------|-------------------|------|
| «Сохранить как пресет» (POST presets) | **применяет кривую сразу** (SetCurve — «сохранил = сразу применил», решение создателя 2026-09-15) | записывает/перезаписывает пресет, `active[component] = name` |
| «Применить пресет» (POST presets/apply) | SetCurve из пресета | `active[component] = name` |
| «Вернуть заводской» (POST presets/reset-default) | ResetCurve (кодовые дефолты) | перезаписывает пресет `default`, `active[component] = default` |
| DELETE presets | — (текущая кривая не меняется) | удаляет запись; `default` удалить нельзя (422) |

**Старт сервера:**

1. Нет файла → создать из заводских дефолтов (§3 = `default*Curve()` кода),
   `active = default` для всех компонент, записать атомарно.
2. Файл есть → прочитать; каждый пресет проходит валидацию §6 (как PUT).
   Невалидные пресеты пропускаются с лог-предупреждением (не роняют старт).
3. Для каждой компоненты: пресет из `active` → SetCurve. Если имени в
   `active` нет / пресет невалиден → SetCurve(default), `active[component]`
   перезаписывается на `default`.
4. Битый JSON (коррапт) → лог-предупреждение, все кривые = дефолты; файл
   пересоздаётся при первой записи пресета. Сервер НЕ падает.

**Атомарность записи (обязательна):** запись всегда во временный файл
`<имя>.tmp` в той же директории + `os.Rename` (атомарный на одной ФС) —
при падении сервера посреди записи старый файл остаётся целым. Родительская
директория (`config/`) создаётся `os.MkdirAll` при старте (страховка на
случай отсутствия). Одна пишущая сторона — блокировка
`balancerStore.mu` (store и файл меняются согласованно: Lock → мутация
store → запись файла → Unlock).

**Отсутствие файла / ошибка записи — режим отказа:** пресеты работают в
рамках сессии (in-memory CRUD на сохранённой копии), кривые и весь
балансировщик НЕ ломаются — лог-предупреждение при старте и при каждой
неудачной записи. Лечится правами на каталог / заданием env.

**Прецеденты:** файловый пресет — `internal/generator/settlement/preset.go`
(JSON + RWMutex; его путь `LoadPreset("config/settlement_preset.json")` —
от cwd, ломается на проде (B14) — НЕ повторяем: у пресетов балансировщика
путь стабильный — дефолт `config/balancer_presets.json`, не зависит от cwd;
env `BALANCER_PRESETS_FILE` переопределяет при необходимости); UI пресетов —
`web/static/js/admin/settlementPresets.js` (select + confirm при перезаписи).

- Сервер: `SetCurve` (горячая подмена — кривая влияет на расчёты населения
  сразу, без рестарта; то же поведение, что у PUT) → запись/перезапись
  пресета в файле → `active[component] = name` → атомарная запись файла.
  **«Сохранил = сразу применил»** (решение создателя 2026-09-15): POST presets
  сохраняет пресет в файл И делает его активной кривой в store.
- **Перезапись занятого имени — разрешена** (идемпотентно, `updated_at`
  обновляется); подтверждение — на UI (§7), не 422.
- Валидация → 422: component не из 4; name пустой / > 32 символов /
  недопустимые символы (не `[\p{L}\p{N}_\- ]`). Имя `default` допустимо
  (перезапись заводского — кодовые дефолты всегда восстановимы
  через reset-default).
- Ответ — сохранённый пресет `{component, name, updated_at}`.

### POST /admin/balancer/presets/apply

«Применить пресет». Тело: `{"component": "heat", "name": "жесткая-жара"}`.

- Пресет из файла → `SetCurve` (hot-swap, влияет на следующий расчёт) →
  `active[component] = name` → атомарная запись файла.
- Пресет не найден → **404** (имя изменено/удалено вручную в файле).
- Данные пресета невалидны (файл правили руками) → **422** с текстом, store
  не меняется.
- Ответ — применённая кривая (как GET curve).

### DELETE /admin/balancer/presets

Тело: `{"component": "heat", "name": "жесткая-жара"}`.

- Удаляет запись из файла, атомарная запись. Текущая кривая в store НЕ
  меняется (удаление пресета не сбрасывает активную кривую).
- Пресет не найден → 404.
- **`name = "default"` → 422**: «default — заводской пресет; используйте
  "Вернуть заводской" (reset-default)». Если `default` активен и активная
  кривая = дефолт — ничего не теряется; если активный пресет удалён —
  активная кривая остаётся в store до рестарта, после рестарта — fallback
  на default (§5).

### POST /admin/balancer/presets/reset-default

«Вернуть заводской». Тело: `{"component": "heat"}`.

- `ResetCurve(component)` (кодовые дефолты `default*Curve()`, §3) + перезапись
  пресета `default` в файле + `active[component] = default` + атомарная
  запись. Ответ — дефолтная кривая (как GET curve).

Авторизация всех эндпоинтов — `auth.AdminAuth` (как остальные админские).

## 7. UI — вкладка «Балансировка» в админке

### Структура

Новая вкладка `tab-balancer` в `web/admin.html`:

```html
<button class="tab-btn" data-tab="tab-balancer">⚖️ Балансировка</button>
```

Карточка:

1. **Выбор компоненты** — `<select>`: жара / холод / гравитация / радиация.
   Смена → загрузка кривой (GET curve) + оцифровка (POST sample) + эталонов
   (GET etalons) + списка пресетов компоненты (GET presets).

2. **График** — `<canvas>` (Canvas 2D). Элементы:

   - **Кривая** — ломаная по серверным точкам sample (плавный рендер
     соединяет точки).
   - **Эталонные крестики** (×, фикс. цвет, §4).
   - **Узлы-ручки** — draggable markers на позициях узлов.
   - **Bend-ручки** — ОТДЕЛЬНЫЙ элемент на середине каждого сегмента.

3. **Масштаб по Y — пользовательский** (решение создателя 2026-09-15). R одной
   кривой тянется на 8–9 порядков (жара: 5.9·10⁻⁹ при 70 °C … 0.98 при 4000 °C):
   фиксированная шкала на весь размах делает рабочие области 0.1–0.5% полосой
   в полпроцента высоты — узлы мышкой не ловить. Управление обзором:

   **3.1 Зум колесом мыши по Y + панорамирование.**

   - Колесо над графиком меняет видимый диапазон декад оси Y: вверх —
     приближение (видимый интервал декад сужается), вниз — отдаление.
     Масштабирование привязано к позиции курсора по Y (точка под курсором
     остаётся на месте).
   - **Панорамирование:** зажим ЛКМ на ПУСТОМ месте графика (не на узле, не
     на bend-ромбике) и перетаскивание — сдвиг видимой области по Y и X
     одновременно. Фиксированный масштаб исчез: после панорамирования X
     клиент запрашивает повторный sample для нового видимого диапазона X
     (POST sample, §6) — кривая пересчитывается серверно.
   - Узлы и bend-ромбики рисуются в экранных координатах (позиция
     пересчитывается из данных через текущий масштаб) — зум и пан их
     не ломают: они всегда остаются на своих (x, y) данных.
   - **Ограничения видимого диапазона:** Y-видимое ∈ [1e-14, 2]. Нижняя
     граница 1e-14: ниже нет данных (все R-компоненты ≥ 0, ноль отображается
     отдельно, §3.3). Верхняя 2: запас над эталонными крестиками с R ≈ 0.98
     (крестик «+4000 °C» = 0.6019, кривая жары до 0.98) — чтобы крестики и
     узлы у верха не упирались в кромку; 2 > любой валидный y < 1 и оставляет
     полдекады воздуха. За эти пределы зум/пан не уводит (кламп).

   **3.2 Кнопка «По узлам»** — авто-подгон видимой области Y под узлы текущей
   кривой: видимый диапазон = [min(y узлов)·10⁻⁰·⁵, max(y узлов)·10⁺⁰·⁵],
   границы округляются до целых декад (вниз для минимума, вверх для
   максимума), затем кламп к [1e-14, 2]. Быстрый возврат к рабочему набору
   узлов после экспериментов с зумом. Чисто клиентская арифметика, никакой
   серверной магии (см. §12).

   **3.3 Переключатель «лог / линейная» Y.**

   - **Лог — по умолчанию:** видна форма кривой на всём размахе порядков
     (R от 10⁻⁹ до 1). Ровный ноль (y = 0) — нижняя кромка графика
     (пунктирная линия «0»), тултип «R = 0 здесь не отображается (лог-шкала)».
   - **Линейная** — для точной работы в узкой области у малых R (например
     0.1–0.5% = R 0.001–0.005): в лог-шкале эта полоса сжата, в линейной —
     растянута. В линейном режиме ноль — нижняя кромка, шкала честно линейная.
   - **Поведение данных при переключении:** координаты узлов и bend НЕ
     меняются — меняется только отображение (преобразование y → экран).
     Узлы и bend-ромбики пересчитывают экранные позиции по новой шкале.
     Drag-узла и drag-ромбика работают одинаково в обоих режимах: смещение
     мыши → дельта в координатах данных по текущей шкале (в лог-режиме —
     относительный шаг, в линейном — абсолютный). Математика bend (§5/§7 п.5)
     от шкалы не зависит — она оперирует y данных.

   **3.4 Индикаторы ▲/▼ за краем видимой области.**

   - Узлы и эталонные крестики, чей y вне видимого [yMin, yMax], НЕ исчезают
     молча: на своей X-позиции у верхней (▼ наверху) или нижней (▲ снизу)
     кромки рисуется **стрелочка-индикатор** в цвет узла/крестика.
   - Клик по стрелочке — **прыжок к объекту**: видимый диапазон Y смещается
     так, что целевой y попадает в центр видимой области (ширина диапазона в
     декадах сохраняется). Повторный клик по той же стрелочке — ничего
     (цель уже в центре).
   - Если за краем несколько объектов — стрелочки стоят рядом на своих
     X-позициях (не сливаются), тултип «узел 70 °C, R=5.9·10⁻⁹ — за нижним
     краем».

4. **Управление узлами:**

   - **Drag узла** — перемещение по X и Y (горизонтально — по оси X,
     вертикально — по R). При перетаскивании — live-предпросмотр: клиент
     перерисовывает кривую локально (клиентский `evaluateCurve` для
     предпросмотра ДУБЛИРУЕТ серверную математику — это допустимое
     исключение удобства; при сохранении (PUT) сервер пересчитывает
     по-настоящему). Прежняя кривая — пунктиром, новая — сплошной.
   - **Shift+клик по кривой** — добавить узел (x = клик, y = текущее
     значение кривой в этой x). Лимит 16 — при достижении подсказка.
   - **ПКМ по узлу** — удалить (минимум 3 — при попытке удалить третий
     подсказка).
   - **Тултип узла:** «X = …, R = …, t₅₀ = …» (t₅₀ = ln 2 / |ln(1−R)|).

5. **Задание bend мышкой — ВЕРТИКАЛЬНЫЙ ДРАГ СЕРЕДИНЫ СЕГМЕНТА** (самый
   наглядный способ, решение):

   - На середине каждого сегмента рисуется **ромб-ручка (◆)** на текущей
     кривой.
   - Вертикальный drag ромба: вверх → bend > 0 (выпуклая), вниз → bend < 0
     (вогнутая). Ромб живёт на кривой: смещаешь вверх — кривая «выпуклеет»,
     вниз — «вогнутеет».
   - **Обратная формула** (перевод смещения ромба в k):

     ```
     m = (y_пользователь − yᵢ) / (yᵢ₊₁ − yᵢ)  — целевая позиция как доля высоты сегмента
     k = 2·ln(1/m − 1)                         — из k: tₖ(0.5) = 1/(1+e^{k/2})
     ```

     m ∈ (0.01, 0.99) → k ∈ [−9.2, +9.2] — внутри |k| ≤ 10; за пределами
     k кламп к ±10 (визуально кривая уже почти не меняется — честно
     показываем предел).
   - Почему середина сегмента: симметричная точка, однозначная инверсия k
     (на любой другой доле тоже возможно, но середина — самая наглядная и
     обратимая формула), форма кривой при этом меняется предсказуемо.
   - **Hit-test:** ромб — радиус 8 px, узлы — радиус 10 px. Курсоры grab/
     grabbing.

6. **Информационная панель:** для каждого эталона — `R_кривая(X)/R_маркер`,
   время вымирания t₅₀ и t₁₀₀₀. Guard NaN/Inf: R ≤ 0 → «не вымирает»,
   R ≥ 1 → «мгновенно» (недостижимо валидацией, но страховка).

7. **Кнопки:** «Сохранить» (PUT curve), «Отмена» (GET curve + перерисовка),
   «Сброс на дефолты» (POST reset, с подтверждением), «По узлам»
   (авто-масштаб Y, §3.2), переключатель «лог / линейная» Y (§3.3).

8. **Пресеты** (итерация 7; решение создателя 2026-09-15) — панель под
   кнопками «Сохранить/Отмена/Сброс»: 

   ```
   Пресеты: [ ▾ жесткая-жара ] [Применить] [Удалить]
                           [Сохранить как…] [Вернуть заводской]
   ```

   - **Список привязан к выбранной компоненте** (п.1): при смене компоненты
     выполняется GET presets?component= и дропдаун перезаполняется
     пресетами этой компоненты. «default» всегда в списке (заводской).
- **«Сохранить как…»** — prompt с именем (по умолчанию — текущее имя из
      дропдауна). Если имя занято — `confirm` «Пресет „X“ уже есть —
      перезаписать?» (паттерн `settlementPresets.js`). Перед вызовом POST
      presets клиент автоматически отправляет PUT текущих экранных
      узлов/bends — пресет сохраняет ТО, ЧТО НА ЭКРАНЕ (кривая из store,
      §6 POST presets), включая несохранённые правки. **Сохранение сразу
      применяет кривую к расчётам** («сохранил = применил», решение
      создателя): hot-swap в store — влияет на население без рестарта,
      как кнопка «Сохранить» (PUT).
   - **«Применить»** — POST presets/apply; после применения кривая
     перерисовывается (GET curve + sample).
   - **«Удалить»** — confirm; выбран `default` → кнопка неактивна
     (подсказка «заводской — используйте "Вернуть заводской"»).
   - **«Вернуть заводской»** — confirm («кривая и пресет default будут
     заменены кодовыми дефолтами»), POST presets/reset-default.
   - Тултип пункта списка: имя + дата `updated_at` (utc).

9. **Примечание-ссылка:** «СПЖ и коэффициент рождаемости настраиваются в
   Настройках населения (вкладка „Основное“)» → `#tab-settlement`.

```js
view = {
  logY: true,        // лог/линейная (§7 п.3.3)
  yMin, yMax: 1e-14..2,  // видимая область по Y, кламп (§7 п.3.1)
  xMin, xMax: 0..Infinity // видимая область по X (для sample при пане)
}
```

- Колесо → пересчёт yMin/yMax (точка под курсором неподвижна); пан пустого
  места → сдвиг xMin/xMax + yMin/yMax; после пана по X — повторный
  POST sample с новым диапазоном (§6; клиент не дублирует evaluateCurve
  на постоянных данных — только на live-preview при drag, §7 п.4).
- «По узлам» (§7 п.3.2): арифметика декад в клиенте (округление степеней 10,
  кламп [1e-14, 2]);
- ▲/▼ за краем (§7 п.3.4): узлы/крестики вне [yMin, yMax] отрисовываются
  стрелочками на своих X; клик → центрирование диапазона на целевой y.
- Преобразование данных→экран — в `balancerCanvas.js` (лог: экран =
  (log10(y) − log10(yMin))/(log10(yMax) − log10(yMin)); линейный: (y−yMin)/(yMax−yMin)).
  Одно место преобразования — узлы, кривая, крестики и стрелочки рисуются
  через него, артефактов рассинхрона нет.
