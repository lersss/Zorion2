## 1. Цель и скоуп

Спроектировать **общий механизм мягкой подкрутки генератора планет под расу-дома кластера** — реализацию конфигуратора §7.2 спеки 99.2.21. Механизм закрывает две дыры, выявленные честным прогоном (идея 56a, копилка 2026-09-17):

1. **Копилка незаселившихся (20 из 50 рас):** каскад не производит нужные газы (NH₃/H₂S — вообще, CH₄ — следы 0–5%) и даёт heat_flux = 0 для зрелых планет (терморедокс/кремниевые живут только у молодых, F_accretion). Группа А (газы) и Группа Б (тепло) из копилки.
2. **Дыра «в некоторых кластерах по одной обитаемой планете»:** расе-дому нужна достаточная частота подходящих планет в её кластере.

**Механизм (замысел создателя 2026-09-17):** мягкая подкрутка **входов** каскада под расу-дома кластера, по образцу профилей регионов (59a/99.2.10). Физика каскада НЕ ломается: сдвигаются входы (орбита, бюджет летучих, возраст, состав атмосферы, поверхность-альбедо, число планет, веса звёзд), формулы 99.2.20 не трогаются.

**Синергия «звёзды+планеты» (решение создателя 2026-09-17, итерация 4):** не слабый звёздный слой + сильный планетный (как в v1–v3), а **два равноправных умеренных слоя**, которые в сумме закрывают окна расы. Звёздный слой (ручка 5) усилен: веса спектральных классов кластера мягко сдвигаются к `home.star_classes` карточки (home-классы ×1.6, диапазон ×1.3–2.0; все типы звёзд остаются возможны — инвариант). Планетный слой ослаблен: кламп орбиты ужат с [0.5, 14.0] до **[0.35, 3.0]** (планета добирает остаток до окна, а не тащится с орбиты 1 на орбиту 8); обогащение состава, тепло/возраст, давление — как были (уже умеренные). Принцип: звезда «своя» (home-класс) → планета почти не подкручивается; звезда «чужая» → подкрутка добирает остаток. Суммарно (звёзды чаще свои + планеты добирают) — окна рас закрываются.

**Итерация 2 (эта спека):** вердикт @balancetester В1 (2026-09-17) — при числах v1 пригодны ~7–8 из 20 при s=0.5; вердикт @scientist (2026-09-17) — вилки физики (CH₄/NH₃/серные миры). Переработаны: формула f_vol_target (ошибка константы 1000×), семантика клампа f_vol (глобальный, пол 10⁻⁶), правило P_target (решение из T-окна, не «lo×1.5»), состав горячих (разбавление парника N₂-доминантой), калибровка T_target₀ с F_int, возраст тепловых (адаптивный, минимально достаточный), кламп орбиты [0.5, 14], ручка O/B (занижение снято), мягкость (двухслойная: непрерывная частота + вероятностные физические ручки). Заявленный эффект «20 рас копилки получают планеты при s=0.5» следует из формул (§3.3, §4, §14.8).

**Итерация 3 (эта спека):** вердикт @balancetester В1 от 2026-09-17 по итерации 2 — v1-замечания закрыты, найдены 2 новых противоречия + 3 минорных. Закрыты здесь:
1. **T₀_base = t0 без ×1.1505** (не `prelimBandTemp` — тот включает номинальный парник; размерностное противоречие формулы и смоука, §3.5).
2. **Холодный аналог ручки 7:** SurfaceOverride тёмные скалы/кратеры (A = 0.15) для холодных рас — каскад считает t0 по реальному альбедо поверхности, лёд (A 0.60–0.65) ≈ половина весов холодной полосы → T_final ≈ 0.80·center — холодные расы выпадали из окон (§3.3 ручка 7-холод). Горячая ручка 7 унифицирована на A = 0.15 (сходится с базой T₀_base; T₁ = 379.8 > 373 держится).
3. Формулировка F_int_actual поправлена на √M_nom ∈ [0.75, 1.66] (§6).
4. Слой 2: early-exit при s = 0 / s ≥ 1 — ролл не потребляет энтропию («s = 0 → как есть» строго для того же seed, §4.3).
5. Режим-гейт O/B (ручка 5): явный дефолт для окон через 600 K и для холодных тепловых (глубинники) — классификация по opt_hi (§3.3 ручка 5).
Плюс найденный при пересчёте смоука фикс: **обогащение применяется только к need-газам с min > 0** («need: {X: 0}» = «не требуется», suitable.go: comp[X] ≥ 0 проходит всегда; обогащение до 5% газа, который расе не нужен, — ошибка, §3.3 ручка 2).

**Итерация 4 (эта спека):** решение создателя 2026-09-17 — **синергия «звёзды+планеты»**: два равноправных умеренных слоя вместо «слабые звёзды + сильные планеты». Звёздный слой усилен (home-классы ×1.3 → **×1.6**, из `home.star_classes` карточки; все 50 рас заполнены, дефолт не нужен), планетный ослаблен (кламп орбиты [0.5, 14.0] → **[0.35, 3.0]**; обогащение/тепло/давление без изменений). Смоук пересчитан честно: класс звезды берётся из сдвинутого распределения (не 100% home-классов), планетный слой умеренный — все 20 рас копилки по-прежнему получают ненулевую частоту при s = 0.5 (§14.8).

**В скоупе:** доставка расы-дома в генератор (без миграций), набор ручек подкрутки (общий механизм, НЕ заточенный под конкретные газы), вывод ручек из карточки расы (принцип «один источник»), мягкость/жёсткость (0–1) и её место в админке, композиция с профилями регионов, инварианты.

**НЕ в скоупе (границы — §8):** R-модель рас (reproduction/resilience в поселениях), отчёты игроку, артефакты рас, перепроектирование ядра (доделки 45a — отдельно), генератор поселений рас (65a — работает), экзотические планеты, бэкфилл старых планет, миграции БД, код/конфиги (только дизайн).

## 2. Природа механизма — развилки и решения

### 2.1. Как генератор узнаёт расу-дома планеты

**Решение: вычисление на лету, без изменения схемы** (без изменений от v1):

- `regions.race_id` уже существует (миграция 000038), `loadRegionsWithProfiles()` SELECT'ит его в той же строке, что и profile. Доставка — ноль миграций.
- Привязка консистентна с profile: та же `regionprofile.NearestRegionIndex` по координатам мира (99.2.10 §10). Раса-дом = `regions[idx].RaceID` — ровно та, что использует генератор поселений рас (`decideRaceSettlements`). Единый источник привязки.
- Колонка `worlds.race_id` — запасной вариант, если регионы станут редактируемыми (как `worlds.region_id` в 99.2.10 §12.3). Сейчас не нужна.

**Механика доставки (два уровня):**

- **Планетный генератор:** `planet.WorldInfo` получает поле `RaceID string` (пусто = фоновый регион/легаси-вселенная без рас). Хендлер заполняет его там же, где profile: `wi.RaceID = regions[idx].RaceID`. Генератор по `races.ByID(RaceID)` получает карточку и вычисляет подкрутку (функция карточки + s + seed, §3.3).
- **Звёздный генератор (galaxy):** `generateWorldsPoisson` уже знает регион точки (`pointRegion[i]`); добавляется чтение `regions[ri].RaceID` — те же хуки, что у profile (spectral_mult, §3.4). `assignRacesToRegions` выполняется до генерации миров (в buildRegions) — раса доступна.

**Легаси-вселенные** (регионы без race_id): подкрутки нет (нейтрально, как profile nil). **Фоновые регионы** (без расы): нет.

### 2.2. Природа сущности «подкрутка»

Разбор по правилу «сущность с двумя экземплярами — не сущность» (GD_PROMPT):

1. **Природа.** Подкрутка — **производный параметр генерации** (вход каскада), НЕ событие, НЕ лог, НЕ атрибут планеты. Не хранится в БД: вычисляется на лету из карточки расы + мягкости + seed (функция генерации). Проявление в мире — распределение планет (частоты), не запись.
2. **Владелец.** Одна подкрутка → все планеты кластера расы (1:N по кластеру). Расширяемость закладывается сразу: подкрутка — функция карточки, 51-я раса получает подкрутку автоматически (без правок кода и конфига).
3. **Расширяемость.** Механизм общий (не per-газ): ручки выводятся из окон карточки. Схема переживает 51-ю расу по построению.

**Анти-ловушка «сущность вне игры»:** сущность «конфигуратор подкрутки» в игре отсутствует (генераторный механизм, не игровая сущность). На текущие числа (карточки рас, поселения, R-модель) она **не влияет** — она меняет распределение планет при НОВОЙ генерации; пригодность (`Race.Suitable`) и поселения считаются той же функцией по тем же окнам. Двойного учёта нет. Сущности «колыбель расы» и «серные источники» (кандидаты, §9) в числа не входят.

## 3. Ручки подкрутки — разворот подходов и выбранный механизм

### 3.1. Разворот подходов: как задаются ручки

**Решение (без изменений от v1): C. Гибрид: авто-вывод из карточки + override-файл** (`config/race_tuning_overrides.json`, пустой = чистый вывод). Окна живут в карточке, вывод — функция карточки; override — явное исключение (заменяет выведенное значение поля, не умножает). Создатель может выбрать A (без файла) или B (полный конфиг) — развилка §11.1.

### 3.2. Разворот подходов: как применяется сдвиг

**Решение (без изменений от v1): M1. Сдвиг входов каскада.** Сдвигаются OrbitRadiusAU, FVolOverride, AgeGyr, состав (через оверрайд), поверхность-альбедо (SurfaceOverride), число планет, веса звёзд. Формулы 99.2.20 не трогаются; гейты воды/жизни фильтруют по физике. M2 (пост-обработка), M3 (второй генератор), M4 (пере-ролл) — отклонены (v1 §3.2).

### 3.3. Ручки (выведенные из карточки; применяются на «подстроенных» мирах — §4)

Подкрутка — **производный объект `RaceTuning`**, функция карточки (вычисляется при загрузке каталога, кэшируется). Поля и формулы (сильная, s = 1; числа — предположение дизайнера, калибровка @balancetester):

| # | Ручка | Вход каскада | Вывод из карточки | Формула (сильная, s = 1) |
|---|---|---|---|---|
| 1 | **Сдвиг орбиты (температура)** | `OrbitRadiusAU` (S-планеты) | окно `temperature` | `T_target₀ = clamp(center(opt)/(G(P_target)·H_int), floor_regime, ceil_regime)`; `orbit_radius_mult = (T₀_base/T_target₀)²`, кламп **[0.35, 3.0]** (умеренный, синергия «звёзды+планеты» 2026-09-17; v1/v2: [0.5, 14.0]). G(P) = (1 + ¾·τ(P))^0.25, τ(P) = P·κ_eff (κ_eff — эффективный вес парника состава, §3.3 ручка 2). H_int = (1 + F_int_expected/(F★_nat·0.85))^0.25 — поправка на внутреннее тепло (§3.3 ручка 4). **T₀_base = t0 с альбедо 0.15 БЕЗ номинального парника** (`tempFromFlux(fStar, 0.15, 0, 0, 0)`), **НЕ `prelimBandTemp`** (тот включает ×1.1505 — T₁-стиль; явное решение итерации 3, §3.5). H₂S добавляется в словарь состава + молекулярная масса 64 в `meanMolecularWeight` (сейчас отсутствует; классификатор уже проверяет H₂S). **Пометка:** H₂S/SO₂/NH₃ не входят в τ_IR каскада (формула τ = P·(200·w_H₂O + 1.0·w_CO₂ + 1.2·w_CH₄ + 3·w_N₂O) фиксирована, 99.2.20) — обогащение меняет состав и μ, но не парник; эффект на T мал (±2–4 K), поглощается окнами |

**Ключевые свойства механизма (общий, не per-газ):**

- **Обогащение применяется один раз** (в шаге состава, до τ_IR): жизненный проход меняет состав только в умеренном режиме, а обогащение в умеренном запрещено режим-гейтом — конфликта нет.
- **P-планеты** (circumbinary, runCascade): ручки 2–4, 6 применяются (тот же каскад); ручка 1 (сдвиг орбиты) — НЕТ: r_P = 3·companion_sep_au фиксирован разделением пары (99.2.18), сдвиг сломал бы семантику циркумбинарной орбиты; ручки 7 и 7-холод — да (поверхность-альбедо).

### 3.5. Почему O/B-звёзды полезны умеренно-горячим (исправление v1)

В v1 ручка 5 снижала O/B для тепловых рас с обоснованием «O/B-планеты стерилизованы XUV-стриппингом — атмосферы нет, горячий режим недостижим». **Это фактически неверно (вердикт баланс-тестера, замечание 8):** f_strip (0.1–0.01) истончает атмосферу, но не снимает её полностью: f_atm = f_vol×f_strip → P ≈ 1–12 атм → τ ≈ 1–11 → T_final ≈ 380–620 K — **ровно диапазон умеренно-горячих (350–560)**. Занижение O/B (0.5/0.7) отрезало единственный естественный путь умеренно-горячих. С √L-лэддером (99.2.20 §3.2) инсоляция орбиты i одинакова для всех классов — класс звезды определяет стриппинг, а не температуру орбиты. Поэтому: занижение снято; умеренно-горячим O/B усилены (×1.3) как естественный источник тонких атмосфер; очень горячим (нужен толстый парник) O/B нейтральны.

### 3.5а. T₀_base = t0 без ×1.1505 — явное решение (итерация 3)

**Развилка (замечание 1 баланс-тестера):** в v2 формула ручки 1 называла T₀_base = `prelimBandTemp` (каскад §3.5, альбедо 0.15), но `prelimBandTemp` (cascade.go:542–546) = t0(A=0.15)·**1.1505** (T₁-стиль: `t0 · (1 + ¾·nominalTau)^0.25`, nominalTau = 1.0). Смоук-числа v2 (метановые mult 4.6–13.75 и т.д.) считались при T₀_base = t0 **без** ×1.1505.

**Решение: T₀_base = t0 (без ×1.1505).** Обоснование:

- **Размерностная согласованность.** T_target₀ = center(opt)/(G(P_target)·H_int) — это **до-парниковая** T₀ (G переводит T₀ → T_final). База множителя орбиты обязана быть в той же шкале: t0 = `tempFromFlux(fStar, 0.15, 0, 0, 0)`. `prelimBandTemp` — уже **после** номинального парника (T₁-шкала): подстановка его в формулу (T₀_base/T_target₀)² даёт двойной учёт парника — орбита сдвигается на 1.1505² ≈ 1.324× дальше, планета оседает на 13% холоднее цели (T_final = 0.869·center).
- **Проверка на метановых (окно [90, 115]):** при prelimBandTemp T_final = 0.869·97.5 ≈ 84.7 < 88 surv lo ✗; при t0 T_final = center = 97.5 ∈ [90, 105] opt ✓. Для умеренно-горячих (серные): при prelimBandTemp сдвиг уводит T₁ ниже 373 → умеренный режим → горячий путь (секвестрация = 1, тонкая атмосфера) умирает; при t0 T_target₀ = 330 (горячий пол) → T₁ = 379.8 > 373 → горячий режим держится ✓.
- **Кламп орбиты [0.35, 3.0] (синергия «звёзды+планеты», 2026-09-17):** при t0 максимальный требуемый mult — метановые с орбиты 1: (324.5/83.7)² ≈ 15.2 → кламп 3.0 → t0_new = 324.5/√3 = 187.3 → T_final = 217.8 — вне окна (орбита 1 не добирается, это и есть «не тащить с орбиты 1 на орбиту 8»); метановые добирают с орбит 4–7 (mult 0.62–3.04 → T_final 91.8–98.2 ∈ [90, 115] ✓). При prelimBandTemp mult был бы до 19.9 — ещё одно подтверждение решения T₀_base = t0.

**Следствие для ручек 7 и 7-холод:** обе поверхности-оверрайда заданы **A = 0.15** — ровно базовое альбедо T₀_base → t0_actual = T_target₀ точно (без смещения). В v2 горячая ручка 7 имела A = 0.10 → t0_actual = 1.0144·T_target₀ → T_final = 1.0144·center (+1.4%, поглощалось окнами, но неаккуратно). Унифицировано.

### 3.5б. Холодное альбедо поверхности — почему нужна ручка 7-холод (итерация 3)

Каскад считает t0 по **реальному** альбедо сгенерированной поверхности (cascade.go:390–396: `prelimSurface = GenerateSurfaceComposition(bandSurface, …)`, `aSurface = computeAlbedo(prelimSurface)`), а не по фиксированному 0.15. В холодной полосе (fallbackCascadeBand «холодный») веса: скалы 0.25, **ледники 0.35, мёрзлые газы 0.15**, кратеры 0.15, озёра 0.1 → лёд ≈ 50% роллов. Альбедо: ледники 0.65, мёрзлые газы 0.60 (physics.go `albedoByForm`).

При ледяной доминанте: t0_actual = t0(A=0.15)·((1−0.65)/(1−0.15))^0.25 = t0·0.4118^0.25 = t0·**0.80** → T_final ≈ 0.80·center(opt). Проверка по копилке: метановые 0.80·97.5 = 78 < 88 ✗, аммиачники 0.80·217.5 = 174 < 196 ✗, туманники 0.80·220 = 176 < 190 ✗, глубинники 0.80·286.5 = 229 < 268 ✗ — все холодные расы выпадают из surv при ледяной поверхности (pass-rate ≈ 0.3–0.45 — «половина роллов ледяные», замечание 2).

**Решение: ручка 7-холод** (SurfaceOverride тёмные скалы/кратеры A = 0.15) — симметричный аналог ручки 7 горячих. Альтернатива «признать pass-rate 0.3–0.45 и честно переформулировать смоук» отклонена: она оставляет половину миров кластера расы непригодными (против замысла «раса живёт в кластере заметно чаще»), а тёмные холодные миры физичны (Титан: альбедо 0.22, толины; тёмный углеродистый реголит). Цена: финальная поверхность каскада (ледяная при холодной T) и альбедо для T (0.15) расходятся косметически — та же абстракция, что у ручки 7 горячих (зафиксировано).

### 3.6. Семантика клампа f_vol — явное решение

**Решение: глобальный кламп [10⁻⁶, 0.3], НЕ per-zone.** Обоснование:

- Per-zone кламп ломает холодные расы: метановые живут на внешних орбитах (зона внешняя, диапазон [10⁻², 0.3]), а им нужна тонкая атмосфера f_vol ≈ 1.5·10⁻⁴ (P ≈ 1.2 атм при T 90–120 K) — per-zone кламп поднял бы f_vol до 10⁻² → P ≈ 80 атм → T ≈ 250 K, вне окна.
- Глобальный пол 10⁻⁶ открывает тонкие горячие атмосферы (P ≈ 1–6 атм при T 350–560) — умеренно-горячий путь (замечание 1 баланс-тестера: «пол зоны 10⁻⁴ = венероподобный бюджет»).
- Зонные диапазоны [10⁻⁴…0.3] описывают **естественное распределение** бюджета летучих, а не физический закон: бедная летучими ледяная планета (Меркурий-режим) и бедный летучими горячий мир физичны. Оверрайд f_vol — сдвиг входа, каскад считает P/τ/T по своим формулам.
- Потолок 0.3 — физический максимум (ледяные миры); выше — мини-нептуны (граница каскада §12).

## 4. Мягкость/жёсткость (0–1) — двухслойная

**Параметр конфигуратора** (решение создателя 56a: «не могу ответить по мягкости/жесткости сейчас» — решается здесь).

### 4.1. Проблема непрерывной мягкости (вердикт В1, замечания 2–3, 5–6)

В v1 мягкость масштабировала все ручки непрерывно (`eff = 1 + (config−1)×s`). Проверка @balancetester показала: **непрерывная мягкость не достигает крайних окон при s = 0.5**:

- **Орбита:** метановым нужен mult ≈ 4.6–13.75 (от орбит 3–1); при s = 0.5 эффективный mult ≈ 2.8 → T ≈ 129 K вне surv [88, 115] (порог s ≥ 0.65). Туманникам (mistfolk) нужен mult ≈ 2.7 → при s = 0.5 T ≈ 265 K вне surv [190, 255] (порог s ≥ 0.6).
- **f_vol (горячие):** T ∝ P^0.25 (τ = P·κ_CO2) — половинный сдвиг f_vol даёт половинный P, но T остаётся в убегающем парнике: при f_vol_eff = 3·10⁻⁵ (s = 0.5 от 3·10⁻⁴) P ≈ 35 атм → T ≈ 780 K. Порог s ≈ 0.85–0.9 — непрерывная мягкость для f_vol бессмысленна.
- **Возраст:** LERP «класс-возраст → U(0.1, 0.4)» при s = 0.5 даёт age ≈ 2.6 млрд лет → F_accretion = 0 (тепловые расы не получают тепла; порог s ≈ 0.95). А «eff = config × s» из v1 при s = 0 давало age = 0 → максимум тепла — регрессия инварианта 8.

### 4.2. Разворот подходов: как масштабируется мягкость

| Подход | Что | Вердикт |
|---|---|---|
| **A. Двухслойная (выбрана): частота непрерывно + физика вероятностно** | Ручки частоты (спектральные веса, число планет) — непрерывно `eff = 1 + (config−1)×s` (значения умеренные ×0.7–1.3, непрерывность работает). Ручки физики (орбита, f_vol, состав, возраст, поверхность) — **вероятностно**: каждый мир кластера расы с вероятностью s (seed-ролл в фиксированной позиции) получает ПОЛНУЮ подкрутку (все физические ручки на config), иначе — генератор как есть | Эффект следует из формул при s = 0.5 (полная подкрутка попадает в окна); s = 0 → ни одного подстроенного мира (нулевая регрессия); s = 1 → все миры подстроены (жёсткая гарантия). Семантика: «s = доля миров кластера, подстроенных под расу-дома» — прямое прочтение «раса живёт в кластере заметно чаще, но не гарантированно» (56a) |
| B. Непрерывная + дефолт 0.7–0.8 | Все ручки непрерывно, дефолт поднят | Метановые/туманники покрываются (s ≥ 0.65/0.6), но горячие (f_vol) и тепловые (возраст) — только при s ≈ 0.9; честный отчёт: при s = 0.5 — не все 20 |
| C. Непрерывная со степенным законом s^k (k < 1) | `eff = 1 + (config−1)×s^k` | Метановые покрываются при k ≈ 0.5, но горячие/тепловые — нет (та же f_vol/age-проблема); закон ad hoc |
| D. Сдвиг по лэддеру целиком | Все орбиты звезды сдвигаются на общий множитель | Эквивалентно множителю для той же орбиты (T₀(i) масштабируется одинаково); не решает s-проблему; меняет все планеты звезды, а не целевые |

**Решение: A (двухслойная).** Цена: распределение миров кластера бимодально (подстроенные/естественные) — это свойство, а не дефект: кластер расы = смесь «домов расы» и фоновых миров (разнообразие сохраняется, инвариант 1). Детерминизм по seed сохраняется (ролл в фиксированной позиции). Создатель может выбрать B — развилка §11.3.

### 4.3. Параметры

- **Шкала:** непрерывная s ∈ [0, 1]. s = 0 — генератор как есть (ни один мир не подстроен; спектральные веса нейтральны, число планет без множителя); s = 1 — все миры кластера подстроены (жёсткая гарантия).
- **Слой 1 (непрерывный):** spectral_mult, planet_count_mult — `eff = 1 + (config − 1) × s`.
- **Слой 2 (вероятностный):** для каждого мира кластера расы ролл `rng.Float64() < s` → применить все физические ручки (1–4, 7, 7-холод) на полную силу; иначе — не применять ни одну. Ролл — в фиксированной позиции (в функции подкрутки, до каскада), тот же seed → те же миры. **Early-exit (фикс итерации 3, замечание 4):** при `s <= 0` — «не подстроен» без потребления энтропии; при `s >= 1` — «подстроен» без потребления энтропии. Иначе ролл `Float64() < s` при s = 0/1 сдвигал бы RNG-поток и «s = 0 → генератор как есть» не был бы строгим для того же seed (инвариант 3). При 0 < s < 1 ролл потребляет один Float64 — детерминировано по seed.
- **Куда:** админка, блок «Генерация планет» — крутилка **«Подкрутка под расу-дома»** (0–100%, дефолт **50%**), рядом крутилка **«Число планет в кластерах рас»** (0.7–1.3, дефолт 1.1). Хранятся в `generation_config` (JSONB, тот же store, что PlanetMeans — 99.2.3 §4.3). Читаются и звёздным, и планетным джобами.
- **Дефолт 0.5** — «половина миров кластера подстроена под расу»; создатель может переопределить (гейт §11.3).

## 5. Композиция с профилями регионов (59a) и поселениями рас (55a/65a)

- **Профиль + раса в одном регионе:** обе подкрутки применяются, сдвиги композируются (мультипликативные — умножение, аддитивные — сложение). Обе мягкие, все веса > 0 — инвариант «все типы возможны» сохраняется. Пример: токсичный профиль (M×1.5, K×1.2) + серная раса (O×1.3, K/M×1.6) → веса усилены, ноль не появляется.
- **Поселения рас (65a) не трогаются:** `decideRaceSettlements` и `Race.Suitable` — те же функции, те же окна. Подкрутка делает больше планет проходящими `Suitable` для доминанты кластера (и, естественно, для соседей, чьи окна совпадают — подселение на выбросах работает как раньше).
- **Люди (раса №1) тоже получают подкрутку** своего кластера: сдвиг орбиты к умеренному окну (T opt 273–310), число планет ×1.1. Обогащения нет (O₂ не в режим-гейте; O₂ даёт жизненный проход). Глобальная обитаемая доля ~6% почти не меняется: подкрутка действует только в кластерах рас (~1–2 региона из 80 на расу).

## 7. Инварианты

1. **Все типы планет возможны:** все множители весов строго > 0 (O/B 1.3 — усиление, не запрет); orbit_radius_mult клампится, но не запрещает орбиты; обогащение нормирует состав; f_vol клампится к глобальному диапазону; возраст не убирает планеты; вероятностная подкрутка оставляет (1−s) миров естественными. Жёстких правил нет.
2. **Каскад не модифицируется:** формулы 99.2.20 не трогаются; сдвигаются только входы (OrbitRadiusAU, FVolOverride, AgeGyr, CompositionOverride, SurfaceOverride, mean, веса звёзд). Гейты воды/жизни фильтруют по физике независимо от сдвига.
3. **Детерминизм по seed:** вывод подкрутки — функция карточки + s + seed; ролл «подстроен/нет» — в фиксированной позиции (до каскада) **с early-exit при s ≤ 0 и s ≥ 1** (ролл не потребляет энтропию — «s = 0 → как есть» строго для того же seed, замечание 4); хуки не вставляют роллы в середину последовательности — заменяют существующие в тех же позициях (age вместо determineSystemAge, f_vol вместо volatileBudget; ζ_fvol — один ролл на месте). Тот же seed → те же планеты.
4. **Сумма состава = 100** после обогащения/разбавления (ренормализация) — аудит `atmosphere_sum_not_100` не срабатывает.
5. **Обогащение — только режим-совместимые газы** (холод: NH₃/CH₄; жар: H₂S/SO₂; умер: нет) **и только need-газы с min > 0** («need: {X: 0}» = «не требуется», фикс итерации 3). H₂S добавляется в словарь состава + молекулярная масса 64 (аддитивно). Разбавление парника — только горячий режим.
6. **Не ломает 59a:** профиль и подкрутка композируются (умножение/сложение); профиль региона без изменений.
7. **Не ломает 55a/65a:** `Race.Suitable` не меняется; поселения рас не трогаются; пригодность — та же функция по тем же окнам.
8. **s = 0 → нулевая регрессия:** ни один мир не подстроен (вероятностный слой даёт 0 подстроенных, ролл не потребляет энтропию — seed-поток не сдвигается); спектральные веса нейтральны, число планет без множителя, возраст по классу (нет LERP-регрессии v1: «eff = config × s» давало age = 0 при s = 0).
9. **Тепло — только через возраст (F_accretion);** ядро не перепроектируется (доделки 45a — отдельная сессия).
10. **Экзотика не трогается** (`generateExoticPlanet` — ветка без каскада; F9 расы уже заселились, подкрутка им не нужна).
11. **Проверка @balancetester** (гейт): распределения в кластере с подкруткой vs без (все типы присутствуют; 20 рас копилки получают планеты при s = 0.5; сдвиг не перекашивает глобальную обитаемость).

## 9. Кандидаты ГД-сущностей (Вопрос → Ответ)

Каждое задание приносит +1 кандидата; в текущие числа **не входят** (анти-двойной учёт):

- **«Колыбель расы (homeworld)»** (из v1) — в кластере расы выделяется ОДИН мир-колыбель: первая/наиболее подходящая планета территории (максимум совпадения с opt-окнами), помеченная особым статусом (развитие, культурная ценность, уникальный артефакт-реликвия, дипломатическая значимость). Подкрутка делает колыбели возможными (раньше у 20 рас не было ни одного подходящего мира); колыбель даёт игроку мотив посещать миры рас и естественно ложится на рынок отчётов. **Зависимость:** реализация — отдельная фича (после генератора поселений рас и ресурсной модели 99.2.5); в числа этой спеки не входит.
- **«Серные источники (газовые месторождения серных миров)»** (новый, итерация 2) — обогащённые H₂S/SO₂ атмосферы и вулканические миры умеренно-горячих серных рас становятся источником серных соединений как добываемых ресурсов (атмосферный экстрактор, `10_exploration.md` §10.2.4; неистощаемо, требует энергии и содержания). Даёт серным мирам экономическую идентичность (своя ресурсная ниша) и игроку мотив осваивать их. Отличается от кандидата «Атмосферные ресурсы» (99.2.20 §10 — общая добыча газов) и «Артефакты рас» (99.2.21 §11 — уникальные товары расы): это конкретные месторождения серных соединений на серных мирах. **Зависимость:** ресурсная модель 99.2.5; в числа этой спеки не входит.
