## 1. Цель и скоуп

Сейчас R-модель (кривая изменения населения от среды) — одна, человеческая: оптимум
~+15…+30 °C, при −70 °C люди умирают за дни. Поселения рас (65a) создаются с
`race_id`, но считаются **человеческой** R-моделью: аммиачник в своём комфорте
(215 K) получает человеческий холод R ≈ 2.6·10⁻⁵/сек и вымирает за ~9 дней
(t50 ≈ 7.4 ч) — раса не живёт в собственном доме. Замысел создателя (2026-09-17): **у каждой расы
своя R-кривая** — оптимум в её окне, свой темп размножения (reproduction), свой
градиент деградации вне окна (resilience); инструмент балансировки — **«близнецы»
с выбором расы** (прогон клона с варьируемой осью и поселениями выбранной расы).

**Решение создателя «Вариант Б» (2026-09-17), дословно:** «не автоматически, а
один раз — чтобы я потом мог перебалансить... Дефолты сохраняются ("заводские
настройки"), но я их смогу крутить». Следствия, принятые в этой спеке:

- Кривая R расы **генерируется ОДИН раз** из параметров карточки (окна opt/surv,
  reproduction, resilience) и **сохраняется** как отдельный настраиваемый объект.
- Это «заводские настройки» (дефолт) — из них всегда можно вернуться /
  перегенерировать.
- Создатель **крутит кривую вручную в UI** (узлы/bends, как человеческий
  балансировщик 99.2.17).
- **Правка карточки ≠ правка кривой:** кривая живёт своей жизнью после генерации.
  Перебаланс — через кривую, не через карточку.
- Близнецы показывают **текущую (настроенную)** кривую расы, не дефолтную.
- Спец-случай humans: NULL/"humans" — ровно текущая модель (без изменений).

**В скоупе:**

1. **Материализуемая расовая R-кривая** — объект `{reproduction, curves{жара,
   холод, гравитация, радиация}}`, генерируемый из карточки расы один раз и
   сохраняемый в файл `config/race_balancer.json` (паттерн пресетов 99.2.17:
   in-memory store + файловый слой, переживает рестарт). Две копии: **factory**
   («заводские настройки», снимок из карточки) и **active** (текущая, настроенная
   — то, что использует R-модель).
2. **R-модель расы** — `ChangeComponents` для поселений с `race_id ≠ NULL` и
   `≠ "humans"` использует **active-кривые расы** из расового store; человеческая
   модель (NULL и "humans") **не меняется** (не-регрессия).
3. **«Близнецы» с расой** — выбор расы в UI «Проверка гипотез» (Люди + 50 рас),
   поселения групп создаются с `race_id`, гейт пригодности (`Race.Suitable`),
   отчёт показывает реакцию населения расы по варьируемой оси (по **active**-кривой).
4. **UI балансировки расовых кривых** — расширение вкладки «Балансировка»
   (99.2.17): селектор расы, редактирование кривых (узлы/bends — тот же canvas),
   поле reproduction, кнопки «Сгенерировать из карточки» / «Вернуть заводские»,
   оверлей заводской кривой.
5. **Эталон балансировки** — контрольные точки для каждой расы (оптимум → прирост,
   края surv → вымирание); что видит создатель в близнецах.

**НЕ в скоупе (границы — §8):** код/миграции (только дизайн-док); отчёты игроку
(поле «тип жизни/раса» — при реализации отчётов); артефакты рас (99.2.21 §11);
перепроектирование ядра (45a); подножный корм рас (99.2.5); heat_flux как
R-компонента (в `PlanetInput` её нет — это ось генерации/пригодности, не R-модели);
давление/атмосфера как R-компоненты (оси пригодности, не R-модели); бэкфилл
старых поселений; правка карточек рас (`config/races.json` не меняется); правка
человеческих кривых балансировщика (99.2.17, глобальный store — как есть).

## 2. Природа механизма — развилки и решения

### 2.1. Расовая R-кривая — природа сущности

Разбор по правилу «сущность с двумя экземплярами — не сущность» (GD_PROMPT):

1. **Природа.** Расовая R-кривая — **материализуемый объект-состояние** (запись
   конфигурации кривой под именем расы), как пресеты 99.2.17 §5 («запись-состояние,
   не событие»). НЕ событие, НЕ лог, НЕ атрибут планеты, НЕ производный параметр,
   вычисляемый на лету (это было в итерации 3 — отменено Вариантом Б). Хранится
   **в файле конфигурации** (`config/race_balancer.json`), не в БД (решение
   создателя 2026-09-15 для кривых: «In-memory, не таблица БД»; расы — файловая
   сущность `config/races.json`, кривые — их конфигурация). Проявление в мире —
   кривая изменения населения поселений расы, не запись в мире.
2. **Владелец.** Глобальный сервер (один набор на все учётки админов, как пресеты
   99.2.17 §5; per-user кривые — не здесь). **Одна запись на расу** — 4 компоненты
   как единое целое (раса = набор кривых; атомарность: правка жары не рассинхронивает
   расу). Расширяемость закладывается сразу: 51-я раса получает запись автоматически
   (авто-инициализация §4.4), 5-я компонента (кислотная атмосфера) — новый ключ в
   `curves` (JSON, миграция не нужна).
3. **Расширяемость.** Механизм общий (не per-раса): генерация из карточек,
   валидация, store — единые. Схема переживает 51-ю расу по построению.

**Анти-ловушка «сущность вне игры»:** сущность «расовая R-кривая» в игре
отсутствует (конфигурация модели, не игровая сущность). На текущие числа (карточки
рас, пригодность) она **не влияет** — пригодность (`Race.Suitable`) и генерация
считаются по окнам карточки той же функцией, что раньше; кривая меняет только
расчёт изменения населения поселений рас. Двойного учёта нет: карточка участвует
только в момент генерации (и в пометке «устарело», §4.4), кривая — только в
R-модели. Сущность «реликвии вымирания» (кандидат, §9) в числа не входит.

### 2.2. Как R-модель узнаёт расу поселения

**Решение: `PlanetInput` получает поле `RaceID`** (пусто = человеческая модель).
Путь пересчёта:

- `RecomputeSettlementPopulation(s, input, now)` уже имеет `s.RaceID` — ставит
  `input.RaceID = s.RaceID` перед вызовом `ChangeComponents` (одна точка).
- `planetMortalityInput` (planet_repo.go) — вход строит из планеты; RaceID
  проставляется из поселения в цикле пересчёта (там `settlements[j]` уже загружен
  с RaceID, `GetSettlementsByPlanetIDs` сканирует `race_id`).
- Предпросмотр `/admin/mortality-preview` — новый query-параметр `race_id`
  (пусто = человеческая модель): админ видит кривую расы на планете.
- Близнецы — `runHypothesisJob` проставляет `race_id` из группы (см. §5).

**Зависимость пакетов:** `internal/economy/settlement` импортирует
`internal/races` (для `ByID` + генерации из карточки). Цикла нет: `races` не
импортирует `settlement` (проверено: imports races = json/fmt/math/os/path/filepath).

### 2.3. Спец-случай «humans»

Карточка людей (`config/races.json`): opt [273, 310] K, reproduction 1.0,
resilience 50. Но **якоря человеческой R-модели другие**: жара 0 при ≤ 303 K (30 °C),
холод 0 при ≥ 288 K (15 °C), рампа естественной пары [15, 30] °C. Если бы кривая
людей выводилась из карточки, она отличалась бы от текущей (жара с 310 K вместо
303 K, холод с 273 K вместо 288 K) — регрессия.

**Решение: `race_id = NULL` или `"humans"` → человеческая модель ровно как сейчас**
(глобальный store 99.2.17). Расовый store применяется только к `race_id ≠ NULL` и
`≠ "humans"`. Записи для `"humans"` в `config/race_balancer.json` **нет** (не
создаётся и не используется — чтобы не было двух источников правды для людей).
Это гарантирует не-регрессию и для легаси-поселений (NULL), и для поселений людей,
созданных генератором рас (65a может назначить региону расу "humans").

### 2.4. Разворот подходов — материализация, хранение, перегенерация

#### 2.4.1. Как карточка расы → своя кривая R (форма вывода)

| Подход | Что | Вердикт |
|---|---|---|
| **A. Сдвиг + масштаб человеческих кривых (выбран)** | Сегментные кривые 4 компонент (99.2.17) сдвигаются по X на разницу якорей (жара: opt_hi − 303 K; холод: opt_lo − 288 K; гравитация: ветки от opt; радиация: opt_hi − 20) и масштабируются по Y на resilience | Форма (калиброванная, проверенная @balancetester) сохраняется; позиция — из окна расы; градиент — из resilience. Минимум новых констант. Цена: форма человеческая (двухрежимная сшивка) применяется к чужим биохимиям — осознанное допущение (см. §10) |
| B. Отдельные кривые на расу (nodes+bends в карточке) | Каждая раса хранит свою сегментную кривую в карточке | 50×4 кривых в карточке — ручная калибровка каждой; смешивает «данные» и «производное»; правка карточки = правка кривой (противоречит Варианту Б). Отклонено |
| C. Параметрическая формула на расу (аналитическая) | Формула из окон (как 99.2.12/99.2.13 до перевода в кривые) | Откат к формулам после того, как 99.2.17 перевёл всё в сегментные кривые (единая математика evaluateCurve); две математики в коде. Отклонено |
| D. Сдвиг + растяжение X (масштаб окна) | X-диапазон кривой масштабируется на ширину окна расы | **Пересмотрено (итерация 2, В1 @balancetester):** как общий механизм для всех веток — отклонено; **принято частично — только для горячей ветки жары** (см. §3.3, «Принято: A + растяжение жары») |

**Принято: A + растяжение горячей ветки жары** — сдвиг по X + масштаб по Y
(resilience) + **растяжение X горячей ветки под окно расы** (итерация 2, по В1
баланс-тестера: без растяжения у рас с `surv_hi − opt_hi < ~55 K` весь горячий
surv попадает в слабую зону человеческой кривой жары — t50 годы, surv-граница
бессмысленна). Механика растяжения — §3.3; обоснование — §3.3 и §12.

**Форма при генерации** берётся из **текущих** человеческих кривых store
(99.2.17) в момент генерации: сдвиг/масштаб/растяжение применяются к активным
кривым глобального store. После генерации расовая кривая **независима** от
человеческой: правка человеческой кривой не меняет уже сгенерированные расовые
(это следствие Варианта Б; в итерации 3 было иначе — «шаблон формы», §4.3
отменён).

#### 2.4.2. Хранение расовых кривых

| Подход | Что | Цена | Вердикт |
|---|---|---|---|
| **A. Файл + in-memory store (выбран)** | `config/race_balancer.json` (env `RACE_BALANCER_FILE`), store `map[raceID]*RaceCurves`, атомарная запись (tmp + rename), как пресеты 99.2.17 | Единый паттерн с балансировщиком (решение создателя 2026-09-15 «In-memory, не таблица БД»); расы — файловая сущность (`config/races.json`), кривые — их конфигурация, консистентно; переживает рестарт; объём 50 рас × 2 копии × 4 кривые ≈ 200–300 КБ — нормально для JSON | **Принято** |
| B. Таблица в БД (`race_curves`) | race_id, component, nodes/bends (JSONB), kind (factory/active) | Расы в БД не хранятся (файл) — разрыв источника «расы = файл»; миграция; кривые — конфигурация инструмента балансировки, не игровые данные (не читаются игровым кодом, только админкой и R-моделью) | Отклонено (кривые — конфигурация, как пресеты; БД — для игровых данных) |
| C. В карточку расы (`config/races.json`) | Кривые прямо в карточке | Смешивает «данные» и «производное»; правка карточки = правка кривой — прямое противоречие Варианту Б («правка карточки ≠ правка кривой») | Отклонено |
| D. Только in-memory (без файла) | Генерация при старте, правки живут до рестарта | Правки создателя теряются при рестарте — противоречит «сохраняется как отдельный настраиваемый объект» | Отклонено |

**Принято: A** — файл + in-memory store, паттерн 99.2.17 §5 (store и файл меняются
согласованно: Lock → мутация → атомарная запись tmp + `os.Rename`; битый JSON →
лог-предупреждение, store пуст, файл пересоздаётся при первой записи).

#### 2.4.3. Когда генерировать (один раз)

| Подход | Что | Цена | Вердикт |
|---|---|---|---|
| **A. Авто-инициализация при старте + кнопка перегенерации (выбран)** | Раса без записи в файле → при старте сервера factory/active = вывод из карточки, запись в файл. Дальше — только кнопки в админке | «Один раз при создании расы»: раса добавлена в `config/races.json` → при следующем старте инициализируется (кривая есть, раса живёт в своём доме). Запись есть → не трогается при старте (не пересчитывается — «не автоматически»). Перегенерация — вручную, кнопкой | **Принято** |
| B. Только кнопка в админке | Создатель вручную генерирует для каждой из 50 рас | 50 ручных кликов при первом запуске; раса без кривой → человеческая модель (баг замысла: аммиачник вымирает в своём доме, пока не сгенерировали) | Отклонено |
| C. Авто при каждом старте | Всегда пересчитывать factory из карточки | Противоречит «не автоматически»; ручная правка factory невозможна (каждый старт затирает) | Отклонено |

**Принято: A.** «Не автоматически» из решения создателя относится к
**пересчёту/перебалансу** (не вычислять на лету, не пересчитывать при каждом
старте); инициализация расы без записи — это «один раз при создании», не
перегенерация.

#### 2.4.4. Сосуществование «заводских» и ручной правки

| Подход | Что | Цена | Вердикт |
|---|---|---|---|
| **A. factory и active раздельно; перегенерация трогает только factory (выбран)** | `factory` — снимок из карточки (заводские настройки); `active` — текущая (настроенная). R-модель и близнецы используют **active**. Перегенерация из карточки обновляет только `factory`; ручная правка `active` **не затирается**. Применить новые заводские — кнопка «Вернуть заводские» (`active = factory`, с подтверждением, если `active ≠ factory`) | Ручная правка защищена; «заводские» всегда доступны для возврата; правка карточки не ломает настроенную кривую (пометка «устарело» — §4.4) | **Принято** |
| B. factory и active оба обновляются при перегенерации | Перегенерация затирает ручную правку (с предупреждением) | Ручная правка теряется при обновлении карточки — против замысла «кривая живёт своей жизнью» | Отклонено |
| C. Только предупреждение, ничего не обновляется | «Карточка изменилась» — создатель сам решает | Нет механизма обновления заводских без ручного редактирования | Отклонено |

**Принято: A.** Сравнение `active == factory` (по узлам/bends/reproduction,
поэлементно) — признак «не тронута»; флаг `manual` не хранится (производное
сравнение, точное для deep-copy).

#### 2.4.5. Что материализуется

Вариант Б: «кривая R генерируется из параметров карточки (окна opt/surv,
reproduction, resilience)». Чтобы «перебаланс — через кривую, не через карточку»
работал для **темпа размножения**, материализуется и `reproduction` (число), и
4 кривые (resilience вшит в Y узлов при генерации — отдельной ручки не нужно,
градиент крутится правкой Y):

- `reproduction` — множитель естественной пары (из карточки при генерации;
  далее — редактируемое поле в UI).
- `curves{heat, cold, gravity, radiation}` — узлы + изгибы (resilience уже
  применён к Y).

**Альтернатива (reproduction остаётся параметром формулы из карточки) — отклонена:**
правка карточки меняла бы темп роста без перегенерации — противоречит «правка
карточки ≠ правка кривой» и «перебаланс — через кривую».

## 3. Генерация, хранение, R-модель

### 3.1. Материализуемый объект расы

Запись в `config/race_balancer.json` (одна на расу):

```json
{
  "race_id": "ammonia",
  "card_hash": "sha256:…",
  "factory": {
    "reproduction": 0.05,
    "curves": {
      "heat":      {"nodes": [{"x": -38.15, "y": 0}, "…"], "bends": [2.1, "…"]},
      "cold":      {"nodes": [{"x": -273.15, "y": 0.0387}, "…"], "bends": [-0.2, "…"]},
      "gravity":   {"nodes": [{"x": 0, "y": 8.0e-8}, "…"], "bends": [-0.3, "…"]},
      "radiation": {"nodes": [{"x": 0, "y": 0}, "…"], "bends": [-10, "…"]}
    }
  },
  "active": { "reproduction": 0.05, "curves": { "…": "…" } },
  "updated_at": "2026-09-17T12:00:00Z"
}
```

- `factory` — «заводские настройки»: снимок вывода из карточки в момент генерации.
- `active` — текущая (настроенная) кривая: то, что использует R-модель, близнецы
  и предпросмотр. Сразу после генерации `active = factory` (deep copy).
- `card_hash` — sha256 канонического JSON карточки (`json.Marshal(Race)` — порядок
  полей фиксирован структурой) в момент генерации; при старте сравнивается с
  текущим — расхождение = пометка «заводские настройки устарели» (§4.4).
- `updated_at` — RFC3339, ставит сервер при любой записи (не из тела запроса).
- Валидация кривых — как PUT 99.2.17 §6 (узлы строго возрастают, y ∈ [0, 0.999),
  |bend| ≤ 10, 3–16 узлов); невалидные записи при загрузке пропускаются с
  лог-предупреждением (не роняют старт).

**Формат файла:**

```json
{ "races": [ { "race_id": "…", "card_hash": "…", "factory": {…}, "active": {…}, "updated_at": "…" } ] }
```

- `races` — плоский список (не map): проще CRUD, совместим с расширением.
- Путь: дефолт `config/race_balancer.json`, env `RACE_BALANCER_FILE` переопределяет
  (паттерн `BALANCER_PRESETS_FILE`, 99.2.17 §8).

### 3.2. R-модель расы — формула

```
R_total_расы = active.reproduction · (1 − k) · R_ест
             + evaluateCurve(active.curves.heat, T°C)
             + evaluateCurve(active.curves.cold, T)
             + evaluateCurve(active.curves.gravity, g)
             + evaluateCurve(active.curves.radiation, rad)
```

- **Источник кривых — `active` расы из расового store** (не глобальный store, не
  производные на лету из карточки). Resilience уже вшит в Y при генерации —
  отдельного масштаба в формуле нет.
- **Естественная пара** — константа (без человеческой рампы [15, 30] °C):
  `R_ест_расы = active.reproduction·R_ест`, `R_рожд_расы = −k·active.reproduction·R_ест`,
  нетто `active.reproduction·(1−k)·R_ест`. Рампа — артефакт человеческой калибровки;
  температурная реакция расы целиком в кривых. В оптимуме кривые = 0 → нетто =
  `active.reproduction·(1−k)·R_ест` (рост при k > 1, статика при k = 1, убыль при
  k < 1 — инвариант k сохраняется для всех рас).
- **Гвард отсутствия записи:** `race_id ≠ NULL/"humans"`, но расы нет в расовом
  store (теоретически невозможно после авто-инициализации §4.4; страховка) →
  человеческая модель + лог-предупреждение (сервер не падает, поселение не
  «ломается»).
- **Гвард r ≥ 1** (мгновенная гибель, `Population`) — без изменений; рост
  r < 0 разрешён (как сейчас).
- **Гвард переполнения роста (поправки В1 + В2, без изменений из итерации 3):**
  три уровня: (1) расчётный кламп `MaxPopulation = 1e300` в `Population`
  (технический порог, ~5 порядков ниже `math.MaxFloat64`; недостижим в игре);
  (2) **кламп записи `MaxInt4Population = 2^31−1 = 2 147 483 647`** перед
  приведением к int в обоих путях записи (БД и «простой визит» — единая
  константа, защита от «integer out of range» в int4-колонке
  `settlements.population`); (3) витринный кламп 1e15 отменяется (был недостижим —
  запись падала раньше). In-memory проекции (предпросмотр, отчёт близнецов)
  показывают истинные float64 (read-only диагностика). TDD — §14 тест 11.

**Семантика reproduction (решение по развилке, без изменений из итерации 3):**
множитель применяется к **естественной паре целиком** (нетто), а не только к
рождаемости. Обоснование: (а) формулировка создателя «множитель к R_ест
(рождаемость/прирост)» — «прирост» это нетто; (б) при масштабировании только
рождаемости расы с reproduction < 0.5 (~20 рас) не воспроизводят себя даже в
оптимуме — медленное вымирание в собственном доме, противоречит замыслу «раса
живёт в своём окне»; (в) масштабирование пары биологически когерентно
(k-стратеги/r-стратеги). Альтернатива (буквальное прочтение) — гейт-вопрос §11.1.

### 3.3. Генерация из карточки (механика вывода, вызывается один раз)

Функция `deriveRaceCurves(race, humanCurves) → {reproduction, curves}` — вывод
4 кривых из карточки + текущих человеческих кривых store. Вызывается **только**
при генерации (авто-инициализация §4.4, кнопка «Сгенерировать из карточки» §4.3);
в R-модели не участвует (там — готовые `active`-кривые).

Кривые человеческого store хранятся в °C (жара/холод), g (гравитация), rad
(радиация) — как в balancer store (99.2.17). Сдвиг — операция над узлами; изгибы
(bends) сохраняются (форма сегментов не меняется).

- **Жара:** `X' = (opt_hi − 273.15) + (X − 30)·HeatStretch` (X в °C — узлы
  человеческой кривой; результат X' в °C; в K-эквиваленте:
  `T' = opt_hi + (T_чел − 303)·HeatStretch`). Первый узел (30 °C, Y=0) →
  `opt_hi − 273.15` °C (жара 0 при T ≤ opt_hi). **Растяжение горячей ветки
  (итерация 2, В1):** `HeatStretch = (surv_hi − opt_hi)/60` — край surv расы
  отображается на отклонение 60 K человеческой кривой (90 °C), где R ≈ 3.9·10⁻⁵
  (t50 ≈ 5 ч): для узких окон (аммиачники +20 K) кривая сжимается, сильная зона
  попадает в surv; для широких (солевые +100 K) — растягивается. Без растяжения
  у рас с `surv_hi − opt_hi < ~55 K` весь горячий surv лежал в слабой зоне
  человеческой кривой (R ≤ 1.2·10⁻⁶, t50 месяцы-годы) — дыра В1. **Почти-ступенька
  на узких горячих окнах (замечание В2, осознанно, симметрично холоду):** у рас с
  узким горячим окном (водородники `surv_hi − opt_hi` = 5 K, HeatStretch = 0.083)
  сигмоидный переход человеческой кривой (84–90 °C: R 1.6·10⁻⁷ → 3.9·10⁻⁵, ~×250)
  сжимается в ~0.5 K перед surv_hi — почти-ступенька. Гладкость формально
  соблюдена (кривая непрерывна); свойство узких физических окон (жидкий H₂,
  20–35 K), осознанно. Верхний край кривой (4000 °C) сдвигается так же;
  экстраполяция вправо — константа (как сейчас). `HeatStretch > 0` всегда:
  `opt ⊂ surv` строго по валидации карточки (99.2.21 §16); при `surv_hi = opt_hi`
  (невозможно по валидации) — гвард `HeatStretch = max(..., 1e-3)`.
- **Холод:** `X' = X + ColdShiftK`; **левый узел пинится на абсолютный ноль**
  (−273.15 °C, Y = 0.05 — максимум человеческой кривой): у холодных рас
  (opt_lo < 288 K) сдвиг отрицательный и узлы уходят ниже 0 K — нефизично;
  пиннинг левого узла на −273.15 °C с Y = 0.05 и отбрасывание промежуточных узлов
  ниже −273.15 °C (с соответствующими bends) даёт «максимум деградации на 0 K»
  для любой расы. Правый узел (14.85 °C, Y=0) → `opt_lo − 273.15` °C (холод 0 при
  T ≥ opt_lo). **На краю surv — слабый хвост, «квази-порога» НЕТ (поправка В2):**
  сильная зона кривой (0.05 у 0 K) у холодных рас уходит в **нежилой слой**
  ниже `surv_lo` (поселение не создаётся — Suitable = false). Пример:
  метан-грибницы (ColdShiftK = −193) → сдвинутые узлы 0 K (пин, 0.05), 7 K
  (3.0·10⁻⁵), …, 95 K (0); обрыв 0.05 → 3·10⁻⁵ лежит в 0–7 K (ниже surv_lo
  90 K), а весь холодный surv [90, 95] K ложится на слабый хвост: R_холод(90 K)
  ≈ 4.9·10⁻⁶ (t50 ≈ 1.7 дня), середина surv ≈ 3.1·10⁻⁶ (t50 ≈ 2.6 дня) —
  не «R ≈ 5·10⁻², t50 минуты» (ошибка ~4 порядка, В2). Кривая гладкая, скачок
  только в нежилом слое. Растяжение холодной ветки НЕ вводится (холод и так
  даёт t50 дни на краю surv — критерий §6 «часы-дни» держится; поправка В2:
  числа и обоснование, не механика).
- **Гравитация:** узлы X < 0.8 → `X' = X + GravityLoShift`; узлы X > 1.2 →
  `X' = X + GravityHiShift`; два узла комфорта (0.8, 1.2) → (opt_lo, opt_hi)
  (линейный ремап комфорта на окно расы). Узлы, уходящие ниже 0 g, отбрасываются
  (левая ветка клампится к 0 g). Для opt уже человеческого (0.8–1.2) — без
  изменений. Для opt шире человеческого ветки разъезжаются (комфорт шире);
  для уже — ветки сближаются, комфорт сужается (проверка: opt ⊆ surv по валидации
  карточки 99.2.21 §16).
- **Радиация:** `X' = X + RadiationShift`; первый узел (20, Y=0) → `opt_hi` rad.
  Узлы ниже 0 rad отбрасываются (кламп к 0).
- **Масштаб Y:** все узлы всех четырёх кривых × `ResilienceScale = 50/resilience`
  (после сдвига X). Валидация кривой (y ∈ [0, 0.999)) — после масштаба;
  ResilienceScale 0.625–1.43 (карта 35–80) не выводит Y за 0.999 (максимум
  человеческой кривой 0.98 × 1.43 = 1.40 → **кламп Y ≤ 0.999** — гвард, как в
  validateCurve).
- **Reproduction:** `active.reproduction = factory.reproduction = attributes.reproduction`
  (из карточки, без преобразования — множитель).

### 3.4. Что НЕ сдвигается

- **Heat_flux** — не компонента R-модели (`PlanetInput` без heat_flux): ось
  пригодности/генерации, в R-кривые не входит (граница §8).
- **Давление, атмосфера (need/poison)** — оси пригодности (`Race.Suitable`),
  не R-компоненты.
- **СПЖ и k** — глобальные ручки (99.2.16), для рас не меняются (СПЖ на расу в
  карточке нет — только reproduction/resilience; при будущем введении СПЖ расы —
  отдельная правка, анти-двойной учёт).

## 4. Границы применения и интеграция

### 4.1. Где действует расовая R-модель

- **Действует:** поселения с `race_id ≠ NULL` и `≠ "humans"` — все пути пересчёта
  (рекомпут по событию, предпросмотр, близнецы). Это включает поселения рас,
  созданные генератором 65a: их поведение **меняется** (раньше — человеческая
  модель, вымирали в своём комфорте; теперь — расовая, живут в оптимуме). Это
  замысел фичи, не регрессия; вселенная транзиентная (перегенерация штатным
  инструментом).
- **Не действует (не-регрессия):** `race_id = NULL` (легаси/люди) и
  `race_id = "humans"` — ровно текущая модель (жара/холод/гравитация/радиация из
  глобального store, рампа [15, 30] °C, нетто (1−k)·R_ест).
- **Легаси-поселения** не трогаем: бэкфилла нет, пересчёт при следующем событии
  идёт той же формулой, что раньше (для NULL — человеческой).

### 4.2. Лог «Вымерло» и причины

- Механизм `DeathTime`/`DeathCause` не меняется: `r` — полная компонента
  (`ChangeComponents` с расовыми `active`-кривыми), причина — argmax по вкладам
  среды, `natural` при нулевых вкладах среды. Для рас «все вклады среды = 0» =
  полный комфорт в оптимуме (кривые 0) — причина `natural` корректна.
- Запись «Вымерло» — у всех вымерших (как сейчас); для расовых поселений дата
  считается по расовому r.

### 4.3. Балансер-UI (99.2.17) — редактирование расовых кривых

**В итерации 3 было:** «правка человеческой кривой меняет форму всех расовых
(шаблон формы); показ расовых кривых в балансер-UI — вне сессии». **Отменено
Вариантом Б:** расовые кривые материализованы и независимы; редактирование
расовых кривых — **в скоупе** этой сессии.

**Решение: расширение вкладки «Балансировка» (99.2.17), не отдельная вкладка.**
Canvas-редактор (balancer.js/balancerCanvas.js) переиспользуется как есть —
формат кривых (узлы + bends) идентичен, математика evaluateCurve общая.

**Селектор расы** в шапке вкладки: «Люди (глобальная)» + 50 рас из каталога.
- **«Люди»** — текущее поведение 99.2.17 (глобальный store, пресеты, кнопки
  «Сохранить/Отмена/Сброс/Вернуть заводской»); расовые кнопки скрыты.
- **Раса** — загрузка `active`-кривых расы (GET с `race_id`), редактирование
  узлов/bends — тот же drag/Shift+клик/ПКМ/зум/лог-линейная. Дополнительно:

  - **Поле «Множитель размножения (reproduction)»** — число > 0 (валидация),
    живой расчёт «рост в оптимуме при k=2: ×N/год» под полем.
  - **Кнопка «Сгенерировать из карточки»** — перегенерировать `factory` из
    текущей карточки (механика §3.3); `active` **не трогается**; `card_hash`
    обновляется. Подтверждение: «Заводские настройки будут пересчитаны из
    карточки; текущая (настроенная) кривая не изменится».
  - **Кнопка «Вернуть заводские»** — `active = factory` (deep copy); активна,
    если `active ≠ factory`; подтверждение «Текущая кривая будет заменена
    заводской».
  - **Оверлей заводской кривой** — пунктирная линия factory-кривой поверх
    active (в цвет компоненты, полупрозрачно); переключатель «показать заводскую».
    Визуально видно расхождение ручной правки от заводской.
  - **Пометка «Заводские настройки устарели»** — если `card_hash` ≠ хэшу текущей
    карточки (карточку правили после генерации): жёлтая плашка + кнопка
    «Обновить заводские» (то же, что «Сгенерировать из карточки»).
  - **Пресеты 99.2.17 (панель пресетов) для рас** — **не в скоупе** (у расы
    заводские + активная; пресеты — слой глобального балансировщика, §8).

**Хендлеры (новый префикс `/admin/race-balancer/*`, не ломает 99.2.17):**

### 4.4. Жизненный цикл записи расы

| Операция | factory | active | card_hash |
|---|---|---|---|
| Авто-инициализация при старте (расы без записи) | = вывод из карточки | = factory (deep copy) | = текущий хэш карточки |
| Старт (запись есть) | не трогается | не трогается | не трогается; при расхождении с текущей карточкой — пометка «устарело» (в UI, не в файле) |
| PUT curve / PUT reproduction | — | обновляется | — |
| «Сгенерировать из карточки» (POST generate) | = вывод из карточки | **не трогается** | = текущий хэш |
| «Вернуть заводские» (POST reset-factory) | — | = factory | — |

**Старт сервера** (паттерн 99.2.17 §5 «Старт»):

1. Загрузить каталог рас (`LoadCatalog`).
2. Прочитать `config/race_balancer.json` (если есть); каждая запись проходит
   валидацию §3.1; невалидные пропускаются с логом.
3. Для каждой расы каталога: записи нет → сгенерировать factory/active из
   карточки, записать в store и файл (атомарно, tmp + rename). Запись есть →
   не трогать (даже при устаревшем card_hash — только пометка).
4. Битый JSON → лог-предупреждение, store пуст; расы инициализируются как в п.3
   (файл пересоздаётся при первой записи). Сервер НЕ падает.

**Атомарность записи (обязательна):** временный файл `<имя>.tmp` в той же
директории + `os.Rename` (как 99.2.17 §5). Одна пишущая сторона — Lock store.

## 5. «Близнецы» с расой

### 5.1. TwinSpec — новое поле

`TwinGroup` получает `race_id` (string, опционально; пусто = люди/легаси):

```jsonc
{ "id": "young", "name": "Молодые",
  "race_id": "ammonia",                 // пусто = человеческая модель
  "overrides": { "temperature": 215 },  // ось в K
  "planets_per_world": 3,
  "settlement": { "chance": 1.0, "settlements_per_planet": 1,
                  "population": { "kind": "fixed", "fixed": 100000000 } } }
```

- **Раса — на группу** (не на эксперимент): гибче — можно сравнить две расы на
  одном клоне (аммиачники vs люди при −60 °C) или одну расу на двух значениях оси.
  Альтернатива «раса на эксперимент» — гейт-вопрос §11.4.
- Валидация: `race_id` из каталога (`races.ByID`), пусто — ок.

### 5.2. Гейт пригодности

В `runHypothesisJob` при создании поселений группы с `race_id`:

- `race := races.ByID(race_id)`; если `!race.Suitable(planetData)` — поселение **не
  создаётся**, планета идёт в счётчик «не пригодна» группы (в отчёте). Словами
  задачи: «расы, непригодные на клоне — не селятся (видно „не пригодна")».
- Если пригодна — вставка с `race_id` (колонка уже существует, миграции нет).
- `race_id = "humans"` или пусто — как сейчас (гейт применяется и к людям:
  `HumansSuitable`/`humans.Suitable` — единый источник пригодности, 65a;
  поведение «не селится на непригодном» сохраняется).

### 5.3. Отчёт — что видит создатель

Текущий отчёт: «Создано планет: N, поселений: M, невозможных: K». Для балансировки
кривой расы этого мало. Расширение (поле `report` джоба):

```
Группа «Молодые» (раса: Аммиачники, T = −58 °C):
  планет: 3, поселений: 3, непригодных: 0
  r_per_sec: −3.2e-11 (рост +0.1%/год)   ← расовая R_total в точке оси (active-кривая)
  t50: ∞ (рост), t_death: —
  население через 1 год: 100 100 000
```

Для каждой группы: значение варьируемой оси (температура в °C для читаемости),
`r_per_sec` (расовый `ChangeComponents` в точке оси — **по active-кривой расы**),
`t50`/`t_death_hours`, проекция на 1 год (`Projection`), число поселений и
«непригодных». Создатель видит **числа R на контрольных точках оси** (таблица
групп = оцифровка кривой расы по оси) — этого достаточно, чтобы настраивать
кривую (прямая правка узлов/bends + reproduction в балансер-UI). **Проценты роста
в отчёте — экспоненциальные** (`(1−r)^год − 1`): для термо-роев (r = −1.27·10⁻⁷)
показывать «×54.9/год», а не «+400%/год» (поправки В1 + В2, §7.1).

### 5.4. UI «Проверка гипотез»

- В карточку группы добавляется дропдаун **«Раса»**: «Люди» (дефолт, пусто) + 50
  рас из каталога (источник — существующий доступ к каталогу в админке рас).
- Сборка TwinSpec: `race_id` из дропдауна (пусто → не передавать).
- Пометка в UI: «поселения группы создаются с R-моделью выбранной расы (текущая
  настроенная кривая); непригодная раса на клоне не селится (видно в отчёте)».
- Температура оси в UI — °C, в данных — K (конверсия уже есть, hypothesis.js).

### 5.5. Предпросмотр `/admin/mortality-preview`

Query-параметр `race_id` (пусто = человеческая модель): админ смотрит кривую расы
на конкретной планете (r_per_sec, t_death, projection) без прогона близнецов —
быстрая проверка одной точки. Использует **active**-кривую расы.

## 7. Числа — предположение дизайнера (проверит @balancetester)

Числа — предположение, эталон не задан; правка — в константах/формулах генерации,
не в коде (как 99.2.22 §6). **Итерация 4:** числа §7 — **ожидания генерации**

### 7.1. Нетто в оптимуме при k=2 (дефолт ручки)

`нетто = reproduction·(1−2)·R_ест = −reproduction·R_ест` (минус = рост).
**Проценты — экспоненциальные** (поправка В1): рост за год = `(1−r)^год − 1`
(дискретная экспонента, §3.2; год = 365·24·3600 с, как в проекциях 99.2.16);
линейная оценка `100·|r|·год` валидна только при `|r|·год < 0.3` (аммиачники,
люди), при больших r расходится в разы (термо-рои:
`(1+1.27·10⁻⁷)^(365·24·3600) − 1 ≈ ×54.9/год` — точное значение ×54.9, не
×54.6 (поправка В2), и не «+400%/год»):

| Раса | reproduction | Рост в оптимуме | Комментарий |
|---|---|---|---|
| Люди (модель) | 1.0 | +2%/год (×1.02) | без изменений |
| Аммиачники (5) | 0.05 | +0.1%/год (×1.001) | медленно (удвоение ~700 лет) |
| Метан-грибницы (11) | 0.001 | +0.002%/год (×1.00002) | почти статика |
| Кремниевые стражи (35) | 5·10⁻⁶ | ~0 | статика (кристаллический рост) |
| Серные гнёзда (15) | 30 | ×1.82/год (+82%/год) | быстро |
| Термо-рои (26) | 200 | ×54.9/год (+5390%/год) | удвоение ~63 дня |

Диапазон карточки 4·10⁻⁶–200 → нетто от ~0 до ×54.9/год. Сверка с @scientist:
числа reproduction уже проверены в 99.2.21 §9 (холод ×0.01–0.1, метан ×10⁻⁵–10⁻³,
кремний ×10⁻⁶, сера ×10–100, жара ×10–1000 — «попадаю»); здесь они становятся
темпом роста в оптимуме — расхождений нет.

### 7.2. Resilience — масштаб деградации

`ResilienceScale = 50/resilience` (линейная, «50 = человек»). Карта 35–80 →
масштаб 0.625–1.43. Примеры: аммиачники (65) → ×0.77 (медленнее человека),
кремниевые стражи (80) → ×0.625, солевые (40) → ×1.25, термо-рои (35) → ×1.43.
Диапазон умеренный — resilience как мягкая ручка градиента, не как переключатель
(эталон «порог-переключатель запрещён» соблюдён: кривые гладкие, масштаб
мультипликативный). **Замечание В1 (минорное, зафиксировано):** контраст 2.3×
мал на фоне порядковых различий деградации — как «мягкая ручка» ок, как контраст
слаб; лог-альтернатива (3.5×) — гейт §11.2, решение отложено до балансировки
создателем через близнецов. **Итерация 4:** resilience вшит в Y при генерации;
создатель может компенсировать слабый контраст прямой правкой Y узлов в
балансер-UI (ручка теперь доступна напрямую — следствие Варианта Б).

### 7.3. Сдвиги кривых — примеры (ожидания генерации)

| Раса | opt T, K | surv T, K | HeatShiftK | HeatStretch | Жара 0 при | Край surv жары → R |
|---|---|---|---|---|---|---|
| Аммиачники | 200–235 | 196–255 | −68 | 20/60 = 0.333 | T ≤ 235 K | 255 K → ≈3.9·10⁻⁵·0.77 (t50 ≈ 6 ч) |
| Метан-грибницы | 95–110 | 90–120 | −193 | 10/60 = 0.167 | T ≤ 110 K | 120 K → ≈3.9·10⁻⁵·0.71 (t50 ≈ 7 ч) |
| Термо-рои | 500–700 | 480–780 | +397 | 80/60 = 1.333 | T ≤ 700 K | 780 K → ≈3.9·10⁻⁵·1.43 (t50 ≈ 3.5 ч) |
| Кремниевые стражи | 750–1050 | 700–1150 | +747 | 100/60 = 1.667 | T ≤ 1050 K | 1150 K → ≈3.9·10⁻⁵·0.625 (t50 ≈ 8 ч) |

Холод: `ColdShiftK = opt_lo − 288` (без растяжения; сильная зона кривой (0.05
у 0 K) у холодных рас уходит в нежилой слой ниже surv_lo — на краю surv слабый
хвост: метан-грибницы на 90 K → R ≈ 4.9·10⁻⁶, t50 ≈ 1.7 дня; критерий
«часы-дни» держится (дни); «квази-порога» нет — поправка В2, §3.3). Гравитация:
крио-небесные (opt [1, 5]) → комфорт [1, 5] g, ветки вне. Радиация:
радиотолерантные (opt [0, 90]) → 0 при rad ≤ 90. Пример деградации аммиачника
вне оптимума: T = 180 K (ниже opt_lo 200 K, выше surv_lo 196 K? — нет, 180 < 196
= вне surv → Suitable false, поселения нет; поселения аммиачников существуют
только в [196, 255] K, деградация — в [196, 200) и (235, 255]).

### 7.4. Проверка на «аммиачник в своём доме» (смоук-пример)

Планета T = 215 K (центр opt аммиачников), g = 1, rad = 10: сгенерированные
жара/холод = 0 (215 ∈ [200, 235]), гравитация/радиация в комфорте = 0 → нетто =
0.05·(−1)·R_ест = −3.2·10⁻¹¹/сек → рост +0.1%/год. **Раньше** (человеческая
модель): холод R ≈ 2.6·10⁻⁵/сек → **t50 ≈ 7.4 часа, полное вымирание 10⁹ ≈ 9.2 дня**
(поправка В1: было «t50 ≈ 8 дней» — неверно, R_холод(215 K) = 2.6·10⁻⁵ → t50 =
ln2/2.6·10⁻⁵ = 7.4 ч). Фича чинит дом расы.

## 9. Кандидат ГД-сущности (Вопрос → Ответ)

Каждое задание приносит +1 кандидата; в текущие числа **не входит**
(анти-двойной учёт):

- **Размножение разных биохимий (аммиак/метан/сера/кремний)** — уже сверено в

- **Форма кривой для чужих биохимий** — человеческая двухрежимная сшивка

  осознанное допущение: форма «деградация ускоряется с отклонением» универсальна,
  абсолютные позиции — из окон карточек (фазы NH₃/CH₄/серы — сверены с @scientist

  ветки (итерация 2, В1)** — X-масштаб, не новая форма: на **горячем** краю surv
  деградация критическая (край отображается на сильную зону кривой: R ≈
  3.9·10⁻⁵·ResilienceScale, t50 часы) — согласуется с физикой фаз вверх по T
  (кипение NH₃ 239.8 K, CH₄ 111.7 K; 99.2.21 §9). На **холодном** краю
  (плавление/замерзание) деградация умеренная — слабый хвост кривой (R ≈
  3–5·10⁻⁶, t50 ≈ 1.7–2.6 дня; поправка В2): осознанная асимметрия сторон
  (растяжение только для жары), форма «деградация ускоряется с отклонением»
  сохранена, критерий §6 «часы-дни» держится на обеих сторонах. Сильного
  расхождения нет: окна карточек (фазы) сверены с @scientist в 99.2.21 §9,
  скорость деградации внутри окна — дизайнерская форма (человеческая,
  осознанное допущение §3.3).
- **Resilience (градиент деградации вне оптимума)** — дизайнерская ручка, не
  физический факт; вилки физики нет — предположение дизайнера (линейная шкала,
  §7.2), проверка @balancetester.
- **Итерация 4 (материализация)** — физических утверждений не добавляет: числа
  генерации те же, что в итерации 3; меняется только жизненный цикл (один раз +
  ручная правка). Сверка не пересматривается.

## 14. Инварианты и проверки (TDD)

1. **Не-регрессия людей:** `ChangeComponents` при `RaceID = ""` и `RaceID = "humans"`

   store + рампа [15, 30] °C + нетто (1−k)·R_ест) — существующие тесты
   `change_components_test.go`/`mortality_test.go` зелёные без правок ожиданий.
2. **Генерация из карточки (детерминизм):** `deriveRaceCurves(ammonia)` → жара 0
   при T ≤ 235 K, холод 0 при T ≥ 200 K, HeatStretch = 20/60 = 0.333, Y × 0.769
   (resilience 65); два вызова из одной карточки и одних человеческих кривых —
   одинаковый результат.
3. **Сдвиги (ожидания генерации):** термо-рои (500–700): жара 0 при ≤ 700 K,
   холод 0 при ≥ 500 K; крио-небесные (opt g [1, 5]): гравитация 0 в [1, 5],
   ветки вне; радиотолерантные (opt rad [0, 90]): радиация 0 при rad ≤ 90.
   Холодный левый узел ≥ −273.15 °C (пиннинг на 0 K), узлы строго возрастают
   (валидация кривой не ломается).
4. **Масштаб:** `ResilienceScale(65) = 0.769`, `(50) = 1.0`, `(35) = 1.429`;
   Y узлов после масштаба клампится в [0, 0.999).
5. **Сохранение/загрузка (round-trip):** запись store → файл → загрузка →
   идентичные узлы/bends/reproduction (порядок полей канонический).
6. **Авто-инициализация при старте:** раса без записи → factory/active из
   карточки, card_hash = текущий, файл записан; раса с записью → не трогается

   карточки, **active не тронут** (приоритет ручной правки), card_hash обновлён;
   POST reset-factory → active = factory.
8. **Устаревание:** card_hash ≠ хэш текущей карточки → флаг «устарело» в status;
