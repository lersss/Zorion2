## 0. Резюме (одним абзацем)

Вводится сущность **«внутрисистемная позиция»** — местоположение игрока внутри звёздной
системы (`users.current_position` JSONB, NULL = вне системы): **позиция ЯВНО отражает полёт**
(решение создателя 2026-09-20): покой — `{status: orbit, объект, level, biome}` (уровни
orbit/surface + biome — задел под высадку, решение А), внутрисистемный полёт —
`{status: in_flight, from, to, start_time, arrive_at}`. Игрок в своей системе может **лететь
на орбиту любого объекта** (главная звезда, **компаньоны — цели v1, решение создателя**,
планета, спутник) прямо из модалки системы: кнопка «Лететь» у объектов, модалка **не
закрывается**, полёт виден внутри неё (прогресс/таймер/анимация корабля), длительность
честная по расстоянию в а.е. (двухрежимная формула с параметром скорости двигателя sf:
манёвренный режим до 100 а.е. — `max(3, dist×sf)`; крейсерский режим дальних дистанций —
`100×sf + (dist−100)×sf×0.1` — «пусть ускоряется в полёте на дальние расстояния», сшивка
непрерывна при любом sf; реальный диапазон **3 с – ~5.5 мин**, потолка нет). Полёты
персистентны по паттерну 97a (отдельная таблица `player_intrasystem_flights`, Restore,
битые цели отбрасываются). Прибытие на орбиту планеты = **авто-знание** о ней (свежее,
source `presence`, 77a §6.3). Правило видимости 90a изменяется (решение создателя С2):
стоящие на орбите видны другим в радиусе — координаты звезды + статус «у планеты X» /
«у компаньона X» (С3). Межзвёздный полёт и внутрисистемная позиция согласованы (С1):
старт межзвёздного → позиция NULL, прибытие в систему → «орбита звезды». Высадка на
поверхность и NPC-полёты — следующие итерации (уровни заложены, расширяемость без реализации).

## 1. Концепция и термины

**Внутрисистемная позиция** (термин, GLOSSARY-кандидат, §2 «Пространство и география») —
местоположение игрока внутри звёздной системы: орбита объекта (звезда/планета/спутник) или
поверхность (задел под высадку, в этой фиче не выставляется). NULL = игрок вне системы
(в межзвёздном полёте) или данных нет. Хранится в `users.current_position`; всегда согласована
с `users.current_world_id`. Термин «позиция» в 77a §5.3 занят (позиции игроков на карте) —
поэтому фиксируется полное название «внутрисистемная позиция» (критик, мелкое 3; открытый
вопрос №4 идеи закрыт).

**Внутрисистемный полёт** — перемещение игрока с орбиты одного объекта системы на орбиту
другого (звезда/планета/спутник) с честной длительностью по расстоянию. Инициируется из
модалки системы «как на карте» (решение создателя №6); модалка не закрывается (суть
пожелания). Полёт — отдельное состояние (таблица `player_intrasystem_flights`) + позиция
переходит в `{status: in_flight}` (явно отражает полёт, решение создателя 2026-09-20);
по прибытии позиция — `{status: orbit}` на цели (как `current_world_id` при межзвёздном
полёте обновляется по прибытии).

**Объекты системы** — цели полёта: главная звезда (`object_type=star`, `object_id` = мир),
**компаньоны/внешние звёзды кратных** (`object_type=star`, `object_id` = синтетический id,
решение создателя 2026-09-20 — цели v1), планеты (`planet`), спутники (`satellite`).
Синтетические id компаньонов — §3.1.

## 2. Сущность «внутрисистемная позиция»

### 2.1. Природа сущности (обязательный разбор)

1. **Природа** — состояние/атрибут игрока (результат-состояние «где я сейчас»), не событие
   и не лог: запись одна на игрока, истории нет. Хранится как атрибут `users` (JSONB-колонка).
2. **Владелец** — один объект (игрок): одна запись на игрока, атрибут, не таблица. Правило
   «не зажимай поток записей в атрибуты» не нарушается: поток записей — это полёты
   (отдельная таблица §3.2), позиция — текущее состояние (атрибут).
3. **Расширяемость** — уровни `orbit`/`surface` + `biome` (задел под высадку) ложатся в ту же
   JSONB-схему без миграции; второй владелец (NPC, итерация 2) — своя колонка у `npc_agents`
   по той же схеме (расширяемость заложена, §8.2).

### 2.2. Модель и хранение

`users.current_position` — JSONB, NULL = вне системы (в межзвёздном полёте) или нет данных.
**Позиция ЯВНО отражает внутрисистемный полёт (решение создателя, гейт 2026-09-20):**

```json
// в покое — на орбите объекта
{ "status": "orbit", "object_type": "star"|"planet"|"satellite", "object_id": "<id>",
  "level": "orbit", "biome": null }
// в полёте — внутрисистемный полёт идёт (никакого «телепорта»)
{ "status": "in_flight", "from_type": "star"|"planet"|"satellite", "from_id": "<id>",
  "to_type": "star"|"planet"|"satellite", "to_id": "<id>",
  "start_time": <ms>, "arrive_at": <ms> }
```

- `status=orbit` (покой): `object_type=star` → `object_id` = `current_world_id` (главная
  звезда) **или синтетический id компаньона** (`companion:<world_id>` / `extra:<world_id>:<i>`,
  §3.1); `object_type=planet` → `planets.id`; `object_type=satellite` → id спутника из
  `planets.data.satellites` (UUID, `models.PlanetSatellite.ID`). `level` в этой фиче всегда
  `"orbit"`; `"surface"` и `biome` — задел (решение А), сервер их не пишет.
- `status=in_flight`: позиция = текущий внутрисистемный полёт (from/to/start/arrive).
  Переходы: старт полёта → `in_flight` (атомарно с записью таблицы полётов, §3.2);
  прибытие → `orbit` на цели (атомарно с удалением строки, §3.6). `start_time` добавлен
  сверх минимума создателя — нужен прогресс-бару полосы полёта (§5.7).

### 2.3. Согласование (инварианты)

- **ИП-1:** `current_position != NULL` ⇒ `current_world_id != NULL` и объект(ы) принадлежат
  системе `current_world_id` (star → id = world или синтетический id компаньона системы;
  planet → `world_id` планеты = world; satellite → входит в `satellites` планеты этой
  системы; `in_flight` → from/to принадлежат системе).
- **ИП-2 (С1):** старт межзвёздного полёта (`POST /travel`) → `current_position = NULL`
  (игрок покидает систему); прибытие межзвёздного полёта (onArrival → `UpdateCurrentWorld`)
  → `current_position = {status: orbit, star, world_id}` (дефолт «орбита звезды», критик,
  мелкое 1).
- **ИП-3:** во время внутрисистемного полёта `current_position = {status: in_flight, ...}`
  (явно отражает полёт — решение создателя); по прибытии → `{status: orbit}` на цели.
- **ИП-4:** битый `current_position` (объект удалён перегенерацией) при чтении трактуется
  как `{status: orbit, star, current_world_id}` (безопасный фолбэк; для `in_flight` с битым
  from/to — фолбэк «орбита звезды»); при сбросе битого `current_world_id` (существующая
  логика `/travel`) `current_position` также NULL-ится. Фолбэк применяется и при отдаче
  `my_position` (§4.4) и статуса (§4.5) — ничего не падает (М-2).

## 3. Внутрисистемный полёт

### 3.1. Цель

Цель полёта — **орбита** объекта (решение создателя №5): главная звезда, **компаньоны
(решение создателя, гейт 2026-09-20: «А почему не слетать к компаньону? Пусть ускоряется
в полёте на дальние расстояния» — компаньоны ЦЕЛИ v1)**, планета, спутник. Смысл цели
«орбита звезды» — возврат с орбиты планеты/спутника/компаньона (критик, мелкое 1). Цель
«на поверхность» — следующая итерация (высадка), не входит.

**Компаньоны — синтетические id (факт: компаньоны НЕ отдельные миры).** Проверено по коду:
компаньоны живут в `worlds.stellar_mods` (спектр/масса/температура/sep_au,
`models/stellar_mods.go:15-17` — «не отдельная сущность»; генератор создаёт один world на
систему, `galaxy.go:471-496`) — миров-записей у компаньонов нет, `worlds.id` у них
отсутствует. Поэтому цель компаньона: `object_type: "star"` + **синтетический стабильный id**:

- главный компаньон: `companion:<world_id>` (один на систему);
- внешний компаньон кратной: `extra:<world_id>:<i>` (i — индекс в `extra_companions`).

Синтетические id вычисляются детерминированно (без миграции/бэкфилла), отдаются в API
планет аддитивно: `companion_id` и `extra_companions[].id` (§4.4). Валидация цели (§4.1):
`object_type=star` → `object_id` = `current_world_id` или валидный синтетический id
компаньона системы.

### 3.2. Хранение: таблица `player_intrasystem_flights` (С5)

`player_flights` не подходит (from/to — UUID мира NOT NULL, критик С5). Отдельная таблица по
паттерну 97a (абсолютный `arrive_at`, Restore, битые цели отбрасываются):

```sql
CREATE TABLE player_intrasystem_flights (
    user_id    UUID PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    world_id   UUID NOT NULL,                 -- система (current_world_id на момент старта)
    from_type  TEXT NOT NULL CHECK (from_type  IN ('star','planet','satellite')),
    from_id    TEXT NOT NULL,                 -- UUID (мир/планета/спутник) или синтетический id компаньона
    to_type    TEXT NOT NULL CHECK (to_type    IN ('star','planet','satellite')),
    to_id      TEXT NOT NULL,
    start_time TIMESTAMPTZ NOT NULL,
    arrive_at  TIMESTAMPTZ NOT NULL           -- абсолютное время прибытия
);
```

Одна запись на игрока (PK `user_id`); повторный старт (редирект) заменяет сегмент
(INSERT ON CONFLICT DO UPDATE, как 97a). `from` хранится для Restore и отображения «from → to»
в модалке; стартовая точка сегмента в а.е. не хранится (см. §3.5 — редирект от объекта
отправления, упрощение). `from_id`/`to_id` — TEXT: синтетические id компаньонов не UUID
(§3.1); колонки новые, конвертации нет.

**Старт полёта (атомарность):** запись строки таблицы + `current_position = {status:
in_flight, from, to, start_time, arrive_at}` — одной транзакцией (С-1): позиция и таблица
не расходятся; модалка/`my_position` сразу видят полёт.

### 3.3. Менеджер

Новый менеджер `travel.IntrasystemManager` (тот же пакет `internal/travel`, паттерн
`travel.Manager` 97a): `StartIntraFlight` / `CancelIntraFlight` / `GetIntraFlight` /
`RestoreIntra`; карта `map[string]*IntraFlightInfo` под `sync.RWMutex`; горутина-таймер с
`CancelChan`; персистентность через store (репозиторий `player_intrasystem_flight_repository.go`
по образцу `player_flight_repository.go`); TOCTOU-гвард удаления строки (после onArrival, под
локом — 97a). Взаимоисключение с межзвёздным полётом — в хендлерах (§4.1, §4.2):
одновременно активны не могут.

### 3.4. Длительность (С4) — предположение дизайнера, числа сверены с генератором (@balancetester, Н1–Н3)

**Расстояние между объектами** (в а.е., радиальная разность; фазы орбит — косметика модалки,
в данных не хранятся):

| Объект | r (а.е.) |
|---|---|
| звезда (главная) | 0 |
| планета | `orbit_radius_au` (S: `0.4×1.7^i×√L`, `planet_data_generate.go:362,451`; P: `3×companion_sep_au`) |
| спутник | r родительской планеты (спутник у планеты) |
| компаньон | `companion_sep_au` (главный) / `extra_companions[i].sep_au` (внешний) — честное разделение 99.2.18: wide 100–3000 а.е., кратные 1000–10000 а.е. |

`dist = |r(from) − r(to)|`. Спутник → своя планета → dist = 0 → минимум.

**Факты генератора (Н1, проверено @balancetester):** P-планеты генерируются ТОЛЬКО у
close-пар — одна P-орбита на систему, `3×sep` ∈ [0.15, 2.7] а.е. (`circumbinary.go:29`);
у wide/multiple — S-планеты. S-орбиты — `0.4×1.7^i×√L`, потолок планет 8 (внешняя орбита
G-звезды ~16 а.е.). **Компаньоны — цели v1 (решение создателя 2026-09-20):** их разделения
(100–10000 а.е.) дают реальные dist > 100 а.е. — крейсерский режим теперь реально
используется (не только редкие O/B-звёзды).

**Формула (рекомендация — двухрежимная, сшивка непрерывна при любом sf; Н3):**

```
sf = ship.EngineSpeed(users.equipment)          // 0.3 (91a §7.1, значение 66a)
dist ≤ 100 а.е.:  duration = max(3, dist × sf) сек               // манёвренный режим
dist > 100 а.е.:  duration = 100×sf + (dist−100) × sf × 0.1 сек  // крейсерский режим
```

- Коэффициент sf — тот же, что у межзвёздного полёта («тот же корабль, тот же коэффициент»);
  **единицы разные (М-3):** сек/px у межзвёздного (66a) vs сек/а.е. у внутрисистемного.
  Сшивка на 100 а.е.: `100×sf` = 30 с при sf = 0.3 — непрерывна при любом будущем sf
  (замысел 77a §1.3: скорость зависит от двигателей; захардкоженное «30» не рвётся при
  sf ≠ 0.3).
- Минимум 3 сек — как у межзвёздного (66a).
- **Крейсерский режим (dist > 100 а.е.) — «пусть ускоряется в полёте на дальние
  расстояния» (создатель, 2026-09-20):** включается у компаньонов (100–10000 а.е.)
  и дальних S-планет ярких звёзд; игровая логика — на дальних дистанциях корабль идёт
  крейсерским ходом (в 10 раз быстрее). Это и есть запрошенное создателем ускорение.

**Реальный диапазон длительностей: 3 с … ~5.5 мин** (компаньон 10000 а.е. → 327 с).
Потолка НЕТ (как 66a «честная длительность без потолка») — крейсерский режим сам
сжимает дальние дистанции; вопрос потолка — на гейт (§11.2).

| dist (а.е.) | сценарий (реализуемый) | длительность |
|---|---|---|
| 0 | спутник → своя планета | 3 с (мин) |
| 0.15–2.7 | звезда → P-планета close-пары (единственная на систему) | 3 с |
| 0.68–16.4 | звезда → S-планеты G-звезды (idx 1–7, √L = 1) | 3–5 с |
| 73.4 | звезда → внешняя S-планета A-звезды (idx 7, √L ≈ 4.5) | 22 с |
| 152 | звезда → единственная S-планета O-звезды (idx 1, √L ≈ 224) | ~32 с (крейсерский) |
| 518 | звезда → внешняя S-планета B-звезды (idx 7, √L ≈ 32) | ~43 с (крейсерский) |
| 1000 | звезда → компаньон (wide, мин) | 57 с (крейсерский) |
| 10000 | звезда → внешний компаньон (кратная, макс) | 327 с ≈ 5.5 мин (крейсерский) |

В системах без компаньонов (M/K/G/F) все полёты ≤ ~9 с; крейсерский режим — компаньоны
и редкие O/B-звёзды. Иерархия «локальный хоп < галактический перелёт» сохраняется
(типичный межзвёздный — 45–60 с).

Разворот подходов (альтернативы, цена — на гейт §11.1):
- **B. Одна линейная + потолок:** `max(3, dist×sf)`, потолок 10 мин. Проще, но потолок
  при максимуме ~5.5 мин почти мёртв; теряется ускорение на дальних (создатель просил).
- **C. Одна линейная без потолка:** честно до конца, но компаньон 10000 а.е. → 50 мин —
  непропорционально (создатель просил ускорение).
- **Принято: A** (двухрежимная) — честная в пределах режима, крейсерский режим =
  ускорение на дальних (создатель 2026-09-20), сшивка непрерывна при любом sf.

### 3.5. Правила старта, редиректа, отмены

- **Двигатель** (91a §6.1): для `role=player` без установленного двигателя
  (`!ship.HasEngine`) — отказ «Двигатель не установлен — полёт невозможен»; админ/skycomposer —
  исключение.
- **Уже на орбите** (критик, мелкое 1; нулевое расстояние): в покое (`status=orbit`) цель ==
  объект позиции (совпадают `object_type` и `object_id`) → 400 «Вы уже на орбите этого
  объекта»; в полёте (`status=in_flight`) цель == объект отправления (`from_type`+`from_id`)
  → 400 (UX-5 блокирует кнопку клиентски).
- **Взаимоисключение:** активный межзвёздный полёт → внутрисистемный старт отклоняется
  (400 «Вы в межзвёздном полёте»); старт межзвёздного (`/travel`) отменяет активный
  внутрисистемный полёт и NULL-ит позицию (С1).
- **Идемпотентность** (как `/travel`): активный внутрисистемный полёт к той же цели
  (пара `to_type` + `to_id`, М-7) → 202 с текущим полётом (без перезапуска).
- **Редирект** (другая цель при активном внутрисистемном полёте): отмена текущего + новый
  полёт **от объекта отправления** (from текущего полёта); позиция переходит в новый
  `in_flight` (новые from/to/start_time/arrive_at). Упрощение против 61a (точка P не
  интерполируется): внутрисистемные полёты короткие (3 с – ~5.5 мин), интерполяция в а.е. —
  оверинжиниринг; зафиксировано как осознанное упрощение.
- **Отмена:** серверная `CancelIntraFlight` существует (для старта межзвёздного и чистоты);
  UI-кнопки отмены в этой итерации нет (полёты короткие) — границы §8.
- **Restore** (паттерн 97a, при старте сервера; **порядок: сначала межзвёздные
  (`player_flights`, как 97a), затем внутрисистемные**, С-1): `arrive_at ≤ now` → onArrival
  сразу + удаление строки; `arrive_at > now` → перерегистрация в памяти с оригинальными
  временами, горутина ждёт остаток; битая система (`world_id` не существует) или битая цель
  (планета не в системе / спутник не найден) → строка удаляется, позиция не трогается;
  **если у игрока есть межзвёздная строка — внутрисистемная удаляется БЕЗ вызова onArrival**
  (иначе позиция `{planet, старый мир}` запишется при новом `current_world_id` — нарушение
  ИП-1, С-1).

### 3.6. Прибытие (onArrival)

1. `current_position = {status: orbit, to_type, to_id, level: "orbit"}` — **атомарно с
   удалением строки полёта** (одна транзакция, С-1): позиция и таблица не расходятся;
   модалка/`my_position` сразу видят прибытие (полоса полёта уходит, маркер «я здесь» — на
   цели). **Битая цель (перегенерация) на момент прибытия → фолбэк `{status: orbit, star,
   current_world_id}` (ИП-4).**
2. **Авто-знание (С6, решение создателя):** цель — планета → UPSERT `player_planet_knowledge`
   (планета = `to_id`); цель — спутник → UPSERT для **родительской планеты** (спутник в
   `satellites` планеты); цель — звезда → знания нет. Данные — как у сканера
   (`surface_dominant`, `surface_composition`, `settlements_count`, по образцу
   `KnowledgeRepository.ScanSystem`), `scanned_at = NOW()`, `source = 'presence'`
   (новое значение source, 77a §8.1: `scanner`/`report`/`presence`; CHECK-ограничения нет —
   миграция не нужна). Рынок отчётов не страдает (решение создателя: стоять можно только
   у одной планеты).
   **Осознанное отклонение от 77a И5 (М-5):** И5 говорит «присутствие = полные данные»;
   v1 авто-знание даёт скан-уровень (поверхность + поселения), полный уровень
   (недра/атмосфера/детали) — задел; решение создателя С6 фиксирует только «свежее, как
   физическое присутствие».
3. **Атомарность (С-1):** запись `current_position` (в т.ч. переход `in_flight` → `orbit`)
   и `current_world_id` (при межзвёздном прибытии) — одним `UPDATE users SET
   current_world_id = $1, current_position = $2` (или двумя в одной транзакции): позиция
   никогда не остаётся битой между двумя апдейтами (краш-окно закрыто).
4. Удаление строки полёта ПОСЛЕ onArrival под TOCTOU-гвардом (97a) — в одной транзакции
   с записью позиции (п.1).

## 4. API

### 4.1. `POST /api/intrasystem-flight` — старт внутрисистемного полёта (новый)

Тело:

```json
{ "object_type": "planet", "object_id": "<uuid>" }
```

`object_type`: `star` | `planet` | `satellite`. Для `star` `object_id` = `current_world_id`
(главная звезда) или синтетический id компаньона системы (§3.1). Система цели —
`current_world_id` игрока (в теле не передаётся).

Валидация (порядок):
1. Авторизация (JWT).
2. `role=player` без двигателя → 400 «Двигатель не установлен — полёт невозможен» (91a).
3. Активный межзвёздный полёт → 400 «Вы в межзвёздном полёте».
4. `current_world_id` NULL или мир битый → 400 «Вы не находитесь в системе».
5. Цель не принадлежит системе (планеты/спутники `current_world_id`; `star` — `object_id` =
   `current_world_id` или валидный синтетический id компаньона) → 400 «Объект не найден
   в вашей системе».
6. Идемпотентность: активный полёт к той же цели (пара `to_type` + `to_id`, М-7) → 202
   с текущим полётом.
7. «Уже на орбите» (§3.5) → 400 (в покое — цель == объект позиции; в полёте — цель ==
   объект отправления).

Ответ (202):

```json
{
  "duration": 14,
  "from_type": "star", "from_id": "<world>",
  "to_type": "planet", "to_id": "<planet>",
  "start_time": 1726800000000,
  "arrive_at": 1726800014000
}
```

(`start_time`/`arrive_at` — UnixMilli, как `start_time` в `/travel`.)

### 4.2. `POST /travel` — дельта (С1)

При старте межзвёздного полёта: отменить активный внутрисистемный полёт
(`IntrasystemManager.CancelIntraFlight`) и записать `current_position = NULL`. **Атомарность
(С-1):** отмена intra + запись позиции NULL — одним `UPDATE users SET current_position = NULL`
(или в одной транзакции с отменой): не остаётся окна, где intra отменён, а позиция ещё не
NULL. Остальная логика не меняется.

### 4.3. `GET /me` — аддитивные поля

- `current_position` — `users.current_position` (JSONB) или `null`. При активном
  внутрисистемном полёте содержит `status=in_flight` с from/to/start_time/arrive_at —
  восстановление после рефреша (паттерн 42a) идёт из позиции; отдельного поля
  `intrasystem_flight` нет (один источник, позиция = полёт).

### 4.4. `GET /api/worlds/{worldID}/planets` — аддитивные поля (для модалки)

- `my_position` — `current_position` игрока, **только если** `current_world_id == worldID`,
  иначе `null` (игрок не в этой системе). При активном внутрисистемном полёте — `status:
  in_flight` (модалка при открытии сразу показывает полосу полёта и маршрут «откуда →
  куда», §5.7). **Битая цель (перегенерация) → фолбэк «орбита звезды» (ИП-4, М-2):**
  отдаётся `{status: orbit, star, world_id}`, ничего не падает.
- **Компаньоны (решение создателя):** в ответе аддитивно отдаются синтетические id —
  `companion_id` (`companion:<worldID>`, если есть компаньон) и `extra_companions[].id`
  (`extra:<worldID>:<i>` по индексу). Старый контракт не ломается (поля новые).
- Отдельного поля `my_intrasystem_flight` нет — полёт отдаётся в `my_position`
  (`status=in_flight`), один источник.

Хендлер уже грузит user для `role=player` (77a §11.2) — добавление полей аддитивно,
существующие поля не меняются.

### 4.5. `GET /api/players/positions` — изменение правила (С2/С3)

**Правило 90a изменяется (решение создателя 2026-09-20, С2):** показываются игроки
с определённым местоположением: (а) активный межзвёздный полёт, (б) `current_position !=
NULL` (покой `status=orbit` / внутрисистемный полёт `status=in_flight`). Радиус-фильтр для
`role=player` (77a) сохраняется; для админа — без радиуса (И7), правило активности то же
(вариант a 90a).

| Случай | x, y | status | object_type / object_id |
|---|---|---|---|
| межзвёздный полёт | интерполяция (как сейчас) | «в полёте» | null / null |
| внутрисистемный полёт (`status=in_flight`) | координаты звезды (`current_world_id`) | «в полёте (система X)» | null / null |
| позиция = планета | координаты звезды | «у планеты X» | `planet` / id |
| позиция = спутник | координаты звезды | «у спутника X» | `satellite` / id |
| позиция = главная звезда | координаты звезды | «в системе X» | `star` / world_id |
| позиция = компаньон | координаты звезды | «у компаньона X» / «у внешнего компаньона X» | `star` / синтетический id |

Источник статуса — `current_position.status` (позиция пишется атомарно со
стартом/прибытием полёта — консистентна с менеджером; `PlayerPositions` читает новую
колонку). **Компаньон — НЕ отдельный мир на карте (факт: компаньоны в `stellar_mods`,
миров нет, §3.1):** координаты игрока у компаньона = звезда системы (С3-якорь), статус
«у компаньона X» (X — спектральный класс / индекс).

С3 (нет AU→px): внутрисистемная позиция не имеет мировых координат — якорь — координаты
звезды; радиус радара считается от них (для игрока на орбите планеты радар центрирован на
звезду — `PlayerPosition` уже возвращает координаты `current_world_id` вне межзвёздного
полёта, менять не нужно). `object_type`/`object_id` — для модалки (маркеры «кто у какого
объекта», §5.4); маршрут/цель чужих полётов не показываются (77a §5.3, И-разведданные).
**Статус — готовой строкой с именем объекта от сервера** (решение @uidesigner, §6):
сервер резолвит имя планеты/спутника (`«у планеты Nemurzan II»`), клиент карты не знает
планет чужих систем. **Битая цель (перегенерация) → фолбэк «в системе X» (ИП-4, М-2):**
позиция трактуется как «орбита звезды», статус не падает.

**Офлайн-нюанс:** понятия «онлайн» в системе нет (90a); стоящий офлайн-игрок с
персистентной позицией будет виден в радиусе. Принято как следствие решения создателя
(корабль физически там); альтернатива (свежесть по `last_seen`) — звоночек на гейт (§11).

## 5. UI модалки (поведение и данные; пиксели — @uidesigner)

### 5.1. Доступность

Внутрисистемный полёт доступен, **только когда модалка открыта на свою систему**
(`current_world_id == worldId` модалки; `my_position != null` из §4.4). Для чужих систем —
только существующий межзвёздный «Перелететь» (ПКМ по звезде, модалка закрывается).

> **Дельта 2026-09-21 (99.2.30, композитный маршрут).** Правило «для чужих систем —
> только „Перелететь"» изменяется: планеты/компаньоны чужой системы летят «Лететь»
> через ПКМ-меню (композитный маршрут, 2 сегмента: межзвёздный + автостарт
> внутрисистемного по прибытии). «Лететь» остаётся и для звезды чужой системы
> (межзвёздный, без намерения). §5.5 (точки входа) читается с этой поправкой.

### 5.2. Кнопка «Лететь» (инициирование «как на карте», решение №6)

- Планеты и спутники: кнопка «Лететь» в карточке объекта (правая панель). Данные для
  запроса: `object_type` + `object_id` объекта.
- Звезда: ПКМ → контекстное меню. Новая логика: игрок в этой системе → пункт
  «На орбиту звезды» (внутрисистемный; скрыт/заблокирован, если уже на орбите звезды);
  игрок не в этой системе → существующий «Перелететь» (межзвёздный, без изменений).
  **В своей системе «Перелететь» из модалки убирается (М-6, осознанно):** игрок на орбите
  планеты своей системы межзвёздно улетает с карты (не из модалки); «Перелететь» остаётся
  в модалке только для чужих/403 систем.
- **Компаньоны (решение создателя):** ПКМ по компаньону на канвасе (hit
  `{type:'star', starIndex>0}`) → пункт «На орбиту компаньона» (внутрисистемный; скрыт,
  если уже на орбите этого компаньона). Сейчас контекстное меню обрабатывает только
  `hit === 'star'` (главная) — расширить хит-тест на компаньонов (`events.js`
  contextmenu); цель — синтетический id (`companion:<world>` / `extra:<world>:<i>`, §3.1).
- Без двигателя (91a): кнопка блокируется с подсказкой «Двигатель не установлен» (как
  сейчас «Перелететь» в модалке, `modalState.hasEngine`).

### 5.3. Полёт внутри модалки (модалка НЕ закрывается — суть пожелания)

- При старте внутрисистемного полёта модалка остаётся открытой (в отличие от
  межзвёздного «Перелететь», который её закрывает).
- Индикатор полёта: «from → to», таймер обратного отсчёта, прогресс-бар (данные —
  ответ §4.1: `duration`, `start_time`, `arrive_at`; прогресс считается клиентским
  таймером, как панель полёта на карте `map/flight.js`).
- Анимация корабля: маркер игрока движется по орбите от объекта отправления к цели
  (косметика, в canvas модалки; точную анимацию — @uidesigner).
- По прибытии (клиентский таймер): повторный запрос `/api/worlds/{worldId}/planets`
  (обновляется `my_position` — `status` переходит `in_flight` → `orbit`) → маркер «я здесь»
  переезжает на цель, карточка цели показывается/выбирается.
- Рефреш страницы во время полёта: модалка закрыта; при повторном открытии
  `my_position` отдаёт `status=in_flight` → модалка показывает полосу полёта и его
  продолжение (паттерн 42a). На карте игрок — в своей системе (координаты звезды),
  без изменений.

### 5.4. «Я здесь» и другие игроки

- Маркер «я здесь»: на объекте `my_position` (canvas + карточка объекта). Во время полёта —
  маркер-корабль на пути (§5.3).
- Другие игроки: из `/api/players/positions` — **опрос 5 с** (`state.playerPositions`),
  модалка фильтрует по `object_type`/`object_id` этой системы — маркеры у объектов.
  **Чужие внутрисистемно летящие в модалке НЕ показываются (v1)** — только стоящие.
  **Скопление многих игроков у одной планеты — решение @uidesigner, вариант A (§5.12).**

### 5.5. Точки входа (решение @uidesigner)

- Планета: кнопка «🚀 Лететь» в карточке (рядом с «Обновить»/«Назад»).
- Спутник: кнопка «🚀 Лететь» в карточке спутника (вкладка планеты).
- Звезда своей системы: ПКМ → контекстное меню → пункт «На орбиту звезды».
- Компаньон своей системы: ПКМ по компаньону на канвасе → «На орбиту компаньона»
  (аналог звезды, §5.2).
- Чужая система / 403: существующий «Перелететь» (межзвёздный, без изменений).
- Клик по планете на канвасе полёт НЕ запускает — только выделение (существующее поведение).

### 5.6. Доступность (решение @uidesigner)

- Блок полёта виден, только когда `my_position != null` (своя система,
  `current_world_id == worldId` модалки).
- Кнопка «Лететь» disabled при: нет двигателя (91a), цель == текущая позиция,
  цель == активный полёт.
- ПКМ-пункт «На орбиту звезды» скрывается, если игрок уже на орбите звезды

- ПКМ-пункт «На орбиту компаньона» скрывается, если игрок уже на орбите этого компаньона.

### 5.7. Полоса полёта (flight strip, решение @uidesigner)

- Модалка во время полёта НЕ закрывается.
- Полоса полёта — между блоком чипов и контентом: «🚀 Полёт: <от> → <к> · осталось N сек»
  + прогресс-бар.
- Таймер — в существующем rAF-тике модалки (`index.js tick`).
- Восстанавливается при открытии модалки из `my_position` (`status=in_flight` с
  from/to/start_time/arrive_at, 42a-паттерн) — полоса и маршрут «откуда → куда» видны
  сразу, без «телепорта» (решение создателя).
- Отмены в UI нет — редирект единственный способ передумать (UX-5, звоночек §11.7).

### 5.8. Анимация корабля на канвасе (решение @uidesigner)

- Маркер-корабль: `lerp(отправление, цель, progress)`, след-пунктир.
- Спутник-цель: летим к позиции родительской планеты (спутники на канвасе не рисуются,
  v1; звоночек §11.8).
- Компаньон-цель: летим к позиции компаньона на канвасе (`layout.stars[starIndex]`).
- Статичный маркер «я здесь» во время полёта не рисуется (только движущийся корабль).
- **Обновлено 2026-09-22 (спека размеров, этап 1):** корабль в схеме — **крошечное
  мировое тело** `R = 1.0` мировой px (Земля R=10 → ровно ×10; корабль виден лишь на

## 8. Границы скоупа

- **Высадка на поверхность** — следующая итерация (решение №3): сущность заложена с уровнями
  `orbit`/`surface` + `biome` (§2.2), в этой фиче выставляется только `orbit`; цель «на
  поверхность» не принимается.
- **NPC-агенты** — вторая итерация (решение №8): внутрисистемные полёты NPC не реализуются.
  Расширяемость заложена: модель позиции (object_type/object_id/level) и схема полёта
  (from/to/arrive_at) переносимы на `npc_agents` (своя колонка позиции + свои поля полёта
  по образцу 20a.1); `npcSpeedFactor` (0.3, 91a §6.1) — их настройка скорости, двигатель
  NPC не проверяется.
- **Компаньоны — цели v1** (решение создателя 2026-09-20): синтетические id (§3.1),
  крейсерский режим реально используется (100–10000 а.е.). Компаньоны НЕ становятся
  отдельными мирами на карте (факт: живут в `stellar_mods`) — координаты игрока у
  компаньона = звезда системы (звоночек §11.10).
- **Отмена полёта в UI** — нет (полёты 3 с – ~5.5 мин; «Лететь» на объект отправления во
  время полёта заблокирован, UX-5); серверная отмена существует. Звоночек §11.7.
- **Редирект от точки P** (61a-интерполяция) — упрощён до «от объекта отправления» (§3.5).
- **Рынки/топливо/загруженность** — не затрагиваются (77a §7.3, 91a §9).
- **HUD-отображение внутрисистемного полёта на карте** — не делается (полёт суб-пикселен,
  виден в модалке).

- Двигатель обязателен для `role=player` (91a §6.1); админ/skycomposer — исключение.

**Новые числа (предположение дизайнера, сверены с генератором @balancetester, Н1–Н3;**
**компаньоны — решение создателя 2026-09-20):**
- Двухрежимная формула §3.4 с параметром sf: `dist ≤ 100 а.е. → max(3, dist×sf)`;
  `dist > 100 а.е. → 100×sf + (dist−100)×sf×0.1` (сшивка непрерывна при любом sf).
  Реальный диапазон длительностей: **3 с – ~5.5 мин** (компаньон 10000 а.е. → 327 с;
  в системах без компаньонов ≤ ~43 с, в большинстве ≤ ~9 с). Потолка нет (66a-стиль).

**Инварианты:**
- **И1 (позиция согласована с миром):** `current_position != NULL` ⇒ объект(ы) принадлежат
  `current_world_id` (ИП-1–ИП-4, §2.3; `in_flight` — from/to системы).
- **И2 (С1):** межзвёздный полёт и внутрисистемная позиция не сосуществуют: старт
  межзвёздного → позиция NULL; прибытие → «орбита звезды»; внутрисистемный старт при
  активном межзвёздном → отказ.
- **И3 (один активный полёт):** у игрока одновременно не более одного активного полёта
  (межзвёздного или внутрисистемного); старт одного отменяет другой.
- **И4 (полёт требует двигателя):** 91a §6.1 — для `role=player`; админ/skycomposer — исключение.
- **И5 (сервер — источник видимости):** 77a И1 — стоящие игроки фильтруются по радиусу на
  сервере; клиент не получает скрытых позиций.
- **И6 (знание от присутствия свежее):** 77a §6.3/И5 — прибытие на орбиту = авто-знание
  (`source='presence'`, `scanned_at = NOW()`); протухание 7 дней не меняется; рынок отчётов
  не дублируется (стоять можно у одной планеты — решение создателя).
- **И7 (персистентность):** позиция переживает рефреш (42a-паттерн) и рестарт сервера
  (97a-паттерн: Restore, битые цели отбрасываются).
- **И8 (не-регрессия межзвёздного полёта):** `/travel`, `player_flights`, редирект 61a,
  интерполяция 77a §4.2 не меняются; `/travel` получает только дельту С1 (§4.2). Restore
  при старте: сначала межзвёздные, затем внутрисистемные (С-1).
- **И9 (не-регрессия 77a/90a):** правило 90a изменено решением создателя (С2) — изменение
  зафиксировано; радиус-фильтр, статусы, скрытие маршрутов чужих полётов сохраняются.
- **И10 (стоимость не от размера галактики, инвариант 2 проекта):** внутрисистемные полёты —
  по игроку (O(1) на запрос, Restore O(строки)); обходов планет/тиков нет.

**Риски и режимы отказа:**
- **Битый `current_position`** (перегенерация) → фолбэк «орбита звезды» (ИП-4); битая цель
  полёта при Restore → строка удаляется, позиция не трогается (§3.5).
- **Офлайн-игроки видны на орбитах** — следствие С2 (нет понятия «онлайн»); если создатель
  решит скрывать давно неактивных — потребуется механизм свежести (звоночек §11).
- **P-планета одна на систему** — перелётов P→P нет (Н1); dist = 0 только у спутника
  к своей планете (3 с, осознанно: фазы орбит косметические).
- **Крейсерский режим «нечестен» в 10 раз** — осознанный компромисс против длинных полётов
  к дальним целям (компаньоны 100–10000 а.е., S-планеты ярких звёзд); это и есть
  запрошенное создателем «пусть ускоряется»; сшивка непрерывна (`100×sf`), режим линеен
  внутри себя.

object_type, object_id, message, placed_at); цена — риск спама (лимит маяков на игрока,
убираются при уходе из системы). В текущие числа фичи **не входит** (анти-двойной учёт):
реализуется только при явном решении создателя.
