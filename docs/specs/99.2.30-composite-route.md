## 0. Резюме (одним абзацем)

Вводится **композитный маршрут** — цепочка из двух сегментов полёта: межзвёздный (к системе X,
`/travel`) + внутрисистемный (к объекту P системы X, `/api/intrasystem-flight`), инициируемая
пунктом «🚀 Лететь» контекстного меню канваса (ПКМ по планете/компаньону; у спутника —
кнопка карточки, §6.5) **чужой** системы (решение создателя 1:
«где игрок — там и камера»: клик → модалка закрывается, игрок на основной карте с полосой
перелёта и слежением; по прибытии модалка системы открывается сама и показывает внутрисистемный
сегмент). Механика маршрута — **серверная** (решение 2): сервер хранит **намерение**
«после прибытия в систему X лететь к объекту P» (`users.pending_destination` JSONB, NULL =
намерения нет), по onArrival межзвёздного полёта сам запускает внутрисистемный сегмент
(автостарт — НЕ через POST-хендлер: у POST известен баг — битый from без ИП-4-фолбэка,
идея модалки §8 п.9; у автостарта from всегда = звезда прибытия, битая цель — собственный
фолбэк «орбита звезды» без 400);
намерение переживает рефреш (БД). Разворот маршрута (решение 3): игрок в межзвёздном полёте +
клик «Лететь» к планете другой системы → маршрут разворачивается (61a), намерение новой
системы сохраняется (перезапись). Слежение переключается само (карта ↔ модалка); в скоуп
входит починка бага «Найти меня» при межзвёздном полёте (идея модалки §8 п.10). Пункт «Лететь»
доступен, пока модалка открыта (данные планеты есть, 77a); если игрок уже в этой системе — обычный
внутрисистемный полёт, без изменений (решение 5). Новых чисел баланса нет — только цепочка
существующих сегментов (@balancetester не нужен, идея §5).

## 1. Концепция и термины

**Композитный маршрут** (термин, GLOSSARY-кандидат) — цепочка из двух сегментов полёта к
объекту чужой системы: межзвёздный сегмент (к системе, `/travel`, 66a/61a/97a) + внутрисистемный
сегмент (к объекту системы, `/api/intrasystem-flight`, 99.2.27), инициируемая пунктом
«🚀 Лететь» контекстного меню канваса (ПКМ по планете/компаньону) или кнопкой карточки
спутника (§6.5) чужой системы. Первый сегмент — обычный межзвёздный полёт;
второй запускается сервером автоматически по прибытии (**автостарт**), если сервер хранит
намерение.

**Намерение** (термин, GLOSSARY-кандидат) — серверное состояние игрока «после прибытия в
систему X лететь к объекту P»: `users.pending_destination` JSONB `{world_id, object_type,
object_id}`. NULL = намерения нет. Существует только во время межзвёздного сегмента
композитного маршрута; переживает рефреш (БД) и рестарт сервера (Restore-обработка, §4.5).

**Автостарт** — серверный запуск внутрисистемного сегмента по onArrival межзвёздного полёта.
Серверный (не клиентский POST после прибытия — решение 2 создателя) и НЕ через
`POST /api/intrasystem-flight` (критик, мелкое 2): у POST известен баг (идея модалки §8 п.9) —
при битом ОБЪЕКТЕ ОТПРАВЛЕНИЯ (from) в хендлере старта не применяется ИП-4-фолбэк, игрок
застревает до 400. У нашего автостарта нет from-проблемы (from всегда = звезда прибытия,
живая), а битая ЦЕЛЬ обрабатывается собственной валидацией «объект жив» с фолбэком «орбита
звезды» без 400. «Битая цель → 400» как валидация POST /travel с destination (§3.1) —
корректна, не смешивай с багом идеи модалки §8 п.9 (битый from).

**Объекты системы** — цели внутрисистемного сегмента: планеты (`planet`), спутники
(`satellite`) и компаньоны (`companion`, синтетические id `companion:<world>` /
`extra:<world>:<i>`) — терминология 99.2.27 §1. Звезда чужой системы — цель межзвёздного
«Лететь» без намерения (решение 5). Компаньоны чужой системы — в скоупе (решение создателя
2026-09-21): в 200-модалке (радар/знание — планеты видны) видны на канвасе, ПКМ по компаньону
→ «Лететь» (композитный маршрут, §6.1/§6.5); в 403-модалке компаньонов нет (77a §5.5).

## 2. Сущность «намерение»

### 2.1. Природа сущности (обязательный разбор)

1. **Природа** — результат-состояние игрока («куда я направляюсь после прибытия»), не событие
   и не лог: одна запись на игрока, истории нет, убирается по исполнению/замене/неактуальности.
   → атрибут `users` (JSONB-колонка), аналог `users.current_position` (99.2.27 §2.1 — та же
   природа; архитектурный фильтр идеи §3).
2. **Владелец** — один объект (игрок): одна запись на игрока → атрибут `users`, не таблица.
   Поток записей — это полёты (отдельные таблицы `player_flights`/`player_intrasystem_flights`),
   намерение — текущее состояние (атрибут). Правило «не зажимай поток записей в атрибуты» не
   нарушается.
3. **Расширяемость** — тип один (цель = объект системы: мир + объект); второй тип (например,
   «вернуться к месту после добычи») ложится в ту же JSONB-схему полем `kind` (задел, в этой
   фиче не пишется). Схема переживает второй тип без миграции.

### 2.2. Модель и хранение

`users.pending_destination` — JSONB, NULL = намерения нет (легаси-состояние корректно,
бэкфилла нет):

```json
{ "world_id": "<uuid>", "object_type": "planet"|"satellite"|"companion", "object_id": "<id>" }
```

- `world_id` — система назначения межзвёздного сегмента (== `req.WorldID` на старте /travel).
- `object_type` ∈ {`planet`, `satellite`, `companion`} — эти цели дают композитный маршрут
  (звезда — «Лететь» без намерения, решение 5; компаньон — решение создателя 2026-09-21,
  §1/§3.1/§6.1).
- `object_id` — `planets.id` для planet; id спутника из `planets.data.satellites`
  (UUID, `models.PlanetSatellite.ID`) для satellite (99.2.27 §2.2); синтетический id компаньона
  `companion:<worldID>` (главный) / `extra:<worldID>:<i>` (внешний) для companion (99.2.27
  §3.1). Компаньон есть, только если в `stellar_mods` системы заполнен `companion` /
  соответствующий `extra_companions[i]` (`IsValidCompanionID`).

### 2.3. Согласование (инварианты)

- **ИН-1 (намерение согласовано с полётом):** `pending_destination != NULL` ⇒ активен
  межзвёздный полёт к `pending_destination.world_id` (`flight.ToWorld == world_id`). Намерение
  существует только во время межзвёздного сегмента (идея §4 п.2). Единственное исключение —
  микро-окно автостарта (позиция уже `in_flight`, намерение ещё не очищено, §4.4), закрытое
  фазой 3в Restore-обработки (§4.5).
- **ИН-2 (не сосуществует с позицией):** при `pending_destination != NULL` `current_position`
  = NULL (следствие С1 99.2.27: при межзвёздном полёте позиция NULL; намерение пишется только
  при старте /travel). Намерение не пишется, когда игрок в своей системе.
- **ИН-3 (очистка):** намерение очищается: (а) при исполнении — автостарт запущен, в любом
  исходе (успех / провал из-за двигателя / битая цель, §4.3–4.4); (б) при любом `/travel`-старте
  без объекта цели (M1, §3.3); (в) при перезаписи новым намерением (разворот 61a с объектом,
  решение 3, §3.4); (г) при пакмане-съедении мира-цели (M3, §5); (д) при Restore-обработке:
  нет активного межзвёздного полёта к `world_id` — включая случай активного внутрисистемного
  полёта без межзвёздного («призрак», §4.5 фаза 3в); (е) при дефенсиве onArrival (мир съеден,
  §4.2).
- **ИН-4 (атомарность со стартом /travel):** запись/очистка намерения на пути старта — одной
  транзакцией с отменой внутрисистемного полёта и позицией NULL (расширение `CancelAtomic`,
  §3.2); на 202-идемпотентном пути — отдельный UPDATE (полёт уже идёт, позиция уже NULL, §3.5).

## 3. Дельта `POST /travel`

### 3.1. Тело: необязательное поле `destination`

```json
{ "world_id": "<uuid>", "destination": { "object_type": "planet"|"satellite"|"companion", "object_id": "<id>" } }
```

Валидация `destination` (только если поле присутствует; порядок после существующих валидаций
двигателя/цели):
1. `object_type` ∈ {`planet`, `satellite`, `companion`} — иначе 400 «Некорректный тип объекта
   назначения». Звезда (`star`) целью `destination` НЕ является (простой «Лететь» без
   намерения, решение 5).
2. `object_id` непустой.
3. Объект принадлежит системе `world_id` (планета с `world_id == req.WorldID`; спутник в
   `satellites` планеты этой системы; компаньон — по `stellar_mods` системы,
   `IsValidCompanionID`) — иначе 400 «Объект не найден в системе назначения».
   Источник planet/satellite — `GetPlanetsLightByWorldID` (тот же, что модалка 99.2.27 §4.4);
   компаньона — `worldRepo.GetByID` (мир со `stellar_mods`): клиент кликает по объекту,
   который модалка уже отдала; битая/чужая цель (перегенерация между модалкой и кликом)
   → честный 400, модалка обновится по refreshPlanets.

### 3.2. Запись намерения (основной путь, старт)

Расширение `PlayerIntrasystemFlightRepository.CancelAtomic` → `CancelAtomicWithDestination
(userID, dest)`: **одна транзакция** — DELETE строки `player_intrasystem_flights` +
`UPDATE users SET current_position = NULL, pending_destination = $dest` (ИН-4). Намерение
пишется атомарно со стартом /travel; окно «намерение без полёта» (краш между транзакцией и
StartFlight) закрыто Restore-обработкой (§4.5). Порядок в `StartTravel` (как сейчас, §4.2
99.2.27): транзакция (intra-строка + позиция NULL + намерение) → in-memory отмена intra →
`StartFlight`.

### 3.3. Очистка при старте без объекта (M1)

На обычном `/travel` (без `destination`) `CancelAtomic` получает дельту: `pending_destination =
NULL` в той же транзакции (позиция NULL + отмена intra + очистка намерения). Иначе намерение
{X, P} висит весь полёт к Z (нарушение ИН-1 «намерение только в сегменте») и переживает
редирект к той же системе X — игрок явно «перелетел» к звезде, а сервер потащит к P.

### 3.4. Разворот 61a с намерением (решение 3)

Игрок в межзвёздном полёте + `/travel` с `destination` {Y, Q} → редирект (существующий путь,
точка P, 61a) + `CancelAtomicWithDestination(userID, {Y, Q})` — перезапись намерения атомарно
со стартом нового сегмента (ИН-3в). Разворот без `destination` → очистка (M1, §3.3).

### 3.5. 202-идемпотентный путь (M2)

Полёт к `req.WorldID` уже идёт (`flight.ToWorld == req.WorldID`, существующая ветка 202):
- с `destination` → валидация объекта (§3.1) + `UPDATE users SET pending_destination = $dest
  WHERE id = $uid` — намерение записывается и на 202-пути (иначе игрок прилетит к звезде, хотя
  кликнул «Лететь»);
- без `destination` → `UPDATE users SET pending_destination = NULL WHERE id = $uid` (игрок явно
  «перелетел» к звезде).

Полёт не перезапускается (202, без сброса прогресса — существующее поведение).

## 4. Автостарт по onArrival межзвёздного полёта

### 4.1. Место

onArrival-колбек межзвёздного полёта (`travel_handlers.go:228-242`). После существующего
`UpdateCurrentWorldAndPosition(uid, worldID, StarOrbitPosition(worldID))` (ИП-2 99.2.27:
прибытие → позиция «орбита звезды», атомарно с current_world_id) — чтение `pending_destination`:
- NULL → обычное прибытие (ничего не меняется);
- `world_id != worldID` (дефенсив, не должно случаться — намерение пишется только для цели
  полёта) → очистить намерение;
- `world_id == worldID` → автостарт (§4.3).

### 4.2. Дефенсив мира

Мир `worldID` съеден (пакман/перегенерация) — существующая ветка `ClearCurrentWorld`
(`worldRepo.GetByID == nil`) → дополнительно очистить намерение (ИН-3е). Основную очистку
делает пакман (§5); здесь — страховка от гонки «пакман съел между запросом и прибытием».

### 4.3. Автостарт (серверный, НЕ через POST-хендлер)

Автостарт НЕ идёт через POST-хендлер: у POST известен баг (идея модалки §8 п.9) — при битом
ОБЪЕКТЕ ОТПРАВЛЕНИЯ (from) в хендлере старта не применяется ИП-4-фолбэк, игрок застревает до
400. У нашего автостарта нет from-проблемы (from всегда = звезда прибытия, живая), а битая
ЦЕЛЬ обрабатывается собственной валидацией «объект жив» с фолбэком «орбита звезды» без 400.
«Битая цель → 400» как валидация POST /travel с destination (§3.1) — корректна, не смешивай
с багом идеи модалки §8 п.9 (битый from).

Валидация ДО старта:
1. **Объект жив:** `planet`/`satellite` — `arrivalTargetValid(planetRepo, worldID, object_type,
   object_id)` (существующий хелпер, `intrasystem_handlers.go:305`: планета существует и
   `world_id` совпадает / спутник найден); `companion` — `IsValidCompanionID(world, object_id)`
   по `stellar_mods` системы (99.2.27 §3.1). Битая цель → фолбэк «орбита звезды» (позиция уже
   выставлена), намерение очищается, **БЕЗ 400** (критик, мелкое 1 — формулировка идеи §3).
2. **Двигатель** (91a §6.1): `role=player` без `ship.HasEngine` → автостарт НЕ запускается,
   намерение очищается, позиция остаётся «орбита звезды» (критик, мелкое 3 — иначе
   намерение-призрак висит до следующего /travel). Админ/skycomposer — исключение.
3. Межзвёздный полёт завершён (мы в onArrival) — внутрисистемный старт не конфликтует (И3
   99.2.27).

Старт (паттерн 99.2.27 §3.2/§4.1, атомарность С-1): `intraRepo.StartAtomic(flight{world_id,
from: star/worldID, to: объект}, InFlightPosition(star, worldID, object_type, object_id, now,
arrive_at))` + `intraManager.StartIntraFlight(...)` с `NewIntraArrivalHandler` (существующий
колбэк — авто-знание presence при прибытии к планете, 99.2.27 §3.6; **повторно не
реализуется**, идея §4 п.7). На границе (внутрисистемный слой) `companion` транслируется во
внутрисистемное представление `object_type='star'` + синтетический id (так его понимают
`objectRadiusAU`, `InFlightPosition`, `onArrival`, `my_position`): в `player_intrasystem_flights`
и `current_position` пишется `to_type='star'`. Длительность — `CalcIntraDuration(dist, sf)` от
звезды (позиция прибытия = орбита звезды; dist = |0 − r(объекта)|, §3.4 99.2.27).

### 4.4. Очистка намерения

В любом исходе автостарта (успех, битая цель, двигатель снят) — `UPDATE users SET
pending_destination = NULL`. Очистка — после StartAtomic (окно «intra активен + намерение ещё
стоит» — микроскопическое, закрыто фазой 3в Restore-обработки §4.5; ИН-1 допускает это окно).

### 4.5. Порядок Restore (паттерн 97a/99.2.27, закрывает С-1 и намерение-призрак)

1) Restore межзвёздных полётов (97a, onArrival для прибывших: позиция «орбита звезды» +
   существующая запись текущего мира);
2) Restore внутрисистемных полётов (99.2.27: перерегистрация из `player_intrasystem_flights` —
   сторона внутрисистемного менеджера, НЕ трогает намерения);
3) обработка намерений (после фаз 1–2): для каждого игрока с `pending_destination != NULL`:
   а) нет активного межзвёздного полёта к `world_id` И объект жив (валидация §4.3.1) →
      **автостарт** (StartAtomic + StartIntraFlight; намерение — через существующую ветку
      «исполнение», §4.4); старт выполняется ПОСЛЕ внутрисистемного Restore — двойной
      регистрации одного полёта нет;
   б) нет активного межзвёздного полёта к `world_id` И объект бит (или двигатель снят) →
      очистить намерение, позиция «орбита звезды» (фолбэк, §4.3);
   в) нет активного межзвёздного полёта к `world_id` И уже есть активный внутрисистемный
      полёт в `world_id` → **очистить намерение** (микро-окно «StartAtomic → UPDATE NULL»
      после рестарта: исполнение уже произошло, намерение — призрак; прежняя формулировка
      с «И нет внутрисистемного полёта» оставляла призрак жить);
   г) есть активный межзвёздный полёт к `world_id` → намерение живёт (автостарт по прибытии);
   д) мир `world_id` съеден/удалён → очистить (в т.ч. дефенсив §4.2).
Стоимость — O(игроки с намерением) — инвариант 2 проекта держится (И8).

## 5. Дельта пакмана (M3)

В `eatPacmanBatchOnce` (`admin_pacman.go`), новый шаг (после шага 4 — DELETE
`player_intrasystem_flights`, до удаления миров):

```sql
UPDATE users SET pending_destination = NULL
WHERE (pending_destination->>'world_id')::uuid = ANY($1)
```

Игрок с намерением к съеденному миру летит из другой системы — шаг 1 (`current_world_id =
ANY($1)`) его не трогает, нужен отдельный UPDATE. Каст `(…)::uuid`: `->>` даёт text, в $1 —
массив uuid; без каста `text = ANY(uuid[])` может не скомпилироваться в PG. Счётчик в отчёт
не добавляется (намерение — состояние, не сущность отчёта). Плюс дефенсив onArrival (§4.2)
как страховка от гонки.

### 6.2. Блокировка при активном межзвёздном (критик, мелкое 4)

В модалке системы, где `my_position` нормализован (система отправления: `current_world_id ==
worldId`, `current_position == NULL` → `my_position` = «орбита звезды», ИП-4-нормализация
99.2.27 §4.4), внутрисистемный старт при активном межзвёздном полёте
(`modalState.interstellarFlight != null`, из `/me.flight`, index.js:87) недоступен (иначе
старт даст 400 «Вы в межзвёздном полёте», валидация 3 §4.1 99.2.27): у планеты/компаньона
пункт ПКМ-меню **скрыт**, у спутника кнопка **disabled** (§6.6). Композитный пункт/кнопка
чужой системы при межзвёздном — НЕ блокируется (это `/travel` 202/редирект, работает,
§3.4/§3.5).

### 6.3. Автооткрытие модалки по прибытии + распознавание автостарта (M5)

- `/me` получает аддитивное поле `pending_destination` (JSONB или null; 99.2.27 §4.3 —
  аддитивные поля, существующие не меняются).
- Клиент карты на прибытии (animationLoop → `loadUserData(true)`, 42a-паттерн): после обработки
  `flight`, если `user.current_position.status === 'in_flight'` ИЛИ `user.pending_destination`
  (world_id == current_world_id) → **автооткрыть модалку системы** (`openSystemModal`). Модалка
  покажет полосу полёта из `my_position` (`status=in_flight`, 99.2.27 §5.7) — распознавание
  автостартовавшего сегмента после рефреша (M5: `me.flight` уже null, `current_position` уже
  `in_flight` — клиент НЕ решает «полёт просто закончился»).
- **Гонка таймеров** (клиентский таймер раньше серверного onArrival): `/me` может вернуть
  `flight=null`, `pending_destination` ещё не очищен, `current_position` ещё null — автооткрытие
  по `pending_destination` срабатывает; модалка подхватит старт intra своим refresh
  (`my_position` → `in_flight`). Крайне узкое окно (намерение уже очищено, позиция ещё null) —
  повторный `/me`-чек через короткую паузу — формализован @uidesigner (§6.8: разворота
   гонки в обе стороны, ~1 с, конвергентно).
- Автооткрытие — только на странице карты; в админке/свёрнутой вкладке — при возврате
  (открытый вопрос идеи §8 п.1; модалка восстановит полосу из `my_position`).

### 6.6. Доступность (решения @uidesigner + создателя 2026-09-21)

- **Пункт «🚀 Лететь» ПКМ-меню** (планета, компаньон) показан, только если модалка открыта на

- **Пункт скрыт** (своя система), если: игрок уже на орбите этой планеты/компаньона; это цель
  текущего полёта (`to_*`); летим ОТ неё (`from_*`); при активном межзвёздном полёте (иначе

- **Без двигателя** (`!modalState.hasEngine`, 91a): пункт ЕСТЬ (как ПКМ звезды), клик даёт тост
  «Двигатель не установлен — полёт невозможен» (та же формулировка, что у существующих точек
  полёта). Сервер валидирует тоже (админ/skycomposer — исключение).
- **Кнопка спутника** (точка входа осталась, §6.5) сохраняет существующее поведение: disabled
  при `!modalState.hasEngine` (тултип «Двигатель не установлен — полёт невозможен»), при
  активном межзвёздном (тултип «Вы в межзвёздном полёте — дождитесь прибытия»), при «уже на
  орбите / цель полёта / летим от неё»; защита от двойного клика (disabled на время запроса);

- В админке (модалка по adminToken, карты нет): ПКМ-меню канваса работает так же (канвас есть
  в модалке); слежение карты недоступно, карта восстановится по возврату (42a).

### 6.7. Стык «карта ↔ модалка»: старт композитного (решение @uidesigner)

Что видит игрок после клика «🚀 Лететь» (композитный: планета/компаньон — ПКМ-меню, спутник —
кнопка карточки; §6.5) — поток A, решение 1:

1. Пункт меню сразу скрывается (`hideStarMenu`), кнопка спутника — disabled на время запроса
   (~1–2 с, защита от дубля).
2. `/travel` успех → модалка закрывается (тот же паттерн, что простой межзвёздный «🚀 Лететь»
   по звезде — `startTravelToStar`, но с телом `{world_id, destination}` — расширение `startFlight`).
3. Карта: существующая панель полёта в шапке — «В полёте: <From> → <To>», полоса прогресса,
   таймер (`showFlightPanel`/`showFlightLabel`, 61a/42a) — **без изменений**.
4. **Камера ведёт корабль (новое для старта из модалки):** после успешного старта клиент
   включает слежение так же, как кнопка «🎯 Найти меня» карты (`centerBtn`): `followShip =
   true`, `sessionStorage.followShip = '1'`, `centerOnAgent()` (центр на корабль по
   маршруту), подсветка centerBtn — всё существующая логика карты (`events.js:515-525`),
   ничего не дублируется.
   - **Факт из кода, который фиксирую:** сейчас простой межзвёздный «🚀 Лететь» по звезде
     (бывш. «Перелететь») из модалки камеру НЕ включает (startFlight не трогает followShip) —
     после него игрок остаётся на прежнем виде. **Рекомендация на гейт:** включить те же
     follow-действия для обоих выходов из модалки в полёт (один общий хелпер «вернулся на
     карту в полёте») — иначе соседние точки полёта («🚀 Лететь» по звезде и композитный)
     ведут камеру по-разному. Если создатель хочет строго «без изменений» для простого
     межзвёздного — композитный всё равно включает слежение (решение 1).
5. Ошибка старта: модалка остаётся открытой, тост с текстом сервера, ничего не закрываем.

### 6.8. Автооткрытие по прибытии + распознавание автостарта (M5; решение @uidesigner)

**Явный переход, а не «полёт просто закончился»:** для клиента прибытие по композитному
маршруту — отдельное событие «прибыл + маршрут продолжается», распознаваемое по трём
серверным признакам (проверяются в порядке следования):

1. `pending_destination` в `/me` и `pending_destination.world_id == current_world_id`
   (намерение пережило клиентский таймер — гонка §6.3, сервер ещё не автостартовал);
2. `current_position.status == 'in_flight'` (автостарт уже запущен сервером);
3. **сессионный маркер** `sessionStorage.compositeRoute == world_id` (намерение уже
   исполнено — автостарт идёт или завершён, а клиент вернулся на карту с задержкой).

Маркер пишется при успешном композитном старте (вместе со слежением, §6.7); стирается:
при автооткрытии (после потребления); при успешном старте обычного межзвёздного «🚀 Лететь»
по звезде (игрок
явно ушёл от маршрута, M1); если `current_world_id` не совпал. Переживает рефреш и переход
в админку (sessionStorage той же вкладки).

**Триггеры автооткрытия (страница карты):**
- **A. Живое прибытие:** ветка прибытия `animationLoop` (elapsed ≥ duration →
  `loadUserData(true)`, 42a-паттерн) — после обработки `flight` проверить признаки 1–3
  для `current_world_id` прибытия.
- **B. Возврат/рефреш:** инициализация карты (первый `loadUserData`) — проверить признаки
  2–3 (маркер / in_flight), если `current_world_id` совпал (случай «ушёл в админку или
  свернул вкладку, вернулся после автостарта»).

Если модалка уже открыта на другой системе — закрыть её (игрок физически в системе
прибытия, «камера там, где игрок», решение 1), затем открыть модалку системы прибытия
(`openSystemModal`). Если модалка уже открыта именно на системе прибытия — не
переоткрывать, только `refreshPlanets()`.

**Что видит игрок при автооткрытии:**
- модалка появляется с существующей анимацией fadeIn (0.2 с);
- сразу видна полоса внутрисистемного полёта «🚀 Полёт: <система> → <планета> · осталось
  N сек» (существующая полоса из `my_position` in_flight, 99.2.27 §5.7 — из «орбиты
  звезды», куда прибыл игрок, на объект-цель);
- карточка цели выбрана: `focusOpts` из `current_position.to_type/to_id` (планета →
  `planetId`; спутник → `satelliteId`); если позиция уже `orbit` (успел долететь за время
  отсутствия) — фокус на объекте позиции;
- камера модалки ведёт корабль (существующее слежение, `followEnabled` вкл по умолчанию);
- тост «🚀 Прибыли в систему <X>» + существующий статус-бар карты «✅ Прибытие!».

**Тост (закрывает открытый вопрос §11 п.3): показать.** Сценарий «наблюдал полёт с карты» —
модалка сама по себе понятна, тост дублирует, но не мешает; сценарий «вернулся со
свёрнутой вкладки/из админки» — тост объясняет, почему карта вдруг под модалкой. Стиль —
существующий `notifyInfo`, без кнопок, ~4 с.

**Гонка таймеров (клиентский раньше серверного onArrival):** автооткрытие по одному
признаку 1 (намерение есть, позиция ещё не in_flight) — модалка подхватит старт своим
`refreshPlanets()` (`my_position` станет in_flight, полоса появится). Если через ~1 с
полоса не появилась (позиция всё ещё не in_flight) — **повторный `/me`-чек**, при
`current_position.status == 'in_flight'` → `refreshPlanets()`. Одноразово, конвергентно:
крайнее окно захлопывается за ≤ 2 циклов (деталь реализации — @developer, контракт выше).

**Крайний случай — мир съеден (пакман) за межзвёздный сегмент:** намерение очищено
сервером (§5), признаков 1–2 нет, маркер не совпал (мир исчез) → автооткрытия нет, игрок
видит обычное поведение после перегенерации.

### 6.9. «Найти меня» при межзвёздном (решение @uidesigner)

- **Условие:** `modalState.interstellarFlight != null` ИЛИ `mapState.isFlying` — импорт
  `map/config.js` динамический, только на странице карты (в админке import-граф карты не
  тянется — фолбэк просто закрыть модалку, §6.4).
- **Что видит игрок после клика 🎯 при межзвёздном:** модалка закрывается; карта под ней —

- **И7 (не-регрессия):** `/travel` (66a/61a/97a), `player_flights`, внутрисистемный полёт

- **И9 (не-регрессия 77a):** видимость/знание не меняются; авто-знание presence при прибытии к

- **«Найти меня» при межзвёздном не срабатывает** (клик до резолва /me) → фикс §6.4

Правило «каждое задание = +1 предложение новой ГД-сущности» (создатель 2026-09-14).
Кандидат по теме фичи (композитный маршрут / полёт к планете):

**Вопрос:** нужны ли **контракты с планетарной точкой доставки** — контракты на перевозку/
поставку, чья точка сдачи — конкретная планета (не только система)? Композитный маршрут делает
их исполнимыми из любой точки галактики: долетел до системы (межзвёздный сегмент) → сегмент к
планете → сдача → возврат.
**Ответ (эталон создателя):** не задан — открытый вопрос (счётчик FAQ +1 при разносе).

Почему повышает игровой интерес: петля «контракт → полёт → добыча → сдача» (вектор «Игрок»)
получает планетарную точность — планеты-цели становятся экономическими точками (сдача у
планеты, а не у звезды), композитный маршрут получает содержательное применение (не только
«долетел посмотреть»). Цена: контракты — будущая система (11.3), планетарная точка доставки —
расширение её модели. В текущие числа фичи **не входит** (анти-двойной учёт): реализуется
только при явном решении создателя.
