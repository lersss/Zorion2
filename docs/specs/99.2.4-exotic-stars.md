## 1. Цель и скоуп

Реализовать распределение типов систем и объектов, заявленное в `02_worlds.md`
§2.1 (сейчас в коде только обычные спектральные классы O–Y), через **три
ортогональных слоя** — по финальному списку §4ж идеи 29a. Экзотика идёт
**явными ветками** со своей физикой; общий путь O–Y и §99.2.11 не трогаются.
Численные дефолты — из ревизии астронома (§4е) и решений менеджера (§4ж, §4и).

**В скоупе:** модель и хранение (разделы D, A), распределения, физика экзотики,
генерация объектов в экзотических системах, аудит-гейты, статистика админки,

**НЕ в скоупе:** §99.2.11 (переворот «физика → архетип» в общем пути O–Y);

профилями регионов §99.2.10); сверхновые, туманности, скопления (решение
астронома §4г — не добавлять).

## 2. Модель: три ортогональных слоя

| Слой | Поле | Значения | Природа |
|---|---|---|---|
| Тип системы | `system_type` | `single` / `binary` / `multiple` | структура: сколько тел |
| Тип объекта | `star_type` | `star` / `white_dwarf` / `neutron` / `black_hole` / `protostar` | природа центрального тела |
| Модификаторы | `stellar_mods` (JSONB, nullable) | см. §4 | редкие особые свойства |

Терминология (элементарная, в `GLOSSARY.md` не дублирую): **«обычная звезда»** —
объект со спектральным классом O–Y (включая субзвёздные L/T/Y как классы игры,
флаг `star`); **«экзотика»** — `star_type ≠ star`; **«остаток»** — ЧД/НЗ/WD как
результат эволюции обычной звезды; **«прочая экзотика»** — сверхгиганты горячих
классов (фаза I, см. §4.4).

Модификаторы — четыре группы (ортогональны друг другу):

1. **Эволюционная фаза** `phase`: `V` (главная последовательность) / `III`
   (гигант) / `I` (сверхгигант). Только для `star`. Решает «красных гигантов»
   (решение §4д.3) и даёт законный гейт пульсирующим переменным.
2. **Переменность** `variable_type`: `eclipsing` / `mira` / `cepheid` / `uv_ceti`
   / `t_tauri` / `nova` / `dwarf_nova`; сопутствующие `variable_period_days`,
   `variable_amplitude` (nullable). Анимаций мерцания нет — бейдж (решение
   §4в.4б).
3. **Подтипы объекта** `subtype`: `pulsar` / `magnetar` (на `neutron`),
   `accretion` (на `black_hole`), `lbv` / `wr` (на `star` фазы I, «прочая
   экзотика»).
4. **Параметры системы** `binary_type` (`wide`/`close`), `companion` (спектр/
   тип компаньона), `disk_state` (`protoplanetary`/`accretion`/`debris`),
   `stellar_mass` (M☉, тип float, nullable — заполняется у экзотики и «прочей
   экзотики»; у обычных звёзд NULL, общий путь не трогаем), `metallicity`
   (nullable, аналогично).

> **Почему модификаторы одним JSONB `stellar_mods`, а не колонками**
> (разворот подходов, решение дизайнера): (а) по-колоночно — 6–8 nullable-
> колонок, ни одна не нужна в WHERE по отдельности; (б) JSONB — открытый пакет:
> новый модификатор это добавка в JSON, не миграция; (в) паттерн уже есть в
> проекте — `planets.data` JSONB. Цена: фильтр «все пульсары» — через
> `stellar_mods->>'subtype'`, чуть менее явно. Платим осознанно: таких запросов
> нет ни в API, ни в админке. Жёсткие слои (`system_type`, `star_type`) —
> колонками: нужны статистике, снапшоту карты, будущим фильтрам.

## 3. Хранение и миграция

**Решение: отдельные поля на `worlds`** (не расширение `spectral_class`):

- Ревизия §4а п.10 требует `star_type` отдельным полем. Расширение класса
  дало бы «ЧД с классом X» в `luminosityBySpectral('X')` → запрещённый fallback
  «как Солнце» (L=1.0, T 5200–6000) либо ветвления в каждом потребителе класса.
- `spectral_class` — свойство атмосферы обычной звезды; у ЧД/НЗ/WD его нет, у
  протозвезды он ещё неопределён. Экзотика пишет **NULL** (колонка `TEXT
  DEFAULT 'G'`, NOT NULL не наложен — NULL уже допустим схемой 006).

Миграция `migrations/000030_add_stellar_types.sql` (+ `.down.sql`, шаблоны
up/down по образцу соседних; применяется автоприменением при старте, `docs/DB.md`):

```sql
ALTER TABLE worlds ADD COLUMN system_type TEXT NOT NULL DEFAULT 'single';
ALTER TABLE worlds ADD COLUMN star_type   TEXT NOT NULL DEFAULT 'star';
ALTER TABLE worlds ADD COLUMN stellar_mods JSONB;
ALTER TABLE worlds ADD CONSTRAINT worlds_system_type_check
  CHECK (system_type IN ('single','binary','multiple'));
ALTER TABLE worlds ADD CONSTRAINT worlds_star_type_check
  CHECK (star_type IN ('star','white_dwarf','neutron','black_hole','protostar'));
COMMENT ON COLUMN worlds.system_type  IS 'Тип системы: single/binary/multiple';
COMMENT ON COLUMN worlds.star_type    IS 'Тип объекта: star/white_dwarf/neutron/black_hole/protostar';
COMMENT ON COLUMN worlds.stellar_mods IS 'Модификаторы: phase, variable_type, subtype, binary_type, disk_state, companion, stellar_mass, metallicity и пр. (открытый пакет)';
```

**Совместимость со старыми данными:** дефолты миграции — все существующие миры
становятся `system_type='single'`, `star_type='star'`, `stellar_mods=NULL`; их
`spectral_class` уже хранит реальный класс O–Y. Маппинг старых строк не нужен —
дефолты и есть их фактическое состояние. Обратная совместимость категории
«ЧД» с классом: категория появляется только при новой генерации.

**Потребители, которых затронет чтение NULL-спектра** (точечно, хирургично):

- `internal/handlers/admin_stats_load.go` `loadWorlds` — `Scan(&w.SpectralClass)`
  на NULL упадёт, строка молча выпадет из статистики → читать
  `COALESCE(spectral_class,'')` + `star_type` (см. §7).
- `internal/generator/planet/` — `WorldInfo` получает `StarType`/`SystemType`/
  `StellarMods`; `determinePlanetCount`/`determineSystemAge`/`gasGiantChance`
  вызываются новой обёрткой с ветвлением по `star_type` (§5). Существующий
  switch по классам не трогается.
- `internal/mapcache/snapshot.go` — в снапшот добавляются `system_type`,
  `star_type`, `stellar_mods` (бейджи карты/модалки, §8).
- `web/static/js/map/…`, `web/static/js/modal/…` — данные из снапшота, цвета из §8.

## 4. Распределения (дефолтные веса)

Источник: §4ж (решения менеджера, эталон). Веса — конфиг генерации звёзд,
редактируется в админке (спека 99.2.3 §4). Здесь — дефолты и семантика.

### 4.1. Типы систем и объектов (сумма весов = 100)

| Ключ | Значение | Вес | Доля |
|---|---|---|---|
| `single` | одиночная обычная звезда | 85 | 85% |
| `binary` | двойная обычная | 5 | 5% |
| `multiple` | кратная (3+) обычная | 2 | 2% |
| `black_hole` | чёрная дыра | 1 | 1% |
| `neutron` | нейтронная звезда | 1 | 1% |
| `white_dwarf` | белый карлик | 2 | 2% |
| `protostar` | протозвезда | 1 | 1% |
| `exotic` | прочая экзотика (сверхгиганты) | 3 | 3% |

Порядок генерации:
1. Ролл по §4.1 (веса → категория).
2. `single`/`binary`/`multiple` → спектральный класс по существующим
   `spectralWeights` (O–Y, относительные доли не меняются), температура —
   существующий `randomTemperature`. Затем ролл модификаторов §4.3.
3. Экзотика — своя ветка параметров (§5), спектр NULL.

Проверка сходимости с `02_worlds.md` §2.1 (85+5+2+1+1+1+5): «экзотическая ~5%»
трактуется как белый карлик ~2% + прочая экзотика ~3% (решение §4ж.4в.1).

### 4.2. Спектральные веса O–Y

Как сейчас (`internal/generator/galaxy/galaxy.go`, `spectralWeights`) — **не
меняются**.

### 4.3. Модификаторы: гейты и вероятности (редкие)

фичи (в админку блок весов модификаторов не выводим — §4и его не заказывал;
отмечено как будущее в 99.2.3 §7).

| Модификатор | Гейт (обязательное условие) | Шанс от популяции гейта | Примечание |
|---|---|---|---|

| `phase I` | `star` + класс F–K | 1% | база цефеид |

| `cepheid` | `star` + `phase I` + F–K | 25% от популяции I | стандартная свеча; `variable_period_days` 1–50 |

| `t_tauri` | `star_type` = protostar | 50% | параметр молодости, связь с диском |
| `subtype pulsar` | `star_type` = neutron | 60% | вращающийся радиопульсар |
| `subtype magnetar` | `star_type` = neutron | 5% | поля 10¹⁴–10¹⁵ Гс, редкая подгруппа |
| `subtype accretion` | `star_type` = black_hole | 10% | микроквазар; диск §5.4 |
| `subtype lbv` / `wr` | `exotic` (сверхгигант O–B) | 10% / 10% | внутри «прочей экзотики» |

### 4.4. Состав «прочей экзотики» (закрывает открытый вопрос №3 из 99.2.4-идеи)

**Решение дизайнера (подтвердить на гейте создателем):** «прочая экзотика ~3%»
= **сверхгиганты горячих классов** — `star` O−B−A с принудительной `phase I`,
`stellar_mass` 10–60 M☉, подтипы `lbv`/`wr` с шансами таблицы. Это не новый тип
объекта, ложится на модель (star + фаза + подтипы) и даёт «боссов среди звёзд»
из `start types.md` §2.4 без новой сущности. Альтернативы астронома (звёздные
скопления, семантика видимости НЗ) не входят — решение §4г и скоуп §1.

## 5. Физика экзотики

Правило №1: **экзотика никогда не попадает в `luminosityBySpectral` с
неизвестным классом.** Для неё отдельная ветка задаёт **фиксированные
температуры по типу объекта** (WD: кламп ≥25 K; ЧД/НЗ: фикс. диапазоны §5.3)
ДО общего пути; `luminosityBySpectral` и её существующий fallback
(закреплён тестами `physics_test.go`) остаются нетронутыми. Fallback «ЧД как
Солнце» (L=1.0, T 5200–6000) **запрещён** (решение §4д.4).

### 5.1. Светимость и температура объекта (порядки, §4е астронома)

| Тип | L (L☉) | T (K), витрина мира | Примечание |
|---|---|---|---|
| WD | 10⁻²–10⁻⁴ | 5000–30000 | светит остаточным теплом |
| Нейтронная | 0.01–1 | 10⁵–10⁶ | радиус ~10 км, поверхность горячая |
| ЧД без аккреции | **0** | **0** | тёмная, фотосферы нет |
| ЧД с аккрецией | диск 10²–10³ | диск 10⁵–10⁷ | свет — от диска, не от ЧД |
| Протозвезда | 1–10² | 3000–4000 | аккреционный нагрев |
| K III (красный гигант) | **10²** | 4500–5200 | абсолют (эталон астронома §4г: гигант-фаза K) |
| M III (красный гигант) | **10²–10³** | 3000–4000 | абсолют (M V = карлик, M III = гигант, §4г) |
| F–K фаза I (сверхгигант, цефеида) | **10³–10⁴** | 5000–7000 | абсолют (цефеидная полоса); не «субгигант» |
| `exotic` (O–B, фаза I) | 10⁴–10⁶ | 15000–40000 | LBV/WR — верх порядка |

T для `worlds.temperature`: WD/протозвезда — честные значения из таблицы; ЧД
без аккреции — 0 (UI показывает «тёмная», §8); нейтронная — 10⁵–10⁶ (INT
помещается). Точные константы кусков L — на проверку @balancetester (§13).

### 5.2. Число планет по типу звезды (конфиг, дефолты — физический реализм)

Источник: §4е; §4и.3 заменил крутилку-коэффициент §4з на **средние по типу**.
Механика целого счёта: `n = floor(mean) + Бернулли(frac)` (mean из таблицы
ниже), потолок 8 — не меняем (Kepler-90 = 8, решение §4е). «Чаще 0» у остатков
— автоматически: mean 0.1 → P(0) = 90%.

| Тип | mean (планет) | Комментарий |
|---|---|---|
| O, B | 0.3 | замена текущего 0–8 (среднее 4) — см. гейт ниже |
| A | 1 | |
| F, G | 6.5 | солнцеподобные: типично 5–7, до 8 (потолок) |
| K | 5.5 | |
| M | 5.5 | |
| L, T, Y | 1 | |
| ЧД | 0.1 | далёкие каменистые, орбиты 10–12; максимум генератора 1 |
| Нейтронная | 0.05 | пульсарные планеты редки; максимум генератора 1 (PSR B1257+12 с 3 планетами — реальный сверхредкий случай, не моделируется) |
| WD | 0.3 | выжившие далёкие (орбиты 5–8, расширены в 4–8×); максимум генератора 1; + `disk_state='debris'` (пояс, не планеты) |
| Протозвезда | 0 | `disk_state='protoplanetary'` — диск вместо планет (будущее ~1–3) |
| Двойная широкая | ×0.9 к счёту главной | S-тип (планеты у главного компонента) |
| Двойная тесная | mean 0.2 | P-тип редок (Kepler-16/47); S-типа почти нет |
| Кратная (3+) | ×0.9 к счёту главной | wide-семантика: S-тип у главного компонента; отдельной ветки генерации нет |
| Прочая экзотика (сверхгиганты O–B–A) | 0.1 | у короткоживущих гигантов планеты редки; максимум 1 |

> **Вилки «0–2»/«0–3» у остатков (ЧД/НЗ/WD) — наблюдаемый диапазон астронома
> (§4е), не mean и не обещание генератора.** Механика `floor + Бернулли` при
> mean < 1 даёт n ∈ {0, 1}: верхний предел генератора — **1 планета**, «чаще 0»
> сохраняется (P(0) = 1 − mean). Случаи вроде PSR B1257+12 (3 планеты) —
> вне достижимости генератора осознанно: моделировать их при mean 0.05 значило
> бы ломать «чаще 0» (для достижимой тройки нужен mean ≥ 2, что противоречит
> вилке).

**Гейт по изменению баланса O–Y (осознанный, нужно «ок» создателя):** дефолты
меняют среднее число планет обычных звёзд с текущих игровых (O/B/A 4, F/G 5,
K/M 3, L/T/Y 2 — `03_planets.md` §3.1) на физические §4е. Это явное требование
§4и.3 («дефолты — физический реализм; скучно — создатель подкрутит вверх»),
поэтому число планет O–Y правится в этой фиче; прочие балансы O–Y и §99.2.11
не трогаются. **Честное средневзвешенное по ВСЕМ типам систем (§4.1 веса):**

- одиночные обычные (85%): Σ спектр. вес × mean = 0.5%·0.3 + 2%·0.3 + 4%·1 +
  7%·6.5 + 12%·6.5 + 17%·5.5 + 32%·5.5 + 8%·1 + 8%·1 + 9.5%·1 ≈ **4.23**
- двойные (5%): 75% wide ×(0.9·4.23) + 25% close ×0.2 ≈ 3.0
- кратные (2%): 0.9·4.23 ≈ 3.81
- экзотика (8%): ЧД 0.1, НЗ 0.05, WD 0.3, протозвезда 0, прочая 0.1

Итого: 0.85·4.23 + 0.05·3.0 + 0.02·3.81 + 0.01·0.1 + 0.01·0.05 + 0.02·0.3 +
0.01·0 + 0.03·0.1 ≈ **3.8 планеты/систему** (было ≈1.78; mean O–Y подняты
2026-09-21, реализм распределения — 8 планет дефолтами не достигается, только
множителями/конфигом админки, спека 99.2.3 §4.3). Не-регрессии: старая галактика
не перегенерируется автоматически, дельту видит только новая генерация.

### 5.3. Генерация планет (ветки экзотики)

Общий путь `generatePlanet(...)` — для обычных звёзд как сейчас (включая
гигантов, океанические, радиоактивные). Экзотика — отдельная
`generateExoticPlanet(starType, diskState, orbitIndex, ...)`:

| Тип | Что генерируется | Параметры планет |
|---|---|---|
| ЧД | mean 0.1 далёких каменистых (0–1, индексы орбит 10–12); аккреционный диск — флаг, НЕ планета | T 30–80 K (тёмная, фоновый нагрев), вода 0, жизнь 0, композиция каменистая/кратерная, ярлык архетипа «холодный», settleable=false |
| Нейтронная | mean 0.05 пульсарных планет (0–1) | T 30–150 K (остаточный/ветровой нагрев), вода 0, жизнь 0, каменистая, settleable=false |
| WD | mean 0.3 выживших (0–1), орбиты 5–8; `disk_state='debris'` — обломочный пояс, НЕ планета | T 25–37 K с **клампом в ветке** (см. ниже): расчёт 278.7·(10⁻²…10⁻⁴)^0.25/√r для r 5.7–28 а.е. даёт 5.3–36.9 K; вода 0, жизнь 0, settleable=false |
| Протозвезда | 0 планет; `disk_state='protoplanetary'` | планета не создаётся; диск описывается в модалке |

Двойные (wide/close) и кратные не имеют отдельной ветки — они используют общий
путь `generatePlanet(...)` для главного компонента с множителем счёта из §5.2
(wide/S-тип: растения у главной; close/P-тип: mean 0.2). Ветки таблицы выше —
только для `star_type ≠ star`.

Запреты ветки: не вызывать `generateOceanicPlanet` (минует физику, ревизия
п.13); газовые гиганты у экзотики не генерируются (`gasGiantChance` — только
общий путь; физически диски фотоиспарились/кик); `GenerateArchetype` не
вызывать. В JSON планеты добавляются поля `star_type` и `exotic_system: true`
— их читают аудит (§6) и UI (§8).

**Кламп T для WD (решение по баланс-проверке В4, 2026-09-15):** равновесная
формула на орбитах 5–8 при L = 10⁻²…10⁻⁴ даёт T = 278.7·L^0.25/√r = **5.3–36.9 K**
(при L ≤ 10⁻³ — половина диапазона L — T < 20 K, т.е. ниже флора аудита
`temp_too_low`, High-лавина). Ветка WD **клампит итоговую T планеты снизу к
25 K**. Итог: планеты WD всегда в 25–37 K — внутри [20, 2500] с запасом 5 K,
формула честно посчитана, диапазон заявлен как фактический результат генерации
(25–37), а не как формула «≤50». Физическая интерпретация клампа: планеты WD
не получают существенного излучения от холодного карлика — нижняя граница
обусловлена остаточным теплом ядра и фоновым нагревом, что в генераторе
выражается фиксированным минимумом. Согласовано с §6.2 (гейт ветки) и §13
(worst case WD 25–37 K).

### 5.4. Диски/пояса — природа сущности (развилка события/лога/атрибута)

Диск/пояс — **не планета и не отдельная таблица**, а атрибут-состояние мира в
`stellar_mods` (`disk_state`, `disk_temp_range`, `disk_notes` для модалки).
Это стабильное состояние (не лог, не событие). Расширяемость: несколько типов
дисков — добавки в тот же JSONB, миграция не нужна.

## 6. Архетипы и аудит (неконфликтность с §99.2.11)

### 6.1. Архетипы экзотики — собственный выход, рулетку не трогаем

§99.2.11 запрещает расширять «рулетку по классу» в сторону экзотики. Ветка
экзотики: **тип объекта → физика (T, вода 0, жизнь 0, композиция) → ярлык
архетипа** («холодный», каменистый) — без `GenerateArchetype`. Общий путь O–Y
остаётся как есть. Пригодность поселений: `settleable=false` всегда (вода 0,
T вне 200–350 K) — экзотика не может стать «пригодной через fallback»
(требование 99.2.4-идеи).

### 6.2. Аудит: какие из 42 правил угрожают экзотике и как ветка их избегает

| Правило (код) | Риск | Гейт ветки |
|---|---|---|
| `temp_too_low` / `temp_too_high` (T вне [20, 2500]) | High-лавина при честной T | планеты экзотики генерируются в T 25–150 K — внутри [20, 2500] (WD: кламп ≥25 K, §5.3; ЧД/НЗ: фикс. диапазоны §5.3); T объекта ЧД = 0 идёт в `worlds.temperature`, не в планету |
| `life_without_water` / `life_without_temperature` | жизнь при воде 0 / T вне 200–400 | вода 0 + жизнь 0 во всех ветках — правила не срабатывают |
| `oceans_in_heat`, `lava_in_cold`, `oceans_without_water` и пр. (формы) | несоответствие композиции | композиция: каменистая/кратерная (ледяные формы — в меру T); без океанов/лав/джунглей; суммы через тот же `Normalize` (100, неотрицательные) |
| `gas_giant_flag_mismatch` | гиганты у экзотики | гиганты не генерируются (§5.3) |
| NaN/zero (`nan_or_inf_value`, `zero_mass`, …) | деление в физике | L=0 у ЧД обрабатывается веткой до `computeEquilibriumTemp` (тёмные планеты получают фиксированную T) — 0/0 не возникает |

**Два новых спец-правила аудита (предложение дизайнера; счётчик правил 40 → 42):**

- `life_in_exotic_system` (High): планета с `exotic_system=true` и `life=true` —
  невозможно по ветке §5.3, машинная гарантия инварианта.
- `settleable_under_exotic` (High): планета с `exotic_system=true` и пресетом
  пригодности (T 200–350 K и вода ≥ 10) — невозможно по ветке.

Правила читают `Raw["star_type"]` / `Raw["exotic_system"]` (поля кладутся в JSON
планеты, §5.3). Цена: +2 правила; аудит одиночных планет в экзотике не сыплет
High за «холодность» — ветка сама держит диапазоны.

## 7. Статистика админки (без «вранья»)

- `admin_stats_load.go` `loadWorlds`: `SELECT id, COALESCE(spectral_class,''),
  star_type, system_type FROM worlds` — NULL-спектр перестаёт ронять строку и
  молча удалять мир из статистики.
- `admin_stats_aggregator.go`: группировка планет по спектральному классу
  остаётся для `star`; экзотика группируется по `star_type` и **показывается
  отдельным блоком** («Белые карлики: N систем», …), а не сливается в класс
  «G» или «по умолчанию». Новый агрегат — распределение миров по `system_type`
  (одиночные/двойные/кратные).
- Названия ключей API менять не нужно: добавляются отдельные ключи
  (`planetsByStarType`, `systemTypeDistribution`); их контекст — агрегаты
  «сколько планет породили системы данного типа объекта» (у экзотики планеты
  генерируются веткой §5.3 — mean < 1, чаще 0, максимум 1 — и попадают в
  `planetsByStarType`, не в `planetsBySpectral`). Ключ `planetsBySpectral`
  остаётся только для обычных звёзд (`star`) и сохраняет смысл.
