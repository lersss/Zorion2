## 1. Цель и скоуп

Научить студию товаров импорту top-каталога (`goods_data/top_catalog.json`, 100 товаров-верхушек, 304 составляющие) кнопкой «Импорт» с **полной заменой** товаров студии (ресурсы не трогаются), и ввести **количество в слотах** (`Slot.quantity`) — инструмент разведения «резина в Т2 vs резина в Т5» количеством в рецепте (решение создателя 2026-09-19, п.7 идеи).

**В скоупе:** парсер top-каталога (пакет `catalog/`), алгоритм замены состояния, схема ID импортированных, `Slot.quantity` (модель/API/UI/экспорт), эндпоинт `POST /api/import`, кнопка «Импорт» + модалка + тост, инпут количества у слота, DoD, дельта в 99a.1. Код — зона @developer по этой спеке.

**НЕ в скоупе (§14):** код Go; отображение связок (решение после просмотра, п.8 идеи — первая итерация: импорт + рендер как есть); автоматический мост «выгрузка → БД» игры; маппинг категорий на игровую модель; изменение формата `top_catalog.json`.

## 3. Парсер top-каталога — `cmd/goods-studio/catalog/topcatalog.go`

Рядом с `import.go` (ресурсы), пакет `catalog`. Читает файл, валидирует, маппит на модель. **Файл только читается, не модифицируется** (решение создателя п.5).

### 3.1. Структуры

```go
type TopCatalog struct {
    SchemaVersion int        `json:"schema_version"`
    Catalog       string     `json:"catalog"`
    GeneratedAt   string     `json:"generated_at"`
    Summary       TopSummary `json:"summary"`
    Goods         []TopGood  `json:"goods"`
}
type TopSummary struct {
    Total      int            `json:"total"`
    PerCategory map[string]int `json:"per_category"`
    Demand     struct{ Continuous, Spike int } `json:"demand"`
}
type TopGood struct {
    ID           string          `json:"id"`
    Name         string          `json:"name"`
    Category     string          `json:"category"`
    WhyTop       string          `json:"why_top"` // НЕ импортируется (решение создателя п.3)
    Constituents []TopConstituent `json:"constituents"`
}
type TopConstituent struct {
    Name string `json:"name"`
    Type string `json:"type"` // "resource" | "good"
}
```

### 3.2. Валидация (ошибка → 400 с перечнем всех проблем, импорт не идёт)

1. `schema_version` ≠ 1 → ошибка «неподдерживаемая версия каталога».
2. `goods` пуст → ошибка.
3. Дубликат `id` (после trim) → ошибка.
4. Дубликат имени (после нормализации §6.3 99a.1: lowercase/trim/схлопывание пробелов) → ошибка.
5. Пустой `name` товара / пустой `category` / пустой `name` составляющей → ошибка.
6. `constituents` пуст (0 составляющих) → ошибка (развилка 4).
7. `type` составляющей не `resource`/`good` → ошибка.
8. Дубликаты составляющих в одном товаре **не ошибка** — два слота с одним товаром осмысленны (99a.1 §6.4).

### 3.3. Маппинг на модель (функция `ApplyTopCatalog(st, tc) []string` — мутирует состояние, возвращает предупреждения)

Полный алгоритм — §4. Здесь — соответствие полей:

| top_catalog | модель |
|---|---|
| `goods[].id` | `Good.ID` (`tg_0001`, §5) |
| `goods[].name` | `Good.Name` |
| `goods[].category` (имя) | `Good.Category` (id категории студии; маппинг по имени, §4.3) |
| `goods[].constituents[]` | `Good.Recipe[]` — слот на каждую составляющую, `quantity=1` (§6), `allow_resource=false` |
| `why_top` | выкидывается (решение создателя п.3) |
| `summary` | не импортируется (справочное) |

## 4. Замена состояния — алгоритм `ApplyTopCatalog`

Выполняется под `s.mu.Lock()` в хендлере импорта (§7), затем атомарный persist. Порядок шагов фиксирован:

1. **Бэкап:** атомарная копия `state.json` → `state.json.bak` (перезаписывается; путь в отчёте). Если `state.json` нет (первый запуск) — бэкап не создаётся, не ошибка.
2. **Сохранить ресурсы:** все `Good` с `kind=resource` (129: слой 20 + витрина 111) изымаются в отдельный список **со всеми полями** (статусы/баны/`banned_at` сохраняются — память статусов, 99a.1 §5.3). Ресурсы не трогаются (решение создателя п.4).
3. **Снести товары:** все `Good` с `kind=good` (черновики/согласованные/исключённые/забаненные, включая g10/g26 «Питательная паста»/«Синтезированный белок») удаляются. Счётчик снесённых — в отчёт.
4. **Категории:** существующие сохраняются как есть. Категории каталога маппятся по нормализованному имени на `Category.ID`; не найденная (в текущем каталоге — 0, факт: 13 из 13 совпадают) — создаётся `NextCategoryID` (решение создателя п.4 «новые категории — создавать»). Счётчик созданных — в отчёт.
5. **Внешние good-компоненты:** для каждого уникального имени составляющих `type=good` (в текущем каталоге ровно 8, факт) создаётся товар:
   - `ID = ext:<slug>` (§5), `Name` = имя из каталога (как есть), `Status = draft` (развилка идеи п.3: состав неизвестен — пустой рецепт; approved с пустым рецептом дал бы валидатор «неполные цепочки»), `Kind = good`, `Source = import` (новый Source, §4.1), `Recipe = []` (пустой — состав неизвестен), `Category` = категория первого топ-товара-потребителя в порядке файла (развилка 3).
   - Резолв топ-товаров на них идёт по имени (§4.4) — «Питательная паста»/«Синтезированный белок» пересоздаются с теми же именами, ссылки сходятся.
6. **Топ-товары:** для каждого `TopGood` создаётся товар:
   - `ID = tg_XXXX` (из каталога), `Name` как есть, `Status = approved` (решение создателя п.2 — сразу «согласовано», поедут в экспорт), `Kind = good`, `Source = import`, `Category` = id из шага 4.
   - `Recipe`: слот на каждую составляющую в порядке файла; `quantity=1` (в каталоге количеств нет, решение создателя п.7); `allow_resource=false` (слоты заполнены — галка не действует); `reason` пуст.
7. **Резолв ссылок** — по имени после нормализации (§4.4). Ненайденный ресурс (в текущем каталоге — 0, факт) → слот остаётся пустым + предупреждение в отчёт.
8. **Проверка циклов не требуется** по построению: топ-товары ссылаются только на ресурсы (тир 0) и внешние компоненты (пустые рецепты, листья) — рёбра только вниз; внутренних ссылок на топ-товары нет (факт). Страховка валидатора §8 99a.1 остаётся.
9. **Прогон валидаторов** (§9) — предупреждения в отчёт.

### 4.1. Новый Source

`SourceImport Source = "import"` в `model/types.go` (рядом с manual/ai/palette). UI: метка «импорт» у товара (рядом с «ИИ» для source=ai). Старые товары не затрагиваются.

### 4.2. Природа сущности (разбор по правилу «событие/лог/атрибут»)

Импорт — **операция** (событие), не сущность: результат — мутация `state.json` (атрибуты существующих сущностей) + отчёт в ответе эндпоинта (лог операции, не хранится). Бэкап — файл-страховка, не сущность. Отдельной таблицы/записей не вводим — поток «импортов» в студию не нужен (локальный инструмент, повторный импорт идемпотентен, §5.2).

### 4.3. Маппинг категорий — детали

Совпадение по нормализованному имени (lowercase/trim/схлопывание пробелов, 99a.1 §6.3). В текущем каталоге 13 из 13 совпадают (факт, включая c13 «Модули кораблей» — создатель переименовал дефолтную «корабли и модули», state.json проверен). Категории, оставшиеся без товаров после импорта, **не удаляются** (свободное множество, 99a.1 §5.1; чистит создатель вручную).

### 4.4. Резолв по имени

Штатный механизм 99a.1 §6.3: `graph.NormalizeName` + `graph.FindByName`. Порядок резолва — после создания всех внешних компонентов (шаг 5) и до вставки рецептов топ-товаров (шаг 6): ресурсы находят существующие `res:*` (100% в текущем каталоге, факт), good — созданные `ext:*` (8 из 8). Совпадение с баном/исключённым невозможно: товары студии снесены (шаг 3), ресурсы не банятся резолвом (бан ресурса не мешает ссылке — статус ресурса не влияет на вхождение в рецепт, валидатор §8 п.3 99a.1 допускает `resource`).

## 5. ID импортированных

### 5.1. Схема

| Сущность | ID | Пример |
|---|---|---|
| Топ-товар | `tg_XXXX` (как в каталоге, без префикса) | `tg_0001` |
| Внешний good-компонент | `ext:<slug>` — нормализованное имя, пробелы → дефис, кириллица допустима | `ext:питательная-паста` |

Коллизий нет: существующие пространства — `res:*` (ресурсы) и `gN` (ручные товары, `NextGoodID` парсит строго `g%d` — `tg_0001`/`ext:*` не сматчатся). Дубликаты id в каталоге — ошибка парсера (§3.2).

### 5.2. Стабильность

Повторный импорт «заменой всё» идемпотентен: те же `tg_XXXX` (из каталога) и те же `ext:<slug>` (детерминированы именем) → состояние после повторного импорта совпадает с первым (кроме `created_at`). Ручные правки между импортами (заполнение рецептов внешних компонентов, согласования, новые товары) сносятся повторным импортом — предупреждение в модалке (§8.2).

## 6. Количество в слотах — `Slot.quantity`

Санкционировано решением создателя 2026-09-19 (п.7 идеи): итерация количества из 99a.1 §6.4/§10.13 вводится сейчас.

### 6.1. Модель

```go
type Slot struct {
    GoodID        string `json:"good_id"`
    Quantity      int    `json:"quantity,omitempty"` // единиц составляющей; 0 = не задано (старый слот) → трактуется как 1
    Reason        string `json:"reason,omitempty"`
    AllowResource bool   `json:"allow_resource"`
}
```

- **Нормализация (развилка 5):** при `LoadState` каждый слот с `Quantity < 1` → `1` (в памяти; файл не переписывается до первой мутации — «старые слоты без миграции», решение создателя п.6). Новые слоты (`POST /api/goods/{id}/slots`, импорт, ИИ-вставка) создаются с `Quantity = 1`.
- **Тир не зависит от количества** (решение создателя п.6): `graph.Tier` не меняется, формула 99a.1 §6.1 без изменений.
- **Валидаторы не зависят от количества** (99a.1 §8): проверяют наличие `GoodID`, не `Quantity`.

### 6.2. API

| Метод/путь | Изменение |
|---|---|
| `PUT /api/goods/{id}/slots/{n}` | body `{good_id, quantity?}`: `quantity` опционально; если передан и ≥ 1 — обновить; не передан — оставить текущее (замена составляющей не сбрасывает количество); < 1 — трактуется как 1 |
| `GET /api/state` | `SlotView` + `quantity` (int, всегда ≥ 1 после нормализации) |

Остальные эндпоинты слотов (POST/DELETE, clear, allow_resource) без изменений.

### 6.3. Экспорт

`export.Slot.Quantity` (формат §11 99a.1 уже имеет поле) заполняется реальным количеством слота (≥ 1). Дельта: 99a.1 §11 «quantity = 1» → «quantity = количество слота».

### 6.4. ИИ-заполнение

ИИ возвращает K имён на K пустых слотов, без количеств (99a.1 §7.3) — слоты от ИИ получают `quantity = 1` (слот уже создан с 1; старый пустой слот с 0 нормализован при загрузке). Промпт не меняется.

### 6.5. UI

- **Детальная панель, заполненный слот:** рядом с именем составляющей — «×» + инпут `number` (min 1, width ~52px, значение = quantity). `change` → `PUT /api/goods/{id}/slots/{n}` `{quantity}`; ошибка — тост, значение возвращается. Пустой слот — без инпута.
- **Карточка графа:** количество не показывается (карточка = обзор, 99a.1 §10.2; слоты на графе не рисуются — только линии).
- **Экспорт:** quantity реальное (тост/модалка как есть).

## 7. Эндпоинт `POST /api/import`

| Метод/путь | Параметры | Ответ |
|---|---|---|
| `POST /api/import` | `{path?}` — путь к top-каталогу; дефолт `filepath.Join(cfg.DataDir, "top_catalog.json")` = `goods_data/top_catalog.json` | новое состояние (StateView) + отчёт |

```json
{
  "report": {
    "imported": 100,           // топ-товаров создано
    "components_created": 8,   // внешних good-компонентов создано
    "goods_removed": 9,        // товаров студии снесено
    "categories_created": 0,   // категорий создано (по имени не найдено)
    "backup": "goods_data/state.json.bak",
    "warnings": ["…"]          // предупреждения парсера (§3.2 — при частичном резолве) + валидаторы (§9)
  },
  "state": { … StateView … }
}
```

**Защита:**
- Файл не найден → `404 {error: "файл не найден: <path>"}`.
- Невалидный JSON / ошибки валидации §3.2 → `400` с перечнем проблем; состояние **не меняется**.
- Активная ИИ-генерация (`s.generating`) → `409 {error: "идёт генерация — импорт после завершения"}` (импорт сносит товары, на которые может писать генерация).
- Путь — как передан (`filepath.Clean`); выход за пределы каталога не блокируется (локальный инструмент, путь задаёт создатель).

**Порядок в хендлере:** `RLock`-проверка generating (409) → `Lock` → `ApplyTopCatalog` (§4) → `persist()` → `buildView()` → ответ. Повторный вызов во время импорта невозможен (один процесс, блокировка).

## 9. Валидаторы после импорта — ожидаемые предупреждения

Прогон §8 99a.1 после импорта даёт **ожидаемые** предупреждения (не ошибки импорта; сигнал создателю):

1. **«Каких ресурсов нет» × 8:** внешние компоненты — draft с пустым рецептом, на них ссылаются топ-товары (входящая степень > 0) → кандидаты в недостающие товары/ресурсы. Корректно: состав внешних компонентов неизвестен, создатель заполняет их рецепты («заполнить комплектующие») или исключает.
2. **«Ссылки на не-согласованных» × 8:** топ-товары (approved) ссылаются на внешние компоненты (draft) → экспорт топ-товаров даст битые ссылки, пока компоненты не согласованы. Корректно: согласование внешних компонентов — следующий шаг создателя после заполнения рецептов.

Топ-товары (approved, рецепты заполнены) предупреждений **не** дают (неполные цепочки — только про пустые рецепты approved; у топ-товаров рецепты заполнены). Страховки (цикл, дубликат имени) — чисты по построению.

## 10. DoD и критерии приёмки

**DoD разработки (AGENTS.md §2):** `go build ./...`, `go vet ./...`, `go test -race ./...`. TDD: тест до кода (красный), после — зелёный. Минимальный набор:

- **Парсер** (`catalog/topcatalog_test.go`): валидная фикстура (малый каталог в тесте, не реальный файл) → структуры и маппинг; дубликат имени → ошибка; дубликат id → ошибка; пустые constituents → ошибка; `type` невалидный → ошибка; битый JSON → ошибка; schema_version ≠ 1 → ошибка.
- **Замена** (`ApplyTopCatalog`): ресурсы сохраняются со статусами/банами (забаненный ресурс остаётся забаненным); черновики сносятся; 100 approved + 8 draft; резолв по имени (ресурс → `res:*`, good → `ext:*`); категории 1:1, неизвестная → создаётся; повторный импорт идемпотентен (те же id, то же состояние).
- **Количество:** нормализация 0 → 1 при загрузке; PUT `{quantity}` обновляет; PUT без quantity не сбрасывает; экспорт пишет реальное quantity; тир не меняется от количества.
- **Эндпоинт:** POST /api/import — 200 (фикстура), 404 (нет файла), 400 (битый файл), 409 (генерация активна); бэкап создаётся.
- **e2e-смоук** `tools/e2e/goods-studio-check.js` (клиентский флоу): кнопка «Импорт» видна; модалка с подтверждением; после подтверждения — тост-отчёт и перерисовка; инпут количества у заполненного слота, изменение сохраняется; экспорт содержит quantity.

**Критерии приёмки (проверка @tester после разработки):**
1. Создатель жмёт «Импорт» → модалка → подтверждение → граф перерисовывается (100 топ-товаров + 8 компонентов), тост-отчёт с числами и предупреждениями.
2. Ресурсы на месте (129, read-only); статусы/баны ресурсов сохранены.
3. Топ-товары — approved с заполненными рецептами (quantity=1); внешние компоненты — draft с пустыми рецептами; валидатор показывает 8× missing_resource + 8× non_approved_ref.
4. Количество: инпут у слота в детали; изменение переживает перезапуск студии; в export.json quantity реальное; тир товара не меняется.
5. Повторный импорт — те же id (`tg_XXXX`, `ext:*`), состояние идентично первому импорту.
6. Игровой сервер не затронут: `go build ./...` чистый; `internal/resource` только читается.
7. `state.json.bak` создан перед импортом; восстановление из бэкапа работает (замена файла вручную).
8. Импорт при активной генерации — 409, состояние без изменений.
