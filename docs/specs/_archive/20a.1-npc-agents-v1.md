## 0. Резюме (одним абзацем)

Вводится сущность `npc_agents` — наблюдатель-агенты, рассчитанные на **сотни тысяч
экземпляров**. Агент автоматически перемещается между мирами (рандом в радиусе
1000), по прибытии помечает мир как «посещённый» (ленивый пересчёт населения
происходит при визите игрока), при включённых уведомлениях шлёт пуш через WebSocket
всем подключённым клиентам (дросселируется: не чаще раза в 5 с), виден на карте как
движущаяся иконка (когда видны имена звёзд). Управление — вкладка «NPC» в админке.
Скорость и интервал тика — настраиваемые.

## 1. Контекст и решения

**Создатель (2026-09-14):** «Создать NPC-агентов в первом приближении. Они
перемещаются по галактике, "смотрят" на планеты (обновляют данные о населении),

админке). Видны на карте. Управляются через вкладку "NPC" в админке.»

## 2. Архитектура (масштаб: сотни тысяч агентов)

### 2.1. Проблема

При 100k агентов:
- NPCManager тикает каждые 5с → нужно обработать 100k записей за 5с (20k/сек).
- Каждый агент → отдельная транзакция = 100k транзакций на тик = БД ляжет.
- Поток прибытий: при средней длительности полёта ~200 с (§3.2) = 100k ÷ 200 с ≈
  **500 прибытий/сек** ≈ 2500 за тик 5с (при условии, что все 100k в полёте). Batch
  должен покрывать поток, иначе очередь растёт навсегда (В3, П1).
- `/api/npc/positions` при 100k агентов → медленный запрос на каждый рендер.

### 2.2. Решения

#### A. Batch-обработка в NPCManager

**Вместо** `SELECT * FROM npc_agents WHERE status='flying' AND arrive_at <= now`
(10k строк на тик при 100k агентов, 2k тиков жизни):

```
Batch size = 2000 (конфигурируется)
Tick: process next batch (cursor-based, не OFFSET)
```

- Каждый тик обрабатывает **не все** агенты, а следующую порцию.
- Курсор хранится в памяти (текущий `last_processed_id`).
- При старте сервера курсор сбрасывается (обработка идёт по кругу).
- **Стоимость тика = O(batch_size)**, а не O(total_agents).
- **Приоритет прибытий:** бюджет тика сначала уходит на прибытия
  (`arrive_at <= now`), запуск новых полётов (`idle → flying`) — из остатка.
- **Сходимость с потоком (В3/П1):** равновесный поток прибытий от длительности
  полёта не зависит и ограничен бюджетом тика (~1000 прибытий + ~1000 стартов).
  Batch 2000/тик (400 прибытий/сек) покрывает его с запасом ~2×. Грубый спрос при
  всех 100k в полёте (~500/сек, §2.1) кратковременно превышает бюджет — в этом
  случае (плотный кластер, короткие перелёты) мягкая деградация: наблюдение и
  уведомление задерживаются, очередь видна в админке; данные не теряются
  (состояние в БД).

#### B. In-memory позиции для карты

**Проблема:** `/api/npc/positions` при 100k агентов = медленный SELECT.

**Решение:** кэш позиций в памяти, обновляемый на тик:

```go
type PositionCache struct {
    mu        sync.RWMutex
    positions []InterpolatedPosition // уже x,y на now
    snapshot  atomic.Pointer[[]InterpolatedPosition]
}
```

- Каждый тик NPCManager: пересчитать позиции для **всех** агентов (интерполяция —
  дешёвая операция: `from + (to - from) * progress`).
- Результат → `atomic.Pointer` (lock-free read для HTTP-хендлера).
- `/api/npc/positions` → просто отдаёт snapshot. **O(1)** на запрос.
- При 100k агентов: 100k интерполяций × 5с = 20k интерполяций/сек (тривиально для CPU).

#### C. Batch-уведомления

**Проблема:** ~2500 агентов прибывают за тик (500/сек × 5с) → 2500 WS-сообщений = flood.

**Решение:** batch-отправка с дросселем:

```go
type NotificationBatch struct {
    mu          sync.Mutex
    arrivals    []ArrivalEvent
    total       int             // прибытий за окно сверх maxBatch
    since       time.Time       // начало окна
    interval    time.Duration   // npcNotifyInterval, default: 5s
    maxBatch    int             // npcNotificationMaxBatch, default: 100
}
```

- Прибытие → добавить в batch (не отправлять сразу).
- **Дроссель:** сообщение отправляется **не чаще раза в `interval` (5 с)** — при
  500 прибытий/сек это ≤ 12 сообщений/мин на клиента вместо 500/сек (снижение
  ~2500×).
- В одном сообщении до `maxBatch` (100) детальных записей; прибытия сверх 100 за
  окно — в поле `total` (счётчик).
  ```json
  {
    "type": "npc_arrivals_batch",
    "since": "2026-09-14T12:00:00Z",
    "arrivals": [
      {"agent": {...}, "world": {...}, "population": 12345},
      ...
    ],
    "total": 2400
  }
  ```
- Френтенд обновляет UI пачкой (не по одному), `total` — счётчиком «всего прибытий».

### 2.3. Сводка архитектурных решений

| Компонент | Решение | Масштаб |
|-----------|---------|---------|
| NPCManager tick | Batch-обработка (курсор, 2000/тик, приоритет прибытий) | 100k агентов → 50 тиков на полный цикл |
| Наблюдение | UPDATE `last_observed_at` (без пересчёта, §4) | 0 пересчётов на прилёт |
| Позиции для карты | In-memory snapshot (atomic.Pointer) | O(1) на запрос |
| Уведомления | Batch + дроссель (не чаще 1 сообщения / 5с) | ≤ 12 сообщений/мин на клиента |
| БД-операции | COPY/ batch UPDATE вместо одиночных | 100k записей = 1 запрос |

### 2.4. Лимиты (configurable)

| Параметр | Дефолт | Описание |
|----------|--------|----------|
| `npcTickInterval` | 5s | Интервал тика NPCManager |
| `npcBatchSize` | 2000 | Агентов за тик (покрывает равновесный поток ~200/сек при 100k, §2.2.A) |
| `npcSpeedFactor` | 0.3 | Коэффициент длительности полёта: `duration = dist × factor` (с), без потолка; дефолт = скорость игрока (§10.1) |
| `npcNotifyInterval` | 5s | Мин. интервал между WS-сообщениями (дроссель, §5) |
| `npcNotificationMaxBatch` | 100 | Макс. детальных записей в одном WS-сообщении; избыток — в `total` |

## 3. Механика перемещения

### Модель: время-функция, а не горутины

Полёт агента **не** держится горутиной (в отличие от `travel.Manager`, который
на `userID` и с отменой). Агент в пути — чистая функция от времени между двумя
точками, ровно как §6.7.7. Позиция в момент `now`:

```
progress = clamp((now - depart_at) / (arrive_at - depart_at), 0, 1)
x = from.x + (target.x - from.x) * progress
y = from.y + (target.y - from.y) * progress
```

Так дешевле и масштабируется на многих агентов без горутины на каждого, и это
единственная модель, совместимая с «рисуется интерполяцией» на клиенте.

### События смены состояния

Нужен фоновый планировщик: без него «прибытие» (и, значит, уведомление) не
произойдёт в нужный момент — клиент лишь рисует, а событие наблюдения должно
сработать на сервере.

**`NPCManager`** — одна горутина, стартует при старте сервера, тикает каждые
`npcTickInterval` (по умолчанию **5 с**, конфигурируется в админке §6). На тик:

1. `SELECT` агентов со `status='flying'` и `arrive_at <= now` (по курсору, до
   `npcBatchSize`) → для каждого:
   - `status='observing'`, выполнить наблюдение (§4),
   - после наблюдения `status='idle'`, `current_world_id = target`,
     `last_observed_at = now`, `updated_at = now`,
   - если `notify_enabled` → добавить в batch-уведомлений (§5).
   Всё изменение одного агента — одной транзакцией (инвариант 1).
   **Приоритет:** бюджет тика сначала уходит на прибытия; запуск новых полётов
   (п. 2) — из остатка бюджета. При перегрузке агенты ждут обработки (мягкая
   деградация, §2.2.A), данные не теряются.
2. `SELECT` агентов со `status='idle'` → для каждого выбрать следующий маршрут
   (§3.2) и перевести в `status='flying'`: заполнить кортеж полёта.

Тик не обходит галактику и не сканирует планеты глобально — трогает только
строки `npc_agents` (их мало) и поселения целевого мира при наблюдении.
Стоимость ∝ числу агентов, не размеру галактики (инвариант 2).

**Отказной режим.** Планировщик падает с `recover` (как `runFlight`), логирует и
переживает. Агент в полёте, если сервер упал, продолжает «лететь» по времени при
следующем тике — состояние в БД, детерминировано, ничего не теряется. Рестарт
сервера не ломает маршрут: `arrive_at` абсолютен.

### 3.2. Выбор маршрута

**Решение:** рандомный мир в радиусе 1000 от текущей позиции. Если в радиусе нет
миров — берём ближайший.

**Скорость:** настраивается в админке (`npcSpeedFactor`), дефолт **0.3 с/ед.
расстояния** (= скорость перелёта игрока, решение §10.1). Формула **отдельная от
`/travel`**, потолок 20 с к агентам не применяется:

```
duration = dist × npcSpeedFactor   (мин. 3 с, потолка нет)
```

**Почему без потолка 20 с (В3, П4):** потолок у игрока — UX-особенность
`/travel` (игрок не ждёт дольше 20 с) и к фоновым агентам не относится. С потолком
все полёты внутри радиуса 1000 стали бы одинаковыми (20 с), «длительность ∝
расстояние» перестала бы работать, а поток при 100k вырос бы до 5000 прибытий/сек.
Без потолка пропорциональность строгая: средний перелёт в радиусе 1000 ≈
**667 ед.** (старт фиксирован в центре, цель равномерна в круге радиуса R:
E[dist] = 2R/3 ≈ 667; формула 0.905R ≈ 905 ед применима к двум независимым точкам
в круге — к нашей модели не относится) → **~200 с (3.3 мин)**.

**Сходимость с эталоном «сотни тысяч» (В3, П1):** грубый спрос при всех 100k
агентов в полёте = 100k ÷ 200 с ≈ **500 прибытий/сек** ≈ 2500 за тик 5 с;
равновесный поток, ограниченный бюджетом тика, ниже — §2.2.A. Пересечение
галактики: MapSize = 8000, диаметр 16000. По прямой — 16000 ÷ 667 ≈ **24 хопа**
(~80 мин); случайным блужданием (смещение ∝ √n × шаг) до пересечения —
n ≈ (16000/667)² ≈ **580 хопов** (~32 ч). И то, и другое — «медленно», как и
задумано для наблюдателя (при 20с-потолке блуждание было бы 580 × 20 с ≈ 3.2 ч —
не медленно).

**Триггер:** автоматически. Агент автономен после создания — сам летает и наблюдает.

### 3.3. Открытый вопрос: формула длительности полёта (В3, П1)

Эталон «архитектура рассчитана на сотни тысяч агентов» + «дефолт = скорость
игрока» (§10.1) заданы, но **конкретная формула — не задана**. Рабочий вариант в
спеке — **A**; создатель выбирает (финальное решение за ним):

| Вариант | Формула / числа | Плюсы | Минусы / цена |
|---|---|---|---|
| **A (в спеке)** | `dist × 0.3`, без потолка; batch 2000 | Дефолт дословно = скорость игрока (§10.1); полёт «медленный» (3.3 мин), пропорциональность строгая | Покрывает равновесный поток (запас ~2×); грубый спрос ~500/сек (все 100k в полёте) превышает бюджет — в плотном кластере поднимать batch вручную / мягкая деградация |
| **B** | `dist × 0.55`, без потолка (средний полёт ~370 с ≈ 6.1 мин); batch ≥ 1400 | Поток ~270/сек — в окне тестера (100–500/сек); полёт ещё «медленнее» | Дефолт ≠ скорости игрока (нарушение буквы §10.1 — нужно согласие создателя); batch 1200/тик (240/сек) уже не покрывает поток — нужен ≥ 1400 |
| **C** | `clamp(dist × 0.3, 3с, 60с)`; batch 9000 | Все полёты короче минуты — «карта живее» | Снова убивает пропорциональность (все полёты в радиусе 1000 = 60 с); поток 1667/сек → огромный batch и максимум WS-нагрузки. Не рекомендуется |

Эталон зафиксирован как открытый вопрос в `06_factions.md` §6.7.10 (FAQ); до
одобрения создателя рабочая конфигурация — вариант A.

## 4. Действие «наблюдение»

**Решение:** при прибытии агент **помечает** мир как «посещённый»
(`last_observed_at`). Пересчёт населения **не запускается** на тике агента.

**Почему:** при 100k агентов запуск `RecomputeSettlementPopulation` на каждый
прилёт = тысячи транзакций. Население и так пересчитывается лениво при открытии
карточки планеты игроком. Агент лишь фиксирует факт присутствия.

**Когда пересчёт реально происходит:**
- При открытии карточки планеты игроком (`attachSettlements` — уже работает).
- При первом визите после «устаревания» ( > `MinPersistInterval`).

**Итого:** агент = «это место посещали recently». Данные свежие, когда игрок
реально смотрит. Экономия: 0 транзакций на прилёт (только UPDATE
`last_observed_at`).

**Лог наблюдений:** только `last_observed_at` агента (решение создателя §10.7).

**Отклонение §6.7.2:** принято для v1. Агент = инструмент наблюдения, не
экономический клиент. В полной модели §6.7 должно быть закрыто.

## 5. Уведомления

**Решение:** WebSocket (существующий), broadcast **всем подключённым клиентам**
(пока ролей нет).标记 на доработку: после 99.2.14 (ролевая модель) — broadcast
только по роли `admin`/`skycomposer`.

**Batch-отправка с дросселем** (§2.2.C): сообщения копятся и отправляются **не
чаще раза в `npcNotifyInterval` (5 с)**; в одном сообщении до
`npcNotificationMaxBatch` (100) детальных записей, прибытия сверх 100 за окно — в
поле `total`. При 500 прибытий/сек это ≤ 12 сообщений/мин на клиента (снижение
~2500×). Дроссель в v1 не фильтрует по повторности визитов (агент = «живая
карта»); ролевой фильтр — после 99.2.14.

**Выключение:** per-agent флаг `notify_enabled` (переключатель в таблице админки,
§6). Глобальный рубильник не нужен (админка позволяет выключить по агенту).

> **Изменено 26a.1 (2026-09-15):** добавлен **глобальный рубильник**
> `notify_enabled_global` в настройках вкладки NPC (по умолчанию ВЫКЛЮЧЕН);
> отправка ⇔ рубильник И per-agent флаг; дефолт `notify_enabled` новых агентов =
> `false` (был `true`). Подробности — `26a.1` §7.

Формат сообщения (пачка):

```json
{
  "type": "npc_arrivals_batch",
  "since": "2026-09-14T12:00:00Z",
  "arrivals": [
    {
      "agent": { "id": "uuid", "name": "Наблюдатель-3" },
      "world": { "id": "uuid", "name": "Sirius" },
      "population": 12345,
      "observed_at": "2026-09-14T12:00:00Z"
    }
  ],
  "total": 2400
}
```

Админ-фронт показывает toast/уведомление по `type == "npc_arrivals_batch"`; `total`
показывается счётчиком («ещё N прибытий за окно»).

## 6. Вкладка «NPC» в админке

Новая вкладка «NPC» в `web/admin.html` (по образцу существующих; регистрация —
через `tabs.js`/`main.js`).

Содержимое:

- **Таблица агентов:** имя, статус (`idle`/`flying`/`observing`), текущий мир,
  целевой мир, `last_observed_at`, переключатель «уведомления» (чекбокс).
- **Кнопки:** «Создать агента» (поле имени + опционально стартовый мир),
  «Удалить» (подтверждение), переключатель уведомлений per-row.
- **Настройки (глобальные):** коэффициент времени полёта (`npcSpeedFactor`),
  интервал тика (`npcTickInterval`), batch size, интервал уведомлений
  (`npcNotifyInterval`). Поля в верхней части вкладки, сохраняются в конфиг
  (БД-таблица настроек или env с перезаписью из админки).

**Фронт-файлы:** `web/static/js/admin/npc.js` (новый) + регистрация в `tabs.js`,
`main.js`; `web/admin.html` — вкладка и каркас.

## 7. Отрисовка на карте

Корабль агента на карте — по §6.7.7 интерполяцией между двумя точками.

**Источник данных:** новый публичный (игровой) эндпоинт `GET /api/npc/positions`
(§8) возвращает все агенты с **уже интерполированной** позицией `x,y` на момент
`now` из in-memory snapshot (§2.2.B — O(1), lock-free). Клиент не знает и не
хранит кортежи полёта.

**Рендер (`web/static/js/map/`):** `map_render.js` получает список позиций
(периодический опрос, согласованно с `npcTickInterval`, по умолчанию 5 с) и рисует
отличительную иконку агента (маленький цветной ромб/кружок с именем при
достаточном зуме), экранный cull как у звёзд. При полёте иконка движется между
сэмплами. Клик по иконке → мини-панель: имя, статус, текущий/целевой мир.

**Видимость на зуме (решение):** агенты видны, **когда видны имена звёзд**
(тот же порог, что `nameDisplayThreshold` — `web/static/js/config.js`). На
галактическом обзоре (имена не видны) агенты скрыты.

**Радар (§6.7.7):** радара в игре ещё нет; видимость — экранный cull без радара.
Осознанное отклонение, переносится на момент введения радара (§9).

## 9. Инварианты и ограничения

Проверка по двенадцати инвариантам:

- **И1 (многопользовательность).** Агент виден многим клиентам. Источник правды —
  БД; планировщик — единственный писатель; карта читает in-memory snapshot
  (`atomic.Pointer`, lock-free). Смена состояния агента — batch-транзакциями.
- **И2 (стоимость не от размера галактики).** Tick обрабатывает batch (2000
  агентов), не обходя галактику. Выбор маршрута — случайный мир в радиусе 1000
  (поиск по индексу, не по всей галактике). Соблюдено.
- **И3 (сложность добровольна).** Агенты не добавляют игроку бухгалтерии.
  Соблюдено.
- **И5 (информация имеет возраст).** Агент «в присутствии» — маркер свежести;
  данные пересчитываются при визите игрока. Соблюдено.
- **И8 (контракт — единственный рычаг удалённого действия).** Агент не рычаг для
  игрока, это симуляция мира; наблюдение не даёт игроку дистанционного действия.
  Соблюдено.
- **И12 (NPC — пол, не потолок).** Наблюдатели не конкурируют экономически.
  Соблюдено.

**Массштабируемость (сверх инвариантов):**

- 100k агентов: tick = batch 2000 → полный цикл за 50 тиков (250 с при 5с тике).
- Каждый тик: до 2000 UPDATE `last_observed_at` (batch), **0 пересчётов населения**.
- Позиции: snapshot в памяти, O(1) чтение.
- Уведомления: дроссель — не более 1 WS-сообщения / 5с, ≤ 100 деталей + `total`.

**Известные отклонения (зафиксированы, не молча):**

1. **§6.7.2 «агент — клиент, а не слой».** Первое приближение даёт агенту прямую
   запись `last_observed_at` (не через отчёты/контракты). Принято создателем
   (решение 2026-09-14); в полной модели §6.7 должно быть закрыто.
2. **§6.7.7 «радар».** Видимость без радара (экранный cull), до введения радара.
   Переносится.
3. **Наблюдение ≠ пересчёт населения** в v1: агент только помечает посещение;
   пересчёт остаётся за визитом игрока (§4). Отдельная дедупликация не нужна —
   пересчёт агент не запускает вовсе (П2).

## 11. План реализации и DoD

Разработчик идёт по этапам, после каждого — гейт.

### Этап 1. Миграция и модель
- `migrations/000026_create_npc_agents.sql`; `internal/models/npc_agent.go`;
  `internal/repository/npc_repository.go` — batch-методы (ListBatch по курсору,
  UpdateStatusBatch, Insert, Delete).
- **Готово:** миграция применяется на старте; тесты репозитория зелёные.

### Этап 2. Планировщик
- `internal/npc/manager.go` (+ `doc.go`): фоновый тик, **курсорная batch-обработка**
  (§2.2.A, приоритет прибытий), выбор маршрута в радиусе 1000 (§3.2), формула
  длительности `dist × npcSpeedFactor` без потолка (§3.2), обработка прибытий,
  `recover`, конфигурируемые лимиты (§2.4).
- **Готово:** unit-тесты переходов `idle→flying→observing→idle`, курсорной
  обработки, детерминизм позиции по времени, **тест формулы**: длительность
  строго ∝ расстоянию, без потолка (например `dist=667 → ~200 с`).

### Этап 3. Наблюдение
- Прибытие: UPDATE `last_observed_at` + `status→idle` (без пересчёта населения).
- **Готово:** тест: прибытие обновляет `last_observed_at`, население не трогается.

### Этап 4. Позиции и ручки
- `PositionCache` (in-memory snapshot, §2.2.B); `internal/handlers/admin_npc.go`
  + `npc_handlers.go`; регистрация в `main.go`.
- **Готово:** ручки §8 работают; позиции из snapshot, O(1).

### Этап 5. Уведомления
- `NotificationBatch` (§2.2.C) с дросселем: интервал 5с, ≤ 100 деталей + `total`;
  `WSHub.Broadcast(msg)` всем подключённым; добавление в batch на прибытие при
  `notify_enabled`.
- **Готово:** подключённый клиент получает `npc_arrivals_batch` не чаще раза в 5с;
  `notify_enabled=false` не шлёт; при > 100 прибытий за окно `total` растёт, число
  сообщений не растёт (тест дросселя).

### Этап 6. Фронт: админка + карта
- `web/static/js/admin/npc.js`, `tabs.js`, `main.js`, `web/admin.html` (вкладка с
  таблицей и настройками §6); `map_render.js`/`data.js` (опрос позиций, иконка при
  видимых именах звёзд, клик).
- **Готово:** вкладка NPC (создать/удалить/переключить уведомления/настройки
  скорости); агенты видны на карте и двигаются.
