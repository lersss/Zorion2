## 0. Резюме (одним абзацем)

Во вкладку «NPC» админки добавляется режим **«Добавить N»**: админ вводит число (валидация только `count ≥ 1`, лимита нет), сервер генерирует ровно N новых агентов со сгенерированными **англоязычными именами «имя-фамилия»** (слоговый генератор, комбинаторное пространство миллионов пар — уникальность пары гарантирована до 100к+), стартовый мир — **случайный по всей галактике**, статус `idle` (подхватывает планировщик, как одиночное создание). Вставка — одной **COPY-операцией** (`pq.CopyIn`, паттерн проекта), операция — **асинхронный джоб** по образцу генерации вселенной/гипотез (202 + poll прогресса). В этой же фиче: **пагинация** `GET /admin/npc` (cursor-keyset по `(created_at, id)`, «показать ещё»), **поиск агента на карте** (поле на карте → центрирование + подсветка иконки), **пуши: глобальный рубильник (по умолчанию выключен) + per-agent флаг**, **метрики**: время генерации пачки, очередь на тик (живой COUNT `overdue_arrivals`), лаги планировщика — in-memory + лёгкие COUNT, без новой таблицы. Механики 20a (полёт, наблюдение, `/api/npc/positions`, баланс полёта) не трогаются.

## 1. Контекст и решения

**Создатель (2026-09-15):** «Нужно сделать генератор агентов. Наверное, им нужно свой генератор имён (имя-фамилия), англоязычных. В админке, просто указанием количества. Хочу протестировать на большой галактике как они себя ведут в количестве 10-50-100к».

**Принятые решения создателя (2026-09-15, полный пакет, обязательны):**

| Параметр | Решение |
|----------|---------|
| Имена | Слоговый генератор «звучит как английское», имя-фамилия; уникальность пары до больших чисел (100к+) |
| Режим | «Добавить N» — создалось ровно столько новых (не «заполнить до N») |
| Стартовые миры | Случайные по всей галактике |
| Лимит count | **Без лимита** — валидация только `count ≥ 1`; защита от ошибок — на фронте (confirm и пр.) |
| Список агентов | **Постраничный** (пагинация) — при 100к полный список каждые 10 с тяжёлый |
| «Найти агента» | **Кнопка поиска на карте**: найти по имени/id → показать на карте (центрирование) |
| Пуши | **Общая галка на всех агентов** (глобальный рубильник), **по умолчанию выключена**; per-agent переключатели остаются; дефолт новых агентов — `notify_enabled = false` |
| Метрики | Включить в фичу — время генерации пачки, очередь на тик, лаги планировщика |
| Бенчмарк 10-50-100к | НЕ в этой фиче — идея 26b, бэклог; спека 26a учитывает, но не включает |

**Что уже есть (из 20a.1, реализовано):** таблица `npc_agents` (миграция 000026, индекс `(status, id)`), планировщик `internal/npc/manager.go` (batch-тикание, курсоры), позиции in-memory, вкладка «NPC» (`admin_npc.go`, `npc.js`) с одиночным созданием `POST /admin/npc` (Insert), `GET /admin/npc/settings`/`PATCH`. ## 2. Пространство решений («разворот подходов»)

Развилки, по которым выбор не был задан создателем. По каждой — классы подходов, цена, выбор. Углубление в принятый вариант — в §3–8.

### Р1. Транспорт генерации (синхронный запрос vs асинхронный джоб vs гибрид)

| Вариант | Механика | Цена / режим отказа |
|---|---|---|
| **A. Синхронно с таймаутом** | `POST` крутит генерацию и вставку до ответа | При «без лимита» N не ограничен сверху: время ответа непредсказуемо (100к ≈ 2–5 с, миллион ≈ минуты); прокси/браузерные таймауты — риск оборванного запроса при неоткатанной транзакции; прогресса нет; UI блокируется. **Невозможен тем более** (решение «без лимита») |
| **B. Асинхронный джоб (принято)** | Паттерн генерации вселенной/гипотез: `statusManager` + 202 + poll | Один консистентный путь для любого N; прогресс и отчёт уже умеет `poll.js`; отмена — `Cancel` (в 26a не используется, но доступна). Цена: ответ «started» без результата — фронт ждёт poll |
| **C. Гибрид: до N синхронно, свыше — джоб** | Два кода, два контракта ответа | Ветвление логики и UI ради экономии на малых N (одиночный путь уже есть — `POST /admin/npc`); непоследовательные ошибки |

**Выбор: B.** Единый асинхронный джоб для любого N ≥ 1. Джоб итерирует по N — это безопасно при любом разумном N; защита от «миллиона случайно» — фронт (confirm), не сервер.

### Р2. Способ вставки N строк

| Вариант | Механика | Цена / режим отказа |
|---|---|---|
| **A. N одиночных `Insert`** | Существующий `Insert` в цикле | 100к × ~1–3 мс ≈ **100–300 с**; N транзакций — БД ляжет (спека 20a.1 §2.1 прямо называет это запретным). Отклонён |
| **B. Multi-row VALUES пачками** | `INSERT ... VALUES (...),(...),...` по ~4000 строк (лимит параметров 65535) | 25 запросов по 100+ КБ SQL на 100к; Postgres парсит каждый; медленнее COPY (комментарий `planet_data_batch.go`: 5–10×). Приемлемо, но не лучший существующий паттерн |
| **C. COPY через `pq.CopyIn` (принято)** | Настоящий `COPY FROM STDIN`, одна транзакция, пачка целиком | Паттерн проекта (`planet_data_batch.go`); 100к строк ≈ 1–3 с; без лимита параметров; атомарно «всё или ничего». Реализация: локальный хелпер `copyInNPC` в `npc_repository.go` (~25 строк) — общий хелпер не выносится (хирургичность: `planet.copyInRows` чужой файл, два потребителя не оправдывают рефакторинг пакета planet) |

**Выбор: C.**

### Р3. Генератор имён: словарь vs слоговый vs гибрид

| Вариант | Механика | Цена / режим отказа |
|---|---|---|
| **A. Словарь реальных имён** (100 имен × 100 фамилий = 10к пар) | Хардкод списков | Правдоподобно, но: пар **10к < 100к** — уникальность не обеспечить без суффиксов-цифр; словарь конечен, пополняется руками |
| **B. Слоговый комбинаторный (принято)** | Пулы открывающих/закрывающих слогов имени и фамилии, пары из миллионов комбинаций | «Звучит как английское» (Marion Hale, Cyrus Venn — §3.1); пространство ~7.5 млн пар ≫ 100к; паттерн — как `GeneratePlanetName` (расчёт в комментарии). Цена: часть сочетаний «не звучит» субъективно — компенсируется запасом ×75 |
| **C. Марковская модель по реальным именам** | Цепи переходов букв из корпуса имён | Самое «английское» звучание; но: корпус нужно собирать/встраивать (лицензия, объём), генерация медленнее, сложнее тест уникальности. Переусложнение для имён — не механика |

**Выбор: B.** Создатель выбрал слоговый — углубление в §3.

### Р4. Метрики: где живут

| Вариант | Механика | Цена / режим отказа |
|---|---|---|
| **A. Отдельная БД-таблица** | `npc_metrics` пишется на тик/пачку | Таблица + запись каждые 5 с = постоянная нагрузка на БД ради инструмента замеров; история не нужна (тест — это сейчас) |
| **B. In-memory + живой COUNT при запросе (принято, вариант «а» создателя)** | Атомарные счётчики в Manager (тики, время тика) + счётчики «создано пачкой»; `overdue_arrivals` — **живой COUNT** (`flying AND arrive_at <= now`) при каждом запросе метрик; `agents_total/flying` — лёгкие COUNT по индексу | Нет БД-нагрузки на тик; COUNT на 100к — ~10–50 мс на запрос метрик (опрос раз в ~10 с) — приемлемо и именно это число показывает перегрузку (решение создателя: вариант (а)). При рестарте счётчики сбрасываются — для теста это норм, отмечено явно. Отчёт пачки — в `statusManager.SetReport` |
| **C. PostgreSQL `pg_stat_*`** | Готовые системные метрики | Не про наши очереди (не видно «наши прибытия просрочены»), хрупко к версиям |

**Выбор: B.**

### Р5. Пагинация списка: offset vs cursor

| Вариант | Механика | Цена / режим отказа |
|---|---|---|
| **A. `LIMIT/OFFSET`** | `OFFSET 1000 LIMIT 200`, сортировка `created_at DESC` | Прост, но Postgres сканирует все пропущенные строки: глубокая страница при 100к — деградация O(offset); стабильность страниц при вставках — плавает. Для админки с «листают свежих» — приемлемо, но неоптимально |
| **B. Cursor / keyset (принято)** | `WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT n`; курсор — opaque-строка в ответе | O(глубина страницы) при 100к — постоянная цена любой страницы; «показать ещё» = передать `next_cursor`; новых вставок не боится (вставки новее первого курсора — наверх, стабильность). Цена: контракт чуть сложнее, движение «назад» — ещё один курсор (не нужен для «показать ещё») |

**Выбор: B.** Ключевое свойство для задачи: **после массовой генерации пачка должна быть видна сверху** — обе схемы дают это при сортировке `created_at DESC` (пачка пишется с одинаковым `created_at = NOW()` транзакции, новее старых). Выбираем cursor за стабильную стоимость на 100к. Сортировка по имени не нужна: админка смотрит свежих; поиск по имени — отдельный игровой эндпоинт (§6).

### Р6. Поиск агента: где живёт и как центрирует

| Вариант | Механика | Цена / режим отказа |
|---|---|---|
| **A. В админке, с переходом на карту** | Поле во вкладке NPC → после выбора переключает на карту | Разрыв контекста: карта отдельная страница, переход теряет выбор; два UI |
| **B. На карте (принято)** | Поле + кнопка в контролах карты (`#zoom-controls`, рядом с «🎯 Найти меня») → центрирование вьюпорта на агенте + подсветка иконки | Создатель: «на карте кнопку». Единый контекст; механизм центрирования уже есть (`centerViewport`, `navigation.js`) — экспортируется; новые агенты и так видны на карте (20a §7). Цена: игровой эндпоинт поиска (по имени — ILIKE; по id — точный) + подсветка иконки |
| **C. Глобальное поле поверх карты** | Поиск в шапке сайта | Подходит под «найти всё» (миры, агенты, товары) — это отдельная фича поиска, для одной кнопки избыточно |

**Выбор: B.** Углубление в §6.

## 3. Генератор имён агентов — `internal/names/agent.go`

### 3.1. Устройство

Два слоговых пула на имя и два на фамилию (плюс «пустое» окончание у фамилии — односложные «Hale», «Venn»):

```
имя     = слог1_имени + слог2_имени        («Mar» + «ion» = Marion, «Cy» + «rus» = Cyrus)
фамилия = основа_фамилии + окончание_фамилии («Hal» + «e» = Hale; «Ven» + ∅ = Venn)
полное  = имя + " " + фамилия              «Marion Hale»
```

- **Слог1 имени** (~60 шт): сильные открывающие: `Mar, Cy, No, Ad, Bri, Car, Dan, El, Em, Er, Ev, Fel, Gab, Hal, Hel, Jan, Jen, Jo, Ka, Ke, Lan, Leo, Lu, Ma, Mel, Mic, Na, Ni, Ol, Pa, Pe, Phi, Ra, Re, Ri, Ro, Ru, Sa, Se, Si, So, Ste, Ta, Te, The, Tho, Ti, To, Va, Ve, Vi, Wal, Wil, Za, Ze...`
- **Слог2 имени** (~56 шт): финали: `a, e, i, o, an, en, in, on, un, er, or, ar, el, al, id, ad, us, is, os, as, ie, ia, io, ew, ow, ay, ey, yn, ot, et, it, at, ace, ian, ion, iel, eon, ose, ene, ine, one, ard, ert, ick, iff, igh, ille, ish, itt, ock, oyd, ull, yle...`
- **Основа фамилии** (~75 шт): `Hal, Ven, Por, Shaw, Crane, Whit, Ash, Bell, Brook, Carr, Clay, Cole, Cross, Dale, Dean, Dell, Drake, Fenn, Ford, Frost, Gale, Grant, Gray, Hart, Holt, Kent, Kirk, Lane, Lark, Leith, Lind, Lorn, Marsh, Moore, Moss, Neal, North, Park, Penn, Pike, Price, Quinn, Reed, Rook, Rose, Scott, Sloan, Smith, Snow, Stark, Stone, Storm, Swift, Tate, Thorn, Vane, Voss, Wade, Ward, Wayne, Webb, West, Wren, Yale, York...`
- **Окончание фамилии** (~30 шт, включая «∅» с вероятностью ~30%): `e, a, er, or, et, ell, en, ing, ley, man, son, sen, s, es, ey, ock, ort, ose, eld, burg, ford, wood, house, field, shore...` + пустое (фамилия = основа).

**Комбинаторный расчёт (комментарий в коде, как `GeneratePlanetName`):**
`имён = 60 × 56 = 3360`; `фамилий = 75 × 30 = 2250`; **пар = 3360 × 2250 ≈ 7.5 млн**.
- Цель: 100к агентов → заполняемость пространства **~1.3%** — коллизии редки, в среднем ~1.01 попытки на имя (генерация 100к имён — десятки миллисекунд).
- Запас: **×75 от цели**. Даже если субъективно «не звучит» половина сочетаний, остаётся ~3.7 млн пар (×37) — до предельной заполняемости, после которой генерация замедляется, не дойти в 26a (100к + повторные пачки).
- Страховка от деградации пулов при правках: **unit-тест «комбинаторное пространство ≥ 1 млн»** (DoD, §12).
- Fallback при исчерпании (недостижимо в 26a, но паттерн существующих генераторов требует): `"Agent-" + randomSuffix(rng)`, как `GeneratePlanetName` → `"Planet-XXXX"`.

### 3.2. Уникальность и память

- Уникальна **пара «имя-фамилия»** (полная строка), не отдельно имена/фамилии — однофамильцы и тёзки допустимы (имена и фамилии не обязаны быть уникальны по отдельности).
- Паттерн `usedNames map[string]bool` (как планеты). **Гарантия между пачками:** перед генерацией пачки в map загружаются существующие имена из БД (`SELECT name FROM npc_agents`, одна колонка, один запрос — `ListNames()`, §4.1).
- **Память:** 100к ключей ≈ **6–10 МБ** (заголовок строки 16 Б + данные ~16 Б + overhead map ~30–50 Б на entry). Плюс seed из БД при 100к существующих — ещё до ~10 МБ, временно (освобождается после пачки). Суммарно < 25 МБ transient — для сервера приемлемо (оценка; точные цифры — бенчмарк 26b).
- UNIQUE-индекс на `name` в БД **не вводим**: уникальность гарантирует генератор (как для планет/звёзд), индекс на 100к строк текста — лишний вес на каждую вставку; коллизия между пачками исключена seed'ом. Осознанное решение, в 26b при прогонах подтвердить.

### 3.3. API генератора

```go
// names/agent.go
// GenerateAgentName — «имя-фамилия» из слоговых пулов (§3.1). Гарантированно
// уникальна относительно usedNames (map растёт на каждой генерации).
// Использовать только с локальным *rand.Rand вызывающего (AGENTS.md §0).
func GenerateAgentName(rng *rand.Rand, usedNames map[string]bool) string
```

Сигнатура ровно как `GeneratePlanetName`: без `error` (fallback как у существующих), пакет `names` так устроен. Отдельный bulk-метод генератора не нужен: хендлер циклом вызывает функцию (локальный rng на джоб — AGENTS.md §0, общие `*rand.Rand` не потокобезопасны). Загрузка seed-имен — метод репозитория `ListNames` (§4.1).

## 4. Массовая генерация (бэкенд)

### 4.1. Поток операции

```
POST /admin/npc/generate {"count": N}          (валидация §4.3)
  → statusManager.TryStart(JobGenerateNPC, N, cancel)
  → 202 {"status":"started"}  |  409 при уже идущем джобе  |  400 при невалидном count
  → горутина:
      1. seed-карта имён: SELECT name FROM npc_agents (ListNames) → usedNames
      2. список миров галактики из сетки (RandomWorlds, §4.4) — предвычислен один раз
      3. цикл i = 0..N: имя = GenerateAgentName(localRng, usedNames);
         мир = allWorldIDs[rng.Intn(len)] ; агент = {ID: uuid, Name, CurrentWorldID,
         NotifyEnabled: false (§7)}
         каждые 10к → statusManager.Progress(JobGenerateNPC, i)
      4. NPCRepository.BulkInsert(agents) — одна COPY-транзакция (§4.2)
      5. statusManager.SetReport: «✅ Создано агентов: N за X.X с»
         + manager.RecordBulk(count, duration) — метрика in-memory (§8)
      6. statusManager.Done | Fail(err)  (panic → Fail, как в admin_hypothesis.go)
```

Прогресс по итерациям генерации имён (быстрая фаза), вставка — последним одним скачком: `Progress` → `Total` перед COPY, `Done` после. Фронт видит «из 100000 обработано 100000» и ждёт отчёта. При очень большом N (миллион) джоб просто дольше работает — прогресс виден, UI не блокируется.

**Источник миров — без N запросов к БД:** сетка миров уже живёт в `manager.worldGrid` (immutable между генерациями вселенной). Перечень id — предвычисленный **слайс `allIDs` в `worldGrid`**, строится в `buildGrid` (одно поле, O(n) — встроено в уже существующий проход, И2 не нарушается). Выбор стартового мира пачки: `worldGrid.randomWorlds(rnd, n)` — N раз `ids[rnd.Intn(len)]`, O(1) на агента, **без** N запросов и без построения слайса на каждый вызов (проблема текущего `RandomWorld()`: `make([]string, len(byID))` на каждый вызов — при 100к агентов 100к × O(миры) = нельзя).
- `RandomWorld()` (используется одиночным созданием, спека §8) рефакторится на `allIDs[rnd.Intn(len)]` — поведение то же, код проще.
- Повторы стартовых миров **допустимы** («случайные по всей галактике» ≠ «разные миры»): при 100к агентов и карте в ~20к миров — ~5 агентов на мир в среднем; редкий мир не «забивается». Уникальность распределения — вне 26a.

**Статус новых агентов: `idle`** (как одиночное создание, спека 20a.1 §8). `flying` сразу не вводим: маршрут и кортеж полёта — зона единственного писателя `NPCManager` (И1, спека §9); создание пишет только `idle`-строку. Планировщик развезёт 100к за ~50 тиков (~250 с при 5с-тике, спека §2.2.A).

**Новые методы репозитория `npc_repository.go`:**
```go
// BulkInsert — массовое создание агентов одной COPY-операцией (§4.2).
// Транзакция: все или ничего. Повторный запуск с тем же count — новая пачка.
// notify_enabled = false для всех (§7: пуши — только через глобальный рубильник).
func (r *NPCRepository) BulkInsert(agents []models.NPCAgent) error

// ListNames — все имена агентов (seed уникальности, §3.2). Одна колонка.
func (r *NPCRepository) ListNames() ([]string, error)
```

### 4.2. Оценка объёма и времени (ориентиры производительности, не баланс)

- **Строка COPY** (колонки `id, name, status, current_world_id, notify_enabled, created_at, updated_at`; пустые колонки полёта не входят — DEFAULT NULL): uuid 36 + name ~10–18 + status 4 + uuid 36 + bool 1 + 2×timestamptz ~16 ≈ **~120–150 Б/строка**.
- **100к строк ≈ 12–15 МБ** через COPY. Оценка: COPY 100к — **~1–3 с** (ориентир по опыту массовых вставок проекта (`planet_data_batch.go`); точные числа — бенчмарк 26b), генерация имён 100к — десятки мс (§3.1), UUID — ~0.1 с. **Итого пачка 100к ≈ 2–5 с** — это и показывает метрика `duration_ms`.
- Для сравнения: 100к одиночных `Insert` ≈ 100–300 с (§2, Р2-A) — неприемлемо; multi-row VALUES с лимитом 65535 параметров — пачки ~4000 строк, медленнее COPY в 5–10× (комментарий `planet_data_batch.go`).

### 4.3. Валидация и лимиты

- `count` — целое, **`count ≥ 1`** (решение создателя: **без верхнего лимита**). Иначе `400 {"error": "count должен быть ≥ 1"}`. Паттерн валидации — как в админ-хендлерах (`admin_npc.go` — 400 с текстом).
- **Защита от ошибок — на фронте:** confirm при больших N, disabled-кнопка во время джоба, тост ошибок. Сервер лимит не накладывает; джоб итерирует по N — безопасно при любом разумном N, прогресс виден.
- **409** — если `JobGenerateNPC` уже крутится (`TryStart`), как во вселенной/гипотезах. Защита от двойного клика и параллельных админов (джобы пишут в одни таблицы и не знают о соседе, AGENTS.md §23).
- **400 «Нет миров для старта»** — если снапшот карты не готов/галактика пуста (сетка пуста, как `resolveStartWorld`).
- Отмена (Cancel) в 26a не вешаем: `Cancel` висит в `statusManager` для всех джоб; для пачки — лишний UI (кнопка «Отмена»); при необходимости добавится позже без изменения контракта.

### 4.4. Точки интеграции

- `internal/generator/status.go`: константа `JobGenerateNPC JobType = "generate_npc"` — **одна строка**, статусные ручки `/admin/generate-status` и `Cancel` работают без изменений.
- `internal/handlers/admin_npc.go`: в `HandleObject` (диспетчер `/admin/npc/{path}`) секции `path == "generate"` → POST-хендлер, `path == "metrics"` → GET-хендлер (как существующий `path == "settings"`).
- `AdminNPCHandlers` получает доступ к `h.db` для COPY? Нет — COPY в репозитории (`BulkInsert`), хендлер только собирает агентов и вызывает метод. Природа: репозиторий владеет БД, хендлер — оркестрация (существующее разделение: `CreateAgent` → `npcRepo.Insert`).

## 5. Пагинация списка агентов — `GET /admin/npc`

### 5.1. Проблема и решение

Сейчас `GET /admin/npc` возвращает всех агентов (`ListAll` → JSON). При 100к: SELECT 100к строк + ~20 МБ JSON каждые 10 с (авторефреш вкладки) — тяжело и БД, и сети. Вводим постраничный вывод (решение создателя: пагинация в этой фиче).

**Сортировка:** `created_at DESC, id DESC` — свежие сверху. **После массовой генерации пачка видна на первых страницах целиком**: все строки пачки пишутся одной COPY-транзакцией с одинаковым `created_at = NOW()` (время старта транзакции), которое новее старых агентов; внутри пачки порядок по uuid-идам (tie-breaker). «Видеть свежих» — выполнено.

### 5.2. Контракт

```
GET /admin/npc?limit=200&cursor=<opaque>   (AdminAuth) → 200
{
  "agents": [ ...NPCAgent (текущее интерполированное состояние, как сейчас)... ],
  "next_cursor": "MTIwMi0wOS0xNVQxMjowMDowMFosMTIzZTQ1Njct..." | null
}
```

- `limit` — размер страницы, default **200**, max **1000** (защита от гигантских ответов; вне диапазона — 400).
- `cursor` — opaque-строка: `base64url(created_atRFC3339Nano + "," + id)` точки последней записи предыдущей страницы. Пустой/отсутствующий — первая страница. Невалидный cursor — 400.
- `next_cursor = null`, когда страниц больше нет (конец списка) — фронт прячет «Показать ещё».
- SQL (keyset):
  ```sql
  SELECT <колонки> FROM npc_agents
  WHERE (created_at, id) < ($1, $2)          -- первая страница: без WHERE
  ORDER BY created_at DESC, id DESC LIMIT $3;
  ```
- `total` не отдаём (лишний COUNT при каждом опросе не нужен; счётчики — в метриках §8).

### 5.3. Индекс

Нужна **лёгкая миграция `000027_npc_indexes.sql`**:

```sql
CREATE INDEX IF NOT EXISTS idx_npc_agents_created_id ON npc_agents (created_at DESC, id DESC);
```

Без неё keyset-фильтр + сортировка на 100к — sort всей таблицы на каждый запрос страницы (~50–100 мс). С индексом — O(страница). Индекс `(status, id)` (000026) остаётся для планировщика; новый — аддитивен, на тик не влияет.

### 5.4. Фронт

- Таблица вкладки: первая страница при загрузке/авторефреше (10 с) — всегда свежие сверху; при том же `next_cursor` авторефреш не трогает доп. страницы? Нет — авторефреш **сбрасывает к первой странице** (простое и предсказуемое: вкладка показывает «сейчас»), накопленные страницы перерисовываются.
- Кнопка **«Показать ещё»** под таблицей: аппендит следующую страницу к DOM (`next_cursor` из ответа), скрывается при `null`; счётчик «показано N».
- Малые объёмы (страниц нет) — одной страницы хватает, кнопки нет — поведение неотличимо от текущего.

## 6. Поиск агента на карте

### 6.1. Эндпоинт (игровой)

```
GET /api/npc/search?q=<строка>&limit=20   (игровой JWT) → 200
{
  "results": [
    {"id": "...", "name": "Marion Hale", "status": "flying",
     "x": 123.4, "y": 567.8,          // интерполированная позиция на now (как /api/npc/positions)
     "world_id": "..."}               // текущий мир (idle) или цель полёта
  ]
}
```

- `q` — обязателен, после trim непустой, ≤ 100 символов (400 при нарушении).
- **Поиск:** если `q` — валидный UUID → точное совпадение по `id` (PK, быстрый, 0–1 результат). Иначе — `name ILIKE '%q%'` (регистронезависимо), `LIMIT` (default 20, max 100).
- **Позиция** — из существующего in-memory snapshot `PositionCache` (§2.2.B 20a.1): линейный поиск по id в слайсе — ≤ 20 × 100к сравнений на запрос, разово, приемлемо. Агента нет в snapshot (миров нет в сетке) — `x/y` = null; клиент центрирует только при наличии.
- **SQL** — `SELECT id, name, status, current_world_id, target_world_id FROM npc_agents WHERE name ILIKE $1 LIMIT $2`: на 100к — seq scan ~10–50 мс. Для разового поиска приемлемо; при частом использовании — `pg_trgm`-индекс (кандидат 26b, §14).
- Ошибки — `{"error": "..."}`. Это **игровая** ручка (карта — игровая страница, агенты на ней видны игрокам — спека 20a.1 §7), НЕ админская.

### 6.2. Клиент карты

- **UI:** компактное поле + кнопка «🔍 Найти агента» в `#zoom-controls` (`web/map.html`, рядом с существующей кнопкой «🎯 Найти меня»).
- **Центрирование:** механизм уже есть — `centerViewport(x, y)` в `web/static/js/map/navigation.js` (не экспортирован → экспортировать, либо обёртка `focusOnPoint`). Подсветка: `state.highlightedNpcId` (`config.js`) + ореол вокруг иконки в `drawNPCAgents` (`npc_agents.js`); сброс — при новом поиске или клике по пустому месту карты.
- **Результаты:** 0 → тост «Не найден»; 1 → центр + подсветка; >1 → мини-список (до 10, имя + мир) над полем, клик по пункту → центр + подсветка. Зум при центрировании сохраняется (минимум 1.0), как `centerViewport`.

## 7. Пуши: глобальный рубильник + per-agent

### 7.1. Решение создателя (вариант «а»)

Глобальный рубильник уведомлений **«на всех агентов»** в настройках вкладки NPC, **по умолчанию выключен**; per-agent переключатели в таблице остаются. Мотивация: галка для отладки при малом числе агентов (≤50), при больших количествах пуши не нужны (флуд). **Меняет решение 20a §10.6** («глобальный рубильник не нужен») — в 20a.1 внесены пометки (§5, §8, §10.6).

### 7.2. Хранение

Настройки NPC живут **в памяти** `Settings` (`internal/npc/settings.go`, спека 20a.1 §2.4: «механизма БД-настроек в проекте нет, таблица ради пяти чисел не вводится»). Новое поле:

```go
// Settings
notifyGlobalEnabled bool // глобальный рубильник пушей, default false
```

После рестарта — снова `false` (выключен). Это соответствует мотивации создателя («включить для отладки, поиграться, выключить»): персистентная «включённость» пушей не нужна и опасна (забыл включённой → флуд после рестарта). Развилка «память vs БД» — расширение Р4: остаёмся в памяти, консистентно с остальными настройками NPC.

### 7.3. Взаимодействие с per-agent

```
уведомление отправляется ⇔ notifyGlobalEnabled И agent.notify_enabled
```

- Гейт — в `Manager.processArrivals` (единственная точка отправки): `if m.settings.NotifyGlobalEnabled() && a.NotifyEnabled { m.notifier.NotifyArrival(...) }`. Логика тика не меняется — только условие отправки.
- Per-agent чекбоксы в таблице остаются, но **эффект имеют только при включённой галке**. В UI — подпись при выключенной галке: «Глобальные пуши выключены — per-agent переключатели не действуют».

### 7.4. Дефолт новых агентов

**`notify_enabled = false`** (меняется текущее поведение 20a §8 «создание с уведомлениями»):
- одиночный `Insert` (POST /admin/npc) больше не пишет `true` — пишет `false` явно;
- массовая `BulkInsert` — `false` для всех (§4.1);
- **существующие агенты не трогаем** (в БД у старых может быть `true` — эффекта нет, пока рубильник выключен).

Включение — галка (глобально) или per-agent чекбокс (под галкой) — как отладка на малых числах.

### 7.5. Контракт настроек

`GET /admin/npc/settings` и `PATCH /admin/npc/settings` расширяются полем `notify_enabled_global` (bool):
- GET → `{"speed_factor":…, "tick_interval_sec":…, "batch_size":…, "notify_interval_sec":…, "notification_max_batch":…, "notify_enabled_global": false}`;
- PATCH `{"notify_enabled_global": true}` → применяется сразу.

## 8. Метрики поведения

Минимальный набор инструмента замеров (тест 10-50-100к). Без отдельной таблицы (§2, Р4): in-memory в `Manager` + **живые COUNT** при запросе (вариант «а» создателя).

### 8.1. Состав

| Метрика | Источник | Цена |
|---|---|---|
| `last_bulk.count` / `duration_ms` / `finished_at` | память `Manager` (`RecordBulk`, пишет джоб по завершении §4.1) | 0 (пишется раз за пачку) |
| `agents_total` | `COUNT(*)` | ~10–50 мс на 100к при запросе |
| `agents_idle` / `agents_flying` | `COUNT(*) ... WHERE status=?` (индекс `(status,id)`) | ~5–20 мс |
| `overdue_arrivals` — **очередь на тик** | **живой COUNT** `COUNT(*) WHERE status='flying' AND arrive_at <= now` при каждом опросе метрик (вариант «а», решение создателя) | ~10–50 мс (фильтр по времени не покрыт индексом целиком — bitmap/seq scan сотни тысяч строк; опрос раз в ~10 с — приемлемо; именно эта цифра показывает перегрузку) |
| `scheduler.last_tick_ms` / `last_tick_at` / `ticks_total` / `full_batches` | atomic-счётчики в `Manager` (замер вокруг `tick()`, `full_batches` — сколько раз прибытия заняли весь `batchSize` = очередь не разобрана за тик) | 0 |

`overdue_arrivals` — главный индикатор «лагов планировщика» (спека 20a.1 §2.2.A: при перегрузке очередь растёт, данные не теряются): растёт, когда поток прибытий превышает бюджет тика. `last_tick_ms` — занятость тика (ListAll 100к каждые 5 с — спека 2.2.B, может быть секунды при 100к — метрика это покажет). `full_batches` — кумулятивный счётчик перегрузок.

### 8.2. Контракт

```
GET /admin/npc/metrics   (AdminAuth) → 200
{
  "agents_total": 12345,
  "agents_idle": 3000,
  "agents_flying": 9000,
  "overdue_arrivals": 500,
  "scheduler": {
    "last_tick_ms": 42.5,
    "last_tick_at": "2026-09-15T12:00:00Z",
    "ticks_total": 120,
    "full_batches": 3
  },
  "last_bulk": {
    "count": 100000,
    "duration_ms": 2300,
    "finished_at": "2026-09-15T11:59:58Z"
  } | null
}
```

- `last_bulk` = `null`, если пачка ещё не запускалась (с рестарта — снова null, метрики in-memory; для инструмента замеров это ок, отмечено).
- Отчёт последней пачки дублируется в `statusManager.report` (`GET /admin/generate-status?job=generate_npc`) — фронт видит результат без отдельного запроса метрик.
- Расположение: новый файл `internal/handlers/npc_metrics.go` (как `npc_settings.go`), чтение COUNT — методы-счётчики репозитория (`CountTotal/CountByStatus/CountOverdue` или один `Metrics()`), счётчики планировщика — `manager.Metrics()`.

## 9. Фронт (вкладка «NPC», npc.js + admin.html)

**Блок «Массовая генерация»** (над таблицей агентов, рядом с одиночным созданием):
- Поле `input` (число) + кнопка **«Сгенерировать N агентов»**.
- **Подтверждение** для больших N (`confirm`; порог ≥ 1000, чтобы и 10к, и миллион спрашивали; текст: «Создать N агентов? Операция необратима, пачка пишется одной транзакцией»). Малые N — без confirm (быстро и обратимо удалением).
- Запуск: `POST /admin/npc/generate {count}` → 202 → `pollJob('generate_npc', ...)` (существующий `poll.js`, прогресс + отчёт: «✅ Создано агентов: 100000 за 2.3 с»). 409 → тост «Генерация уже идёт».
- Во время джоба кнопка disabled (защита от дурака на фронте, §4.3). После `done` — `loadNPC()` (обновить таблицу, первая страница) + `loadNPCMetrics()`.

**Таблица агентов — пагинация** (§5.4): первая страница при загрузке/авторефреше, кнопка «Показать ещё».

**Настройки** (§7.5): чекбокс «Пуши прибытий (глобально)» в блоке настроек + подпись «per-agent переключатели работают только при включённой галке»; сохранение — `PATCH /admin/npc/settings {notify_enabled_global}`.

**Блок «Метрики»** (верх вкладки, компактная строка):
- `Агентов: 12345 · В полёте: 9000 · idle: 3000 · Очередь на тик: 500 · Тик: 42 мс · Последняя пачка: 100000 за 2.3 с`.
- Опрос `GET /admin/npc/metrics` раз в ~5 с (отдельный интервал; `loadNPC` остаётся на 10 с).
- `overdue_arrivals > 0` и `full_batches > 0` — выделение цветом (жёлтый/красный) — лаги видны без чтения цифр.

## 11. Инварианты и границы

**Проверка по инвариантам 20a.1 §9 (и двенадцати глобальным):**

- **И1 (многопользовательность / единственный писатель).** Массовая генерация пишет только строки-создание (`idle` + стартовый мир + `notify=false`) — как существующий `CreateAgent`; смены состояния (`idle→flying→idle`) остаются за `NPCManager` (единственный писатель статусов, batch-транзакции). `usedNames` и `allIDs` — локальные данные джоба/immutable сетка (atomic.Pointer, чтение из хендлера — AGENTS.md §0). Поиск на карте — только чтение. Соблюдено.
- **И2 (стоимость не от размера галактики).** Выбор стартового мира «случайно по всей галактике» — **одноразовая операция при создании**, на тик не влияет (тик читает `allIDs` — предвычисленный слайс, O(1) на выбор). Массовая генерация — разовая операция админа, не периодический расчёт. Пагинация — O(страница) по индексу `(created_at, id)`, добавляется без затрагивания тика. Соблюдено.
- **И5, И8, И12 (информация/рычаги/NPC-пол):** не затронуты — фича инструментальная (админка + карта), поведение агентов то же; поиск агента — это «посмотреть», не рычаг (И8).
- **И10 (сущность оправдана решением):** новых сущностей нет (§1, сверка с DB.md); новый индекс — не сущность.

**Границы (хирургичность):**
- Механика полёта/наблюдения/уведомлений 20a.1 не меняется: пуши — только дополнительный гейт `global AND per-agent` в единственной точке отправки (§7.3), логика тика не трогается.
- Контракт `/api/npc/positions` и игровые ручки (кроме **нового** `/api/npc/search`) не меняются.
- Числа баланса полёта (`npcSpeedFactor`, формула длительности, batch/tick дефолты) не трогаются.
- Новая таблица не вводится; одна миграция — **только индекс** (000027, §5.3), аддитивна.
- Изменения контрактов 20a.1: `GET /admin/npc` (пагинация, §5), дефолт `notify_enabled` новых агентов (false, §7.4), уведомления (глобальный рубильник, §7) — все три помечены в 20a.1.

**Известные ограничения (зафиксированы):**
1. Метрики и рубильник пушей in-memory — сбрасываются при рестарте сервера (рубильник — намеренно, §7.2; метрики — для инструмента замеров ок).
2. Уникальность имён гарантируется генератором + seed'ом из БД, не UNIQUE-индексом (решение §3.2).
3. Прогресс джоба на фазе COPY не поштучный (скачок до Total) — вставка одна транзакция, поштучный прогресс внутри неё — лишнее.
4. Поиск по имени (`ILIKE '%q%'`) — seq scan на 100к (~10–50 мс); при частом использовании — `pg_trgm`-индекс (кандидат 26b).

## 14. Открытые вопросы

Закрыты решениями создателя 2026-09-15: лимит count (без лимита), пагинация (в фиче), поиск на карте (в фиче), рубильник пушей (общая галка, выключена), overdue (вариант «а» — живой COUNT), кланы (заметка в GDD, вне 26a).

Осталось (не блокеры, отмечены для менеджера/26b):
1. **Пагинация: cursor-keyset + «показать ещё»** (§5) — принято в спеке; если создатель предпочтёт классические страницы с номерами — переделать контракт (цена: +total COUNT, курсор «назад»).
2. **Поиск по имени — seq scan** на 100к ~10–50 мс (§6.1, ограничение 4 §11). Ок для разового поиска; если поиск станет частым — `pg_trgm`-индекс логичнее делать в 26b вместе с бенчмарком.
3. **`confirm`-порог массовой генерации** (предложение: ≥ 1000, §9) — косметика, создатель может поменять.
4. **26b** — бенчмарк 10-50-100к: прогон метрик, времени COPY и памяти имён на целевом объёме; кандидаты: trgm-индекс, EXPLAIN-проверка keyset на 100к.

Счётчик FAQ не тронут: новых эталонов мира/баланса в фиче нет (решения создателя зафиксированы в идее и спеке, не в FAQ-реестре GDD).
