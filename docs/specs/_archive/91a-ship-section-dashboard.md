## 0. Резюме (одним абзацем)

Вводится **полноценный раздел «Корабль»** на странице дашборда `/` (`web/index.html`), по референсу «космические рейнджеры»: экран корабля со слотами модулей и характеристиками. Раздел показывает **только личное** (решение создателя 2026-09-18): модель корабля (имя), 3 активных слота (радар / сканер / двигатель) с установленными модулями и их характеристиками (радар — радиус 800 px; сканер — глубина «поверхность» + поселения; двигатель — **настоящий модуль** `engine_1`, скорость 0.3 сек/px), плюс **пустые ячейки под будущие слоты** (задел, без подписей). **Двигатель становится настоящим модулем** (решение создателя, круг 2): добавляется в каталог (`engine_1`, params `{"speed_factor": 0.3}`), выдаётся в стартовую комплектацию (радар + сканер + двигатель), полёт берёт скорость из установленного двигателя (`ship.EngineSpeed`, значение не меняется — 0.3, меняется источник); **без двигателя корабль НЕ ЛЕТАЕТ** (решение создателя, уточнение гейта: «не может летать без двигателя») — `/travel` для `role=player` без установленного двигателя отказывает, фолбэка-скорости нет; админ/skycomposer — исключение (летают всегда); NPC-агенты не трогаются (своя настройка `npcSpeedFactor`). Каталог «что бывает» в UI **не показывается**. Визуал корабля — **только превью** (спрайт+цвет 61b); селектор 61b **не встраивается и не переносится** (легаси, остаётся как есть — корабль станет физическим объектом с покупкой/продажей, будущее). Формат модулей — **ячейки-слоты на силуэте корабля** (схематичный контур SVG/CSS, без новых ассетов). Серверная часть — **аддитивное расширение `/me`** (по прецеденту `ship_options`): имя модели, каталог оборудования (`id`/`type`/`name`/`params`, включая `engine_1`) и `ship_speed_factor` из двигателя; существующие поля `/me` не меняются. Миграция `000043` — `engine_1` в каталог + бэкфилл существующих игроков. Энциклопедия «Корабли/оборудование» (86a §5.5) — **не в скоупе** (отдельная далёкая задача). Новых сущностей БД **нет** (двигатель — запись существующей таблицы `equipment`), новых чисел баланса **нет** — характеристики это факты каталога и константа 66a.

## 2. Природа сущностей — разбор по правилу «сущность с двумя экземплярами»

1. **Раздел «Корабль»** — **слой отображения** (UI), не сущность: показывает данные, которые уже существуют (модель корабля, установленное оборудование, скорость). Своей таблицы не имеет, новых сущностей не вводит.
2. **Каталог оборудования** — существующая сущность-справочник (77a §3, таблица `equipment`, in-memory `internal/ship/catalog.go`). Природа: справочник/каталог, владелец — все игроки, расширяемость — таблица переживает новые типы (двигатель, уровни радара) без изменения схемы. **Двигатель `engine_1` — новая запись существующей таблицы** (тип `engine` уже заложен CHECK-ограничением 77a §3.2), не новая сущность. 91a отдаёт каталог клиенту (новый канал, не новая сущность).
3. **Модель корабля** — существующая сущность-справочник (77a §2, таблица `ship_models`). 91a отдаёт имя модели клиенту (сейчас отдаётся только `ship_model_id`).
4. **Журнал открытий / статистика** — не затрагивается: раздел «Корабль» не участвует в «открыто X из Y» (это личная оснастка, не справочник; открывать нечего — «только личное»).

**Анти-ловушка «сущность вне игры» (обязательный разбор):**

- **Двигатель как механика скорости** — до 91a отсутствовал в игре (слот `engine` пуст, предметов двигателей в каталоге нет, скорость от двигателя не зависела). **91a вводит двигатель в игру** (запись каталога + стартовая выдача + источник скорости + **требование полёта**: без двигателя корабль не летает) — это первый шаг замысла 77a §1.3 («скорость будет зависеть от установленных двигателей и загруженности»). Полная механика (загруженность, разные двигатели, рынки) — вне скоупа (§9). Двойного учёта нет: скорость была константой 0.3 и остаётся 0.3 — меняется только источник (из установленного двигателя), новые числа не вводятся; запрет полёта без двигателя — новое правило, но при стартовой выдаче и бэкфилле (`000043`) у всех игроков двигатель есть (крайний случай — теоретический, §8).
- **Рынки оборудования** — в игре отсутствуют (77a: покупка/смена оборудования — будущие локальные рынки, вкладка «Оборудование»). **Влияние исключено:** раздел ничего не покупает и не продаёт, только показывает установленное; кнопок покупки/смены нет (§9).
- **Энциклопедия «Корабли/оборудование»** (86a §5.5) — заготовка без контента, отдельная далёкая задача (решение создателя 2026-09-18). **Не влияет:** раздел «Корабль» — личная оснастка, энциклопедия — справочник; контент не дублируется (раздел показывает только установленное, энциклопедия — «что бывает», когда появится).
- **NPC-агенты** — не затрагиваются: у них своя настройка скорости `npcSpeedFactor` (0.3, `internal/npc/settings.go`), механика без изменений (§9). «Скорость игрока» для NPC остаётся константой — это их собственная настройка, не производная от оборудования игроков.

## 3. Состав раздела «Корабль»

### 3.1. Расположение и структура

Раздел «Корабль» — отдельная карточка на дашборде `/` (рядом с существующими: шапка профиля, статистика, энциклопедия). Существующий блок «Корабль» (селектор спрайта/цвета 61b) **не трогается** — остаётся как есть, в стороне (легаси, §3.3).

Структура раздела сверху вниз:

1. **Шапка раздела:** превью корабля (спрайт `ship_icon` + цвет `ship_color`, переиспользование `recolorShipSprite` из `web/static/js/map/ship_sprites.js` — как в шапке профиля 86a §4.1) + имя модели (например, «Стартовый разведчик», из `/me.ship_model.name`, §7).
2. **Силуэт корабля со слотами:** схематичный контур-силуэт (SVG/CSS, без новых ассетов), на котором размещены ячейки-слоты: 3 активных (радар / сканер / двигатель) с установленными модулями и пустые ячейки будущих слотов (§4, §5).
3. **Характеристики корабля (сводно):** радиус радара, возможности сканера, скорость (§6).
4. **Внешний вид:** только превью корабля (в шапке раздела, §3.3) — селектор 61b не встраивается.

### 3.2. Только личное (решение создателя)

Раздел показывает **только установленное у игрока**: модули из `users.equipment` (по слотам модели), их имена и характеристики из каталога. Каталог «что бывает» (другие предметы, уровни, ассортимент) **в UI не показывается** — клиент получает данные только для установленного (§7). Будущие слоты (§5) — это рамка возможностей корабля (типы слотов, не предметы): показываются как **пустые ячейки** без названий и подписей.

### 3.3. Внешний вид — «почти легаси» (решение создателя, круг 2)

**Решение:** в разделе показывается **только превью** корабля (спрайт + цвет, переиспользование `recolorShipSprite`). Селектор 61b (смена спрайта/цвета: сетка 21 спрайта + палитра 9 цветов + «Оригинал», PUT `/me/ship-icon` + `/me/ship-color`) **НЕ встраивается и НЕ переносится** — остаётся как есть (легаси). Обоснование создателя: корабль станет физическим объектом с покупкой/продажей (как в КР) — будущее; сейчас менять селектор не нужно.

Развилка первого круга «встроить в раздел / оставить рядом» **закрыта** (решение круг 2): не трогаем. Не-регрессия 61b/86a — по построению (ничего не меняется).

## 4. Формат отображения модулей: ячейки-слоты на силуэте корабля

**Решение (создатель, круг 2):** ряд ячеек-слотов, **на силуэте корабля** — схематичный контур + отсеки, как в КР; простой SVG/CSS-силуэт, **без новых ассетов** (не спрайты, не картинки — кодовая фигура).

### 4.1. Как рисуется силуэт

- **Контур:** простой схематичный силуэт корабля (вид сверху/сбоку) — SVG-фигура или CSS-композиция (например, вытянутый корпус с носом и кормой), нейтрального цвета (тёмный контур на фоне карточки), без детализации. Рисуется кодом (inline SVG / CSS-блоки), не загружается как ассет.
- **Позиции слотов:** на силуэте размещаются ячейки-слоты в фиксированных позициях (как «отсеки» корабля):
  - **радар** — носовая часть (передняя);
  - **сканер** — средняя часть (центр);
  - **двигатель** — кормовая часть (задняя);
  - **будущие слоты** — свободные позиции (например, по бортам/под корпусом), пустые ячейки (§5).
- **Ячейка слота:** небольшой блок (иконка типа слота + имя установленного модуля или «пусто»); активные ячейки — с рамкой/подсветкой, пустые — приглушённые.
- **Иконки типов слотов** — простые символы/эмодзи (📡 радар, 🔭 сканер, ⚙️ двигатель), не новые ассеты (косметика, решается при разработке).

Точная геометрия силуэта (пропорции, позиции ячеек) — ТЗ при разработке; требование одно: читается как «экран корабля» с отсеками (КР), без новых ассетов.

### 4.2. Разворот подходов (история)

| Вариант | Как | Итог |
|---|---|---|
| **A. Ячейки-слоты на силуэте корабля (принято, круг 2)** | схематичный контур SVG/CSS + ячейки-отсеки (активные + пустые будущие) | принято создателем: «лучше на силуэте корабля (схематичный контур + отсеки, как в КР; простой SVG/CSS-силуэт, без новых ассетов)» |
| **B. Ряд ячеек-слотов без силуэта** (первый круг) | линейный ряд ячеек (иконка + имя модуля) | отклонено кругом 2: силуэт даёт «экран корабля» (КР) |
| **C. Только карточки установленных модулей** | сетка карточек по одному на модуль | отклонено: пустые слоты не видны, будущие некуда встроить, не КР |
| **D. Таблица** | «слот / модуль / характеристики» | отклонено: не «экран корабля» (КР) |

| **Трюм** | грузоподъёмность корабля — ядро экономики (перевозка товаров, контракты на перевозку, 11.3.4) | экономика Zorion |
| **Топливный бак** | дальность полёта — будущий ограничитель («дальность полёта по топливному баку ещё будет ограничиваться», 77a §7.3) | решение создателя 2026-09-17 (77a) |
| **Генератор** | энергия для оборудования корабля (аналог энергии построек, 11.1.2) | энергия как сущность |
| **Оружие** | оборона/война (война — потребитель товаров, GD_PROMPT); боевая система — далёкое будущее | референс КР |
| **Броня / щиты** | защита корабля (фронтир, риск); боевая система — далёкое будущее | референс КР |

Список **открытый** (правило «не закрывать открытые списки»): при появлении новых механик (связь, ремонтные дроны и т.п.) слоты добавляются в тот же ряд. Числа и механики будущих слотов **не проектируются** (вне скоупа, вернутся с рынками/боевкой — отдельные задачи).

### 5.2. Как показаны в UI (решение создателя, круг 2)

**Решение:** будущие слоты — **пустые ячейки** на силуэте корабля (§4.1): приглушённые ячейки без подписей «скоро» и без названий типов. Игрок видит, что у корабля есть свободные места под будущее, но не получает каталога «что бывает» (решение «только личное», §3.2).

Разворот подходов (история):

| Вариант | Как | Итог |
|---|---|---|
| **A. Пустые ячейки без подписей (принято, круг 2)** | приглушённые ячейки на силуэте, без названий и «скоро» | принято создателем: «просто видно, что есть свободные места под будущее» |
| **B. Заблокированные ячейки «скоро»** (первый круг) | серые ячейки с иконкой типа и подписью «скоро» | отклонено кругом 2: подписи/названия — это каталог «что бывает», противоречит «только личное» |
| **C. Не показывать** | только 3 активных слота | отклонено: задел не виден; при появлении механик слоты «появляются из ниоткуда» |

### 6.1. Полёт без двигателя (решение создателя, уточнение гейта)

**Решение: без двигателя корабль НЕ ЛЕТАЕТ** («не может летать без двигателя» — создатель). Фолбэка-скорости **нет**: полёт без установленного двигателя невозможен для `role=player`.

- **Серверная валидация `/travel`** (`internal/handlers/travel_handlers.go`): для `role=player` без установленного двигателя в слоте `engine` — отказ (ошибка 400/403, сообщение «Двигатель не установлен — полёт невозможен»). Проверка — новая функция `ship.HasEngine(equipment)` по образцу `ship.HasScanner` (`internal/ship/catalog.go`): установлен ли валидный двигатель (предмет существует в каталоге, тип `engine`).
- **Админ/skycomposer — исключение** (летают всегда, по аналогии с видимостью 77a: «админ и skycomposer видят всё навсегда»): валидация двигателя применяется только к `role=player`.
- **UI:** в ячейке слота двигателя при отсутствии — «не установлен»; полёт из интерфейса недоступен без двигателя (кнопка «Лететь» блокируется / показывает подсказку «Двигатель не установлен»). После миграции `000043` все игроки имеют двигатель — крайний случай теоретический, но правило честное.
- **NPC-агенты не трогаем** — у них своя настройка `npcSpeedFactor` (0.3), валидация двигателя только для `role=player`.

Разворот подходов (история): «0.3 без двигателя (фолбэк)» — **отклонено** (решение создателя на гейте: «не может летать без двигателя»); «—» — отклонено (теряется реальная информация); «зависит от двигателя» — отклонено (ложь при отсутствии механики); **«не летает без двигателя» — принято** (уточнение гейта).

## 7. Серверная схема: двигатель, отдача каталога и имени модели

### 7.1. Двигатель — настоящий модуль (решение создателя, круг 2)

**Сущность `engine_1`:**

| Поле | Значение |
|---|---|
| `id` | `engine_1` |
| `type` | `engine` (тип уже заложен CHECK-ограничением 77a §3.2) |
| `name` | «Двигатель-1» |
| `params` | `{"speed_factor": 0.3}` |

**Стартовая комплектация** (77a §3.3, обновляется): `users.equipment` = `{"radar":"radar_1","scanner":"scanner_1","engine":"engine_1"}` (радар + сканер + двигатель). `models.StarterEquipment` обновляется.

**Серверные функции** (по образцу `internal/ship/radar.go` / `catalog.go`):
- `ship.EngineSpeed(equipment)` — возвращает `params.speed_factor` установленного двигателя (0.3). Вызывается только при наличии валидного двигателя (после проверки `HasEngine`); битый `params` у валидного двигателя → 0.3 (значение по умолчанию, безопасное чтение).
- `ship.HasEngine(equipment)` — установлен ли валидный двигатель (по образцу `ship.HasScanner`, `internal/ship/catalog.go`): предмет в слоте `engine` существует в каталоге и имеет тип `engine`. Используется валидацией `/travel` (§6.1).

**Полёт** (`internal/handlers/travel_handlers.go:52-59`): `calcTravelDuration` берёт скорость из установленного двигателя игрока (`ship.EngineSpeed(users.equipment)`) вместо константы 0.3. **Значение не меняется — 0.3, меняется источник** (замысел 77a §1.3, первый шаг). Минимум 3 сек сохраняется (66a). **Валидация:** для `role=player` без установленного двигателя (`!ship.HasEngine`) — отказ «Двигатель не установлен — полёт невозможен» (§6.1); админ/skycomposer — исключение (летают всегда).

**NPC-агентов НЕ трогаем:** у них своя настройка `npcSpeedFactor` (0.3, `internal/npc/settings.go`), механика без изменений; при необходимости — только обновить комментарий («скорость игрока» теперь из двигателя, у NPC — своя настройка).

**`/me`:** `ship_speed_factor` отдаётся из `ship.EngineSpeed(user.Equipment)` (0.3) — §7.2.

> **Дельта 2026-09-24** (спека `2026-09-24-магазин-модулей-локальный-рынок.md` §9; покупка модуля в `universal*`). `ship.HasScanner`/`ship.HasEngine` читают валидный модуль по типу из **любого** слота `users.equipment` (в т.ч. `universal*`), не только из легаси-слотов `scanner`/`engine`. **`ship.EngineSpeed` в v1 не меняется:** скорость берётся из легаси-слота `engine`; двигатель в `universal*` даёт право полёта (`HasEngine` — любой слот), но скорость не изменяет (задел vNext — «скорость из любого двигателя»).

### 7.2. Развилка: куда отдавать каталог (решено, круг 2)

**Решение (создатель, круг 2): расширить `/me`** (принята рекомендация первого круга, прецедент `ship_options`). Альтернативы (резолв только установленного / отдельный эндпоинт) отклонены: прецедент `ship_options`, один запрос, объём мал; «только личное» — про UI-показ, не про транспорт данных (клиент получает каталог, но рисует только установленное, И1).

### 7.3. Схема данных (вариант A, эскиз)

Добавляемые поля в ответе `/me` (существующие поля — `ship_model_id`, `equipment`, `radar_radius`, `ship_icon`, `ship_color`, `ship_options` — **не меняются**, И3):

```json
{
  "ship_model": {
    "id": "starter",
    "name": "Стартовый разведчик",
    "slots": {"radar": 1, "scanner": 1, "engine": 1}
  },
  "ship_catalog": [
    {"id": "radar_1", "type": "radar", "name": "Радар-1", "params": {"radius": 800}},
    {"id": "scanner_1", "type": "scanner", "name": "Сканер-1", "params": {"depth": "surface", "settlements": true}},
    {"id": "engine_1", "type": "engine", "name": "Двигатель-1", "params": {"speed_factor": 0.3}}
  ],
  "ship_speed_factor": 0.3
}
```

- `ship_model` — из таблицы `ship_models` (id/name/slots); `slots` — рамка слотов модели (77a §2.2).
- `ship_catalog` — весь каталог оборудования из `internal/ship` (`EquipmentByID`/каталог в памяти; id/type/name/params), включая `engine_1`. Клиент для каждого слота из `users.equipment` берёт предмет по id из каталога — так имена и характеристики приходят с сервера, а не дублируются в JS (И2, «один факт — одно место»).
- `ship_speed_factor` — из `ship.EngineSpeed(user.Equipment)` (0.3), отдаётся сервером, чтобы клиент не хардкодил число (И2). При будущей реализации разных двигателей значение будет зависеть от установленного — поле останется, источник уже готов (`EngineSpeed`). Без двигателя полёт запрещён (§6.1) — клиент получает `ship_speed_factor` только при установленном двигателе (иначе ячейка «не установлен», скорость не показывается как текущая).

Серверное резолвление: имя модели (`ship_models`) — загрузчик в память по образцу `ship.LoadCatalog` (решение при разработке; таблица существует, 77a §12). Каталог уже в памяти (`internal/ship/catalog.go`), после миграции `000043` содержит `engine_1`.

### 7.4. Миграция `000043` (забронирована за 91a, `docs/DB.md`)

Содержимое (детальная схема SQL согласуется с @manager при разработке):

```sql
-- 1. Каталог: двигатель-1 (тип engine уже в CHECK 77a §3.2)
INSERT INTO equipment (id, type, name, params)
VALUES ('engine_1', 'engine', 'Двигатель-1', '{"speed_factor": 0.3}');

-- 2. Бэкфилл существующих игроков: проставить engine_1 в users.equipment,
--    где слот engine пуст/отсутствует (по образцу бэкфилла 000040)
--    users.equipment JSONB: {"radar":"radar_1","scanner":"scanner_1","engine":null}
--    → {"radar":"radar_1","scanner":"scanner_1","engine":"engine_1"}
UPDATE users
SET equipment = jsonb_set(COALESCE(equipment, '{}'::jsonb), '{engine}', '"engine_1"')
WHERE equipment IS NULL
   OR NOT (equipment ? 'engine')
   OR equipment->>'engine' IS NULL
   OR equipment->>'engine' = '';
```

Порядок: INSERT каталога → бэкфилл игроков (в одной миграции). Новых таблиц нет (двигатель — запись существующей `equipment`).

### 7.5. Производительность

- `/me` — один запрос на загрузку дашборда; каталог в памяти (read-only, как `ship_options`); `ship_models` — загрузчик в память при старте (по образцу `LoadCatalog`); `EngineSpeed`/`HasEngine` — чтение из каталога в памяти (как `RadarRadius`/`HasScanner`). Инвариант 2 проекта (стоимость не от размера галактики) держится: никаких обходов планет/тиков, O(размер каталога) ≈ O(3 предмета).

## 8. Инварианты и числа

**Числа (факты, не новые):**

- Радиус радара: **800 px** (`radar_1`, 77a §4.2, миграция `000042`); без радара — 200 px (минимум, 77a).
- Сканер: глубина **surface** + поселения **true** (`scanner_1`, 77a §6.2).
- Скорость полёта: **0.3 сек × дистанция, мин 3** (66a) — значение сохраняется, источник меняется на установленный двигатель (`engine_1` → `speed_factor` 0.3, §7.1). **Полёт без двигателя — невозможен** (для `role=player`, решение создателя; фолбэка-скорости нет, §6.1). NPC — `npcSpeedFactor=0.3` (своя настройка, не трогаем).
- Слоты: 3 активных (радар/сканер/двигатель) + пустые ячейки будущих слотов (оружие, броня/щиты, генератор, трюм, топливный бак — открытый список-задел, §5.1).
- Стартовая комплектация: радар-1 + сканер-1 + **двигатель-1** (77a §3.3, обновлено кругом 2).

**Инварианты:**

- **И1 (только личное):** раздел показывает только установленное у игрока; каталог «что бывает» в UI не показывается (решение создателя). Будущие слоты — пустые ячейки без названий (§5.2), не каталог.
- **И2 (один факт — одно место):** имена/характеристики модулей — из каталога на сервере (`ship_catalog` в `/me`), не дублируются в JS; скорость — `ship_speed_factor` с сервера (из `EngineSpeed`), не хардкод в клиенте; константа 66a — один источник на сервере.
- **И3 (не-регрессия 77a):** существующие поля `/me` (`ship_model_id`, `equipment`, `radar_radius`) не меняются — расширение аддитивное; радиус радара в разделе = `radar_radius` в `/me` (один источник — установленный радар).
- **И4 (скорость из установленного двигателя; полёт требует двигателя):** скорость полёта игрока = `ship.EngineSpeed(users.equipment)` (77a §1.3 — первый шаг); **полёт без установленного двигателя невозможен** для `role=player` (`ship.HasEngine` → отказ `/travel`, §6.1); админ/skycomposer — исключение (летают всегда, по аналогии с видимостью 77a); NPC-агенты — своя настройка `npcSpeedFactor`, не зависят от оборудования игроков.
- **И5 (не-регрессия 61b/86a):** селектор спрайта/цвета 61b **не трогается** (легаси, решение круг 2) — не встраивается, не переносится, не меняется; энциклопедия «Корабли/оборудование» (86a §5.5) не трогается.
- **И6 (нет новых чисел):** числа — факты каталога (77a) и константа 66a; новые механики (загруженность, разные двигатели, топливо, рынки, прогрессия радара) не проектируются.
- **И7 (нет новых сущностей/миграций сверх одной):** раздел — UI-слой; новых таблиц нет; единственная миграция — `000043` (двигатель в каталог + бэкфилл, §7.4); `ship_catalog`/`ship_model` — отдача существующих справочников.
- **И8 (консистентность с 77a):** характеристики модулей — из params установленных предметов каталога; двигатель — запись существующей таблицы `equipment` (тип `engine` уже в CHECK 77a §3.2).

**Риски и режимы отказа:**

- **Бэкфилл пропустил часть игроков** (легаси с пустым `engine`) — полёт для них запрещён (`/travel` отказ, §6.1); UI показывает «не установлен» в слоте двигателя и блокирует «Лететь». Крайний случай теоретический (миграция `000043` выдаёт двигатель всем, §7.4), но правило честное: без двигателя не летает.
- **`HasEngine` на битом каталоге** (двигатель не загрузился) — двигатель «не установлен» → полёт запрещён (безопасный отказ, не «слепой полёт»); админ/skycomposer — исключение.
- **Клиент показывает каталог «что бывает»** — нарушение И1; защита: UI рисует только слоты из `users.equipment` (по id из каталога), каталог используется как справочник имён/параметров.
- **Дрейф `ship_speed_factor` от константы 66a** — один источник на сервере (`EngineSpeed` ← каталог ← миграция `000043`); при изменении механики полёта правка в одном месте (И2).
- **Пустые ячейки без подписей не читаются** — риск косметический: силуэт с ячейками (§4.1) показывает «свободные места»; если создатель решит иначе — вернутся подписи (отдельное решение).

## 9. Границы (что НЕ делаем)

- **Не показываем каталог «что бывает»** — только установленное (И1, решение создателя).
- **Не проектируем полную механику двигателей** (загруженность, разные двигатели, формулы) — замысел 77a §1.3 вне скоупа; 91a делает первый шаг: один двигатель `engine_1` со `speed_factor` 0.3, скорость из установленного двигателя, полёт требует двигателя.
- **Не вводим фолбэк-скорость без двигателя** — полёт без двигателя запрещён (решение создателя, §6.1); «не стоит на месте» отклонено.
- **Не трогаем NPC-агентов** — своя настройка `npcSpeedFactor` (0.3), механика без изменений; валидация двигателя только для `role=player`; максимум — комментарий в коде (решение создателя, круг 2).
- **Не трогаем селектор 61b** (смена спрайта/цвета) — легаси, остаётся как есть (решение создателя, круг 2); в разделе — только превью корабля.
- **Не проектируем топливо/дальность полёта** — будущий ограничитель (77a §7.3), слот-задел §5.1, механика не реализуется.
- **Не проектируем рынки оборудования** — покупка/смена — будущие локальные рынки (77a §3.3); раздел ничего не покупает.
- **Не трогаем энциклопедию «Корабли/оборудование»** (86a §5.5) — отдельная далёкая задача (решение создателя).
- **Не меняем механику полёта** (66a: длительность, минимум 3 сек, рефреш-переживание) — меняется только источник скорости (из установленного двигателя, значение 0.3).
- **Не создаём новых таблиц** (И7) — единственная миграция `000043` (двигатель в каталог + бэкфилл).
- **Не меняем существующие поля `/me`** (И3) — расширение аддитивное.
- **Не вводим новые числа баланса** (И6) — характеристики — факты каталога и константа 66a.
- **Не делаем HUD-отображение радара/сканера на карте** — кандидат на отдельную идею (хвост идеи 91a).
- **Не проектируем прогрессию радара** (уровни/цены) — вне скоупа, вернётся с рынками (77a §4.2).

## 12. Кандидат ГД-сущности (Вопрос → Ответ, в числа не входит)

Правило «каждое задание = +1 предложение новой ГД-сущности» (создатель 2026-09-14). Кандидат по теме фичи (раздел «Корабль», скорость/полёт):

**Вопрос:** нужен ли игроку **топливный бак и топливо** — расходуемый ресурс корабля (покупается на рынках, сгорает при полёте) и модуль-слот, определяющий дальность полёта (77a §7.3: «дальность полёта по топливному баку ещё будет ограничиваться»)?
**Ответ (эталон создателя):** не задан — открытый вопрос (счётчик FAQ +1 при разносе).

Почему повышает игровой интерес: полёт сейчас бесплатен и безграничен (66a) — топливо даёт экономику перемещения: дальность становится планированием (куда лететь, сколько топлива взять), рынок топлива — торговый товар (экономика Zorion), география сада/фронтира получает механический смысл (дальние перелёты дороже). **Актуализация (круг 2):** двигатель стал настоящим модулем (`engine_1`, скорость из установленного двигателя) — топливный бак естественно соседствует с ним как второй модуль полётной группы (двигатель — скорость, бак — дальность); оба — слоты будущего/текущего корабля, механики разделены и не пересекаются (скорость и дальность — разные характеристики). Механика дешёвая: слот-задел уже в §5.1, расход при полёте — событие в `/travel` (лениво, инвариант 2), покупка — будущие рынки. Цена: риск «топливо — налог» (инвариант 10 GD_PROMPT: сущность оправдана решением — здесь решение есть: куда лететь); баланс цены топлива против заработка. В текущие числа фичи **не входит** (анти-двойной учёт): реализуется только при явном решении создателя.
