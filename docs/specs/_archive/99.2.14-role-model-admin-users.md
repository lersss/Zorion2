## 1. Контекст и решения создателя

Админка открывалась общим паролем `X-Admin-Password` (env `ADMIN_PASSWORD`, `internal/auth/admin_auth.go`), ролей и учёток не было. Создатель решил (2026-09-14, дословно в идее `18a`):

- Админка открывается **обычной формой логина** (JWT, роль в токене). Глобальный `X-Admin-Password` снимается.
- Роли: **PLAYER** (игровой клиент), **ADMIN** (вся админка, но без управления правами и системных настроек), **Skycomposer** (всё, что ADMIN + управление ролями, сброс паролей, бан/удаление, создание пользователей).
- Раздел «Пользователи»: поиск (username/email) + пагинация + просмотр профиля + редактирование прав + создание пользователя.
- Админов назначает/снимает **только Skycomposer**.

Эталоны зафиксированы в `20_admin_roles.md` §«Эталоны (FAQ)».

## 2. Модель данных

### Миграция `000025_add_user_role.sql`

```sql
ALTER TABLE users ADD COLUMN role TEXT NOT NULL DEFAULT 'player';
ALTER TABLE users ADD CONSTRAINT users_role_check
    CHECK (role IN ('player', 'admin', 'skycomposer'));
```

- Существующие пользователи автоматически получают `player` — до фичи ролей не было, значит никто не админ. Первый Skycomposer создаётся бутстрапом (§5).
- `CHECK` защищает от опечаток в значениях роли (дешевле, чем полагаться на код).
- Индекс по `role` не нужен: таблица `users` малая, поиск по `username`/`email`, фильтр по роли дешёвый.

### Go-тип

`internal/models/user.go`:

```go
type Role string

const (
    RolePlayer      Role = "player"
    RoleAdmin       Role = "admin"
    RoleSkycomposer Role = "skycomposer"
)
```

`models.User` получает поле `Role Role \`json:"role"\``.

## 3. Авторизация

### JWT-клеймы (`internal/auth/jwt.go`)

- `Claims` получает `Role string \`json:"role"\``.
- `GenerateToken(userID, role string)` — подписывает роль в токен.
- `VerifyToken(tokenString) (userID, role string, err error)` — возвращает и роль. **Правило отсутствующей роли:** если в валидном токене роль не задана (старый токен с TTL 24 ч) — считать `player`. Безопасный дефолт наименьших прав: старый токен не получит доступ в админку, но продолжит работать для игры.

**Решение по старым токенам:** принимаем, что токены без роли живут до истечения (24 ч) и трактуются как `player`. Секрет не меняем, версию клеймов не поднимаем. Цена: до 24 ч после деплоя админы должны перелогиниться (новый токен с ролью). Режим отказа не возникает: «без роли = player» безопасна, игру не ломает.

### Middleware (`internal/auth/middleware.go`, `admin_auth.go`)

- `AuthMiddleware` кладёт в контекст `userID` и `role` (добавляем `auth.RoleKey`).
- Новый `RequireRole(next, roles ...Role) http.HandlerFunc` — читает роль из контекста, при несовпадении возвращает `403 {"error":"Недостаточно прав"}`.
- `AdminAuth` **переопределяется**, сохраняя сигнатуру (минимальный диф в `main.go`):

```go
func AdminAuth(next http.HandlerFunc) http.HandlerFunc {
    return AuthMiddleware(RequireRole(next, RoleAdmin, RoleSkycomposer))
}
```

- Новый `SkycomposerAuth` для управления пользователями:

```go
func SkycomposerAuth(next http.HandlerFunc) http.HandlerFunc {
    return AuthMiddleware(RequireRole(next, RoleSkycomposer))
}
```

- `internal/auth/admin_auth.go` (X-Admin-Password) **удаляется**; тесты на него (`auth_test.go`) переписываются под ролевую проверку.

### Снятие `X-Admin-Password`

- `internal/auth/admin_auth.go` с глобальным паролем удаляется.
- `internal/config/config.go`: убираем `AdminPassword` и требование `ADMIN_PASSWORD` (сейчас это `log.Fatal` — без правки dev/деплой упадут). Добавляем `SkycomposerBootstrapUsername` / `SkycomposerBootstrapPassword` (env `SKYCOMPOSER_BOOTSTRAP_USERNAME` / `SKYCOMPOSER_BOOTSTRAP_PASSWORD`) — см. §5.

## 4. Вход в админку

**Решение: отдельной страницы логина не добавляем.** `/admin` (статичный `web/admin.html`) гейтится на клиенте: при загрузке проверяем валидность токена и роль (через `/me`, который теперь возвращает `role`); нет прав — показываем оверлей-форму логина прямо на странице админки, которая постит в существующий `POST /login`.

- Игровой клиент хранит токен в `localStorage['token']`; админка хранит свой в **`localStorage['adminToken']`** — ключи не конфликтуют (человек может быть и игроком, и админом).
- Сервер всё равно проверяет роль на каждой `/admin/*` ручке — клиентский гейт это только UX, не защита.

`POST /login` и `POST /register` (AuthResponse) теперь возвращают и `role` — фронт знает свою роль. `/me` тоже возвращает `role`.

---

## 5. Bootstrap первого Skycomposer

**Решение: env-переменные на старте.** После применения миграций сервер проверяет число учёток с ролью `skycomposer`:

1. Если их ≥ 1 — ничего не делаем.
2. Если их 0 и заданы `SKYCOMPOSER_BOOTSTRAP_USERNAME` + `SKYCOMPOSER_BOOTSTRAP_PASSWORD`:
   - если пользователь с таким `username` существует — повышаем его до `skycomposer`;
   - иначе — создаём нового пользователя с ролью `skycomposer` (bcrypt-хэш пароля).
3. Если их 0 и env не заданы — `log.Warn` («админка недоступна, пока не создан Skycomposer; задайте SKYCOMPOSER_BOOTSTRAP_*»), сервер продолжает работу.

**Почему так:** проект уже конфигурирует доверенные секреты через env (`JWT_SECRET`, прежний `ADMIN_PASSWORD`), работает в Docker/Amvera; env-бутстрап детерминирован и не требует ручного SQL/команды. Риск минимален: бутстрап срабатывает только пока Skycomposer'ов нет, повторно не назначается.

**Отвергнутые альтернативы** (см. §9): «первый зарегистрированный становится skycomposer» — опасно (гонка и компрометация); «служебная команда/SQL» — требует ручного действия, ломает автоматический деплой.

## 6. API

Все ручки управления пользователями — под `auth.SkycomposerAuth`. Ошибки — JSON `{"error": "..."}` (как `writeJSONError`).

### 6.1. `GET /admin/users?query=&role=&page=&limit=` — список

**Только Skycomposer.**

| Параметр | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `query` | string | `""` | подстрока по `username` (case-insensitive) или `email` |
| `role` | string | `""` | фильтр: `player`/`admin`/`skycomposer` |
| `page` | int | `1` | 1-based |
| `limit` | int | `20` | max `100` |

Ответ `200`:

```json
{
  "total": 42,
  "page": 1,
  "limit": 20,
  "users": [
    { "id": "uuid", "username": "bob", "email": "b@x.io", "role": "admin",
      "created_at": "...", "updated_at": "..." }
  ]
}
```

### 6.2. `GET /admin/users/{id}` — профиль

**Только Skycomposer.** Ответ `200` — полный профиль:

```json
{
  "id": "uuid", "username": "bob", "email": "b@x.io", "role": "admin",
  "created_at": "...", "updated_at": "...",
  "current_world_id": "uuid|null", "current_world_name": "name|null",
  "ship_icon": "ship_strela.svg", "agent_id": "uuid|null"
}
```

`404` если пользователь не найден.

### 6.3. `POST /admin/users` — создание пользователя

**Только Skycomposer.** Тело:

```json
{ "username": "newbie", "password": "secret", "email": "n@x.io", "role": "player" }
```

- `username`, `password` обязательны; `email` опционален; `role` — `player` (по умолчанию) / `admin` / `skycomposer`.
- Skycomposer вправе создать пользователя любой роли (включая `admin` и `skycomposer`).
- `201` — профиль созданного; `400` — невалидные поля; `409` — username занят.

### 6.4. `PATCH /admin/users/{id}/role` — смена роли

**Только Skycomposer.** Тело: `{ "role": "admin" }`.

- `200` — роль обновлена (в теле — новый профиль).
- `403` — если операция нарушает инварианты (сам себя, последний Skycomposer) — см. §7.
- `404` — пользователь не найден.

### 6.5. `POST /admin/users/{id}/reset-password` — сброс пароля

**Только Skycomposer.** Тело: `{ "password": "новый" }`.

- `200` — пароль обновлён (bcrypt-хэш сохраняется).

### 6.6. `DELETE /admin/users/{id}` — удаление

**Только Skycomposer.**

- `204` — удалён.
- `403` — если это сам пользователь или последний Skycomposer (§7).
- `404` — не найден.

**Бан вынесен в открытые вопросы (§9):** отдельная колонка + гейт в логине/`/me` — это дополнительный скоуп; по умолчанию в спринт берём только удаление.

## 7. Инварианты и защита от потери контроля

Проверки выполняются **в одной транзакции с изменением** (атомарно, защита от гонки — инвариант 1).

- **И1 — в системе всегда ≥ 1 учётка `skycomposer`.** Запрещено: смена роли `skycomposer` → `player`/`admin` последнего Skycomposer; удаление последнего Skycomposer. Проверка: перед изменением считать число Skycomposer'ов, если меняем последнего — `403`.
- **И2 — нельзя менять/удалять самого себя.** Skycomposer не может понизить себя, сбросить права или удалить себя через раздел «Пользователи» (случайное самоисключение). Самостоятельный сброс своего пароля допустим вне этого раздела (вне скоупа).
- **И3 — управление ролями и создание пользователей — только Skycomposer.** Роуты §6 закрыты `auth.SkycomposerAuth`; не-Skycomposer получает `403` на уровне middleware.
- **И4 — нельзя выдать роль выше своей.** Сейчас `skycomposer` — верх иерархии, потому правило фактически неактивно, но фиксируется как принцип: если появится роль выше — назначать её сможет только обладатель такой же или высшей. Держится на том, что роли меняет только Skycomposer.

Игровые маршруты (`/worlds`, `/travel`, `/me`, `/ws`, `/api/...`) остаются доступными **любому залогиненному** — роль не ограничивает игру (решение создателя).

## 8. Интерфейс раздела «Пользователи»

Новая вкладка «Пользователи» в `web/admin.html`. **Кнопка вкладки и функции видны только Skycomposer** (определяется по роли из `/me`/токена); ADMIN вкладку не видит.

- **Таблица:** id, username, email, роль, даты создан/обновлён. Сверху — поиск по username/email, фильтр по роли, пагинация.
- **Профиль (модалка или раскрытие строки):** username, email, роль, даты, текущий мир (название), иконка корабля, `agent_id`. Внутри — кнопки «Сменить роль», «Сбросить пароль», «Удалить» (подтверждение).
- **Форма создания пользователя:** username, password, email, роль (селект).

### Фронт-файлы

- `web/static/js/admin/auth.js` — замена `X-Admin-Password` на `Authorization: Bearer <adminToken>`; проверка роли на старте; оверлей логина; на `401` — снова показать логин.
- `web/static/js/admin/users.js` (новый) — список/поиск/фильтр/пагинация, профиль, создание, смена роли, сброс пароля, удаление.
- `web/static/js/admin/tabs.js` + `main.js` — регистрация вкладки.
- `web/admin.html` — вкладка и каркас; удалить блок «Пароль администратора» (строки 36–43).

## 9. Открытые вопросы (нужно решение создателя)

1. **Бан/удаление.** Создатель в схеме прав упомянул «бан/удаление», ТЗ — «если вводим». Предлагаю в спринте сделать **только удаление** (и §6.6), а бан (колонка `is_banned` + гейт в логине и `/me` = отдельный скоуп) вынести отдельной фичей. Нужно подтверждение: делаем только удаление или добавляем и бан?
2. **Bootstrap Skycomposer.** Предложен env-механизм (§5). Подтвердить либо выбрать альтернативу (SQL/команда). Предложение по умолчанию — env.
3. **Сброс своего пароля вне админки** — вне скоупа этой фичи; сейчас правится только через раздел «Пользователи» (самим себе нельзя, §И2). Оставить так.
