## 1. Цель и скоуп

Сделать двойные (binary) и кратные (multiple) системы физико-игровой моделью:
планеты знают, вокруг чего обращаются (S-тип — вокруг главной, P-тип — вокруг
барицентра пары), орбиты и инсоляция считаются честно от обоих компонентов,
модалка показывает две (и более) звёзды с реальными параметрами. Текущее
поведение (планеты одной звезды-центра, в модалке видна одна звезда) — для
двойных неприемлемо (пожелание создателя, идея 35b). Слой 35a (визуальные
компаньоны на карте/в модалке) остаётся и развивается до полной модели.

**В скоупе:** параметры компаньонов в данных (`companion_mass/companion_temp/
companion_sep_au`, `extra_companions[]`), орбитальный контекст планет
(`orbit_center`, `orbit_radius_au`), генерация компонентов и планет (S-инварианты,
P-ветка), числа баланса (инсоляция P, wide-границы), фронт (барицентричная
геометрия орбит, две звезды в модалке, гибрид-отрисовка wide-компаньона,
карта), проверка мини-карты (явное требование создателя, §6.5 и §8).

**НЕ в скоупе:**
- **Экзотика** (ЧД/НЗ/WD/протозвезда/сверхгиганты) и её генератор — отдельная
  будущая фича (свой баланс/дизайн); `fillExoticWorld` и ветки `99.2.4` §5 не
  трогаются. Компаньон всегда обычная звезда O–Y (`randomSpectralClass`), не
  экзотика.
- **Планеты у компаньона** (S-тип вокруг второго компонента) — не генерируются.
- **N-body динамика** (реальная эволюция орбит 3+ тел, орбитальный резонанс) —
  не моделируется; орбиты статичны, анимация косметическая.
- **Квадрупль/иерархии** — не моделируются; `extra_companions[]` — статичные
  внешние компаньоны (1 шт. у кратных), без собственных планет.
- **Числа планет, веса систем, экзотика** — НЕ меняются (mean 0.2 close /
  ×0.9 wide / ×0.9 multiple; веса §4.1 спеки 99.2.4; решение создателя,
  идея 35b §«Правки» п.2 и п.8 задания).
- Распределение **широких (wide) разделений** — log-uniform **[100, 3000] а.е.**
  (исходный дизайн, идея 35b; принято @balancetester В4; пример решения №3б
  «342 а.е.» — из этого диапазона). Канон a = 100 а.е. — нижняя граница
  (worst case баланса, §3.2/§5.3), не единственное значение.

**История решений** (кратко; полный след — идея 35b): вариант A честной физики
P-планет принят создателем (модалка не «врёт»); сортировка «главная = ярче» —
принята (отсекает хвосты инсоляции M+G +217% → worst +18.9%); multiple →
принудительно wide — принято; маркер барицентра — отклонён (шум).

## 2. Модель данных

Миграций SQL **нет** — всё в существующих JSONB (паттерн «открытый пакет»,
99.2.4 §2; колонки `worlds.stellar_mods` и `planets.data` уже JSONB).

### 2.1. `worlds.stellar_mods` — новые поля (структура `internal/models/stellar_mods.go`)

| Поле | Тип | Семантика | Когда |
|---|---|---|---|
| `companion_mass` | float (M☉) | масса компаньона | binary/multiple |
| `companion_temp` | int (K) | температура компаньона | binary/multiple |
| `companion_sep_au` | float (а.е.) | разделение пары (большая полуось орбиты компаньона) | binary/multiple |
| `extra_companions` | []object | внешние компаньоны кратных: `{spectral_class, mass, temp, sep_au}` | multiple |

Существующие `companion` (спектр компаньона), `binary_type` (`wide`/`close`) —
остаются как есть; `companion_mass/temp/sep_au` — уточнение того же компаньона
(не отдельная сущность). Природа сущности — **атрибут-состояние мира** (не
событие, не лог): стабильные параметры системы, по образцу `disk_state` из
99.2.4 §5.4. Расширяемость — массив `extra_companions[]` (второй внешний
компаньон — добавка в тот же массив, миграция не нужна; схема переживает
второй тип системы с 2+ внешними компаньонами).

### 2.2. `planets.data` — новые поля

| Поле | Тип | Значения | Семантика |
|---|---|---|---|
| `orbit_center` | string | `main` / `barycenter` | вокруг чего обращается планета: главная звезда (S-тип) или барицентр пары (P-тип) |
| `orbit_radius_au` | float (а.е.) | фактический радиус орбиты | S: `orbitRadiusByIndex(i)`; P: `3 × companion_sep_au` |

Хранение фактического `orbit_radius_au` — решение создателя (гейт №3, идея 35b).
Природа — атрибут планеты в её JSON-данных; реестр `03_planets.md` §3.11
дополняется двумя строками (дельтой менеджеру).

## 3. Генерация звёзд (`internal/generator/galaxy/galaxy.go` → `rollStarMods`)

Порядок для `binary`/`multiple` (обычная звезда O–Y; экзотика-компаньон
невозможна — компаньон всегда `randomSpectralClass`, обычный класс):

1. **Спектры пары:** главная — существующий спектральный ролл мира
   (`spectralClass()`), компаньон — `randomSpectralClass(rng)` (как сейчас).
2. **Параметры компаньона:**
   - `companion_mass` — `randomMass(класс компаньона)` — равномерно в диапазоне
     массы класса (`DefaultStellarMassRanges`, galaxy.go);
   - `companion_temp` — `randomTemperature(класс компаньона)` (диапазоны
     `spectralWeights`, galaxy.go);
   - `companion_sep_au` — по `binary_type`:
- **close:** log-uniform **[0.05, 0.9] а.е.** (решение создателя, гейт №3;
        источник P-планет);
      - **wide:** log-uniform **[100, 3000] а.е.** (исходный дизайн, принят
        @balancetester В4; «a ≳ 100» из 99.2.4 §4.3 — нижняя граница). Для
        баланса worst case — нижняя граница 100 а.е. (§5.3).
3. **Сортировка «главная = ярче» (решение создателя №2):** сравнить
   `luminosityBySpectral(класс₁)` и `luminosityBySpectral(класс₂)`
   (`internal/generator/planet/physics.go`); если светимость компаньона больше —
   **поменять местами** главную и компаньона целиком: `world.SpectralClass`,
   `world.Temperature`, массы (главной — в `stellar_mass`, компаньона — в
   `companion_mass`), `companion_temp` и `companion`-спектр. Инвариант:
   **L₂/L₁ ≤ 1** после сортировки. Следствие по цепочке генерации: счёт планет
   и `gasGiantChance` считаются от нового класса главной.
4. **Множественные → принудительно wide (решение создателя №3а):** для
   `multiple` `BinaryType` всегда `wide` (close у кратных невозможен — иначе
   физический абсурд тесной иерархии); + **внешний компаньон**
   `extra_companions[0] = {spectral_class, mass, temp, sep_au}`:
   - `sep_au` — log-uniform **[1000, 10000] а.е.**, инвариант **≥ 3×
     `companion_sep_au` внутренней пары** (при дефолтных диапазонах выполняется
     автоматически: close ≤ 0.9 а.е. → 3× ≤ 2.7 ≪ 1000; wide = 100 → 3× = 300
     < 1000; пере-ролл при нарушении на случай кастомизированных диапазонов);
   - `spectral_class` — `randomSpectralClass`; `mass` — `randomMass(cls)`;
     `temp` — `randomTemperature(cls)`;
   - количество внешних компаньонов — 1 (один на систему; `extra_companions[]`
     — массив для расширяемости, схема §2.1 переживает 2+).
5. Затменные переменные (`eclipsing`, 3% от двойных) — без изменений (гейт
   99.2.4 §4.3).

Таблицы параметров (источник, не дублируются):

| Параметр | Источник |
|---|---|
| Диапазоны массы по классам | `DefaultStellarMassRanges` (`galaxy.go`): O 15–60, B 3–18, A 1.5–3.5, F 1.1–1.6, G 0.9–1.2, K 0.6–0.9, M 0.1–0.6, L 0.03–0.08, T 0.015–0.03, Y 0.01–0.02 M☉ |
| Диапазоны температуры по классам | `spectralWeights` (`galaxy.go`): O 30000–50000, B 10000–30000, A 7500–10000, F 6000–7500, G 5200–6000, K 3700–5200, M 2400–3700, L 1300–2400, T 700–1300, Y 300–700 K |
| Светимость по классу | `luminosityBySpectral` (`planet/physics.go`): O 1000, B 100, A 10, F 2, G 1, K 0.1, M 0.01, L 0.001, T 0.0001, Y 0.00001 L☉ |

## 4. Генерация планет (`internal/generator/planet/`)

**Числа планет НЕ меняются** (решение создателя п.8): `planetCountFor`
(`planet_data_generate.go`) сохраняет mean 0.2 close / ×0.9 wide / ×0.9 multiple
(`DefaultPlanetMeans`). **Меняется реализация:** close получает собственную
ветку вместо общего пути.

Генерация каждой планеты получает орбитальный контекст:

- **S-планеты** (wide и multiple): `orbit_center = "main"`,
  `orbit_radius_au = orbitRadiusByIndex(orbitIndex)` (0.4 × 1.7^index, physics.go) —
  фактический радиус пишется в JSON; инсоляция **только от главной** (см.
  инварианты ниже). Реализация — существующий путь `generatePlanet(...)`
  (архетипная рулетка сохраняется — спектральный класс главной).
- **P-планеты** (close, mean 0.2 → n ∈ {0,1}): собственная ветка
  `generateCircumbinaryPlanet(...)` (§4.1).

### 4.1. P-ветка `generateCircumbinaryPlanet` (отклонение от 99.2.4 §5.3)

> **Отклонение от спеки 99.2.4 §5.3** («двойные wide/close и кратные не имеют
> отдельной ветки — общий путь»): **close уходит на явную ветку
> `generateCircumbinaryPlanet`.** Зафиксировано явно; одобрено создателем
> 2026-09-15 (вариант A, решения №1 и №7 задания).

- **Орбита:** одна P-орбита на систему, `r_P = 3 × companion_sep_au`
  (парный пол; правило стабильности P-типа 3×). Для n = 1 планета встаёт на
  неё; `orbit_center = "barycenter"`, `orbit_radius_au = r_P`.
  При 3a ∈ [1.16, 1.97] а.е. и G-подобной паре — пригодная P-планета (§5.1).
- **Температура:** честно от **L_total = L₁ + L₂** (сумма светимостей обоих
  компонентов по `luminosityBySpectral`):
  `T = 278.7 × L_total^0.25 / √(r_P)` — **без клампов архетипов**
  (`ArchetypeMin/Max`, §99.2.11 не применяются); **абсолютные границы
  [20, 2500] K** (`TempAbsoluteMin/Max`, physics.go) применяются всегда — это
  аудит-гейты 99.2.4 §6.2, не архетип-клампы. Горячая пара → горячая планета
  (модалка не «врёт», п.1 решения создателя). Для очень горячих пар честный
  расчёт превышает 2500 K (worst: O+O при a=0.05 → 4812 K) — кламп к 2500,
  планета остаётся «выжженной».
- **Композиция/вода/жизнь — по температурной полосе от честной T, как в
  общем пути** (полосы `generateWater`/`generateLife`, `properties.go`): вода —
  T > 250 && < 400 → полный шанс; 150 < T ≤ 250 → ×0.7; иначе ×0.3; жизнь —
  вода > 10 и 200 < T < 400 → шанс. Композиция — по T (горячая/умеренная/
  холодная полоса стандартного генератора композиции). Свойства передаются от
  честной T, а не от архетипа (без рулетки `GenerateArchetype`).
- **Гиганты P-типа разрешены:** шанс `gasGiantChance(спектр главной)`
  (0.3–0.8 по классу), орбита — та же 3a.
- **Флаги JSON:** `orbit_center="barycenter"`, `orbit_radius_au=3a`,
  `circumbinary=true` (маркер для UI/подписей). Аналогично S-планеты несут
  `orbit_center="main"` + `orbit_radius_au`.
- **Пригодность:** возможна (вариант A: G-подобные пары на 1.16–1.97 а.е.) —
  `settleable` по общим правилам (`settlement.Suitable`). Новых правил аудита
  **не требуется** (п.1 решения создателя; существующие `temp_too_low/high`,
  `life_without_*` валидны: T в [20, 2500], вода/жизнь — по полосам).
- Океанические/радиоактивные подветки общего пути P-веткой **не вызываются**
  (они привязаны к архетипной рулетке главной; P — своя полосная генерация).

### 4.2. S-инварианты (wide и multiple)

1. **Стабильная зона S-планет:** орбита планеты
   `orbitRadiusByIndex(i) ≤ 0.33 × companion_sep_au` (**эталонная граница:
   0.33×a** — Holman–Wiegert для равных масс; решение менеджера 2026-09-15,
   исходное дизайн-правило 0.5×a отклонено как оптимистичное — обе не влияют
   на код: лэддер орбит (индексы 1–8 → 0.68–27.9 а.е.; индекс 9 = 47.4 а.е.
   уже за границей 33 а.е. при минимальном wide a=100) не достигает ни одной —
   явный кап орбит не требуется (потолок 8 планет, Kepler-90).
2. **Вклад wide-компаньона в инсоляцию S-планет НЕ добавляется:** честная
   граница на генерируемых орбитах **≤ 8.4% потока (≤ +2% T)** при a = 100 а.е.
   (worst: равные по яркости, внешняя S-орбита 27.9 а.е.); типика **≤ 0.8%**.
   Расхождение пренебрежимо и заявлено в модели — вклад осознанно исключён
   (иначе двойной учёт при будущей калибровке). Пометка: сущности «вклад
   компаньона» в числах нет — это фиксированное исключение, не будущая
   механика.
3. T S-планет — **регрессия:** формула от главной как сейчас
   (`computeEquilibriumTemp`/`computeSurfaceTemp` с L = L₁), множители
   `binary_wide_factor ×0.9`/`multiple_factor ×0.9` не меняются.

## 5. Числа баланса

### 5.1. Инсоляция и температуры P-планет

Формула (эталон — честная физика, вариант A): `T_P = 278.7 × (L₁+L₂)^0.25 / √(3a)`.

Множитель P-инсоляции относительно «только главная»: `((L₁+L₂)/L_main)^0.25`:

| Пара | L_total / L_main | Множитель T |
|---|---|---|
| Равные по яркости (G+G, M+M, …) | 2 | **+18.9%** (2^0.25) |
| F+G (главная F, L₁=2, L₂=1) | 1.5 | **+10.7%** ((3/2)^0.25) |
| M+G свободный ролл (главная M, L₁=0.01, L₂=1) | 101 | **+217%** — классический worst свободного ролла; **отсечён** сортировкой «главная = ярче» (решение №2) |
| Worst после сортировки | 2 | +18.9% (равные пары) |

Оценка @balancetester: заявленный ранее «worst +4.5%» — **арифметическая
ошибка (В2)** — двойное применение степени 0.25; честный worst +18.9% (равные
массы), без сортировки — M+G +217% (см. §5.5 статус прогона).

Температура P-планет по парам (справочный расчёт по формуле; a — ролл
log-uniform [0.05, 0.9] а.е., r_P = 3a):

| Пара | L_total (L☉) | T_P при a=0.05 K | T_P при a=0.9 K |
|---|---|---|---|
| G+G | 2 | 856 | 202 |
| F+G | 3 | 947 | 223 |
| G+K | 1.1 | 737 | 174 |
| K+K | 0.2 | 481 | 113 |
| M+G | 1.01 | 721 | 170 |
| M+M | 0.02 | 271 | 64 |
| O+O (worst) | 2000 | 4812 → **кламп 2500** (аудит-гейт) | 1134 |

**Пригодные P-планеты:** только G-подобные пары, r_P ∈ [1.16, 1.97] а.е.
(→ a ∈ [0.39, 0.66] а.е., T_eq 236–308 K) — **~0.02–0.05% систем, 0–2 на
галактику** (п.1 решения создателя). Требование «модалка не врёт» выполнено:
горячая пара → горячая P-планета.

## 6. Фронт

### 6.1. `web/static/js/modal/layout.js` — барицентричная геометрия

- `computeLayout(...)` расширяется: кроме главной принимает параметры
  компаньона (массы, `companion_sep_au`, спектры для размеров/цветов).
  **Геометрия пары:** барицентр в центре кадра `(cx, cy)`; главная смещена на
  `d₁ = a·m₂/(m₁+m₂)`, компаньон — на `d₂ = a·m₁/(m₁+m₂)` (равные массы →
  симметричное смещение a/2). Массы отсутствуют (старые миры) → фолбэк
  0.5/0.5 (§2.4).
- **Орбиты:** P-планеты (`orbit_center=barycenter`) — вокруг `(cx, cy)`;
  S-планеты (`orbit_center=main`) — вокруг позиции главной. Радиусы орбит —
  существующая визуальная шкала от `orbit_index` (`getOrbitRadius`), физическая
  разница P/S выражается через центр вращения.
- **Гибрид-шкала:** если честное разделение компаньона больше доступного
  радиуса кадра (wide, множественные) — компаньон рисуется **на краю кадра** в
  направлении орбитального угла (решение создателя №3б), подпись см. §6.2.
- **Периоды (анимация косметическая):** `getPlanetAngle` — относительные доли
  по Кеплеру III от массы центрального тела: S-планеты ∝ √(r³/M₁) (как сейчас,
  визуальная формула `25 + orbitRadius·0.35` s сохраняется для S); P-планеты —
  ∝ √(r³/(M₁+M₂)) с бо́льшим визуальным периодом (орбита 3a). Абсолютная
  скорость — косметика, честного времени не моделируем.
- `getPlanetPose`/`getPlanetSize` — без изменений механики (центр вращения
  приходит из контекста планеты).

### 6.2. `web/static/js/modal/modal_render.js` — две звезды

- Замена блока 35a (close «вплотную справа» / wide «на медленной орбите»):
  компаньон рисуется **по честной барицентричной геометрии** §6.1: размер и
  цвет — по спектру компаньона (`getStarColor(companion)`), позиция — из
  layout.
- **wide-компаньон вне честного масштаба:** на краю кадра + **подпись
  реального расстояния** («компаньон: 342 а.е.» — пример; число —
  `companion_sep_au`; у кратных — и `extra_companions[*].sep_au`). Без
  `companion_sep_au` (старые миры) подпись не выводится (§2.4).
- **Маркер барицентра НЕ рисуем** (решение создателя №3в — шум): просто две
  звезды; P-планеты вокруг общего центра вращения.
- Планеты: S — вокруг главной, P — вокруг барицентра (§6.1); ховер/клик/подсветка
  без изменений.
- T компаньона при ховере/подписях — `companion_temp` (старые миры — «—»).

### 6.3. `web/static/js/modal/panel.js` — карточка звезды

Точки-компаньоны (сейчас `fillStyle = color` главной, 35a) перекрашиваются:

у кратных — каждый по своему спектру (`extra_companions[*].spectral_class`).
Данные уже в снапшоте (`StellarMods` map, §2.3).

### 6.5. Мини-карта (`web/static/js/modal/minimap.js`) — явное требование создателя

Решение создателя №3б: **«обязательно проверить мини-карту — что там
происходит, когда wide-компаньон вне честного масштаба»**. Требование входит в
спеку и в проверки @developer/@tester (§8):

- Мини-карта использует тот же `computeLayout` (общий центр), поэтому получает
  компаньонов автоматически — поведение при wide-компаньоне вне безопасной
  шкалы мини-карты (120 px) **должно быть проверено и осознанно определено**.
- Ожидаемое поведение (дизайн, не догма): компаньон вне масштаба мини-карты —
  **у края круга мини-карты**, цвет по спектру, подпись расстояния
  (аналог §6.2); не перекрывает планеты и рамку видимой области. Точный
  отступ/подавление подписи на малом масштабе — визуальное решение
  @developer/@gdesigner с обязательной фиксацией результата в критерии §8 п.5.
- Альтернатива «компаньон не рисуется на мини-карте вовсе» допустима **только**
  с явным обоснованием (скрытие вместо «вранья» масштабом) и фиксацией в §8.

## 7. Границы

Поведение, осознанно НЕ реализуемое этой фичей (скоуп §1, код не трогается):

- Экзотические звёзды и их компаньоны; генератор редких звёзд — отдельная
  фича (создатель: «по редким звёздам отдельно будем настраивать»).
- Планеты у компаньона; планеты вокруг внешних компаньонов кратных.
- N-body: орбиты не эволюционируют, периоды анимации косметические.
- Иерархии/квадрупль: внешний компаньон кратных — статичный, 1 шт., без
  собственных планет.
- Изменение чисел: веса систем (§4.1 спеки 99.2.4), средние планет
  (mean 0.2 / ×0.9 / ×0.9), экзотика — не меняются.
- Приливные эффекты, синхронизация вращения, обитаемость зон P/S сверх
  формул §4–5 — не моделируются (вне баланса, при необходимости — отдельная
  фича).
- Аудит: новых правил нет (вариант A / P-ветка держит диапазоны сама, §4.1).
- Старые миры не перегенерируются; поведение — только фолбэки §2.4.

## 8. Критерии приёмки (TDD; финальная проверка — создателем)

1. **Генерация пары:** у binary/multiple заполнены `companion_mass`/
   `companion_temp`/`companion_sep_au`; у multiple — `extra_companions[0]` с
   `sep_au ∈ [1000, 10000]` и ≥ 3× внутреннего; инвариант **L₂/L₁ ≤ 1**
   (сортировка «главная = ярче») — юнит-тест ролла, включая случай «компаньон
   ярче главной» (swap).
2. **P-ветка:** close-система с планетой (mean 0.2 → 0/1) даёт
   `orbit_center=barycenter`, `orbit_radius_au=3×sep`, `circumbinary=true`;
   T = 278.7·(L₁+L₂)^0.25/√(3a) **без архетип-клампов**, в [20, 2500];
   гигант P-типа возможен; вода/жизнь — по полосам от честной T (тест: пара
   G+G при a∈[0.39, 0.66] даёт T_eq 236–308 K — пригодная полоса; worst
   O+O a=0.05 → 4812 → кламп 2500).
3. **S-инварианты:** S-планеты несут `orbit_center=main`; их T — регрессия от
   главной (вклад компаньона не добавлен); орбиты внутри лэддера (стабильная
   зона не нарушается). Не-регрессия числа планет: mean-модель close/wide/
   multiple не изменилась (0.2 / ×0.9 / ×0.9).
4. **Модалка:** две звезды по честной геометрии (equal-mass пара —
   симметричное смещение a/2); P-планеты вокруг барицентра, S — вокруг
   главной; **маркера барицентра нет**; wide-компаньон — край кадра + подпись
   реального расстояния («компаньон: N а.е.»).
5. **Мини-карта (требование создателя №3б):** открыть wide/multiple мир с
   компаньоном вне честного масштаба — **проверить и зафиксировать**
   поведение мини-карты: рисуется ли компаньон, где (край/центр/отсутствует),
   как подписан, не перекрывает ли планеты/рамку; результат — строка в
   чек-листе @tester (`docs/QA_CHECKLIST.md`) и, при скрытии, явное обоснование.
6. **Старые миры:** world без новых полей (+ планеты без `orbit_center`) —
   модалка и карта рендерятся без ошибок: фолбэки §2.4 (массы 0.5/0.5;
   `orbit_center=main`; wide без sep — отрисовка 35a без подписи). Авто-тест
   рендера/данных на фикстуре старого мира.
7. **Визуальная регрессия:** одиночные системы (85%) — отрисовка и T планет
   не изменились; экзотика — без изменений.
8. DoD `go build ./...`, `go vet ./...`, `go test ./...` (локально,
   `-race` — после 1.0, AGENTS.md §2).

**Закрытые при переносе неоднозначности (решения менеджера 2026-09-15, без
влияния на код):**
- **S-граница стабильной зоны:** зафиксирована эталонная **0.33×a** (Holman–
  Wiegert, равные массы; дизайн-правило 0.5×a отклонено как оптимистичное).
  Лэддер орбит не достигает ни одной — кап не нужен (§4.2 п.1, §5.3).
- **Wide-разделение:** зафиксировано **log-uniform [100, 3000] а.е.** (исходный

## 9. Кандидат ГД-сущности (Вопрос → Ответ)

Каждое задание приносит +1 кандидата; в текущие числа **не входит**
(анти-двойной учёт):

- **«Двойной рассвет» (бинарные панорамы):** планеты в двойных системах
  (P и S) получают уникальные описания неба/рассветов с двумя солнцами
  (генератор текста + потенциально ассет), как контентная сущность для
  атмосферы мира и будущего туризма. Ответ: кандидат на будущую сущность;
  если принят — генератор контента в отдельной фиче, в числа баланса 35b не
  входит.
