## 1. Цель и скоуп

Спроектировать **Go-продукт «Студия товаров»** — отдельный локальный инструмент
создателя (аналог арт-студии `cmd/art-studio`), который генерирует производственные
цепочки «сверху вниз»: топ-тир товары → составляющие (товары меньших тиров или
новые) → … → ресурсы. Результат — JSON-выгрузка, «которую игра потом прочитает и
загрузит себе в базу». В первой итерации выгрузка вгружается в игру **руками**
(решение создателя 2026-09-18), автоматический мост «выгрузка → БД» — будущий.

**Продукт:** отдельный бинарь `zorion-goods-studio.exe` (`cmd/goods-studio/`),
веб-UI (embed), генерация контента — нейросеть через opencode API создателя
(на проде не будет). Игровой сервер не трогает.

**В скоупе:** спека Go-инструмента (архитектура `cmd/goods-studio/`, HTTP API,
конфиги `config/goods/*.json`, модель данных `state.json`, граф рецептов с тирами,
ИИ-интеграция «заполнить комплектующие», валидаторы, экспорт JSON). Код — зона
@developer по этой спеке.

**НЕ в скоупе (границы — §17):** код Go; машинные окна свойств (корзина качества —
следующая итерация); роботы/постройки/энергия как товары; проверка наличия
потребителя (§5.2.1); загрузка выгрузки в БД игры (будущий мост); валидаторы
перекосов цепочек и качества (следующая итерация).

### 5.1. Сущности

- **Категория** — свободное множество, прописывает создатель (решение №5);
  при первом старте **предзаполнено 13 позициями §5.2.1** (продовольствие,
  топливо, конструкционные материалы, химикаты, полимеры, комплектующие, детали,
  медикаменты, товары быта, оборудование, оружие, броня, корабли и модули) как
  стартовое удобство (решение создателя 2026-09-18; решение №5 не отменяется —
  множество остаётся свободным, просто предзаполнено). `id` — стабильный
  (uuid/счётчик), `name` — уникальное. Ресурсные категории (6,
  `internal/resource/categories.go`) — **отдельное пространство имён** для
  импортированных ресурсов (третий реестр осознанно, решение №5): категория
  студии ≠ категория ресурса, не смешиваются. **Категории студии в первой
  итерации не синхронизируются с игровой моделью §5.2.1** (решение создателя
  2026-09-18, критика С-1): «корабль — это тоже производимый товар» — категории
  студии валидны без маппинга на номенклатуру; маппинг — будущий.
- **Товар** (`Good`) — узел графа. Поля: `id`, `name` (уникальное, §6.3),
  `category` (id категории студии; для ресурсов — код категории ресурса),
  `status`, `banned_at` (ISO8601 или null), `kind` (`good`|`resource`),
  `source` (`manual`|`ai`|`palette` — откуда появился), `recipe` (список слотов),
  `created_at`. Для ресурсов: `resource_ref` {catalog: layer|real, catalog_id}.
- **Слот** (`Slot`) — элемент рецепта: ссылка на составляющий товар `good_id`
  (или пустой). **1 слот = 1 единица** (решение критика №8: проговорено явно;
  поле количества — будущая итерация корзины качества). Новый товар рождается с
  **одним пустым слотом** (по умолчанию, слова создателя, конспект п.8);
  дополнительные пустые слоты добавляются кнопкой «+ слот», заполняются кнопкой
  «заполнить комплектующие» (ИИ) или вручную.
- **Рецепт** — атрибут товара (список слотов), НЕ отдельная сущность: владелец —
  один товар, поток записей ограничен (слоты товара), схема расширяема
  (окна свойств добавятся массивом `windows` на товар в итерации качества).

### 5.2. Статусы (ровно один на товар)

| Статус | Смысл | Экспорт | ИИ предлагает | Виден в графе/палитре |
|---|---|---|---|---|
| `draft` | черновик (по умолчанию для новых) | нет | да (если имя совпало — ссылка) | да |
| `approved` | согласовано (контент) | **да** | да | да |
| `excluded` | исключено (не контент, возвращаемо) | нет | **нет** (список в промпте + локальный фильтр) | да, с бейджем |
| `banned` | бан (ИИ больше не предлагает; возврат в один клик) | нет | **нет** (то же) | только на переключателе «забаненные» |
| `resource` | импортированный ресурс (старая студия; в /studio роль = kind, статус `resource` упразднён — iterB §4.3) | да, если на ресурс ссылается выгруженный рецепт (§11) | да (по имени) | да, в палитре |

- **Бан — отдельный статус** (не путать с «неиспользуемыми»): забаненные
  скрыты из обычных видов, на отдельном переключателе, отсортированы по
  `banned_at` (новые сверху), разбан в один клик (конспект п.4, поправка
  2026-09-18). Банить можно и товары, и ресурсы (запрет предложений ИИ).
- **«Неиспользуемые» — НЕ статус**, а производное свойство: товар, на который
  не ссылается ни один слот ни одного рецепта (входящая степень 0), и не
  забаненный. Правая колонка палитры, карточки перетаскиваются на слоты
  (конспект п.7, поправка 2026-09-18).
- Исключённый/забаненный можно вернуть вручную (в `draft`/`approved`) — память
  статусов хранит их до явного удаления (конспект п.3: «не удаляя из базы
  сервиса — чтобы сохранить возможность включить в другие рецепты»).

### 5.3. Импортированные ресурсы (старая студия: read-only; в /studio — без привилегий)

**Старая студия (`cmd/goods-studio`, легаси до итерации C):** при старте
импортирует `LayerCatalog()` (20, `layer.go`) и `RealCatalog()` (111, `real.go`)
как товары `kind=resource`, `status=resource`, `recipe=[]` (слотов у ресурсов нет —
добываются, не производятся). Переименование/удаление/смена категории ресурса —
вне студии (правка `layer.go`/`real.go` сервера, перезапуск студии); API
блокирует: `PUT`/`DELETE /api/goods/{id}` для ресурса — 403 (§9). Ресурс можно

**Перенесённая студия (`/studio`, iterA §7):** ресурсы **без привилегий** (идея

## 6. Граф рецептов: тиры и инварианты

### 6.1. Тир = уровень в графе = сложность рецепта

Решение создателя (триаж №4): «сложность — это тир в графе (верхний уровень —
высший тир), и это целое число. Никакого противоречия» с `11_production.md`
§11.1.1 / `13_tiers.md` §13.9.1.

**Формула (производная, не хранится):**

```
тир(ресурс)            = 0
тир(товар)             = 1 + max(тиры заполненных слотов)
тир(товар с пустым рецептом) = 0   (лист — цепочка не достроена)
```

- **База шкалы — ресурсы = тир 0** (решение создателя 2026-09-18, после звоночка
  баланс-тестера): базовый товар из ресурсов = тир 1, поселение тира 1
  производит (согласуется с `13_tiers.md` §13.7.2 «тир 1 = массовое простое
  производство»). `13_tiers.md`/`11_production.md` не правятся — согласованы.
- Тир выводится из графа при чтении состояния («мы сами увидим», конспект п.6).
- Ребро «товар → составляющая» всегда идёт вниз: тир составляющей < тира товара
  автоматически по формуле (составляющая входит в max).
- **Тир = сложность рецепта** (одно и то же число). В выгрузке поле называется
  `complexity` (термин игры, §11.1.1); в UI — «тир».

### 6.2. Циклы исключены построением

Рёбра только вверх (решение создателя). Механизм: при добавлении составляющей X
в слот товара Y студия проверяет **достижимость Y из X** (DFS по составляющим
X). Y достижим из X или X == Y → отклонение с сообщением. Проверка сильнее
сравнения тиров и работает при пустых рецептах (тир листа определён формулой —
0, §6.1).
Граф — DAG по построению; валидатор держит проверку-страховку (§8).

### 6.3. Дубликаты и конфликты имён

- Имена товаров уникальны (нормализация: lowercase, trim, схлопывание пробелов).
- Дубликат отклоняется при: создании вручную, переименовании, вставке ответа ИИ
  (имя, совпавшее с существующим товаром, превращается в **ссылку** на него, а
  не в новый товар — это и есть способ (в) «выбрать из уже имеющихся»).
- Совпадение с баном/исключённым в ответе ИИ → дроп + отчёт (§7.4).
- Ресурсы и товары — одно пространство имён (ресурс — частный вид товара,
  GLOSSARY §5): товар с именем ресурса невозможен.

### 6.4. Количество

**1 слот = 1 единица по умолчанию; количество введено (99a.2 §6):** слот несёт
`quantity` (int, дефолт 1; нормализация <1 → 1 при загрузке — старые слоты без
миграции, zero value трактуется как 1). Два слота с одним товаром = 2 единицы
(допустимо и осмысленно); различие «резина в Т2 vs резина в Т5» выражается
количеством в рецепте (решение создателя 2026-09-19). **Тир и валидаторы от
количества не зависят** (тир = 1 + max(тиры составляющих), §6.1).

## 7. ИИ-интеграция — «заполнить комплектующие»

> **Устарело (iterC, 2026-09-20):** fill перенесён в игровой сервер и стал
> **двухфазным «предложи → подтверди в попапе»** (решение создателя 2026-09-20):
> `POST /studio/api/goods/{id}/fill` — асинхронный запуск ИИ, ответ разбирается в
> **предложения (proposals)**, НЕ применяется; попап «Предложения ИИ» с вариантами
> по каждому пункту (Создать/Заполнить/Пропустить/Изменить категорию);
> `…/fill/apply` — применяется только принятое (per-slot `ApplyProposals`, полный
> отчёт, дропы С1–С3); `…/fill/cancel` — отмена. Ниже — исторический контракт
> однофазного fill (спека iterC §5–§6).

### 7.1. Триггер

Кнопка на карточке товара. Работает, только если есть пустые слоты (нет пустых —
сообщение). Одна активная генерация (TryStart).

### 7.2. Промпт (конспект, уточнение создателя 2026-09-18)

```
Система: ты — генератор производственных цепочек космической экономической игры.
Товар производится из составляющих (товаров или ресурсов). Отвечай строго JSON.

Пользователь:
Товар: {name} (категория: {category}, тир: {tier}).
Уже заполненные слоты (не предлагай их): {имена заполненных составляющих}.
Забаненные и исключённые (не предлагай): {имена бана и исключённых}.
Известные ресурсы (если составляющая — существующий ресурс, используй его точное имя):
{имена слоя 20 + витрины 111}.
Категории студии: {имена категорий}.
Пустых слотов: {K}.
Верни ровно {K} составляющих — по одному на каждый пустой слот, максимально полно
описывающих состав товара на уровень ниже в графе.
JSON: {"components":[{"name":"...","category":"...","reason":"..."}]}
```

### 7.3. Ответ ИИ

`{"components": [{"name": string, "category": string, "reason": string} × K]}` —
**ровно столько товаров, сколько пустых слотов** (2 пустых → 2 товара, уточнение
создателя 2026-09-18, дважды). Не «до 10 кандидатов» (это было раньше, п.5
конспекта) и не жёстко «два».

- `name` — обязателен. `category` — из списка категорий студии (если нет/невалидна
  → категория родителя). `reason` — опционально, тултип на карточке («почему в
  составе»).

> **Устарело (iterC, 2026-09-20):** в `/studio` категория нового товара — **выбор в
> попапе** (дефолт — категория родителя при невалидной от ИИ, пометка «категория
> „Y" не найдена»), не молчаливый фолбек (спека iterC §5.4/§6, решение создателя
> 2026-09-20).

### 7.4. Обработка ответа (студия — локальный фильтр, инвариант)

1. Разбор JSON; ошибка/мусор/таймаут → слоты остаются пустыми, сообщение в UI.
2. Меньше K элементов → вставка того, что есть; остальные слоты пустые + отчёт.
3. **Больше K элементов** → вставка первых K по порядку; лишние дроп + отчёт
   («ИИ вернул больше запрошенного: N лишних — пропущены»).
4. Имя нормализуется (§6.3):
   - совпало с баном/исключённым → **дроп** + отчёт («ИИ предложил забаненное:
     X — пропущено»); список бана в промпте — best-effort, локальный фильтр —
     инвариант;
   - совпало с существующим товаром/ресурсом → **ссылка** на него (новый товар
     не создаётся);
   - иначе → новый товар `status=draft`, `source=ai`, категория по §7.3.
5. Вставка в пустые слоты по порядку; проверка цикла (§6.2) на каждую вставку
   (для ссылок на существующие товары). **Цикл → дроп этой вставки + отчёт,
   слот остаётся пустым** (не откат всей пачки: частичная вставка уже принята
   для малого ответа, шаг 2).

### 7.5. Транспорт

HTTP к локальному opencode создателя (`studio.json`: `opencode_url`, `model`,
`timeout_s`, `max_retries`). Точный endpoint и формат запроса opencode API —
зона @developer (техническое, белое пятно идеи); логический контракт — §7.2–§7.4.
**Модель явно видна создателю** — в конфиге `studio.json` и в UI (верхняя панель,
рядом с индикатором генерации): создатель должен видеть, что делает система
(решение создателя 2026-09-18).

## 8. Валидаторы

Прогон при чтении состояния (`GET /api/state` → `warnings`) и по кнопке
`GET /api/validate`. В первой итерации — структурные проверки (не качество и не
перекосы — те в следующей итерации, конспект п.13):

1. **«Каких ресурсов нет»** (ограничение первой итерации, решение №2): листья
   графа (товары без заполненных слотов), **на которые ссылаются рецепты других
   товаров (входящая степень > 0)**, не покрытые каталогами (слой 20 + витрина
   111) → список имён — кандидаты в недостающие ресурсы. Товар-верхушка с пустым
   рецептом (входящая степень 0) — **лист-намерение** (цепочка не достроена), в
   кандидаты не входит. Полевые ресурсы (тысячи, §9.2.3) валидатор **не видит** —
   осознанное ограничение.
2. **Неполные цепочки:** согласованные товары с пустым рецептом (тир = 0, лист).
3. **Ссылки на не-согласованных:** рецепт согласованного товара ссылается на
   `draft`/`excluded`/`banned` составляющего (выгрузка будет с битой ссылкой, §11).
4. **Страховки:** цикл (невозможен по построению §6.2), дубликат имени
   (невозможен по построению §6.3) — проверка-страховка, не «чинить».

## 9. HTTP API

Один процесс, порт 8799 (фикс; `studio.json`). Ответы — `Cache-Control:
no-store, no-cache, must-revalidate`; JSON — `Content-Type: application/json;
charset=utf-8`.

| Метод/путь | Параметры | Ответ |
|---|---|---|
| `GET /` | — | HTML UI |
| `GET /api/state` | — | полное состояние: категории, товары (имя, категория, тир, статус, слоты), banned (по `banned_at`), unused, warnings (§8) |
| `GET /api/resources` | — | импортированные каталоги (layer 20 + real 111) для палитры |
| `POST /api/categories` | `{name}` | создана категория (дубликат имени — 409) |
| `PUT /api/categories/{id}` | `{name}` | переименование |
| `DELETE /api/categories/{id}` | — | удаление; **блок**, если категория не пуста (сначала перекатегоризовать) |
| `POST /api/goods` | `{name, category_id}` | создан товар-черновик с одним пустым слотом (дубликат имени — 409) |
| `PUT /api/goods/{id}` | `{name?, category_id?}` | переименование/смена категории (старая студия: для ресурсов — 403; в /studio — разрешено, iterA §7) |
| `DELETE /api/goods/{id}` | — | удаление совсем; слоты, ссылающиеся на него, очищаются (старая студия: для ресурсов — 403, §5.3; в /studio — разрешено, iterA §7) |
| `POST /api/goods/{id}/status` | `{status}` | `draft`/`approved`/`excluded`/`banned`/`unban` (старая студия: для ресурсов — только `banned`/`unban`; в /studio — все статусы, iterA §7) |
| `POST /api/goods/{id}/slots` | — | добавить пустой слот |
| `DELETE /api/goods/{id}/slots/{n}` | — | удалить слот |
| `PUT /api/goods/{id}/slots/{n}` | `{good_id}` | положить составляющую (цикл §6.2 — 409; дубликат имени не возникает — ссылка) |
| `DELETE /api/goods/{id}/slots/{n}/component` | — | очистить слот («исключить из рецепта», товар остаётся в реестре) |
| `POST /api/goods/{id}/fill` | — | «заполнить комплектующие» (§7); ответ — обновлённое состояние + отчёт |
| `POST /api/export` | `{path?}` | запись `export.json` (дефолт `goods_data/export.json`) + warnings |
| `POST /api/import` | `{path?}` | импорт top-каталога (99a.2): полная замена товаров студии, ресурсы не тронуты; ответ — новое состояние + отчёт |
| `GET /api/validate` | — | прогон валидаторов (§8) |

Каждая мутация персистит `state.json` атомарно. Защита от одновременного запуска
`/fill`: одна активная генерация (TryStart).

## 10. UI/UX (исполнимое ТЗ; основа — конспект п.7, доработано @uidesigner 2026-09-19)

«Приятный современный интерфейс со слотами, куда кладутся карточки ресурсов, от
топ вниз; каждый листик связан с другими». Техника рендера (canvas vs HTML-оверлей
карточек) — зона @developer; требования §10.2–§10.11 обязательны независимо от техники.

### 10.1. Компоновка — четыре области

**Верхняя панель (3 строки, фиксирована):**
1. **Шапка:** заголовок «Студия товаров»; справа — модель ИИ (явно, §7.5),
   индикатор генерации (§10.8), фильтр категорий (селект «все категории»), поиск по
   имени (инкрементальный), переключатель «забаненные», переключатель «обратные
   рёбра», кнопка «Экспорт».
2. **Категории:** селект категории + «Переименовать» + «Удалить» + поле имени +
   «+ категория» (конфликт имён — 409, тост).
3. **Новый товар:** поле имени + селект категории + «+ товар» (рождается черновиком
   с одним пустым слотом, §5.1; дубликат имени — 409, тост).

**Основная область:** слева — **граф** (полотно рёбер + карточки, zoom колесо
0.2–4x от курсора, пан drag; клик по пустому месту — сброс выбора). Справа —
вертикальная колонка (скролл): **детальная панель** выбранного товара (§10.3) →
**палитра** (§10.4) → панель **«забаненные»** (скрыта, пока выключен переключатель).

**Слой поверх:** тосты-отчёты (правый нижний угол, авто-скрытие 8 с), модалки
(подтверждение удаления §10.10, экспорт с warnings §10.9).

Три способа добавить товар в граф (конспект п.2): (а) «заполнить комплектующие» —
ИИ вставляет карточки в пустые слоты (§10.8); (б) «+ товар» вручную (в т.ч.
товар-верхушка); (в) перетащить из палитры на слот (§10.4).

### 10.2. Карточки на графе — компактный обзор

Было: слоты и все кнопки на карточке. Станет: **карточка = обзор, редактирование —
детальная панель** (почему: «на экран всё не влезет», кнопки/текст внутри canvas-
карточки — плохой UX и сложная реализация; разделение «обзор/правка» — стандарт
узловых редакторов).

Карточка: имя, категория, бейджи «тир N» и статуса (✓ согласовано / ✗ исключено /
🔨 черновик / ⛔ бан / ресурс), **пипсы слотов** (заполнен/пуст). Hover — тултип:
полное имя, категория, тир. Клик — выбор + открытие детали.

Состояния карточки: обычная / выбранная (обводка) / banned (только при включённом
переключателе «забаненные», приглушённый стиль) / resource (нижний ряд, тир 0).
Товар без слотов (все удалены) — карточка-лист, тир 0.

### 10.3. Детальная панель

Пустая (нет выбора): подсказка «Кликните товар на графе — здесь появятся слоты и
действия».

Товар (`kind=good`): шапка — имя (клик — inline-переименование, PUT goods),
категория (селект — смена), бейджи тир/статус, метка «ИИ» (`source=ai`). Слоты —
список: заполненный (имя составляющей + тир + «×» очистить; reason — тултип) /
пустой (пунктир, drop-target §10.4); у каждого слота — кнопка «удалить слот»
(DELETE slots/{n}). Кнопки: «+ слот», «заполнить комплектующие» (disabled при
активной генерации или без пустых слотов), статус-действия (Согласовать /
Исключить / Забанить — показываются, если статус не совпадает; «Вернуть» — только
для banned), «удалить» (подтверждение). Блок **«Используется в:»** — обратные рёбра
(§10.7).

Ресурс (`kind=resource`): **без привилегий** (идея переноса §1.2, С1/С3) —
переименование/удаление/смена категории/тир/статусы доступны; нет «+ слот»/
«заполнить» (ресурс — лист, 403). Старая студия была read-only — легаси до C (§5.3).

### 10.4. Палитра и drag & drop

Раздел **«Ресурсы»** (из `/api/resources`, 20+111, карточки, клик — выбор ресурса
на графе). Раздел **«Неиспользуемые»** (товары in-degree 0, НЕ banned, НЕ ресурсы,
§5.2; пусто — «все товары используются»).

Перетаскивание: карточка из палитры/неиспользуемых на слот — заполнение пустого
или **замена** содержимого заполненного (заменяемый товар остаётся в реестре). Над
слотом — подсветка drop-target. Недопустимый сброс (цикл §6.2) — отклонение + тост
«Цикл: товар X не может входить в состав Y», слот без изменений. После сброса —
перерисовка (тиры пересчитаны).

### 10.5. Забаненные

Переключатель «забаненные»: **вкл** — панель «забаненные» (список по `banned_at`,
новые сверху, кнопка «Вернуть» у каждой; выбор карточки — деталь с
«Вернуть»/«удалить») + забаненные карточки на графе (приглушённые). **Выкл** —
панель и карточки скрыты. Разбан в один клик, без подтверждения.

### 10.6. Фильтр и поиск

Фильтр категорий — граф показывает только товары категории; **ресурсы (нижний ряд)
видны всегда** (иначе рёбра обрываются). Поиск — инкрементальный по имени, только
карточки графа; пусто — оверлей «ничего не найдено». Фильтр/поиск **не влияют** на
детальную панель и палитру. Забаненные скрыты фильтром, пока не включён
переключатель.

### 10.7. Обратные рёбра — «что делается ИЗ этого товара»

Переключатель «обратные рёбра»: режим подсветки — у выбранного товара рисуются
обратные рёбра (родители → товар, отдельный цвет). Блок «Используется в:» в детали
виден всегда: список родителей, клик — переход к родителю (его деталь открывается,
«Используется в» обновляется — цикл навигации по графу).

### 10.8. ИИ-генерация

Кнопка «заполнить комплектующие»: enabled только при ≥1 пустом слоте и отсутствии
активной генерации (одна генерация, TryStart §7.1). Во время генерации —
глобальный индикатор «⚙ генерация… (модель M)» в шапке; кнопка disabled у всех
товаров. По завершении (авто-обновление §10.12) — карточки в слотах + тост-отчёт
(§7.4): «ИИ вернул больше запрошенного: N лишних — пропущены» / «ИИ предложил
забаненное: X — пропущено» / «Цикл: вставка X пропущена, слот пуст» / «Ошибка
разбора или таймаут — слоты остались пустыми». Клик при отсутствии пустых слотов —
тост «Сначала добавьте слот («+ слот»)».

### 10.9. Экспорт

Кнопка «Экспорт» → если warnings (§8) непусты — **модалка**: список предупреждений,
поле пути (опционально, дефолт `goods_data/export.json`), [Экспортировать всё равно]
[Отмена]; warnings пусты — экспорт сразу. После: тост «Экспорт записан: <путь>»
(+ warnings, если появились) или тост ошибки. Правило «только согласованные» (§11)
не меняется.

### 10.10. Состояния (глобальные)

| Состояние | Поведение |
|---|---|
| Загрузка (первичная) | спиннер/скелетон на графе; панели неактивны |
| Сеть потеряна (сервер перезапущен) | пилюля «нет связи, повтор через 3 с»; последние данные остаются, выбор не сбрасывается |
| Пустой реестр (нет товаров) | оверлей «Реестр пуст — добавьте первый товар» + CTA «+ товар» |
| Пустой результат поиска/фильтра | оверлей «ничего не найдено» |
| Ошибка действия (409 дубликат/цикл; 403 — старая студия: ресурс, в /studio: слот ресурсу) | тост с текстом сервера; состояние без изменений |
| Удаление товара | модалка «Удалить товар «X»? Слоты, ссылающиеся на него (N), очистятся» |
| Удаление непустой категории | тост «категория не пуста — сначала переместите товары» (409) |

### 10.11. Реактивность по действиям

| Действие | Результат |
|---|---|
| «+ слот» | новый пустой слот в детали; пипс на карточке |
| «заполнить комплектующие» | §10.8 |
| Согласовать / Исключить / Забанить | бейдж статуса обновляется; бан — карточка уходит (если выключен переключатель), появляется в списке забаненных |
| Вернуть | карточка возвращается в обычный вид; уходит из списка забаненных |
| «×» на слоте | слот очищен, товар остаётся в реестре |
| «удалить слот» | слот удалён целиком |
| Удалить товар | после подтверждения карточка исчезает; ссылавшиеся слоты очищены |
| drag & drop | §10.4 |
| Переключатель «забаненные» | панель и карточки — показать/скрыть (§10.5) |
| Фильтр / поиск | перерисовка графа; выбор и деталь не сбрасываются |
| «обратные рёбра» | подсветка обратных рёбер выбранного (§10.7) |
| Категории (добавить/переименовать/удалить) | перерисовка селектов; ошибки — тосты (§10.10) |

Все мутации — через API (§9), **без оптимистичных обновлений**: UI ждёт ответ,
дифф-рендер после.

### 10.12. Авто-обновление и память

Опрос `/api/state` каждые 3 с (`auto_refresh_ms`, §12.3); дифф-рендер не сбрасывает
выбор, зум, пан, открытые модалки. localStorage: активная категория, зум, позиция,
переключатели «забаненные»/«обратные рёбра».

### 10.13. Что не трогать (инварианты UI)

- **Статусы и семантика (§5.2):** бан/исключённое ИИ не предлагается — UI не обходит
  локальный фильтр (§7.4); разбан в один клик.
- **Тиры — производные от графа (§6.1):** UI только отображает, не хранит и не
  редактирует.
- **Количество в слоте (§6.4):** показ/ввод количества у слота — в детальной
  панели (99a.2 §6.5); на карточке графа не показывается (карточка = обзор).
- **Ресурсы без привилегий (§1.2 идеи переноса, С1/С3):** переименование/удаление/

- **DAG и уникальность имён (§6.2/§6.3):** UI показывает ошибки сервера, не обходит.
- **Одна активная генерация (§7.1):** повторный fill недоступен во время генерации.
- **Авто-обновление 3 с без сброса выбора (§12.3).**

## 11. Экспорт — JSON для игры

Кнопка «Экспорт» → `goods_data/export.json` (путь можно задать). **Только
согласованные товары** (решение §2, развилка 5). Загрузка в БД игры — будущий
мост (схема substances/resources — следующий релиз, 94a); в первой итерации
выгрузка вгружается **руками** (решение создателя 2026-09-18).

```json
{
  "schema_version": 1,
  "exported_at": "2026-09-18T12:00:00Z",
  "categories": [{"id": "c2", "name": "Конструкционные материалы"}],
  "goods": [
    {
      "id": "g42",
      "name": "Стальной каркас",
      "category": "c2",
      "complexity": 1,
      "recipe": [
        {"good_id": "res:zhelezo", "quantity": 1},
        {"good_id": "res:uglerod", "quantity": 1}
      ]
    }
  ],
  "resources": [
    {"id": "res:zhelezo", "name": "Железо Fe", "catalog": "real", "catalog_id": "zhelezo"},
    {"id": "res:uglerod", "name": "Углерод C", "catalog": "real", "catalog_id": "uglerod"}
  ],
  "warnings": []
}
```

- `complexity` = тир товара в графе (одно и то же, решение №4); поле названо
  термином игры (§11.1.1). База шкалы — ресурсы = тир 0 (решение создателя
  2026-09-18): в примере оба ресурса = 0 → complexity = 1 + max(0, 0) = 1
  (базовый товар из ресурсов). `quantity` = количество слота (дефолт 1, §6.4;
  реальное значение, ≥ 1).
- `categories` — категории студии выгружаются как есть (идентификаторы студии);
  маппинг на игровую модель §5.2.1 — будущий (первая итерация: без синхронизации,
  решение создателя 2026-09-18).
- `resources` — ресурсы, на которые ссылаются выгруженные рецепты, с источником
  каталога (layer/real + catalog_id) — мост резолвит их в ресурсную модель игры.
- `warnings` — вывод валидаторов (§8) при экспорте; выгрузка пишется, предупреждения
  видны в UI до записи (подтверждение).
- Расширяемость: окна свойств (корзина качества) добавятся полем `windows` на
  товар без слома `schema_version` (мажор — при изменении структуры).

## 13. DoD и критерии приёмки

**DoD разработки (AGENTS.md §2):** `go build ./...`, `go vet ./...`,
`go test -race ./...` (93a: `-race` доступен локально, gcc WinLibs). TDD: на
каждую фичу — автоматический тест (до кода красный, после — зелёный). Минимальный
набор тестов: round-trip `state.json` (атомарность, переживает рестарт); тиры
(цепочка, смешанные тиры, пустой рецепт = 0); циклы (прямой X→X, транзитивный
X→Y→Z + попытка Z→X — отклонение); дубликаты имён (нормализация, отклонение);
парсинг ответа ИИ (валидный JSON, K элементов, малый ответ, большой ответ —
первые K + отчёт, мусор, дроп бана/исключённого, цикл из ИИ-ответа — дроп
позиции, слот пуст); валидатор (листья-составляющие не покрытые каталогами —
кандидаты, верхушки — нет; неполные цепочки; ссылки на не-согласованных,
включая banned); экспорт (только согласованные, complexity = тир, quantity =
количество слота, warnings); защита порта (второй запуск падает).

**Критерии приёмки (проверка @tester после разработки):**
1. Создатель строит цепочку сверху вниз: товар-верхушка → «+ слот» → «заполнить
   комплектующие» вставляет карточки (по одной на слот) → отбор (согласовать/
   исключить/забанить).
2. Граф отображается рядами по тиру, zoom/drag работают; правая колонка
   «неиспользуемые» перетаскивается на слоты; переключатель «забаненные» показывает
   список по времени бана, разбан в один клик.
3. Цикл и дубликат имени невозможны (отклонение с сообщением).
4. Валидатор «каких ресурсов нет» считает по слою 20 + витрине 111.
5. Экспорт: только согласованные, complexity, quantity = количество слота,
   warnings; файл — валидный JSON.
6. Статусы/бан/граф переживают перезапуск студии.
7. Игровой сервер не затронут: `go build ./...` чистый, поведение `internal/resource`
   не менялось (только чтение существующих аксессоров).
8. UI-состояния и реактивность (§10.10–§10.11): загрузка/пусто/ошибка, товар без
   слотов, генерация ИИ (индикатор + отчёты §10.8), экспорт с warnings (§10.9);
   авто-обновление 3 с не сбрасывает выбор; ресурсы без привилегий (слоты
   недоступны); разбан в один клик.

## 14. Инварианты

1. **Один процесс, один порт 8799** — дубль невозможен (bind при старте, §12.1).
2. **Игровой сервер не трогается** — импорт `internal/resource` только читает
   существующие `LayerCatalog()`/`RealCatalog()`; правок сервера нет.
3. **Граф — DAG:** циклы исключены проверкой достижимости при каждом добавлении
   составляющей (§6.2).
4. **Имена товаров уникальны** (нормализация); дубликат отклоняется при создании/
   переименовании/вставке ИИ (§6.3).
5. **Тир выводится из графа, не хранится:** ресурс = 0, товар = 1 + max(тиры
   составляющих), пустой рецепт = лист = 0 (§6.1).
6. **Количество в слоте:** `quantity` (int, дефолт 1; нормализация <1 → 1 при
   загрузке); тир и валидаторы от количества не зависят (99a.2 §6).
7. **Статусы:** `draft`/`approved`/`excluded`/`banned`/`resource`; бан сортируется
   по `banned_at`, разбан в один клик; «неиспользуемые» — производное свойство,
   не статус (§5.2).
8. **Экспорт = только согласованные**; `complexity` = тир; слоты = заполненные
   (пустые не входят); `quantity` = количество слота (≥ 1); ресурсы — только те,
   на которые ссылаются выгруженные рецепты (§11).
9. **ИИ-ответы фильтруются локально:** бан/исключённое не вставляется (§7.4).
10. **Память переживает перезапуск** — `state.json`, атомарная запись (§12.2).
11. **Валидатор «каких ресурсов нет» — по слою 20 + витрине 111** (ограничение
    первой итерации; полевые ресурсы не видны, решение №2).
12. **Без роботов/построек/энергии:** студия не блокирует кодом — валидность
    глазами создателя (решение №6); третье правило §5.2.1 соблюдается отбором.
13. **Категории — свободное множество** (третий реестр поверх §5.2.1 и §9.1.3,
    осознанно); при первом старте предзаполнено 13 позициями §5.2.1 (стартовое
    удобство, решение создателя 2026-09-18); маппинг на §5.2.1 — будущий; студия
    не проверяет наличие потребителя (решение №5).
14. **Кандидат ГД-сущности (§16) в числа/механику не входит** (анти-двойной учёт).
15. **Ресурсы без привилегий (С1/С3, идея переноса §1.2):** `PUT`/`DELETE
    /api/goods/{id}`, status, tier для ресурса — разрешены; слоты недоступны
    (403 при POST slots). Старая студия блокировала 403 — легаси до C (§5.3, §9;
    в /studio — iterA §7).
