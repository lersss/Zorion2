## 1. Цель и скоуп

Перенести студию товаров с отдельного бинаря (`cmd/goods-studio`, state.json) на игровой
сервер (`cmd/server`): каталог товаров и ресурсов — в PostgreSQL, UI — на собственном URL
`/studio` (НЕ админка), доступ — JWT-роли admin/skycomposer. **Итерация A — каркас на БД**:
таблицы, сидер ресурсов, роуты, серверная логика на SQL, ресурсы без привилегий. UI к новому
API не подключается (итерация B), ИИ/импорт/экспорт/удаление старой студии — итерация C.

**В скоупе A:** таблицы `categories`/`goods`/`goods_slots` (миграция `000045`); сидер
= все 131 ресурс (слой 20 + витрина 111) + 6 ресурсных + 13 товарных категорий;
роуты `/studio/*` (JWT admin/skycomposer, статика из `web/`); перенос хендлеров студии
на SQL (CRUD товаров/категорий/слотов/статусов/тир-оверрайдов, bulk-подгрузка);
ресурсы без привилегий (создание/удаление/бан/переименование/тир-назначение; категория —
только ресурсные коды; слотов у ресурсов нет — 403); переиспользование чистых пакетов
`graph/`/`validate/` (перенос в `internal/goodsstudio/`); конкурентность (транзакции,
удаление с очисткой ссылок + count очищенных в ответе).

**НЕ в скоупе A (итерации B/C):** подключение UI к новому API (B); витрина «Реальные
вещества» 94a на чтение из БД (B); ИИ «заполнить комплектующие» (C); импорт
top-каталога/деревьев Т8 (C); экспорт (C); удаление `cmd/goods-studio` + `goods_data/` (C);
перевод читателей Go-каталога на БД (C); одна активная ИИ-генерация TryStart — только
заложена (C).

**Перенос пакетов (разв. 5):** `cmd/goods-studio/{model,graph,validate}` перемещаются в
`internal/goodsstudio/` (move, не копия — иначе коллизия имён файлов, AGENTS.md §4.9).
Старая студия продолжает работать: правятся только импорты
(`zorion/cmd/goods-studio/model` → `zorion/internal/goodsstudio/model` и т.д. — в
`model/state.go`, `handlers/*.go`, `catalog/*.go`, `ai/*.go`, `export/*.go`).
`catalog/`, `ai/`, `export/`, `model/state.go` (persist state.json) остаются в старой студии
до C — на сервер не переносятся.

**Почему не в `internal/handlers` напрямую:** graph/validate — доменная логика каталога,
не HTTP; отдельный пакет `internal/goodsstudio` — домен (паттерн `internal/ship`,
`internal/races`). Репозиторий и хендлеры — по стандартным местам проекта.

**Конкурентность (AGENTS.md §0):** каталог целиком в БД — общего in-memory состояния нет
(кроме будущего флага генерации, C). Каждая мутация — транзакция с `SELECT ... FOR UPDATE`
на изменяемом товаре (§9). `*rand.Rand` не используется. Будущая одна активная
ИИ-генерация — TryStart (заложено, §9.3).

## 4. Таблицы БД — миграция `000045_create_goods_catalog.sql`

### 4.1. `categories` — категории (товарные + ресурсные, единая таблица, разв. 3)

```sql
CREATE TABLE categories (
    id         BIGSERIAL PRIMARY KEY,
    name       TEXT NOT NULL,
    name_norm  TEXT NOT NULL GENERATED ALWAYS AS
               (lower(btrim(regexp_replace(name, '\s+', ' ', 'g')))) STORED,
    kind       TEXT NOT NULL CHECK (kind IN ('good', 'resource')),
    code       TEXT UNIQUE,              -- только для ресурсных: water/gas/mineral/organic/fuel/rare
    is_system  BOOLEAN NOT NULL DEFAULT false,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (kind, id),                    -- для составного FK из goods
    UNIQUE (kind, name_norm)              -- дубликаты имён в каждом пространстве отдельно
);
```

- **Товарные категории** (kind='good'): свободное создание (решение создателя 99a №5);
  сидер сеет 13 позиций §5.2.1 как стартовое удобство (продовольствие, топливо,
  конструкционные материалы, химикаты, полимеры, комплектующие, детали, медикаменты,
  товары быта, оборудование, оружие, броня, корабли и модули).
- **Ресурсные категории** (kind='resource'): ровно 6, системные (is_system=true),
  сидер создаёт из `internal/resource/categories.go` (code + русское имя).
  `code` — игровой код категории ресурса (маппинги `surfaceToCategories` и т.п. ссылаются
  на него). Переименование/удаление системной категории — 403 (код — константа игры).
- **Природа сущности** (архитектурный фильтр): справочник-состояние (как ship_models/
  equipment), не событие и не лог; владелец — глобальный каталог (один на сервер);
  расширяемость — kind открыт (второй тип категорий влезает в ту же схему).

### 4.2. `goods` — товары и ресурсы (единый каталог)

```sql
CREATE TABLE goods (
    id            BIGSERIAL PRIMARY KEY,
    name          TEXT NOT NULL,
    name_norm     TEXT NOT NULL GENERATED ALWAYS AS
                  (lower(btrim(regexp_replace(name, '\s+', ' ', 'g')))) STORED,
    category_id   BIGINT NOT NULL,
    kind          TEXT NOT NULL CHECK (kind IN ('good', 'resource')),
    status        TEXT NOT NULL DEFAULT 'draft'
                  CHECK (status IN ('draft', 'approved', 'excluded', 'banned')),
    source        TEXT NOT NULL DEFAULT 'manual'
                  CHECK (source IN ('manual', 'ai', 'palette', 'import')),
    tier_override INT NULL CHECK (tier_override IS NULL OR tier_override >= 0),
    banned_at     TIMESTAMPTZ NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    props         JSONB NULL,             -- только kind=resource (решение гейта 2026-09-19, §17)
    UNIQUE (name_norm),                   -- одно пространство имён: товар с именем ресурса невозможен
    FOREIGN KEY (kind, category_id) REFERENCES categories (kind, id),
    CHECK ((kind = 'good' AND props IS NULL) OR (kind = 'resource'))
);
```

- **Составной FK** `(kind, category_id) → categories(kind, id)` гарантирует на уровне БД:
  товар ссылается на товарную категорию, ресурс — на ресурсную (категория ресурса —
  только ресурсные коды, решение С5).
- **`name_norm`** — нормализация по правилу `graph.NormalizeName` (lowercase, trim,
  схлопывание пробелов) как generated-колонка + UNIQUE: дубликат имени невозможен даже
  при параллельных вставках (два админа создают «Железо» и «железо» одновременно).
  Приложение дополнительно возвращает 409 до вставки (человечное сообщение).
- **`status`** — 4 статуса (старый `resource`-статус упразднён: его роль выполняет
  `kind='resource'`). Сидер сеет ресурсы со `status='approved'` (ресурсы — база контента,
  экспорт = только approved; иначе 131 ресурс пришлось бы вручную согласовывать).
- **`props` JSONB** (только ресурсы, решение гейта 2026-09-19): 10 осей (0–100, ключи — русские
  имена осей из `layer.go`), `t_melt_k`/`t_boil_k` (Кельвины — внутренняя единица модели,
  PITFALLS «температура»), `family` (только real), `closes` (только layer),
  `bridge`/`supercritical` (только layer). Будущая модель substances (99.2.5) мигрирует
  из этой колонки. Без props витрина 94a в B не сможет читать свойства из БД (С1).
- **Природа сущности:** справочник-состояние; владелец — глобальный каталог;
  расширяемость — kind открыт, будущая экономика (`goods_batches`, `factories`) будет
  ссылаться на `goods.id` (стабильные BIGSERIAL, FK — при создании тех таблиц).

### 4.3. `goods_slots` — слоты рецептов (отдельная таблица, разв. 1)

```sql
CREATE TABLE goods_slots (
    id             BIGSERIAL PRIMARY KEY,
    good_id        BIGINT NOT NULL REFERENCES goods (id) ON DELETE CASCADE,
    pos            INT NOT NULL,          -- порядок слота в рецепте (0-based)
    component_id   BIGINT NULL REFERENCES goods (id) ON DELETE SET NULL,  -- NULL = пустой слот
    quantity       INT NOT NULL DEFAULT 1 CHECK (quantity >= 1),
    reason         TEXT NULL,             -- ИИ-обоснование (тултип)
    allow_resource BOOLEAN NOT NULL DEFAULT false,
    UNIQUE (good_id, pos)
);
CREATE INDEX idx_goods_slots_component ON goods_slots (component_id);
```

- **Почему таблица, а не JSONB** (разв. 1): (1) FK-целостность — component_id не может
  указывать на удалённый товар; (2) индекс по component_id — обратные рёбра
  («что делается из X», in-degree для «неиспользуемых» и валидатора) одним запросом;
  (3) параллельные правки разных товаров не конфликтуют (row-локи слотов), JSONB
  переписывал бы всю строку goods; (4) CHECK на quantity; (5) цикл-проверка (§9.2)
  читает весь граф одним SELECT.
- **`pos`** — порядок слота; перестановка слотов не нужна (в старой студии не было),
  вставка/удаление слота — сдвиг pos в той же транзакции.
- **Инвариант «у kind=resource слотов быть не может»** (решение создателя №1): CHECK не
  может смотреть в другую строку — enforcement в приложении (§9.1: 403 при POST slots
  ресурсу) + сидер/создание ресурса никогда не создают слоты. Нарушение невозможно
  по построению.

### 4.4. Прочее

- **`generation_config`** — маркер сидера: ключ `goods_catalog_seed`, payload
  `{"applied_at": "...", "resources": 131, "categories": 19}` (паттерн «дефолты в коде +
  override в БД», спека 99.2.3 §3; таблица уже есть, новая не нужна).
- **`truncateTables` (ClearUniverse) НЕ трогает** `categories`/`goods`/`goods_slots`:
  каталог — контент, не данные вселенной (в `admin_universe.go` не добавлять).
- **Имена колонок/таблиц** — в стиле проекта (snake_case, единственное число, без
  префиксов); `goods_slots` не конфликтует с будущей экономикой (каталог
  номенклатуры отделён от партий; `goods_batches` удалена, 000034 — не мешает).

## 5. Сидер ресурсов (Go, при первом старте; маркер в `generation_config`)

**Механика (разв. 2):** после `migrations.Apply(db)`, до старта HTTP — `goodsstudio.Seed(db)`:

1. `SELECT payload FROM generation_config WHERE key = 'goods_catalog_seed'` — есть → пропуск.
2. В одной транзакции:
   - 6 ресурсных категорий (kind='resource', is_system=true, code из `resource.AllCategories`,
     имя из `resource.Categories`);
   - 13 товарных категорий §5.2.1 (kind='good');
   - 131 ресурс: `LayerCatalog()` (20) + `RealCatalog()` (111) — name, категория (код),
     kind='resource', status='approved', source='palette', props JSONB (§4.2), created_at=NOW();
   - маркер в `generation_config` (ключ `goods_catalog_seed`).
3. Ошибка транзакции → `log.Fatal` (сервер без базового каталога не стартует — как
   `migrations.Apply`; альтернатива «лог и продолжить» отклонена решением гейта 2026-09-19).

**Свойства сида (инварианты):**
- **БД — источник правды (С1):** Go-каталог — только первичное наполнение. При повторных
  стартах сид не запускается (маркер). Правки студии (имя/категория/тир/статус/бан) из БД
  Go-каталогом НЕ перезаписываются.
- **Удалил ресурс в студии — не возвращается:** маркер не даёт повторному сиду вернуть
  удалённое (вариант «если таблица пуста» отклонён именно за это).
- **Обновление Go-каталога после сида не происходит** — осознанно (С1): новые ресурсы
  создаются в студии (кнопка «+ ресурс»), а не правкой layer.go/real.go. Если создатель
  захочет досеять из Go-каталога — отдельное ручное действие (вне A).
- Сид идемпотентен по маркеру; повторный прогон (маркер удалён вручную) упадёт на
  UNIQUE-конфликтах — безопасно (транзакция откатится).

## 6. Роуты и доступ — `/studio/*`

Регистрация в `cmd/server/main.go` (паттерн админки, `auth.AdminAuth` = admin+skycomposer):

```go
studioHandlers := handlers.NewStudioHandlers(db)

// API — только admin/skycomposer
http.HandleFunc("/studio/api/state",      auth.AdminAuth(studioHandlers.State))
http.HandleFunc("/studio/api/resources",  auth.AdminAuth(studioHandlers.Resources))
http.HandleFunc("/studio/api/categories", auth.AdminAuth(studioHandlers.Categories))
http.HandleFunc("/studio/api/categories/", auth.AdminAuth(studioHandlers.CategoryByID))
http.HandleFunc("/studio/api/goods",      auth.AdminAuth(studioHandlers.Goods))
http.HandleFunc("/studio/api/goods/",     auth.AdminAuth(studioHandlers.GoodByID)) // + status/tier/slots/bulk
http.HandleFunc("/studio/api/validate",   auth.AdminAuth(studioHandlers.Validate))

// Статика — публичный HTML (паттерн /admin), данные закрыты API
http.Handle("/studio", noCache(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    http.ServeFile(w, r, "./web/studio.html")
})))
http.Handle("/studio/", noCache(http.StripPrefix("/studio/", http.FileServer(http.Dir("./web/static/studio")))))
```

**Как авторизовать статику и API (вопрос идеи §4):**
- **API** — за `auth.AdminAuth` (JWT Bearer, роли admin/skycomposer; player → 403,
  аноним → 401). Это и есть защита данных каталога («на проде открывать нельзя»).
- **HTML-страница** — публична (как `/admin`, `/map`, `/contracts`): браузерная навигация
  не умеет кастомных заголовков, JWT лежит в localStorage (`adminToken`, паттерн

  Альтернатива «закрыть HTML серверно» требует cookie-авторизации, которой в проекте нет —
  отклонено.
- **Статика из `web/`, не embed** (решение идеи; PITFALLS «студия embed'ит HTML»):

## 8. Валидация, граф, тиры

### 8.1. Переиспользование чистых пакетов

`internal/goodsstudio/graph` и `internal/goodsstudio/validate` используются **как есть**
(перенос §3) с двумя правками под решения создателя: `graph.EffectiveTier` (§8.2, С3) и
исключение ресурсов из валидаторов по kind (§8.3, критика №1). Они оперируют `model.Good`
(в памяти) — репозиторий собирает снимок каталога из БД (все goods + все slots, порядок
по pos) в одной транзакции чтения (REPEATABLE READ — согласованный снимок без «рваных»
пар goods/slots), маппит в `[]model.Good` и вызывает чистые функции. Масштаб каталога (сотни
товаров × единицы слотов) — полный снимок на запрос дёшев (старая студия делала то же
с state.json).

### 8.2. Тир (ПРАВКА чистого пакета — решение С3)

Формула (99a.1 §6.1, без изменений):
```
тир(ресурс)            = 0
тир(товар)             = 1 + max(тиры заполненных слотов)
тир(товар с пустым рецептом) = 0
тир_эффективный        = tier_override ?? вычисленный
```

**Изменение `graph.EffectiveTier`** (сейчас: ресурс → 0 всегда, оверрайд игнорируется):
```
if g.TierOverride != nil { return *g.TierOverride }   // сначала оверрайд — теперь и для ресурсов (С3)
if g.Kind == KindResource { return 0 }
return Tier(g, byID)
```
`Tier` (вычисленный) не меняется: ресурс = 0 (рецепта нет). Оверрайд не влияет на
структуру графа (промпт ИИ, валидаторы — по вычисленному). Правка применяется к
`internal/goodsstudio/graph` — старая студия получает то же поведение (консистентно).
Тест: ресурс с tier_override=3 → EffectiveTier=3, Tier=0.

### 8.3. Валидаторы (99a.1 §8 + ПРАВКА: ресурсы по kind, критика №1)

**Правка (среднее критика №1):** ресурсы исключаются из валидаторов по kind — иначе
сид посеял бы 131 approved-ресурс без слотов, и каждый флагался бы как «неполная цепочка»:

1. «Каких ресурсов нет» — листья с in-degree > 0, не покрытые каталогами
   (в БД «покрытие» = kind=resource — логика та же, источник данных — БД);
   ресурсы пропускаются (как в оригинале);
2. неполные цепочки (approved без заполненных слотов) — **пропускать kind=resource**
   (ресурс — лист по определению, пустой рецепт не «недострой»);
3. ссылки на не-согласованных (draft/excluded/banned составляющие approved товара) —
   **пропускать составляющие kind=resource** (ресурс — валидный лист независимо от
   статуса; его статус управляет экспортом, а не структурой ссылки);
4. страховки: цикл (ресурс — лист, в цикле участвовать не может — проверка по товарам),
   дубликат имени (общее пространство имён, проверка остаётся на всех).

Правка применяется к `internal/goodsstudio/validate` — старая студия получает то же
поведение (консистентно).

## 9. Конкурентность (С4)

### 9.1. Транзакции

Каждая мутация — `BEGIN` … `COMMIT`. **Глобальная сериализация мутаций каталога** —
`pg_advisory_xact_lock(<фиксированный ключ каталога>)` в начале каждой мутации
(одна мутация за раз на каталог; каталог — контент-инструмент с низкой частотой записи,
потери параллельности нет; закрывает TOCTOU между «проверил ссылки» и «очистил» — среднее
критика №3). Внутри — `SELECT ... FOR UPDATE` для явной блокировки строк и согласованности
снимков (цикл-проверка). Примеры:

- **PUT slot:** tx → advisory lock → `SELECT kind FROM goods WHERE id=$1 FOR UPDATE`
  (403 если resource) → загрузка графа в tx (все goods+slots) →
  `graph.WouldCreateCycle(component, good)` (409) →
  `UPDATE goods_slots SET component_id=$x, reason='' WHERE good_id=$1 AND pos=$n` → COMMIT.
- **DELETE good:** tx → advisory lock → `SELECT id FROM goods WHERE id=$1 FOR UPDATE`
  (удаляемая строка; нет — 404) → `UPDATE goods_slots SET component_id=NULL, reason=''
  WHERE component_id=$1` (очистка ссылок в той же транзакции; `RowsAffected` = N) →
  `DELETE FROM goods WHERE id=$1` (каскад на свои слоты) → COMMIT →
  ответ `{deleted: id, cleared_links: N}`. Очистка и удаление атомарны: между ними никто
  не вставит новую ссылку на удаляемый товар (advisory lock + FK ON DELETE SET NULL как
  страховка).
- **POST good:** tx → advisory lock → проверка `name_norm` (409) → INSERT → COMMIT.
  UNIQUE-индекс — страховка от гонки двух вставок (ошибка БД → 409).

### 9.2. Циклы

Проверка достижимости (DFS, `graph.WouldCreateCycle`) выполняется **внутри транзакции** на
снимке графа из той же tx — между проверкой и UPDATE никто не вставит ребро
(advisory lock на мутацию + FOR UPDATE на родителе). Граф — DAG по построению;
валидатор — страховка.

### 9.3. Одна активная ИИ-генерация — заложено

В A генерации нет (fill — C). Закладка: поле `generating` в StateView (всегда false в A),
контракт `/studio/api/goods/{id}/fill` зарезервирован; в C — TryStart (не `if running +
Start`) по паттерну старой студии (§7.1) и `StatusManager` (ARCHITECTURE §0).

## 12. Инварианты

1. **БД — источник правды каталога (С1):** Go-каталог — только сид; повторные старты
   не перезаписывают правки студии; удалённый ресурс не возвращается.
2. **Ресурс — лист:** слотов у kind=resource нет (403 при добавлении; сидер/создание
   ресурса не создают слотов).
3. **Категория соответствует kind:** составной FK `goods(kind, category_id)`; ресурс —
   только в одну из 6 ресурсных категорий (С5), товар — только в товарную.
4. **Имена уникальны** в одном пространстве (товары+ресурсы): `name_norm` UNIQUE на
   уровне БД + 409 в приложении (нормализация 99a.1 §6.3).
5. **Граф — DAG:** цикл исключён проверкой достижимости в транзакции (409); валидатор —
   страховка.
6. **Тир:** вычисленный — ресурс=0, товар=1+max(слоты), пустой рецепт=0; эффективный —
   override ?? вычисленный, **оверрайд работает и для ресурсов (С3)**; тир не хранится
   (кроме оверрайда).
7. **Статусы:** draft/approved/excluded/banned (статус `resource` упразднён — kind);
   бан — banned_at, разбан в один клик (unban → draft); «неиспользуемые» — производное.
8. **Экспорт = только approved** (правило сохраняется для C; сид сеет ресурсы approved).
9. **Удаление товара очищает ссылки на него** в слотах других товаров (component_id → NULL,
   reason → '') **в той же транзакции**; ответ несёт `cleared_links` (count); удаление
   атомарно (advisory lock + FOR UPDATE, TOCTOU закрыт); ресурсы удаляются как товары.
10. **Каталог — контент, не данные вселенной:** ClearUniverse его не трогает.
11. **Каталог не очищается миграциями и не пересоздаётся** — только точечные правки API.
12. **Одна активная ИИ-генерация** — заложено (C, TryStart).
13. **Кандидат ГД-сущности (§14) в числа/механику не входит** (анти-двойной учёт).

  это **видимость** каталога (информационный товар среднего слоя, рынок отчётов
  `10_exploration.md` §10.3), чертежи — **разблокировка** производства (дискретная
  возможность). Перенос студии на сервер делает атлас естественным: данные уже в БД игры,
  нужен только срез + механика продажи.
  **Вопрос:** где и как игрок получает «Промышленный атлас» (покупка у фракций, разведка,
  контракты) и что он показывает (полный каталог, тиры, рецепты — или только категории)?
  **Ответ (эталон создателя):** эталон не задан (2026-09-19) — открытый вопрос.
  **Зависимость:** реализация — отдельная фича, после переноса студии (B/C); в числа этой
  спеки не входит.
