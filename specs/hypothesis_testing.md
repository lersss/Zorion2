## 1. Проблема: пресеты не изолируют гипотезу

Пресеты генерации поселений (`web/static/js/admin/settlementPresets.js`) сейчас работают как **фильтры сверху**: берут случайную вселенную и отбирают планеты по правилам (AND по полям `planet.data`). Ловушка:

**Пример «Горячие ядра» (`young_worlds`).** Правило одно: `system_age ∈ [0.1, 2]`. Но:

1. Внутри пула — всё разнообразие вселенной: газовые гиганты, лед, радиоактивные, жара, сушь. Все эти оси доминируют над дельтой населения сильнее, чем возраст ядра. Гипотеза «геотермальный ресурс держит фронтир» на таком пуле не читается: дельта — конгломерат десятков эффектов.
2. Корреляция «возраст → температура» зашита в сам генератор:
   - `internal/generator/planet/core.go:185` — `ageFactor = max(0.15, 1 − Age/15)`: молодое ядро греет в разы сильнее (вклад в температуру у Age=1 в ~2.8 раза больше, чем у Age=10);
   - `determineSystemAge` (`planet_data_generate.go:28`) берёт возраст от спектрального класса, а спектр задаёт и светимость (`luminosityBySpectral`, `physics.go:213`) → равновесную температуру.

То есть «молодость» в данных уже тащит за собой «жару» — фильтр по возрасту неявно фильтрует и по температуре.

**Вывод (решение игрока 2026-09-13):** генератор поселений не трогать. Вместо фильтрации — **генерировать выборки снизу вверх**: строить планеты по плану осей, добиваясь нужного распределения по каждой оси независимо от корреляций природного генератора. Это полноценный инструмент анализа, на постоянное место в админке.

**Критерий успеха:** вкладка «Проверка гипотез» даёт возможность для любой из 12 гипотез построить «эксперимент + контроль» — два пула с идентичными осями, кроме одной варьируемой, и поселения с заданной стратегией населения. Пул строится генерацией, а не фильтром.

## 2. Цель и не-цели

### Цель

1. **Параметрический генератор планет** — Go-модуль, который генерирует планеты по плану осей: каждая ось `planet.data` может быть «естественной» (природное распределение), пришпилена к значению или ограничена диапазоном. Умеет разрывать естественные корреляции.
2. **Подсистема «Проверка гипотез»** — отдельная вкладка в админке: очистка галактики (миры + планеты + поселения), генерация миров/планет/поселений по пресету выбранной гипотезы, прогресс/отмена, тег группы в данных планет для будущего анализа дельты.

### Не-цели

- **Не** переписывать природный генератор вселенной (`GeneratePlanetsForWorlds` и его путь) — остаётся как есть.
- **Не** реализовывать экономику/дельту населения (`13_tiers_impl.md`) — инструмент строит **тестовый полигон** (миры + планеты + стартовое население поселений); чтение дельты — следующий этап, уже поверх этого полигона.
- **Не** создавать заводы/товары для эксперимента: гипотезы сформулированы вокруг населения, заводы — отдельная ось и остаются за рамками (ср. `STATUS.md` §3 п.4 — «удалить старую логику генерации заводов»).
- **Не** сохранять историю экспериментов в БД. Универсум транзиентный: следующий прогон перетирает предыдущий (это осознанный выбор — см. §7 «Открытые вопросы»).

## 3. Параметрический генератор планет

### 3.1. Где живёт

Внутри пакета `internal/generator/planet` (новые файлы), **не** отдельный пакет: нужен доступ к неэкспортированным помощникам физики (`computeSurfaceTemp`, `computeGravity`, `computeRadius`) и композиции. Природный путь генерации не трогаем, но общие примитивы переиспользуем.

Предлагаемые файлы (помнить правило «файл > 200–300 строк — разделить», `AGENTS.md` §4.8):

- `parametric.go` — `ParamSpec`, `AxisSpec`, `GroupSpec`, драйвер `GenerateControlledPlanetsGroup` / `GenerateControlledPlanets`.
- `parametric_exec.go` — исполнение плана оси: как из `AxisSpec` получить значение (естественный розыгрыш / пин / диапазон) и как пересчитать зависимые поля после пинования.
- `parametric_world.go` — генерация миров под группу (возраст системы, спектр, число планет на мир).
- `parametric_test.go` — тесты (§8).

### 3.2. План осей (`AxisSpec`)

JSON-контракт (это же идёт с фронта):

```jsonc
{
  "axes": {
    "system_age":     { "min": 0.1, "max": 2.0 },   // диапазон (равномерно)
    "temperature":    { "value": 300 },              // пин (в Кельвинах!)
    "water_percent":  null,                          // null / отсутствие ключа = естественный розыгрыш
    "is_gas_giant":   { "is": false },               // bool-пин
    "atmosphere":     { "in": ["азотно-кислородная"] } // стринг-пин (один из допустимых)
  },
  "count": 300
}
```

Семантика **pin**: ось фиксируется до вызова природного розыгрыша.
Семантика **range**: генератор розыгрывает значение равномерно в диапазоне, затем трактует его как пин (каскад вниз).
Семантика **естественный**: текущее поведение — значение из архетипа/композиции.

Реестр допустимых осей и типов — уже существует: `internal/generator/settlement/fields.go` (`FieldSpecKey`). Параметрический генератор работает с теми же ключами `planet.data`. Для скорости фронт и бэкенд используют один и тот же перечень полей (`GET /admin/settlement-fields`).

### 3.3. Каскад зависимостей и разрыв корреляций

Порядок розыгрыша в природном генераторе (`GenerateProperties`, `properties.go:31`):

```
mass → (surface preliminary) → density → size
     → subterrain → core → temperature (luminosity, orbit, albedo, greenhouse, core heat)
     → water (archetype.Hydrosphere, temp)
     → life (biosphere, water, temp)
     → moons, political, conflict, development
type ← classify(surface, temp, water, life, settleable)
system_age ← world (задаётся миром в generatePlanet)
```

Пинование оси **перезаписывает** значение в этом каскаде, а **зависимые** поля пересчитываются от припиненного значения:

- `mass` зашит → `density`/`size`/`gravity` пересчитываются (gravity = `mass / size²`, `physics.go`);
- `temperature` зашита → вода/жизнь/тип зависят от неё (`generateWater`, `generateLife`, классификация) — пересчитать их от новой температуры;
- `system_age` зашит → `core.Age` = этому значению (`core.go:61`), `HeatContribution` считается от него;
- `life`, `atmosphere`, `hydrosphere`, `biosphere` припинены → снимается зависимость «естественно выпало из конфига архетипа».

**Разрыв корреляции «возраст → температура» (ключевой кейс).** Для эксперимента по возрасту нужны пулы с **одинаковой температурой при разном возрасте**. Текущий каскад связывает их через ядро. Средство:

- `system_age` и `temperature` объявляются **независимыми осями** в плане;
- при расчёте температуры внутренний нагрев ядра **исключается через флаг** (аналог `SkipInternal` в `physics.go:150`, сейчас задействован только для газовых гигантов) — то есть температура приписывается только светимости/орбите/альбедо/парнику;
- `system_age` остаётся видимым в `data` и в `core`, но не влияет на температуру поверхности: его будущий экономический эффект — геотермальная ветка, которую потом читает дельта (§1).

**Механика реализации:** в инпут `computeSurfaceTemp` добавляется поле-надстройка «use_core_heat bool` (или `CoreHeatOverride float64`). В параметрическом режиме при припиненной температуре: `use_core_heat=false`; ядро генерируется **с заданным возрастом**, но на температуру не влияет. Это честнее, чем молча «отрезать» ядро: гипотеза «горячие ядра» в формулировке пресета опирается на геотермальную **энергию**, а не на нагрев поверхности — поверхность держим равной по пулам.

### 3.4. Драйвер

```go
// parametric.go
type ParamSpec struct {
    // Группы — «эксперимент» и «контроль» в терминах игрока (две и более).
    Groups []GroupSpec `json:"groups"`
}

type GroupSpec struct {
    ID      string              `json:"id"`   // машиночитаемый: "young", "old"
    Name    string              `json:"name"` // читаемый для вкладки
    Axes    map[string]AxisSpec `json:"axes"` // план осей (см. 3.2)
    Count   int                 `json:"count"`
    // Миры группы: сколько звёзд и планет на мир (см. §4.2).
    Worlds         int `json:"worlds"`
    PlanetsPerWorld int `json:"planets_per_world"`
}

func (g *Generator) GenerateControlledPlanets(spec ParamSpec, progressFn func(g, processed int)) (map[string]PlanGroupResult, error)
```

Возврат: статистика по группе (число миров, планет, сколько из них пригодно/заселено) + теги.

### 3.5. Тег группы в данных

Каждая сгенерированная планета дополнительно получает в `planet.data`:

```json
"_experiment": { "id": "young_worlds", "group": "young" }
```

Это единственная «память» об эксперименте в БД. Нужно для будущего SQL-анализа дельты: `WHERE data->>'group' = 'young'`. Миграция не нужна — поле в JSONB. (Осознанно: свой отдельный столбец не заводим, пока анализ в SQL работает с `data`.)

## 4. Подсистема «Проверка гипотез»

### 4.1. Бэкенд

Новый файл `internal/handlers/admin_hypothesis.go`. Паттерн — как у существующих генераторов (`admin_universe.go` / `admin_settlements.go`):

- новый тип джобы `generator.JobHypothesis` в `internal/generator/status.go`;
- `statusManager` уже умеет `TryStart / Progress / Done / Fail / Cancel` — переиспользуем;
- блокировка повторного запуска (`409 Generation already running`) как у остальных.

**Конвейр запуска (в фоновой горутине):**

1. `clearUniverseTx` — та же очистка, что в `GenerateUniverse` (`admin_universe.go:56`): TRUNCATE без CASCADE + явный список таблиц + временное снятие FK `users`. Она уже сносит миры, планеты, поселения, заводы, товары, фракции, регионы — ровно «очистить галактику».
2. Генерация миров по группам (`parametric_world.go`).
3. `GenerateControlledPlanets` для всех групп.
4. Поселения: для каждой планеты группы применяется стратегия населения группы (см. 4.3), вставка только в `settlements` (`uuid, planet_id, population, stability`).
5. После успеха — `h.recomputePlanetStats()` и `h.mapCache.LoadAsync(h.db)` (обязательно, иначе карта/статистика устареют).

### 4.2. Миры группы

Для гипотезы «горячие ядра» нужны миры с молодым возрастом системы. Группа несёт свои параметры мира:

```jsonc
"worlds":  60,             // миров в группе
"planets_per_world": 5,    // планет на мир → 300 планет в группе
"world": { "system_age": { "min": 0.1, "max": 2 } }
```

- `world.system_age` — пин/диапазон возраста, обходит `determineSystemAge` (возраст больше не выводится из спектра).
- Спектр мира — обычный розыгрыш (`randomSpectralClass`, `galaxy.go`), если не припинен `world.spectral_class`.
- Вставка миров — как в `GenerateUniverse` (INSERT в `worlds`).
- Координаты миров — равномерно по карте `MapSize` (простой разброс; кластеризация тут не нужна — карта и эксперимент не пересекаются). Регионы не создаём.

**Связка возраст системы → температура планеты из §3.3:** на уровне миров это ок — возраст мира пишется в планеты группы, а температура планет управляется планом осей (ядерный нагрев выключен). Это и есть честный эксперимент.

### 4.3. Поселения

Стратегия населения — текущая из модели генерации (`settlement/model.go`, стратегии `fixed`/`random`), но **без правил**: планета уже сгенерирована точно под группу, фильтровать нечего.

```jsonc
"settlement": {
  "chance": 1.0,
  "population": { "kind": "random", "min": 10000, "max": 300000000 }
}
```

- `chance` — шанс заселения планеты группы (как в simple-режиме модели).
- Население пишется напрямую (тот же `buildSettlement`-паттерн), **не** через `settlement.Generator.GenerateSettlements` — тот умеет только глобальный проход по всем планетам, а тут население задаётся по группе.
- Заводы и товары не создаются (см. §2 «Не-цели»).

### 4.4. Endpoint

```
POST /admin/hypothesis/run
{ "hypothesis": "young_worlds" }        // берём пресет гипотезы из конфига
→ 202 { "status": "started" }
→ 409, если другой джоб уже крутится
```

Пресеты гипотез — **в коде** (JS на фронте + зеркало плана в Go), не в БД: повторяем подход `settlementPresets.js`.

`GET /admin/hypothesis/status` — переиспользуем `GenerateStatus` с `job=hypothesis`.

### 4.5. Фронт

- Новая вкладка в `web/admin.html` «🧪 Гипотезы» (рядом с «Поселения»).
- Новый файл `web/static/js/admin/hypothesisPresets.js` — пресеты гипотез: для каждой из 12 гипотез — имя, текст гипотезы (переносим из `settlementPresets.js` `hypothesis`), **две группы** (эксперимент и контроль), план осей каждой группы (§3.2, температуры в °C на форме → в K на сервере, как в `buildSettlementModel`), параметры миров и поселений.
- Новая форма: селект гипотезы → превью плана (две группы, их оси, входная и контрольная точки) → кнопка «Запустить эксперимент» (с подтверждением «вселенная будет перетёрта») → прогресс/отмена/результат (числа планет и поселений по группам).
- `web/static/js/admin/generation.js` — вёрстка/логика формы по образцу блока поселений; `loadSettlementFields`-аналог для выбора осей не нужен (оси заданы пресетом), но на превью можно показать только их.

## 5. Формат пресета гипотезы (пример «Горячие ядра»)

```jsonc
{
  "id": "young_worlds",
  "name": "Горячие ядра",
  "hypothesis": "Гипотеза возраста: возраст системы — скрытый запас энергии...",
  "groups": [
    {
      "id": "young",
      "name": "Молодые (0.1–2 млрд лет)",
      "worlds": 60, "planets_per_world": 5,
      "world": { "system_age": { "min": 0.1, "max": 2 } },
      "axes": {
        "temperature":    { "min": 273, "max": 303 },   // K; одинаковые в обеих группах
        "is_gas_giant":   { "is": false },
        "radioactive":    { "is": false },
        "water_percent":  { "min": 10 }
      },
      "settlement": { "chance": 1.0, "population": { "kind": "random", "min": 10000, "max": 300000000 } }
    },
    {
      "id": "old",
      "name": "Старые (6–13 млрд лет)",
      "worlds": 60, "planets_per_world": 5,
      "world": { "system_age": { "min": 6, "max": 13 } },
      "axes": { /* те же, что у young */ },
      "settlement": { "chance": 1.0, "population": { "kind": "random", "min": 10000, "max": 300000000 } }
    }
  ]
}
```

Только `world.system_age` и температура пулов — припинены одинаково; остальные оси, припиненные в young, дублируются в old (**правило «близнецов»**: контроль повторяет план эксперимента с точностью до варьируемой оси).

## 6. Порядок работ (этапы)

Следуем приоритету из решения игрока («сначала генератор, потом вкладка»):

1. **Параметрический генератор планет** (Go): `AxisSpec` + каскад + разрыв «возраст → температура» (`parametric*.go`). Выход: `GenerateControlledPlanets` собирает `[]*PlanetData` с тегом `_experiment`. Проверка: тесты §8 (1–4).
2. **Миры под группу** (`parametric_world.go`) + вставка миров. Проверка: тест 5.
3. **Конвейр «Проверка гипотез»** (`admin_hypothesis.go`): джоб, очистка, генерация, поселения, кэши. Проверка: sqlmock-тесты 6–7 + ручной прогон в админке.
4. **Фронт**: `hypothesisPresets.js`, вкладка, форма, прогресс. Проверка: ручной прогон на dev-БД, `node --check`.
5. **DoD** (`AGENTS.md` §2): `go build ./...`, `go vet ./...`, `go test ./...` (+ ручной, из-за локального исключения `-race`): прогнать эксперимент «Горячие ядра», проверить в БД две группы с равными температурами и разным `system_age`.

## 7. Открытые вопросы

1. **Перетирание универсума.** Эксперимент сносит текущую вселенную (в dev — прототип-планета; ловушка «вселенная очищена»). Приемлемо для инструмента анализа? (Вероятное решение — да; игрок подтверждает в диалоге перед запуском.)
2. **Числа групп/миров.** Дефолт группы 60 миров × 5 планет = 300 планет — достаточно ли для статистики дельты? Калибровать на первом прогоне.
3. **Геотермальная ветка.** «Разрыв» в §3.3 отключает нагрев ядра для температурной изоляции, но тогда гипотеза «геотерма держит фронтир» опирается на будущий экономический слой. Верно ли, или для §13.8 нужен атрибут `core.age`/`heat` на планете как **вход** в формулу прироста?
4. **Корреляция «старые ≠ холоднее» в реальных данных.** Текущая БД (зоопарк прошлой перегенерации) — про случайный пул: фильтром возраст коррелируется с жарой. Это аргумент за параметрику, а не за фильтр. Фиксировать в выводах.
5. **Имя джобы/поля тега.** `hypothesis` vs `experiment`, `group` vs `pool` — зафиксировать термины один раз (влияет на SQL-запросы анализа и на будущую экономику).

## 8. Тесты

Пишутся вместе с фичей (`AGENTS.md` §4.12):

| # | Что проверяет |
|---|---|
| 1 | Пин оси `temperature` даёт температуру в заданном диапазоне у всех планет группы |
